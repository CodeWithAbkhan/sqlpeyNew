“Generating C/C++ Assembly Code with GCC and Alternatives”

Obtaining the assembly representation of high-level source code is crucial for deep performance tuning, security auditing, or simply appreciating how the compiler translates constructs. Several robust techniques exist, primarily centered around the GNU Compiler Collection (GCC) and related binutils.

Direct Assembly Generation with GCC/G++

The primary mechanism to instruct GCC or G++ to halt compilation after the assembly stage (before the assembler runs) is the -S flag.

Basic Assembly Output

Using -S outputs the assembly instructions to a file with a .s extension, corresponding to the input source file.

For a C file named routine.c:

gcc -S routine.c
# This creates routine.s

If you are working with C++ sources, substitute gcc with g++:

g++ -S service.cc
# This creates service.s

This technique only works if the original source file is available. You can also explicitly specify the output file name using -o:

gcc -S -o custom_output.s main_program.c

To send the output directly to standard output (useful for piping), use -o -:

gcc -S main_program.c -o - | less

Enhanced Assembly Output with Verbosity and Debug Info

To get assembly output that is easier to map back to the original source, specific flags can be combined with -S.

  1. Interleaving Source Lines: The -fverbose-asm option integrates comments showing the original C names and line numbers within the assembly, which greatly aids readability, especially at low optimization levels like -O0.

    g++ -S -fverbose-asm -g -O2 complex_calc.cc -o complex_calc.s

  2. Maximizing Source Interleaving: A more aggressive approach involves piping the initial assembly through the assembler (as) with specific flags to produce a detailed listing file that includes source lines as comments. This is often used in conjunction with debug flags (-g).

    # Generate assembly with verbose ASM and debug info
g++ -S -fverbose-asm -g -O2 test.cc -o test.s

# Create a detailed listing file interlaced with source lines
as -alhnd test.s > test_listing.lst

Disassembling Existing Object Files with objdump

If you only possess an object file (.o) or an executable (not the source), objdump becomes the necessary tool. The -S option tells objdump to interleave source lines with the disassembly, provided the object file was compiled with debug information enabled (using -g).

# Assuming 'my_module.o' was compiled with 'gcc -c -g my_module.c'
objdump -S --disassemble my_module.o > module_analysis.dump

Useful objdump Refinements:

  • Intel Syntax: If you prefer Intel syntax over the default AT&T syntax for x86 architecture: 
    objdump -drwC -Mintel -S foo.o | less
    • -d: Disassemble sections that contain executable code.
    • -r: Show relocations (useful for .o files).
    • -w: Disable line wrapping.
    • -C: Demangle C++ names.

Preserving Intermediate Build Files with -save-temps

When integrating assembly generation into an existing build system (like a Makefile or CMake configuration), using -S might break subsequent compilation steps. The -save-temps option is a cleaner alternative as it allows the compilation to proceed to the object file while saving the preprocessed (.i), assembly (.s), and (optionally) object (.o) files.

If you compile a file named data_proc.c:

gcc -save-temps -c -o build/data_proc.o data_proc.c

This command results in:

  • build/data_proc.o (The final object file)
  • data_proc.i (Preprocessed source)
  • data_proc.s (Assembly code)

Managing Output Locations: To prevent naming conflicts when compiling multiple files, use -save-temps=obj. This forces the intermediate files (.i, .s) to be placed alongside the specified object file output path.

gcc -save-temps=obj -c -o build/sub/module.o sub/module.c
# Intermediate files created in build/sub/

Viewing the explicit steps taken by GCC during compilation is simplified by adding the verbose flag (-v) alongside -save-temps:

gcc -save-temps -c -o main.o -v main.c
# Output shows paths to cc1 (C compiler frontend), as (assembler), etc.

Alternative Tooling and Environments

  1. Compiler Explorer (Godbolt): For immediate visualization without managing local files, Matt Godbolt’s Compiler Explorer is invaluable. It shows live, side-by-side comparisons of source code against assembly output from various compilers and optimization levels. You can also clone and run this project locally via its GitHub repository .

  2. LLVM Assembly: If targeting the LLVM toolchain, you can instruct llvm-gcc (or relevant clang/llvm tools) to output LLVM’s intermediate representation (IR) assembly:

    llvm-gcc -emit-llvm -S hello.c

  3. Intermediate GCC Forms: Exploring GCC’s internal representation before final assembly generation can offer insight into optimization passes. Flags like -fdump-tree-all reveal various stages of the GIMPLE and TREE structures.

  4. Runtime Inspection with GDB: If you have an executable, the GNU Debugger (gdb) allows disassembly of functions at runtime.

    gcc program.c
gdb ./a.out

(gdb) disass main  # Disassemble the 'main' function

  5. Post-Processing Scripts: For users who strongly prefer NASM syntax over AT&T syntax, external Perl scripts exist that can process the output of objdump -M intel to clean up syntax artifacts, such as the script provided that replaces verbose pointer notations.

FAQs on Generating C Assembly Code

Q: What is the simplest command to get assembly output from a C file

ANS: The simplest method is using the GCC -S flag: gcc -S sourcefile.c. This generates sourcefile.s.

Q: How do I ensure the assembly output clearly maps to my source lines

ANS: Combine the -S flag with -fverbose-asm and potentially the -g debug flag. For maximum source annotation, process the .s file using the assembler with listing options, for example, as -alhnd source.s > listing.lst.

Q: Can I see assembly if I only have the object file and no source code

ANS: Yes, use objdump with the -S option, like objdump -S source.o. This works best if the object file was compiled with debugging symbols (-g).

Q: What option preserves intermediate files during a normal compilation run

ANS: Use the -save-temps option with gcc or g++. It saves the preprocessed (.i) and assembly (.s) files in the current directory or the object file’s directory if -save-temps=obj is specified.

Q: Does optimization level affect the generated assembly output

ANS: Yes, optimization levels significantly alter the assembly. Code generated with -O0 (no optimization) closely follows source structure, whereas aggressive optimization levels like -O2 or -O3 may drastically restructure loops and functions for performance.
