“C++ Memory Model: Store Reordering on Weakly Ordered Architectures”

When developing concurrent applications, particularly those aiming for lock-free designs, a nuanced grasp of memory ordering is paramount. Architectures with weakly ordered memory models, such as ARM and POWER, present unique challenges where the order in which stores become visible to other threads might not align with the program’s written sequence. This can manifest as threads observing the same set of stores in different orders, a scenario often probed through tests known as IRIW (Independent Readers, Independent Writers).

The Core Issue: Disagreement on Global Store Order

The C++11 memory model, while providing strong guarantees, does not mandate that all threads agree on a single, global ordering of all stores, especially on processors that employ relaxed memory ordering. This lack of a unified global store order is a direct consequence of hardware design choices aimed at optimizing performance, often at the expense of strict ordering.

Hardware Mechanisms and Reordering

One plausible hardware mechanism contributing to this reordering involves the interaction between Simultaneous MultiThreading (SMT) and store buffers. On physical cores supporting SMT (like Intel’s Hyperthreading or generic multi-threading), logical cores share resources. While speculative stores are kept private to their respective logical cores, non-speculative stores that have retired from the out-of-order execution engine might be buffered.

These buffered, non-speculative stores can potentially be made visible to SMT sibling logical cores before they are globally committed to the main cache hierarchy. This localized visibility to a subset of cores (SMT siblings) can create a situation where threads on different physical cores perceive stores in a different sequence compared to threads on the same physical core.

For instance, POWER CPUs, known for their SMT implementation, might exhibit this behavior. While ARM’s theoretical models have allowed for such reordering, actual implementations might differ, and newer specifications like ARMv8 have strengthened their on-paper models to disallow it even for future hardware.

“Multiple-Copy Atomic” vs. Relaxed Models

Machines where stores are instantaneously visible to all other threads, enforcing a single global store order, are termed “multiple-copy atomic” or “multi-copy atomic.” Architectures like x86 and SPARC, with their Total Store Order (TSO) memory models, possess this property. In contrast, ARM and POWER do not inherently require it.

On x86 and similar architectures, the MESI cache coherence protocol ensures all cores share a consistent view of memory. Stores are globally visible once they exit the store buffer and enter the L1d cache. The MESI protocol maintains a single coherency domain, inherently establishing a consistent order for stores committing to the cache. By employing appropriate memory barriers, sequential consistency can be achieved.

However, on weakly ordered systems, a store can become visible to some cores before it’s universally visible.

Store-to-Load Forwarding and its Implications

Loads typically retrieve data from the L1d cache. However, when a load targets data recently stored by the same core, it can forward directly from the store buffer, bypassing the cache. This is known as store-to-load forwarding (SLF). In certain scenarios, even on strongly ordered architectures like x86, a load might observe a value that was never officially present in the L1d cache, particularly with partial SLF. For a deeper dive into this, see discussions on Globally Invisible Load Instructions .

Testing for Store Order Discrepancies (IRIW)

To verify the behavior of memory models and test for store reordering, specific test scenarios are employed. One such scenario involves multiple threads reading from shared atomic variables.

Consider this setup:

#include <atomic>
#include <thread>
#include <vector>
#include <iostream>

std::atomic<int> x{0};
std::atomic<int> y{0};

void thread1() {
    x.store(1, std::memory_order_release);
}

void thread2() {
    y.store(2, std::memory_order_release);
}

void thread3() {
    int r1 = x.load(std::memory_order_acquire);
    int r2 = y.load(std::memory_order_acquire);
    // Observe r1 and r2
}

void thread4() {
    int r3 = y.load(std::memory_order_acquire); // Note the swap from original content
    int r4 = x.load(std::memory_order_acquire);
    // Observe r3 and r4
}

int main() {
    std::vector<std::thread> threads;
    threads.emplace_back(thread1);
    threads.emplace_back(thread2);
    threads.emplace_back(thread3);
    threads.emplace_back(thread4);

    for (auto& t : threads) {
        t.join();
    }

    // Analysis of results from thread3 and thread4
    return 0;
}

The “weird outcome” mentioned in related discussions refers to specific read patterns that wouldn’t occur in a strictly sequentially consistent execution. For instance, on a weakly ordered processor, it might be possible for thread3 to observe r1 == 1 and r2 == 0, while thread4 observes r3 == 2 and r4 == 0. This implies that thread3 saw the store to x before the store to y, but thread4 saw the store to y before the store to x.

Sequentially Consistent Execution Example

In a sequentially consistent execution, the original example (before the swap in thread4’s reads) would proceed like this:

  • Initially: x = 0, y = 0
  • thread4 reads x (e.g., r3 = 0)
  • thread1 stores 1 to x (x.store(1, std::memory_order_release))
  • thread3 reads x (e.g., r1 = 1) and then reads y (e.g., r2 = 0)
  • thread2 stores 2 to y (y.store(2, std::memory_order_release))
  • thread4 reads y (e.g., r4 = 2)

This sequence r1=1, r2=0, r3=0, r4=2 is not considered unusual in a sequentially consistent model. To truly test for reordering, readers often access variables in opposite orders.

Memory Orders and Their Impact

  • std::memory_order_relaxed: Provides atomicity guarantees but no ordering constraints between operations on different atomic variables. Replacing acquire and release with relaxed in the example does not alter the potential for the described reordering.
  • std::memory_order_acquire / std::memory_order_release: Establish a one-way ordering. An acquire load synchronizes-with a release store.
  • std::memory_order_seq_cst: Offers the strongest guarantee, providing sequential consistency. This means all seq_cst operations appear to happen in a single, global order, interleaved with non-seq_cst operations. The constraint “acquire-loads may not move before release-writes” is one aspect of this stronger ordering. The existence of a “total order” for all seq_cst operations prevents the unusual reordering patterns.

Can Stores Reorder Across Different Atomic Variables?

Yes, the C++ standard does not mandate that stores to different atomic variables must maintain their program order across all threads, especially when using memory orders weaker than seq_cst. The absence of an explicit guarantee means it’s not required, regardless of whether one can readily conceive of a hardware mechanism for it.

Is the “Weird Outcome” Possible?

Under the C++11 memory model, outcomes like r1==1, r2==0, r3==0, r4==2 (as per the original example’s variable access pattern) are indeed permitted on weakly ordered architectures. This highlights the divergence from a strictly sequential view of operations across different atomic variables when not using std::memory_order_seq_cst.

FAQs on C++ Memory Model Store Reordering

Q: What is IRIW in the context of C++ memory models

ANS: IRIW stands for Independent Readers, Independent Writers. It’s a testing methodology used to check if different threads reading from shared memory can observe the same set of writes in different orders, a phenomenon characteristic of weakly ordered architectures.

Q: Does x86 processors reorder stores like ARM or POWER

ANS: No, x86 processors generally adhere to a stronger memory model, typically Total Store Order (TSO), where stores are seen in a consistent order by other processors, thus avoiding the kind of store reordering seen on weaker architectures.

Q: Can store-to-load forwarding cause memory reordering issues

ANS: Yes, store-to-load forwarding (SLF), where a load retrieves data directly from a store buffer, can contribute to perceived reordering. It’s possible for a load to see a value from the store buffer before it’s fully committed to the cache, and this behavior can differ across architectures and SMT implementations.

Q: What is the difference between memory_order_relaxed and memory_order_seq_cst

ANS: memory_order_relaxed offers no ordering guarantees between operations on different atomic objects. memory_order_seq_cst provides the strongest ordering, ensuring a single global order for all seq_cst operations, effectively preventing reordering between them.

Q: When should I use memory_order_acquire and memory_order_release

ANS: Use memory_order_acquire for loads and memory_order_release for stores to establish a synchronization point. An acquire load synchronizes-with a release store, ensuring that all writes that happened-before the release store are visible to the thread performing the acquire load. This is common in producer-consumer patterns.
