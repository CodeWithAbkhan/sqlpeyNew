“C++ Undefined Behavior: When to Use delete vs delete[] for Dynamically Allocated Memory”

When dealing with dynamic memory allocation in C++, the choice between delete and delete[] is paramount. Using the wrong operator to free memory allocated via new or new[] results in Undefined Behavior (UB). This state is perilous because its manifestation—ranging from apparent success to catastrophic failure, memory corruption, or system instability—is entirely unpredictable and compiler/platform-dependent.

What exactly constitutes this Undefined Behavior, and how does the mismatch manifest across different environments?

Defining Undefined Behavior in Deallocation

Undefined Behavior means the C++ standard imposes no requirements on the compiler regarding the behavior of the program. It might work flawlessly, appear to leak memory, crash immediately, or behave inconsistently across different compiler versions, operating systems, or even during different runs based on subtle environmental factors like processor neutrino flux (metaphorically speaking). The firm directive is to avoid it entirely.

The core difference between the two operators lies in destructor invocation:

  • delete ptr;: Calls the destructor once for the single object pointed to by ptr (if it exists), and then frees the memory chunk.
  • delete[] ptr_array;: Calls the destructors sequentially for every element in the array allocated via new[], and then frees the entire memory block.

When an array allocated with new T[n] is freed using delete, the destructors for elements beyond the first are often skipped, potentially leading to resource leaks if those destructors manage external resources. Conversely, using delete[] on memory allocated with new T invokes destructor logic incorrectly or attempts to free a block size that the memory manager doesn’t recognize as corresponding to an array, leading to corruption.
