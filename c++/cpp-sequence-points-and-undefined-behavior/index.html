“C++ Sequence Points and Undefined Behavior with Side Effects”

When writing expressions in C and C++, particularly those involving multiple operations that modify the same variable (side effects), the order in which these operations are evaluated is frequently unspecified. This lack of guaranteed order can lead to bugs that are difficult to track down. How do we manage this uncertainty, especially concerning the evaluation of expressions containing pre/post-increment operators?

The Problem with Unsequenced Operations

In most standard expressions, the compiler is not required to evaluate subexpressions in a specific order (e.g., strictly left-to-right or right-to-left). The primary exceptions involve operators that introduce sequence points, such as the logical AND (&&), logical OR (||), and the ternary operator (?:).

If an expression modifies the same scalar variable more than once between two sequence points, the behavior is typically Undefined Behavior (UB), or at least unspecified execution order.

Explicitly Separating Statements for Predictability

If you absolutely require a specific sequence for operations that modify a variable, the most robust solution is to break the complex expression into multiple, simple statements.

For example, if you have a function call foo(test) that modifies test, and you need test to be evaluated before the function call, you must sequence them explicitly:

// Original problematic structure (order of test evaluation vs foo(test) is NOT guaranteed)
// int result = (test > 5) || (test = foo(test));

// Guaranteed sequence: test is read, then modified by foo(test)
if (test > 5) {
    // Test condition evaluated first
}
test = some_function_that_modifies_test(); 
// Now use the modified value if necessary

C++17 Changes Regarding Operator Overloading and Sequencing

It is important to note that the rules regarding sequencing have evolved, particularly with the C++17 standard update.

Prior to C++17, the evaluation order for overloaded operators was consistent with built-in operators. However, C++17 introduced specific sequencing guarantees for certain operators:

  1. Overloaded Operators: Evaluation order for overloaded operators now aligns with how built-in operators are sequenced (per [over.match.oper]/2 in the standard).
  2. Shift Operators (<<, >>): The left operand is now sequenced before the right operand.
  3. Subscripting Operator ([]): The left operand (the array/container) is sequenced before the right operand (the index).
  4. Function Calls: The evaluation of the postfix-expression (the function name itself) is sequenced before the evaluation of its arguments.

Even with these C++17 improvements, general advice still cautions against relying on side effects within complex expressions due to legacy codebases and the remaining unsequenced operators (like binary +, which remains unsequenced).

Undefined Behavior Related to Increment/Decrement Operators

Increment (++) and decrement (--) operators introduce side effects that are highly susceptible to creating Undefined Behavior if sequence rules are violated. The C++ reference details scenarios where UB occurs due to unsequenced side effects on the same scalar object or when a side effect occurs relative to a value computation involving that object.
