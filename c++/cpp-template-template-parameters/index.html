“C++ Template Template Parameters: Syntax, Use Cases, and Examples”

When working with C++ templates, you often need to pass template arguments that are themselves template types. This is where template template parameters come into play, allowing for more flexible and generic code. But what exactly are they, how do you use them, and in what scenarios are they most beneficial?

Let’s delve into the intricacies of C++ template template parameters, supported by practical examples to illustrate their power and utility.

Core Concept: What are Template Template Parameters?

A template template parameter is a way to declare a function or class template that accepts another template as an argument. This is distinct from a regular template parameter, which accepts a type or a non-type value.

The syntax involves specifying the template parameters of the argument template within angle brackets. For instance, template <template <class> class H> declares a template template parameter H that expects a template accepting one type argument.

Practical Use Cases and Solutions

The utility of template template parameters spans several common programming patterns and problem-solving scenarios in C++.

Solution 1: Handling Specializations of a Template

One primary use case is to create functions that operate on all specializations of a given template, without needing to know the exact type or number of template arguments beforehand.

Consider a function that needs to manipulate elements of various container types.

#include <iostream>
#include <vector>
#include <list>
#include <deque>

// Function to process elements of any container with one template argument
template <template <typename> class Container, typename T>
void processContainerElements(const Container<T>& c) {
    for (const auto& element : c) {
        std::cout << element << " ";
    }
    std::cout << std::endl;
}

// Function to process elements of containers with two template arguments (e.g., vector, list)
template <template <typename, typename> class Container, typename T, typename Allocator>
void processContainerElementsWithAllocator(const Container<T, Allocator>& c) {
    for (const auto& element : c) {
        std::cout << element << " ";
    }
    std::cout << std::endl;
}

int main() {
    std::vector<int> myVector = {1, 2, 3};
    std::list<double> myList = {1.1, 2.2, 3.3};

    processContainerElements(myVector);
    processContainerElements(myList); // This would fail as list has two template args

    processContainerElementsWithAllocator(myVector);
    processContainerElementsWithAllocator(myList);

    return 0;
}

Explanation:

  • processContainerElements accepts a template Container that takes one type argument.
  • processContainerElementsWithAllocator accepts a template Container that takes two type arguments (type and allocator).
  • The code demonstrates how to call these functions with different container types like std::vector and std::list.

Note: While std::vector and std::list can be passed, the precise template parameter list must match. Modern C++ features like auto can sometimes simplify these scenarios, as shown in a later example.

Solution 2: Stream Output Operators for Containers

A common need is to provide a uniform way to stream output for various standard library containers, which unfortunately don’t always have built-in stream operators.

#include <iostream>
#include <vector>
#include <list>
#include <deque>
#include <string>
#include <map>

// Generic stream output for sequence containers
template<template <typename, typename> class Container, typename T, typename Allocator>
std::ostream& operator<<(std::ostream& os, const Container<T, Allocator>& c) {
    os << '[';
    bool first = true;
    for (const auto& element : c) {
        if (!first) {
            os << ", ";
        }
        os << element;
        first = false;
    }
    os << ']';
    return os;
}

// Specialized stream output for std::map
template<typename K, typename V>
std::ostream& operator<<(std::ostream& os, const std::map<K, V>& m) {
    os << '{';
    bool first = true;
    for (const auto& pair : m) {
        if (!first) {
            os << ", ";
        }
        os << pair.first << ": " << pair.second;
        first = false;
    }
    os << '}';
    return os;
}

int main() {
    std::vector<int> numbers = {10, 20, 30};
    std::list<std::string> words = {"hello", "world"};
    std::map<std::string, int> scores = {{"Alice", 95}, {"Bob", 88}};

    std::cout << "Numbers: " << numbers << std::endl;
    std::cout << "Words: " << words << std::endl;
    std::cout << "Scores: " << scores << std::endl;

    return 0;
}

Explanation:

  • The generic operator<< handles sequence containers like std::vector and std::list by accepting their template template Container and its arguments.
  • A specific overload for std::map is provided due to its different structure (key-value pairs).
  • This allows for consistent output formatting across different container types.
Solution 3: Policy-Based Design

Template template parameters are instrumental in implementing the policy pattern, allowing customization of class behavior through template arguments.

// Example inspired by "Modern C++ Design" by Andrei Alexandrescu

// A generic policy for creating objects
template <class Product>
class DefaultCreationPolicy {
public:
    static Product* create() { return new Product; }
};

// A class that uses a creation policy
template <template <class> class CreationPolicy>
class WidgetManager {
public:
    void createWidget() {
        Widget* w = CreationPolicy<Widget>::create();
        // ... use widget ...
        delete w;
    }
};

// A custom policy
template <class Product>
class CustomCreationPolicy {
public:
    static Product* create() {
        // Custom creation logic
        return new Product;
    }
};

// Type alias for cleaner usage
typedef WidgetManager<DefaultCreationPolicy> DefaultWidgetMgr;
typedef WidgetManager<CustomCreationPolicy> CustomWidgetMgr;

// Dummy Widget class for demonstration
class Widget {};

int main() {
    DefaultWidgetMgr defaultMgr;
    defaultMgr.createWidget(); // Uses DefaultCreationPolicy

    CustomWidgetMgr customMgr;
    customMgr.createWidget(); // Uses CustomCreationPolicy

    return 0;
}

Explanation:

  • WidgetManager is a template class that takes a CreationPolicy template as a template template parameter.
  • DefaultCreationPolicy and CustomCreationPolicy are examples of policies that define how a Widget is created.
  • Using template template parameters makes the instantiation cleaner, e.g., WidgetManager<DefaultCreationPolicy> instead of WidgetManager<DefaultCreationPolicy<Widget>>.
Solution 4: GPU/CPU Tensor Implementations in Machine Learning

In libraries dealing with high-performance computing, like those for machine learning, template template parameters can manage different backend implementations (e.g., CPU vs. GPU).

// Simplified representation for demonstration

// Base Tensor class
template <class T>
class Tensor {
public:
    // Tensor operations
};

// Tensor implementation for GPU
template <class T>
class TensorGPU : public Tensor<T> {
public:
    // GPU-specific tensor operations
};

// A generic layer that can hold tensors
template <template <class> class TensorType, class DataType>
class GenericLayer : public BaseLayer<TensorType<DataType>> {
public:
    TensorType<DataType> weights;
    TensorType<DataType> inputs;
    TensorType<int> connectionMatrix; // Always int
};

// A CUDA-specific layer
class CudaLayer : public GenericLayer<TensorGPU, float> {
    // Specific CUDA layer logic
};

// Base layer struct for compilation
template<typename TensorType>
class BaseLayer {};


int main() {
    CudaLayer cudaLayer;
    // cudaLayer.weights and cudaLayer.inputs are TensorGPU<float>
    // cudaLayer.connectionMatrix is Tensor<int>
    return 0;
}

Explanation:

  • TensorType in GenericLayer is a template template parameter.
  • This allows GenericLayer to work with any tensor implementation (like Tensor or TensorGPU) by specifying it during instantiation.
  • CudaLayer instantiates GenericLayer with TensorGPU and float, meaning its weights and inputs will be GPU-accelerated float tensors. The connectionMatrix remains an integer tensor.
Solution 5: Recursive Type Definitions and Self-Referential Templates

Template template parameters can help resolve complex, self-referential type definitions that might otherwise lead to infinite recursion.

template<class T>
class B {
public:
    T* associated_data; // Pointer to the associated data
    int dummy_value; // A sample value
};

// Problematic recursive definition without template template parameter
// template<class T_B>
// class A {
//     T_B associated_b_instance;
// };
// class InstanceProblem : A<B<A<B<...>>>> {};

// Solution using template template parameter for A
template<template<class> class T_Container>
class A {
public:
    T_Container<A<T_Container>> associated_container_instance; // Self-referential instance
};

// Concrete instance type
class MyConcreteA : public A<B> {
public:
    void setup() {
        // Example of setting up the associated data
        associated_container_instance.associated_data = reinterpret_cast<B<A<B>>*>(this);
        associated_container_instance.dummy_value = 42;
    }
    void display() {
        // Accessing nested data
        std::cout << "Associated data dummy value: " << associated_container_instance.associated_data->dummy_value << std::endl;
    }
};

int main() {
    MyConcreteA instance;
    instance.setup();
    instance.display();
    return 0;
}

Explanation:

  • The initial attempt leads to a type like A<B<A<B<...>>>> which fails to compile.
  • By using template<template<class> class T_Container> class A, we define A to accept a template that takes one type argument.
  • Inside A, T_Container<A<T_Container>> correctly references the nested type structure, allowing MyConcreteA to be instantiated with A<B>.
Solution 6: Simplifying CRTP Usage

The Curiously Recurring Template Pattern (CRTP) can be made more elegant and less redundant with template template parameters, especially when dealing with multiple template arguments.

// Without template template parameters (redundant type specification)
template <typename Derived, typename Value>
class BaseInterface {
protected:
    void processValue(Value v) {
        static_cast<Derived*>(this)->customProcess(v);
    }
};

template <typename Value>
class DerivedClass : public BaseInterface<DerivedClass<Value>, Value> {
public:
    void customProcess(Value v) {
        // Specific processing for DerivedClass
        std::cout << "Processing value: " << v << std::endl;
    }
};

// Redundant specification: DerivedClass<int> has to be specified twice
typedef BaseInterface<DerivedClass<int>, int> DerivedIntInterface_V1;


// With template template parameters
template <template <typename> class DerivedTemplate, typename Value>
class BetterBaseInterface {
protected:
    void processValue(Value v) {
        static_cast<DerivedTemplate<Value>*>(this)->customProcess(v);
    }
};

template <typename Value>
class BetterDerivedClass : public BetterBaseInterface<BetterDerivedClass, Value> {
public:
    void customProcess(Value v) {
        std::cout << "Better processing value: " << v << std::endl;
    }
};

// Cleaner specification
typedef BetterBaseInterface<BetterDerivedClass, int> DerivedIntInterface_V2;

int main() {
    DerivedClass<int> obj1;
    obj1.processValue(10);

    BetterDerivedClass<int> obj2;
    obj2.processValue(20);

    return 0;
}

Explanation:

  • The BaseInterface requires Derived and Value. In the first version, DerivedClass<int> is duplicated.
  • BetterBaseInterface uses a template template parameter DerivedTemplate for the derived class, simplifying the typedef to BetterBaseInterface<BetterDerivedClass, int>.
Solution 7: Default Allocator Customization

Template template parameters are useful for providing default template arguments for class templates, such as custom allocators.

#include <vector>
#include <iostream>

// A custom allocator (simplified)
template <class T>
class CustomAllocator {
public:
    using value_type = T;
    // ... allocator methods ...
    T* allocate(size_t n) { return static_cast<T*>(::operator new(n * sizeof(T))); }
    void deallocate(T* p, size_t n) { ::operator delete(p); }
};

// Class using a default allocator
template <template <class T> class Allocator = CustomAllocator>
class ConfigurableContainer {
public:
    std::vector<int, Allocator<int>> data;
};

int main() {
    ConfigurableContainer<> container1; // Uses default CustomAllocator
    container1.data.push_back(100);
    std::cout << "Container 1 element: " << container1.data[0] << std::endl;

    // You can also specify a different allocator if needed (though not directly via template template param here)
    // std::vector<int, std::allocator<int>> data_std;

    return 0;
}

Explanation:

  • ConfigurableContainer has a default template parameter for its allocator, which is a template template parameter Allocator.
  • By default, it uses CustomAllocator. If you wanted to use std::allocator, you would typically pass it directly, but this demonstrates the pattern.
Solution 8: Handling Variadic Template Specialization with Maps

When using variadic templates for generic container output, specializing for types like std::map requires careful handling to avoid the greedy nature of variadic template matching.

#include <iostream>
#include <vector>
#include <deque>
#include <list>
#include <map>
#include <string>

namespace display {
    // Generic handler for containers with multiple template arguments
    template <typename T, template <typename, typename...> class Container, typename... Args>
    std::ostream& operator<<(std::ostream& os, const Container<T, Args...>& c) {
        os << "[Generic: ";
        for (const auto& element : c) {
            os << element << ' ';
        }
        os << ']';
        return os;
    }
}

// Specialized handler for std::map
template <typename K, typename V>
std::ostream& operator<<(std::ostream& os, const std::map<K, V>& m) {
    os << "{Map: ";
    bool first = true;
    for (const auto& pair : m) {
        if (!first) {
            os << ", ";
        }
        os << pair.first << ": " << pair.second;
        first = false;
    }
    os << '}';
    return os;
}

int main() {
    // Using the generic handler
    std::vector<float> vf = {1.1f, 2.2f, 3.3f, 4.4f};
    std::cout << vf << std::endl;

    std::list<char> lc = {'a', 'b', 'c', 'd'};
    std::cout << lc << std::endl;

    std::deque<int> di = {1, 2, 3, 4};
    std::cout << di << std::endl;

    // Using the specialized map handler
    std::map<std::string, std::string> m1 = {{"key1", "value1"}, {"key2", "value2"}};
    std::cout << m1 << std::endl;

    return 0;
}

Explanation:

  • The generic operator<< in display namespace uses template <typename T, template <typename, typename...> class Container, typename... Args> to capture containers with one primary type and any additional arguments.
  • A separate, non-namespaced operator<< is defined for std::map to handle its key-value structure correctly, preventing the variadic generic handler from being ambiguously chosen.
Solution 9: Enhancing Readability and Type Safety

Template template parameters can lead to more readable and type-safe code by explicitly defining the expected template structure.

#include <iostream>
#include <vector>
#include <list>

// Version without template template parameter
template <typename T>
void printSimple(const T& container) {
    for (const auto& item : container) {
        std::cout << item << ' ';
    }
    std::cout << '\n';
}

// Version with template template parameter for containers with type and allocator
template <template <typename, typename> class Container, typename Value, typename Alloc>
void printSpecific(const Container<Value, Alloc>& container) {
    for (const auto& item : container) {
        std::cout << item << ' ';
    }
    std::cout << '\n';
}

int main() {
    std::vector<int> v = {1, 2, 3};
    std::list<double> l = {1.1, 2.2, 3.3};

    printSimple(v); // Works fine
    printSimple(l); // Works fine

    printSpecific<std::vector, int, std::allocator<int>>(v); // Explicitly specify
    printSpecific<std::list, double, std::allocator<double>>(l); // Explicitly specify

    // Example of type safety: passing a non-container
    // printSpecific(5); // This would cause a compile-time error

    return 0;
}

Explanation:

  • printSimple is more general but might accept types that aren’t containers, leading to potential runtime errors if not handled carefully.
  • printSpecific explicitly requires a container template with specific template arguments, enhancing compile-time safety. If you try to pass a non-container type or a container with a different signature, it will fail compilation.
Solution 10: Versioned Type Handling

When dealing with types that are versioned using templates (e.g., MyType<VersionNumber>), template template parameters allow functions to adapt their behavior based on the version.

#include <iostream>
#include <cstdint>
#include <cassert>

// Example of a versioned type
template <uint8_t Version>
class DataPacket {
public:
    static const uint8_t packetVersion = Version;
    // ... data members ...
};

// Function that handles different versions of DataPacket
template <template <uint8_t> class PacketType, uint8_t Version>
void processVersionedPacket(const PacketType<Version>& packet) {
    std::cout << "Processing packet of version: " << Version << std::endl;
    assert(Version > 1 && "Versions prior to 2 are not supported.");

    switch (Version) {
        case 2:
            // Process version 2 specifics
            break;
        case 3:
            // Process version 3 specifics
            break;
        default:
            // Default handling
            break;
    }
}

int main() {
    DataPacket<2> packet2;
    DataPacket<3> packet3;

    processVersionedPacket(packet2);
    processVersionedPacket(packet3);

    return 0;
}

Explanation:

  • processVersionedPacket uses a template template parameter PacketType and a non-type template parameter Version.
  • This allows the function to accept any DataPacket specialization and perform version-specific logic using the captured Version.
Solution 11: Generic Meta-Function Instantiation

Template template parameters are essential for generic meta-programming, enabling functions to instantiate other templates with derived sets of types.

#include <iostream>
#include <memory>
#include <tuple>
#include <type_traits> // For std::is_same

// Generic meta-function to wrap types
template <template <typename...> class TypeWrapper, typename... Types>
struct WrapTypes {
    using type = std::tuple<TypeWrapper<Types>...>;
};

// Alias for unique_ptr wrapping
template <typename... Types>
using wrap_in_unique_ptr_t = typename WrapTypes<std::unique_ptr, Types...>::type;

// Alias for shared_ptr wrapping
template <typename... Types>
using wrap_in_shared_ptr_t = typename WrapTypes<std::shared_ptr, Types...>::type;

int main() {
    // Verify unique_ptr wrapping
    using UniquePtrTuple = std::tuple<std::unique_ptr<int>, std::unique_ptr<float>, std::unique_ptr<bool>>;
    static_assert(std::is_same<wrap_in_unique_ptr_t<int, float, bool>, UniquePtrTuple>::value, "UniquePtr wrapping failed");
    std::cout << "UniquePtr wrapping is correct." << std::endl;

    // Verify shared_ptr wrapping
    using SharedPtrTuple = std::tuple<std::shared_ptr<int>, std::shared_ptr<float>, std::shared_ptr<bool>>;
    static_assert(std::is_same<wrap_in_shared_ptr_t<int, float, bool>, SharedPtrTuple>::value, "SharedPtr wrapping failed");
    std::cout << "SharedPtr wrapping is correct." << std::endl;

    return 0;
}

Explanation:

  • WrapTypes uses a template template parameter TypeWrapper to generalize the wrapping mechanism.
  • Aliases wrap_in_unique_ptr_t and wrap_in_shared_ptr_t are created by specializing WrapTypes with std::unique_ptr and std::shared_ptr respectively.
  • This avoids code duplication and allows easy extension to wrap other templated types.

When to Use Template Template Parameters

Consider using template template parameters when:

  • Your function or class template needs to operate on a variety of template types that share a common structure (e.g., all standard library containers).
  • You are implementing generic algorithms or policies where the underlying container or policy mechanism is itself a template.
  • You want to reduce boilerplate code when dealing with different instantiations of template types.

Alternatives and Considerations

  • typename: For many cases, a simple typename parameter might be sufficient if you only need to accept a single template type (e.g., template <typename Container> void func(const Container& c)). However, this approach doesn’t allow you to constrain the inner template parameters of the Container type itself.
  • auto: C++11 and later auto keyword can simplify parameter deduction in function arguments, sometimes reducing the need for explicit template parameters.
  • Type Traits: For more advanced compile-time introspection and manipulation of types, type traits from <type_traits> are invaluable.

Template template parameters, while powerful, can increase code complexity. Ensure they are necessary for achieving the desired level of genericity and abstraction in your C++ projects.

FAQs on C++ Template Template Parameters

Q: What is the basic syntax for a template template parameter in C++

ANS: The syntax involves declaring a template parameter that expects a template, like template <template <typename> class MyTemplate>. This specifies that MyTemplate is a template that takes one type argument.

Q: Can template template parameters accept templates with multiple arguments

ANS: Yes, you can specify the number and types of template arguments the parameter template expects, for example: template <template <typename, typename> class MyContainer>.

Q: When is it appropriate to use template template parameters

ANS: Use them when your function or class template needs to work with different instantiations of another template, such as various standard library containers, or when implementing policy-based designs.

Q: Are there simpler alternatives to template template parameters

ANS: Often, a simple typename parameter might suffice if you don’t need to constrain the arguments of the template itself. C++11’s auto can also simplify function parameter deduction in some scenarios.

Q: How do template template parameters help with CRTP

ANS: They reduce redundancy by allowing the base class to accept the derived class template directly, avoiding the need to specify the derived class’s template arguments multiple times.

Q: Can template template parameters be used for versioned types

ANS: Yes, they are very useful for creating functions that can process different versions of a templated type by capturing the version number as a non-type template parameter.
