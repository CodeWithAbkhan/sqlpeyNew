“C++ Union Type-Punning: Is it Defined Behavior?”

Let’s delve into the standards and common interpretations to shed light on this practice.

C vs. C++ Union Behavior

A key distinction lies in how C and C++ handle union members.

C (C11 Standard - 6.5.2.3 Structure and union members): The C standard, specifically C11, provides language that addresses the reinterpretation of union members:

  1. If the member used to read the contents of a union object is not the same as the member last used to store a value in the object, the appropriate part of the object representation of the value is reinterpreted as an object representation in the new type as described in 6.2.6 (a process sometimes called ‘‘typepunning’’). This might be a trap representation.

This excerpt clearly indicates that C allows for type-punning by reinterpreting the object’s representation.

C++ (C++11 Standard - 9.5 Unions [class.union]): In contrast, the C++11 standard presents a different perspective:

In a union, at most one of the non-static data members can be active at any time, that is, the value of at most one of the non-static data members can be stored in a union at any time.

This statement highlights that only one member of a union can hold a valid value at any given moment. The C++ standard later introduced provisions for unions containing structs with common initial sequences. While this facilitates certain interactions, it does not inherently permit general type-punning.

Examining the C++ Standard for Type-Punning Clarification

To ascertain the permissibility of union type-punning in C++, further examination of the standard is necessary. C++11 draws normative references from C99, which features similar wording to C11 regarding union type-punning.

3.9 Types [basic.types]: This section defines object representation:

4 - The object representation of an object of type T is the sequence of N unsigned char objects taken up by the object of type T, where N equals sizeof(T). The value representation of an object is the set of bits that hold the value of type T. For trivially copyable types, the value representation is a set of bits in the object representation that determines a value, which is one discrete element of an implementation-deﬁned set of values. 42 42) The intent is that the memory model of C++ is compatible with that of ISO/IEC 9899 Programming Language C.

This implies a degree of compatibility between the memory models of C and C++.

3.8 Object lifetime [basic.life]: Regarding object lifetime:

The lifetime of an object of type T begins when: — storage with the proper alignment and size for type T is obtained, and — if the object has non-trivial initialization, its initialization is complete.

For a primitive type within a union, its lifetime is tied to the union’s lifetime, allowing for valid object access.

4.1 Lvalue-to-rvalue conversion [conv.lval]: This conversion is relevant when accessing union members:

A glvalue of a non-function, non-array type T can be converted to a prvalue. If T is an incomplete type, a program that necessitates this conversion is ill-formed. If the object to which the glvalue refers is not an object of type T and is not an object of a type derived from T, or if the object is uninitialized, a program that necessitates this conversion has undeﬁned behavior.

The crucial question becomes whether a non-active union member is considered initialized. The standard suggests that direct access to a non-active member, without specific interpositions like byte-wise copying or conforming cross-language access (as per ISO/IEC 9899), results in undefined behavior. This is because such an access might be considered an access to an uninitialized object.

This means that while you can validly form an lvalue to a non-active union member (making assignments to it permissible without explicit construction), it is often treated as uninitialized for read operations unless specific conditions are met.

Practical Implications and Allowed Interpositions

The C++ standard outlines specific scenarios where accessing a non-active union member is defined:

  1. Union Copying: If a union is copied into a char array storage and then back, or if a union is byte-wise copied to another union of the same type.
  2. Cross-Language Access: If a union is accessed across language boundaries by a program element conforming to ISO/IEC 9899 (the C standard).

These interpositions allow for defined access to the object and value representations, adhering to the standard’s rules.

C++ Standard Implications for Optimization

Implementations may assume that undefined behavior does not occur. Therefore, when type-punning through unions in a manner not explicitly defined by the standard, compilers might perform optimizations that lead to unexpected results.

Alternative Perspectives and Interpretations

Some interpretations suggest that the C++ standard implies undefined behavior for type-punning unless specific conditions are met.

C99 Defect Report #283: This report added a footnote to the C standard concerning union access:

78a) If the member used to access the contents of a union object is not the same as the member last used to store a value in the object, the appropriate part of the object representation of the value is reinterpreted as an object representation in the new type as described in 6.2.6 (a process sometimes called "type punning"). This might be a trap representation.

While this clarifies the intent, the status of footnotes as normative additions can vary.

Common Initial Sequences: The standard, in sections like C99 §6.5.2.3/5 and C++11 §9.2/19, permits inspecting the common initial part of structures within a union if they share a common initial sequence. This implies that direct “inspection” (reading) is permitted primarily if it’s the member most recently written or part of a common initial sequence. Doing otherwise is considered close to, if not precisely, undefined behavior.

Footnote 37 (6.2.5, paragraph 21): This footnote states:

Note that aggregate type does not include union type because an object with union type can only contain one member at a time.

This requirement can be interpreted as a strong indicator that writing to one member and reading from another is not directly supported and might lead to undefined behavior due to a lack of specification.

Illustrative Example: Union A

Consider the following union:

union Data {
   int value_int;
   short value_short[2];
};

Assuming sizeof(int) is 4 and sizeof(short) is 2, if we initialize Data d = {10};, the memory might look like this:

       |          value_int          |   value_short[0]   |   value_short[1]   |

Here, d.value_int is 10. Now, if we modify d.value_short[0] = 37;:

       |          value_int          |   value_short[0]   |   value_short[1]   |

   d-> | 0000 0000 | 0010 0101 | 0000 0000 | 0000 1010 |

Reading d.value_int after this modification could yield a value like 2424842 (decimal), depending on the endianness and the exact bit representation. This demonstrates how reinterpreting bytes can lead to different values.

The core issue remains: is this reinterpretation, performed by reading d.value_int after writing to d.value_short[0], officially defined behavior in C++? The consensus leans towards it being undefined behavior unless specific allowed interpositions are used.
