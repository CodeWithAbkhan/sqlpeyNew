“C++17 Expression Evaluation Order Changes: Key Updates Explained”

The introduction of C++17 brought significant clarifications and specifications regarding the order of expression evaluation, particularly addressing areas that were previously unspecified or led to undefined behavior. This evolution aimed to improve code predictability and safety, especially in complex scenarios involving function calls and side effects.

Key Changes in C++17 Evaluation Order

One of the most impactful changes in C++17 relates to the evaluation order of function arguments. Previously, the order in which arguments were evaluated relative to each other was unspecified. C++17 introduces rules to make these scenarios more predictable.

How did C++17 refine function argument evaluation?

In C++17, the evaluation of arguments to a function call is now subject to stricter sequencing. While the order of evaluation for arguments like g(), h(), and j() in f(g(), h(), j()) remains unspecified among themselves, there are crucial guarantees. The evaluation of the function itself (e.g., f in f(...) or getf in getf()(...)) is sequenced before any of its arguments. Furthermore, each argument’s evaluation is now required to complete fully, including all its side effects, before the evaluation of any subsequent argument begins.

Consider this example:

#include <iostream>
#include <string>
#include <vector>
#include <cassert>

struct Speaker {
    int index = 0;
    Speaker(std::vector<std::string> words) : words_(words) {}
    std::vector<std::string> words_;

    std::string operator()() {
        assert(!words_.empty());
        if (index == words_.size()) {
            index = 0;
        }
        std::string current_word = words_[index];
        index++;
        return current_word;
    }
};

int main() {
    auto speaker_instance = Speaker{{"Greeting", "World", "How", "Are", "You"}};
    // The order of calls to speaker_instance() is now more predictable
    std::cout << speaker_instance() << ", "
              << speaker_instance() << ", "
              << speaker_instance() << ", "
              << speaker_instance() << ", "
              << speaker_instance() << std::endl;
}

Pre-C++17 vs. C++17 Behavior:

In versions prior to C++17, code like std::cout << f() << f(); was unspecified regarding the order of f() calls. This could lead to output like SecondFirst or FirstSecond. With C++17, the evaluation of f() calls is sequenced relative to each other, generally resulting in FirstSecond due to operator precedence rules concerning <<.

A more complex example involves chaining replace operations:

#include <iostream>
#include <string>

int main() {
    std::string message = "but I have heard it works even if you don't believe in it";
    // This chained operation is now more predictable with C++17
    message.replace(0, 4, "").replace(message.find("even"), 4, "only")
           .replace(message.find(" don't"), 6, "");
    std::cout << message << std::endl; // Expected: "I have heard it works only if you believe in it"
    return 0;
}

The evaluation order for such chained method calls, where the result of one method is used in the next, is now more reliably defined.

Impact on Resource Management and Safety:

C++17 also addresses potential resource leaks caused by unspecified evaluation order, particularly in scenarios involving smart pointers and exception safety. Consider the following pattern:

#include <memory>
#include <iostream>

struct ResourceA {};
struct ResourceB {};

void process_resources(std::unique_ptr<ResourceA> res_a, std::unique_ptr<ResourceB> res_b) {
    std::cout << "Processing resources." << std::endl;
}

std::unique_ptr<ResourceA> create_a() { return std::make_unique<ResourceA>(); }
std::unique_ptr<ResourceB> create_b() { return std::make_unique<ResourceB>(); }

int main() {
    // Pre-C++17, this could lead to leaks if constructor throws
    // process_resources(std::unique_ptr<ResourceA>(new ResourceA), std::unique_ptr<ResourceB>(new ResourceB));

    // With C++17, interleaving of these operations is prohibited.
    // Two safe orderings:
    // 1. new A -> unique_ptr<A> ctor -> new B -> unique_ptr<B> ctor
    // 2. new B -> unique_ptr<B> ctor -> new A -> unique_ptr<A> ctor
    process_resources(create_a(), create_b());
    return 0;
}

Before C++17, the sequence of new operations and smart pointer constructions was unspecified. If, for instance, new ResourceB executed and threw an exception before std::unique_ptr<ResourceA> was fully constructed, the ResourceA allocated by new ResourceA would leak. C++17 prohibits this interleaving, ensuring that the creation and construction of arguments for a function call occur in a complete, non-interleaved manner, thus preventing such leaks. The standard now states that function invocations do not interleave with each other.

Undefined Behavior vs. Unspecified Behavior:

It’s important to distinguish between undefined and unspecified behavior.

  • Undefined Behavior (UB): Anything can happen. The compiler is not required to diagnose UB, and the program’s behavior is unpredictable.
  • Unspecified Behavior: The standard allows for multiple valid outcomes, but the specific outcome is not dictated. The behavior is deterministic within a single execution but may vary across different executions or compilers.

C++17 transitions some cases from undefined to unspecified, offering more predictable outcomes. For instance, the evaluation order of i++ and i in f(i++, i) was UB, but is now unspecified. This means f(1, 1) (if i++ is evaluated second) or f(1, 2) (if i++ is evaluated first) are possible, but f(2, 2) is not. Each argument evaluation must complete before the next starts.

C++17 Expression Evaluation Order Summary

C++17 introduced clarifications to expression evaluation order, including:

  • Function Calls: The function designator is evaluated before any arguments. Each argument’s evaluation completes before the next argument’s evaluation begins.
  • Operator Precedence: Order of evaluation for operands of operators like << is clarified.
  • Resource Safety: Prevents interleaving of operations like new and constructor calls within function arguments, mitigating potential resource leaks.
  • Undefined to Unspecified: Some previously undefined behaviors are now specified as unspecified, leading to more consistent outcomes.

These changes contribute to writing more robust and predictable C++ code.

FAQs on C++17 Expression Evaluation Order

Q: What is the primary benefit of C++17's revised expression evaluation order

ANS: C++17 clarifies evaluation order, transforming some undefined behaviors into specified (though sometimes unspecified) behaviors, thereby increasing predictability and safety in complex code structures, particularly function calls.

Q: Is the order of arguments to a C++ function call now fully specified in C++17

ANS: No, the order in which arguments themselves are evaluated relative to each other remains unspecified. However, C++17 mandates that each argument’s evaluation and all its side effects must complete before the evaluation of the next argument begins.

Q: How does C++17 prevent resource leaks in function calls

ANS: C++17 prohibits the interleaving of operations when constructing function arguments. This ensures that a resource allocated for one argument is properly managed (e.g., through smart pointer construction) before the allocation or construction of another argument proceeds, thus preventing leaks if an intermediate step throws an exception.

Q: What is the difference between undefined and unspecified behavior in C++

ANS: Undefined behavior means the C++ standard places no requirements on the outcome; anything can happen. Unspecified behavior means the standard allows for multiple outcomes, but the specific outcome chosen by the implementation is not dictated, though it will be consistent within a given execution.

Q: Does C++17 guarantee the output order of chained output operations like std::cout << a << b

ANS: Yes, C++17 generally clarifies the sequencing for chained operations like std::cout << f() << f();, making the order of evaluation more predictable by sequencing the calls to f() rather than leaving them entirely to chance.
