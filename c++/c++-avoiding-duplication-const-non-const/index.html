“C++: Avoiding Duplication in Const and Non-Const Member Functions”

When designing C++ classes, a common challenge arises when you need both const and non-const versions of a member function. Both functions often contain identical core logic, but the const version must guarantee it doesn’t modify the object, while the non-const version allows modifications. This leads to the dilemma of code duplication versus potential safety issues. How can we effectively share the implementation logic while maintaining type safety and adhering to C++ best practices?

Let’s delve into various strategies to address this, examining their nuances and practical applications.

The Core Problem: Shared Logic, Different Guarantees

Consider a scenario where you have a getter function that retrieves an element from a container. The const version returns a const reference, ensuring the object remains unchanged. The non-const version, however, returns a non-const reference, permitting modifications. The underlying logic to find the element might be complex, involving index validation, data access, and error handling. Duplicating this logic in both functions is error-prone and violates the DRY (Don’t Repeat Yourself) principle.

Solution 1: Scott Meyers’ Approach with const_cast

A widely recognized solution, often attributed to Scott Meyers in “Effective C++,” involves having the non-const member function call the const member function and then const_cast the result.

struct C {
  const char &get() const {
    // Complex logic to retrieve the character
    return c;
  }

  char &get() {
    // Call the const version and remove constness
    return const_cast<char &>(static_cast<const C &>(*this).get());
  }

  char c; // Example member
};

The rationale here is that if the non-const get() is called, the object itself is not const. Therefore, casting away const from the return value is safe in this context, as it implies the object was mutable to begin with. The nested casts and function call might appear verbose, but they correctly delegate the core logic.

Solution 2: C++17 std::as_const

C++17 introduced std::as_const, which provides a cleaner way to achieve the same goal as the static_cast<const C &>(*this) part of the previous solution.

// Assuming 'T' is the type of the element being returned
T const &f() const {
    // Complex logic
    return something_complicated();
}

T &f() {
    // Use std::as_const to get a const reference, then cast
    return const_cast<T &>(std::as_const(*this).f());
}

This approach is more explicit about the intent and fits neatly on a single line. To further enhance type deduction and safety, especially regarding volatile qualifiers (though volatile is less common), a helper function can be employed:

template<typename T>
constexpr T &as_mutable(T const &value) noexcept {
    return const_cast<T &>(value);
}

// ... later in the class ...
decltype(auto) f() const {
    return something_complicated();
}

decltype(auto) f() {
    return as_mutable(std::as_const(*this).f());
}

This as_mutable helper, along with std::as_const, creates a robust pattern for safely accessing the underlying data. For more details on std::as_const, refer to the cppreference documentation .

Solution 3: Delegating to a Private Helper Function

Another common and often preferred pattern is to delegate the core logic to a private helper function. This helper can be a regular function or a template.

Private Member Function Delegation

The non-const member function calls the const member function and re-casts the return value.

class X {
   std::vector<Z> vecZ; // Assuming Z is some type

public:
   const Z &z(size_t index) const {
      // Core logic for validation and access
      return vecZ[index];
   }

   Z &z(size_t index) {
      // One line to call const version and remove const
      return const_cast<Z &>(static_cast<const X &>(*this).z(index));
   }

   // Alternative, slightly less verbose:
   /*
   Z &z(size_t index) {
      const X &constMe = *this;
      return const_cast<Z &>(constMe.z(index));
   }
   */
};

Important Note: It is crucial to place the core logic in the const member function. Having the non-const function contain the logic and call the const version can lead to undefined behavior if the const function accidentally modifies the object (which it shouldn’t).

Private Static Template Helper Function

A more flexible approach uses a private static template function that deduces the object’s const-ness.

class X {
    std::vector<Z> vecZ;

    // ReturnType is explicitly 'Z&' or 'const Z&'
    // ThisType is deduced to be 'X' or 'const X'
    template <typename ReturnType, typename ThisType>
    static ReturnType Z_impl(ThisType &self, size_t index) {
        // Massive amounts of code for validating index
        ReturnType ret = self.vecZ[index];
        // Even more code for determining...
        return ret;
    }

public:
    Z &Z(size_t index) {
        return Z_impl<Z &>(*this, index);
    }

    const Z &Z(size_t index) const {
        return Z_impl<const Z &>(*this, index);
    }
};

This pattern avoids const_cast directly within the public interface, encapsulating it within the private helper. For more on C++ access control and design, see discussions on class member access .

Solution 4: C++23 Deducing this

C++23 introduces “Deducing this,” which significantly simplifies this pattern by allowing a single member function template to handle both const and non-const cases naturally.

struct s {
    // 'self' will be 's&' or 'const s&' based on the call
    auto &&f(this auto &&self) {
        // All common code goes here
        // 'self' can be used to access members.
        // Its constness is automatically deduced.
        return /* access logic using self */;
    }
};

This feature, stemming from P0847: Deducing this , removes the need for explicit const_cast or multiple overloads for the same core logic.

Solution 5: Helper Function with Type Traits (C++11)

Leveraging C++11’s variadic templates and type traits, a more generic helper can be created.

template <typename T>
struct NonConst { typedef T type; };

template <typename T>
struct NonConst<T const> { typedef T type; }; // by value

template <typename T>
struct NonConst<T const &> { typedef T &type; }; // by reference

template <typename T>
struct NonConst<T const *> { typedef T *type; }; // by pointer

template <typename T>
struct NonConst<T const &&> { typedef T &&type; }; // by rvalue-reference

template<typename TConstReturn, class TObj, typename... TArgs>
typename NonConst<TConstReturn>::type likeConstVersion(
   TObj const* obj,
   TConstReturn (TObj::* memFun)(TArgs...) const,
   TArgs&&... args) {
      // Cast away const from the return type
      return const_cast<typename NonConst<TConstReturn>::type>(
         (obj->*memFun)(std::forward<TArgs>(args)...));
}

// Usage example:
struct T {
   int arr[100];

   int const &getElement(size_t i) const {
      return arr[i];
   }

   int &getElement(size_t i) {
      // Use the helper to call the const version and get a non-const reference
      return likeConstVersion(this, &T::getElement, i);
   }
};

This approach abstracts the const_cast logic into a reusable helper.

Solution 6: Static Helper with Template Instance Type

This method uses a static template function that takes a template parameter for the instance type, allowing it to deduce const-ness.

class X {
private:
    std::vector<Z> v; // Assuming Z is a type

    // Template to deduce instance type (const or non-const)
    template<typename InstanceType>
    static auto get(InstanceType &instance, std::size_t i) -> decltype(instance.get(i)) {
        // Massive amounts of code for validation...
        // 'instance' can be used to access class members.
        return instance.v[i];
    }

public:
    const Z &get(std::size_t i) const {
        return get(*this, i);
    }

    Z &get(std::size_t i) {
        return get(*this, i);
    }
};

This is clean but requires a static member, which might not always be desirable.

Solution 7: Private Helper for Controlled Access

A private helper function can contain the core logic, with the public getters acting as controlled interfaces.

class X {
private:
    // This method MUST NOT be called except from boilerplate accessors.
    Z &_getZ(size_t index) const {
        // Core logic
        return something; // Assuming 'something' is a member of Z or accessible
    }

public:
    // Boilerplate accessors
    Z &getZ(size_t index) { return _getZ(index); }
    const Z &getZ(size_t index) const { return _getZ(index); }
};

The key here is that _getZ is private, enforcing that it’s only called through the correctly qualified public accessors. If _getZ itself needs to const_cast a return value from another const-qualified function, careful consideration of the safety implications is needed, as noted in the original discussion.

Solution 8: Macro-Based Generation (C++17)

For those comfortable with macros and using C++17, a macro can simplify generating the non-const overload.

#include <utility>
#include <type_traits>

// Helper to get non-const type from const type
template <typename T> struct NonConst;
template <typename T> struct NonConst<T const &> { using type = T &; };
template <typename T> struct NonConst<T const *> { using type = T *; };

// Macro to generate non-const getter
#define NON_CONST(func) \
    template <typename... T> auto func(T &&... a) \
        -> typename NonConst<decltype(func(std::forward<T>(a)...))>::type \
    { \
        return const_cast<decltype(func(std::forward<T>(a)...))>( \
            std::as_const(*this).func(std::forward<T>(a)...)); \
    }

class X {
    const Z &get(size_t index) const { /* ... */ }
    NON_CONST(get) // Generates the non-const version
};

This reduces boilerplate by defining the NON_CONST macro once. Compiler support for this pattern might vary across versions (e.g., GCC 8.1+, Clang 5+).

Solution 9: Templated Implementation in .cpp

The complex logic can reside in a template function defined in the .cpp file, with public methods in the header calling this implementation.

// In .h file
class X {
    // ...
    Z &GetZ(size_t index);
    const Z &GetZ(size_t index) const;
};

// In .cpp file
template<class ParentPtr, class Child>
Child &GetZImpl(ParentPtr parent, size_t index) {
    // ... implementation using parent->GetVector()[index] ...
    return parent->GetVector()[index];
}

Z &X::GetZ(size_t index) {
    return GetZImpl<X *, Z>(this, index);
}

const Z &X::GetZ(size_t index) const {
    return GetZImpl<const X *, const Z>(this, index);
}

This pattern keeps the header clean, but requires careful management of member access (e.g., providing public getters for internal data or using friend declarations, though friends are often discouraged).

Solution 10: C++17 std::enable_if_t with Macros

This approach combines C++17 features with macros for conditional compilation based on type traits.

#include <type_traits>

#define REQUIRES(...) class = std::enable_if_t<(__VA_ARGS__)>
#define REQUIRES_CV_OF(A, B) REQUIRES(std::is_same_v<std::remove_cv_t<A>, B>)

class Foobar {
private:
    int something;

    template<class FOOBAR, REQUIRES_CV_OF(FOOBAR, Foobar)>
    static auto &_getSomething(FOOBAR &self, int index) {
        // Big, non-trivial chunk of code...
        return self.something;
    }

public:
    auto &getSomething(int index) { return _getSomething(*this, index); }
    auto &getSomething(int index) const { return _getSomething(*this, index); }
};

This uses std::enable_if_t to conditionally enable template instantiations based on the const-ness of the FOOBAR type.

Solution 11: CppCoreGuidelines Prefer Template Helpers

The C++ Core Guidelines recommend preferring template helper functions that deduce const-ness over direct const_cast in public methods.

// Less ideal, const_cast in public interface
class Foo {
public:
    Bar &get_bar() {
        return const_cast<Bar &>(static_cast<const Foo &>(*this).get_bar());
    }
    const Bar &get_bar() const { /* complex logic */ }
private:
    Bar my_bar;
};

// Preferred, logic in template helper
class Foo {
public:
    Bar &get_bar() { return get_bar_impl(*this); }
    const Bar &get_bar() const { return get_bar_impl(*this); }
private:
    Bar my_bar;

    template <class T> // Deduces const or non-const
    static auto &get_bar_impl(T &t) { /* complex logic */ }
};

The guideline emphasizes that while the const_cast pattern is safe when applied correctly, its safety is hard for compilers to automatically check. A template helper hides this complexity. Be mindful of code bloat if the helper contains significant non-dependent code.

Solution 12: Private Helper for Simplicity

If the logic is straightforward, a private helper that simply returns the reference might suffice, though this pattern is similar to Solution 7.

Solution 13: Private Static Helper with Explicit Return Types

Similar to Solution 3’s static template helper, this explicitly defines return types.

template <typename ReturnType, typename ThisType>
static ReturnType Z_impl(ThisType &self, size_t index);

// ...

Z &Z(size_t index) {
    return Z_impl<Z &>(*this, index);
}
const Z &Z(size_t index) const {
    return Z_impl<const Z &>(*this, index);
}

This offers clarity by explicitly stating the expected return types for const and non-const calls.

Solution 14: Macro for Identical Logic

For cases where the logic is exactly the same, a macro can explicitly declare this intent.

struct A {
#define GETTER_CORE_CODE \
    /* line 1 */ \
    /* line 2 */ \
    /* ... */ \
    /* line n */

   B &get() { GETTER_CORE_CODE }
   const B &get() const { GETTER_CORE_CODE }

#undef GETTER_CORE_CODE
};

This is explicit but relies heavily on macros, which can sometimes reduce readability.

Solution 15: Macro for Invoking Const Overload (C++98 Compatible)

A macro can wrap the call to the const overload, providing a reusable mechanism.

template <typename T> T &WithoutConst(const T &ref) { return const_cast<T &>(ref); }
template <typename T> T *WithoutConst(const T *ptr) { return const_cast<T *>(ptr); }
template <typename T> const T *WithConst(T *ptr) { return ptr; }

#define FROM_CONST_OVERLOAD(FunctionCall) \
  WithoutConst(WithConst(this)->FunctionCall)

// Usage
class MyClass {
    const std::string &GetRef(std::size_t index) const { return data[index]; }
    std::string &GetRef(std::size_t index) {
        return FROM_CONST_OVERLOAD(GetRef(index));
    }
    // ... other examples for pointers ...
};

This offers a clean syntax, works with C++98, and avoids extra member functions. It’s best suited when arguments map directly between overloads.

Solution 16: Macro for Generating Const/Non-Const Pairs

A macro can be used to automatically generate both versions, with a special token (CV) to mark const placement.

// C++20 style with __VA_OPT__
#define MAYBE_CONST(...) IMPL_CV_maybe_const( (IMPL_CV_null,__VA_ARGS__)() )
#define CV )(IMPL_CV_identity,
#define CV_IN(...) )(IMPL_CV_p_open,)(IMPL_CV_null,__VA_ARGS__)(IMPL_CV_p_close,)(IMPL_CV_null,
// ... implementation details ...

class A {
    MAYBE_CONST(
        CV int &GetX() CV { return x; } // Expands to 'int &GetX() { return x; }' and 'const int &GetX() const { return x; }'
    )
};

This is powerful but requires understanding complex macro expansions and has syntax considerations for nested parentheses.

Solution 17: Templated Private Helper with Instance Type

Similar to Solution 3’s static helper, this template allows passing the instance type explicitly.

template <class C, typename T>
static T privateGetI(C c) { // 'c' can be 'MyClass' or 'const MyClass'
    return c._i;
}

// Usage
class MyClass {
    int _i;
public:
    int getI() { return privateGetI<MyClass, int>(*this); }
    const int getI() const { return privateGetI<const MyClass, const int>(*this); }
};

This method effectively passes *this as either a MyClass or const MyClass object to the private helper.

Solution 18: Direct Duplication for Simple Getters/Setters

For very simple, one-line getters and setters, direct code duplication is often acceptable and easier to read than complex templating or macros. The key is keeping these snippets directly adjacent for maintainability.

Solution 19: Handling std::shared_ptr

The principles apply to smart pointers as well. For std::shared_ptr, a const_pointer_cast might be necessary.

// Assuming const_pointer_cast is defined appropriately
struct C {
  std::shared_ptr<const char> get() const { return c; }
  std::shared_ptr<char> get() {
    return const_pointer_cast<char>(static_cast<const C &>(*this).get());
  }
  std::shared_ptr<char> c;
};

This mirrors the const_cast approach but adapts it for smart pointer semantics.

Solution 20: Template Wrappers for Multiple Overloads

This approach uses template wrappers to handle multiple overloads of the same function name, especially when dealing with different argument types.

struct C {
  int x[10];
  // ... various const getter overloads ...

  template<typename... Ts>
  auto* getp(Ts... args) {
    // Use a wrapper to call the correct const overload and cast
    return const_cast<int*>(static_cast<const C*>(this)->getp(args...));
  }
};

template<typename T, typename... Ts>
auto* pwrap(T const* (C::*f)(Ts...) const, Ts... args) {
    return const_cast<T*>((this->*f)(args...));
}

int* C::getp_i(int i) { return pwrap(&C::getp_i, i); } // Example usage

This pattern can become complex, especially with argument matching for overloaded functions.

Solution 21: Macro with std::as_const for Getter

A macro leveraging std::as_const and a helper to remove const can provide a concise solution.

template <typename T> constexpr T &as_non_const(const T &t) noexcept { return const_cast<T &>(t); }

#define NON_CONST_GETTER(const_getter) \
  auto &const_getter() { return as_non_const(std::as_const(*this).const_getter()); }

class C {
  const int &get() const { return secret; }
  NON_CONST_GETTER(get); // Generates non-const version
};

This is similar to Solution 8 but uses a more focused macro for getter functions.

Solution 22: Template Specialization (No const_cast)

Some advanced techniques, like template specialization, might avoid const_cast altogether. However, for simple getters, the overhead might not be justified compared to carefully applied const_cast or helper functions. The key challenge with avoiding const_cast is often ensuring that the non-const version doesn’t inadvertently violate const semantics, especially if the underlying implementation is complex.

Choosing the Right Approach

The best solution depends on your project’s C++ standard support, the complexity of the shared logic, and your team’s coding standards.

  • C++23 Deducing this: If available, this is the most elegant and modern solution.
  • Private Template Helpers: Generally considered a robust and readable approach, balancing safety and code reuse.
  • std::as_const (C++17): A good improvement over manual casting for the common const_cast pattern.
  • Scott Meyers’ const_cast: A time-tested method, still widely applicable.
  • Macros: Useful for reducing boilerplate, but use judiciously to maintain readability.
  • Direct Duplication: Suitable for very simple, adjacent code snippets.

When making your choice, consider the trade-offs between code duplication, readability, maintainability, and the risk of introducing subtle bugs. Exploring these patterns helps in writing more robust and efficient C++ code.

FAQs on C++ Const/Non-Const Member Function Duplication

Q: Why is duplicating logic between const and non-const member functions a problem

ANS: Duplicating logic leads to increased maintenance effort. If you need to change the logic, you must update it in two places, increasing the risk of introducing inconsistencies or bugs. It also violates the DRY (Don’t Repeat Yourself) principle.

Q: What is the primary concern when a non-const function calls a const function and casts away const

ANS: The primary concern is ensuring that the object was actually mutable when the non-const function was called. If a const object were somehow passed to the non-const function, and that function then cast away const and modified the object, it would result in undefined behavior. The safety relies on the caller always having a non-const object when invoking the non-const member.

Q: Can I put the logic in the non-const function and have the const function call it

ANS: No, this is generally unsafe. If the const function calls the non-const function, and the non-const function modifies the object, it violates the const-correctness guarantee. The const function is expected to never modify the object’s state.

Q: Is std::as_const the same as static_cast<const T&>(*this)

ANS: std::as_const provides a slightly more semantic way to obtain a const reference to an object. While functionally similar to static_cast<const T&>(*this) for simple objects, std::as_const is designed specifically for this purpose and can be clearer in intent. It’s part of the C++17 standard library.

Q: Which C++ standard introduced the Deducing this feature

ANS: The Deducing this feature was introduced in the C++23 standard.
