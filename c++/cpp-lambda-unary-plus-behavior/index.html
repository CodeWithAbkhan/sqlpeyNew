“C++ Lambda Unary Plus Behavior: Function Pointer Conversion Explained”

How does the C++ standard dictate the behavior when the unary plus operator (+) is applied directly to a non-capturing lambda expression? Specifically, what is the resulting type, and why does this mechanism allow subsequent assignment to a standard function pointer?

The accepted interpretation confirms that yes, the code conforms to the C++ standard, and the unary plus operator explicitly triggers a conversion to a plain old function pointer for the lambda object.

Mechanism of Conversion: The Closure Type

When the compiler encounters a non-capturing lambda expression, such as []{} or [=](){ /* no captures */ }, it generates a unique, unnamed closure type as specified in [expr.prim.lambda] §5.1.2.

For lambdas that involve no captures (i.e., they do not capture any variables from the surrounding scope), the standard mandates a specific conversion capability within that closure type:

The closure type for a lambda-expression with no lambda-capture has a public non-virtual non-explicit conversion function to pointer to function having the same parameter and return types as the closure type’s function call operator.

This conversion function guarantees that the closure object can masquerade as a standard function pointer (T*) matching the lambda’s signature.

Role of the Unary Plus Operator

The reason the unary + is effective here lies in the overloads defined for the built-in operators, particularly [over.built] §13.6 (8):

For every type T there exist candidate operator functions of the form T* operator+(T*);

When the unary plus operator is applied to an instance of the lambda’s closure type, the overload resolution process evaluates candidate functions. Because the closure type possesses an exact conversion to a function pointer type, and the built-in operator+ exists for pointers, the compiler selects the overload that leverages this conversion.

The result is a clean promotion to the plain function pointer type corresponding to the lambda’s signature.

Code Demonstration

Consider the following scenario. We define a non-capturing lambda and then use the unary plus operator to deduce its resulting type.

#include <iostream>
#include <type_traits>

// Lambda signature: void()
auto lambda_expression = +[]{}; 

// Define the target function pointer type explicitly for comparison
using TargetFuncPtr = void(*)(); 

int main() {
    // 1. Check the type deduced after applying unary plus
    using DeducedType = decltype(lambda_expression);

    std::cout << "Is the deduced type a function pointer? " 
              << std::boolalpha << std::is_same_v<DeducedType, TargetFuncPtr> 
              << std::endl;
              
    // The resulting object 'lambda_expression' IS a function pointer.
    
    // 2. Direct assignment test
    TargetFuncPtr ptr_assignment = +[]{}; 
    
    std::cout << "Successfully assigned lambda conversion result to TargetFuncPtr." << std::endl;
    
    return 0;
}

In the example above, decltype(lambda_expression) will resolve to void(*)(), confirming the conversion to a standard function pointer.

Alternative Assignment Methods

While using the unary plus (+) is an explicit way to force this conversion during type deduction or assignment, the standard conversion mechanism also applies in contexts where a function pointer is explicitly expected:

  1. Direct Assignment: Assigning the non-capturing lambda directly to a function pointer variable type will invoke the conversion function implicitly.

    void call_it() { /* ... */ }

// The compiler implicitly calls the conversion function in this context
void(*fp_direct)() = [](){ std::cout << "Directly assigned." << std::endl; };
fp_direct();

  2. Function Call Argument: Passing the lambda as an argument to a function expecting a function pointer automatically triggers the conversion.

    void execute_callback(void(*cb)()) {
    cb();
}

execute_callback([](){ std::cout << "Passed as argument." << std::endl; });

The application of + simply makes this conversion explicit and observable when using decltype or when needing the precise function pointer type without the context of a function call. If the lambda captures variables, this conversion function is not generated, and applying + would result in a compilation error as there is no built-in overload for the closure object itself (see potential errors related to type deduction here: https://sqlpey.com/python/solved-how-to-fix-could-not-find-a-version-that-satisfies-the-requirement-error-in-python/ ).

FAQs on C++ Lambda Unary Plus Behavior

Q: What happens if the lambda captures state

ANS: If the lambda captures any variable (even by value, like [=]), the resulting closure type will not have the implicit conversion function to a plain function pointer. Applying the unary plus operator to a capturing lambda will typically result in a compilation error because no appropriate overload is found.

Q: Is the conversion function virtual

ANS: No, the standard explicitly states that the conversion function generated for a non-capturing lambda is public, non-virtual, and non-explicit.

Q: Can I always use auto with a non-capturing lambda

ANS: Yes, you can always use auto to deduce the closure type itself. However, applying + before auto forces the deduction to the resultant function pointer type, as shown in the explanation.
