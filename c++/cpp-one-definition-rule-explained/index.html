“C++ One-Definition Rule Explained: TU Violations and Linker Errors”

The behavior surrounding multiple definitions in C++ programming is strictly governed by the One-Definition Rule (ODR), primarily detailed in the C++ standard’s [basic.def.odr] subclause. This rule dictates where and how entities like variables, functions, classes, and templates can be defined within a program to maintain integrity and avoid ambiguity during linking.

How precisely does the standard define the limits on definitions across the program?

Constraints Within a Single Translation Unit

The most fundamental aspect of the ODR concerns a single translation unit (TU), which is essentially one source file after preprocessing.

Rule Summary from the Standard (3.2 One definition rule)

No translation unit shall contain more than one definition of any variable, function, class type, enumeration type or template.

This means that within one .cpp file, every entity must have at most one definition.

Practical Implication: Attempting to define the same non-inline entity twice in the same file typically results in a compiler error indicating a “re-definition.”

Consider this C++ snippet demonstrating a TU violation:

// main.cpp (A single translation unit)

void process_data() { /* Implementation A */ }
void process_data() { /* Implementation B - Compiler Error */ } // Multiple definition!

class Configuration { int value = 10; };
class Configuration { int value = 10; }; // Error: Redeclaration of class type

Definitions Across Multiple Translation Units

The ODR becomes more nuanced when dealing with multiple TUs (e.g., different .cpp files). The rule here shifts focus to ensuring that every entity used in the program has exactly one definition available during the linking phase, with specific exceptions for inline functions and templates.

The Program-Level Definition Requirement

For any definable item $D$ that has definitions appearing in multiple translation units:

  1. If $D$ is a non-inline, non-templated function or variable, the program is ill-formed if its definitions across TUs differ, or if more than one exists.
  2. If definitions exist in different TUs, they must satisfy stringent equivalence requirements.

Practical Implication: If you define a standard function or variable in file1.cpp and again in file2.cpp, even if the definitions look identical, the program will likely fail during the linker phase, reporting a “multiple definitions of…” error. This is why definitions generally belong in source files, not headers, unless specific inclusion rules are met.

Special Treatment for Inline Functions and Templates

Templates and inline functions are exceptions because they can be defined across multiple TUs. However, this allowance comes with a strict caveat: all definitions across all TUs where they are used must be equivalent.

For example:

// utility.h (Included in multiple TUs)

// TU 1 (file_a.cpp)
inline int calculate_score(int base) { return base * 2; } // Definition 1

// TU 2 (file_b.cpp)
inline int calculate_score(int base) { return base * 2; } // Definition 2 (Equivalent - OK)

// TU 3 (file_c.cpp)
inline int calculate_score(int base) { return base + 10; } // Definition 3 (Not Equivalent - Ill-formed)

If Definition 3 is present, the program is ill-formed, although the standard permits the compiler to issue no diagnostic (i.e., it might not flag the error immediately, leaving undefined behavior for the linker).

ODR-Use and Definition Existence

The ODR also mandates that anything an entity is “odr-used” in must have a definition present in the final program.

What constitutes ODR-use? ODR-use occurs when a construct is used in a way that requires its actual definition to be known, for instance, when its value is being computed or its memory address taken.

What is NOT ODR-use? Operations within an unevaluated context generally do not trigger ODR-use. A common example is decltype.

A contrast example:

// Function declaration (only a promise of a definition elsewhere)
int retrieve_status(); 

// Not ODR-use: The compiler only needs to know the type signature, not the body.
using StatusType = decltype(retrieve_status()); 

// ODR-use: The function body must exist to calculate the result.
int current_value = retrieve_status(); // Linker error if not defined!

If a function or variable is odr-used but has no definition supplied anywhere (not in a TU, not implicitly defined, not in a required library), the result is a linker error stating “no definition of [entity]”.

FAQs on C++ One Definition Rule Explained

Q: What is the main consequence of violating the ODR within one C++ source file

ANS: The compiler typically raises an immediate error signaling a “re-definition” of the item within that single translation unit.

Q: When can an inline function have different definitions across different source files

ANS: It cannot. All definitions of an inline function used across different translation units must be strictly equivalent according to the standard.

Q: Does using decltype on a function name trigger ODR-use

ANS: No, using decltype on a function name is an unevaluated context and does not trigger ODR-use, meaning a definition is not immediately required.

Q: What error results if a non-inline function is defined in two separate .cpp files

ANS: This usually results in a linker error indicating “multiple definitions” for that function.
