“C++ Memory Management: When to Use delete vs delete[] Operators”

In C++ memory management, correctly pairing allocation and deallocation operators is crucial to prevent undefined behavior and memory leaks. The choice between delete and delete[] directly impacts how destructors are called for single objects versus arrays of objects.

Core Differentiation: Single Objects vs. Arrays

The fundamental divergence lies in what the pointer points to: a single instance created via new, or a contiguous block of memory allocated for multiple instances via new[].

  1. delete Operator: This is designated for deallocating memory associated with a single object allocated using new. It ensures the object’s destructor is executed once, followed by the release of the allocated heap memory.

  2. delete[] Operator: This is specifically required to deallocate memory for an array of objects created using new[]. It performs two vital steps:

    • It calls the destructor for every element within the array.
    • It then releases the entire contiguous memory block back to the system.

Mismatched usage, such as using delete on memory allocated by new[], or conversely, using delete[] on memory allocated by new, leads to undefined behavior. Runtime environments often store metadata (like array size) adjacent to the allocated block for use by delete[]. Using the wrong operator causes the runtime to misinterpret this metadata, leading to potential corruption or failure to call destructors for all array elements.

Operator Selection Mechanics

The Standard Library mandates specific lookups based on the allocation method:

  • Allocation with new T (Single Object): The system looks for a global operator delete or one defined within class T’s scope. It passes exactly sizeof(T) bytes for deallocation.
  • Allocation with new T[N] (Array): The system searches for operator delete[] (global or in class scope). Crucially, the allocation routine often requests more memory than simply $N \times \text{sizeof(ElementType)}$ to embed array size information. This size information is what delete[] uses to correctly iterate and call destructors $N$ times.

If a class has a non-default destructor, failing to use delete[] after new[] will result in memory leaks because the destructors for elements beyond the first will not be invoked.

Illustrative Code Scenarios

Consider the following allocation patterns and their corresponding correct deallocation:

// Scenario 1: Single Object Allocation
int* single_ptr = new int;
delete single_ptr; // Correct deallocation

// Scenario 2: Array Allocation
double* array_ptr = new double[50];
delete[] array_ptr; // Correct deallocation for an array of 50 doubles

// Scenario 3: Array of Custom Objects
class DataContainer {
public:
    DataContainer() { std::cout << "Constructor called." << std::endl; }
    ~DataContainer() { std::cout << "Destructor called." << std::endl; }
};

DataContainer* collection = new DataContainer[5];
// WRONG: delete collection; // Undefined behavior, only first destructor called if at all!
delete[] collection; // Correct: Destructors for all 5 objects are called.

Examining Specific Type Declarations

The standard also accounts for array types defined via typedef:

typedef int array_of_one[1];

// Creating a dynamic object of array type (behaves like new int[1] conceptually)
array_of_one *a = new array_of_one; 
delete[] a; // Requires delete[] because 'new array_type' implies array allocation rules apply.

// Creating a standard single int
int *b = new int;
delete b; // Requires simple delete

// Creating an explicit array of one int
int *c = new int[1];
delete[] c; // Requires delete[]

// Creating a multi-dimensional array pointer (pointer to an array of 2 ints)
int (*d)[2] = new int[1][2]; // Allocates one block for one array of 2 ints
delete[] d; // Requires delete[] as it was allocated via array form new[][].

Alternative Allocation Methods

While new/delete are the C++ idiomatic tools, standard C library functions provide lower-level memory control, though they bypass constructor/destructor calls entirely:

  • malloc() / free(): malloc allocates raw memory, and free releases it. These are unsuitable for complex objects with destructors.
  • Smart Pointers: In modern C++, std::unique_ptr and std::shared_ptr are strongly preferred. They automate deallocation, adhering to RAII principles.
    • For single objects: std::unique_ptr<T> ptr(new T); cleans up automatically with delete.
    • For arrays: std::unique_ptr<T[]> ptr(new T[N]); cleans up automatically with delete[].

If your class relies on specific resource cleanup within its destructor (e.g., closing files or releasing locks), using the wrong delete operator directly causes resource mismanagement. Check resources like the official C++ documentation on memory allocation for deeper specification details.

FAQs on C++ Memory Management

Q: Why is using delete on memory allocated by new[] bad

ANS: Using delete on memory allocated by new[] results in undefined behavior because the runtime system cannot determine how many destructors need to be called, potentially leading to memory corruption or only destroying the first element.

Q: What operator does new[] look for

ANS: For an array allocation like new T[N], the Standard looks for operator delete[] in the global scope or within the class type T’s scope for deallocation later.

Q: Does delete call the base class destructor correctly

ANS: If the pointer passed to delete is a base class pointer but points to a derived object, the base class destructor must be virtual for correct behavior; otherwise, only the base class destructor is called, leading to undefined behavior for the derived parts.
