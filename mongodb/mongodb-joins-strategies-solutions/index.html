MongoDB Joins: Strategies and Solutions

When working with MongoDB, a NoSQL database, the concept of “joins” differs from relational databases like SQL. While MongoDB doesn’t natively support traditional SQL joins, several powerful techniques and strategies allow you to achieve similar results, effectively combining data from different collections. This post explores these methods, providing practical code examples and insights.

The $lookup Operator: A Primary Tool

Introduced in MongoDB 3.2, the $lookup aggregation operator is the primary mechanism for performing “joins” between collections. It functions similarly to a left outer join in SQL, adding documents from a “joined” collection to the input documents.

Syntax:

{
   $lookup:
     {
       from: "<collection to join>",
       localField: "<field from the input documents>",
       foreignField: "<field from the documents of the 'from' collection>",
       as: "<output array field>"
     }
}

Example Scenario: Joining Comments and Users

Let’s consider two collections: comments and users. We want to retrieve comments and include the associated user information.

  • Comments Collection:

    db.comments.insertMany([
  { uid: 12345, pid: 444, comment: "This is a great post!" },
  { uid: 12345, pid: 888, comment: "Interesting point." },
  { uid: 99999, pid: 444, comment: "I agree." }
]);

  • Users Collection:

    db.users.insertMany([
  { uid: 12345, name: "Alice" },
  { uid: 99999, name: "Bob" }
]);

Using $lookup for Joining:

To join comments with users on the uid field:

db.comments.aggregate([
   {
     $lookup: {
       from: "users",             // The collection to join with
       localField: "uid",         // Field from the input documents (comments)
       foreignField: "uid",       // Field from the documents of the "from" collection (users)
       as: "userData"             // Output array field name
     }
   }
]);

This query will return comments, with each document having an added userData array containing matching user documents.

Handling Multiple Join Conditions

The $lookup operator can be chained to perform joins on multiple fields, similar to SQL’s composite join conditions.

Example: Joining LeftTable and RightTable with multiple conditions

Consider the SQL query: SELECT S.* FROM LeftTable S LEFT JOIN RightTable R ON S.ID = R.ID AND S.MID = R.MID WHERE R.TIM > 0 AND S.MOB IS NOT NULL

This can be achieved in MongoDB using a sequence of $lookup, $unwind, $project, and $match stages:

db.LeftTable.aggregate([
  // Stage 1: Link all tables
  {
    $lookup: {
      from: "RightTable",
      localField: "ID",
      foreignField: "ID",
      as: "R"
    }
  },
  { $unwind: "$R" }, // De-normalize the array from $lookup

  // Stage 2: Define all conditionals
  {
    $project: {
      midEq: { $eq: ["$MID", "$R.MID"] }, // Condition for MID equality
      ID: 1, MOB: 1, MID: 1, "R.TIM": 1 // Select fields for later use
    }
  },

  // Stage 3: Join all the conditionals
  {
    $match: {
      $and: [
        { "R.TIM": { $gt: 0 } },    // WHERE R.TIM > 0
        { MOB: { $exists: true } }, // WHERE S.MOB IS NOT NULL
        { midEq: { $eq: true } }    // AND S.MID = R.MID
      ]
    }
  },

  // Stage 4: Undefine conditionals
  {
    $project: {
      midEq: 0 // Remove the helper field
    }
  }
]);

Client-Side Data Manipulation

Before $lookup was introduced, or in scenarios where complex joins are needed or when using older MongoDB versions, client-side processing was common. This involves fetching data from multiple collections separately and then merging them in your application code.

Example: Iterative Fetching

// Hypothetical JavaScript example
db.users.find().forEach(function (user) {
    var userComments = db.comments.find({ "uid": user.uid }).toArray();
    // Process user and userComments together
    printjson({ user: user, comments: userComments });
});

This approach can be less efficient for large datasets due to multiple round trips to the database and requires careful handling of the data in the application layer.

Denormalization and Embedded Documents

MongoDB’s schema flexibility often encourages denormalization. Instead of relating data through separate collections, you can embed related data directly within a document. For example, if a story always requires its author’s username, you could embed the username in the story document.

Example: Embedding Category Information

If you have a books collection and a categories collection, you could embed category details into the book document during insertion or update.

  • Initial Setup:

    // Authors, Categories, Books, and Lendings setup as provided in the original content.
db.authors.insert([
    { _id: 'a1', name: { first: 'orlando', last: 'becerra' }, age: 27 },
    { _id: 'a2', name: { first: 'mayra', last: 'sanchez' }, age: 21 }
]);
db.categories.insert([
    { _id: 'c1', name: 'sci-fi' },
    { _id: 'c2', name: 'romance' }
]);
db.books.insert([
    { _id: 'b1', name: 'Groovy Book', category: 'c1', authors: ['a1'] },
    { _id: 'b2', name: 'Java Book', category: 'c2', authors: ['a1', 'a2'] }
]);
db.lendings.insert([
    { _id: 'l1', book: 'b1', date: new Date('01/01/11'), lendingBy: 'jose' },
    { _id: 'l2', book: 'b1', date: new Date('02/02/12'), lendingBy: 'maria' }
]);

  • Merging Data into a New Collection:

    db.books.find().forEach(function (newBook) {
    newBook.category = db.categories.findOne({ "_id": newBook.category });
    newBook.lendings = db.lendings.find({ "book": newBook._id }).toArray();
    newBook.authors = db.authors.find({ "_id": { $in: newBook.authors } }).toArray();
    db.booksReloaded.insert(newBook);
});

db.booksReloaded.find().pretty();

    This process creates a new collection (booksReloaded) with embedded related data.

  • playORM with S-SQL: Offers joins within partitions for scalable SQL operations.

MapReduce for Data Restructuring

The mapReduce function can be used to restructure data, effectively creating relationships between collections, though it’s generally more complex than $lookup.

Example: Restructuring Actors and Movies

To create a movies collection with embedded actor lists from an actors collection:

// Map function
var map = function() {
  for(var i in this.movies){
    key = { movie: this.movies[i] };
    value = { actors: [ this.actor ] };
    emit(key, value);
  }
}

// Reduce function
var reduce = function(key, values) {
  actor_list = { actors: [] };
  for(var i in values) {
    actor_list.actors = values[i].actors.concat(actor_list.actors);
  }
  return actor_list;
}

// Execute mapReduce and output to 'pivot' collection
db.actors.mapReduce(map, reduce, "pivot");
db.pivot.find().forEach(printjson);

DBRefs and Manual References

MongoDB supports two ways to reference documents in other collections:

  • Manual References: Storing the _id of a document from another collection. This is the most common and efficient method when the referenced collection is known.
  • DBRefs: A more formal specification that includes the collection name and the document’s _id. Useful when the referenced collection might change.

Considerations for Normalization vs. Denormalization

While the temptation to replicate relational database structures in MongoDB exists, it’s crucial to leverage MongoDB’s strengths. Denormalization can often lead to better performance for read operations by reducing the need for joins. However, it can increase data redundancy and complexity in update operations. The choice depends on your specific use case, read/write patterns, and performance requirements. For read-heavy workloads, denormalization is often favored.

The concept of “client-side joins” where you fetch data and combine it in your application layer is a valid strategy in NoSQL. It often avoids issues with duplicate rows common in SQL’s many-to-many joins and allows your application servers to handle the heavy lifting.

If your primary need is normalized data and complex relational queries, exploring other database solutions might be more appropriate.

FAQs on MongoDB Joins

Q: Can I perform joins in MongoDB like in SQL

ANS: MongoDB doesn’t have direct SQL-style JOINs. However, the $lookup aggregation operator provides functionality similar to a left outer join. You can also achieve join-like behavior through client-side data manipulation or denormalization.

Q: What is the $lookup operator

ANS: The $lookup operator is an aggregation stage that performs a left outer join to another collection in the same database. It adds a new array field to the input documents, containing matching documents from the joined collection.

Q: How to join multiple collections in MongoDB

ANS: You can chain multiple $lookup stages in an aggregation pipeline to join several collections. Additionally, you can use client-side logic or plugins like mongo-join to manage complex joins across multiple collections.

Q: Is denormalization always necessary for MongoDB joins

ANS: Denormalization is an option to consider for performance, but not always necessary. $lookup and client-side fetching are effective alternatives. Embedding related data can improve read performance by reducing the need for joins.

Q: What are manual references and DBRefs

ANS: Manual references store the _id of a related document. DBRefs are a more formal specification including the collection name and _id, useful when the referenced collection might change.
