“MongoDB Strategies for Combining Data Across Collections”

This document outlines several accepted approaches for correlating data across multiple MongoDB collections, ranging from native aggregation features to older MapReduce patterns.

Approach 1: Using $lookup Aggregation Stage for Left Outer Joins

Since MongoDB version 3.2, the $lookup aggregation stage provides a mechanism analogous to a left outer join, allowing data from a “foreign” collection to be incorporated into documents from a “local” collection based on matching fields.

Scenario Example: Merging book details from the books collection with sales figures from books_selling_data using the isbn field.

Initial Data Structures:

Collection books:

{
    "isbn": "978-3-16-148410-0",
    "title": "Some cool book",
    "author": "John Doe"
}
// ... other books

Collection books_selling_data:

{
    "_id": ObjectId("56e31bcf76cdf52e541d9d26"),
    "isbn": "978-3-16-148410-0",
    "copies_sold": 12500
}
// ... multiple entries can exist for one ISBN

Aggregation Query:

To join these collections:

db.books.aggregate([
    {
        $lookup: {
            from: "books_selling_data",
            localField: "isbn",
            foreignField: "isbn",
            as: "sales_records" // The resulting field will be an array
        }
    }
])

Result Interpretation: The output document from the books collection will now include a field (sales_records in this rewritten example, named copies_sold originally) containing an array of matching documents from books_selling_data.

Key Considerations for $lookup:

  • The from collection specified in $lookup cannot be sharded.
  • The output field specified by as will invariably be an array, even if only zero or one match is found.
  • If localField or foreignField are absent in their respective documents, they are treated as null for matching purposes.

If the goal is to achieve a flattened field, rather than an array of joined documents (like summarizing total copies sold), further pipeline stages such as $unwind followed by $group (with summation) would be necessary.

Approach 2: Utilizing Map-Reduce for Data Consolidation

Prior to extensive aggregation pipeline features, Map-Reduce offered a powerful, albeit asynchronous, method for combining data, particularly useful for creating derived collections. This is often best suited for batch processing, such as cron jobs, rather than real-time lookups.

Scenario Example: Merging user demographics (users collection) with user comments (comments collection based on userId).

The process involves running mapReduce on each source collection and directing the output to the same “reduce” collection using the {"out": {"reduce": "target_collection"}} option.

Map Functions: Define how data from each source should be emitted with a common key (e.g., userId or _id).

// Map function for users collection
var mapUsers = function() {
    var values = {
        country: this.country,
        gender: this.gender,
        age: this.age
    };
    emit(this._id, values);
};

// Map function for comments collection
var mapComments = function() {
    var values = {
        commentId: this._id,
        comment: this.comment,
        created: this.created
    };
    emit(this.userId, values);
};

Reduce Function: Defines logic to merge emitted values associated with the same key. A complex reduce function is needed to discern which source the value came from (e.g., by checking for existence of fields like "comment" vs. demographic fields).

After executing db.users.mapReduce(mapUsers, reduce, {"out": {"reduce": "users_comments"}}); and then db.comments.mapReduce(mapComments, reduce, {"out": {"reduce": "users_comments"}});, the users_comments collection will contain merged documents keyed by the user identifier.

Post-Processing for Flattening: If the resulting structure contains nested arrays (like comments within a user document), another map-reduce job can be executed to “flatten” the data structure, producing one document per comment while carrying over the demographic information. Note that indexing the final collection, e.g., db.comments_with_demographics.ensureIndex({"value.created": 1}), is crucial for performance, as data resides within the value field post-MapReduce.

Approach 3: Simulating SQL UNION with Aggregation and $lookup (MongoDB 4.0+)

For operations resembling a UNION ALL in SQL—combining results from two conceptually separate sources into one pipeline result—a specific aggregation trick is employed. This technique relies on an initial document to host the lookups.

Prerequisite: The pipeline must start from a collection known to have at least one document. If this cannot be guaranteed, a dummy collection containing a single empty document should exist.

Query Steps:

  1. Start aggregation on a collection (e.g., freelancers).
  2. Limit to one document ($limit: 1) and remove all its fields ($project: { _id: '$$REMOVE' }) to get a blank slate document {}.
  3. Use sequential $lookup stages to fetch data from all source collections you wish to “union,” aliasing each result (e.g., $employees, $freelancers). Pipelines within $lookup allow initial filtering.
  4. Combine these arrays using $project and $concatArrays.
  5. Finally, use $unwind followed by $replaceRoot to deconstruct the combined array back into individual documents.
db.freelancers.aggregate([
    { $limit: 1 }, 
    { $project: { _id: '$$REMOVE' } }, 

    // Lookup source collections
    { $lookup: { from: 'employees', pipeline: [{ $match: { department: 'sales' } }], as: 'employees_data' } },
    { $lookup: { from: 'freelancers', pipeline: [{ $match: { department: 'sales' } }], as: 'freelancers_data' } },

    // Combine arrays
    { $project: { union_result: { $concatArrays: ["$employees_data", "$freelancers_data"] } } },

    // Flatten the result set
    { $unwind: '$union_result' },
    { $replaceRoot: { newRoot: '$union_result' } }
]);

Approach 4: Native Set Union with $unionWith (MongoDB 4.4+)

For versions MongoDB 4.4 and later, the $unionWith aggregation stage offers a direct, cleaner way to perform a set union of documents from another collection directly within an aggregation pipeline. This is often superior to the $lookup trick for simple unions.

Coupling $unionWith with the $group stage and the flexible $accumulator operator allows for complex merging logic when combining documents from disparate schemas (like combining user profiles, book records, and movie records based on a common user ID).

db.users.aggregate([
  { $unionWith: "books"  }, // Merges documents from 'books'
  { $unionWith: "movies" }, // Merges documents from 'movies'
  { $group: {
    _id: "$user", // Assuming 'user' field links documents across collections
    user_details: {
      $accumulator: {
        accumulateArgs: ["$name", "$book", "$movie"],
        init: function() { return { books: [], movies: [] } },
        accumulate: function(state, name, book, movie) {
          if (name) state.name = name;
          if (book) state.books.push(book);
          if (movie) state.movies.push(movie);
          return state;
        },
        merge: function(state1, state2) {
          // Logic to merge accumulator states if running distributedly
          if (state2.name) state1.name = state2.name;
          state1.books = state1.books.concat(state2.books);
          state1.movies = state1.movies.concat(state2.movies);
          return state1;
        },
        lang: "js"
      }
    }
  }}
])

Approach 5: Chaining Multiple $lookup with Null-Tolerant $unwind

When linking a primary collection to several secondary collections (one-to-one or one-to-many relationships) and you must preserve all primary documents even if related data is missing, utilize $lookup followed by $unwind using the preserveNullAndEmptyArrays: true option.

If a lookup yields an empty array (no match), a standard $unwind removes the document, whereas using the option keeps the document structure intact, inserting null for the unwound field.

db.users.aggregate([
    {
        $lookup: {
            from: "userinfo",
            localField: "userId",
            foreignField: "userId",
            as: "userInfoData"
        }
    },
    {
        $lookup: {
            from: "userrole",
            localField: "userId",
            foreignField: "userId",
            as: "userRoleData"
        }
    },
    // Preserves user documents even if userinfo or userrole are missing
    { $unwind: { path: "$userInfoData", preserveNullAndEmptyArrays: true }},
    { $unwind: { path: "$userRoleData", preserveNullAndEmptyArrays: true }}
])

Approach 6: Simple Iterative Insertion (Application Layer Alternative)

For cases where performance isn’t hyper-critical or when migrating data without complex logic, simple iteration and insertion can combine collections (e.g., moving data from small_collection to big_collection):

db.small_collection.find().forEach(function(obj){ 
   db.big_collection.insert(obj)
});

Approach 7: Multiple Lookups and Unwinds for Detailed Correlation

Similar to Approach 5, this pattern is typical when one document needs to pull related data from several distinct collections simultaneously, often resulting in a highly denormalized output document.

Example Detail: Retrieving service location details along with associated orders and service time types. Note the $unwind stages on both $orders and $serviceTime to flatten these relationships if required.

db.servicelocations.aggregate([
  {
    $match: {
      serviceLocationId: { $in: ["36728"] }
    }
  },
  {
    $lookup: {
      from: "orders",
      localField: "serviceLocationId",
      foreignField: "serviceLocationId",
      as: "orders"
    }
  },
  {
    $lookup: {
      from: "timewindowtypes",
      localField: "timeWindow.timeWindowTypeId",
      foreignField: "timeWindowTypeId",
      as: "timeWindow" // Note: this lookup returns array elements that may need further processing
    }
  },
  {
    $lookup: {
      from: "servicetimetypes",
      localField: "serviceTimeTypeId",
      foreignField: "serviceTimeTypeId",
      as: "serviceTime"
    }
  },
  { $unwind: "$orders" },
  { $unwind: "$serviceTime" },
  { $limit: 14 }
])

Approach 8: Data Consolidation via mongodump and mongorestore

An operational method involves using MongoDB utilities. A process could involve dumping one collection, renaming the second collection to match the first, and then restoring the dump. This effectively overwrites or merges content at the filesystem level, although this is not an in-database query solution.

# Conceptual steps:
mongodump --db mydatabase --collection collection1
# Manually rename collection2 to collection1 in the dump directory structure
mongorestore --db mydatabase

This is generally faster for very large dataset moves but lacks transactional safety compared to query-based operations.

Approach 9: Custom Utility Function for Data Transfer

A custom JavaScript function executable in the Mongo shell can loop through source collections and insert their contents into a target collection.

function transferDocuments(targetCollectionName, sourceCollectionName1 /*, sourceCollectionName2, ... */) {
  const targetCol = db.getCollection(targetCollectionName);
  for (let i = 1; i < arguments.length; i++) {
    const sourceCol = db.getCollection(arguments[i]);
    sourceCol.find().forEach(
        function (doc) {
            targetCol.insert(doc);
        }
    );
  }
}
// Usage: transferDocuments("master_collection", "temp_data_1", "temp_data_2");

Approach 10: Complex MapReduce for Many-to-One Joins and Flattening

This demonstrates a more intricate Map-Reduce sequence to simulate a join between customers (cust) and zip code details (zip) and then flatten the intermediate result for direct querying. This involves two map-reduce passes.

  1. First Pass (Reduce): Merge cust and zip data into an intermediate collection (cust_zip) keyed by zip_id.
  2. Second Pass (Flatten): Remap the intermediate collection to create one document per customer by iterating through the cust_ids array within the reduced documents.
  3. Final Cleanup: A shell function flattenMRCollection iterates over the results of the second map-reduce job, which typically nests the final data inside a $value field, and uses a bulk write operation to replace those documents with their contents, making them directly queryable.

Approach 11: Application-Level Reference Resolution

If data integration needs to be managed outside the database, application frameworks utilizing Object-Relational Mappers (ORMs) or Object-Document Mappers (ODMs) like Morphia can handle data linking via references (e.g., @Reference annotations). The ODM layer abstracts the need for manual $lookup or Map-Reduce by fetching related entities automatically when a document is queried.

FAQs on MongoDB Data Combination Strategies

Q: Which MongoDB version introduced $lookup for joins

ANS: The $lookup aggregation stage, enabling join-like functionality, was introduced starting in MongoDB version 3.2.

Q: Can $lookup be used on a sharded collection

ANS: No, the collection specified in the from field of the $lookup stage must not be sharded.

Q: Is map-reduce a real-time join alternative

ANS: Map-Reduce is typically used for batch processing or asynchronous data aggregation, not for immediate, real-time joins within a standard query execution path.

Q: What is the benefit of $unionWith over $lookup trick

ANS: $unionWith (available MongoDB 4.4+) is a dedicated aggregation stage for set union operations, offering cleaner syntax and likely better performance than the multi-stage $lookup and $concatArrays workaround.

Q: How to avoid document loss with $unwind after $lookup

ANS: Use the option { $unwind: { path: "$fieldName", preserveNullAndEmptyArrays: true }}. This ensures parent documents are kept even if the lookup array (fieldName) is empty.
