“Solved: How to Retrieve Rows with Maximum Value Per Group in SQL”

While a simple GROUP BY with MAX() can give you the maximum value, it won’t automatically bring along other column data from that specific row. This comprehensive guide explores multiple powerful and efficient SQL approaches to tackle this widely encountered scenario.

Let’s consider a sample table named DocumentRevisions with columns record_id, version_num, and detail_info.

Our goal is to get the full row for each record_id that has the highest version_num.

Approach 1: Joining with a Subquery for Maximum Values

This method is highly common and widely supported across various SQL databases, including PostgreSQL and MySQL . It involves two main steps: first, identify the maximum version_num for each record_id using a subquery; second, join this result back to the original table to retrieve the associated detail_info.

SELECT
    dr.record_id,
    dr.version_num,
    dr.detail_info
FROM
    DocumentRevisions dr
INNER JOIN (
    SELECT
        record_id,
        MAX(version_num) AS max_version
    FROM
        DocumentRevisions
    GROUP BY
        record_id
) AS max_revs ON dr.record_id = max_revs.record_id AND dr.version_num = max_revs.max_version;

This query first finds the highest version_num for each record_id in the max_revs subquery. Then, it joins DocumentRevisions back to max_revs on both record_id and version_num. If there are multiple rows with the same maximum version_num for a given record_id (i.e., a tie), all such rows will be included in the result.

Approach 2: Using the IN Clause with a Subquery

A more concise way to achieve a similar outcome, especially favored for its readability, is by using the IN clause. This approach leverages a subquery to generate a set of (record_id, max_version) pairs, and then filters the main table based on whether its (record_id, version_num) pair exists in this set.

SELECT
    *
FROM
    DocumentRevisions
WHERE
    (record_id, version_num) IN (
        SELECT
            record_id,
            MAX(version_num)
        FROM
            DocumentRevisions
        GROUP BY
            record_id
    );

This method can be particularly appealing for its simplified syntax, making it easier to read and maintain for many developers. It’s often well-optimized by modern RDBMS.

Approach 3: Left Join with Self and Filtering NULL Values

This clever technique involves performing a LEFT OUTER JOIN of the table with itself. The key is how the join conditions are set up.

SELECT
    dr1.*
FROM
    DocumentRevisions dr1
LEFT OUTER JOIN
    DocumentRevisions dr2 ON dr1.record_id = dr2.record_id AND dr1.version_num < dr2.version_num
WHERE
    dr2.record_id IS NULL;

In this query, dr1 is joined to dr2 on record_id. The critical second join condition, dr1.version_num < dr2.version_num, ensures that if dr1’s version is not the maximum for its record_id, there will be a matching row in dr2 with a higher version_num. For rows where dr1.version_num is the maximum, no dr2 row will satisfy dr1.version_num < dr2.version_num, resulting in NULL values in dr2’s columns (because it’s a LEFT JOIN). Filtering WHERE dr2.record_id IS NULL then isolates only those rows from dr1 that have the maximum version_num per record_id.

Approach 4: Leveraging SQL Window Functions (Recommended)

Window functions, introduced in ANSI/ISO Standard SQL:2003, offer one of the most powerful and often performant ways to solve the “greatest-n-per-group” problem. They allow you to perform calculations across a set of table rows that are related to the current row without having to group the result set.

Using ROW_NUMBER() is a prime example:

SELECT
    ranked_revisions.record_id,
    ranked_revisions.version_num,
    ranked_revisions.detail_info
FROM (
    SELECT
        record_id,
        version_num,
        detail_info,
        ROW_NUMBER() OVER (PARTITION BY record_id ORDER BY version_num DESC) AS revision_rank
    FROM
        DocumentRevisions
) AS ranked_revisions
WHERE
    ranked_revisions.revision_rank = 1;

Here, ROW_NUMBER() OVER (PARTITION BY record_id ORDER BY version_num DESC) assigns a unique rank to each row within its record_id group. The row with the highest version_num gets a rank of 1. The outer query then simply selects rows where revision_rank is 1.

There are other ranking functions like RANK(), DENSE_RANK(), and NTILE() that can handle ties differently:

  • ROW_NUMBER(): Assigns a unique rank (e.g., 1, 2, 3) even if values are tied.
  • RANK(): Assigns the same rank to tied values, but skips the next rank (e.g., 1, 1, 3).
  • DENSE_RANK(): Assigns the same rank to tied values, but does not skip the next rank (e.g., 1, 1, 2).

For example, to get all rows in case of a tie with RANK():

SELECT
    ranked_revisions.record_id,
    ranked_revisions.version_num,
    ranked_revisions.detail_info
FROM (
    SELECT
        record_id,
        version_num,
        detail_info,
        RANK() OVER (PARTITION BY record_id ORDER BY version_num DESC) AS revision_rank
    FROM
        DocumentRevisions
) AS ranked_revisions
WHERE
    ranked_revisions.revision_rank = 1;

Another window function approach uses MAX() as an analytic function:

SELECT
    dr.record_id,
    dr.version_num,
    dr.detail_info
FROM (
    SELECT
        record_id,
        version_num,
        detail_info,
        MAX(version_num) OVER (PARTITION BY record_id) AS group_max_version
    FROM
        DocumentRevisions
) AS dr
WHERE
    dr.version_num = dr.group_max_version;

This query computes the maximum version_num for each record_id across all rows in the group (group_max_version) and then filters for rows where the version_num matches this calculated group maximum. This can be faster than ROW_NUMBER() in some scenarios as MAX() complexity might be lower.

Approach 5: Correlated Subquery

A correlated subquery executes for each row processed by the outer query. While sometimes less performant for very large datasets without proper indexing, it’s a clear and readable solution.

SELECT
    dr_outer.record_id,
    dr_outer.version_num,
    dr_outer.detail_info
FROM
    DocumentRevisions dr_outer
WHERE
    dr_outer.version_num = (
        SELECT
            MAX(dr_inner.version_num)
        FROM
            DocumentRevisions dr_inner
        WHERE
            dr_outer.record_id = dr_inner.record_id
    );

This query selects rows from dr_outer where its version_num matches the maximum version_num found for that specific record_id (as determined by the inner subquery). An index on (record_id, version_num) can significantly boost the performance of this approach.

Approach 6: MySQL Specific Optimization (GROUP_CONCAT)

This is a specific technique often employed in MySQL (pre-8.0, and with caveats) due to its behavior with GROUP BY and GROUP_CONCAT(). It might not be considered standard SQL, and its use should be carefully evaluated.

-- This example assumes 'numeric_content' as a placeholder for 'detail_info' that can be ordered
SELECT
    record_id,
    MAX(version_num) AS max_version,
    0 + SUBSTRING_INDEX(GROUP_CONCAT(detail_info ORDER BY version_num DESC), ',', 1) AS latest_detail
FROM
    DocumentRevisions
GROUP BY
    record_id;

This method relies on GROUP_CONCAT() to concatenate detail_info values within each group, ordered by version_num descending. SUBSTRING_INDEX() then extracts the first (highest version) detail_info. Keep in mind GROUP_CONCAT() has a maximum length limit (group_concat_max_len variable), which might be an issue for large groups or long detail_info strings.

A simpler, non-standard MySQL behavior solution (which might not be reliable in newer versions or strict SQL modes like ONLY_FULL_GROUP_BY):

SELECT *
FROM (
    SELECT * FROM DocumentRevisions ORDER BY record_id, version_num DESC
) AS ordered_revisions
GROUP BY record_id;

This works in older MySQL versions because when ONLY_FULL_GROUP_BY is disabled, MySQL returns an arbitrary row from the group for columns not in the GROUP BY clause. By pre-ordering the data, we influence which “arbitrary” row is chosen (the first one, which corresponds to the highest version_num). This behavior is discouraged for production systems due to its non-standard and potentially unpredictable nature.

Approach 7: Common Table Expressions (CTEs) and CROSS APPLY (SQL Server, Oracle)

For SQL Server and Oracle, CROSS APPLY (or OUTER APPLY) provides a powerful and often optimized way to solve this.

-- SQL Server / Oracle using CROSS APPLY
WITH DistinctRecords AS (
    SELECT DISTINCT record_id FROM DocumentRevisions
)
SELECT
    dr_main.record_id,
    dr_main.version_num,
    dr_main.detail_info
FROM
    DistinctRecords dr_distinct
CROSS APPLY (
    SELECT TOP 1 * FROM DocumentRevisions dr_inner
    WHERE dr_inner.record_id = dr_distinct.record_id
    ORDER BY dr_inner.version_num DESC
) dr_main;

This method first creates a CTE of distinct record_id values. Then, CROSS APPLY effectively iterates through each distinct record_id and, for each, executes the subquery to find the top 1 row ordered by version_num descending. This is highly efficient, especially with appropriate indexing.

Approach 8: Temporary Tables (Specific Use Cases)

While often overkill for this problem, in complex scenarios where you need to perform multiple operations or debug intermediate results, using a temporary table can be beneficial.

-- Example for temp table (SQL Server syntax)

    record_id VARCHAR(20),
    max_version INT

INSERT INTO #TempMaxVersions
SELECT
    record_id,

This involves creating a temporary table to store the record_id and max_version pairs, then joining back to the original table. This can be useful when the subquery itself is very complex or reused.

Performance Considerations

All the presented approaches are generally performant, but their efficiency can vary depending on the specific RDBMS, table structure, data volume, and most importantly, indexing.

  • Indexing: An index on (record_id, version_num) is crucial for almost all methods to achieve optimal performance.
  • Window Functions: Often highly optimized by modern database engines. They perform a single pass over the data.
  • Join-based and IN Clause: Generally perform well, with the subquery being evaluated once before the join or IN comparison.
  • Correlated Subquery: Can be slower if not properly indexed, as the inner query runs for each row of the outer query.
  • MySQL-specific (non-standard GROUP BY): While sometimes surprisingly fast in older MySQL, its non-standard behavior means it’s not guaranteed to work as expected across versions or configurations. It’s usually best to avoid it for reliability.
  • CROSS APPLY: Very efficient in SQL Server and Oracle, designed for this type of problem.

Benchmarking with your specific data and RDBMS is always the best way to determine the most performant solution for your use case.

FAQs on How to Retrieve Rows with Maximum Value Per Group in SQL

Q: What is the greatest n per group problem

ANS: The greatest n per group problem refers to the common task of retrieving the top N (or in this case, the single greatest) rows for each distinct group within a dataset, based on a specific column’s value.

Q: Are SQL window functions widely supported

ANS: Yes, SQL window functions like ROW_NUMBER and RANK are widely supported by all major modern RDBMS, including PostgreSQL MySQL Oracle SQL Server and SQLite. They conform to ANSI ISO SQL standards.

Q: Which method is best for performance

ANS: The best method for performance often depends on your specific RDBMS version data size and indexing. Generally window functions and well-indexed join based solutions are highly efficient. Correlated subqueries can be slower without proper indexing. Benchmarking is recommended for your specific scenario.

Q: Can these solutions handle ties in maximum values

ANS: Yes many of these solutions can handle ties. Methods like joining with a subquery the IN clause and MAX analytic function will return all rows that share the maximum value for a group. ROW_NUMBER will arbitrarily pick one if there’s a tie while RANK and DENSE_RANK will return all tied rows.

Q: Is the MySQL specific GROUP BY solution reliable

ANS: The MySQL specific GROUP BY solution relying on non standard behavior where it returns an arbitrary row from each group is not considered reliable or portable across different MySQL versions or strict SQL modes. It is generally advised to use standard SQL approaches like window functions or joins for robust solutions.
