“Generating Auto-Incremented Prefixed IDs in SQL Without Standard Auto Increment”

How can a database developer structure table entries to yield identifiers that combine a fixed text prefix (e.g., ‘LHPL’) with a sequentially increasing number, formatted to ensure a specific length (e.g., ‘LHPL001’, ‘LHPL002’), especially when the standard AUTO_INCREMENT property is insufficient on its own? We examine several robust database design patterns to achieve this synthetic sequencing.

Solution 1: Utilizing a Sequence Table and Database Triggers (MySQL Focus)

A common pattern, particularly effective in MySQL environments where native sequences might be less utilized, involves decoupling the sequential numeric value into a helper table and enforcing the formatting logic via a BEFORE INSERT trigger on the main table.

Setup: Separated Sequence Table and Main Data Table

First, define two structures: one to manage the raw sequence number and the primary table for data storage.

-- Helper table to manage raw sequential IDs
CREATE TABLE table1_seq
(
  seq_id INT NOT NULL AUTO_INCREMENT PRIMARY KEY
);

-- Primary data table structure
CREATE TABLE table1
(
  id VARCHAR(7) NOT NULL PRIMARY KEY DEFAULT '0', 
  name VARCHAR(30)
);

Enforcing Prefixing Logic with a Trigger

The key here is the trigger, which executes before any insertion into table1. It inserts a record into the sequence table, captures the newly generated numeric ID via LAST_INSERT_ID(), and then formats it before assigning it to the NEW.id column.

DELIMITER $$
CREATE TRIGGER tg_table1_insert
BEFORE INSERT ON table1
FOR EACH ROW
BEGIN
  -- Generate a new sequence number
  INSERT INTO table1_seq VALUES (NULL);
  
  -- Format the ID: Prefix + Left-padded sequence number (3 digits)
  SET NEW.id = CONCAT('LHPL', LPAD(LAST_INSERT_ID(), 3, '0'));
END$$
DELIMITER ;

Insertion Example

When data is inserted, the prefixing happens automatically:

INSERT INTO Table1 (name) 
VALUES ('Jhon'), ('Mark');

Solution 2: Leveraging Native Numeric Column Attributes (ZEROFILL) or Post-Query Formatting

Alternatively, the sequential number can be stored directly in the primary table, relying on column attributes or post-retrieval formatting functions to achieve the desired string appearance.

Option 2A: Using ZEROFILL Attribute

Define the numeric ID column with ZEROFILL and a minimum display width. While this affects display in some clients, concatenation is still needed for the final prefixed string.

create table so_zerofill (
 id INT(3) UNSIGNED ZEROFILL NOT NULL AUTO_INCREMENT PRIMARY KEY,
 name VARCHAR(30) NOT NULL
);

INSERT INTO so_zerofill SET name = 'John';
INSERT INTO so_zerofill SET name = 'Mark';

-- Querying requires CONCAT to add the prefix
SELECT CONCAT('LHPL', id) AS id, name FROM so_zerofill;

Option 2B: Using LPAD During Selection

Store the ID as a standard unsigned integer, and use LPAD at the time of reading the data to ensure the numeric part is padded correctly before concatenation.

create table so_padded (
 id INT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
 name VARCHAR(30) NOT NULL
);

INSERT INTO so_padded SET name = 'John';
INSERT INTO so_padded SET name = 'Mark';

-- Querying uses LPAD(id, 3, 0) for padding
SELECT CONCAT('LHPL', LPAD(id, 3, 0)) AS id, name FROM so_padded;

Both variations yield the desired output format when queried.

Solution 3: Single-Query Generation Without Triggers or Extra Tables

For environments or constraints that prohibit database triggers or auxiliary tables, it is feasible to calculate the next ID within the INSERT statement itself, albeit this method requires careful handling of concurrent insertions and often relies on transactional safety.

This technique finds the maximum existing prefixed ID, strips the prefix, increments the number, and reapplies padding and the prefix.

CREATE TABLE YOURTABLE(
IDNUMBER VARCHAR(7) NOT NULL PRIMARY KEY,
ENAME VARCHAR(30) not null
);

Calculating and Inserting in Two Steps (or a Stored Procedure):

  1. Calculate the Next ID (Stored in a user variable): This logic parses the MAX(IDNUMBER), isolates the numeric part, adds one, and pads it.

    SELECT IFNULL(
    CONCAT('LHPL', LPAD(
      (SUBSTRING_INDEX(MAX(`IDNUMBER`), 'LHPL', -1) + 1), 5, '0'
    )), 
    'LHPL00001' -- Base case if table is empty, adjusting padding for this example's logic
) AS 'NextID' 
FROM YOURTABLE 
ORDER BY `IDNUMBER` ASC 
INTO @IDNUMBER;

  2. Execute the Insert:

    INSERT INTO YOURTABLE(IDNUMBER, ENAME) VALUES 
(@IDNUMBER, 'EMPLOYEE NAME');

(Note: The padding length (e.g., ‘5’ in the example above vs. ‘3’ in Solution 1) must match the intended final ID length in the YOURTABLE definition.)

Solution 4: PostgreSQL Approach Using Explicit Sequences

PostgreSQL offers dedicated SEQUENCE objects, which are more portable and explicit than MySQL triggers for generating sequence numbers.

PostgreSQL Sequence Definition

Create the sequence first:

CREATE SEQUENCE messages_seq START WITH 1 INCREMENT BY 1;

Table Definition Using Sequence Value

The default value for the ID column explicitly calls nextval() on the sequence and concatenates the result.

CREATE TABLE IF NOT EXISTS messages (
    -- Defaulting using concatenation with the sequence function
    id CHAR(20) NOT NULL DEFAULT ('message_' || nextval('messages_seq')),
    name CHAR(30) NOT NULL
);

-- Optionally, link the sequence ownership to the table for easier cleanup
ALTER SEQUENCE messages_seq OWNED BY messages.id;

This approach separates sequence management cleanly from the data insertion logic. For more details on handling database objects, refer to platform-specific documentation on SQL Sequence Objects .

create table so (
 id int(3) unsigned zerofill not null auto_increment primary key,
 name varchar(30) not null
);

insert into so set name = 'John';
insert into so set name = 'Mark';

select concat('LHPL', id) as id, name from so;

FAQs on Generating Prefixed SQL IDs

Q: Can I use AUTO_INCREMENT directly with a string prefix

ANS: No, standard SQL AUTO_INCREMENT or similar identity columns only function on numeric data types. You must use functions or triggers to combine the prefix with the sequence.

Q: Which solution is best for high concurrency

ANS: Solution 1 (Trigger) or Solution 4 (PostgreSQL Sequence) are generally safer for high concurrency as the ID generation is handled directly by the database engine’s internal mechanisms, minimizing potential race conditions compared to retrieving MAX() manually (Solution 3).
