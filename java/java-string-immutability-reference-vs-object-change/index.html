“Java String Immutability Explained: Why References Change and New Objects Form”

Deconstructing Java String Immutability

The foundational point about Java’s String class is its state: once a String object is instantiated, its content cannot be altered. If an operation seems to modify a String, what is actually occurring under the hood?

Consider the initial setup:

String originalRef = "knowledge"; // Creates String object "knowledge"
String sharedRef = originalRef;     // sharedRef points to the SAME object

When an operation that implies modification is performed, a new object must be created because the existing one cannot change.

originalRef = originalRef.concat(" base");

The Mechanism of Apparent Modification:

  1. The JVM retrieves the value pointed to by originalRef (“knowledge”).
  2. It appends " base", resulting in the new value “knowledge base”.
  3. Since String objects are fixed, the JVM creates an entirely new String object in memory with the value “knowledge base”.
  4. Crucially, the reference variable originalRef is then reassigned to point to this newly created object.

The key takeaway here is that the String object remains immutable; it is the reference variable that changes its allegiance. At this point, sharedRef still points to the original “knowledge” object, while originalRef points to “knowledge base”. Technically, there are now three objects involved: the two main objects (“knowledge” and “knowledge base”) and the literal string " base" used in the operation.

If we perform a modification method without reassigning the reference, the result is lost:

String s1 = "java";
s1.concat(" rules"); // Creates "java rules", but no reference points to it
System.out.println("s1 still refers to: " + s1); // Output: s1 still refers to: java

The new object “java rules” exists momentarily but becomes eligible for garbage collection as it has no active references pointing to it.

Memory Efficiency: The String Constant Pool

To optimize memory usage, especially when dealing with numerous identical string literals, the JVM employs the String Constant Pool (SCP).

When the compiler encounters a String literal (e.g., "hello"), it checks the SCP.

  • If the literal exists: No new object is created. The existing object in the pool receives another reference.
  • If the literal does not exist: A new object is created in the pool and referenced.

Why Immutability is Vital for the SCP: If multiple parts of an application referenced the same string literal from the pool, and one reference could mutate that shared object, chaos would ensue across unrelated parts of the code. Immutability guarantees that any object shared via the pool is safe from unexpected alteration.

Furthermore, the String class itself is declared final, preventing subclassing and overriding of its methods, reinforcing its invariant behavior.

Reference Change vs. Object Mutation

Immutability dictates you cannot change the state of the object itself; you can only change which object a reference variable points to.

Contrast this with mutable classes like StringBuffer (or StringBuilder):

Code Example Demonstrating Reference Reassignment:

This snippet clearly shows that assigning a new literal to a reference variable simply redirects that variable to a different object instance.

String refA = "initial_value";
System.out.println("A initial hash: " + refA.hashCode() + ", value: " + refA);

String refB = refA; // B points to "initial_value"

refA = "new_value"; // A now points to a different object ("new_value")
System.out.println("A after reassignment hash: " + refA.hashCode() + ", value: " + refA);
System.out.println("B remains pointing to: " + refB); // B is unchanged

If you wish to prevent a reference variable from being reassigned, you declare it as final:

final String CONSTANT_DATA = "locked_string";
// CONSTANT_DATA = "attempt_to_change"; // This would result in a compile-time error

Distinguishing new String() from Literals

String literals are automatically interned (managed by the SCP). Using the new String() constructor bypasses this pooling mechanism, creating a distinct object even if the content is identical to an existing literal.

String literal1 = "test_content";
String literal2 = "test_content";
String object1 = new String("test_content");

// Comparison check
boolean areLiteralsSameReference = (literal1 == literal2);      // true (Same object in SCP)
boolean areObjectAndLiteralSameReference = (object1 == literal1); // false (Different memory locations)

System.out.println("Literal == Literal: " + areLiteralsSameReference);
System.out.println("Object == Literal: " + areObjectAndLiteralSameReference);

When using new String(s), you often create a duplicate object that shares the underlying character array, which is generally discouraged unless specific cloning or deep copy behavior is required, as noted by many Java practitioners.

Comparing Hash Codes to Confirm Object Identity

Examining hash codes provides empirical evidence that modification results in a new object instance rather than an in-place change:

class StringReferenceTest {
    public static void main(String[] args) {
        String currentRef = "Alpha";
        System.out.println("1. Initial Value: " + currentRef + ", Hash: " + currentRef.hashCode());

        currentRef = currentRef.concat(" Beta"); // Operation that forces new object creation
        System.out.println("2. After Concat: " + currentRef + ", Hash: " + currentRef.hashCode());
    }
}
// Output will show different hash codes for step 1 and step 2, confirming two distinct objects.

Alternative: Using Mutable Types

When frequent string modifications are necessary within a loop or a complex construction process, using StringBuffer or StringBuilder is the appropriate alternative, as these objects are designed to change their internal state without creating new objects for every modification.

StringBuffer mutableBuffer = new StringBuffer("Start");
System.out.println("Initial Buffer: " + mutableBuffer);

mutableBuffer.append(" Middle");
mutableBuffer.append(" End");

System.out.println("Final Buffer (Mutated): " + mutableBuffer);
// The reference 'mutableBuffer' still points to the same object, but its content has changed.

System.out.println("a 1--&gt;"+a);
String b=a;
a="ty";
System.out.println("a 2--&gt;"+a);
System.out.println("b  --&gt;"+b);
final String a="a";

FAQs on Java String Immutability Explained Why References Change And New Objects Form

Q: What does it mean for a Java String object to be immutable

ANS: An immutable object’s state cannot be changed after its creation. For a Java String, any method that appears to modify it actually returns a reference to a brand new String object containing the modified content.

Q: If String is immutable why can the reference variable be changed

ANS: The String object itself is fixed. The reference variable (like str or a) is just a pointer to memory. Reassigning the reference variable means you tell it to point to a different memory address (a new String object) instead of modifying the data at the original address.

Q: How does the String constant pool benefit from string immutability

ANS: Immutability ensures that if multiple variables reference the same literal String object in the pool, no single variable can alter that shared content, preserving data integrity across the application.

Q: Is using new String('value') the same as using 'value'

ANS: No. Using double quotes like "value" stores the object in the String Constant Pool. Using new String("value") forces the creation of a new object instance, often bypassing the pool, resulting in different object references (== comparison fails).

Q: Which class should be used for frequent string modifications

ANS: Use StringBuffer or StringBuilder. These classes are mutable, allowing in-place modifications without incurring the overhead of constantly creating new String objects.
