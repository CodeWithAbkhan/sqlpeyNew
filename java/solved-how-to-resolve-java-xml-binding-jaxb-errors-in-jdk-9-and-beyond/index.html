“Solved: How to Resolve Java XML Binding (JAXB) Errors in JDK 9 and Beyond”

A common hurdle encountered when moving to or working with Java Development Kit (JDK) 9 and subsequent versions (like Java 10, 11, and newer) is the absence of the Java Architecture for XML Binding (JAXB) APIs from the default classpath. This change, stemming from Java 9’s introduction of the module system (Project Jigsaw), means that APIs previously bundled with the JDK are now considered separate modules.

In Java SE 9, JAXB and other Java EE APIs were moved into separate modules. In Java 11, these modules were completely removed from the JDK. This shift often leads to java.lang.NoClassDefFoundError: javax/xml/bind/JAXBException or similar ClassNotFoundException errors when your application attempts to use JAXB functionalities.

This post provides a comprehensive guide to resolving these JAXB-related issues, covering various approaches suitable for different scenarios and JDK versions.

Understanding the Root Cause: Java Modularity

With the advent of the module system in Java 9 (JEP 261) , the JDK structure changed. APIs like JAXB, which were once part of the core JDK, are now located in distinct modules:

  • java.activation
  • java.corba
  • java.transaction
  • java.xml.bind (This module specifically contains the JAXB APIs)
  • java.xml.ws
  • java.xml.ws.annotation

By default, only the java.se aggregate module is present on the module path. Therefore, applications requiring JAXB must explicitly declare their dependency on the java.xml.bind module or include the necessary JAXB libraries.

Solutions for JAXB Errors

Here are several effective methods to address JAXB errors, ranging from quick fixes for specific JDK versions to robust long-term solutions for modern Java development.

Solution 1: Using Command-Line Arguments (--add-modules)

For JDK 9 and JDK 10, you can make the JAXB APIs available at runtime by specifying a command-line option.

Quick and Dirty Solution (JDK 9/10 only):

When running your Java application, use the --add-modules flag:

java --add-modules java.xml.bind -jar your_application.jar

If you are compiling Java files, you would use:

javac --add-modules java.xml.bind YourClass.java
java --add-modules java.xml.bind YourClass

Important Consideration: This option is specific to JDK 9 and 10. It will not work with Java 11 or later, as the module has been removed.

Using JDK_JAVA_OPTIONS Environment Variable:

An alternative for JDK 9+ is to set the JAVA_OPTIONS environment variable. This is automatically read by the java launcher.

export JDK_JAVA_OPTIONS="--add-modules java.xml.bind"
java -jar your_application.jar

Ignoring Unrecognized VM Options:

To prevent the JVM from failing when encountering unrecognized options (like --add-modules in future versions or on different JVM implementations), you can add -XX:+IgnoreUnrecognizedVMOptions. However, be cautious, as this will also silently ignore any other invalid VM options you might have specified.

java -XX:+IgnoreUnrecognizedVMOptions --add-modules java.xml.bind -jar your_application.jar

This approach is compatible with Oracle/OpenJDK and IBM JDK (as of JDK 8sr4).

Solution 2: Adding JAXB Dependencies to Your Project (Long-Term Solution)

The most recommended and sustainable approach for JDK 9 and beyond, especially for Java 11 and newer, is to include the JAXB APIs and their runtime implementation as dependencies in your project. This is typically managed through build tools like Maven or Gradle.

Maven Dependencies:

For Maven projects, add the following dependencies to your pom.xml:

<dependency>
    <groupId>jakarta.xml.bind</groupId>
    <artifactId>jakarta.xml.bind-api</artifactId>
    <version>2.3.3</version> <!-- Use a recent version, e.g., 2.3.3 or later -->
</dependency>
<dependency>
    <groupId>org.glassfish.jaxb</groupId>
    <artifactId>jaxb-runtime</artifactId>
    <version>2.3.3</version> <!-- Match the API version -->
</dependency>

Note: As of July 2022, versions like 4.0.0 are available for jakarta.xml.bind-api and jaxb-runtime. When using these later versions, the package names change from javax.xml.bind to jakarta.xml.bind. Ensure your code is updated accordingly.

Gradle Dependencies:

For Gradle projects, add these to your build.gradle file:

dependencies {
    // JAX-B dependencies for JDK 9+
    implementation "jakarta.xml.bind:jakarta.xml.bind-api:2.3.3"
    implementation "org.glassfish.jaxb:jaxb-runtime:2.3.3"
}

Specific Versions and Older Dependencies:

Some projects might still require older versions or different artifact combinations. For example, some users found success with:

<!-- For Spring Boot fat jars -->
<dependency>
    <groupId>javax.xml.bind</groupId>
    <artifactId>jaxb-api</artifactId>
    <version>2.3.1</version>
</dependency>

Or a more comprehensive set:

<dependencies>
    <dependency>
        <groupId>javax.xml.bind</groupId>
        <artifactId>jaxb-api</artifactId>
        <version>2.3.0</version>
    </dependency>
    <dependency>
        <groupId>com.sun.xml.bind</groupId>
        <artifactId>jaxb-impl</artifactId>
        <version>2.3.0</version>
    </dependency>
    <dependency>
        <groupId>org.glassfish.jaxb</groupId>
        <artifactId>jaxb-runtime</artifactId>
        <version>2.3.0</version>
    </dependency>
    <dependency>
        <groupId>javax.activation</groupId>
        <artifactId>activation</artifactId>
        <version>1.1.1</version>
    </dependency>
</dependencies>

When migrating from older Java EE versions, you might encounter the jakarta.xml.bind namespace. Ensure you use the correct artifact IDs and versions based on your Java version and build tool. For detailed artifact information, refer to the Eclipse Implementation of JAXB or Maven Central .

Solution 3: Using Specific Implementations (e.g., EclipseLink MOXy)

If you want to avoid pulling in the entire GlassFish JAXB runtime, you can opt for a more focused implementation like EclipseLink MOXy.

Maven:

<dependency>
    <groupId>org.eclipse.persistence</groupId>
    <artifactId>org.eclipse.persistence.moxy</artifactId>
    <version>2.7.10</version> <!-- Use a recent version -->
</dependency>

Gradle:

implementation 'org.eclipse.persistence:org.eclipse.persistence.moxy:2.7.10'

In scenarios where this is used, you might need to set a system property to explicitly tell JAXB to use the MOXy implementation:

System.setProperty("javax.xml.bind.JAXBContextFactory", "org.eclipse.persistence.jaxb.JAXBContextFactory");

This method can help create JARs that are compatible with both JRE 8 and newer JDKs without additional command-line arguments.

Solution 4: Manual JAR Inclusion

For projects not using build tools, or in specific environments (like some application servers), you can manually download the required JAXB JAR files and add them to your project’s classpath or library directory.

Required JARs (example versions):

  • javax.activation-1.2.0.jar (Download from Maven Central )
  • jaxb-api-2.3.0.jar (Download from Maven Central )
  • jaxb-core-2.3.0.jar (Download from Maven Central )
  • jaxb-impl-2.3.0.jar (Download from Maven Central )

After downloading, copy these JARs into your project’s libs folder and ensure they are added to your Java Build Path.

Solution 5: Addressing Specific Environments (Tomcat, Gradle Daemon)

Tomcat:

If you encounter JAXB errors within a Tomcat server environment on Java 11, you might need to manually place the jaxb-api.jar into Tomcat’s lib directory.

# Example using wget and moving the file
sudo wget https://repo1.maven.org/maven2/javax/xml/bind/jaxb-api/2.4.0-b180830.0359/jaxb-api-2.4.0-b180830.0359.jar -P /opt/tomcat/temp/
sudo mv /opt/tomcat/temp/jaxb-api-2.4.0-b180830.0359.jar /opt/tomcat/lib/jaxb-api.jar

# Ensure correct permissions
sudo chown -R tomcat:tomcat /opt/tomcat
sudo chmod -R 777 /opt/tomcat/

# Restart Tomcat
sudo systemctl restart tomcat

Gradle Daemon:

For Gradle projects, ensure your Gradle daemon is not running with a conflicting JDK version. You can configure the JDK used by Gradle via gradle.properties or by setting JAVA_HOME. In Android projects, check your project’s JDK settings in Android Studio’s Project Structure.

Solution 6: Handling Specific Libraries (e.g., JJWT)

Libraries like JJWT (Java JWT) have evolved to handle JAXB dependencies differently in newer Java versions. If you’re using JJWT version 0.9.x with Java 11 and encountering ClassNotFoundException:javax.xml.bind.DatatypeConverter, consider upgrading to JJWT version 0.11.x or later. The JJWT project has split its packages to address compatibility issues with modular Java.

Solution 7: Profile Management in Maven

For complex projects, you can use Maven profiles to conditionally include JAXB dependencies based on the JDK version.

<profiles>
    <profile>
        <id>java-9</id>
        <activation>
            <jdk>9</jdk>
        </activation>
        <dependencies>
            <dependency>
                <groupId>org.glassfish.jaxb</groupId>
                <artifactId>jaxb-runtime</artifactId>
                <version>2.3.0</version>
            </dependency>
            <dependency>
                <groupId>javax.activation</groupId>
                <artifactId>activation</artifactId>
                <version>1.1.1</version>
            </dependency>
        </dependencies>
    </profile>
</profiles>

You can then activate this profile in your IDE (e.g., Eclipse) or via the command line using mvn -Pjava-9 clean install.

Solution 8: Check Maven/IDE JDK Configuration

Sometimes, the issue isn’t with the dependencies but with how your build tool or IDE is configured. Ensure that your Maven installation or your IDE (like IntelliJ IDEA, Eclipse) is correctly pointing to the JDK version you intend to use. If your global JAVA_HOME is set to JDK 8, but Maven or your IDE is configured to use JDK 11, this can lead to unexpected JAXB errors.

FAQs on JAXB Errors in Modern Java

Q: Why am I getting javax xml bind JAXBException in Java 11

ANS: In Java 11, JAXB was completely removed from the JDK. This means the necessary classes are no longer available by default, leading to NoClassDefFoundError or JAXBException. To fix this, you need to add JAXB API and runtime dependencies to your project, typically via Maven or Gradle.

Q: How to add JAXB dependency in Maven for Java 9+

ANS: Add the following dependencies to your pom.xml:

<dependency>
    <groupId>jakarta.xml.bind</groupId>
    <artifactId>jakarta.xml.bind-api</artifactId>
    <version>2.3.3</version>
</dependency>
<dependency>
    <groupId>org.glassfish.jaxb</groupId>
    <artifactId>jaxb-runtime</artifactId>
    <version>2.3.3</version>
</dependency>

Remember to use versions compatible with your Java version and namespace requirements (e.g., jakarta.xml.bind for newer versions).

Q: Is there a quick fix for JAXB errors in JDK 9 and 10

ANS: Yes, for JDK 9 and 10, you can use the command-line argument --add-modules java.xml.bind when running or compiling your Java code. For example: java --add-modules java.xml.bind -jar your_app.jar. This is not a solution for Java 11+.

Q: Can I use JAXB with Java 8 and Java 11 simultaneously

ANS: Yes, by managing your dependencies correctly. Ensure your project’s dependencies include the JAXB artifacts. For Java 8 environments that might have JAXB present, the dependencies are often optional. For Java 11+, you must explicitly include them as described in the solutions above. Using Maven profiles can help manage these conditional dependencies.

Q: What are the new package names for JAXB in recent versions

ANS: In recent versions of JAXB (e.g., 2.3.2 and later), the package names have changed from javax.xml.bind to jakarta.xml.bind as part of the Jakarta EE specification. Ensure your imports and dependency declarations reflect these changes if you are using newer JAXB artifact versions.
