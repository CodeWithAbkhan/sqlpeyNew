“Maven Packaging: Creating Executable JARs with Dependencies”

Creating a self-contained, executable JAR file for a Java application, often referred to as a “fat JAR” or “uber-JAR,” is a common requirement for deployment and distribution. This process involves bundling all necessary library dependencies along with your application code into a single JAR file. Maven provides several powerful plugins and configurations to achieve this.

Methods for Packaging Dependencies

Several approaches can be employed within Maven to create an executable JAR with dependencies. Each method has its nuances and advantages depending on the specific project needs.

Solution 1: Using the maven-assembly-plugin with jar-with-dependencies

The maven-assembly-plugin is a versatile tool for assembling project artifacts. The jar-with-dependencies descriptor is a pre-defined configuration that bundles all project artifacts and their transitive dependencies into a single JAR.

<build>
  <plugins>
    <!-- Other plugins -->
    <plugin>
      <artifactId>maven-assembly-plugin</artifactId>
      <executions>
        <execution>
          <phase>package</phase>
          <goals>
            <goal>single</goal>
          </goals>
        </execution>
      </executions>
      <configuration>
        <descriptorRefs>
          <descriptorRef>jar-with-dependencies</descriptorRef>
        </descriptorRefs>
      </configuration>
    </plugin>
  </plugins>
</build>

This configuration ensures that when you run mvn package, the assembly plugin will create a JAR named your-artifact-id-version-jar-with-dependencies.jar.

Solution 2: Command-Line Execution with maven-assembly-plugin

Alternatively, you can leverage the maven-assembly-plugin directly from the command line without explicit configuration in the pom.xml for a single build.

mvn assembly:assembly -DdescriptorId=jar-with-dependencies

To make this JAR executable, you can specify the mainClass within the plugin’s configuration in your pom.xml.

<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-assembly-plugin</artifactId>
  <configuration>
    <archive>
      <manifest>
        <mainClass>com.example.MyApplication</mainClass>
      </manifest>
    </archive>
  </configuration>
</plugin>

For integrating this into the standard build lifecycle, bind the single goal to the package phase:

<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-assembly-plugin</artifactId>
  <executions>
    <execution>
      <id>create-my-bundle</id>
      <phase>package</phase>
      <goals>
        <goal>single</goal>
      </goals>
      <configuration>
        <descriptorRefs>
          <descriptorRef>jar-with-dependencies</descriptorRef>
        </descriptorRefs>
        <!-- Other configurations like archive/manifest can be added here -->
      </configuration>
    </execution>
  </executions>
</plugin>

Solution 3: Creating an Executable JAR with a Specific Main Class

When you need an executable JAR that precisely points to your application’s entry point, combine the jar-with-dependencies descriptor with manifest configuration.

<plugins>
  <plugin>
    <artifactId>maven-assembly-plugin</artifactId>
    <executions>
      <execution>
        <phase>package</phase>
        <goals>
          <goal>single</goal>
        </goals>
      </execution>
    </executions>
    <configuration>
      <archive>
        <manifest>
          <mainClass>com.fully.qualified.MainClass</mainClass>
        </manifest>
      </archive>
      <descriptorRefs>
        <descriptorRef>jar-with-dependencies</descriptorRef>
      </descriptorRefs>
    </configuration>
  </plugin>
</plugins>

Solution 4: Copying Dependencies to a lib Folder

An alternative approach involves copying all dependency JARs into a target/lib directory and then configuring the main JAR’s manifest to include this directory in its classpath.

Method 1: Using maven-dependency-plugin and maven-jar-plugin

This method uses maven-dependency-plugin to copy dependencies and maven-jar-plugin to set the classpath in the manifest.

<!-- Copy dependencies to target/lib -->
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-dependency-plugin</artifactId>
  <configuration>
    <outputDirectory>${project.build.directory}/lib</outputDirectory>
    <excludeTransitive>false</excludeTransitive>
    <stripVersion>false</stripVersion>
  </configuration>
  <executions>
    <execution>
      <id>copy-dependencies</id>
      <phase>package</phase>
      <goals>
        <goal>copy-dependencies</goal>
      </goals>
    </execution>
  </executions>
</plugin>

<!-- Add LIB folder to classpath in MANIFEST -->
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-jar-plugin</artifactId>
  <version>3.3.0</version> <!-- Use a recent version -->
  <configuration>
    <archive>
      <manifest>
        <addClasspath>true</addClasspath>
        <classpathPrefix>lib/</classpathPrefix>
      </manifest>
    </archive>
  </configuration>
</plugin>

Method 2: Unpacking and Repackaging with maven-assembly-plugin

This approach uses maven-assembly-plugin to unpack all dependencies and repack them into a single JAR. Be aware that overlapping resources might be lost.

<plugin>
  <artifactId>maven-assembly-plugin</artifactId>
  <executions>
    <execution>
      <phase>package</phase>
      <goals>
        <goal>single</goal>
      </goals>
    </execution>
  </executions>
  <configuration>
    <descriptorRefs>
      <descriptorRef>jar-with-dependencies</descriptorRef>
    </descriptorRefs>
  </configuration>
</plugin>

Solution 5: Utilizing the maven-shade-plugin

The maven-shade-plugin is another powerful option, particularly useful for relocating (or “shading”) dependency packages to avoid classpath conflicts. This is especially valuable when dealing with multiple libraries that might have identical package names.

Solution 6: Using a Classifier for Dependency JARs

If you wish to reference the dependency-included JAR as a distinct artifact within your Maven project or for external use, you can assign it a classifier.

<dependencies>
  <dependency>
    <groupId>your.group.id</groupId>
    <artifactId>your.artifact.id</artifactId>
    <version>1.0</version>
    <type>jar</type>
    <classifier>jar-with-dependencies</classifier>
  </dependency>
</dependencies>

Solution 7: WAR Project as a Dependency Wrapper (A Creative Trick)

For a different perspective, especially if you find assembling JARs complex, consider using a WAR project as a wrapper.

  1. Create a standard Maven JAR project for your application.
  2. Set up a Maven WAR project that depends on your JAR project. This WAR project only needs a minimal src/main/webapp/WEB-INF/web.xml to function.
  3. Build the WAR project. This process effectively bundles your application JAR and its dependencies into a deployable WAR.
  4. Rename the .war file to .zip and extract its contents. You will find a lib directory containing your application JAR and all its dependencies, which can be referenced in the classpath: java -cp 'path/lib/*' com.example.MainClass. This method offers clarity on application structure and dependency versions.

Solution 8: Exploring Uber-JAR Construction Methods

The concept of an “uber-JAR” is well-explained on resources like Fiji’s Uber-JAR explanation . The primary methods include:

  • Unshaded: All JARs are unpacked and repacked into one. This can cause issues if files with identical paths (like META-INF/services/*) exist in multiple dependency JARs, as they will overwrite each other. Tools: maven-assembly-plugin, Classworlds Uberjar.
  • Shaded: Similar to unshaded, but dependency packages are renamed. This helps avoid some version clashes but can still suffer from resource overwriting. Tools: maven-shade-plugin.
  • JAR of JARs: The final JAR embeds other JARs. This preserves all resources and avoids version clashes but requires a custom bootstrap classloader. Tools: Eclipse JAR File Exporter, One-JAR.

Solution 9: Custom Classloader Approach (Eclipse Luna Example)

For advanced control, a custom classloader can be integrated. The Eclipse JDT UI project provides a JarRsrcLoader which is known for its efficiency.

// Example usage with properties set in pom.xml
// mvn clean dependency:copy-dependencies package
// Creates a jar with dependencies in a lib folder and a thin classloader.

<project>
  <properties>
    <project.mainClass>org.eclipse.jdt.internal.jarinjarloader.JarRsrcLoader</project.mainClass>
    <project.realMainClass>com.example.MyClass</project.realMainClass>
  </properties>
  <build>
    <resources>
      <resource>
        <directory>src/main/java</directory>
        <includes>
          <include>**/*.java</include>
          <include>**/*.properties</include>
        </includes>
      </resource>
      <resource>
        <directory>src/main/resources</directory>
        <filtering>true</filtering>
        <includes>
          <include>**/*</include>
        </includes>
        <targetPath>META-INF/</targetPath>
      </resource>
      <resource>
        <directory>${project.build.directory}/dependency/</directory>
        <includes>
          <include>*.jar</include>
        </includes>
        <targetPath>lib/</targetPath>
      </resource>
    </resources>
    <pluginManagement>
      <plugins>
        <plugin>
          <groupId>org.apache.maven.plugins</groupId>
          <artifactId>maven-jar-plugin</artifactId>
          <configuration>
            <archive>
              <manifest>
                <addClasspath>true</addClasspath>
                <mainClass>${project.mainClass}</mainClass>
                <classpathPrefix>lib/</classpathPrefix>
              </manifest>
              <manifestEntries>
                <Rsrc-Main-Class>${project.realMainClass}</Rsrc-Main-Class>
                <Class-Path>./</Class-Path>
              </manifestEntries>
            </archive>
          </configuration>
        </plugin>
        <plugin>
          <groupId>org.apache.maven.plugins</groupId>
          <artifactId>maven-dependency-plugin</artifactId>
          <executions>
            <execution>
              <id>copy-dependencies</id>
              <phase>package</phase>
              <goals>
                <goal>copy-dependencies</goal>
              </goals>
            </execution>
          </executions>
        </plugin>
      </plugins>
    </pluginManagement>
  </build>
</project>

Beyond Maven, the One-JAR project provides a way to package libraries within the main JAR, requiring a custom classloader.

Solution 12: Unpacking Specific Directories with maven-dependency-plugin

If you only need to include specific directories from a dependency rather than all its JARs, the unpack goal of the maven-dependency-plugin is useful.

<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-dependency-plugin</artifactId>
  <executions>
    <execution>
      <id>unpack</id>
      <phase>prepare-package</phase>
      <goals>
        <goal>unpack</goal>
      </goals>
      <configuration>
        <artifactItems>
          <artifactItem>
            <groupId>my.group</groupId>
            <artifactId>my.artifact</artifactId>
            <classifier>occupied</classifier> <!-- If classifier is already used -->
            <version>1.0</version>
            <type>jar</type>
          </artifactItem>
        </artifactItems>
        <outputDirectory>${project.build.directory}/classes</outputDirectory>
        <includes>aaa/**, bbb/**, ccc/**</includes> <!-- Specify directories to include -->
      </configuration>
    </execution>
  </executions>
</plugin>

Solution 13: Spring Boot’s Packaging

For Spring applications, the spring-boot-maven-plugin simplifies this process significantly. Its repackage goal creates an executable JAR with an embedded classloader, effectively managing dependencies.

<plugin>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-maven-plugin</artifactId>
  <executions>
    <execution>
      <goals>
        <goal>repackage</goal>
      </goals>
      <configuration>
        <classifier>spring-boot</classifier>
        <mainClass>com.nirav.certificate.CertificateUtility</mainClass>
      </configuration>
    </execution>
  </executions>
</plugin>

Solution 14: Dependency Plugin for Copying WARs

The maven-dependency-plugin’s copy goal can be used to copy WAR files or other artifacts into specific locations, such as the classes directory, which are then included in the final JAR.

<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-dependency-plugin</artifactId>
  <executions>
    <execution>
      <id>getWar</id>
      <phase>package</phase>
      <goals>
        <goal>copy</goal>
      </goals>
      <configuration>
        <artifactItems>
          <artifactItem>
            <groupId>the.group.I.use</groupId>
            <artifactId>MyServerServer</artifactId>
            <version>${env.JAVA_SERVER_REL_VER}</version>
            <type>war</type>
            <destFileName>myWar.war</destFileName>
          </artifactItem>
        </artifactItems>
        <outputDirectory>${project.build.directory}/classes</outputDirectory>
      </configuration>
    </execution>
  </executions>
</plugin>

Solution 15: Using dependencies Descriptor with maven-assembly-plugin

A simpler descriptor for the maven-assembly-plugin is dependencies, which also creates a fat JAR including all dependent libraries.

<plugin>
  <artifactId>maven-assembly-plugin</artifactId>
  <executions>
    <execution>
      <phase>package</phase>
      <goals>
        <goal>single</goal>
      </goals>
    </execution>
  </executions>
  <configuration>
    <descriptorRefs>
      <descriptorRef>dependencies</descriptorRef>
    </descriptorRefs>
  </configuration>
</plugin>

Considerations for Dependency Management

When packaging dependencies, potential issues include:

  • Resource Overwriting: Files with the same path in different JARs can lead to unexpected behavior.
  • Version Conflicts: Different dependencies might require conflicting versions of the same library. Shading or careful dependency management can mitigate this.
  • JAR Size: Including all dependencies can result in large JAR files. Consider modularization or optional dependencies if size is a concern.
  • Spring Boot: If you are using Spring Boot, its built-in mechanisms are generally the most straightforward for creating executable JARs.

FAQs on Maven Packaging

Q: What is the easiest way to create an executable JAR with all my dependencies in Maven

ANS: The maven-assembly-plugin with the jar-with-dependencies descriptor is often the most direct method for creating a fat JAR with all dependencies. Configuring the mainClass in the maven-jar-plugin or maven-assembly-plugin ensures it’s executable.

Q: How do I specify the main class for an executable JAR in Maven

ANS: You can specify the main class by adding a <manifest> section within the <configuration> of either the maven-jar-plugin or the maven-assembly-plugin in your pom.xml, setting the <mainClass> element.

Q: What happens if my dependencies have conflicting resources

ANS: If dependencies contain files with identical paths (e.g., in META-INF), the last file encountered during the packaging process might overwrite others. This can lead to application errors. The maven-shade-plugin with shading configurations can help by renaming packages to resolve these conflicts.

Q: Can I exclude certain dependencies from my executable JAR

ANS: Yes, you can exclude specific dependencies using Maven’s <exclusions> element within your <dependency> declarations in the pom.xml. For more granular control over which artifacts are included by plugins like maven-assembly-plugin, you might need custom assembly descriptors.

Q: What is the difference between jar-with-dependencies and the shade plugin

ANS: jar-with-dependencies simply bundles all dependencies as they are. The shade plugin, however, allows you to relocate (shade) packages within dependencies to avoid classpath conflicts, making it more robust for complex dependency graphs.
