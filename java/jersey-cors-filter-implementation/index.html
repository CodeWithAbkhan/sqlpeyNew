“Jersey CORS Configuration: Implementing Request and Response Filters for API Access Control”

How does one effectively configure Cross-Origin Resource Sharing (CORS) handling within a Jersey-based RESTful application, considering variations between Jersey 1.x and 2.x, and addressing the nuances of simple versus preflight requests?

Setting up CORS correctly is vital for frontend applications to communicate with your backend APIs hosted on different domains. Jersey offers several mechanisms, primarily through container filters.

Solution 1: Utilizing Container Filters for Jersey 2.x and 1.x

The fundamental approach involves implementing a ContainerResponseFilter. Note that the interfaces differ slightly between major Jersey versions.

Jersey 2.x Container Response Filter Implementation

For Jersey 2.x, implement ContainerResponseFilter and use ContainerRequestContext and ContainerResponseContext.

import java.io.IOException;
import javax.ws.rs.container.ContainerRequestContext;
import javax.ws.rs.container.ContainerResponseContext;
import javax.ws.rs.container.ContainerResponseFilter;
import javax.ws.rs.ext.Provider;

@Provider
public class J2CorsFilter implements ContainerResponseFilter {

    @Override
    public void filter(ContainerRequestContext request,
            ContainerResponseContext response) throws IOException {
        response.getHeaders().add("Access-Control-Allow-Origin", "*");
        response.getHeaders().add("Access-Control-Allow-Headers",
                "CSRF-Token, X-Requested-By, Authorization, Content-Type");
        response.getHeaders().add("Access-Control-Allow-Credentials", "true");
        response.getHeaders().add("Access-Control-Allow-Methods",
                "GET, POST, PUT, DELETE, OPTIONS, HEAD");
    }
}

Registration in Jersey 2.x:

If package scanning is active (using @Provider), registration may be automatic. If explicit registration is required with ResourceConfig:

final ResourceConfig resourceConfig = new ResourceConfig();
resourceConfig.register(J2CorsFilter.class); // Registering the class reference
final URI uri = new URI("http://localhost:8080/api");
final HttpServer httpServer = GrizzlyHttpServerFactory.createHttpServer(uri, resourceConfig);

Jersey 1.x Container Response Filter Implementation

Jersey 1.x uses different package imports and method signatures for its filters.

import com.sun.jersey.spi.container.ContainerRequest;
import com.sun.jersey.spi.container.ContainerResponse;
import com.sun.jersey.spi.container.ContainerResponseFilter;
import javax.ws.rs.ext.Provider;

@Provider
public class J1CorsFilter implements ContainerResponseFilter {
    @Override
    public ContainerResponse filter(ContainerRequest request,
            ContainerResponse response) {

        response.getHttpHeaders().add("Access-Control-Allow-Origin", "*");
        response.getHttpHeaders().add("Access-Control-Allow-Headers",
                "CSRF-Token, X-Requested-By, Authorization, Content-Type");
        response.getHttpHeaders().add("Access-Control-Allow-Credentials", "true");
        response.getHttpHeaders().add("Access-Control-Allow-Methods",
                "GET, POST, PUT, DELETE, OPTIONS, HEAD");

        return response;
    }
}

Registration in Jersey 1.x:

  1. web.xml Configuration: 
    <init-param>
  <param-name>com.sun.jersey.spi.container.ContainerResponseFilters</param-name>
  <param-value>com.yourpackage.J1CorsFilter</param-value>
</init-param>
  2. Programmatic Registration: 
    resourceConfig.getContainerResponseFilters().add(new J1CorsFilter());

Refinement: Handling Preflight (OPTIONS) Requests Correctly

The initial implementation above is “lazy” as it applies CORS headers to all responses, even those that aren’t cross-origin or are preflight requests. Preflight requests (OPTIONS method with an Origin header) require special handling as per the CORS specification.

A more robust filter combines ContainerRequestFilter and ContainerResponseFilter and uses @PreMatching to intercept the request early.

import javax.ws.rs.container.ContainerRequestFilter;
import javax.ws.rs.container.ContainerResponseFilter;
import javax.ws.rs.container.ContainerRequestContext;
import javax.ws.rs.container.ContainerResponseContext;
import javax.ws.rs.ext.Provider;
import javax.ws.rs.Priorities;
import javax.ws.rs.core.Response;

@Provider
@PreMatching
public class AdvancedCorsFilter implements ContainerRequestFilter, ContainerResponseFilter {

    private boolean isPreflightRequest(ContainerRequestContext request) {
        // Check for Origin header presence and OPTIONS method
        return request.getHeaderString("Origin") != null
                && request.getMethod().equalsIgnoreCase("OPTIONS");
    }

    /**
     * ContainerRequestFilter logic: Abort preflight requests early with a 200 OK.
     */
    @Override
    public void filter(ContainerRequestContext request) throws IOException {
        if (isPreflightRequest(request)) {
            // Abort processing; response filter will handle headers.
            request.abortWith(Response.ok().build());
            return;
        }
    }

    /**
     * ContainerResponseFilter logic: Add necessary CORS headers.
     */
    @Override
    public void filter(ContainerRequestContext request, ContainerResponseContext response)
            throws IOException {

        // Only proceed if an Origin header is present (i.e., it's a CORS request)
        if (request.getHeaderString("Origin") == null) {
            return;
        }

        // Headers specific to preflight responses (handled in request filter abort, but safe to set again)
        if (isPreflightRequest(request)) {
            response.getHeaders().add("Access-Control-Allow-Credentials", "true");
            response.getHeaders().add("Access-Control-Allow-Methods",
                "GET, POST, PUT, DELETE, OPTIONS, HEAD");
            response.getHeaders().add("Access-Control-Allow-Headers",
                "X-Requested-With, Authorization, " +
                "Accept-Version, Content-MD5, CSRF-Token, Content-Type");
        }

        // Access-Control-Allow-Origin is needed for both simple and preflight requests
        response.getHeaders().add("Access-Control-Allow-Origin", "*");
    }
}

Solution 2: Setting Headers Directly on Response Entity

If you bypass framework-level filters (perhaps by removing an annotation like @CrossOriginResourceSharing(allowAllOrigins = true)), you can manually set headers when returning the final Response object. This applies primarily to non-preflight requests where you control the response creation.

// Assuming 'pojoObject' needs to be serialized to JSON
// POJO Object should replace 'jsonResponse' placeholder
return Response.ok()
               .entity(pojoObject) 
               .header("Access-Control-Allow-Origin", "*")
               .build();

Solution 3: Leveraging Servlet Container Filters (e.g., Tomcat)

It is possible to mix Jersey filters with standard Servlet Filters, such as a CORS filter provided by the servlet container (like Tomcat). This configuration is often managed entirely in web.xml, separating CORS configuration from the Jersey application code.

Solution 4: Preventing Duplicate Header Errors Using put Instead of add

A common issue arises when multiple filters attempt to set the same header (Access-Control-Allow-Origin), resulting in errors like: The 'Access-Control-Allow-Origin' header contains multiple values '*, *', but only one is allowed.

If using the older Jersey 1.x style headers (response.getHttpHeaders().add(...)), switching to put can overwrite previous values instead of appending them.

// Custom Jersey 1.x Filter using put() to overwrite existing headers
public class MCORSFilter implements ContainerResponseFilter {
    // ... constants defined ...

    @Override
    public ContainerResponse filter(ContainerRequest request, ContainerResponse response) {
        for (int i = 0; i < ALL_HEADERs.length; i++) {
            ArrayList<Object> value = new ArrayList<>();
            value.add(ALL_HEADER_VALUEs[i]);
            // Using put overwrites if the key already exists
            response.getHttpHeaders().put(ALL_HEADERs[i], value); 
        }
        return response;
    }
}

This filter would then be registered via web.xml.

Solution 5: Configuration via Maven Tomcat Plugin

When using embedded Tomcat via the tomcat7-maven-plugin, CORS configuration can be injected by pointing the plugin to a custom web.xml containing the necessary filter definitions, ensuring CORS is active during integration tests or development builds.

<!-- Snippet from pom.xml using tomcat7-maven-plugin -->
<configuration>
    <port>${maven.tomcat.port}</port>
    <useSeparateTomcatClassLoader>true</useSeparateTomcatClassLoader>
    <contextFile>${project.basedir}/tomcat/context.xml</contextFile>
    <tomcatWebXml>${maven.tomcat.web-xml.file}</tomcatWebXml> <!-- Points to custom web.xml -->
</configuration>

Solution 6: Conditional CORS based on Environment or Annotation (Jersey 3)

For more granular control, especially in Jersey 3, one might implement a DynamicFeature that conditionally registers a CORS filter based on an environment flag (isCORS) or the presence of a custom annotation (@CORS) on resource methods.

This involves:

  1. A configuration flag set during ResourceConfig setup (e.g., in MyApplication extending ResourceConfig).
  2. A custom annotation @CORS.
  3. A CORSFilterDynamic implementing DynamicFeature to register the filter only when needed.
  4. A combined ContainerRequestFilter (to abort preflight OPTIONS requests) and ContainerResponseFilter (to set headers).
// Excerpt from the Request Filter part:
@Override public void filter(ContainerRequestContext creq) throws IOException {
    if(isPreflight(creq))
         // Abort request so resource method isn't invoked
         creq.abortWith(Response.ok().build()); 
}
// ... In Response Filter ...
@Override public void filter(ContainerRequestContext creq, ContainerResponseContext cres) throws IOException {
    setCORS(cres, creq.getHeaderString("Origin") );
}

Solution 7: Handling Multiple Allowed Origins Dynamically

If you need to allow specific origins rather than universally allowing *, you must inspect the incoming Origin header and set the Access-Control-Allow-Origin header dynamically to match the caller’s domain, or use * if the domain is recognized.

@Provider
public class DynamicCorsFilter implements ContainerResponseFilter {

    @Override
    public void filter(ContainerRequestContext requestContext, ContainerResponseContext responseContext) {

        final String domain = generateAllowOrigin(requestContext);

        responseContext.getHeaders().add("Access-Control-Allow-Origin", domain);
        // ... other headers ...
    }

    private static String generateAllowOrigin(ContainerRequestContext requestContext) {
        String callerOrigin = requestContext.getHeaderString("Origin");
        final String allowedDomain;
        
        // Example: Allow specific port or a fallback production domain
        if (callerOrigin != null && callerOrigin.contains("localhost:4141")) {
            allowedDomain = "http://localhost:4141";
        } else {
            allowedDomain = "https://example.com";
        }
        return allowedDomain;
    }
}

FAQs on Jersey CORS Filter Implementation

Q: How do I configure CORS filters for Jersey 1x versus Jersey 2x

ANS: Jersey 1.x uses com.sun.jersey.spi.container.ContainerResponseFilter with response.getHttpHeaders().add(), while Jersey 2.x uses javax.ws.rs.container.ContainerResponseFilter with responseContext.getHeaders().add(). Registration methods also differ (Servlet filter vs. ResourceConfig).

Q: What is the purpose of aborting the request in the ContainerRequestFilter for OPTIONS

ANS: Aborting the request with request.abortWith(Response.ok().build()); prevents the actual REST resource method (like a GET or POST handler) from executing for a preflight OPTIONS request. The response filter then immediately adds the required CORS headers to the aborted 200 OK response.

Q: How to solve Access-Control-Allow-Origin header contains multiple values error

ANS: This error happens when multiple filters attempt to set the same header. In older Jersey styles (1.x), switch from using the add method to the put method on the HttpHeaders map to overwrite any previously set value for that specific header key.

Q: Can I use Tomcat's native CORS filter with Jersey

ANS: Yes, it is possible to mix standard Servlet Filters, like Tomcat’s CORS filter configured in web.xml, with Jersey’s JAX-RS filters.

Q: Should Access-Control-Allow-Origin always be set to *

ANS: Setting it to * allows all origins. For production environments, it is safer to dynamically check the incoming Origin request header and explicitly list the allowed domain(s) instead of using *.
