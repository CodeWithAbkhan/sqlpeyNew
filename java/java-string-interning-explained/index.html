“Java String Interning Explained: Memory Saving & Comparison”

When working with strings in Java, you might have encountered situations where two seemingly identical strings behave differently when compared using == versus .equals(). This often boils down to Java’s string interning mechanism. What exactly is string interning, how does it impact memory usage, and when should you be mindful of its behavior?

Let’s delve into the intricacies of Java’s string pool and the String.intern() method.

What is String Interning?

String interning is an optimization technique where Java ensures that all string literals with the same sequence of characters refer to a single, unique String object. This is achieved by maintaining a special memory area known as the “string pool” or “String Constant Pool” (SCP).

When you create a string literal (e.g., String myString = "example";), Java checks if a string with that exact content already exists in the string pool.

  • If it exists, Java returns a reference to that existing object.
  • If it doesn’t exist, a new String object is created in the string pool, and its reference is returned.

This process significantly reduces memory consumption, especially when the same string literal appears multiple times within your application.

The String.intern() Method

The String.intern() method provides a way to explicitly add a string to the string pool or retrieve a string from it if it already exists. When intern() is called on a String object:

  1. Java checks if the string’s content is already present in the string pool.
  2. If found, it returns a reference to the existing string in the pool.
  3. If not found, it adds the string to the pool and returns a reference to the newly added object.

This is particularly useful for strings created dynamically, such as those generated from user input or by concatenating other strings, as they might not automatically be placed in the string pool.

Memory Considerations with intern()

Historically, prior to JDK 7, interned strings were stored in the Permanent Generation (PermGen) of the JVM. PermGen had a fixed, limited size, and excessive use of String.intern() could lead to OutOfMemoryError: PermGen space.

From JDK 7 onwards, this behavior changed significantly. Interned strings are now allocated within the main Java heap (young and old generations), just like other objects. While this resolves the PermGen issue, it means that a larger portion of your application’s heap may be occupied by interned strings. For applications that heavily rely on String.intern() with a vast number of unique strings, this could necessitate adjusting heap sizes.

  • Benefit: Reduces memory by ensuring duplicate string values point to the same object.
  • Caveat: Overuse with many unique strings can increase overall heap usage.

You can find more details on these changes in the Java SE 7 Features and Enhancements documentation.

== vs. .equals(): The Crucial Distinction

In Java, the == operator compares the references of objects, while the .equals() method compares the content of objects. This difference is critical when dealing with strings and the string pool.

  • == Operator: Checks if two string variables point to the exact same object in memory.
  • .equals() Method: Checks if the sequence of characters within two string objects is identical.

Illustrative Example:

String literal1 = "Hello";
String literal2 = "Hello";
String dynamicString = new String("Hello");

System.out.println("literal1 == literal2: " + (literal1 == literal2)); // Output: true
System.out.println("literal1.equals(literal2): " + literal1.equals(literal2)); // Output: true

System.out.println("literal1 == dynamicString: " + (literal1 == dynamicString)); // Output: false
System.out.println("literal1.equals(dynamicString): " + literal1.equals(dynamicString)); // Output: true

String internedDynamic = dynamicString.intern();
System.out.println("literal1 == internedDynamic: " + (literal1 == internedDynamic)); // Output: true

In this example:

  • literal1 and literal2 both refer to the same “Hello” object in the string pool, so literal1 == literal2 is true.
  • dynamicString is created using new String(), which explicitly allocates a new String object in the heap, separate from the string pool. Therefore, literal1 == dynamicString is false, even though their contents are the same.
  • Calling dynamicString.intern() makes internedDynamic point to the existing “Hello” object in the string pool, thus literal1 == internedDynamic becomes true.

This clearly demonstrates why using .equals() is generally preferred for comparing string content to avoid issues related to where and how the string object was created.

Practical Code Snippets

Let’s examine some code scenarios:

Scenario 1: Compiler Interning

The compiler automatically interns string literals.

String s1 = "testString";
String s2 = "testString";
if (s1 == s2) {
    System.out.println("equals!"); // This will print "equals!"
}

This works because both s1 and s2 point to the same “testString” object in the string pool due to compiler optimization.

Scenario 2: JVM Interning and String Concatenation

When strings are concatenated at compile time using literals, the result is also interned. However, if concatenation involves a non-literal variable, a new string object might be created in the heap, which can then be interned.

String hello = "Hello";
String lo = "lo";
System.out.println(hello == "Hello"); // true (literal)
System.out.println(hello == ("Hel" + "lo")); // true (compile-time constant folding)
System.out.println(hello == ("Hel" + lo)); // false (runtime concatenation with variable)
System.out.println(hello == ("Hel" + lo).intern()); // true (interning the runtime result)

Scenario 3: Comparing int to String

When converting numbers to strings, it’s crucial to remember the difference between string literals and dynamically created strings.

String value1 = "70"; // Interned literal
String value2 = "70"; // Also points to the same interned literal
String value3 = new Integer(70).toString(); // Creates a new String object in the heap

System.out.println("value1 == value2: " + (value1 == value2));         // true
System.out.println("value1 == value3: " + (value1 == value3));         // false
System.out.println("value1.equals(value3): " + value1.equals(value3)); // true
System.out.println("value1 == value3.intern(): " + (value1 == value3.intern())); // true

Scenario 4: Bytecode Perspective

Decompiling bytecode reveals how ldc (load constant pool) instruction is used for string literals, referencing a dedicated CONSTANT_String_info structure pointing to CONSTANT_Utf8_info.

// Example bytecode representation for String literals
public class StringPool {
    public static void main(String[] args) {
        String a = "abc"; // Loaded via ldc #2
        String b = "abc"; // Also loaded via ldc #2
        String c = new String("abc"); // New String object created

        System.out.println(a == c); // Compares references of a and c
    }
}

This shows direct bytecode support for the string pool, making it efficient. Unlike primitive wrappers like Integer, which rely on method calls (Integer.valueOf()) for pooling, strings have a more direct mechanism.

String Interning in C# (for comparison)

While the core concept of interning exists in other languages, implementation details vary. In C#, string interning is also managed by the runtime.

object obj = "Int32";
string str1 = "Int32";
string str2 = typeof(int).Name; // Evaluated at runtime via reflection

Console.WriteLine(obj == str1); // true (both refer to interned literal)
Console.WriteLine(str1 == str2); // true (runtime evaluation results in same string)
Console.WriteLine(obj == str2); // true (if str2 is interned and matches)

In C#, if typeof(int).Name evaluates to “Int32”, and “Int32” is already in the intern pool (which it would be if used as a literal elsewhere), then all comparisons would yield true. The key is that runtime evaluations might not immediately place strings in the intern pool unless explicitly done or if the runtime optimizes it.

Summary of String Pool Behavior

  • Literals ("..."): Java automatically places string literals into the string pool. Identical literals point to the same object.
  • new String("..."): Creates a new String object in the heap, separate from the pool. It does not automatically add the string to the pool.
  • String.intern(): Explicitly adds a string to the pool if it’s not already there and returns a reference to the pooled object. This is how you can get a pool reference for strings created with new.

FAQs on Java String Interning Explained

Q: What is the primary benefit of Java string interning

ANS: The primary benefit is memory efficiency. By ensuring that identical string literals refer to a single object in the string pool, Java avoids creating multiple copies of the same string, thereby saving memory.

Q: When should I use String.intern()

ANS: Use String.intern() when you have strings created dynamically (e.g., from user input, file reads, or complex concatenations) and you want to ensure they are part of the string pool for potential memory savings if these strings are frequently duplicated. Be mindful of heap usage in Java 7+.

Q: Why does '==' sometimes return true for strings and sometimes false

ANS: The == operator compares object references. If two string variables point to the same object in memory (e.g., they are both interned string literals referring to the same pool entry), == returns true. If they point to different objects (even if the content is identical), == returns false. This is why .equals() is generally preferred for comparing string content.

Q: Where are interned strings stored in Java 7 and later

ANS: In Java 7 and later, interned strings are stored in the main Java heap (young and old generations), not in the separate Permanent Generation (PermGen) which was removed.

Q: Is there any performance cost to using String.intern()

ANS: Yes, calling String.intern() involves a lookup in the string pool. If the string is not found, it also involves adding it to the pool. This lookup and potential addition can have a slight performance overhead compared to simply using a string literal. However, the memory savings from effective interning often outweigh this overhead for applications with many duplicate strings.

Q: How does interning affect string concatenation

ANS: String literals concatenated at compile time are interned. For example, "a" + "b" results in an interned "ab". However, if a variable is involved, like "a" + variableB, the result is typically a new String object created in the heap, which you might then need to intern() yourself if you want it in the pool.
