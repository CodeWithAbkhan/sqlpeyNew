“Implementing Token Authentication and Authorization in JAX-RS 2 0”

Token-based authentication presents an alternative to traditional session management. At its core, a client swaps persistent credentials (like username and password) for a temporary data artifact—the token. Subsequent requests leverage this token for verification instead of repeatedly sending the initial credentials.

How does this sequence operate in practice?

  1. Credential Submission: The client transmits user credentials (username/password) to the server.
  2. Token Generation: Upon validating these credentials, the server produces a unique token intended for the user.
  3. Server Storage: The server records this newly generated token, associating it with the user ID and setting an expiration time in persistent storage.
  4. Token Return: The server sends the created token back to the client.
  5. Subsequent Requests: The client includes this token with every following request directed to the server.
  6. Token Verification: For each incoming request, the server extracts the token, looks up associated user details to confirm authenticity.

If the token verification succeeds, the server processes the request. Failure results in a request denial. Following successful authentication, the server then proceeds to authorization checks. Some token schemes feature an explicit endpoint for token refreshment.

Employing Pure JAX-RS 2.0 (Jersey, RESTEasy, Apache CXF)

This approach strictly adheres to the JAX-RS 2.0 specification, avoiding proprietary vendor features. This ensures interoperability across implementations like Jersey, RESTEasy, and Apache CXF. It is important to recognize that token authentication represents a bespoke security mechanism, diverging from built-in Java EE security features configurable in the web.xml descriptor.

Authenticating Credentials and Issuing a Token

The initial step involves creating a JAX-RS resource method capable of receiving and verifying credentials, subsequently issuing the token.

When submitting credentials via application/x-www-form-urlencoded, the payload must look like this:

username=tester&password=secure123

Here is a sample resource for credential handling:

@Path("/authentication")
public class IdentityService {

    @POST
    @Produces(MediaType.APPLICATION_JSON)
    @Consumes(MediaType.APPLICATION_FORM_URLENCODED)
    public Response exchangeCredentials(@FormParam("username") String user,

        try {

            verifyIdentity(user, pass);

            String generatedToken = constructToken(user);

            return Response.ok(generatedToken).build();

        } catch (SecurityException ex) {
            // Credentials failed validation
            return Response.status(Response.Status.FORBIDDEN).build();
        }      
    }

    private void verifyIdentity(String user, String pass) throws SecurityException {
        // Logic to check user/pass against DB, LDAP, etc.
        // Throw SecurityException if credentials fail.
    }

    private String constructToken(String user) {
        // Create a random string or a JWT, associating it to the user.
        return "secure_token_value_for_" + user;

Extracting and Validating the Token

The client must present the token in the standard HTTP Authorization header, typically formatted as Authorization: Bearer <token-goes-here>.

To intercept requests and perform validation before they reach resource methods, JAX-RS offers @NameBinding. We define a custom annotation, say @Protected, to mark methods requiring security:

@NameBinding
@Retention(java.lang.annotation.RetentionPolicy.RUNTIME)
@Target({java.lang.annotation.ElementType.TYPE, java.lang.annotation.ElementType.METHOD})
public @interface Protected { }

This binding targets a ContainerRequestFilter, which executes early in the request pipeline, allowing access to headers via ContainerRequestContext.

@Protected
@Provider
@Priority(Priorities.AUTHENTICATION)
public class TokenValidationFilter implements ContainerRequestFilter {

    private static final String AUTH_REALM = "ServiceRealm";
    private static final String AUTH_SCHEME = "Bearer";

    @Override
    public void filter(ContainerRequestContext context) throws java.io.IOException {

        // Fetch the Authorization header value
        String authHeader = context.getHeaderString(HttpHeaders.AUTHORIZATION);

        // Verify header structure
        if (!isBearerScheme(authHeader)) {
            denyAccess(context, "Missing or invalid Authorization scheme.");
            return;
        }

        // Isolate the token value
        String token = authHeader.substring(AUTH_SCHEME.length()).trim();

        try {
            // Verify token validity (signature, expiration, issuer)
            verifyTokenSignature(token);

        } catch (java.lang.SecurityException e) {
            denyAccess(context, "Token validation failed.");
        }
    }

    private boolean isBearerScheme(String header) {
        // Case-insensitive check for "Bearer " prefix
        return header != null && header.toLowerCase()
                    .startsWith(AUTH_SCHEME.toLowerCase() + " ");
    }

    private void denyAccess(ContainerRequestContext context, String message) {
        // Abort processing, send 401 Unauthorized
        context.abortWith(
                Response.status(Response.Status.UNAUTHORIZED)
                        .header(HttpHeaders.WWW_AUTHENTICATE, 
                                AUTH_SCHEME + " realm=\"" + AUTH_REALM + "\"")
                        .build());
    }

    private void verifyTokenSignature(String token) throws java.lang.SecurityException {
        // Detailed check against stored tokens or cryptographic verification (e.g., JWT)
        // Throw an exception if invalid.
    }
}

If validation fails, the filter aborts the chain, sending back 401 Unauthorized. Upon success, processing continues to the intended resource method.

Determining the Active User Identity

After successful authentication, obtaining the user principal is often necessary.

Approach A: Overriding the Security Context

Within the ContainerRequestFilter, you can replace the request’s SecurityContext:

final SecurityContext originalContext = context.getSecurityContext();

context.setSecurityContext(new SecurityContext() {
    @Override
    public Principal getUserPrincipal() {
        // Return a Principal based on the validated username
        return () -> validatedUsername; 
    }
    // Implement other SecurityContext methods...
    @Override
    public boolean isUserInRole(String role) { /* ... */ return true; }
    @Override
    public boolean isSecure() { return originalContext.isSecure(); }
    @Override
    public String getAuthenticationScheme() { return AUTH_SCHEME; }
});

This allows injection into resource classes or methods using @Context:

@GET
@Protected

    Principal user = secCtx.getUserPrincipal();
    String name = user.getName(); // This will be the username retrieved from the token
    return Response.ok("Logged in as: " + name).build();
}
Approach B: Utilizing CDI (Contexts and Dependency Injection)

If overriding SecurityContext is undesirable, CDI events offer a decoupled way to propagate user data across request scope.

  1. Define a Qualifier:

    @Qualifier
@Retention(RUNTIME)
@Target({ METHOD, FIELD, PARAMETER })
public @interface AuthenticatedPrincipal { }

  2. Fire Event in Filter: Inject the CDI event bus in your filter:

    @Inject @AuthenticatedPrincipal Event<String> userEvent;
// ... in filter method after validation ...

  3. Produce the User Instance: A CDI producer bean binds the event to a request-scoped object (User):

    @RequestScoped
public class UserProducer {

    @Produces
    @RequestScoped
    @AuthenticatedPrincipal
    private User activeUser;

    public void captureEvent(@Observes @AuthenticatedPrincipal String username) {
        this.activeUser = retrieveUserRecord(username);
    }

    private User retrieveUserRecord(String user) {
        // Logic to fetch User object from persistence layer
        return new User(user); 
    }
}

  4. Inject the User: Now, any CDI-managed bean (like a JAX-RS service) can inject the active user:

    @Inject @AuthenticatedPrincipal User currentUser;

@GET @Protected
public Response getUserDetails() {
    return Response.ok("User ID: " + currentUser.getId()).build();
}

Note on Annotations: Be precise: CDI: javax.enterprise.inject.Produces differs from JAX-RS: javax.ws.rs.Produces.

Token Formats: Opaque vs. Self-Contained

Tokens can be:

  • Opaque: A random, non-descriptive value requiring a server lookup (e.g., a database ID).
  • Self-contained: Carries user claims directly (e.g., JWT).

Random String as an Opaque Token

Generate a cryptographically secure random string and persist it alongside the user ID and expiry time. Secure random generation example:

import java.security.SecureRandom;
import java.math.BigInteger;

// Inside issueToken method:
SecureRandom rng = new SecureRandom();
String opaqueToken = new BigInteger(160, rng).toString(36).toUpperCase();
// Store opaqueToken and user mapping...
return opaqueToken;

JWT (JSON Web Token)

JWT (RFC 7519) encapsulates claims in its payload, Base64-encoded JSON. Standard claims include:

  • iss: Issuer
  • sub: Subject (user ID)
  • exp: Expiration time
  • nbf: Not before time
  • iat: Issued at time
  • jti: Unique token identifier

Security Warning: Never place sensitive data like passwords inside JWT claims. The payload is only encoded, not encrypted, though the signature prevents tampering.

If tracking is not strictly required, JWTs don’t necessitate server storage. However, storage allows for immediate revocation. If persisting JWTs for tracking, store only the jti claim along with metadata (user, expiry) to manage database size by regularly purging old entries.

Popular Java JWT Libraries:

  • jjwt
  • java-jwt
  • jose4j

For further JWT insights, consult https://jwt.io .

Handling JWT Revocation

To revoke a JWT before its natural expiry, you must track its unique identifier (jti claim). When validating a token, verify that its jti is not present in a server-side blacklist. For robust security, execute a full token blacklist check for any user who modifies their password.

Final Security Consideration

Regardless of the chosen authentication method, ensure all communications occur over HTTPS to mitigate man-in-the-middle attacks.

Role-Based Authorization Augmentation

The authentication structure described above can be extended for authorization checks, often separated into a distinct step or filter executing after authentication.

Custom @Secured Annotation for Role Authorization

If relying on custom roles defined in an enumeration:

public enum AppRole {
    ADMINISTRATOR,
    STANDARD_USER,
    GUEST
}

Update the binding annotation to accept roles:

@NameBinding
@Retention(RUNTIME)
@Target({TYPE, METHOD})
public @interface Protected {
    AppRole[] requiredRoles() default {}; // Default to no specific role needed
}

Apply this to resources, allowing method annotations to override class definitions:

@Path("/admin-area")
@Protected(requiredRoles = {AppRole.ADMINISTRATOR})
public class AdminPanel {

    @GET
    public Response viewDashboard() {
        // Accessible only by users possessing ADMINISTRATOR role
        return Response.ok("Admin View").build();
    }
}

This requires an AuthorizationFilter prioritized after the authentication filter (@Priority(Priorities.AUTHORIZATION)). This filter inspects ResourceInfo to find the required roles and checks the authenticated user’s roles (available via the SecurityContext set previously).

@Protected
@Provider
@Priority(Priorities.AUTHORIZATION)
public class RoleAuthorizationFilter implements ContainerRequestFilter {

    @Context
    private ResourceInfo resourceContext;

    @Override
    public void filter(ContainerRequestContext context) throws java.io.IOException {
        
        // Get method/class annotations to find required roles
        Method targetMethod = resourceContext.getResourceMethod();
        Class<?> targetClass = resourceContext.getResourceClass();

        Protected classSecured = targetClass.getAnnotation(Protected.class);
        Protected methodSecured = targetMethod.getAnnotation(Protected.class);

        AppRole[] requiredRoles;

        if (methodSecured != null) {
            requiredRoles = methodSecured.requiredRoles();
        } else if (classSecured != null) {
            requiredRoles = classSecured.requiredRoles();
        } else {
            // No @Protected on method or class, assume authenticated access is fine
            return;
        }

        if (requiredRoles.length > 0) {
            verifyUserRoles(requiredRoles, context.getSecurityContext());
        }
        // If requiredRoles is empty, access is permitted for any authenticated user.
    }

    private void verifyUserRoles(AppRole[] needed, SecurityContext security) throws SecurityException {
        for (AppRole role : needed) {
            if (security.isUserInRole(role.name())) {
                return; // Found required role
            }
        }
        // If loop completes, throw exception to deny access (403 Forbidden)
        throw new SecurityException("Insufficient privileges.");
    }
}

Supporting JSR-250 Annotations (@RolesAllowed, @PermitAll, @DenyAll)

JAX-RS does not natively support JSR-250 security annotations, but a custom filter can interpret them. The precedence rules are critical: method annotations generally override class annotations.

A filter prioritizing JSR-250 checks might look like this:

@Provider
@Priority(Priorities.AUTHORIZATION)
public class Jsr250AuthorizationFilter implements ContainerRequestFilter {

    @Context
    private ResourceInfo info;

    @Override
    public void filter(ContainerRequestContext context) throws java.io.IOException {
        Method method = info.getResourceMethod();
        
        // 1. Check @DenyAll on method (highest precedence)
        if (method.isAnnotationPresent(DenyAll.class)) {
            refuse(context);
        } 
        
        // 2. Check @RolesAllowed on method
        RolesAllowed methodRoles = method.getAnnotation(RolesAllowed.class);
        if (methodRoles != null) {
            checkRoles(methodRoles.value(), context);
            return;
        }

        // 3. Check @PermitAll on method
        if (method.isAnnotationPresent(PermitAll.class)) {
            return; // Access granted regardless of class settings
        }

        // 4. Check @RolesAllowed on class
        RolesAllowed classRoles = info.getResourceClass().getAnnotation(RolesAllowed.class);
        if (classRoles != null) {
            checkRoles(classRoles.value(), context);
            return;
        }

        // 5. Check @PermitAll on class
        if (info.getResourceClass().isAnnotationPresent(PermitAll.class)) {
            return;
        }

        // 6. Default: If no annotation implies authentication is required
        if (!isUserAuthenticated(context)) {
            refuse(context);
        }
    }
    
    private void refuse(ContainerRequestContext context) {
        context.abortWith(Response.status(Response.Status.FORBIDDEN).build());
    }

    private void checkRoles(String[] required, SecurityContext security) {
        boolean permitted = false;
        for (String role : required) {
            if (security.isUserInRole(role)) {
                permitted = true;
                break;
            }
        }
        if (!permitted) {
            refuse(context);
        }
    }
    
    private boolean isUserAuthenticated(ContainerRequestContext context) {
        // Example check: return context.getSecurityContext().getUserPrincipal() != null;
        return false; 
    }
}

FAQs on Token Authentication Authorization in JAX-RS

Q: What is the primary benefit of token authentication over traditional session management

ANS: Token authentication decouples the client state from the server session. Tokens are typically stateless (especially JWTs), simplifying horizontal scaling across multiple servers since no shared session data needs constant synchronization.

Q: Can I use JWT tokens without server-side storage

ANS: Yes, if you rely solely on cryptographic signature verification for integrity and use claims like ’exp’ for expiry, the token itself contains all necessary validation data. Server storage is only needed if you require immediate revocation before expiry or need to store opaque references.

Q: How does a client send the generated token back to the server

ANS: The client commonly places the token in the HTTP Authorization header, prefixed with the scheme, like Authorization: Bearer eyJhbGciOiJ....

Q: What HTTP status code indicates an authentication failure due to an invalid token

ANS: An invalid token during the request phase generally results in a 401 Unauthorized response, as indicated when the AuthenticationFilter aborts the request chain.

Q: How do method annotations override class annotations in authorization

ANS: In authorization filter design, specific annotations applied directly to a resource method (like @Protected(requiredRoles = {ROLE_X})) take precedence over annotations applied to the containing resource class, allowing finer control over endpoint security.

            refuseRequest();
        }

        // @RolesAllowed on the method takes precedence over @PermitAll
        RolesAllowed rolesAllowed = method.getAnnotation(RolesAllowed.class);
        if (rolesAllowed != null) {
            performAuthorization(rolesAllowed.value(), requestContext);
            return;
        }

        // @PermitAll on the method takes precedence over @RolesAllowed on the class
        if (method.isAnnotationPresent(PermitAll.class)) {
            // Do nothing
            return;
        }

        // @DenyAll can't be attached to classes

        // @RolesAllowed on the class takes precedence over @PermitAll on the class
        rolesAllowed = 
            resourceInfo.getResourceClass().getAnnotation(RolesAllowed.class);
        if (rolesAllowed != null) {
            performAuthorization(rolesAllowed.value(), requestContext);
        }

        // @PermitAll on the class
        if (resourceInfo.getResourceClass().isAnnotationPresent(PermitAll.class)) {
            // Do nothing
            return;
        }

        // Authentication is required for non-annotated methods
        if (!isAuthenticated(requestContext)) {
            refuseRequest();
        }
    }

    /**
     * Perform authorization based on roles.
     *
     * @param rolesAllowed
     * @param requestContext
     */
    private void performAuthorization(String[] rolesAllowed, 
                                      ContainerRequestContext requestContext) {

        if (rolesAllowed.length &gt; 0 &amp;&amp; !isAuthenticated(requestContext)) {
            refuseRequest();
        }

        for (final String role : rolesAllowed) {
            if (requestContext.getSecurityContext().isUserInRole(role)) {
                return;
            }
        }

        refuseRequest();
    }

     * Check if the user is authenticated.
