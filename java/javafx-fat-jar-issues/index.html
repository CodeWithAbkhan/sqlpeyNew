“JavaFX Fat Jar Issues and Modern Distribution Alternatives”

When building JavaFX applications, particularly those intended for wider distribution, packaging them into a single “fat” or “uber” jar is a common desire. However, this approach can lead to specific errors, especially with JavaFX versions like 11 and later, and brings forth modern alternatives for more robust application distribution.

Why Do Fat/Uber Jars Fail with JavaFX 11+?

The core of the problem lies in how JavaFX, since version 11, is distributed as a set of modular JAR files. The JavaFX runtime specifically expects these modules to be present and loaded correctly within the module path. When you create a fat jar, you are essentially bypassing the module path and placing all classes onto the classpath.

This conflict is highlighted by the sun.launcher.LauncherHelper within the java.base module. When your main application class extends javafx.application.Application and has a main method, LauncherHelper checks for the javafx.graphics module to be available as a named module. If it’s not found (because it’s on the classpath within your fat jar), the launch process is aborted.

You might also encounter a warning from the Maven shade plugin itself: [WARNING] Discovered module-info.class. Shading will break its strong encapsulation. This warning points to the underlying issue: by bundling everything into a single jar, you disrupt the strong encapsulation provided by Java’s module system.

The JavaFX runtime relies on this modular structure. Loading JavaFX classes from the classpath breaks encapsulation, preventing you from leveraging the benefits of the Java module system.

Workaround: The Separate Main Class Approach

An often-cited solution, particularly for Maven projects, involves creating a new, simple main class that does not extend Application. This new class’s sole purpose is to delegate the execution to your original Application class.

1. Create a New Main Class:

Introduce a new class within your application’s package. A name like NewMain is illustrative, though you should choose a more descriptive name for your project.

// src/main/java/com/example/myapp/NewMain.java
package com.example.myapp;

import javafx.application.Application;

public class NewMain {

    public static void main(String[] args) {
        // Delegate the launch to the original Application class
        Application.launch(com.example.myapp.Main.class, args);
    }
}

2. Keep Your Original Main Class:

Your existing Main class, which extends Application, remains as is.

// src/main/java/com/example/myapp/Main.java
package com.example.myapp;

import javafx.application.Application;
import javafx.stage.Stage;

public class Main extends Application {

    @Override
    public void start(Stage stage) {
        // Your application's UI setup
        System.out.println("JavaFX Application Started!");
    }

    public static void main(String[] args) {
        launch(args); // This method is still useful for certain execution contexts
    }
}

3. Configure Your Build Tool (Maven Example):

You need to instruct your build tool, such as the Maven shade plugin, to use this new NewMain class as the entry point for your fat jar.

In your pom.xml file, within the shade plugin configuration, set the <mainClass> to your new entry point:

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-shade-plugin</artifactId>
            <version>3.5.1</version> <!-- Use a recent version -->
            <executions>
                <execution>
                    <phase>package</phase>
                    <goals>
                        <goal>shade</goal>
                    </goals>
                    <configuration>
                        <transformers>
                            <transformer implementation="org.apache.maven.plugins.shade.resource.ManifestResourceTransformer">
                                <mainClass>com.example.myapp.NewMain</mainClass>
                            </transformer>
                        </transformers>
                    </configuration>
                </execution>
            </executions>
        </plugin>
    </plugins>
</build>

After building, you can run your fat jar:

java -jar your-application-name-1.0-SNAPSHOT.jar

Important Note on Warnings:

Even with this workaround, you will likely still see warnings upon execution:

Oct 02, 2021 1:45:21 PM com.sun.javafx.application.PlatformImpl startup
WARNING: Unsupported JavaFX configuration: classes were loaded from 'unnamed module @14c24f4c'
[WARNING] Discovered module-info.class. Shading will break its strong encapsulation.

These warnings are indicators that the fat jar approach is not the officially recommended or robust method for distributing JavaFX applications.

Platform-Specific vs. Cross-Platform Fat Jars

The Maven shade plugin, by default, bundles dependencies based on your current operating system. If you’re on Windows, it will include the Windows-specific native libraries for JavaFX.

<!-- Example dependency setup -->
<dependencies>
    <dependency>
        <groupId>org.openjfx</groupId>
        <artifactId>javafx-controls</artifactId>
        <version>11.0.2</version>
    </dependency>
    <dependency>
        <groupId>org.openjfx</groupId>
        <artifactId>javafx-graphics</artifactId>
        <version>11.0.2</version>
        <classifier>win</classifier> <!-- Windows specific -->
    </dependency>
    <!-- ... other platform dependencies -->
</dependencies>

This results in a fat jar that is platform-specific. Running java -jar your-application.jar will only work on the platform for which the native libraries were included.

To create a truly cross-platform fat jar, you must explicitly include the native library dependencies for all target platforms (Windows, Linux, macOS).

<dependencies>
    <!-- Base dependencies -->
    <dependency>
        <groupId>org.openjfx</groupId>
        <artifactId>javafx-controls</artifactId>
        <version>11.0.2</version>
    </dependency>
    <dependency>
        <groupId>org.openjfx</groupId>
        <artifactId>javafx-graphics</artifactId>
        <version>11.0.2</version>
    </dependency>
    <dependency>
        <groupId>org.openjfx</groupId>
        <artifactId>javafx-base</artifactId>
        <version>11.0.2</version>
    </dependency>

    <!-- Platform-specific dependencies -->
    <dependency>
        <groupId>org.openjfx</groupId>
        <artifactId>javafx-controls</artifactId>
        <version>11.0.2</version>
        <classifier>win</classifier>
    </dependency>
    <dependency>
        <groupId>org.openjfx</groupId>
        <artifactId>javafx-graphics</artifactId>
        <version>11.0.2</version>
        <classifier>win</classifier>
    </dependency>
    <dependency>
        <groupId>org.openjfx</groupId>
        <artifactId>javafx-controls</artifactId>
        <version>11.0.2</version>
        <classifier>linux</classifier>
    </dependency>
    <dependency>
        <groupId>org.openjfx</groupId>
        <artifactId>javafx-graphics</artifactId>
        <version>11.0.2</version>
        <classifier>linux</classifier>
    </dependency>
    <dependency>
        <groupId>org.openjfx</groupId>
        <artifactId>javafx-controls</artifactId>
        <version>11.0.2</version>
        <classifier>mac</classifier>
    </dependency>
    <dependency>
        <groupId>org.openjfx</groupId>
        <artifactId>javafx-graphics</artifactId>
        <version>11.0.2</version>
        <classifier>mac</classifier>
    </dependency>
</dependencies>

The Size Concern

A significant drawback of the cross-platform fat jar approach is the substantial increase in file size. Including native libraries for multiple operating systems can easily push the jar size into hundreds of megabytes. For instance, if your application utilizes the WebView control, the inclusion of WebKit native libraries alone can add approximately 220 MB.

Support for Apple M Series Processors

For macOS applications targeting newer Macs with Apple’s M series processors (ARM-based), you also need to include the mac-aarch64 classifier for JavaFX graphics dependencies. This is supported from JavaFX 19 onwards. Ensure all your JavaFX components use the same version, and that your JDK also supports M series Macs (e.g., JDK 17+).

<dependency>
    <groupId>org.openjfx</groupId>
    <artifactId>javafx-graphics</artifactId>
    <version>20.0.2</version> <!-- Example version -->
    <classifier>mac-aarch64</classifier>
</dependency>

Modern Alternatives for JavaFX Distribution

Given the limitations and warnings associated with fat jars, it’s highly recommended to explore modern, native distribution methods provided by the JDK and GraalVM. These tools offer better performance, smaller deployment sizes, and a more native feel for your applications.

  • jlink: This tool allows you to create a custom runtime image that includes only the necessary modules for your application and the JVM. This results in smaller, more efficient deployments.
  • jpackage: Builds upon jlink to create native installers for your application, tailored for specific operating systems (e.g., .exe for Windows, .dmg for macOS, .deb/.rpm for Linux). This provides a familiar installation experience for users.
  • GraalVM native-image: For truly native executables, GraalVM’s native-image tool can compile your Java application ahead-of-time into a self-contained native binary. This offers significant performance improvements and can eliminate the need for a separate JVM installation.

These methods respect the modularity of JavaFX and avoid the pitfalls of the fat jar approach. For more details on packaging JavaFX applications, refer to the Packaging in the JavaFX tag or official Oracle/OpenJFX documentation.

FAQs on JavaFX Fat Jar Issues and Modern Distribution Alternatives

Q: Why does my JavaFX application fail when packaged as a fat jar on Java 11

ANS: JavaFX 11 and later are distributed as modules. Fat jars place all code on the classpath, which breaks JavaFX’s modularity expectations. The sun.launcher.LauncherHelper detects this and aborts the launch because the required javafx.graphics module is not found as a named module.

Q: What is the workaround for creating a runnable fat jar with JavaFX

ANS: Create a new main class that doesn’t extend javafx.application.Application. This new class simply calls Application.launch() with your original application class. You then configure your build tool (e.g., Maven shade plugin) to use this new class as the entry point.

Q: Will the workaround for fat jars make the warnings disappear

ANS: No, the warnings about “Unsupported JavaFX configuration” and “Discovered module-info.class” will still appear. These indicate that the fat jar approach is not the recommended way to package JavaFX applications.

Q: How can I create a cross-platform JavaFX fat jar

ANS: To make a fat jar cross-platform, you must explicitly include the platform-specific native library dependencies for all target operating systems (Windows, Linux, macOS) in your build configuration.

Q: What are the downsides of creating cross-platform fat jars

ANS: The primary downside is the significant increase in file size. Bundling native libraries for multiple operating systems can result in very large JAR files, especially if using components like WebView.

Q: How do I support Apple M series Macs with JavaFX fat jars

ANS: For JavaFX 19+, include the mac-aarch64 classifier for your JavaFX graphics dependencies. Ensure your JavaFX versions are consistent and you are using a JDK that supports M series Macs (e.g., JDK 17+).

Q: What are better alternatives to JavaFX fat jars for distribution

ANS: Modern alternatives like jlink (to create custom runtime images), jpackage (to create native installers), and GraalVM native-image (for ahead-of-time compilation to native executables) are recommended. These methods are more efficient and align better with JavaFX’s modular design.
