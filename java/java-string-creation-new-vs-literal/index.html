“Java String Creation new vs Literal: Performance and Memory Explained”

Why Does new String("text") Differ from String s = "text"?

The core distinction lies in how Java handles string creation and memory allocation for these two approaches.

  • String s = "text";: This method utilizes the String Constant Pool. When you declare a string literal, Java first checks if a string with that exact value already exists in the pool. If it does, the existing reference is reused. If not, a new string object is created in the pool, and a reference to it is returned. This means multiple string literals with the same value will point to the same object in memory.

  • String s = new String("text");: This method explicitly creates a new and referentially distinct instance of a String object. Even if a string with the same value already exists in the String Constant Pool, new String("text") will always create a fresh object in the heap memory.

Referential Distinction Explained

Consider this example:

String s1 = "foobar";
String s2 = "foobar";

System.out.println(s1 == s2); // Output: true

s2 = new String("foobar");
System.out.println(s1 == s2); // Output: false
System.out.println(s1.equals(s2)); // Output: true

In the first comparison (s1 == s2), true is printed because both s1 and s2 reference the same string object (“foobar”) from the String Constant Pool. However, when s2 is reassigned using new String("foobar"), a new object is created in the heap. Therefore, s1 and s2 now point to different objects, even though their content is identical, leading to s1 == s2 evaluating to false. The s1.equals(s2) comparison, which checks for content equality, correctly returns true.

While it’s possible to force the creation of two equal but not identical strings using new String(), this is rarely the intended behavior and can lead to unexpected outcomes.

Understanding the String Constant Pool

The String Constant Pool is a dedicated area within the Java heap where string literals are stored. This mechanism optimizes memory usage and performance.

Let’s visualize the object creation process:

// Scenario 1: String literals
String str1 = "java5"; // "java5" is created in the pool, str1 points to it.
String str2 = "java5"; // str2 points to the existing "java5" in the pool.

// Scenario 2: Using 'new'
String str3 = new String("java5"); // A new "java5" object is created in the heap, str3 points to it.
                                   // The literal "java5" is also in the pool.
String str4 = "java5"; // str4 points to the existing "java5" in the pool.

In this scenario, there is one object in the String Constant Pool and two objects in the heap.

Object creation breakdown:

  1. String str1 = new String("java5");
    • Pool: "java5" (1 Object)
    • Heap: str1 points to "java5" (1 Object)
  2. String str2 = "java5";
    • Pool: str2 points to "java5" (1 Object)
    • Heap: str1 points to "java5" (1 Object)
  3. String str3 = new String(str2);
    • Pool: str2 points to "java5" (1 Object)
    • Heap: str1 points to "java5", str3 points to a new "java5" (2 Objects)
  4. String str4 = "java5";
    • Pool: str2 and str4 point to "java5" (1 Object)
    • Heap: str1 points to "java5", str3 points to "java5" (2 Objects)

Total objects: Pool - 1, Heap - 2.

The Role of String.intern()

The String.intern() method plays a crucial role in string management. When called on a string object, it checks if the string’s value is already present in the String Constant Pool. If it is, intern() returns a reference to the existing string in the pool. If not, it adds the string to the pool and returns a reference to it.

Consider the following code:

import java.util.*;

class GFG {
    public static void main(String[] args) {
        String siteName1 = "java.com";
        String siteName2 = "java.com";
        String siteName3 = new String("java.com");
        String siteName4 = new String("java.com").intern();

        System.out.println("siteName1::: " + Integer.toHexString(System.identityHashCode(siteName1)));
        System.out.println("siteName2::: " + Integer.toHexString(System.identityHashCode(siteName2)));
        // SiteName3 is a new object in the heap, distinct from the pool
        System.out.println("siteName3 creation Of New Object Without Interned::: " + Integer.toHexString(System.identityHashCode(siteName3)));
        // SiteName4 is interned, so it points to the pool's object
        System.out.println("siteName4 creation Of New Object With Interned::: " + Integer.toHexString(System.identityHashCode(siteName4)));

        System.out.println(siteName1 == siteName2); // true (both point to the same pool object)
        System.out.println(siteName1 == siteName3); // false (siteName1 is from pool, siteName3 is new in heap)

        String siteName5 = siteName3.intern(); // siteName5 now points to the pool's object
        System.out.println("siteName5 Interned from siteName3::: " + Integer.toHexString(System.identityHashCode(siteName5)));

        System.out.println(siteName1 == siteName3); // false (siteName3 itself remains a heap object)
        System.out.println(siteName1 == siteName5); // true (both point to the same pool object)
        System.out.println(siteName1 == siteName4); // true
        System.out.println(siteName5 == siteName4); // true
    }
}

This demonstrates that intern() ensures that strings with the same content refer to the same object, promoting memory efficiency.

Why Prefer String Literals?

Using string literals (String s = "text";) over the new String("text") constructor is generally recommended due to several advantages:

  1. Memory Efficiency: String literals leverage the String Constant Pool, preventing the creation of redundant string objects in the heap. This can lead to significant memory savings, especially in applications with extensive string manipulation. Tools like SpotBugs often flag the use of new String(String) as a performance anti-pattern (DM_STRING_CTOR).

  2. Performance: Reusing string objects from the pool is faster than creating new ones. When multiple parts of your code need the same string, accessing the pre-existing object from the pool is more efficient than allocating new memory and initializing a new object.

  3. Predictable Behavior: The String Constant Pool ensures that identical string literals always refer to the same object, making comparisons with the == operator reliable for literals.

Performance Impact of new String()

Using new String("text") bypasses the String Constant Pool for the initial creation. While the literal "text" might still be added to the pool, the new operator forces the creation of a separate object in the heap. This leads to:

  • Increased Memory Consumption: Each new String(...) call creates a new object, potentially leading to a larger heap footprint.
  • Reduced Performance: Creating new objects and managing them can be more resource-intensive than referencing existing ones.

When a string is created by concatenation or modification (e.g., String str2 = "abc" + "def";), new objects are created. If these resulting strings are not already in the pool, they will be added upon their first appearance.

Java Language Specification (JLS) and JVM Insights

The behavior of string literals is explicitly defined by the Java Language Specification (JLS) and the Java Virtual Machine Specification (JVMS).

  • JLS §3.10.5 String Literals: States that string literals are “interned” to share unique instances using String.intern(). This ensures that identical string literals always refer to the same instance.

  • JVMS §5.1 String Literals: Explains that string literals are derived from CONSTANT_String_info structures in class files. The JVM ensures that identical string literals refer to the same String instance. If String.intern() has been called on an equivalent string, the same instance is returned.

Bytecode analysis further illustrates this. When you use string literals, the ldc (load constant) instruction efficiently retrieves the string from the constant pool. Using new String(...) involves creating a new object and then calling its constructor, which is a more involved process.

String Comparisons: == vs. equals()

It’s crucial to remember the difference between == and equals() for String objects:

  • ==: Compares object references. It checks if two variables point to the exact same object in memory.
  • .equals(): Compares the actual content (sequence of characters) of the strings.

As seen in the s1 == s2 examples, == will return true for string literals pointing to the same pool object, but false for a literal compared to a new String() object, even if their values are identical. For content comparison, always use .equals().

Comparing Different String Creation Scenarios

Let’s look at a few common patterns:

  1. Literal vs. Literal:

    String s1 = "abc";
String s2 = "abc";
System.out.println(s1 == s2); // true

    Both s1 and s2 point to the same “abc” in the String Constant Pool.

  2. Literal vs. New:

    String s1 = "abc";
String s2 = new String("abc");
System.out.println(s1 == s2); // false

    s1 points to the pooled “abc”, while s2 points to a new “abc” object in the heap.

  3. New vs. New:

    String s1 = new String("abc");
String s2 = new String("abc");
System.out.println(s1 == s2); // false

    Both s1 and s2 point to distinct “abc” objects in the heap.

  4. Literal with Concatenation vs. Literal:

    String s1 = "abc";
String s2 = "abc" + "def"; // "abcdef" is created in the pool
System.out.println(s1 == s2); // false (assuming "abc" and "abcdef" are distinct)

    String concatenation that results in a compile-time constant expression will be interned. Dynamically generated strings through concatenation might not be automatically interned unless intern() is called.

  5. Literal Assignment and Reassignment:

    String str1 = "abc"; // "abc" in pool
str1 = "xyz";      // "xyz" in pool, str1 points to it

    When str1 is reassigned, it points to a different string literal in the pool. The previous “abc” might become eligible for garbage collection if no other references exist.

Performance and Memory: The Bottom Line

The primary takeaway is that creating strings using literals (String s = "text";) is the preferred method in Java for optimal performance and memory efficiency. It leverages the String Constant Pool, ensuring that identical strings are represented by a single object. Using new String("text") should be avoided unless there’s a specific, rare requirement to create a distinct, non-pooled string object.

FAQs on Java String Creation

Q: What is the String Constant Pool in Java

ANS: The String Constant Pool is a special memory area in the Java heap where string literals are stored. When you declare a string literal, Java checks if a string with that value already exists in the pool. If it does, the existing reference is reused; otherwise, a new string object is created in the pool, and a reference to it is returned. This optimizes memory usage by preventing duplicate string objects. For more details on Java string behavior, refer to Java String Memory Management .

Q: Why is String.intern used

ANS: The String.intern() method is used to ensure that a string object is represented by a single instance in the String Constant Pool. When called, it checks if a string with the same value already exists in the pool. If so, it returns a reference to that pooled string. If not, it adds the string to the pool and returns a reference to it. This is beneficial for reducing memory usage and improving the performance of string comparisons. Q: Should I use new String('literal') or String literal

ANS: It is generally recommended to use string literals (String s = "literal") instead of new String("literal"). String literals are stored in the String Constant Pool, promoting memory efficiency and performance by reusing existing string objects. The new String("literal") constructor always creates a new object in the heap, bypassing the pool and consuming more memory. Explore how to fix Python errors .

Q: What is the difference between s1 == s2 and s1.equals(s2) for strings

ANS: For strings, s1 == s2 checks if s1 and s2 refer to the exact same object in memory (reference equality). s1.equals(s2) checks if the content (sequence of characters) of the two strings is identical (value equality). String literals that have the same value will return true for == because they point to the same object in the String Constant Pool. However, new String("literal") creates a new object, so == will return false even if the content is the same. For reliable string content comparison, always use .equals(). Q: Does concatenation create new string objects

ANS: Yes, string concatenation can create new string objects. If the concatenation can be resolved at compile time (e.g., "hello" + "world"), the resulting string literal is typically interned. However, if the concatenation involves variables or operations that cannot be determined at compile time (e.g., String s = var1 + var2;), new String objects are created on the heap.
