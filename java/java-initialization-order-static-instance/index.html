“Java Class Initialization Order: Static vs Instance Execution Flow”

When dealing with Java classes, especially those involving inheritance, static members, and instance initializers (the blocks { ... }), tracing the exact order of execution during object creation can be complex. What dictates this strict flow, and how do static initializations interact with instance creation?

What is the precise order of execution when creating a Java object?

According to the Java Language Specification, specifically sections $\S$12.4.2 and $\S$12.5, the initialization process follows a fixed textual order:

  1. Static Initialization: Static variable initializers and static initialization blocks are executed, in the order they appear in the source code, only if the class has not been previously initialized.
  2. Superclass Constructor Call: The super() call within the constructor runs. This can be explicit in the code or implicit (invoking the no-argument constructor of the direct superclass).
  3. Instance Initialization: Instance variable initializers and instance initialization blocks are executed, in textual order.
  4. Constructor Body: The remaining statements within the constructor body, following the super() call, are executed.

How does inheritance affect the initialization sequence demonstrated by class structures?

Consider a simple inheritance scenario involving classes X, Y, and a subclass Z. The decompiled structure reveals how instance variables are effectively moved into the constructor flow.

For the following structure:

class X {
    Y b;

    X() {
        b = new Y();
        System.out.print("X");
    }
}

class Y {
    Y() {
        System.out.print("Y");
    }
}

public class Z extends X {

    Y y;

    Z() {
        y = new Y();
        System.out.print("Z");
    }

    public static void main(String args[]) {
        new Z();
    }
}

The execution sequence when new Z() is called proceeds as follows:

  1. The constructor for Z is invoked.
  2. This triggers the default constructor of the parent class X (since no explicit super() call is present).
  3. Inside X’s constructor, the first statement b = new Y() executes, resulting in:
    • Print Y
  4. The rest of X’s constructor runs:
    • Print X
  5. Execution returns to Z’s constructor. The first line, y = new Y(), runs:
    • Print Y
  6. The remainder of Z’s constructor executes:
    • Print Z

The resulting output is YX YZ. This demonstrates that the superclass constructor must finish execution before the subclass constructor body begins, and instance initializations (like b = new Y()) are woven into the constructor path.

What happens when instance field initialization throws an exception?

When instance variable initializers run before the constructor body, they participate in exception handling flow during construction.

Observe this program where the instance initializer throws an exception immediately:

public class Tester {
    private Tester internalInstance = new Tester(); // Field initialization point
    public Tester() throws Exception {
        throw new Exception("Boom");
    }
    public static void main(String[] args) {
        try {
            Tester b = new Tester();
            System.out.println("Eye-Opener!");
        } catch (Exception ex) {
            System.out.println("Exception catched");
        }
    }
}

If you anticipate the catch block handling the thrown “Boom” exception, you might be surprised. Running this code results in a StackOverflowError, not catching the Exception.

Why? Because the very first line of code executed in the Tester() constructor is the initialization of internalInstance, which recursively calls new Tester(). This self-referential initialization creates an infinite recursion of constructor calls before the throw new Exception("Boom") line is ever reached, leading to a stack overflow.

How do static and instance blocks interleave during the first object creation versus subsequent creations?

The interaction between static blocks, static field initializers, instance blocks, and instance field initializers is heavily dependent on whether the class is being loaded for the first time.

Examine this complex example involving static initialization, instance initialization, and a static final field that forces an object creation during class loading:

public class Foo {

    {
        System.out.println("Instance Block 1");
    }

    static {
        System.out.println("Static Block 1");
    }

    public static final Foo FOO = new Foo();

    {
        System.out.println("Instance Block 2");
    }

    static {
        System.out.println("Static Block 2 (Weird!!)");
    }

    public Foo() {
        System.out.println("Constructor");
    }

    public static void main(String[] args) {
        System.out.println("In Main");
        new Foo();
    }
}

When the JVM loads Foo, it executes all static initializations sequentially, interleaving them with any instance initializations caused by those static initializations.

Output during Class Loading (First Time Foo is referenced via public static final Foo FOO = new Foo();):

Static Block 1
Instance Block 1
Instance Block 2
Constructor
Static Block 2 (Weird!!)

Note the unusual placement of Static Block 2—it executes after the instance initializations caused by FOO = new Foo() have completed.

Output during subsequent object creation (new Foo() in main):

In Main
Instance Block 1
Instance Block 2
Constructor

For subsequent creations, static sections are skipped entirely, and only instance initializers and the constructor run in textual order.

The key observation is that the initialization of the static final field FOO forces the first full object initialization sequence to occur during class loading, interjecting instance logic between static initializers. See related discussions on Java class loading at Java Class Loading Mechanics .

How does deep inheritance affect the interleaving of static, instance, and anonymous inner class initializations?

When extending classes and using anonymous inner classes, the initialization order strictly follows the hierarchy: parent static members first, then child static members, then parent instance members, and finally child instance members/constructor logic.

In the detailed example involving CodeBlockSeq, Hello (parent), and Bello (child subclass instantiated anonymously):

The sequence follows this general pattern:

  1. Static initializations of the parent class (Hello), in declaration order.
  2. Static initializations of the extension class (Bello), in declaration order.
  3. Instance initializers/fields of the parent class (Hello), in declaration order.
  4. Parent constructor (super()).
  5. Instance initializers/fields of the extension class (Bello), in declaration order.
  6. Extension class constructor (Bello(...)).
  7. Instance initializers/fields of the anonymous extension class, in declaration order.

The demonstration highlights that even when replacing a static field initialization (s0) with an actual constructor call (new Hello("jello")), the JVM doesn’t intelligently skip subsequent static initialization stages for the parent class; it treats the execution of the s0 initializer (whether it’s a field declaration or a constructor call) as a single step in the static sequence for Bello. FAQs on Java Initialization Order

Q: What runs first static initialization or instance initialization

ANS: Static variable initializers and static initialization blocks run first, as they must complete before any instance of the class can be created.

Q: Where does the super constructor call fit in the execution flow

ANS: The call to the superclass constructor (explicit or implicit super()) executes before any instance variable initializers or instance initialization blocks of the current class.

Q: Can a constructor's instance initializer cause a stack overflow

ANS: Yes, if an instance variable initializer recursively calls the constructor being initialized (e.g., private FieldType f = new FieldType(); inside FieldType()), it results in infinite recursion and a StackOverflowError before the constructor body executes.

Q: Does the order of static blocks matter if they are separated by instance initializers

ANS: Yes, static blocks and static initializers run strictly in textual order upon class loading. If an instance initializer runs due to a static field initialization, it interrupts the sequential execution of static blocks, but the remaining static blocks will execute later in their declared order once instance execution completes for that step.
