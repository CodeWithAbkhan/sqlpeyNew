“Solved: How to Address Android Runtime Permission Issues”

When developing Android applications, especially those targeting Android 6.0 (Marshmallow) and above (targetSdkVersion 23+), you’ll encounter a crucial shift in how permissions are handled. Unlike older Android versions where permissions were granted solely during app installation, modern Android versions require developers to request “dangerous” permissions from the user at runtime. This is a fundamental security enhancement designed to give users more control over their device data.

This guide delves into the reasons behind these changes and provides practical, code-driven solutions to manage runtime permissions effectively, ensuring your app functions correctly and securely.

The Core of the Matter: Runtime Permissions

The primary driver for these runtime permission requirements is the introduction of the runtime permission model starting with Android 6.0. For permissions classified as “dangerous,” your app must explicitly ask the user for consent before accessing sensitive data or device features. This applies even if you’ve declared these permissions in your app’s AndroidManifest.xml file.

What Constitutes a “Dangerous” Permission?

Dangerous permissions are those that could potentially impact the user’s privacy or the device’s operation. Here’s a comprehensive list of common dangerous permissions you’ll need to handle at runtime:

  • Calendar:
    • READ_CALENDAR
    • WRITE_CALENDAR
  • Camera:
    • CAMERA
  • Contacts:
    • READ_CONTACTS
    • WRITE_CONTACTS
    • GET_ACCOUNTS
  • Location:
    • ACCESS_FINE_LOCATION
    • ACCESS_COARSE_LOCATION
  • Microphone:
    • RECORD_AUDIO
  • Phone:
    • READ_PHONE_STATE
    • READ_PHONE_NUMBERS
    • CALL_PHONE
    • ANSWER_PHONE_CALLS (Must request at runtime)
    • READ_CALL_LOG
    • WRITE_CALL_LOG
    • ADD_VOICEMAIL
    • USE_SIP
    • PROCESS_OUTGOING_CALLS
  • Sensors:
    • BODY_SENSORS
  • SMS:
    • SEND_SMS
    • RECEIVE_SMS
    • READ_SMS
    • RECEIVE_WAP_PUSH
    • RECEIVE_MMS
  • Storage:
    • READ_EXTERNAL_STORAGE
    • WRITE_EXTERNAL_STORAGE
  • Activity Recognition:
    • ACTIVITY_RECOGNITION
  • Handover:
    • ACCEPT_HANDOVER
  • Background Location:
    • ACCESS_BACKGROUND_LOCATION
  • Media Location:
    • ACCESS_MEDIA_LOCATION

If your targetSdkVersion is 23 or higher, and your app attempts to access any of these without runtime permission, it will likely result in crashes or unexpected behavior, often manifesting as “permission denied” errors.

Practical Solutions for Runtime Permissions

Here are several effective ways to implement runtime permission requests in your Android application:

Solution 1: The Fundamental Check and Request

This is the standard approach. Before performing an action that requires a dangerous permission, you first check if the permission has been granted. If not, you then request it from the user.

// Define a request code to identify the permission request
private static final int PERMISSION_REQUEST_CODE = 1;

// Check for SEND_SMS permission
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.M) {
    if (checkSelfPermission(Manifest.permission.SEND_SMS)
            == PackageManager.PERMISSION_DENIED) {
        Log.d("permission", "Permission denied for SEND_SMS - requesting it");
        // Request the permission
        String[] permissions = {Manifest.permission.SEND_SMS};
        requestPermissions(permissions, PERMISSION_REQUEST_CODE);
    }
}

This code snippet checks if the current Android version is Marshmallow or higher. If it is, it then checks if the SEND_SMS permission is denied. If it is, it initiates a request for that specific permission.

Solution 2: Using ContextCompat and ActivityCompat

For better compatibility and cleaner code, especially when targeting older SDK versions while still handling runtime permissions, AndroidX libraries provide helpful utilities.

// Example for requesting WRITE_EXTERNAL_STORAGE
int MY_PERMISSIONS_REQUEST_WRITE_EXTERNAL_STORAGE = 0; // Define your request code

// Check if the permission is not already granted
if (ContextCompat.checkSelfPermission(this,
        Manifest.permission.WRITE_EXTERNAL_STORAGE)
        != PackageManager.PERMISSION_GRANTED) {

    // If permission is not granted, check if we need to show an explanation
    if (ActivityCompat.shouldShowRequestPermissionRationale(this,
            Manifest.permission.WRITE_EXTERNAL_STORAGE)) {
        // Show an explanation to the user asynchronously.
        // This is where you might show a Snackbar or dialog explaining why the permission is needed.
    } else {
        // No explanation needed, directly request the permission.
        ActivityCompat.requestPermissions(this,
                new String[]{Manifest.permission.WRITE_EXTERNAL_STORAGE},
                MY_PERMISSIONS_REQUEST_WRITE_EXTERNAL_STORAGE);
    }
} else {
    // Permission has already been granted, proceed with the operation.
    Log.d("PermissionStatus", "WRITE_EXTERNAL_STORAGE permission already granted.");
}

In this approach, shouldShowRequestPermissionRationale is useful for providing context to the user if they’ve previously denied the permission. ActivityCompat.requestPermissions then displays the system’s permission dialog.

Solution 3: A Reusable Permission Check Method

Encapsulating permission checks into a reusable method can simplify your activity or fragment code.

// In your Activity or Fragment
public boolean checkWriteExternalStoragePermission() {
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.M) {
        if (checkSelfPermission(android.Manifest.permission.WRITE_EXTERNAL_STORAGE)
                == PackageManager.PERMISSION_GRANTED) {
            Log.d("PermissionCheck", "WRITE_EXTERNAL_STORAGE permission granted.");
            return true;
        } else {
            Log.d("PermissionCheck", "WRITE_EXTERNAL_STORAGE permission requested.");
            ActivityCompat.requestPermissions(this, new String[]{Manifest.permission.WRITE_EXTERNAL_STORAGE}, 1); // Use an appropriate request code
            return false;
        }
    } else {
        // For API levels below 23, permissions are granted at install time.
        Log.d("PermissionCheck", "Running on API < 23, permission assumed granted.");
        return true;
    }
}

This method checks the permission and requests it if necessary, returning a boolean indicating whether the permission is currently granted.

Solution 4: Managing Multiple Permissions (Kotlin Example)

When you need to request multiple permissions, you can bundle them in an array. This example demonstrates how to request SMS-related permissions in Kotlin.

import android.Manifest
import android.content.pm.PackageManager
import androidx.core.app.ActivityCompat
import androidx.core.content.ContextCompat

class MainActivity : AppCompatActivity() {

    private val smsPermissionRequestCode = 1 // Unique request code for SMS permissions

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)

        requestSmsPermissions()

        // Your other onCreate logic here...
    }

    private fun requestSmsPermissions() {
        val smsPermissions = arrayOf(Manifest.permission.RECEIVE_SMS, Manifest.permission.READ_SMS)

        // Check if all required SMS permissions are granted
        val allGranted = smsPermissions.all {
            ContextCompat.checkSelfPermission(this, it) == PackageManager.PERMISSION_GRANTED
        }

        if (!allGranted) {
            // If not all permissions are granted, request them
            ActivityCompat.requestPermissions(this, smsPermissions, smsPermissionRequestCode)
        } else {
            Log.d("SmsPermission", "All SMS permissions are already granted.")
            // Proceed with SMS related operations
        }
    }

    override fun onRequestPermissionsResult(requestCode: Int, permissions: Array<out String>, grantResults: IntArray) {
        super.onRequestPermissionsResult(requestCode, permissions, grantResults)
        if (requestCode == smsPermissionRequestCode) {
            // Check if the permissions were granted
            val granted = grantResults.isNotEmpty() && grantResults.all { it == PackageManager.PERMISSION_GRANTED }
            if (granted) {
                Log.d("SmsPermissionResult", "SMS permissions granted.")
                // Proceed with SMS related operations
            } else {
                Log.d("SmsPermissionResult", "SMS permissions denied.")
                // Handle the case where permissions are denied
            }
        }
    }
}

This Kotlin example defines a request code, lists the desired permissions, checks if they are granted, and if not, requests them. The onRequestPermissionsResult callback handles the user’s response.

Solution 5: Temporary Workaround (Not Recommended for Production)

As a very temporary measure, or for testing purposes, you could reduce your targetSdkVersion to a value below 23. This bypasses the runtime permission requirements.

Warning: This is not a sustainable solution for production apps. It forfeits security enhancements and prevents you from using the latest Android platform features. You will eventually need to implement the runtime permission system.

// In your app's build.gradle (module level) file
android {
    // ...
    defaultConfig {
        // ...
        targetSdkVersion 22 // Or any value less than 23
        // ...
    }
    // ...
}

Solution 6: Understanding the adb shell dumpsys package Command

For debugging, you can inspect the granted permissions for a specific package using the adb command-line tool.

adb shell dumpsys package <package-name>

Replace <package-name> with your application’s package name (e.g., com.example.myapp). This command outputs detailed information about your app’s state, including its granted permissions.

Solution 7: Order of Permission Requests

In some edge cases, particularly with SMS permissions, the order in which you request them might matter. If you’re facing unexpected behavior, try reordering your permission requests. This might indicate an underlying framework behavior that needs careful handling.

Solution 8: SMS Message Limits

On some custom ROMs or specific Android versions, there might be an SMS message limit setting that can interfere with sending messages, even if the SEND_SMS permission is correctly handled. Check your device’s security settings for any such limitations and adjust them accordingly.

Important Considerations

  • Manifest Declaration: Always declare the permissions your app needs in the AndroidManifest.xml file, even for runtime permissions.
  • Callback Handling: You must implement the onRequestPermissionsResult method in your Activity to handle the user’s response to permission requests.
  • User Experience: Provide clear explanations to users about why your app needs certain permissions. Use shouldShowRequestPermissionRationale to guide them when necessary.
  • targetSdkVersion: Ensure your targetSdkVersion reflects the latest stable Android version you are developing for, and implement runtime permissions accordingly.

By diligently implementing these runtime permission strategies, you can build more secure and user-friendly Android applications that comply with modern Android security practices.

For more detailed information and further examples, consult the official Android developer documentation on Requesting Permissions .

FAQs on Android Runtime Permission Issues

Q: Why do I need to request permissions at runtime for Android 6.0 and above

ANS: For security and user privacy, Android 6.0 (API level 23) introduced the runtime permission model. Dangerous permissions, which can access sensitive user data or device features, must now be explicitly requested from the user at the time of use, rather than only during installation.

Q: What are considered 'dangerous' permissions in Android

ANS: Dangerous permissions are those that can affect the user’s privacy or device operation. Examples include accessing the camera, location, contacts, SMS messages, microphone, and storage. These require runtime user consent.

Q: How do I check if a permission is granted in Android

ANS: You can use ContextCompat.checkSelfPermission(context, permissionName) or Activity.checkSelfPermission(permissionName) to check if a specific permission is granted. The method returns PackageManager.PERMISSION_GRANTED if it is.

Q: How do I request a permission from the user in Android

ANS: Use ActivityCompat.requestPermissions(activity, new String[]{permissionName}, requestCode) to request a permission. You must also implement the onRequestPermissionsResult callback in your Activity to handle the user’s response.

Q: What happens if I don't request runtime permissions for targetSdkVersion 23+

ANS: If your app targets Android 6.0 (API level 23) or higher and attempts to access a dangerous permission without requesting it at runtime, the operation will likely fail, often resulting in a SecurityException or a “permission denied” error.

Q: Can I temporarily avoid runtime permissions by lowering targetSdkVersion

ANS: Yes, you can lower your targetSdkVersion below 23 to bypass runtime permission requirements. However, this is strongly discouraged for production apps as it sacrifices modern security features and limits access to new platform capabilities. It’s a temporary workaround, not a solution.

Q: How do I handle the user denying a permission

ANS: You should use ActivityCompat.shouldShowRequestPermissionRationale(activity, permissionName) in your onRequestPermissionsResult callback or before requesting a permission. This method returns true if the user has previously denied the permission and the app has a chance to explain why it’s needed. If they permanently deny it, subsequent requests might not show a dialog.

Q: Where do I declare permissions in an Android project

ANS: All permissions, including dangerous ones, must be declared in your app’s AndroidManifest.xml file within the <manifest> tag. For example: <uses-permission android:name="android.permission.CAMERA" />.
