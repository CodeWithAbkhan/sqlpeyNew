“Android Runtime: Efficiently Requesting Multiple Permissions at Once”

Handling runtime permissions in Android, especially when multiple sensitive permissions are required for core application features, demands a clear and robust strategy. Developers often face challenges in bundling these requests, correctly interpreting the results, and managing user interactions when permissions are denied. How can we streamline the process of checking and requesting several Android permissions simultaneously and handle the resulting callback gracefully?

Core Approaches for Batch Permission Requests

Several effective patterns exist for soliciting multiple runtime permissions from the user in a single prompt sequence, utilizing the ActivityCompat class introduced in Marshmallow (API 23) and newer APIs.

Method 1: Bulk Request with Helper Check (Java & Kotlin)

The most straightforward approach involves defining an array of all required permissions and passing them together to ActivityCompat.requestPermissions(). The Android system bundles these requests intelligently.

A preliminary check function helps determine which permissions are actually missing before triggering the request dialog.

Java Implementation Example:

We can define a utility method to check the status of multiple permissions:

public static boolean hasPermissions(Context context, String... permissions) {
    if (context != null && permissions != null) {
        for (String permission : permissions) {
            if (ActivityCompat.checkSelfPermission(context, permission) != PackageManager.PERMISSION_GRANTED) {
                return false;
            }
        }
    }
    return true;
}

Then, initiate the request if any permissions are missing:

// Define the set of permissions needed
final int PERMISSION_ALL = 1; 
final String[] PERMISSIONS = {
  android.Manifest.permission.READ_CONTACTS, 
  android.Manifest.permission.WRITE_CONTACTS, 
  android.Manifest.permission.WRITE_EXTERNAL_STORAGE, 
  android.Manifest.permission.READ_SMS, 
  android.Manifest.permission.CAMERA
};

if (!hasPermissions(this, PERMISSIONS)) {
    ActivityCompat.requestPermissions(this, PERMISSIONS, PERMISSION_ALL);
}

Kotlin Equivalent:

In Kotlin, this check becomes concise using the all scope function:

fun hasPermissions(context: Context, vararg permissions: String): Boolean = permissions.all {
    ActivityCompat.checkSelfPermission(context, it) == PackageManager.PERMISSION_GRANTED
}

Method 2: Dynamic List Building and Request (Java)

This method focuses on dynamically collecting only the permissions that are currently not granted into a list before making the request. This approach is often used inside an Activity or Fragment lifecycle method like onCreate. This pattern leverages the Support Library features like ContextCompat to maintain backward compatibility.

public static final int REQUEST_ID_MULTIPLE_PERMISSIONS = 1;

@Override
protected void onCreate(Bundle savedInstanceState) {
    super.onCreate(savedInstanceState);
    setContentView(R.layout.activity_main);
    if(checkAndRequestPermissions()) {
        // Permissions granted, proceed normally
    }
}

private boolean checkAndRequestPermissions() {
    int smsPermission = ContextCompat.checkSelfPermission(this, Manifest.permission.SEND_SMS);
    int locationPermission = ContextCompat.checkSelfPermission(this, Manifest.permission.ACCESS_FINE_LOCATION);
    
    List<String> listPermissionsNeeded = new ArrayList<>();
    
    if (locationPermission != PackageManager.PERMISSION_GRANTED) {
        listPermissionsNeeded.add(Manifest.permission.ACCESS_FINE_LOCATION);
    }
    if (smsPermission != PackageManager.PERMISSION_GRANTED) {
        listPermissionsNeeded.add(Manifest.permission.SEND_SMS);
    }
    
    if (!listPermissionsNeeded.isEmpty()) {
        ActivityCompat.requestPermissions(this, listPermissionsNeeded.toArray(new String[listPermissionsNeeded.size()]), REQUEST_ID_MULTIPLE_PERMISSIONS);
        return false;
    }
    return true;
}

Handling onRequestPermissionsResult and Rationale

When multiple permissions are requested, the onRequestPermissionsResult callback receives arrays containing results corresponding to the requested permissions in the order they were presented to the user.

Interpreting Denials:

A critical aspect is recognizing when a user explicitly selects “Never ask again.” This state is identified by checking ActivityCompat.shouldShowRequestPermissionRationale(activity, permission) after the permission is denied.

  • If shouldShowRequestPermissionRationale returns true: The user denied the request, but we can show an explanation dialog (like a Snackbar or AlertDialog) and prompt them again.
  • If shouldShowRequestPermissionRationale returns false: The user denied the request and checked “Don’t ask again.” In this scenario, the application must redirect the user to the device settings page to enable the necessary permissions manually.

The following structure details how to evaluate results for multiple permissions using a HashMap for clarity:

@Override
public void onRequestPermissionsResult(int requestCode, String permissions[], int[] grantResults) {
    if (requestCode == REQUEST_ID_MULTIPLE_PERMISSIONS) {
        Map<String, Integer> perms = new HashMap<>();
        perms.put(Manifest.permission.SEND_SMS, PackageManager.PERMISSION_GRANTED);
        perms.put(Manifest.permission.ACCESS_FINE_LOCATION, PackageManager.PERMISSION_GRANTED);

        if (grantResults.length > 0) {
            for (int i = 0; i < permissions.length; i++)
                perms.put(permissions[i], grantResults[i]);

            if (perms.get(Manifest.permission.SEND_SMS) == PackageManager.PERMISSION_GRANTED
                    && perms.get(Manifest.permission.ACCESS_FINE_LOCATION) == PackageManager.PERMISSION_GRANTED) {
                Log.d(TAG, "sms & location services permission granted");
                // Process normal flow
            } else {
                // Handle denial, check rationale state
                if (ActivityCompat.shouldShowRequestPermissionRationale(this, Manifest.permission.SEND_SMS) || 
                    ActivityCompat.shouldShowRequestPermissionRationale(this, Manifest.permission.ACCESS_FINE_LOCATION)) {
                    
                    // Case 1: Denied, but can ask again (show explanation)
                    showDialogOK("Required permissions missing", (dialog, which) -> {
                        if (which == DialogInterface.BUTTON_POSITIVE) checkAndRequestPermissions();
                    });
                } else {
                    // Case 2: Denied with "Never ask again" checked
                    Toast.makeText(this, "Permissions permanently denied. Please enable in Settings.", Toast.LENGTH_LONG).show();
                    // Guide user to settings or proceed with limited functionality
                }
            }
        }
    }
}

Method 3: Creating a Reusable Permissions Helper Class

For cleaner separation of concerns, encapsulating permission logic into a dedicated handler class can be beneficial, especially in larger projects. This helper class manages the logic for checking ungranted permissions and processing the results via a listener interface.

Java Permissions Helper Snippet:

public class PermissionsHelper {
    // ... (Helper methods: needRequestRuntimePermissions, findUnGrantedPermissions, etc.)
    
    public void requestPermission(Activity activity, @NonNull String[] permissions, int requestCode, RequestPermissionListener listener) {
        // Logic to check if permissions are needed and request them
        String[] unGrantedPermissions = findUnGrantedPermissions(permissions);
        if (unGrantedPermissions.length == 0) {
            listener.onSuccess();
            return;
        }
        ActivityCompat.requestPermissions(activity, unGrantedPermissions, requestCode);
    }

    public void onRequestPermissionsResult(int requestCode, @NonNull String[] permissions, @NonNull int[] grantResults) {
        // Logic to evaluate results and notify listener
        // ...
    }

    public interface RequestPermissionListener {
        void onSuccess();
        void onFailed();
    }
}

Method 4: Modern Approach with registerForActivityResult (Kotlin)

For applications targeting modern Android versions (using Activity Result APIs), using registerForActivityResult with ActivityResultContracts.RequestMultiplePermissions provides a clean, lifecycle-aware way to handle permission responses without relying on overriding onRequestPermissionsResult.

private val multiplePermissionContract = registerForActivityResult(ActivityResultContracts.RequestMultiplePermissions()) { permissionsStatusMap ->
    // permissionsStatusMap is Map<String, Boolean>
    if (permissionsStatusMap.all { it.value }) {
        // All permissions accepted, execute the feature logic
        Log.d(TAG, "All permissions granted via Activity Result API")
    } else {
        Toast.makeText(this, "Some permissions were denied", Toast.LENGTH_SHORT).show()
        // Handle partial denial
    }
}

// Launching the request:
xyzButton.setOnClickListener {
    multiplePermissionContract.launch(
        arrayOf(
            android.Manifest.permission.READ_CONTACTS, 
            android.Manifest.permission.CAMERA
        )
    )
}

This eliminates the need to manually associate request codes with permission arrays in the callback.

Method 5: Sequential Permission Requests (Alternative to Bulk)

Although generally less efficient as it results in multiple permission dialogs appearing sequentially, one can request permissions one by one if granular control or unique rationale messages per permission are necessary (as detailed in Solution 12).

If you request permissions separately, you must manage the flow carefully, often using the onResume() callback or chaining the requests based on the result of the previous one.

// Example of checking and requesting one by one (less preferred for bulk needs)
private void checkAndRequestSingle(String permission, int requestCode) {
    if (ContextCompat.checkSelfPermission(this, permission) != PackageManager.PERMISSION_GRANTED) {
        if (ActivityCompat.shouldShowRequestPermissionRationale(this, permission)) {
            // Show specific rationale dialog for this permission
            // ... after user OK, call ActivityCompat.requestPermissions(this, new String[]{permission}, requestCode);
        } else {
            ActivityCompat.requestPermissions(this, new String[]{permission}, requestCode);
        }
    }
}

FAQs on Android Efficiently Requesting Multiple Permissions at Once

Q: Does Android automatically handle multiple permission requests in one go

ANS: Yes, when you pass an array of permissions to ActivityCompat.requestPermissions(), Android groups them and presents a single prompt to the user for all listed permissions (if they haven’t been granted previously).

Q: How to check if a user denied permission and selected Never Ask Again

ANS: After denial, check the return value of ActivityCompat.shouldShowRequestPermissionRationale(activity, permissionName). If it returns false, the user has selected “Never ask again,” requiring navigation to the Settings screen.

Q: Is it better to request permissions one by one or all at once

ANS: Requesting them all at once (Method 1 or 2) is generally preferred for a better user experience, as it minimizes the number of dialogs shown. Requesting them individually (Method 5) is useful only when a unique explanation (rationale) is required for each specific permission.

Q: What is the role of ContextCompat in permission handling

ANS: ContextCompat.checkSelfPermission() helps safely check permission status across different Android API levels, providing consistent behavior even on older devices where runtime permissions might not exist or work differently.
