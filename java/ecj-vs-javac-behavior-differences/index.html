“Differentiating Eclipse Compiler (ECJ) vs Javac: Core Behavior Discrepancies”

The Eclipse IDE employs its own sophisticated compiler, the Eclipse Compiler for Java (ECJ), which operates distinctly from the standard javac shipped with the Oracle/Sun JDK. This divergence in implementation leads to several notable operational distinctions crucial for developers using different environments.

Core Architectural Divergence: Independent Compilation Engines

The most significant revelation is that ECJ is not a wrapper around javac. It is an entirely separate compilation engine.

Historical Context: ECJ’s technology originates from IBM’s Jikes Java compiler. Since Eclipse itself started at IBM, this internal development was a natural progression. Jikes was historically noted for its speed compared to earlier versions of javac 1.

Practical Implication: Because ECJ is independent, it is entirely possible to write, compile, and execute Java code within the Eclipse environment even if the Java SDK is not explicitly installed on the system, as ECJ handles the entire compilation pipeline itself.

Error Tolerance and Incremental Building: The ECJ Advantage

A primary behavioral characteristic setting ECJ apart is its approach to code quality during development:

  1. Tolerating Uncompiled Code: ECJ permits the execution and debugging of code segments that have not technically compiled successfully, provided the specific erroneous block is never invoked at runtime. If the faulty code path is executed, the program will halt with an exception detailing the non-compilable nature of that section. This contrasts sharply with javac, which generally enforces strict compilation before execution is permitted.

  2. Incremental Builds: ECJ is designed as an incremental Java compiler, implemented as an Eclipse builder. This design allows for near-instantaneous compilation feedback as code is typed within the IDE. This rapid feedback loop dramatically speeds up the iterative development cycle.

Scenarios Where ECJ is Preferred or Utilized

This unique behavior profile makes ECJ the compiler of choice in several specialized toolchains:

  • Web Containers: Apache Tomcat relies on ECJ specifically for compiling JavaServer Pages (JSPs).
  • Alternative IDEs: IntelliJ IDEA offers built-in support for leveraging ECJ instead of its default compiler.
  • Integration Projects: Environments like Liferay utilize ECJ in their build processes.
  • Compiler Integration: GNU Compiler for Java (GCJ) integrates functionality derived from ECJ.

Noteworthy Behavioral Discrepancies

Beyond fundamental architectural differences, developers often observe subtle variances in how ECJ and javac handle edge cases, often attributable to implementation bugs or different interpretations of the Java specification in boundary conditions:

Compile-Time Optimization Variances

Differences in optimization strategies between the two compilers can surface in specific scenarios. For example, certain optimizations related to handling null values, particularly when involving a default case in a switch statement, might behave differently, potentially indicating a bug in one implementation or the other 2.

Generics Type Inference Differences

Generics handling represents a known area of divergence:

  • Eclipse Execution: Some code involving complex generic type inference might compile and run successfully within Eclipse (using ECJ).
  • javac Failure: The same code may fail to compile when processed strictly by the standard javac compiler.

This difference is particularly visible when dealing with generic methods that accept a null parameter; the way each compiler infers the generic type in that context can lead to compilation success on one platform and failure on the other.

Alternative Viewpoint: Jikes Lineage

Another perspective confirms the separation: ECJ is fundamentally based on the legacy of IBM’s Jikes compiler, maintaining independence from Sun’s tools from its inception. This separation was partly driven by IBM’s desire to maintain its own Java implementation ecosystem, potentially due to licensing considerations at the time 3.

FAQs on Differentiating Eclipse Compiler ECJ vs Javac

Q: Is the Eclipse Compiler a wrapper around javac

ANS: No, the Eclipse Compiler for Java (ECJ) is an entirely separate, independent compilation engine developed internally by Eclipse, evolving from IBM’s Jikes compiler technology.

Q: Can I run code in Eclipse that won't compile with javac

ANS: Yes, ECJ allows running code with uncompiled sections if those specific error-inducing blocks are never executed during runtime.

Q: Why does Tomcat use ECJ for JSPs

ANS: Tomcat utilizes ECJ because it is efficient for incremental compilation, which is suitable for the dynamic nature of JSP processing.

Q: What is the main benefit of ECJ in the IDE

ANS: The primary development benefit is its support for incremental builds, allowing the compiler to check code as you type, providing faster feedback than traditional batch compilation.
