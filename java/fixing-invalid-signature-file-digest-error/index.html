“Fixing Java’s ‘Invalid Signature File Digest for Manifest Main Attributes’ Error”

Encountering the java.lang.SecurityException: Invalid signature file digest for Manifest main attributes error typically surfaces when creating or running executable JAR files (uber-jars or fat-jars) that aggregate multiple dependencies, especially those that are cryptographically signed, like BouncyCastle. The core issue arises because the signature files (.SF, .DSA, .RSA) inside the dependencies conflict with the new, combined structure of the final JAR.

How can developers effectively mitigate or eliminate this security exception across various build environments like Maven, Gradle, or Ant?

Build Tool Configuration Strategies to Exclude Signatures

Several build tools provide mechanisms to exclude these problematic signature files during the JAR creation process.

Maven Shade Plugin Configuration

When utilizing the maven-shade-plugin to create a shaded JAR, explicitly filtering out manifest signature files from all artifacts resolves the conflict.

Solution 1: Excluding Signature Files via Maven Shade Filters

For users running into this when building an uber-jar, adjusting the plugin configuration to exclude .SF, .DSA, and .RSA files is the direct approach:

<configuration>
    <filters>
        <filter>
            <artifact>*:*</artifact>
            <excludes>
                <exclude>META-INF/*.SF</exclude>
                <exclude>META-INF/*.DSA</exclude>
                <exclude>META-INF/*.RSA</exclude>
            </excludes>
        </filter>
    </filters>
    <!-- Further configuration here -->
</configuration>

Solution 6 (Alternative Path): Addressing Cryptographic Provider Issues

A critical note: Deleting signatures, especially for providers like BouncyCastle, can trigger subsequent security exceptions like java.security.NoSuchAlgorithmException because JCE cannot authenticate the provider. If this occurs, the remedy involves either using an executable packer plugin that preserves signatures in a jar-in-jar manner, or obtaining a proper Code Signing Certificate and using the maven-jarsigner-plugin to re-sign the shaded artifact.

The POM configuration for both shading (with exclusions targeted only at BouncyCastle) and subsequent signing looks like this:

<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-shade-plugin</artifactId>
    <version>3.1.0</version>
    <executions>
        <execution>
            <phase>package</phase>
            <goals>
                <goal>shade</goal>
            </goals>
            <configuration>
                <filters>
                    <filter>
                        <artifact>org.bouncycastle:*</artifact> <!-- Target specific artifact -->
                        <excludes>
                            <exclude>META-INF/*.SF</exclude>
                            <exclude>META-INF/*.DSA</exclude>
                            <exclude>META-INF/*.RSA</exclude>
                        </excludes>
                    </filter>
                </filters>
                <transformers>
                    <transformer implementation="org.apache.maven.plugins.shade.resource.ManifestResourceTransformer">
                        <mainClass>your.class.here</mainClass>
                    </transformer>
                </transformers>
                <shadedArtifactAttached>true</shadedArtifactAttached>
            </configuration>
        </execution>
    </executions>
</plugin>
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-jarsigner-plugin</artifactId>
    <version>1.4</version>
    <executions>
        <!-- ... sign and verify goals ... -->
    </executions>
    <configuration>
        <keystore>/path/to/myKeystore</keystore>
        <alias>myfirstkey</alias>
        <storepass>111111</storepass>
        <keypass>111111</keypass>
    </configuration>
</plugin>

Solution 8: Disabling Dependency Reduced POM Generation

For some users, specifically setting <createDependencyReducedPom>false</createDependencyReducedPom> within the shade configuration resolved the issue alongside signature exclusion:

<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-shade-plugin</artifactId>
    <version>3.2.1</version>
    <configuration>
        <createDependencyReducedPom>false</createDependencyReducedPom>
    </configuration>
    <!-- ... executions configuration follows ... -->
</plugin>

Gradle Fat JAR Creation

Gradle build scripts offer direct mechanisms within the jar or shadowJar tasks to exclude unwanted entries.

Solution 2 & 11: Excluding Entries in the jar Block

When configuring the standard jar task for a fat jar, use the exclude directive:

jar {
    doFirst {
        // Collect contents from compile dependencies
        from { configurations.compile.collect { it.isDirectory() ? it : zipTree(it) } } 
    }
    // Remove signature files from the resulting jar
    exclude 'META-INF/*.RSA', 'META-INF/*.SF','META-INF/*.DSA' 
}

Solution 12: Full fatJar Task in Gradle (Groovy)

A complete Gradle task definition specifically for a fat JAR:

task fatJar(type: Jar) {
    manifest {
        attributes 'Implementation-Title': 'Gradle Jar File Example',  
            'Implementation-Version': version,
            'Main-Class': 'com.example.main'
    }
    baseName = project.name + '-all'
    from { configurations.compile.collect { it.isDirectory() ? it : zipTree(it) } }
    exclude 'META-INF/*.RSA', 'META-INF/*.SF','META-INF/*.DSA' 
    with jar
}

Solution 21: Kotlin Script (.kts) Exclusion for Fat Jar

For projects using Kotlin DSL for Gradle builds:

tasks.register<Jar>("fatJar") {
    baseName = "${project.name}-fat"
    manifest {
        attributes["Implementation-Title"] = "Watcher Jar File"
        attributes["Implementation-Version"] = version
        attributes["Main-Class"] = "MainKt"
    }
    from(configurations.runtimeClasspath.get().map { if (it.isDirectory) it else zipTree(it) }) {
        exclude(listOf("META-INF/*.RSA", "META-INF/*.SF", "META-INF/*.DSA"))
    }
    with(tasks.jar.get() as CopySpec)
}

Solution 22: Global Exclusion for Gradle Kotlin Scripts

To exclude these files from all JAR tasks within a project using Kotlin DSL:

tasks.withType<Jar> {
    excludes += listOf("META-INF/*.SF", "META-INF/*.DSA", "META-INF/*.RSA")
}

Solution 18: Using the Shadow Plugin for Gradle

The com.github.johnrengelman.shadow plugin simplifies uber-jar creation and often handles merging complexities better than the standard shade plugin:

plugins {
    // ① Add the shadow plugin
    id "com.github.johnrengelman.shadow" version "5.2.0"
}

// ...

shadowJar {
    archiveBaseName.set('baseName')
    archiveClassifier.set('classifier')
    archiveVersion.set('1.0')
    manifest {
        attributes 'Main-Class': 'Main'
    }
}

// ③ Disable the default jar task
jar.enabled = false
// ④ Execute the shadowJar task when compiling
build.dependsOn(shadowJar)

Command-Line and IDE Solutions

If you are not relying on a specific build tool for this step, direct manipulation of the JAR file or IDE configuration can resolve the issue.

Solution 3 & 10: Direct ZIP Manipulation

You can use the zip command-line utility to delete the offending entries directly from an existing JAR file. This is useful for quick fixes or post-build cleanup.

zip -d yourjar.jar 'META-INF/*.SF' 'META-INF/*.RSA' 'META-INF/*.DSA'

In one reported case involving IntelliJ IDEA, Eclipse-specific signature files were the culprits, requiring specific exclusion: zip -d demoSampler.jar 'META-INF/*.SF' 'META-INF/*.RSA' 'META-INF/*SF'.

Solution 7 & 15: IntelliJ IDEA Artifact Configuration

In IntelliJ IDEA, configuring the artifact build process can force the correct JAR creation, often by instructing the IDE to handle dependencies appropriately.

  1. Navigate to File -> Project Structure -> Artifacts.
  2. Add a new JAR Artifact, selecting your main class.
  3. In the creation window, ensure the option “copy to the output directory and link via manifest” is selected.

Solution 20: Cleaning Build Output

Sometimes, the error persists because stale build artifacts interfere. Deleting the IDE’s output directory (e.g., the out folder) and rebuilding the project can clear hidden conflicts that the build tool configuration failed to address cleanly.

Advanced and Indirect Approaches

Solution 4: Two-Step Ant Build Process

For Ant users, a sequential process is often needed: first, aggregate all dependency JARs into a temporary JAR (deps.jar), and then create the final JAR, merging the class files with the dependencies while excluding signatures from the dependency JAR. A sleep command is sometimes included to prevent file modification date issues:

<target name="jar" depends="compile" description="Create one big jarfile.">
    <jar jarfile="${output.dir}/deps.jar">
        <zipgroupfileset dir="jars">
            <include name="**/*.jar" />
        </zipgroupfileset>
    </jar>
    <sleep seconds="1" />
    <jar jarfile="${output.dir}/myjar.jar" basedir="${classes.dir}">
        <zipfileset src="${output.dir}/deps.jar" excludes="META-INF/*.SF" />
        <manifest>
            <attribute name="Main-Class" value="com.mycompany.MyMain" />
        </manifest>
    </jar>
</target>

Solution 14: Custom Ant Macro to Unsign Jars

A more robust Ant solution involves an unsignjar macro that copies the manifest, strips signature lines using replaceregexp, creates a temporary JAR with the clean manifest, and swaps it back.

Solution 17: Using a Specialized JAR Classloader

If tampering with signatures is strictly undesirable (e.g., due to strict security requirements), utilizing a library that employs a special JAR classloader approach—one that loads bundled dependencies dynamically without unpacking and invalidating signatures—can bypass the issue entirely.

FAQs on Invalid Signature File Digest Error

Q: Why does removing signatures sometimes cause new Java errors

ANS: Removing cryptographic signatures from provider JARs (like BouncyCastle) prevents the Java Cryptography Extension (JCE) from authenticating the provider’s authenticity, leading to NoSuchProviderException or NoSuchAlgorithmException errors when the provider’s algorithms are called.

Q: Is excluding signature files the best long-term fix

ANS: Excluding them fixes the immediate signature error during uber-jar creation. The best fix, if security verification is crucial, is to resign the final JAR using a proper code signing certificate after shading.

Q: Can this error occur outside of Maven shade plugin usage

ANS: Yes, this error occurs anytime multiple JARs are merged into one, and the original signature files conflict with the new archive structure, regardless of whether you use Gradle, Ant, or command-line tools.

Q: What are META-INF SF DSA and RSA files

ANS: These files represent the Manifest (.SF) and the corresponding cryptographic hashes/signatures (.DSA or .RSA) used to verify the integrity of the JAR contents at runtime.
