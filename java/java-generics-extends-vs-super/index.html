“Java Generics: Deciphering ’extends’ vs ‘super’ Wildcards”

When working with Java generics and collections, understanding the difference between ? extends T and ? super T wildcards is crucial for writing type-safe and flexible code. These wildcards, often referred to as upper and lower bounds respectively, dictate how you can interact with generic types.

Let’s break down their behaviors with practical examples and insights.

Understanding ? extends T (Upper Bound)

The declaration List<? extends Number> foo3 signifies that foo3 can refer to a list of Number or any of its subtypes (like Integer, Double, etc.).

Consider this hierarchy:

// Assume a hierarchy like this for demonstration
class Number {}
class Integer extends Number {}
class Double extends Number {}

Reading from List<? extends Number>:

When you read from a List<? extends Number>, you are guaranteed to get an object of type Number or a subclass of Number.

  • You can safely read a Number because any list assigned to foo3 will contain Number instances or their subtypes.
  • You cannot guarantee reading an Integer because foo3 might be pointing to a List<Double>.
  • Similarly, you cannot guarantee reading a Double as foo3 could point to a List<Integer>.

Writing to List<? extends Number>:

The restriction here is significant: you generally cannot add objects to a List<? extends T>. This is because the compiler doesn’t know the exact type of list foo3 refers to, making it unsafe to add any specific type.

  • You cannot add an Integer because foo3 might be a List<Double>.
  • You cannot add a Double because foo3 might be a List<Integer>.
  • You cannot even add a Number because foo3 might be a List<Integer>, and Number is not necessarily a valid element in a list specifically designed for Integers.

The only exception is adding null, which is permissible in mutable lists.

Understanding ? super T (Lower Bound)

The declaration List<? super Integer> foo3 means foo3 can refer to a list of Integer, or any of its supertypes (like Number, Object, etc.).

Consider this hierarchy:

// Assume a hierarchy like this for demonstration
class Object {}
class Number extends Object {}
class Integer extends Number {}

Reading from List<? super Integer>:

When reading from a List<? super Integer>, the only guarantee is that you will get an Object or a subclass of Object. You cannot assume it’s an Integer or a Number.

  • You cannot guarantee an Integer because foo3 could be pointing to a List<Number> or List<Object>.
  • You cannot guarantee a Number because foo3 could be pointing to a List<Object>.
  • The only safe bet is that you’ll receive an instance of Object, but its specific subclass is unknown.

Writing to List<? super Integer>:

This wildcard allows you to add elements to the list. The elements you add must be subtypes of Integer or Integer itself.

  • You can add an Integer because an Integer is compatible with any list declared as List<? super Integer>.
  • You can add an instance of a subclass of Integer for the same reason.
  • You cannot add a Double because foo3 might be a List<Integer>, which cannot hold Doubles.
  • You cannot add a Number because foo3 might be a List<Integer>, and Number isn’t necessarily a supertype of Integer in all contexts, but Integer is a subtype of Number. However, you can’t add a Number to a List<Integer> directly.
  • You cannot add an Object because foo3 might be a List<Integer>, and Object is not necessarily a valid element in a list specifically designed for Integers.

The PECS Principle

A common mnemonic to remember the usage of these wildcards is PECS: Producer Extends, Consumer Super.

  • Producer Extends (? extends T): Use this when the collection is primarily used to produce (read) elements of type T. You can read Ts, but you cannot add to it (except null).
  • Consumer Super (? super T): Use this when the collection is primarily used to consume (write) elements of type T. You can add Ts and its subtypes, but you can only read Objects from it.
  • No Wildcard (List<T>): If you need to both read and write elements of type T, use the standard generic type List<T> without wildcards.

Practical Code Examples

Example 1: Using ? extends for reading

Imagine a method that processes a list of numbers:

import java.util.ArrayList;
import java.util.List;

public class NumberProcessor {

    // Method to sum numbers from a list
    public static double sumNumbers(List<? extends Number> numbers) {
        double sum = 0.0;
        for (Number num : numbers) { // Safe to read as Number
            sum += num.doubleValue();
        }
        // numbers.add(10.5); // ERROR: Cannot add to a List<? extends Number>
        return sum;
    }

    public static void main(String[] args) {
        List<Integer> intList = new ArrayList<>();
        intList.add(5);
        intList.add(10);
        System.out.println("Sum of Integers: " + sumNumbers(intList)); // Works

        List<Double> doubleList = new ArrayList<>();
        doubleList.add(3.14);
        doubleList.add(2.71);
        System.out.println("Sum of Doubles: " + sumNumbers(doubleList)); // Works
    }
}

Example 2: Using ? super for writing

Consider a method to add specific types to a list:

import java.util.ArrayList;
import java.util.List;

public class DataInserter {

    // Method to add an integer to a list
    public static void addInteger(List<? super Integer> integers) {
        integers.add(42); // Safe to add Integer
        // Integer val = integers.get(0); // ERROR: Cannot guarantee Integer from List<? super Integer>
        Object obj = integers.get(0); // Safe to read as Object
        System.out.println("Added: 42, Read: " + obj);
    }

    public static void main(String[] args) {
        List<Integer> intList = new ArrayList<>();
        addInteger(intList); // Works

        List<Number> numberList = new ArrayList<>();
        addInteger(numberList); // Works, as Integer can be added to List<Number>

        List<Object> objectList = new ArrayList<>();
        addInteger(objectList); // Works, as Integer can be added to List<Object>
    }
}

Example 3: The Collections.copy method

The java.util.Collections.copy method is a classic illustration of PECS:

public static <T> void copy(List<? super T> dest, List<? extends T> src) {
    for (int i = 0; i < src.size(); i++) {
        dest.set(i, src.get(i)); // src.get(i) produces T, dest.set() consumes T
    }
}

Here, src is a producer (? extends T) allowing safe reading of Ts, and dest is a consumer (? super T) allowing safe writing of Ts.

Important Note: When reading from any wildcard list (? extends T, ? super T, or List<?>), you can always assign the result to an Object variable.

Key Takeaways

  • ? extends T: Use when you only need to read from the collection. It guarantees you get T or a subtype, but prevents adding anything except null. Think “Producer”.
  • ? super T: Use when you only need to write to the collection. It allows adding T or its subtypes, but guarantees you only read Objects. Think “Consumer”.
  • List<T>: Use when you need to both read and write Ts.

By applying the PECS principle, you can effectively leverage Java’s generics for robust and maintainable code, avoiding common runtime errors and enhancing type safety. For more on Java generics, you might find these resources helpful: Java Generics Tutorial , and Java Generics FAQ .

FAQs on Java Generics Wildcards

Q: What is the primary difference between List<? extends Number> and List<? super Number>

ANS: List<? extends Number> allows you to read Number or its subtypes but not add anything except null. List<? super Number> allows you to add Number or its supertypes but only read Objects.

Q: Can I add an Integer to a List<? extends Number>

ANS: No, you cannot directly add an Integer (or any object other than null) to a List<? extends Number> because the compiler cannot guarantee that the list is not of a subtype of Number that cannot accept an Integer.

Q: What type of object can I read from a List<? super Integer>

ANS: You can only safely read an Object from a List<? super Integer>. You cannot assume it’s an Integer or a Number because the list might be a List<Object> or List<Number>.

Q: When should I use List<?> versus List<? extends T>

ANS: List<?> is for an unknown type, allowing reads of Object and preventing writes. List<? extends T> is for a known upper bound, allowing reads of T or its subtypes and preventing writes (except null).

Q: Does PECS apply to arrays?

ANS: PECS primarily applies to generic types and collections. Arrays in Java behave differently with covariance and subtyping, which can lead to ArrayStoreException if not handled carefully.

Q: Can I add a subclass of T to a List<? super T>

ANS: Yes, you can add a subclass of T to a List<? super T> because any subclass of T is also a valid element for any supertype of T.

Q: What is the role of Java Generics in type safety

ANS: Java Generics provide compile-time type checking, ensuring that you use the correct types with collections and preventing common runtime errors like ClassCastException.
