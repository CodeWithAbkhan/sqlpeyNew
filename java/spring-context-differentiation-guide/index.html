“Spring Web Application: Differentiating applicationContext XML and servlet-specific Contexts”

When building Spring web applications, developers often utilize multiple ApplicationContext configurations. The standard pattern involves a root context, typically loaded via applicationContext.xml, and one or more servlet-specific contexts, often named like *-servlet.xml (e.g., spring-servlet.xml or myApp-servlet.xml), which are bound to a DispatcherServlet.

What precisely dictates the purpose and scope of beans defined in these distinct configuration files, and how do they interact within the lifecycle of a running web application deployed on a servlet container like Tomcat?

Hierarchy and Bean Visibility in Spring Web Apps

Spring establishes a parent-child context hierarchy in web applications. This structure governs which beans are accessible from where.

The Root Web Application Context (the parent context) is defined by applicationContext.xml (or configurations specified via the ContextLoaderListener). This context is typically used for beans that need to be shared across the entire web application, irrespective of which specific Spring MVC servlet handles the request.

Conversely, the Servlet Context (the child context) is created for each deployed DispatcherServlet via its corresponding configuration file (e.g., spring-servlet.xml). This context holds beans scoped specifically for that servlet’s processing needs.

The fundamental rule of visibility in this hierarchy dictates:

  • Beans in the parent context (applicationContext.xml) are visible and accessible by beans in the child context (spring-servlet.xml).
  • Beans defined only in the child context are not visible to the parent context or other sibling child contexts.

This structure makes applicationContext.xml ideal for shared services, data sources, or transaction managers that multiple servlets might need to access. All Spring MVC controllers, however, must reside within the context associated with the DispatcherServlet (the child context).

For very simple applications utilizing only a single servlet, defining the root context might be redundant unless there is a specific need to separate configuration layers.

Non-Web Application Context Loading (Scenario 1)

In environments outside a traditional servlet container—such as a standalone client application (e.g., Swing or a batch job)—the context loading is direct and independent of any web.xml configuration or DispatcherServlet.

// Example for a non-web application loading a configuration file
private static ApplicationContext context = 
    new ClassPathXmlApplicationContext("test-client.xml");

Object myService = context.getBean("serviceName"); 
// No server container or web.xml involved.

In this scenario, the ApplicationContext acts purely as the bean container, and there is zero relationship between this mechanism and the concepts of applicationContext.xml or DispatcherServlet.

Deployment Scenarios in a Servlet Container

When deploying within a server like Tomcat, the structure depends heavily on web.xml setup:

Scenario 2: Using ContextLoaderListener (Root Context Setup)

The ContextLoaderListener initializes the root context before any servlets start up. It typically loads beans from applicationContext.xml.

web.xml Configuration:

<listener>
    <listener-class>org.springframework.web.context.ContextLoaderListener</listener-class>
</listener>
<!-- The listener will look for /WEB-INF/applicationContext.xml by default, 
     or use context-param to specify location(s) -->

If applicationContext.xml imports other resources (e.g., test1.xml, test2.xml), all those beans are instantiated by this listener at server startup. Crucially, this root context remains separate from the servlet contexts.

Scenario 3: Configuring a DispatcherServlet (Servlet Context Setup)

The DispatcherServlet itself is configured as a servlet in web.xml. It creates its own dedicated child context, loading beans from its configured file, like springweb-servlet.xml.

web.xml Configuration:

<servlet>
    <servlet-name>springweb</servlet-name>
    <servlet-class>org.springframework.web.servlet.DispatcherServlet</servlet-class>    
</servlet>
<servlet-mapping>
    <servlet-name>springweb</servlet-name>
    <url-pattern>*.action</url-pattern>
</servlet-mapping>

Upon deployment, the DispatcherServlet loads its configuration, instantiating beans specific to request handling (like Controllers).

Scenario 4: Combined Setup (Root + Multiple DispatcherServlets)

This is the most common web application setup, utilizing both the listener and one or more servlets, establishing the parent-child relationship.

  1. Server Startup: ContextLoaderListener runs, instantiating the Root Context beans from applicationContext.xml (which might import test1.xml through test4.xml).
  2. Servlet Initialization: Once the root context is ready, each DispatcherServlet initializes, creating its Child Context based on its *-servlet.xml.

The instantiation sequence is ordered: Root Context first, then each Child FrameworkServlet context. This ensures that shared infrastructure beans are available when the servlet contexts initialize.

Advanced Context Separation: Component Scanning Directives

To enforce separation of concerns between the contexts, component scanning configurations can be refined using include/exclude filters.

In the Servlet Context (spring-servlet.xml), you might exclusively scan for Controllers:

<!-- Scans only for annotated @Controllers in the web package -->
<context:component-scan base-package="org.test.web" use-default-filters="false">
    <context:include-filter type="annotation" 
                            expression="org.springframework.stereotype.Controller"/>
</context:component-scan>

Conversely, in the Root Context (applicationContext.xml), you scan the rest of the application layers while explicitly excluding controllers:

<!-- Scans base package but excludes any component annotated as a Controller -->
<context:component-scan base-package="org.test">
    <context:exclude-filter type="annotation" 
                            expression="org.springframework.stereotype.Controller"/>
</context:component-scan>

DispatcherServlet Initialization Parameter Control

The DispatcherServlet can be explicitly told which configuration file to use via the contextConfigLocation init-param in web.xml.

For a single servlet, if you omit the listener, the servlet context configuration alone is loaded:

<servlet>
    <servlet-name>SpringController</servlet-name>
    <servlet-class>org.springframework.web.servlet.DispatcherServlet</servlet-class>
    <init-param>
        <param-name>contextConfigLocation</param-name>
        <param-value>/WEB-INF/spring-servlet.xml</param-value>
    </init-param>
    <load-on-startup>1</load-on-startup>
</servlet>

If you require both a root context (using the listener) and a specific servlet context, you configure both elements in web.xml. The listener handles the root context using contextConfigLocation specified either globally via a <context-param> or by default loading applicationContext.xml. The servlet handles its specific context via its own <init-param>.

For instance, to define the root context location for the listener:

<context-param>
    <param-name>contextConfigLocation</param-name>
    <param-value>/WEB-INF/applicationContext.xml</param-value>
</context-param>
<listener>
    <listener-class>org.springframework.web.context.ContextLoaderListener</listener-class>
</listener>
<!-- DispatcherServlet configuration follows, pointing to its own file -->

Benefits of Using ApplicationContext Features

The ApplicationContext interface offers several functional advantages over the basic BeanFactory:

  1. Internationalization (i18n): It implements MessageSource, enabling localized message resolution for text.
  2. Resource Access: It is a ResourceLoader, providing an abstraction layer for accessing deployment-specific resources like images or properties files flexibly via the Resource interface.
  3. Event Propagation: It permits beans to register as listeners, allowing them to react declaratively to events published within the container.
  4. Declarative Configuration: Operations that would require programmatic calls against a BeanFactory can often be handled declaratively within the context configuration.

FAQs on Spring Context Configuration

Q: What is the primary role of applicationContext xml

ANS: It defines beans for the root Web Application Context, intended for resources shared across all servlets in the deployment.

Q: Where should Spring MVC Controllers be placed

ANS: Spring MVC Controllers must be defined in the servlet-specific context (e.g., spring-servlet.xml) associated with the DispatcherServlet.

Q: Can a bean in a servlet context access a bean defined only in the root context

ANS: Yes, beans in the child (servlet) context can reference beans in the parent (root) context due to the context hierarchy.

Q: How does the ContextLoaderListener function

ANS: It initializes the root ApplicationContext at server startup, instantiating shared beans defined in its configuration files before any servlets are initialized.
