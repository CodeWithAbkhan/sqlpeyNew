“Resolving Java Access Restriction Errors in Eclipse Build Paths”

When developing Java applications, encountering an “Access Restriction” error, often seen as a “Forbidden reference (access rules)” warning or error during compilation, can halt progress. This typically stems from mismatches or conflicts between the Java Runtime Environment (JRE) version specified in the build path and classes residing in external libraries or the core Java installation. What are the established techniques for resolving these frustrating compilation barriers?

Strategies for Correcting Forbidden Reference Issues

Several distinct approaches have proven effective in silencing these access rule violations, often revolving around the project’s Build Path configuration or compiler settings.

1. Re-establishing the JRE System Library Connection

A common fix involves refreshing the link between your project and the installed Java environment.

Action Steps:

  1. Navigate to the project’s Properties.
  2. Access the Build Path settings.
  3. Locate the JRE System Library entry under the Libraries tab.
  4. Remove this existing entry.
  5. Re-add it by selecting Add Library, choosing JRE System Library, and accepting the default selection.

This process often forces Eclipse to re-evaluate class loading order, especially when multiple JARs contain overlapping or conflicting class definitions (e.g., multiple versions of javax.xml.soap.SOAPPart found in axis-saaj-1.4.jar, saaj-api-1.3.jar, and rt.jar). A fundamental fix involves ensuring you exclude conflicting JAR files that duplicate classes found in the JRE.

2. Modifying Compiler Error/Warning Thresholds

If the restriction stems from using deprecated or restricted APIs that you are certain are safe for your specific deployment context, you can instruct the compiler to treat them as warnings rather than errors.

Eclipse IDE Configuration:

  • Windows/Linux: Go to Window -> Preferences -> Java -> Compiler -> Errors/Warnings.
  • Mac OS X: Go to Eclipse -> Preferences -> Java -> Compiler -> Errors/Warnings.

Locate the setting for Forbidden reference (access rules) and change its severity from Error to Warning.

3. Aligning JDK vs. JRE Installation Paths

A subtle but significant cause is using a JRE path in the Build Path when a full JDK is installed, or pointing to an incorrect version.

Check and Adjust:

  1. In Eclipse Preferences (not project properties), navigate to Java -> Installed JREs.
  2. Verify that the selected JDK/JRE points precisely to the JDK folder (e.g., C:\Program Files\Java\jdk1.8.0_74), rather than just the JRE subdirectory.
  3. In the project’s Build Path configuration (Properties -> Build Path -> Libraries), edit the JRE System Library entry. Ensure it points to the correct Workspace default JRE or an Alternate JRE that matches your environment setup.

4. Managing Library Order in Build Path

The sequence in which libraries are loaded profoundly impacts which class definition takes precedence. If a third-party JAR contains an older version of a core Java class, it might override the required version.

Order Adjustment:

  1. Open Project Properties -> Build Path -> Order and Export tab.
  2. Adjust the entry order. For many users, moving the JRE System Library entry to the bottom resolves the conflict, allowing external, specific libraries to load their necessary classes first, provided the conflict isn’t caused by the external library overriding a newer required class.

Alternative View: Some developers report success by moving the JRE System Library to the top of the list. Experimentation based on your specific library conflicts is key here.

5. Command-Line Builds: Tycho Compiler Configuration

For projects built via Maven, particularly those using OSGi plugins managed by Tycho, the compiler arguments must be explicitly configured in the pom.xml to suppress these access warnings during the automated build cycle.

Maven pom.xml Configuration Example:

<plugin>
    <groupId>org.eclipse.tycho</groupId>
    <artifactId>tycho-compiler-plugin</artifactId>
    <version>${tycho.version}</version>
    <configuration>
        <!-- Explicitly instruct the compiler to handle discouraged and forbidden rules as warnings -->
        <compilerArgument>-warn:+discouraged,forbidden</compilerArgument>
    </configuration>
</plugin>

This directive tells the Tycho compiler to treat access restrictions as warnings (forbidden) rather than failing the build entirely.

6. Addressing License Violation Concerns (The Root Cause)

It is important to note the context provided by Oracle’s Java licensing regarding core Java packages (java.* or javax.*). Attempting to replace a standard class shipped within rt.jar with a class from an external library may contravene the Java 2 Runtime Environment binary code license agreement.

If you encounter this, the true solution is often to remove the conflicting class from the external library JAR file that is causing the override, unless you are intentionally attempting to substitute a core Java feature (which is generally discouraged and legally risky).

FAQs on Resolving Java Access Restriction Errors

Q: How do I check my project's current Execution Environment in Eclipse

ANS: Navigate to Project Properties -> Java Build Path -> Libraries. Examine the JRE System Library entry; discrepancies between this and the ‘Installed JREs’ can trigger the issue. You might need to adjust settings under Project > Properties > Java Compiler as well.

Q: Can removing the JRE System Library entirely work

ANS: Temporarily removing it and then re-adding it (as suggested in Solution 1 and 3) is a valid troubleshooting step to reset internal path mappings. However, removing it permanently will certainly break compilation as the core Java APIs become unavailable.

Q: What if the error occurs only during Maven build and not in Eclipse

ANS: This points directly to a configuration mismatch between your IDE settings and your pom.xml. Refer to Solution 5 where the Tycho compiler plugin configuration is modified to manage access restrictions via <compilerArgument>.
