“Java Synchronized Keyword: Ensure Thread-Safe Code Execution”

The synchronized keyword in Java is a fundamental mechanism for managing concurrent access to shared data and preventing race conditions. It ensures that only one thread can execute a synchronized method or block of code at any given time, thereby protecting against “dirty reads” and “dirty writes.”

The Core Concept of synchronized

At its heart, synchronized operates on the principle of intrinsic locks, also known as monitors. Every Java object implicitly has an intrinsic lock associated with it. When a thread enters a synchronized block or method, it attempts to acquire the lock for the specified object or class.

  • Exclusive Access: Once a thread acquires the lock, it has exclusive access to the synchronized section. Any other thread attempting to enter a synchronized section on the same object or class will be blocked and must wait until the first thread releases the lock.
  • Visibility Guarantees: Exiting a synchronized block or method also establishes a “happens-before” relationship. This means that any changes made to shared variables within the synchronized section by the exiting thread are guaranteed to be visible to any thread that subsequently acquires the lock for the same object. This prevents memory consistency errors where one thread might see stale data.

Synchronized Methods vs. Synchronized Blocks

There are two primary ways to apply the synchronized keyword:

  1. Synchronized Methods:

    • Instance Methods: When you declare an instance method as synchronized, the intrinsic lock of the object instance (i.e., this) is used as the lock. Only one thread can execute any synchronized instance method on a given object at a time.
    • Static Methods: When you declare a static method as synchronized, the intrinsic lock of the Class object itself is used. This means only one thread can execute any synchronized static method for that class at a time, regardless of the object instances.

  2. Synchronized Blocks:

    • This offers more granular control by allowing you to synchronize specific sections of code within a method. You explicitly specify the object or class whose lock will be used.
    • Syntax: synchronized(lockObject) { // critical section code }
    • Flexibility: synchronized blocks are often preferred for their flexibility. You can choose a specific object for locking, which can prevent a single synchronized method from blocking unrelated synchronized methods on the same object, thus improving concurrency. For instance, you can have two separate synchronized blocks using different lock objects, allowing two threads to execute these blocks concurrently if they don’t contend for the same lock.

Practical Code Examples

Let’s illustrate with code:

Example 1: Synchronized Instance Method

This example shows a simple counter where multiple threads increment it. Without synchronized, the final count would be unpredictable.

class Counter {
    private int count = 0;

    // synchronized ensures only one thread can access this method at a time
    public synchronized void increment() {
        count++;
        System.out.println(Thread.currentThread().getName() + " incremented count to: " + count);
    }

    public synchronized int getCount() {
        return count;
    }
}

public class SynchronizedMethodDemo {
    public static void main(String[] args) {
        Counter counter = new Counter();

        // Thread 1
        Thread thread1 = new Thread(() -> {
            for (int i = 0; i < 5; i++) {
                counter.increment();
                try {
                    Thread.sleep(100); // Simulate some work
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }
        }, "Worker-1");

        // Thread 2
        Thread thread2 = new Thread(() -> {
            for (int i = 0; i < 5; i++) {
                counter.increment();
                try {
                    Thread.sleep(150); // Simulate some work
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }
        }, "Worker-2");

        thread1.start();
        thread2.start();

        // Wait for threads to complete
        try {
            thread1.join();
            thread2.join();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }

        System.out.println("Final counter value: " + counter.getCount());
    }
}

Example 2: Synchronized Block with a Specific Lock Object

This example uses a synchronized block with an explicit lock object, demonstrating how to isolate synchronization to specific operations.

class SharedResource {
    private int sharedValue = 0;
    private final Object lock1 = new Object(); // Lock for operation A
    private final Object lock2 = new Object(); // Lock for operation B

    public void performOperationA(String threadName) {
        synchronized (lock1) {
            System.out.println(threadName + " entered synchronized block for operation A.");
            for (int i = 0; i < 3; i++) {
                sharedValue++;
                System.out.println(threadName + " - Operation A: sharedValue = " + sharedValue);
                try {
                    Thread.sleep(50);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }
            System.out.println(threadName + " exiting synchronized block for operation A.");
        }
    }

    public void performOperationB(String threadName) {
        synchronized (lock2) { // Using a different lock object
            System.out.println(threadName + " entered synchronized block for operation B.");
            for (int i = 0; i < 2; i++) {
                sharedValue--; // Note: Decrementing is not synchronized on the same lock as increment
                System.out.println(threadName + " - Operation B: sharedValue = " + sharedValue);
                try {
                    Thread.sleep(70);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }
            System.out.println(threadName + " exiting synchronized block for operation B.");
        }
    }

    public int getSharedValue() {
        return sharedValue;
    }
}

public class SynchronizedBlockDemo {
    public static void main(String[] args) {
        SharedResource resource = new SharedResource();

        Thread threadA1 = new Thread(() -> resource.performOperationA("Thread-A1"), "Thread-A1");
        Thread threadA2 = new Thread(() -> resource.performOperationA("Thread-A2"), "Thread-A2");
        Thread threadB1 = new Thread(() -> resource.performOperationB("Thread-B1"), "Thread-B1");

        threadA1.start();
        threadB1.start(); // Thread B1 can run alongside Thread A1 because of different locks
        try {
            Thread.sleep(200); // Give some time for initial operations
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        threadA2.start();

        try {
            threadA1.join();
            threadA2.join();
            threadB1.join();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }

        System.out.println("Final sharedValue: " + resource.getSharedValue());
    }
}

Expected Output (with synchronized blocks): Observe how operations on lock1 are serialized, but operations on lock2 can potentially run concurrently with lock1 operations.

Thread-A1 - Operation A: sharedValue = 1
Thread-B1 entered synchronized block for operation B.
Thread-B1 - Operation B: sharedValue = 0

Thread-B1 exited synchronized block for operation B.
Thread-A1 - Operation A: sharedValue = 3
Thread-A1 exited synchronized block for operation A.
Thread-A2 entered synchronized block for operation A.
Thread-A2 - Operation A: sharedValue = 4
Thread-A2 - Operation A: sharedValue = 5
Thread-A2 - Operation A: sharedValue = 6
Thread-A2 exited synchronized block for operation A.
Final sharedValue: 6

When Synchronization Might Not Be Enough

It’s important to note that synchronized makes methods or blocks thread-safe for a given object instance. However, it doesn’t automatically make entire complex operations thread-safe if they involve multiple independent synchronized calls.

Consider this common pattern:

if (myVector.isEmpty()) {
    myVector.add(data);
}

Even if myVector.isEmpty() and myVector.add(data) are individually synchronized methods, there’s a small window between the check and the add. Another thread could potentially add an element after the isEmpty() check but before add() is called, leading to a vector with two elements when only one was intended. To guard such compound actions, you must apply synchronized at the level of the entire compound operation:

synchronized (myVector) { // Synchronize the entire check-and-add operation
    if (myVector.isEmpty()) {
        myVector.add(data);
    }
}

This highlights the need to synchronize operations that depend on the state of shared data as a whole.

Alternatives and Advanced Concepts

While synchronized is a powerful tool, Java’s java.util.concurrent package offers more advanced and often more efficient alternatives, such as:

  • Lock Interface: Provides more explicit control over locking, including timed waits and interruptible locks. Classes like ReentrantLock are common.
  • Atomic Variables: Classes like AtomicInteger, AtomicLong, etc., provide atomic operations (like increment, decrement) without explicit locks, often using hardware compare-and-swap (CAS) operations for better performance.
  • Concurrent Collections: Data structures like ConcurrentLinkedDeque, ConcurrentHashMap, etc., are designed for high concurrency and handle synchronization internally.

FAQs on Java Synchronized Keyword

Q: What is the primary purpose of the synchronized keyword in Java

ANS: The synchronized keyword in Java is used to ensure thread safety. It prevents multiple threads from accessing a shared resource (like a variable or object) simultaneously, thereby avoiding race conditions and data inconsistencies. It achieves this by enforcing exclusive access to synchronized methods or blocks of code via intrinsic locks.

Q: How does synchronized ensure data visibility between threads

ANS: When a thread exits a synchronized block or method, it releases the intrinsic lock. This action establishes a “happens-before” relationship, guaranteeing that all modifications made to shared variables within that synchronized section are visible to any other thread that subsequently acquires the same lock.

Q: Can synchronized methods on different objects be called concurrently

ANS: Yes. If two threads call synchronized instance methods on different object instances, they can execute concurrently. The synchronized keyword applies to the lock associated with the specific object instance.

Q: What is the difference between synchronized methods and synchronized blocks

ANS: Synchronized methods synchronize the entire method body using the object’s intrinsic lock (or the class’s lock for static methods). Synchronized blocks allow finer-grained control, enabling you to specify a particular object or class for locking within a method, synchronizing only a specific code segment.

Q: When is synchronization not sufficient for thread safety

ANS: Synchronization is not sufficient for thread safety when a compound operation involves multiple separate synchronized calls. For instance, a check-then-act sequence on a collection might still have a race condition between the check and the act if not synchronized as a single atomic unit. Always synchronize the entire critical operation.

Q: What are alternatives to using the synchronized keyword

ANS: Alternatives include using the java.util.concurrent.locks.Lock interface (e.g., ReentrantLock), atomic variables (AtomicInteger, AtomicLong), and concurrent collections (ConcurrentHashMap, ConcurrentLinkedDeque) from the java.util.concurrent package. These often provide more flexibility and performance.

Q: What happens if a thread tries to access a synchronized method when another thread is already inside it

ANS: The thread attempting to access the synchronized method will be blocked. It will have to wait until the thread currently executing the synchronized method exits it, releasing the intrinsic lock associated with the object.

Q: How do synchronized static methods differ from synchronized instance methods

ANS: Synchronized static methods use the intrinsic lock of the Class object, meaning only one thread can execute any synchronized static method for that class at a time. Synchronized instance methods use the intrinsic lock of the specific object instance, allowing concurrent execution of synchronized methods on different object instances.
