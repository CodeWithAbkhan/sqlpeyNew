“Java String Literal vs New String Comparison: Memory Allocation Details”

The Core Difference: String Constant Pool vs. Heap Allocation

When you define a string in Java, the mechanism dictates object creation, memory footprint, and reference behavior.

String Literal Declaration (String s = "value";)

When using a string literal, the Java Virtual Machine (JVM) utilizes the String Constant Pool (SCP) located in the area of memory known as the Metaspace (or PermGen in older versions).

  1. Pooling Behavior: The JVM checks the SCP for an existing string object with the identical character sequence.
  2. Reusing Objects: If found, the reference variable (s in this case) points directly to the existing object in the pool. If not found, a new String object containing the sequence is created in the pool, and the reference is assigned to s. This process is often implicitly invoked via the String.intern() method logic.

Constructor Declaration (String s = new String("value");)

Invoking the String constructor forces the creation of a brand new object on the standard Heap, regardless of whether an identical string exists in the SCP.

  1. Heap Allocation: A new String object is instantiated on the Heap.
  2. Literal Check (Optional): If the argument passed to the constructor (e.g., "value") is itself a literal, the JVM might still check the SCP for that literal part, but the resulting object referenced by the variable will be a distinct, separate instance on the Heap.

Examining Object Identity (==) vs. Content Equality (.equals())

Because of the differing creation paths, comparing references using == yields different results than comparing content using .equals().

Practical Demonstration of Identity Check

Consider the following scenario to observe memory references:

// Scenario A: Literals - They share the same object via intern mechanism
String refA1 = "MemoryEfficientString";
String refA2 = "MemoryEfficientString";
System.out.println("A1 == A2: " + (refA1 == refA2)); // Expected: true

// Scenario B: Constructor - Forces new object creation on the Heap
String refB1 = new String("SeparateInstance");
String refB2 = new String("SeparateInstance");
System.out.println("B1 == B2: " + (refB1 == refB2)); // Expected: false

// Scenario C: Mixed Comparison
System.out.println("A1 == B1: " + (refA1 == refB1)); // Expected: false (SCP vs Heap)
System.out.println("A1 equals B1: " + refA1.equals(refB1)); // Expected: true (Content comparison)

If you subsequently call .intern() on the Heap-created object, you can force its reference to align with the SCP version:

String refC = new String("ForcePool");
String refD = "ForcePool"; // Already in pool

System.out.println("Initial C == D: " + (refC == refD)); // false

refC = refC.intern(); // C now points to the object in the SCP, same as D

System.out.println("After intern C == D: " + (refC == refD)); // true

Bytecode Inspection Reveals the Mechanism

Examining the compiled Java bytecode (javap) clearly illustrates the difference in instruction sets used by the JVM:

For String literal_name = "text";: The ldc (Load Constant) instruction is used, which retrieves the already existing constant from the Constant Pool.

For String new_name = new String("text");: The bytecode sequence involves new (allocate space on the Heap), dup (duplicate reference), and invokespecial (call the constructor).

// Sample Bytecode Snippet Analysis (Conceptual)
public static void demonstrateStrings() {
    String literalStr = "SampleText"; // Uses ldc instruction
    String newStr = new String("SampleText"); // Uses new, dup, invokespecial
}

Best Practices and Alternatives

Recommendation: Always favor string literals (String s = "text";) over the constructor (new String("text");) for initialization.

  1. Performance: Literals are faster as they avoid unnecessary heap allocation and constructor invocation overhead, leveraging the highly optimized SCP.
  2. Memory: Pooling reduces memory consumption by eliminating duplicate string objects.
  3. Readability: Literals are syntactically cleaner.

The official Java documentation itself implies that using the constructor is rarely beneficial, stating that the constructor should only be used when “an explicit copy of original is needed,” a scenario rarely encountered given the immutability of strings.

FAQs on Java String Literal vs New String Comparison

Q: Why does 'new String()' create a different object than a literal

ANS: The new String("...") constructor explicitly mandates the creation of a new object instance on the Heap memory space, while the string literal syntax leverages the String Constant Pool (SCP) for object reuse, leading to different memory addresses even if the content is identical.

Q: When should I ever use String s = new String()

ANS: Generally, you should avoid it. The only compelling, though rare, reason is if you explicitly require a distinct object on the Heap that is not pooled, or if you need to pass a known literal content into a constructor that performs other initialization logic (which is discouraged due to string immutability).

Q: What happens when calling intern() on a new String object

ANS: Calling .intern() on a String object residing on the Heap causes the JVM to check the SCP. If a matching string exists, the Heap object’s reference is updated to point to the SCP object. If it does not exist, the string is added to the SCP, and its reference is returned.

Q: Is it safe to use == for String comparison

ANS: No, it is unsafe for general content comparison. == tests object identity (memory address). Use the .equals() method to reliably compare the actual character content of two strings.
