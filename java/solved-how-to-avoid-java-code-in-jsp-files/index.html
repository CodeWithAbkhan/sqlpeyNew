“Solved: How to Avoid Java Code in JSP Files”

The disadvantages of relying on scriptlets are significant:

  • Reusability Challenges: Code within scriptlets is difficult to reuse across different JSP pages without extensive copy-pasting.
  • Replaceability Issues: Scriptlet code is inherently concrete, making it challenging to abstract or swap out implementations.
  • Object-Oriented Impediments: Scriptlets do not naturally support object-oriented principles like inheritance or composition, limiting architectural flexibility.
  • Debugging Difficulties: Exceptions thrown within scriptlets can lead to blank pages or obscure error messages, making debugging a cumbersome process.
  • Limited Testability: Scriptlet logic is tightly coupled with the JSP rendering cycle, making it difficult to unit test independently.
  • Maintenance Overhead: Mingled presentation and business logic result in cluttered, duplicated, and hard-to-maintain codebases.

Even Sun Oracle’s JSP coding conventions recommend avoiding scriptlets whenever equivalent functionality is available through tag libraries or Expression Language (EL). The JSP 1.2 Specification strongly suggests using the JSP Standard Tag Library (JSTL) to reduce scriptlet usage, stating that “pages that use JSTL are, in general, easier to read and maintain.” This guidance emphasizes separating business logic from presentation logic and evolving pages towards the JSP 2.0 style, which de-emphasizes scriptlets.

The complete replacement of scriptlets depends entirely on the purpose of the embedded Java code. Often, this logic should be refactored into dedicated Java classes.

Strategic Replacements for JSP Scriptlets

Several architectural patterns and technologies offer robust alternatives to scriptlets:

1. Utilizing Filters for Request-Agnostic Logic

For Java code that needs to execute on every incoming request, irrespective of the specific page, such as user authentication checks, a Servlet Filter is an ideal solution. This approach centralizes logic, preventing duplication across multiple JSP pages.

Example Filter for User Authentication:

import javax.servlet.*;
import javax.servlet.http.*;
import java.io.IOException;

public class SecurityCheckFilter implements Filter {

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) throws ServletException, IOException {
        HttpServletRequest httpRequest = (HttpServletRequest) req;
        HttpServletResponse httpResponse = (HttpServletResponse) res;

        // Check if a 'currentUser' attribute exists in the session
        if (httpRequest.getSession().getAttribute("currentUser") == null) {
            httpResponse.sendRedirect("loginPage"); // Not logged in, redirect to login page.
        } else {
            chain.doFilter(req, res); // User is logged in, continue processing the request.
        }
    }

    @Override
    public void init(FilterConfig filterConfig) throws ServletException {
        // Initialization code if needed
    }

    @Override
    public void destroy() {
        // Cleanup code if needed
    }
}

By mapping this filter to appropriate URL patterns in your web.xml (e.g., *.jsp or specific protected paths), you ensure every relevant request passes through this security check.

2. Processing GET Requests with Servlets

When Java code processes a GET request, like pre-loading data from a database to display in a table (potentially based on query parameters), a Servlet’s doGet() method is the suitable place. This separates data retrieval from presentation, making exception handling more manageable.

Example Servlet for Data Retrieval:

import javax.servlet.*;
import javax.servlet.http.*;
import java.io.IOException;
import java.sql.SQLException;
import java.util.List;
import com.example.model.ProductItem; // Assuming a ProductItem class
import com.example.service.ProductCatalogService; // Assuming a service class

public class ProductCatalogServlet extends HttpServlet {

    private ProductCatalogService itemService = new ProductCatalogService(); // Instantiate your service

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        try {
            List<ProductItem> productList = itemService.retrieveAll(); // Obtain all products from service
            req.setAttribute("catalogItems", productList); // Store products in request scope for JSP
            req.getRequestDispatcher("/WEB-INF/views/productListing.jsp").forward(req, resp); // Forward to JSP
        } catch (SQLException dbEx) {
            throw new ServletException("Failed to retrieve product items!", dbEx);
        }
    }
}

This ensures database access occurs before JSP rendering, allowing for proper error handling and redirection, such as displaying a custom error 500 page configured via <error-page> in web.xml.

3. Handling POST Requests with Servlets

For POST requests, typically used for processing submitted HTML forms, Servlet’s doPost() method is where form data is gathered, validated, converted, and persisted. This provides a clear path for handling success and error scenarios.

Example Servlet for Form Submission:

import javax.servlet.*;
import javax.servlet.http.*;
import java.io.IOException;
import com.example.model.SiteUser; // Assuming a SiteUser class
import com.example.service.UserService; // Assuming a user service

public class UserAuthServlet extends HttpServlet {

    private UserService userManager = new UserService(); // Instantiate user service

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        String inputUsername = req.getParameter("userNameField");
        String inputPassword = req.getParameter("passField");
        SiteUser foundUser = userManager.locateUser(inputUsername, inputPassword);

        if (foundUser != null) {
            req.getSession().setAttribute("loggedInUser", foundUser); // Login user by setting session attribute
            resp.sendRedirect("dashboard"); // Redirect to a protected home page
        } else {
            req.setAttribute("errorMessage", "Invalid credentials. Please try again."); // Store message
            req.getRequestDispatcher("/WEB-INF/views/loginForm.jsp").forward(req, resp); // Redisplay login with error
        }
    }
}

This pattern simplifies redirecting to different pages based on the outcome – either redisplaying the form with validation errors (accessible via ${errorMessage} in EL) or navigating to a success page.

4. Implementing a Front Controller Pattern

To manage the execution flow and request/response destination, implementing a Servlet as a Front Controller is a powerful approach, centralizing request handling and delegating to specific Action classes.

Example Front Controller Servlet:

import javax.servlet.*;
import javax.servlet.http.*;
import java.io.IOException;

public class CentralDispatcherServlet extends HttpServlet {

    @Override
    protected void service(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        try {
            // Assuming ActionFactory resolves an action based on request
            com.example.controller.WebAction currentAction = com.example.controller.ActionFactory.getAppropriateAction(req);
            String targetView = currentAction.execute(req, resp);

            if (targetView.equals(req.getPathInfo().substring(1))) { // Check if it's an internal forward
                req.getRequestDispatcher("/WEB-INF/views/" + targetView + ".jsp").forward(req, resp);
            } else {
                resp.sendRedirect(targetView); // External redirect
            }
        } catch (Exception processEx) {
            throw new ServletException("Action execution failed.", processEx);
        }
    }
}

Alternatively, adopting a full-fledged MVC framework like JSF, Spring MVC, or Apache Wicket can abstract away the need for custom servlets, allowing developers to work primarily with JSP/Facelets pages and JavaBeans.

5. Controlling JSP Flow with JSTL Core Tags

For managing control flow directly within a JSP page (e.g., loops, conditionals), use an existing flow control tag library like JSTL core. JSTL provides XML-style tags that integrate seamlessly with HTML, making the code much more readable and maintainable than scriptlets.

Example: Displaying a List with JSTL forEach:

<%@ taglib uri="http://java.sun.com/jsp/jstl/core" prefix="c" %>
<!-- ... other HTML ... -->
<table>
    <c:forEach items="${catalogItems}" var="singleItem">
        <tr>
            <td>${singleItem.itemName}</td>
            <td>${singleItem.itemDescription}</td>
            <td>${singleItem.itemPrice}</td>
        </tr>
    </c:forEach>
</table>

This approach eliminates the for loops or if statements typically found in scriptlets.

6. Displaying Backend Data with Expression Language (EL)

To access and display “backend” data directly within a JSP page, Expression Language (EL) is the preferred mechanism. EL expressions, enclosed in ${}, provide a concise way to access attributes from various scopes (page, request, session, application), implicit objects, and JavaBeans properties.

Example: Redisplaying Submitted Input with EL:

<input type="text" name="userNameField" value="${param.userNameField}" />

Here, ${param.userNameField} directly accesses the userNameField request parameter, equivalent to request.getParameter("userNameField").

7. Defining Custom EL Functions for Utility Operations

For invoking utility Java code (especially static methods) directly within a JSP, you can define them as EL functions. JSTL includes a standard fn (functions) tag library, but creating your own custom EL functions is also straightforward.

Example: Using JSTL fn:escapeXml for XSS Prevention:

<%@ taglib uri="http://java.sun.com/jsp/jstl/functions" prefix="fn" %>
<!-- ... other HTML ... -->
<input type="text" name="messageInput" value="${fn:escapeXml(param.messageInput)}" />

fn:escapeXml is crucial for preventing Cross-Site Scripting (XSS) attacks by escaping potentially malicious characters in user input. While XSS is a universal web security concern, scriptlets offer no built-in prevention. Facelets, JSP’s successor, implicitly handles HTML escaping, simplifying security.

Enforcing No Scriptlets: Safeguards and Modern Approaches

Disabling Scriptlets as a Safeguard

As a robust safeguard, you can globally disable scriptlets in your web application by configuring web.xml. This prevents any developer from accidentally or intentionally adding scriptlets to JSP files.

<jsp-config>
    <jsp-property-group>
        <url-pattern>*.jsp</url-pattern>
        <scripting-invalid>true</scripting-invalid>
    </jsp-property-group>
</jsp-config>

This configuration will cause a JasperException if any JSP attempts to use scriptlets. Facelets, the successor to JSP (part of JSF), already prohibits scriptlets, naturally enforcing the “right way” of development.

JSTL for Conditionals and Iterations

JSTL offers comprehensive tags for common programming constructs like conditionals (<c:if>, <c:choose>) and loops (<c:forEach>). These tags operate on request attributes, which are typically set by a Servlet that forwards to the JSP.

Example: JSTL Conditional Logic:

<c:if test="${userStatus == 'active'}">
   <p>Welcome, active user!</p>
</c:if>

Component-Based Frameworks

Frameworks like Apache Wicket generate significant portions of HTML for you. They promote an almost empty HTML page structure with very basic HTML elements, keeping logic separate. The trade-off is a learning curve for Wicket’s extensive component API.

JSP’s Role in MVC and Template Engines

In the MVC pattern, JSPs serve as the view layer. Embedding Java code directly is generally a bad practice. Technologies such as JSTL, Apache FreeMarker, and Apache Velocity can be used with JSP as powerful “template engines.” The data provided to these tags often comes from frameworks like Apache Struts 2, which uses OGNL (Object-Graph Navigation Language) to expose JavaBeans properties to JSPs.

Considering Modern Alternatives to JSP

While JSPs have their place, their shortcomings, especially regarding the difficulty of avoiding mixed markup and code, have led to the rise of specialized technologies. Java EE 6 introduced JSF 2.0, offering features like binding Java beans to JSF pages via #{bean.method(argument)} expressions.

Disciplined Approach with Minimal Scriptlets (Though Discouraged)

Even if strictly avoiding scriptlets isn’t feasible, a disciplined approach can minimize their impact. The goal is to keep Java logic in JSPs to an absolute minimum, focusing on variable assignments and view-specific data access, while heavy computation and business logic remain in controllers.

Example: Minimal Scriptlet Usage with a Controller:

<%@ page contentType="text/html;charset=UTF-8" language="java" %>
<% 
// Instantiate a JSP controller (example of poor separation if MyController is too heavy)
com.example.controllers.WebPageController viewController = new com.example.controllers.WebPageController(request, response);

// Process any actions or request data
viewController.handleRequest(request);

// Assign variables for display
String pageGreeting = viewController.getPageGreeting();
%>

<html>
    <head>
    </head>
    <body>
        <form name="mainForm">
            <p><%= pageGreeting %></p>
            <% for(String itemLabel : viewController.getListOfDisplayItems()) { %>
            <p><%= itemLabel %></p><% } %>
            <!-- More content -->
        </form>
    </body>
</html>

Even with this discipline, such an approach is highly discouraged in favor of JSTL and EL.

Mastering Custom Tags

Learning to customize and create your own tags using the JSTL framework is a powerful way to encapsulate complex logic and presentation patterns. While Expression Language (EL) is convenient, it can lead to runtime exceptions and refactoring difficulties due to its dynamic nature.

Example: Custom Tag Definition (web.xml and TLD):

web.xml entry:

<taglib>
    <taglib-uri>/utility_tags</taglib-uri>
    <taglib-location>/WEB-INF/custom-utility.tld</taglib-location>
</taglib>

/WEB-INF/custom-utility.tld (simplified):

<!DOCTYPE taglib
  PUBLIC "-//Sun Microsystems, Inc.//DTD JSP Tag Library 1.2//EN"
   "http://java.sun.com/dtd/web-jsptaglibrary_1_2.dtd">
<taglib xmlns="http://java.sun.com/JSP/TagLibraryDescriptor">
    <tlib-version>1.0</tlib-version>
    <jsp-version>1.2</jsp-version>
    <short-name>MyCustomTags</short-name>
    <tag>
        <name>processContent</name>
        <tag-class>com.example.tags.ContentProcessorTag</tag-class>
        <body-content>JSP</body-content>
        <attribute>
          <name>timesToRepeat</name>
        </attribute>
    </tag>
</taglib>

ContentProcessorTag.java:

package com.example.tags;

import java.io.IOException;
import javax.servlet.jsp.JspWriter;
import javax.servlet.jsp.tagext.BodyContent;
import javax.servlet.jsp.tagext.BodyTagSupport;

public class ContentProcessorTag extends BodyTagSupport {
    private int loopCount = 0;
    private int timesToRepeatValue;

    public void setTimesToRepeat(int i){
        this.timesToRepeatValue = i;
    }

    @Override
    public void setBodyContent(BodyContent bc){
        super.setBodyContent(bc);
        System.out.println("BodyContent read: '" + bc.getString() + "'");
    }

    @Override
    public int doAfterBody(){
        try{
            BodyContent bodyBuffer = super.getBodyContent();
            String bodyOutput  = bodyBuffer.getString();
            JspWriter outBuffer = bodyBuffer.getEnclosingWriter();

            if ( loopCount % 2 == 0 )
                outBuffer.print(bodyOutput.toLowerCase());
            else
                outBuffer.print(bodyOutput.toUpperCase());

            loopCount++;
            bodyBuffer.clear(); // Empty buffer for the next iteration
        }
        catch (IOException e) {
            System.err.println("Error in ContentProcessorTag.doAfterBody(): " + e.getMessage());
            e.printStackTrace();
        }

        int nextAction = SKIP_BODY;

        if ( loopCount < timesToRepeatValue )
            nextAction = EVAL_BODY_AGAIN;

        return nextAction;
    }
}

JSP usage:

<%@ taglib uri="/utility_tags" prefix="myutil" %>
<html>
    <head>
        <title>Custom Tag Demo</title>
    </head>
    <body>
        Demonstrating a custom tag:
        <ol>
            <myutil:processContent timesToRepeat="3">
            <li>Sample text item</li>
            </myutil:processContent>
        </ol>
    </body>
</html>

Modern Template Engines

Many modern Java web applications opt for template engines like Apache Velocity, Apache FreeMarker, or Thymeleaf. These engines offer clear separation of presentation logic and do not allow arbitrary Java code within templates, promoting a cleaner MVC structure.

Frontend JavaScript Frameworks

For complete decoupling of the view from the server-side, consider using a client-side JavaScript framework like Angular, React, or Vue.js. These frameworks render the UI in the browser and fetch data via REST APIs, making the Java backend purely a data and service provider, eliminating Java code from the frontend completely.

JSP 2.0 Tag Files

JSP 2.0 introduced “Tag Files” (.tag extension), enabling the creation of custom tags without external Java code or TLDs (Tag Library Descriptors). These files reside in WEB-INF/tags and can be organized into directories for better structure. They are auto-compiled and changes usually don’t require a server restart, speeding up development.

Example: Simple Label Tag File (/WEB-INF/tags/html/infoLabel.tag):

<%@tag description="Renders a label with a specific CSS class" pageEncoding="UTF-8"%>
<%@attribute name="labelText" required="true" description="The text for the label"%>&gt;

<label class="display-control-label default-style"  id="${labelText}DisplayLabel">${labelText}</label>

Usage in JSP:

<%@ taglib prefix="ui" tagdir="/WEB-INF/tags/html"%>
<ui:infoLabel  labelText="Customer Name" />

Tag files also support including their body content using <jsp:doBody/>:

Example: Bold Text Tag File (/WEB-INF/tags/html/boldText.tag):

<%@tag description="Applies bold formatting to its body content" pageEncoding="UTF-8"%>
<b>
  <jsp:doBody/>
</b>

Usage in JSP:

<%@ taglib prefix="ui" tagdir="/WEB-INF/tags/html"%>
<ui:boldText>This text will be bolded</ui:boldText>

Tag files are highly flexible, allowing the use of JSTL, EL, and passing various parameters, including complex objects like HashMaps. They significantly reduce HTML code duplication and enhance maintainability.

The Reality of Java in JSPs

It’s important to acknowledge that JSPs are, at their core, Java technologies for rendering dynamic HTML. You cannot truly write a meaningful JSP with “no Java.” The aim is to minimize direct Java scriptlet usage (<% %>) in favor of structured, maintainable alternatives like JSTL tags, EL, and properly designed JavaBeans. The capability to embed Java exists for specific, rare use cases where the complexity of refactoring into a full class or custom tag outweighs the benefits for a truly unique, page-specific requirement. Such instances should be minimal and justifiable.

In summary, separating presentation logic from business logic is paramount. Leverage Servlets for controller logic, and utilize JSTL, Expression Language, and custom tags for clean, maintainable view rendering. For projects seeking even greater separation, consider frameworks like JSF, Wicket, or modern JavaScript frontends with REST APIs.

FAQs on How to Avoid Java Code in JSP Files

Q: Why are Java scriptlets in JSP discouraged

ANS: Java scriptlets are discouraged due to issues with reusability, testability, debuggability, maintainability, and poor adherence to object-oriented principles, leading to cluttered code and difficulty in separating concerns.

Q: What is the primary alternative to scriptlets for control flow in JSP

ANS: The primary alternative for control flow (like loops and conditionals) in JSP is the JSP Standard Tag Library JSTL Core.

Q: How can I display data from the backend in JSP without scriptlets

ANS: You can display data using Expression Language EL which allows direct access to attributes in various scopes and JavaBean properties.

Q: What is the role of Servlets in avoiding Java code in JSP

ANS: Servlets act as controllers handling business logic, data processing, and request routing, setting attributes that JSPs then consume using EL or JSTL, thus keeping Java code out of the JSP view.

Q: Can I completely disable scriptlets in my web application

ANS: Yes, you can disable scriptlets globally by adding a scripting-invalid configuration to your web.xml file, which will cause an error if scriptlets are used.

Q: What are custom tags and how do they help

ANS: Custom tags are reusable UI components or logic encapsulated in XML-like tags. They help by abstracting complex Java code and presentation logic into a cleaner, more maintainable format that integrates well with HTML.

Q: Are there other frameworks that promote separation of concerns in Java web development

ANS: Yes, frameworks like JSF Spring MVC Apache Wicket and templating engines such as Apache FreeMarker and Thymeleaf promote a strong separation between logic and presentation. Frontend JavaScript frameworks like Angular or React offer full UI decoupling via REST APIs.

Q: What are JSP Tag Files and why use them

ANS: JSP Tag Files are a feature introduced in JSP 20 that allows you to create custom tags directly in .tag files without needing separate Java classes or TLDs. They are easy to develop, improve reusability, and help minimize HTML code duplication.
