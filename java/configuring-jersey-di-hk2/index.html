“Configuring Dependency Injection in JAX-RS with Jersey and HK2”

When building RESTful services using JAX-RS (like Jersey), providing services and managing component lifecycles is crucial. How does one effectively integrate dependency injection (DI) mechanisms, such as HK2 or CDI, to facilitate the injection of services into JAX-RS resources? Various strategies exist, ranging from explicit binding to leveraging container features.

Primary Approach: Defining and Registering an AbstractBinder

The foundational method involves explicitly defining how your dependencies should be instantiated and registered within your JAX-RS application configuration. This utilizes Jersey’s built-in HK2 binding mechanism.

How do you explicitly map an implementation class to its type using an AbstractBinder?

You create a class extending AbstractBinder and override the configure() method to specify the bindings.

// Custom Binder Implementation
public class AppDependencyBinder extends AbstractBinder {
    @Override
    protected void configure() {
        // Binds MyServiceImpl to the MyService interface/type
        bind(MyServiceImpl.class).to(MyService.class);
    }
}

Where is this binder registered within the JAX-RS application setup?

This binder must be registered within the configuration class that extends ResourceConfig. This same class is often referenced in your web.xml file.

// JAX-RS Application Configuration
public class JerseyApplicationConfig extends ResourceConfig {
    public JerseyApplicationConfig() {
        // 1. Register the custom dependency binder
        register(new AppDependencyBinder());
        
        // 2. Specify packages to scan for REST resources (e.g., classes annotated with @Path)
        packages(true, "com.mypackage.rest.resources");
    }
}

This configuration must then be linked in web.xml so the servlet container knows which application class to use:

<!-- web.xml Configuration Snippet -->
<servlet>
  <servlet-name>RestAppServlet</servlet-name>
  <servlet-class>org.glassfish.jersey.servlet.ServletContainer</servlet-class>
  <init-param>
    <param-name>javax.ws.rs.Application</param-name>
    <param-value>com.mypackage.JerseyApplicationConfig</param-value>
  </init-param>
  <load-on-startup>1</load-on-startup>
</servlet>
<servlet-mapping>
  <servlet-name>RestAppServlet</servlet-name>
  <url-pattern>/api/*</url-pattern>
</servlet-mapping>

Controlling Dependency Scope

When using bind(implementation).to(contract), the default scope for instantiated objects is PerLookup. How can we adjust the lifecycle of injected components?

Scopes can be explicitly defined using .in():

  • Singleton Scope: To ensure only one instance exists across the application lifetime: 
    bind(MyServiceImpl.class).to(MyService.class).in(Singleton.class);
  • Request Scope: To create a new instance for every incoming request: 
    // Alternatively, binding an instance directly results in a singleton by default:
// bind(somePreInstantiatedObject).to(MyService.class);
    The RequestScoped annotation is also relevant if using CDI integration (see Solution 4).

Advanced Binding: Using Factories

For situations requiring more complex object creation logic, factories provide the necessary mechanism, even allowing access to request context information via annotations like @Context.

How do you inject context-dependent objects using a Factory?

Implement the Factory<T> interface.

public class RequestAwareServiceFactory implements Factory<MyService> {
    @Context
    private HttpHeaders headers; // Access request headers directly

    @Override
    public MyService provide() {
        // Create service instance based on request context
        return new MyService(headers.getHeaderString("X-Custom-Request-Header"));
    }

    @Override
    public void dispose(MyService service) { 
        // Cleanup logic if necessary (often left empty)
    }
}

Register the factory in your AbstractBinder:

register(new AbstractBinder() {
    @Override
    public void configure() {
        bindFactory(RequestAwareServiceFactory.class)
            .to(MyService.class)
            .in(RequestScoped.class); // Specify factory-created instance scope
    }
});

Integrating with CDI and Avoiding Manual Binders

Maintaining manual bindings in an AbstractBinder can become cumbersome, especially in large applications. Can we leverage existing CDI providers (like Weld) to handle injection automatically?

Option A: Using CDI Features for Automatic Discovery

If you integrate CDI, Jersey can often discover and manage bindings automatically.

  1. Include CDI Container Dependency: For Tomcat or similar containers, adding a specific CDI integration artifact is often necessary:

    <!-- Example Maven Dependency for CDI bridge -->
<dependency>
    <groupId>org.glassfish.jersey.containers.glassfish</groupId>
    <artifactId>jersey-gf-cdi</artifactId>
    <version>${jersey.version}</version>
</dependency>

  2. CDI Scoping in Resources: Ensure your resources are managed by the DI container. Annotating the resource class with a scope (like @RequestScoped) often enables injection discovery:

    @RequestScoped // Essential for CDI to manage lifecycle
@Path("/endpoint")
public class MyResource {
    @Inject
    SomeManagedBean bean; // Injected via CDI mechanism

    // ... REST methods
}

Option B: Registering a Feature to Inject the Binder

If direct CDI integration isn’t automatic via scanning, you can use a Feature annotated with @Provider. The container scans for @Provider classes and registers them.

import javax.ws.rs.core.Feature;
import javax.ws.rs.core.FeatureContext;
import javax.ws.rs.ext.Provider;

@Provider // Allows Jersey to discover this Feature
public class HK2FeatureRegistrar implements Feature {

    @Override
    public boolean configure(FeatureContext context) {
        // Automatically registers the binder defined elsewhere (e.g., AppBinder)
        context.register(new AppBinder()); 
        return true;
    }
}

This Feature can also be explicitly registered in web.xml via jersey.config.server.provider.classnames.

Option C: Relying on CDI Annotations Only (Oracle Recommendation Context)

If you have a fully functional CDI environment set up (like in Java EE environments), sometimes simply ensuring all injectable types (including services) are CDI beans is sufficient, often requiring the @Path annotation on all types intended for injection, even if they aren’t technically resources themselves (though this might generate warnings).

@Singleton
@Path("singleton-config") // Adding @Path as suggested in some contexts
public class ConfigurationService {
  // ...
}

@Path("my-api")
class ApiProvider {
  @Inject ConfigurationService config; // Injected via CDI/HK2
  // ...
}

Alternative DI Frameworks

Should you prefer another DI framework like Guice, an adapter library like guice-bridge-jit-injector can be employed to bridge Guice with Jersey’s HK2 injection needs, preventing the necessity of defining every binding in HK2 directly.

Essential Dependencies for Servlet Container Use

If running Jersey within a servlet container like Tomcat, ensure you have the necessary artifacts for servlet handling and HK2 integration:

<dependency>
    <groupId>javax.ws.rs</groupId>
    <artifactId>javax.ws.rs-api</artifactId>
    <version>2.1</version>
</dependency>
<dependency>
    <groupId>org.glassfish.jersey.containers</groupId>
    <artifactId>jersey-container-servlet</artifactId>
    <version>${jersey-version}</version>
</dependency>
<dependency>
    <groupId>org.glassfish.jersey.inject</groupId>
    <artifactId>jersey-hk2</artifactId>
    <version>${jersey-version}</version>
</dependency>
<!-- If using CDI -->
<dependency>
    <groupId>org.glassfish.jersey.ext.cdi</groupId>
    <artifactId>jersey-cdi1x</artifactId>
    <version>${jersey-version}</version>
</dependency>

FAQs on Configuring Jersey DI HK2

Q: What is the default scope when binding a class in AbstractBinder

ANS: The default scope when using bind(Class).to(Class) without specifying scope is PerLookup.

Q: Can I make my service a singleton using AbstractBinder

ANS: Yes, chain the binding command with .in(Singleton.class).

Q: Does registering classes via packages() also register my AbstractBinder

ANS: No, the packages() method scans for JAX-RS providers/resources (like those annotated with @Path or @Provider), but explicit registration via context.register() or registering the Binder implementation directly in ResourceConfig is needed for the Binder itself.
