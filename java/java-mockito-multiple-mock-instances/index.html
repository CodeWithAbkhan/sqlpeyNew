“Java Mockito: Resolve Multiple Mock Instances & Null Pointer Issues”

Encountering scenarios where your Mockito mocks aren’t behaving as expected, leading to NullPointerException or default return values instead of your stubbed behavior, is a common hurdle in Java unit testing. This often stems from a misunderstanding of how mocks function as distinct objects and how they are managed within your test setup.

The core issue typically lies in having two or more separate instances of your mock. Your test code might be interacting with one instance, while the class you’re testing (the “class under test”) is inadvertently using a different, uninitialized, or unintended instance. This can also occur if your class under test is directly instantiating dependencies using new rather than receiving them via injection or parameters.

The Problem: Classes Versus Instances

When you call Mockito.mock(SomeClass.class), you are not modifying the SomeClass itself. Instead, you are creating a new, distinct instance of a mock object that behaves like SomeClass. This mock instance must then be explicitly provided to the parts of your code that need it. This could be by passing it as a method argument or injecting it as a dependency.

The @Mock annotation in Mockito also generates a new mock object instance. This instance is then assigned to the field annotated with @Mock. Crucially, this assigned mock object still needs to be integrated into your class under test.

Consider the new keyword in Java. Each time new is used, memory is allocated for a new object, and an instance of that specific class is initialized. Mockito, powerful as it is, cannot magically alter the behavior of a new operation once the object has been instantiated.

Strategies for Effective Mocking

To resolve these issues, it’s vital to design your classes for testability. This means avoiding direct instantiation of dependencies within the class and instead opting for ways to supply these dependencies from the outside.

Here are several common approaches:

1. Modifying Method Signatures to Accept Mock Instances

If you have the flexibility to alter the method signature, you can pass the mock instance directly as a parameter. This ensures the intended mock is used at the point of execution. However, this approach requires that the instance is available at every call site.

Example:

// Class under test
public class DataProcessor {
    public String processData(java.util.Random randomGenerator) {
        return "Processed: " + randomGenerator.nextInt();
    }
}

// Test class
import org.junit.jupiter.api.Test;
import org.mockito.Mockito;
import static org.junit.jupiter.api.Assertions.assertEquals;

public class DataProcessorTest {
    @Test
    void testProcessDataWithExternalRandom() {
        // Create a mock instance of Random
        java.util.Random mockRandom = Mockito.mock(java.util.Random.class);
        // Stub the mock's behavior
        Mockito.when(mockRandom.nextInt()).thenReturn(123);

        // Instantiate the class under test
        DataProcessor processor = new DataProcessor();

        // Call the method, passing the mock
        String result = processor.processData(mockRandom);

        assertEquals("Processed: 123", result);
    }
}

Using Mockito Extension (JUnit 5):

import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;
import static org.junit.jupiter.api.Assertions.assertEquals;

@ExtendWith(MockitoExtension.class)
public class DataProcessorTestAnnotated {
    // Mock instance is automatically created and assigned to this field
    @Mock
    private java.util.Random mockRandom;

    @Test
    void testProcessDataWithAnnotatedMock() {
        // Stub the mock's behavior
        Mockito.when(mockRandom.nextInt()).thenReturn(456);

        // Instantiate the class under test
        DataProcessor processor = new DataProcessor();

        // Call the method, passing the annotated mock
        String result = processor.processData(mockRandom);

        assertEquals("Processed: 456", result);
    }
}
2. Constructor Dependency Injection

A more robust pattern is to inject dependencies through the class constructor. This ensures that the class always receives its dependencies upon creation, and you can easily provide mock objects during testing.

Example:

// Class under test
public class CalculationService {
    private final java.util.concurrent.atomic.AtomicInteger counter;

    // Constructor injection
    public CalculationService(java.util.concurrent.atomic.AtomicInteger counter) {
        this.counter = counter;
    }

    // Optional: Constructor for production use
    public CalculationService() {
        this(new java.util.concurrent.atomic.AtomicInteger(0));
    }

    public int getNextValue() {
        return counter.incrementAndGet();
    }
}

// Test class
import org.junit.jupiter.api.Test;
import org.mockito.Mockito;
import static org.junit.jupiter.api.Assertions.assertEquals;

public class CalculationServiceTest {
    @Test
    void testGetServiceNextValue() {
        // Create a mock instance for AtomicInteger
        java.util.concurrent.atomic.AtomicInteger mockCounter = Mockito.mock(java.util.concurrent.atomic.AtomicInteger.class);
        // Stub the mock's behavior
        Mockito.when(mockCounter.incrementAndGet()).thenReturn(789);

        // Instantiate the class under test, injecting the mock
        CalculationService service = new CalculationService(mockCounter);

        // Call the method
        int value = service.getNextValue();

        assertEquals(789, value);
    }
}

Using Mockito Extension (JUnit 5):

import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;
import static org.junit.jupiter.api.Assertions.assertEquals;

@ExtendWith(MockitoExtension.class)
public class CalculationServiceTestAnnotated {
    @Mock
    private java.util.concurrent.atomic.AtomicInteger mockCounter;

    @Test
    void testGetServiceNextValueAnnotated() {
        // Stub the mock's behavior
        Mockito.when(mockCounter.incrementAndGet()).thenReturn(1011);

        // Instantiate the class under test, injecting the annotated mock
        CalculationService service = new CalculationService(mockCounter);

        // Call the method
        int value = service.getNextValue();

        assertEquals(1011, value);
    }
}
3. Abstract Factory Pattern for Delayed Construction

When a dependency must be instantiated only when a method is called, you can introduce an intermediate layer of indirection using an abstract factory. This factory can then be implemented to return either the real dependency or a test double (like a mock) during tests.

Example:

// Custom factory interface
@FunctionalInterface
public interface ValueGeneratorFactory {
    java.util.concurrent.atomic.AtomicInteger create();
}

// Class under test
public class DynamicValueService {
    private final ValueGeneratorFactory generatorFactory;

    public DynamicValueService(ValueGeneratorFactory generatorFactory) {
        this.generatorFactory = generatorFactory;
    }

    // Optional: Constructor for production
    public DynamicValueService() {
        this(java.util.concurrent.atomic.AtomicInteger::new);
    }

    public int getCurrentDynamicValue() {
        // Factory creates the instance when needed
        return generatorFactory.create().get();
    }
}

// Test class
import org.junit.jupiter.api.Test;
import org.mockito.Mockito;
import static org.junit.jupiter.api.Assertions.assertEquals;

public class DynamicValueServiceTest {
    @Test
    void testGetValueWithFactory() {
        // Create a mock for AtomicInteger
        java.util.concurrent.atomic.AtomicInteger mockAtomicInt = Mockito.mock(java.util.concurrent.atomic.AtomicInteger.class);
        // Stub the mock's behavior
        Mockito.when(mockAtomicInt.get()).thenReturn(2023);

        // Create a factory that returns the mock
        ValueGeneratorFactory mockFactory = () -> mockAtomicInt;

        // Instantiate the service with the mock factory
        DynamicValueService service = new DynamicValueService(mockFactory);

        // Call the method
        int value = service.getCurrentDynamicValue();

        assertEquals(2023, value);
    }
}

Using Mockito Extension (JUnit 5):

import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.Mock;
import org.mockito.Mockito;
import org.mockito.junit.jupiter.MockitoExtension;
import static org.junit.jupiter.api.Assertions.assertEquals;

@ExtendWith(MockitoExtension.class)
public class DynamicValueServiceTestAnnotated {
    @Mock
    private ValueGeneratorFactory mockFactory;

    @Test
    void testGetValueWithAnnotatedFactory() {
        // Create a mock for AtomicInteger
        java.util.concurrent.atomic.AtomicInteger mockAtomicInt = Mockito.mock(java.util.concurrent.atomic.AtomicInteger.class);
        // Stub the mock's behavior
        Mockito.when(mockAtomicInt.get()).thenReturn(3034);

        // Stub the factory to return the mock AtomicInteger
        Mockito.when(mockFactory.create()).thenReturn(mockAtomicInt);

        // Instantiate the service with the annotated mock factory
        DynamicValueService service = new DynamicValueService(mockFactory);

        // Call the method
        int value = service.getCurrentDynamicValue();

        assertEquals(3034, value);
    }
}

Pitfalls with @InjectMocks

The @InjectMocks annotation is designed to simplify dependency injection in tests. However, it’s a common source of confusion if not used correctly.

If you annotate a field with @InjectMocks and then manually reassign that field within your test method (e.g., myObject = Mockito.mock(MyClass.class);), you create a mismatch. @InjectMocks injects the original mock instance created by Mockito into your class under test. If you then reassign the test class’s field, you’re pointing it to a different mock instance that your class under test doesn’t know about.

Problematic Code Example:

@ExtendWith(MockitoExtension.class)
public class IncorrectInjectMocksTest {
    @Mock
    private java.util.Random dependencyMock;

    @InjectMocks
    private DataProcessor processor; // Mockito injects the 'dependencyMock' here

    @Test
    void testProcessorWithIncorrectMockReassignment() {
        // PROBLEM: This line creates a NEW mock and overwrites 'dependencyMock'
        // The 'processor' object still holds the OLD mock instance from @InjectMocks.
        dependencyMock = Mockito.mock(java.util.Random.class);
        Mockito.when(dependencyMock.nextInt()).thenReturn(555);

        // If processor uses 'dependencyMock', it's the old, unconfigured one.
        // This will likely lead to NullPointerException or default behavior.
        // Assertions.assertEquals("Processed: 555", processor.processData(dependencyMock)); // Incorrect usage
    }
}

The solution is to directly configure the mock that @InjectMocks provides, rather than reassigning the field.

Corrected Code Example:

@ExtendWith(MockitoExtension.class)
public class CorrectInjectMocksTest {
    @Mock
    private java.util.Random dependencyMock;

    @InjectMocks
    private DataProcessor processor;

    @Test
    void testProcessorWithCorrectMockConfiguration() {
        // CORRECT: Configure the existing 'dependencyMock'
        Mockito.when(dependencyMock.nextInt()).thenReturn(777);

        // Now, 'processor' correctly uses the configured 'dependencyMock'
        // Assertions.assertEquals("Processed: 777", processor.processData(dependencyMock));
    }
}

A similar issue arises if you manually call MockitoAnnotations.openMocks(this) within a @BeforeEach or @Before method while also using @ExtendWith(MockitoExtension.class) or @RunWith(MockitoJUnitRunner.class). These annotations typically handle the opening of mocks automatically. Redundant calls can lead to the same reassignment problem. Either rely on the runner/extension or use MockitoAnnotations.openMocks explicitly, but not both.

Object Lifecycles and Initialization Order

Another common pitfall involves the order of object creation and initialization, especially when mixing manual setup with framework annotations.

Consider this scenario:

@ExtendWith(MockitoExtension.class)
public class LifecycleIssueTest {
    @Mock
    private java.util.Random mockRandom;

    // PROBLEM: obj is initialized BEFORE @Mock gets assigned,
    // so it receives a 'null' for mockRandom.
    private final DataProcessor processor = new DataProcessor(mockRandom);

    @Test
    void testWithLifecycleIssue() {
        Mockito.when(mockRandom.nextInt()).thenReturn(888);
        // This will likely fail with NPE because processor was created with null.
        // Assertions.assertEquals("Processed: 888", processor.processData(mockRandom));
    }
}

In this case, the test class instance is created by the testing framework. Field initializers run next. The processor is instantiated using new DataProcessor(mockRandom). At this point, mockRandom is still null because the Mockito extension hasn’t yet processed the @Mock annotation. The processor is initialized with a null dependency. Later, the extension assigns a mock object to mockRandom, but this doesn’t retroactively update the processor instance.

Resolution:

To fix this, ensure that dependencies are initialized after mocks are available. Move the instantiation of your class under test into a setup method annotated with @BeforeEach (JUnit 5) or @Before (JUnit 4).

Corrected Initialization Order:

@ExtendWith(MockitoExtension.class)
public class CorrectLifecycleTest {
    @Mock
    private java.util.Random mockRandom;

    private DataProcessor processor;

    @BeforeEach
    void setup() {
        // Initialize processor after mockRandom is available
        processor = new DataProcessor(mockRandom);
    }

    @Test
    void testWithCorrectLifecycle() {
        Mockito.when(mockRandom.nextInt()).thenReturn(999);
        Assertions.assertEquals("Processed: 999", processor.processData(mockRandom));
    }
}

Alternatively, you can perform all setup manually without relying on @ExtendWith or @RunWith, managing both mock creation and class instantiation in your setup method:

Manual Setup:

public class ManualSetupTest {
    private java.util.Random mockRandom;
    private DataProcessor processor;

    @BeforeEach
    void setup() {
        mockRandom = Mockito.mock(java.util.Random.class);
        processor = new DataProcessor(mockRandom);
    }

    @Test
    void testWithManualSetup() {
        Mockito.when(mockRandom.nextInt()).thenReturn(111);
        Assertions.assertEquals("Processed: 111", processor.processData(mockRandom));
    }
}

By carefully managing mock instances and their lifecycle within your tests, you can effectively isolate your code and ensure reliable unit tests.

FAQs on Java Mockito Issues

Q: Why do my mock methods return null or default values when using Mockito

ANS: This typically occurs because the mock instance used by your class under test is different from the mock instance you are configuring in your test. Ensure your mocks are correctly injected or passed to the class under test. Avoid creating new mock instances within the test method after the class under test has already been initialized with a different mock or null.

Q: How to fix NullPointerException when using @InjectMocks

ANS: The NullPointerException with @InjectMocks often happens when you reassign the mocked field after @InjectMocks has already injected the dependency. Instead of reassigning the field, use Mockito’s when() to configure the behavior of the existing injected mock object. Ensure your dependencies are correctly marked with @Mock.

Q: Can I mock classes created with 'new' keyword inside the tested class

ANS: Directly mocking classes that internally use the new keyword to create their dependencies is not possible with standard Mockito. To make such classes testable, you need to refactor them to accept dependencies via constructor injection or method parameters, allowing you to provide mock objects externally.

Q: What is the difference between @Mock and @InjectMocks

ANS: @Mock creates a mock object instance for a specified class. @InjectMocks injects the dependencies (often created by @Mock) into the annotated object, typically your class under test. You use @Mock to create mocks and @InjectMocks to automatically inject them into your test subject.

Q: How to handle dependencies that are instantiated only when a method is called

ANS: For dependencies created lazily within a method, consider the Abstract Factory pattern. Introduce a factory interface or a functional interface (like Supplier) that creates the dependency. You can then mock this factory and configure it to return your mock dependency when its creation method is called within the test.
