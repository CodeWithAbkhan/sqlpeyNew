“Resolving Deprecated Java EE Modules in Modern Java Environments”

How does one substitute these deprecated Java EE modules with appropriate external artifacts to ensure application functionality across contemporary Java runtimes?

Solution Set for Replacing Removed Java Modules

The accepted solutions point toward utilizing artifacts associated with the Jakarta EE platform, which absorbed many Java EE specifications. Here are the verified dependency replacements, typically formatted for a Maven pom.xml.

1. Jakarta Activation (Replacing java.activation)

The JavaBeans Activation Framework (JAF), now known as Jakarta Activation, is available as a standalone component via Maven Central.

<dependency>
    <groupId>com.sun.activation</groupId>
    <artifactId>jakarta.activation</artifactId>
    <version>1.2.2</version>
</dependency>

2. CORBA and RMI-IIOP (java.corba and RMI-IIOP)

As per documentation (JEP 320), there is currently no standalone version provided for CORBA unless third parties undertake its maintenance. Similarly, RMI-IIOP will not receive a standalone version without a dedicated JSR or stewardship transfer (e.g., to the Eclipse Foundation). This area often requires investigation into specific third-party library support if direct use is mandatory.

3. Jakarta Transaction (Replacing java.transaction)

The Java Transaction API (JTA) specification has a standalone implementation available:

<dependency>
    <groupId>jakarta.transaction</groupId>
    <artifactId>jakarta.transaction-api</artifactId>
    <version>1.3.3</version>
</dependency>

4. Jakarta XML Binding (JAXB - Replacing java.xml.bind)

Since Java EE evolved into Jakarta EE, JAXB functionality is sourced through new artifacts. It is often necessary to include both the API and an implementation (runtime). Note that the older com.sun.xml.bind:jaxb-impl has seen recommendations for replacement.

API Dependency:

<dependency>
    <groupId>jakarta.xml.bind</groupId>
    <artifactId>jakarta.xml.bind-api</artifactId>
    <version>2.3.3</version>
</dependency>

Runtime Implementation Options:

  • Option A (Sun Implementation): 
    <dependency>
    <groupId>com.sun.xml.bind</groupId>
    <artifactId>jaxb-impl</artifactId>
    <version>2.3.3</version>
    <scope>runtime</scope>
</dependency>
  • Option B (GlassFish Implementation - Recommended Alternative): This is suggested as a substitute for the deprecated com.sun.xml.bind:jaxb-impl. 
    <dependency>
    <groupId>org.glassfish.jaxb</groupId>
    <artifactId>jaxb-runtime</artifactId>
    <version>2.3.3</version>
    <scope>runtime</scope>
</dependency>

Tools like schemagen and xjc can also be obtained from a standalone JAXB distribution.

5. Jakarta XML Web Services (JAX-WS - Replacing java.xml.ws)

For JAX-WS functionalities, the API and runtime implementation need to be specified separately:

API Dependency:

<dependency>
    <groupId>jakarta.xml.ws</groupId>
    <artifactId>jakarta.xml.ws-api</artifactId>
    <version>2.3.3</version>
</dependency>

Runtime Dependency:

<dependency>
    <groupId>com.sun.xml.ws</groupId>
    <artifactId>jaxws-rt</artifactId>
    <version>2.3.3</version>
</dependency>

A standalone distribution containing tools like wsgen and wsimport is available for download.

6. Common Annotations (Replacing java.xml.ws.annotation)

The Java Commons Annotations are available via Maven Central:

<dependency>
    <groupId>jakarta.annotation</groupId>
    <artifactId>jakarta.annotation-api</artifactId>
    <version>1.3.5</version>
</dependency>

Alternative Strategies and Version Specificity

The choice of versions is highly dependent on the JDK version and framework (like Spring Boot).

Strategy for JDK 9+ (Alternative JAXB 2.3.0): One approach tailored for early JDK 9 environments involved using javax.xml.bind artifacts alongside an activation dependency:

<properties>
    <jaxb-api.version>2.3.0</jaxb-api.version>
</properties>

<!-- JAXB 2.3.0 for jdk9+ -->
<dependency>
    <groupId>javax.xml.bind</groupId>
    <artifactId>jaxb-api</artifactId>
    <version>${jaxb-api.version}</version>
</dependency>
<dependency>
    <groupId>org.glassfish.jaxb</groupId>
    <artifactId>jaxb-runtime</artifactId>
    <version>${jaxb-api.version}</version>
</dependency>
<!-- JAXB requires javax.activation module (jdk9) -->
<dependency>
    <groupId>javax.activation</groupId>
    <artifactId>javax.activation-api</artifactId>
    <version>1.2.0</version>
</dependency>

Conditional Dependency Inclusion (Profile-Based Approach): For improved build clarity, dependencies can be scoped conditionally based on the target JDK version. For example, specifying JAXB runtime dependencies only when building against JDK 11 or later:

<profile>
    <id>when-on-jdk-11</id>
    <activation>
        <jdk>11</jdk>
    </activation>

    <properties>
        <jaxb-api.version>2.3.1</jaxb-api.version>
        <jaxb-impl.version>2.3.2</jaxb-impl.version>
    </properties>

    <dependencies>
        <!-- runtime dependencies to avoid JAXB related CNF exceptions when running on Java 11 -->
        <dependency>
            <groupId>javax.xml.bind</groupId>
            <artifactId>jaxb-api</artifactId>
            <version>${jaxb-api.version}</version>
            <scope>runtime</scope>
        </dependency>
        <dependency>
            <groupId>org.glassfish.jaxb</groupId>
            <artifactId>jaxb-runtime</artifactId>
            <version>${jaxb-impl.version}</version>
            <scope>runtime</scope>
        </dependency>
    </dependencies>
</profile>

Specific Replacements for Spring Boot 2 Applications: Developers using Spring Boot 2 have reported success by using specific combinations, including replacements for java.xml.ws and adding JSON processing libraries like Yasson:

// Gradle dependencies example
runtimeOnly 'javax.xml.ws:jaxws-api:2.3.0' // Replaces javax.xml.ws.*
runtimeOnly 'javax.jws:jsr181-api:1.0-MR1' // For javax.jws.* classes

// JAXB replacement for Spring Boot 2
runtimeOnly 'javax.xml.bind:jaxb-api'
runtimeOnly 'org.glassfish.jaxb:jaxb-runtime:2.3.0.1'
runtimeOnly 'org.glassfish:javax.json:1.1.2'
runtimeOnly 'org.eclipse:yasson:1.0.1'

Note that dependency selection, particularly version matching, can be delicate; one version change might break an expected transitive resolution.

SOAP API Inclusion (Talend/Older Environments): In environments like Talend, adding the SOAP API explicitly can resolve issues on various JDK versions (8, 11, 15):

<dependency>
    <groupId>javax.xml.soap</groupId>
    <artifactId>javax.xml.soap-api</artifactId>
    <version>1.4.0</version>
</dependency>

Dependency Management via dependencyManagement: For projects with multi-module structures, defining versions in a root dependencyManagement section and using scope: import can centrally manage the conflicting dependencies:

<project ...>
  <dependencyManagement>
    <dependencies>
      <!-- Central management for JAXB artifacts removed from JVM -->
      <dependency>
        <groupId>com.sun.xml.bind</groupId>
        <artifactId>jaxb-ri</artifactId>
        <version>2.4.0-b180830.0438</version>
        <scope>import</scope>
        <type>pom</type>
      </dependency>
      <!-- ... -->
    </dependencies>
  </dependencyManagement>
  <!-- ... -->

FAQs on Resolving Deprecated Java EE Modules

Q: Which Java EE modules are typically missing in JDK 9 and later

ANS: The modules commonly removed include java.activation, java.corba, java.transaction, java.xml.bind, and java.xml.ws.

Q: What is the primary replacement location for removed Java EE APIs

ANS: The primary replacement source is artifacts adhering to the Jakarta EE specifications, found under various namespaces like jakarta.xml.bind or jakarta.transaction.

Q: Is there a direct standalone replacement for CORBA in Java SE

ANS: Currently, there is no official standalone Java SE version for CORBA unless third parties take over maintenance or a new JSR is initiated.

Q: Should I use com.sun.xml.bind or org.glassfish.jaxb for JAXB runtime

ANS: While com.sun.xml.bind:jaxb-impl was used, many contemporary solutions suggest preferring org.glassfish.jaxb:jaxb-runtime as an alternative runtime implementation.

Q: How do I manage these dependencies across multiple modules

ANS: Using the <dependencyManagement> section in a parent POM file with <scope>import</scope> allows centralized version control for these critical, environment-dependent artifacts.
