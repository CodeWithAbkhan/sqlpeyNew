“Fixing JSON Infinite Recursion with Jackson: A Deep Dive”

Encountering a StackOverflowError due to infinite recursion during JSON serialization or deserialization is a common challenge when working with bidirectional relationships in Java, particularly with libraries like Jackson. This occurs when two objects mutually reference each other, leading Jackson’s serializer to endlessly traverse the object graph. This post explores a variety of proven techniques to address and prevent this persistent issue, providing practical code examples and explanations for each.

Solution 1: Leveraging @JsonIgnoreProperties

Introduced in a 2017 update, @JsonIgnoreProperties offers a flexible way to manage serialization and deserialization. You can use it to suppress the serialization of specific properties or ignore them during deserialization.

Consider a scenario with Trainee and BodyStat entities:

// Business Object 1: Trainee
@Entity
@Table(name = "ta_trainee", uniqueConstraints = {@UniqueConstraint(columnNames = {"id"})})
public class Trainee extends BusinessObject {

    @OneToMany(mappedBy = "trainee", fetch = FetchType.EAGER, cascade = CascadeType.ALL)
    // Use JsonIgnoreProperties to prevent infinite loop by ignoring 'trainee' in BodyStat during serialization
    @JsonIgnoreProperties("trainee")
    private Set<BodyStat> bodyStats;

    // ... other properties and methods
}

// Business Object 2: BodyStat
@Entity
@Table(name = "ta_bodystat", uniqueConstraints = {@UniqueConstraint(columnNames = {"id"})})
public class BodyStat extends BusinessObject {

    @ManyToOne(fetch = FetchType.EAGER, cascade = CascadeType.ALL)
    @JoinColumn(name = "trainee_fk")
    private Trainee trainee;

    // ... other properties and methods
}

This approach prevents the trainee object within BodyStat from being serialized, thus breaking the cycle.

Solution 2: Employing @JsonManagedReference and @JsonBackReference

Available since Jackson 1.6, these annotations provide a declarative way to manage bidirectional relationships. The idea is to designate one side of the relationship as the “managed” side (which will be serialized) and the other as the “back” reference (which will be ignored during serialization but re-established during deserialization).

Here’s how you’d apply them:

// Business Object 1: Trainee
@Entity
@Table(name = "ta_trainee", uniqueConstraints = {@UniqueConstraint(columnNames = {"id"})})
public class Trainee extends BusinessObject {

    @OneToMany(mappedBy = "trainee", fetch = FetchType.EAGER, cascade = CascadeType.ALL)
    @Column(nullable = true)
    // This is the "managed" side, it will be serialized
    @JsonManagedReference
    private Set<BodyStat> bodyStats;

    // ... other properties and methods
}

// Business Object 2: BodyStat
@Entity
@Table(name = "ta_bodystat", uniqueConstraints = {@UniqueConstraint(columnNames = {"id"})})
public class BodyStat extends BusinessObject {

    @ManyToOne(fetch = FetchType.EAGER, cascade = CascadeType.ALL)
    @JoinColumn(name = "trainee_fk")
    // This is the "back" reference, it will be ignored during serialization
    @JsonBackReference
    private Trainee trainee;

    // ... other properties and methods
}

This method effectively handles the infinite loop by ensuring that only one side of the relationship is serialized. For more insights, refer to articles on Jackson Stackoverflow issues .

Solution 3: Using @JsonIgnore

A simpler approach, @JsonIgnore, can be applied to the getter or field that causes the recursion. This annotation tells Jackson to omit that specific property during serialization.

// Example using @JsonIgnore on the getter
@ManyToOne(fetch = FetchType.EAGER)
@JoinColumn(name = "ID", nullable = false, updatable = false)
@JsonIgnore // This annotation prevents serialization of the 'member' field
private Member member;

Caution: While effective, @JsonIgnore can prevent necessary data from being serialized. If the foreign key data is crucial, this might not be the optimal solution.

Solution 4: Leveraging @JsonIdentityInfo

For Jackson 2.0 and later, @JsonIdentityInfo provides another robust way to handle cyclical references. It assigns a unique identifier to each object during serialization, preventing Jackson from re-processing already serialized objects.

// Trainee Entity with @JsonIdentityInfo
@Entity
@Table(name = "ta_trainee", uniqueConstraints = {@UniqueConstraint(columnNames = {"id"})})
@JsonIdentityInfo(generator = ObjectIdGenerators.IntSequenceGenerator.class, property = "@traineeId")
public class Trainee extends BusinessObject {
    // ...
}

// BodyStat Entity with @JsonIdentityInfo
@Entity
@Table(name = "ta_bodystat", uniqueConstraints = {@UniqueConstraint(columnNames = {"id"})})
@JsonIdentityInfo(generator = ObjectIdGenerators.IntSequenceGenerator.class, property = "@bodyStatId")
public class BodyStat extends BusinessObject {
    // ...
}

This is particularly useful for complex object graphs with multiple interdependencies. You can also use ObjectIdGenerators.PropertyGenerator.class with a specific property like “id” if your entities have a unique identifier field.

@Entity
@Table(name = "ta_trainee", uniqueConstraints = {@UniqueConstraint(columnNames = {"id"})})
@JsonIdentityInfo(generator = ObjectIdGenerators.PropertyGenerator.class, property = "id")
public class Trainee extends BusinessObject {
    // ...
}

Solution 5: Integrating jackson-module-hibernate

For projects heavily utilizing Hibernate, the jackson-datatype-hibernate module can simplify handling Hibernate-specific issues, including lazy initialization and cyclical references.

First, add the dependency to your pom.xml:

<dependency>
    <groupId>com.fasterxml.jackson.datatype</groupId>
    <artifactId>jackson-datatype-hibernate4</artifactId> <!-- Or hibernate5 -->
    <version>2.4.0</version> <!-- Use a compatible Jackson version -->
</dependency>

Then, register the Hibernate4Module (or Hibernate5Module) with your ObjectMapper:

import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.datatype.hibernate4.Hibernate4Module; // or Hibernate5Module

ObjectMapper mapper = new ObjectMapper();
mapper.registerModule(new Hibernate4Module());

This module is designed to manage common serialization pitfalls with Hibernate entities.

Solution 6: Explicitly Ignoring Fields with @JsonIgnoreProperties on Collections

When dealing with collections like Set or List in relationships, using @JsonIgnoreProperties on the collection field itself can be highly effective.

@Entity
public class Material {
    // ...
    @OneToMany(mappedBy = "material")
    @JsonIgnoreProperties("material") // Ignores the 'material' property in Supplier
    private List<Supplier> costSuppliers = new ArrayList<>();
    // ...
}

@Entity
public class Supplier {
    // ...
    @ManyToOne
    @JoinColumn(name = "material_id")
    @JsonIgnoreProperties("costSuppliers") // Ignores the 'costSuppliers' property in Material
    private Material material;
    // ...
}

This example from a blog post http://springquay.blogspot.com/2016/01/new-approach-to-solve-json-recursive.html demonstrates how to break the cycle by ignoring the back-reference.

Solution 7: Using @JsonView for Selective Serialization

@JsonView offers fine-grained control over which fields are serialized, making it a powerful tool for managing complex object graphs and preventing recursion. You define interfaces to act as “views” and annotate fields with the relevant view.

Consider Company and Employee with a circular dependency:

// Company Class
public class Company {
    @JsonView(Filter.CompanyData.class) // Only serialize if CompanyData view is active
    private Employee employee;

    // constructor, getters, setters
}

// Employee Class
public class Employee {
    private Company company; // No @JsonView, so it won't be serialized when EmployeeData view is active
    // constructor, getters, setters
}

// Filter Interfaces
public class Filter {
    public static interface EmployeeData {};
    public static interface CompanyData extends EmployeeData {};
}

When serializing, you specify the view:

// In your test or controller
ObjectMapper mapper = new ObjectMapper();
ObjectWriter writer = mapper.writerWithView(Filter.CompanyData.class);
String jsonCompany = writer.writeValueAsString(company);

This approach allows you to tailor the JSON output precisely, excluding fields that would cause recursion. This aligns with best practices for REST APIs where specific views are often needed. For related issues, see how to fix UnicodeEncodeError in Python .

Solution 8: Modifying Field Visibility with @JsonProperty(access = JsonProperty.Access.WRITE_ONLY)

This annotation makes a property write-only, meaning it will be ignored during serialization but still processed during deserialization.

@JsonProperty(access = JsonProperty.Access.WRITE_ONLY)
private Trainee trainee;

This is useful when you need to set the relationship during deserialization but do not want it included in the JSON output.

Solution 9: Adjusting Collections from Set to List with @JsonIgnore and @ToString.Exclude

In some scenarios, particularly when using Lombok, changing the collection type from Set to List and applying both @JsonIgnore and @ToString.Exclude can resolve recursion issues.

// Before (using Set)
@OneToMany(mappedBy = "client")
private Set<Address> addresses;

// After (using List and annotations)
@OneToMany(mappedBy = "client")
@JsonIgnore // Prevents JSON serialization
@ToString.Exclude // Prevents Lombok's toString from causing recursion
private List<Address> addresses;

@ManyToOne
@JoinColumn(name = "client_id", nullable = false)
@JsonIgnore
@ToString.Exclude
private Client client;

This combination addresses both Jackson serialization and Lombok’s toString() method, which can also contribute to stack overflows.

Solution 11: DTO Pattern for Controlled Serialization

A common and robust solution is to use Data Transfer Objects (DTOs). Instead of serializing your JPA entities directly, you map them to DTOs that contain only the necessary fields for the current serialization context. This inherently avoids serializing the back-references that cause recursion.

// Example: TraineeDTO without bidirectional reference
public class TraineeDTO {
    private Integer id;
    private String name;
    // Potentially a list of BodyStatDTOs, but not the Trainee object itself
}

// In your service or repository:
public TraineeDTO convertToTraineeDTO(Trainee trainee) {
    TraineeDTO dto = new TraineeDTO();
    dto.setId(trainee.getId());
    dto.setName(trainee.getName());
    // ... map other fields ...
    return dto;
}

Solution 12: Excluding Properties in @EqualsAndHashCode (Lombok)

When using Lombok’s @EqualsAndHashCode, be mindful of how it handles collections. To prevent StackOverflowError in hashCode() and equals() methods due to bidirectional relationships, exclude the collection properties:

@Entity
@Data // Lombok annotation
@EqualsAndHashCode(exclude = {"attributeOfTypeList", "attributeOfTypeSet"}) // Exclude problematic collections
public class MyEntity {
    private List<AnotherEntity> attributeOfTypeList;
    private Set<AnotherEntity> attributeOfTypeSet;
    // ...
}

This ensures that Lombok doesn’t get caught in an infinite loop when generating these methods. See also how to fix StackOverflowError in Python .

Solution 13: Entity Relationship Adjustments

Sometimes, a subtle change in the entity relationship mapping can resolve the issue. For instance, removing the mappedBy attribute or adjusting the fetch type might impact how Jackson traverses the graph.

// Original
@OneToMany(mappedBy = "county")
private List<Town> towns;

// Potentially adjusted
@OneToMany
private List<Town> towns;

@ManyToOne
@JoinColumn(name = "county_id")
private County county;

Experimentation with these annotations might be necessary for specific scenarios.

Solution 14: @JsonIgnoreProperties with Lombok and FetchMode.SUBSELECT

Combining @JsonIgnoreProperties with Lombok and ensuring proper handling of collections like Set can be crucial. If you encounter MultipleBagFetchException, switching from Set to List or using @Fetch(value = FetchMode.SUBSELECT) might help.

@Entity
@Data // Lombok
public class Foo extends BaseEntity {
    @OneToMany(fetch = FetchType.EAGER)
    @JoinColumn(name = "foo_id")
    @JsonIgnoreProperties("parentFoo") // Prevents recursion
    @EqualsAndHashCode.Exclude // Lombok exclusion
    private Set<Bar> linkedBars;
}

@Entity
@Data // Lombok
public class Bar extends BaseEntity {
    @Column(name = "foo_id")
    private Long parentFooId;

    @ManyToOne(fetch = FetchType.EAGER)
    @JoinColumn(name = "foo_id", insertable = false, updatable = false)
    @JsonIgnoreProperties({"linkedBars"}) // Prevents recursion
    private Foo parentFoo;
}

Solution 15: Constructor-Based Serialization Control

Without using annotations directly on entities, you can create constructors that deliberately omit the back-referencing fields. You can then use JPQL queries to select these specific constructors.

public class A {
    private int id;
    private String code;
    private String name;
    private List<B> bs; // This list might be omitted in the DTO-like constructor

    public A() {} // Default constructor

    // Constructor excluding the List<B>
    public A(int id, String code, String name) {
        this.id = id;
        this.code = code;
        this.name = name;
    }
}

// Query example: "select new A(id, code, name) from A"

If you’re using Spring Data Rest, creating specific repositories for each entity involved in cyclical references can help manage the serialization context and resolve issues.

Solution 17: Removing @XmlRootElement Annotation

In some instances, particularly with auto-generated JPA entities (e.g., from NetBeans), the presence of @XmlRootElement can interfere with Jackson’s processing. Removing this annotation can resolve unexpected serialization problems.

Solution 18: Placing @JsonIgnore on Setter Methods

Applying @JsonIgnore to the setter method of a collection can also break the serialization cycle.

// In Township.java
@Access(AccessType.PROPERTY)
@OneToMany(fetch = FetchType.LAZY)

    return villages;
}

@JsonIgnore // Applied to the setter

    this.villages = villages;

Solution 19: Combining @JsonBackReference and @ToString.Exclude with Overridden equals and hashCode

Ensure that if you override equals and hashCode methods, they correctly handle collections, potentially by using @ToString.Exclude (from Lombok) or by explicitly excluding collection fields. This, combined with @JsonBackReference, can effectively resolve infinite recursion.

FAQs on JSON Infinite Recursion with Jackson

Q: What causes JSON infinite recursion in Java with Jackson

ANS: Infinite recursion occurs when you have bidirectional relationships between Java objects (e.g., a parent object referencing child objects, and child objects referencing the parent back), and Jackson’s serializer attempts to serialize both sides of the relationship, leading to an endless loop and a StackOverflowError.

Q: Which annotations can help prevent JSON infinite recursion

ANS: Key annotations include @JsonIgnore, @JsonManagedReference, @JsonBackReference, @JsonIgnoreProperties, and @JsonIdentityInfo. Each offers a different strategy to control how Jackson traverses and serializes object relationships.

Q: Is @JsonIgnoreProperties better than @JsonIgnore

ANS: @JsonIgnoreProperties is generally more flexible as it can ignore multiple properties or entire classes during serialization/deserialization. @JsonIgnore is applied to a specific field or getter/setter. The choice depends on the scope of the problem you’re trying to solve.

Q: When should I use @JsonIdentityInfo

ANS: @JsonIdentityInfo is particularly useful for complex object graphs where multiple objects might reference the same object. It assigns a unique ID to each object, preventing Jackson from re-serializing already processed objects, thus avoiding recursion and maintaining object graph integrity.

Q: Can Lombok annotations interfere with Jackson serialization

ANS: Yes, Lombok’s @ToString and @EqualsAndHashCode can cause recursion if not configured correctly. Using @ToString.Exclude or @EqualsAndHashCode(exclude = {...}) on collection fields that participate in bidirectional relationships is recommended.

Q: What is the DTO pattern and how does it help

ANS: The DTO (Data Transfer Object) pattern involves creating separate classes that represent the data structure you want to expose, rather than serializing your domain entities directly. This allows you to exclude bidirectional references that would cause recursion, providing a cleaner API.

Q: How does @JsonManagedReference and @JsonBackReference work

ANS: @JsonManagedReference marks the “forward” side of a bidirectional relationship that should be serialized. @JsonBackReference marks the “back” side, which is ignored during serialization but restored during deserialization. This ensures only one direction of the relationship is serialized.
