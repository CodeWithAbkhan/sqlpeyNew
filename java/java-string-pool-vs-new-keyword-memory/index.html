“Java String Pool vs new Keyword Memory Allocation Differences Explained”

How does Java handle memory when creating String objects using literal assignment versus invoking the new String() constructor? This distinction directly impacts performance and object identity comparison (==).

When dealing with strings in Java, two primary instantiation methods present themselves, leading to different memory behaviors concerning the String Constant Pool (SCP).

The String Literal Approach: Leveraging the Pool

When you initialize a string using double quotes, the Java compiler performs an optimization by checking the String Pool.

Scenario 1: Literal Assignment

String literalOne = "textualContent";
String literalTwo = "textualContent";

In this setup, the compiler ensures only a single String object holding "textualContent" is created and placed within the String Pool (which resides in the heap space in modern JVMs, though historically it was in the PermGen space). Both literalOne and literalTwo reference this singular pooled instance. This is efficient because strings are immutable.

Bytecode Insight (Solution 2 perspective):

The bytecode for this operation often utilizes the ldc (load constant) instruction, pulling the existing constant reference directly from the pool index:

// 0:   ldc     #2; //String textualContent
// 2:   astore_1 // Stores reference in literalOne

The new Keyword Approach: Forcing Heap Allocation

Using the new keyword explicitly forces the creation of a new object instance on the heap, regardless of whether an identical string content already exists in the pool.

Scenario 2: Explicit new Instantiation

String heapObject = new String("textualContent");

This operation generally results in two objects being involved:

  1. The literal "textualContent" is checked against the String Pool. If it doesn’t exist, it is placed there (creating one object).
  2. A second, distinct String object is created on the general heap space containing a copy of the literal’s content, referenced by heapObject.

Exception Handling for Efficiency: If the literal "textualContent" already exists in the pool due to a prior literal assignment (Scenario 1), the pool creation step is skipped, but the explicit heap object creation still occurs. This results in a total of one object (the pooled one) plus one heap object, leading to two total objects in memory if the literal was previously established.

Bytecode Insight (Solution 2 perspective):

The bytecode demonstrates explicit object creation and initialization:

// 3:   new     #3; //class java/lang/String
// 6:   dup
// 7:   ldc     #2; //String textualContent (The literal part used for construction)
// 9:   invokespecial   #4; //Method java/lang/String."":(Ljava/lang/String;)V

Comparing Identity: == vs .equals()

Because new String("value") creates a separate heap instance, direct reference comparison using == will yield false even if the content is identical to a pooled string.

Illustrative Example (Solution 6 demonstration):

String poolRef = "sharedValue";      // Pool object created, poolRef points to it
String heapRef = new String("sharedValue"); // New heap object created, heapRef points to it

// Comparison check
boolean identityCheck = (poolRef == heapRef); // Returns false (Different memory addresses)

// Content check (always recommended for string comparison)
boolean contentCheck = poolRef.equals(heapRef); // Returns true (Same content)

String Interning: Bringing Objects to the Pool

The String.intern() method offers a way to move an existing string instance (especially one created via new) into the String Pool. If the string content is already present in the pool, intern() returns a reference to the existing pooled object.

Example using intern():

Continuing the previous example:

heapRef = heapRef.intern(); // Attempts to place heapRef's content into the pool

// Re-check identity
boolean internedCheck = (poolRef == heapRef); // Now returns true, as both point to the pooled object

When Should new String(String) Be Used?

Calling new String("literal") is generally discouraged due to inefficiency. The primary valid use case involves deliberately breaking the == reference check or when dealing with substrings of very large, short-lived strings (Solution 5).

For instance, if you must guarantee that a variable holds a unique object instance separate from any existing string pool entry, new is the mechanism. A more specific use might involve creating a new object from a dynamic source where you want to guarantee immutability separate from a potentially changing pool state (though this is rare given String immutability).

A specialized, though odd, scenario is explicitly forcing a break in == comparison, as demonstrated in related discussions:

String original = "data";
String uniqueCopy = new String(original); // Forces a new instance separate from poolRef if "data" was pooled

Limitations of the String Pool

The String Pool has a capacity limitation tied to the JVM specification. In older specifications, the storage index within the constant pool structure (specifically CONSTANT_String_info) used a 16-bit unsigned integer (U2), limiting the pool to a maximum of $2^{16}$ or 65,535 unique string references, though actual JVM limits are often governed by available heap memory.

Alternative Initialization Methods

While the discussion centers on literals vs. new, recall that strings can also be constructed from character arrays, offering another path for heap allocation:

char[] chars = {'J', 'a', 'v', 'a'};
String charArrayString = new String(chars); // Creates a new heap object

FAQs on Java String Object Creation Memory Allocation

Q: Does using new String() always create two objects

ANS: Not necessarily. It creates one object on the heap. It also checks the String Pool for the literal content used inside the constructor. If that literal content is not in the pool, a second object is created in the pool. If the literal is already pooled, only the explicit heap object is created.

Q: Where is the String Constant Pool located in current Java versions

ANS: In modern Java versions (Java 8 update 202 onwards), the String Constant Pool is located within the Java Heap space, moving away from the older PermGen memory area.

Q: What is the main advantage of using String literals over new String

ANS: The main advantage is memory efficiency due to String interning/pooling. Literals reuse existing objects, preventing duplicate string data in memory, whereas new String() guarantees a new heap object, often duplicating data already present in the pool.

Q: How do I make a string object point to the pool reference

ANS: Use the String.intern() method on the string object. This method returns a reference to the string in the pool if one exists, or adds the string to the pool and returns a reference to the newly pooled object.
