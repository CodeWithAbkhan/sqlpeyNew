“Resolving Spark NoClassDefFoundError: Classpath & Dependency Conflicts”

Apache Spark’s architecture, where each component can be a separate JVM, necessitates careful attention to classpaths. The dynamic nature of building Spark’s classpath, especially to accommodate per-application user code, makes it susceptible to these problems.

Understanding Spark Application Components and Classpath Requirements

A Spark application is comprised of several key components, each with its own JVM and potential classpath:

  • Driver: This is the main JVM that creates a SparkSession or SparkContext, coordinates the application’s execution, and connects to the cluster manager.
  • Cluster Manager: This acts as an entry point to the cluster and is responsible for allocating Executors for your application. Common cluster managers include Spark’s standalone mode , YARN, and Mesos.
  • Executors: These are JVM processes running on cluster nodes that perform the actual data processing tasks.

The relationship and class loading requirements between these components are crucial for avoiding NoClassDefFoundError.

  • Spark Code: These are the core Spark libraries. They must be present in all three components (Driver, Cluster Manager, Executors) as they provide the communication glue. Spark’s design often bundles code for all components into a single “fat jar” or archive to simplify this.
  • Driver-Only Code: User code that is exclusively used by the driver and does not need to be executed on the executors.
  • Distributed Code: User code that is compiled with the driver but must also be executed on the executors. Any code used in transformations on RDDs, DataFrames, or Datasets falls into this category.

Ensuring Correct Version Compatibility for Spark Applications

A primary cause of NoClassDefFoundError is version mismatch. All dependencies within your Spark application must use compatible versions, particularly for Scala and Spark itself.

Scala Version Alignment

All packages your application uses must be compiled against the same major Scala version (e.g., 2.11, 2.12).

Example of incompatible build.sbt:

name := "MySparkApp"
version := "1.0"

libraryDependencies ++= Seq(
   "org.apache.spark" %% "spark-core" % "2.0.1", // Assumes Scala 2.11
   "org.apache.spark" %% "spark-streaming" % "2.0.1" % "provided", // Explicitly for Scala 2.10
   "com.example" %% "my-custom-lib" % "1.0" // Assumes Scala 2.11
)

Corrected build.sbt using %% for automatic Scala version appending:

name := "MySparkApp"
version := "1.0"
scalaVersion := "2.11.8" // Specify your target Scala version

libraryDependencies ++= Seq(
   "org.apache.spark" %% "spark-core" % "2.0.1",
   "org.apache.spark" %% "spark-streaming" % "2.0.1" % "provided",
   "com.example" %% "my-custom-lib" % "1.0"
)

Maven pom.xml for version consistency:

<project>
  <groupId>com.example</groupId>
  <artifactId>my-spark-app</artifactId>
  <version>1.0</version>
  <packaging>jar</packaging>
  <properties>
    <spark.version>2.0.1</spark.version>
    <scala.version>2.11</scala.version> <!-- Ensure this matches your Scala binary version -->
  </properties>
  <dependencies>
    <dependency>
      <groupId>org.apache.spark</groupId>
      <artifactId>spark-core_${scala.version}</artifactId>
      <version>${spark.version}</version>
      <scope>provided</scope>
    </dependency>
    <dependency>
      <groupId>org.apache.spark</groupId>
      <artifactId>spark-streaming_${scala.version}</artifactId>
      <version>${spark.version}</version>
      <scope>provided</scope>
    </dependency>
    <dependency>
      <groupId>com.example</groupId>
      <artifactId>my-custom-lib_${scala.version}</artifactId>
      <version>1.0</version>
    </dependency>
  </dependencies>
</project>

Spark Version Alignment

Similarly, all Spark-related dependencies must adhere to the same major Spark version. Using Spark 1.6 libraries with Spark 2.0 components will likely lead to errors.

Incorrect Scala example:

name := "MySparkApp"
version := "1.0"

libraryDependencies ++= Seq(
   "org.apache.spark" %% "spark-core" % "1.6.1", // Older Spark version
   "org.apache.spark" %% "spark-streaming" % "2.0.1" // Newer Spark version
)

Corrected Scala example with a version variable:

name := "MySparkApp"
version := "1.0"
val sparkVersion = "2.0.1"

libraryDependencies ++= Seq(
   "org.apache.spark" %% "spark-core" % sparkVersion,
   "org.apache.spark" %% "spark-streaming" % sparkVersion
)

Maven pom.xml for Spark version consistency:

<project>
  <groupId>com.example</groupId>
  <artifactId>my-spark-app</artifactId>
  <version>1.0</version>
  <packaging>jar</packaging>
  <properties>
    <spark.version>2.0.1</spark.version>
    <scala.version>2.11</scala.version>
  </properties>
  <dependencies>
    <dependency>
      <groupId>org.apache.spark</groupId>
      <artifactId>spark-core_${scala.version}</artifactId>
      <version>${spark.version}</version>
      <scope>provided</scope>
    </dependency>
    <dependency>
      <groupId>org.apache.spark</groupId>
      <artifactId>spark-streaming_${scala.version}</artifactId>
      <version>${spark.version}</version>
      <scope>provided</scope>
    </dependency>
  </dependencies>
</project>

Important Note: The Scala version used to build your application jars must match the Scala version used to build the Spark distribution you are running on your cluster. Typically, Spark 1.x uses Scala 2.10, while Spark 2.x uses Scala 2.11.

Packaging and Distributing Application Code

The way your application code and its dependencies are packaged significantly impacts runtime behavior.

Building a Fat Jar (Uber Jar)

A common and effective approach is to create a “fat jar” that bundles your application code along with all its transitive dependencies. This simplifies deployment as you don’t need to manage numerous individual JAR files.

Using sbt-assembly:

  1. Add the plugin: Create a project/assembly.sbt file: 
    addSbtPlugin("com.eed3si9n" % "sbt-assembly" % "0.14.0")
  2. Configure assembly: In your build.sbt, ensure core Spark dependencies are marked as provided if your cluster already has them. You can also specify merge strategies for conflicting files: 
    import sbtassembly.AssemblyKeys._

assemblyMergeStrategy in assembly := {
  case PathList("META-INF", xs @ _*) => MergeStrategy.discard
  case x => MergeStrategy.first
}

libraryDependencies ++= Seq(
  "org.apache.spark" %% "spark-core" % "2.4.0" % "provided",
  "org.apache.spark" %% "spark-streaming" % "2.4.0" % "provided",
  "com.couchbase.client" %% "spark-connector" % "2.2.0"
)
  3. Build: Run sbt assembly in your terminal.

Using Maven Assembly Plugin:

You can configure the Maven Assembly Plugin to create an archive containing your application and its dependencies. Ensure that Spark core dependencies are marked as provided in your pom.xml to avoid conflicts with the Spark distribution on the cluster.

Deploying with spark-submit

When submitting your application, ensure your packaged JARs are accessible to all Spark components.

  • --jars argument: Use this to specify paths to your local JAR files or bundled archives. For cluster mode, the JAR must be accessible on the cluster nodes (e.g., via HDFS or a shared filesystem).
  • --packages argument: Allows Spark to fetch dependencies directly from Maven repositories.
  • spark.jars parameter (via spark-submit): Similar to --jars, this parameter is used when starting the SparkSession or SparkContext and is crucial when deploying to YARN.
  • spark.yarn.archive parameter (for YARN): This specifies an archive (e.g., a gzipped tarball) containing all necessary jars for the application, which the cluster manager distributes to executors.

Scenario: NoClassDefFoundError with Spark Connector

A common scenario involves using external Spark connectors, like the Couchbase connector. If you encounter an error like java.lang.NoClassDefFoundError: rx/Completable$OnSubscribe even after building a fat jar, it suggests a deeper dependency conflict or omission.

Example build.sbt for a Couchbase connector:

lazy val root = (project in file(".")).
  settings(
    name := "spark-couchbase-example",
    version := "1.0",
    scalaVersion := "2.11.12",
    mainClass in Compile := Some("StreamingExample")
  )

libraryDependencies ++= Seq(
  "org.apache.spark" %% "spark-core" % "2.4.0" % "provided",
  "org.apache.spark" %% "spark-streaming" % "2.4.0" % "provided",
  "org.apache.spark" %% "spark-sql" % "2.4.0" % "provided",
  "com.couchbase.client" %% "spark-connector" % "2.2.0"
)

// Merge strategy for sbt-assembly
import sbtassembly.AssemblyKeys._
assemblyMergeStrategy in assembly := {
       case PathList("META-INF", xs @ _*) => MergeStrategy.discard
       case x => MergeStrategy.first
   }

If running this with spark-submit results in java.lang.NoClassDefFoundError: rx/Completable$OnSubscribe, and you can confirm the class rx/Completable$OnSubscribe.class is present in your assembled JAR, consider these points:

  1. Transitive Dependency Conflicts: The rx/Completable class might be provided by multiple libraries with incompatible versions within your fat jar. The sbt-assembly merge strategy can help, but you might need to explicitly exclude certain versions or use dependency exclusion rules in your build configuration.
  2. Spark Distribution Mismatch: Ensure the Spark version your application is compiled against (2.4.0 in the example) perfectly matches the Spark distribution running on the cluster. Minor version differences can cause issues.
  3. Runtime Classloader Issues: Sometimes, the classloader on the executor nodes might not properly load classes from deeply nested JARs or archives. Ensure your fat jar is structured correctly.

Alternative Approaches for Dependency Inclusion

  • --packages with spark-submit: For simpler dependency management, you can often rely on spark-submit --packages "group:artifact:version". This delegates the download and inclusion to Spark.
  • External Dependency JARs: If building a fat jar proves problematic, you can include individual dependency JARs by placing them in the jars directory of your Spark installation or by referencing them via the --jars option in spark-submit.

Specific Cluster Manager Considerations

  • Standalone Mode: The driver and executors share the same Spark installation. Ensure your build.sbt or pom.xml uses the same Scala and Spark versions as the Spark installation.
  • YARN/Mesos: Each application can potentially use different Spark versions. However, all components of a single application must use the same version. You provide the application’s Spark dependencies (often as an archive) via spark.yarn.archive or spark.yarn.jars.

FAQs on Resolving Spark NoClassDefFoundError

Q: What is the primary reason for Spark NoClassDefFoundError

ANS: The most frequent cause is a mismatch in Scala or Spark versions between your application’s dependencies and the Spark distribution on the cluster, or incorrect packaging of your application and its dependencies.

Q: How do I ensure Scala version compatibility in Spark

ANS: Ensure all libraries your Spark application depends on are compiled with the same major Scala version. Using %% in sbt or specifying the Scala binary suffix (e.g., _2.11) in Maven artifacts helps maintain consistency.

Q: When building a fat jar for Spark, what should I do with Spark's own dependencies

ANS: It’s best practice to mark core Spark dependencies (like spark-core, spark-sql) as provided in your build tool (sbt or Maven). This prevents conflicts with the Spark libraries already present on the cluster.

Q: How do I submit an application with external dependencies using spark-submit

ANS: You can use the --jars option to specify local JAR files or use the --packages option to fetch dependencies from Maven repositories. For YARN deployments, spark.yarn.jars or spark.yarn.archive are crucial for distributing your application’s dependencies.

Q: Can different Spark applications on the same cluster use different Spark versions

ANS: Yes, when using cluster managers like YARN or Mesos, each Spark application can be configured with its own specific Spark version. However, all components within a single application must use a consistent Spark version.

Q: What if my fat jar contains the class, but I still get NoClassDefFoundError

ANS: This can indicate deeper issues like conflicting versions of the same library included multiple times, or runtime classloader problems on the executor nodes. Review your dependency tree and consider explicit exclusions or merge strategies in your build.
