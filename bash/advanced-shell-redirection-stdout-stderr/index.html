“Advanced Shell Redirection: Separating and Manipulating Stdout and Stderr”

When executing shell commands, the output is typically separated into Standard Output (FD 1, or stdout) for normal results and Standard Error (FD 2, or stderr) for diagnostic or error messages. Effectively controlling how these streams flow—whether merging them, discarding one, filtering content, or sending them to different destinations—is crucial for robust scripting.

What are the various effective methods for managing the flow of stdout and stderr in a shell environment, especially when piping to another utility like grep?

Techniques for Controlling Output Streams

Here are several documented and tested techniques for achieving specific I/O redirection goals.

Method 1: Merging Stderr into Stdout Before Piping and Discarding Stdout

This approach first ensures that stderr points to the same location as stdout. Then, the combined stream’s original stdout path is redirected to /dev/null, while the pipe operation captures the now-merged stream (which includes the original stderr).

Scenario: Redirect stderr to stdout, discard the original stdout, and pipe the resulting stream (containing only original stderr) to grep.

# Original stdout goes to /dev/null, original stderr goes to the pipe for grep
some_application 2>&1 >/dev/null | grep 'critical_error_pattern'

Technical Insight: Shell redirection order matters. 2>&1 makes FD 2 refer to the same open file description as FD 1. Then >/dev/null changes FD 1, but FD 2 still points to the pipe established before FD 1 was redirected. For a deeper dive into redirection mechanics, consult the Bash reference manual on Redirections .

Method 2: Swapping Standard Output and Standard Error Descriptors

If the goal is to completely reverse the streams—sending original stdout to where stderr normally goes, and vice versa—a temporary file descriptor is needed for safe swapping.

Scenario: Swap the destinations of stdout (1) and stderr (2) using an auxiliary descriptor (3).

# FD 3 gets stdout (1), FD 1 gets stderr (2), FD 2 gets original stdout (3)
some_application 3>&1 1>&2 2>&3

This technique utilizes the nine available file descriptors common in processes, allowing complex maneuvers beyond simple merging or discarding.

Method 3: Using Process Substitution for Independent Destinations

Bash offers process substitution (>(...) for writing and <(...) for reading) which treats the output of a command as a temporary file name, allowing independent redirection for each stream into distinct targets (which could be other commands).

Scenario: Send stderr to a grep process, while simultaneously sending stdout to /dev/null.

# Stderr (2) is directed to a process substitution running grep, Stdout (1) to /dev/null
some_application 2> >(grep 'pattern_to_keep' >&2) >/dev/null

Note: In the example above, we send the output of grep back to its own stderr (>&2) within the substitution to ensure it appears on the terminal, or it could be redirected elsewhere.

Method 4: Filtering Stderr While Preserving Both Streams Intact

This sophisticated method allows filtering specific content from stderr without affecting the flow or content of stdout.

Scenario: Execute a command where all stdout remains as stdout, all stderr remains as stderr, but any line in stderr containing "unwanted_text" is removed from the stderr stream.

# Stderr (2) is redirected into a process substitution that filters it
some_application 2> >(grep -v "unwanted_text" 1>&2)

The grep -v "unwanted_text" 1>&2 inside the substitution ensures that what grep outputs (the filtered lines) is sent back to the main process’s stderr. This avoids mixing streams or losing data.

Method 5: The Shell Pipe Evaluation Order Explained

A critical element in advanced redirection involves realizing that Bash sets up pipes before it interprets local redirections.

Consider the following sequence and its outcome:

  1. command 2>&1 >/dev/null | grep 'something':

    • A pipe (FIFO) is established between command (FD 1) and grep (FD 0).
    • command FD 2 is directed to the pipe (same as FD 1 was pointing).
    • command FD 1 is then redirected to /dev/null.
    • Result: command’s stderr goes to the pipe (and grep), while stdout goes to /dev/null.

  2. command >/dev/null 2>&1 | grep 'something':

    • A pipe is established.
    • command FD 1 is redirected to /dev/null.
    • command FD 2 is then directed to where FD 1 currently points (which is /dev/null).
    • Result: Both stdout and stderr from command go to /dev/null. Nothing reaches the grep pipe.

Method 6: The Bash Shorthand |& Operator

For Bash versions that support it, the |& operator provides a concise way to pipe stderr directly into stdout before the pipe operation.

Scenario: Discard stdout to /dev/null, and pipe the resulting stream (which is now just the original stderr) to grep.

# Stdout redirected to null, then stderr is merged into stdout for piping
some_utility >/dev/null |& grep "specific_message"

This is functionally equivalent to some_utility >/dev/null 2>&1 | grep "specific_message". Some users report that |& can capture output from subprocesses in complex scenarios where 2>&1 might not be as comprehensive, although documentation on this advantage is sparse.

Method 7: Advanced Stream Duplication with Explicit Descriptors

For scenarios requiring extreme control, explicit descriptor manipulation using exec can be employed, often borrowed from LDP examples.

Scenario: Redirect command1’s stderr to command2’s stdin, while preserving command1’s original stdout flow.

exec 3>&1
command1 2>&1 >&3 3>&- | command2 3>&-
exec 3>&-

This uses descriptor 3 as a temporary holding space for the original stdout reference during the complex switch.

Method 8: Persistent Logging and Filtering to Files While Keeping TTY Output

This technique addresses the need to log specific streams to files while retaining immediate terminal feedback from one stream.

Scenario: Save all stdout to std.out, filter stderr to remove messages containing “nasty_msg” before appending the rest to std.err, and keep a separate stream available for direct terminal output.

# Save current terminal stdout to descriptor 3
exec 3>&1
# Redirect stderr (2) to a process that filters it into std.err. Redirect stdout (1) to std.out
exec 2> >(grep -v "nasty_msg" >> std.err) 1>> std.out

# Output directed to std.out
echo "Normal log entry" >&1
# Output directed to filtered std.err
echo "A severe issue" >&2
# This output still goes to the original terminal (FD 3)
echo "Immediate alert on screen" >&3

# Clean up (optional, depending on context)
exec 3>&-

Method 9: Utilizing Named Pipes (FIFOs)

For decoupling processes over a longer duration or when dealing with asynchronous execution paths, named pipes provide explicit channels between processes.

Scenario: Send stdout to one process and stderr to a completely different, concurrently running process using named pipes.

mkfifo stdout_channel
mkfifo stderr_channel

# Listener processes running in the background
cat < stdout_channel | processor_for_stdout &
cat < stderr_channel | processor_for_stderr &

# Main command directing output
executor_program 1>stdout_channel 2>stderr_channel

# Clean up pipes afterwards
rm stdout_channel stderr_channel

Method 10: Using the rc Shell Pipe Syntax

The rc shell (and its compatibility mode in Bash) offers a distinct syntax for specifying which file descriptor to pipe.

Scenario: In rc shell syntax (or using rc -c in Bash), discard stdout and pipe stderr to grep.

# [1] refers to stdout, [2] refers to stderr
executor_task >[1] /dev/null |[2] grep 'important_detail'

This syntax explicitly states that only file descriptor 2 should be piped across the |.

FAQs on Advanced Shell Redirection Stdout Stderr

Q: How do I send both stdout and stderr to the same file in Bash

ANS: Use command &> filename or the equivalent command > filename 2>&1. The latter must be in that specific order.

Q: What is the default file descriptor number for standard error

ANS: The default file descriptor number for standard error is 2.

Q: Can process substitution be used to save stdout and stderr to separate files

ANS: Yes, process substitution allows directing each stream independently, for instance: command > >(cat > stdout.log) 2> >(cat > stderr.log).
