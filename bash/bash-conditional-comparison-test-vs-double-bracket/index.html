“Bash Shell Comparison: When to Use [ vs [[ for Script Conditionals”

When writing shell scripts in Bash, selecting the appropriate construct for conditional testing—either the single bracket [ ] (which is often synonymous with the test command) or the modern double bracket [[ ]]—presents important trade-offs regarding syntax, portability, and execution speed. What are the definitive differences that should influence my script development choices?

Core Differences: POSIX Compliance vs. Bash Extensions

The fundamental distinction between these two constructs lies in their specification adherence and parsing mechanism:

  • [ ] (Single Bracket/test): This is a POSIX-specified command. It behaves like any standard command; ] is simply its final argument. Because it’s a regular command, word splitting and filename generation (globbing) occur on its arguments during normal shell parsing before the command executes.
  • [[ ]] (Double Bracket): This is a Bash extension, originally inspired by KornShell (ksh). It is parsed as a single, special construct within the shell, meaning Bash handles its contents with unique, “magical” parsing rules that differ significantly from standard command execution. It is a shell keyword, not a built-in command.

This difference in parsing leads directly to divergent behaviors, particularly around quoting and special operators.

Example of [ ] Argument Splitting Failure:

If a variable contains spaces or wildcards, unquoted use in [ ] is problematic:

# Example demonstrating argument splitting failure in single bracket
VARIABLE_WITH_SPACES="file one"

# Bad: Expands to [ file one = file ] which is likely a syntax error
if [ $VARIABLE_WITH_SPACES = file ]; then
    echo "This might fail or behave unexpectedly"
fi

# Good (POSIX way): Handles spaces correctly
if [ "$VARIABLE_WITH_SPACES" = "file one" ]; then
    echo "Quoted correctly"
fi

Example: Regular Expression Matching with [[ ]]

[[ ]] is preferred when precise pattern validation is needed:

# Using regex matching (Bash extension)
INPUT_STRING="user_name_123"

if [[ "$INPUT_STRING" =~ ^[a-z_]+[0-9]+$ ]]; then
    echo "Input string matches expected pattern."
else
    echo "Pattern mismatch."
fi

Alternative for [ ] (POSIX): To achieve similar regex matching with [ ], you must rely on external commands:

# POSIX equivalent using grep
INPUT_STRING="user_name_123"
if printf '%s\n' "$INPUT_STRING" | grep -Eq '^[a-z_]+[0-9]+$'; then
    echo "POSIX match confirmed."
fi

Performance and Execution Model

A critical differentiator, particularly for high-volume scripts, is execution efficiency:

  1. Process Spawning: The single bracket [ ] (and the test command) can execute as an external program, forcing the shell to fork a new process, which incurs overhead. While Bash often optimizes this by using its built-in version, the potential for process creation exists, especially in non-Bash environments or specific script contexts.
  2. Shell Keyword: The double bracket [[ ]] is a shell keyword. This means it is parsed and executed internally by the shell process itself, avoiding the overhead of forking a new process.

Performance testing consistently shows that [[ ]] executes faster than [ ] or test, especially when dealing with a massive number of iterations, primarily due to avoiding external process overhead. One analysis showed [[ ]] being around 1.42x faster than [ ] in simple comparisons.

Numerical Comparison Caveats with [[ ]]

While [[ ]] offers cleaner syntax, it exhibits inconsistent behavior when performing numerical comparisons (-ge, -le, etc.) with non-numeric strings, making it potentially unsafe for strict integer validation:

  • When using [ ], providing a non-numeric value to -ge generally throws an explicit “integer expression expected” error.
  • When using [[ ]], a non-numeric string might be interpreted as 0 without an error, or it might throw an error like “value too great for base,” depending on the specific invalid input (e.g., 5foo vs. something).

This ambiguity means that for strictly reliable integer checking, the explicit error handling of [ ] or using arithmetic expansion (( ... )) might be preferable, as noted in some expert reviews.

Portability and External Dependencies

The decision often boils down to the target environment:

  • Portability: If a script must run reliably across any Bourne-like shell (including older systems or minimal environments like dash), [ ] (or test) is mandatory because it is POSIX compliant.
  • Bash/Ksh/Zsh Specific: If the script targets modern Bash environments, [[ ]] is generally favored due to its superior syntax and performance benefits.

It is documented that [[ ]] is unsupported in some older SunOS versions or within specific function declarations in older Bash builds.

Style Guide Recommendations

Major style authorities often lean toward the modern syntax:

  • Google Style Guide: Explicitly prefers [[ ... ]] over [ ... ] and test, citing reduced errors due to the suppression of pathname expansion and word splitting, and the added benefit of regex matching.

Practical Implementation Examples

To illustrate the speed test results, a common Bash comparison structure looks like this (where word1 and word2 are constants):

Performance Test Structure (Faster [[ ]])

WORD_A="constant_value"
WORD_B="different_value"

# Using [[ ]] - Faster, keyword parsing
if [[ "$WORD_A" == "$WORD_B" ]]; then
    echo "Double bracket success"
fi

POSIX Reliable Structure (Slower if process spawning occurs)

WORD_A="constant_value"
WORD_B="different_value"

# Using [ ] - POSIX portable, requires strict quoting
if [ "$WORD_A" = "$WORD_B" ]; then
    echo "Single bracket success"
fi

If your scripting environment guarantees Bash, the benefits of [[ ]] (cleaner syntax, regex support, speed) usually outweigh the portability concerns inherent in using Bash extensions.

FAQs on Bash Conditional Comparison Test Vs Double Bracket

Q: Is the single bracket [ always slower than the double bracket [[

ANS: Yes, typically. The single bracket often invokes the test command, which can result in spawning a separate process (forking), incurring overhead. The double bracket is a shell keyword parsed internally, making it faster.

Q: Can [ be used in scripts intended for dash shell

ANS: Yes, the single bracket [ ] (or test) is POSIX standard and will work correctly in minimal shells like dash, whereas [[ ]] is a Bash/Ksh/Zsh extension and will fail.

Q: Does == behave differently than = inside [ and [[

ANS: In Bash, = and == behave identically within both [ ] and [[ ]] for string comparison. However, == inside [ ] is technically a Bash extension, while = is the core POSIX operator.

Q: How do I perform regex comparison using the standard [ command

ANS: The standard [ ] command does not natively support ERE matching. You must pipe the data to external utilities like grep -E or use awk for pattern matching.
