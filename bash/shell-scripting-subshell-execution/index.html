“Shell Scripting: Executing Commands in Subshells Safely”

When writing shell scripts, you often need to execute commands in a separate shell environment, commonly referred to as a subshell. This is frequently done for tasks involving elevated privileges (sudo), remote execution (ssh), or launching new shell instances (sh, bash). However, the way these commands are invoked and how they interact with standard input and the script’s environment can lead to unexpected behavior if not handled carefully. This discussion delves into the nuances of subshell execution in shell scripting, focusing on how to ensure your commands run as intended.

A core principle to remember is that a section of your script formatted as a here-document for another shell is executed within its own distinct environment. This environment might differ from your main script’s environment, potentially even residing on a different machine. If this sub-script block involves variable expansion (parameter expansion), command substitution, or arithmetic expansion, you need to control where these expansions occur.

Controlling Expansion Scope with Here-Documents

The shell provides a flexible mechanism for here-documents, allowing you to dictate whether expansions happen in the parent shell or the child shell.

1. Expansions in the Parent Shell:

To ensure all expansions are processed by your main (parent) shell before the subshell executes the content, the here-document delimiter must be left unquoted.

command <<DELIMITER
  # Your commands here, with expansions like $VAR or $(command)
DELIMITER

Example:

Let’s see how variable expansions behave when the delimiter is unquoted:

#!/bin/bash

parent_var="initial_value"
echo "Parent shell before subshell: parent_var=$parent_var"

sudo sh <<END
  echo "Inside subshell: parent_var=$parent_var"
  child_var="subshell_value"
  echo "Inside subshell: child_var=$child_var"
END

echo "Parent shell after subshell: parent_var=$parent_var"

Expected Output:

Parent shell before subshell: parent_var=initial_value
Inside subshell: parent_var=initial_value
Inside subshell: child_var=subshell_value
Parent shell after subshell: parent_var=initial_value

In this scenario, parent_var’s value is determined by the parent shell before sh is invoked.

2. Expansions in the Child Shell:

Conversely, if you want all expansions to be performed strictly within the context of the child shell, quote the here-document delimiter.

command <<'DELIMITER'
  # Your commands here, expansions will be interpreted by the child shell
DELIMITER

Example:

Consider the same scenario but with a quoted delimiter:

#!/bin/bash

parent_var="initial_value"
echo "Parent shell before subshell: parent_var=$parent_var"

sudo sh <<'END'
  echo "Inside subshell: parent_var=$parent_var" # $parent_var is not expanded here
  child_var="subshell_value"
  echo "Inside subshell: child_var=$child_var"
END

echo "Parent shell after subshell: parent_var=$parent_var"

Expected Output:

Parent shell before subshell: parent_var=initial_value
Inside subshell: parent_var=$parent_var
Inside subshell: child_var=subshell_value
Parent shell after subshell: parent_var=initial_value

Here, $parent_var is passed literally into the subshell, and any expansions within the subshell (like $child_var) are evaluated there.

3. Mixed Expansion Scopes:

You can achieve a mix where some expansions occur in the parent and others in the child. This requires using an unquoted delimiter and explicitly escaping the expansion expressions that should be evaluated by the child shell.

#!/bin/bash

parent_var="initial_value"
echo "Parent shell before subshell: parent_var=$parent_var"

sudo sh <<END
  echo "Inside subshell: parent_var=$parent_var"
  child_var="subshell_value"
  echo "Inside subshell: child_var=\$child_var" # Escaped to be processed by child
END

echo "Parent shell after subshell: parent_var=$parent_var"

Expected Output:

Parent shell before subshell: parent_var=initial_value
Inside subshell: parent_var=initial_value
Inside subshell: child_var=$child_var
Parent shell after subshell: parent_var=initial_value

In this case, parent_var is expanded in the parent, while \$child_var is treated as a literal string until it reaches the child shell, where it is then evaluated.

Alternative Command Execution Methods

Beyond here-documents, commands like su, ssh, and sh offer direct ways to pass commands as arguments or via standard input, bypassing the need for interactive terminal sessions which can cause issues.

  • Using -c flag: Many commands accept a -c flag to execute a single string of commands.

    sudo sh -c 'echo "Current user: $(whoami)"; echo "Command executed successfully"'
ssh user@remote_host 'uname -a'

  • Piping to Standard Input: You can pipe commands to these utilities, which will then execute them.

    printf 'uname -a; whoami; uptime' | ssh user@remote_host
printf 'echo "Executing via sh"; pwd' | sh

  • Here-Documents with Piping: Combining piping with here-documents provides a clean way to pass multi-line commands.

    ssh user@remote_host <<'EOF'
  echo "Remote system information:"
  uname -a
  who am i
EOF

sh <<'EOF'
  echo "Executing multiple commands:"
  ls -l
  date
EOF

  • Forcing TTY Allocation (Use with Caution): In SSH, the -t option forces TTY allocation. However, this can sometimes interfere with sudo’s password prompt if not managed carefully, as seen in error messages like sudo: no tty present and no askpass program specified.

Handling Interactive Programs with expect

For programs that require interactive input and are sensitive to standard input handling, the expect command offers a robust solution. expect allows you to script interactions with command-line programs.

Example expect script (custom.script):

#!/usr/bin/expect -f

set timeout 60

spawn sudo su -

expect "*?assword" { send "*your_secret_password*\r" }
send_user "Successfully prompted for password.\n"

expect "#" { send "whoami\r" }
expect "#" { send "exit\r" }
send_user "Exited subshell.\n"

To run this script:

$ expect -f custom.script

This approach is particularly useful when dealing with commands that might prompt for input, ensuring a smooth, automated execution flow.

Common Pitfalls:

  • Piping to su or sudo: Piping commands directly to su or sudo without proper TTY allocation or password handling can lead to errors like su: must be run from a terminal or sudo: no tty present and no askpass program specified.
  • read command interaction: When using here-documents with commands that include a read statement, the subsequent commands might be misinterpreted as input for read if not carefully managed.
ssh use@host <<'____HERE'
  echo "Please enter your name:"
  read name
  echo "Processing complete." # This echo might be consumed by 'read'
____HERE

By understanding these mechanisms and choosing the appropriate method for controlling expansion and input, you can write more reliable and efficient shell scripts.

FAQs on Shell Scripting Subshell Execution

Q: How do I ensure variables are expanded in the parent shell when using a here-document?

ANS: Leave the here-document delimiter unquoted. For example: command <<END\n echo $MY_VAR\nEND. The parent shell will expand $MY_VAR before passing the content to command.

Q: What happens if I quote the delimiter in a here-document?

ANS: Quoting the delimiter, like command <<'END'\n echo $MY_VAR\nEND, prevents expansion of variables and command substitutions within the here-document’s content by the parent shell. These expansions will then be attempted by the child shell that receives the content.

Q: Can I mix expansions from parent and child shells?

ANS: Yes, you can. Use an unquoted delimiter and escape specific expansion expressions (e.g., \$VAR) that you want the child shell to interpret.

Q: What are common errors when piping commands to sudo or ssh?

ANS: Common errors include “must be run from a terminal” or “no tty present and no askpass program specified.” This usually occurs because these commands expect an interactive terminal for input, like password prompts, which piping doesn’t provide by default.

Q: How can I automate interaction with programs that prompt for input?

ANS: The expect command is designed for this. You can write expect scripts to define the expected output from a program and the corresponding input to send, automating interactive sessions.

Q: Is it necessary to explicitly exit subshells like 'sudo sh'?

ANS: Generally, no. When the commands provided to sudo sh (or similar) are complete, the subshell will naturally terminate. An explicit exit is often included for clarity or to ensure cleanup, but it’s not always strictly required for the subshell to end.
