“Shell Scripting: How to Iterate Over All Positional Arguments Safely”

When authoring shell scripts (like Bash or sh), processing command-line inputs passed as positional parameters ($1, $2, etc.) requires precision, especially when those inputs might contain internal spaces or special characters. How can one iterate over all arguments reliably, ensuring arguments with spaces are treated as single entities?

The Critical Distinction: “$@” vs. “$*”

The core of the solution lies in correctly quoting the special variables $@ and $*.

When arguments contain spaces, the unquoted forms ($@ and $*) behave identically but often incorrectly for list processing: they split arguments based on whitespace, treating each resulting word as a separate item.

The quoted forms behave distinctly:

  • "$*": Expands the entire argument list into a single string, separated by the first character of the $IFS variable (usually a space).
  • "$@": Expands into a list of separate, quoted arguments. Each argument passed to the script is preserved as a distinct element, even if it contains spaces. This mirrors how the arguments were originally supplied to the script.

The accepted practice for iterating over all command-line arguments while preserving their integrity is to use for var in "$@".

Solution 1: Standard Iteration with "$@"

This approach ensures that arguments containing spaces are processed as single tokens.

#!/bin/sh
# Script: argument_printer.sh

echo "Processing arguments using \"\$@\":"
for arg_item in "$@"
do
    echo "Argument received: '$arg_item'"
done

Solution 2: The Power of eval When Reconstructing Command Lines

When arguments need to be processed, potentially modified (e.g., escaped for security), and then passed to another command (especially if complex quoting is involved), eval can be necessary. However, eval introduces security risks if input is untrusted and requires careful escaping, as demonstrated in advanced scenarios involving filenames with quotes, like "He said, \"Don't do this!\"". For simple iteration, avoid eval.

For complex argument re-invocation, utility programs that correctly escape arguments for eval (sometimes called escape in legacy scripts) might be employed, though this moves beyond standard shell features.

Solution 3: Portable Simplification in sh (If No Spaces Are Expected)

In scenarios where you are absolutely certain that none of your positional parameters contain spaces (or you intend for them to be split by spaces), you can rely on the most minimal form. In Bourne Shell (sh) and modern shells like Bash, if the in WORDS list is omitted from a for loop, it defaults to operating on "$@".

# Simplest form, relies on default behavior if in WORDS is absent
for token
do
    echo "Token: $token"
done

This is functionally equivalent to for token in "$@" in POSIX-compliant shells if no arguments are present, but for maximum clarity and robustness when handling spaces, explicitly using "$@" remains preferred.

Solution 4: Queue Processing with shift

If the goal is to process arguments sequentially from the front, treating the argument list like a queue, the shift command is effective. It discards $1 and moves subsequent arguments down ($2 becomes $1, etc.).

#!/bin/bash
# Processing arguments as a queue

echo "Processing arguments using shift:"
while test $# -gt 0
do
    echo "Popped argument: $1"
    shift
done

Solution 5: Accessing Arguments by Index (Array Conversion)

For situations where you need random access to arguments without iterating sequentially or modifying the argument list structure, you can temporarily copy the arguments into a shell array.

#!/bin/bash

# Capture argument count and convert "$@" to an indexed array
arg_count=$#
declare -a arg_array=("${@}") # Use nameref or simple assignment depending on shell version

echo "Accessing arguments via array index:"
for (( idx=0; idx<arg_count; idx++ )); do
    echo "Element at index $idx: ${arg_array[idx]}"
done

Solution 6: Iteration Using Parameter Expansion with Index (${!i})

This advanced Bash technique allows looping based on the argument count ($#) and directly accessing arguments using indirect expansion (${!i}), where i holds the index number (1, 2, 3…).

#!/bin/bash
# Utilizing indirect parameter expansion

echo "Iterating using indirect expansion:"
for (( i=1; i<=$#; i++ ))
do
  # ${!i} expands to the value of the positional parameter $i
  printf "Argument %d: %s\n" "$i" "${!i}"
done

If run with ./script.sh Hello "World Wide Web":

  • ${!1} evaluates to Hello
  • ${!2} evaluates to World Wide Web

Solution 7: Splitting Arguments at a Marker (e.g., --)

When arguments serve different purposes (e.g., options vs. operands), separating them based on a specific delimiter like -- is common. Bash array slicing (${array[@]:offset:length}) combined with positional parameter manipulation provides a clean way to segment the list without mutation.

toolwrapper() {
   local split_index=0
   # Find the index 'i' where the argument is "--"
   for i in $(seq 1 $#); do
     if [[ "${!i}" == "--" ]]; then
       split_index=$i
       break
     fi
   done

   if [ $split_index -eq 0 ]; then
       echo "Delimiter -- not found."
       echo "All arguments: ${@}"
       return
   fi

   # Use positional slicing: ${@:start:count}
   echo "Arguments before delimiter: ${@:1:$((split_index-1))}"
   echo "Arguments after delimiter: ${@:$((split_index+1)):$#}"
}

# Example invocation
toolwrapper opt1 opt2 -- final_operand argument_two

FAQs on Shell Iterate Arguments Safely

Q: What is the primary difference between \$* and \$@

ANS: When unquoted, they act similarly, splitting by IFS. When quoted ("$*" vs "$@"), "$*" joins all arguments into a single string separated by the first character of $IFS, while "$@" preserves each argument as a distinct, quoted element.

Q: Is using \$@ always correct for iterating arguments

ANS: Yes, for var in "$@" is the most reliable, portable way to iterate over command-line arguments while correctly handling arguments that contain embedded whitespace.

Q: How can I change the arguments being processed later in a script

ANS: You can modify the positional parameters using set -- new_arg1 "new arg 2". This resets $1, $2, etc., to the new list.
