“Effective Strategies for Executing Multiple Remote Commands via SSH in Bash”

Bash Here Document (<<) for Remote Script Execution

One robust method involves using a Bash Here Document to feed a block of commands directly to a shell instance on the remote host.

Standard Approach:

ssh remote_server_alias << EOF
  echo "Starting remote tasks..."
  ls -l /var/log/
  /opt/scripts/deploy_app.sh --production
  df -h
EOF

Addressing Shell Invocation Issues:

To ensure the commands execute within a proper Bash environment, especially if interactive shell features are needed, prepend the command execution explicitly:

ssh remote_server_alias /bin/bash << EOF
  # Commands here
  touch "/tmp/remote_file_check"
  echo "Status check complete."
EOF

Variable Substitution Control:

Here Documents offer control over local variable substitution. If the delimiter (e.g., EOF) is unquoted, local variables defined in the local script will be substituted before transmission:

LOCAL_USER_NAME="operations_user"

ssh remote_host /bin/bash << EOF
  # $LOCAL_USER_NAME is substituted locally before sending
  echo "Running commands for user: ${LOCAL_USER_NAME}"
  mkdir -p "/home/${LOCAL_USER_NAME}/jobs"
EOF

If the delimiter is quoted (e.g., 'EOF'), substitution is suppressed, and all content is passed literally to the remote shell. This is crucial for passing sensitive strings or remote variables without local interference:

ssh remote_server << 'NO_SUB'
  # This script runs exactly as written remotely
  REMOTE_VAR="initial"
  echo "The remote variable is: $REMOTE_VAR"
  # Local variables remain untouched
  echo "Local variable check: $LOCAL_USER_NAME"
NO_SUB

Piping Local Scripts into SSH

An alternative that keeps the remote command simple is piping the content of a locally prepared script file directly to ssh. The remote server reads from its standard input (stdin).

Local Script Example (commands_to_run.sh):

#!/bin/bash
echo "Starting script sequence remotely..."
/usr/local/bin/perform_cleanup
uptime

Execution via Pipe:

cat commands_to_run.sh | ssh remote_user@target_ip "/bin/bash"

A variation of this pipes commands directly from cat without an intermediate file:

cat << SCRIPT_CONTENT | ssh user@remote_server
ls /etc
ps aux | grep sshd
SCRIPT_CONTENT

Encapsulating Commands in Quotes

For very short sequences, wrapping the commands inside double quotes passed directly to the remote shell is the simplest syntax.

ssh db_admin@data_server "
  pg_dump -Fc database_name > backup_$(date +%F).sql;
  echo 'Backup complete.';
  ls -lh /backups/
"

Utilizing SSH Control Sockets for Efficiency

When numerous SSH connections are needed in quick succession, repeatedly establishing the TCP connection is inefficient. SSH multiplexing via Control Sockets reuses an existing connection session.

Step 1: Establish the Master Connection:

This command sets up the master socket path and initiates the connection.

MASTER_SOCKET_PATH="~/.ssh/ssh-master-%r@%h:%p"
ssh -M -S "${MASTER_SOCKET_PATH}" user@remote_host true

Step 2: Run Subsequent Commands Using the Socket:

Subsequent commands use the -O (ControlCommand) flag to instruct SSH to use the existing tunnel, avoiding reconnection overhead.

ssh -S "${MASTER_SOCKET_PATH}" user@remote_host -T "echo 'Fast connection test 1'; /bin/hostname"
ssh -S "${MASTER_SOCKET_PATH}" user@remote_host -T "ls -ld /tmp"

Configuration Alternative: To automate this without modifying every command, configure SSH multiplexing in your local ~/.ssh/config:

Host efficient_host
    Hostname actual.remote.address.com
    User remote_user
    ControlMaster auto
    ControlPath ~/.ssh/sockets/%r@%h:%p
    ControlPersist 5m # Keep socket alive for 5 minutes after last use

With this config, simple calls like ssh efficient_host "date" will leverage the existing connection if available.

Maintaining Local Context: Passing Functions

If you need to execute remote commands that rely on local variables or complex local logic structures (like loops or function definitions), you can pass the definition of a local function to the remote session.

This technique first uses declare -f function_name to output the function definition text and then uses command substitution ($()) to pass this text, alongside the function call, to the remote execution context.

Local Setup:

LOCAL_CONFIG_PATH="/etc/app/config.ini"

remote_deployment_job() {
    echo "Starting remote deployment for configuration: $1"
    # Use local variable $LOCAL_CONFIG_PATH
    sudo cp "$LOCAL_CONFIG_PATH" /tmp/remote_config
    /usr/bin/remote_setup_script --config /tmp/remote_config
    echo "Job finished."
}

Remote Execution (Safely Escaping Arguments):

A helper function (sshqfunc) is often required to properly quote arguments for safe transmission across shells.

# A function to safely quote and prepare a local function call for SSH
sshqfunc() {
    local func_name=$1
    # Output the function definition, then call it, safely quoted for bash -c
    echo "bash -c $(printf "%q" "$(declare -f "$func_name"); $func_name \"\$@\"")"
}

# Execute: We pass the function name, then the required arguments separately.
ssh remote_server "$(sshqfunc remote_deployment_job)" -- "$LOCAL_CONFIG_PATH" 5

This ensures that $LOCAL_CONFIG_PATH is correctly quoted and passed as the first argument ($1) within the remote function remote_deployment_job.

Conditional Execution Logic

Simple sequential execution can also be achieved using logical operators:

  • AND (&&): Executes the second command only if the first succeeds (returns exit code 0).
  • OR (||): Executes the second command only if the first fails.
# Run command 1, IF successful, run command 2.
ssh user@server "command_that_might_fail && echo 'Success' || echo 'Failure'"

For combined operations where you need explicit ordering regardless of success (like the original prompt examples), the semicolon separator remains standard:

ssh user@server "ls /nonexistent_dir; pwd; /usr/local/bin/script.sh"

Handling Privileged Execution (sudo)

When running commands that require elevated privileges remotely, piping commands into sudo can be complex due to password prompts. A method to bypass the prompt for a stream of commands involves piping the commands to sudo -S (silent mode) along with the password read from a separate secure stream (like a Here Document).

Securely Executing Sudo Commands Remotely:

SUDO_PASS="mySecurePwd123"

cat secure_commands.sh - << EOF | ssh admin_user@remote_host "sudo -S -- /bin/bash"
hostname
whoami
echo "Running critical task..."
/etc/init.d/service restart
EOF

# Where secure_commands.sh contains:
# ls -l /root/
# echo "Admin tasks done."

The main input stream (cat ... << EOF) contains the commands, while the password is piped to sudo -S. This requires careful handling of sudo prompts and terminal allocation, often necessitating the use of -S or appropriate SSH flags like -tt if interactive TTY allocation is required for sudo.

FAQs on Executing Multiple Remote Commands via SSH

Q: What is the benefit of quoting the Here Document delimiter like 'EOF'

ANS: Quoting the delimiter, such as using 'EOF', prevents the local shell from performing any variable or command substitution within the body of the Here Document. This ensures that the script block is sent literally to the remote machine.

Q: How can local variables be used within an SSH Here Document

ANS: If the Here Document delimiter is unquoted (e.g., << EOF), the local shell performs variable substitution on the contents before sending them over SSH. For instance, ${LOCAL_VAR} will be replaced by its local value.

Q: Can I run a local function definition remotely over SSH

ANS: Yes, this is achieved by using declare -f function_name locally to capture the function’s source code and then executing it remotely via ssh remote_host "bash -c '$(declare -f func); func arg1 arg2'". This keeps local context variables accessible if quoted correctly.

Q: Is SSH multiplexing required for multiple commands

ANS: No, multiplexing is an optimization. It speeds up execution by reusing a single underlying TCP connection for subsequent SSH commands, which is beneficial for frequent, short command sequences, but standard methods work without it.
ssh otherhost &lt;&lt; EOF
  ls some_folder; 
  ./someaction.sh 'some params'
  pwd
  ./some_other_action 'other params'
EOF
ssh otherhost /bin/bash &lt;&lt; EOF
ssh otherhost /bin/bash &lt;&lt; EOF
touch "/tmp/${NAME}"
EOF
