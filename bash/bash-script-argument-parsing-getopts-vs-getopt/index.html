“Bash Script Argument Parsing: getopts vs getopt and Custom Solutions”

When developing robust shell scripts, correctly processing command-line options and arguments is crucial for user experience and script reliability. The standard tools, getopts and getopt, offer different capabilities but also present limitations, especially regarding long options (e.g., --help). This exploration details several established solutions, focusing on how each approach manages option definition, argument requirements, and error handling.

Solution 1: Standard getopts Implementation with Strict Validation

The getopts built-in is often the preferred method for handling single-character options due to its simplicity and native availability in most shells. However, it strictly enforces that options requiring arguments must have them immediately following the option letter, separated by whitespace or nothing at all.

The Script Structure using getopts

This implementation rigidly checks for required options (-s and -p) and validates the value for -s to be either 45 or 90.

#!/bin/bash

# Function to display usage information and exit
usage() { 
    echo "Usage: $0 [-s <45|90>] [-p <string>]" 1>&2
    exit 1 
}

# Initialize variables
s=""
p=""

# The OPTSTRING ":s:p:" dictates:
# : at the start: Enables silent error reporting (OPTERR is suppressed)
# s: : option -s requires an argument
# p: : option -p requires an argument
while getopts ":s:p:" o; do
    case "${o}" in
        s)
            s=${OPTARG}
            # Validate 's' value is exactly 45 or 90
            ((s == 45 || s == 90)) || usage
            ;;
        p)
            p=${OPTARG}
            ;;
        :)
            # This case catches missing arguments for options marked with ':' (like -s or -p)
            echo "Error: Option -$OPTARG requires an argument." >&2
            usage
            ;;
        \?)
            # This case catches unknown options
            echo "Error: Invalid option -$OPTARG" >&2
            usage
            ;;
    esac
done
shift $((OPTIND-1))

# Final check to ensure both required arguments were provided
if [ -z "${s}" ] || [ -z "${p}" ]; then
    usage
fi

echo "s = ${s}"
echo "p = ${p}"

Solution 2: Enhancing getopts Error Handling and Structure

This approach refines the getopts usage by explicitly handling errors silently (: in the OPTSTRING) and restructuring the case statement to offer more informative feedback when validation fails, particularly for numerical constraints.

Key getopts Syntax Details:

  • OPTSTRING: The string defines expected options. A colon after a letter (e.g., s:) signifies that the option requires an argument.
  • Silent Errors (:s:p:): Starting the string with a colon suppresses default error messages from getopts, allowing custom error reporting within the case block (e.g., catching ? for unknown options or : for missing arguments).
  • OPTARG: Holds the argument value for the current option.
#!/usr/bin/env bash

# Function to display help by grepping comments in the script itself
usage() { 
    echo "$0 usage:"
    # Extract usage details from comments starting with ". ) #"
    grep -E "^\s*\w+\)\s*#.*" $0 | sed -E 's/^\s*\w+\)\s*#\s*(.*)/\1/'
    exit 0 
}

# Check if any arguments were provided
[ $# -eq 0 ] && usage

# Use ":hs:p:" to enable silent error handling
while getopts ":hs:p:" arg; do
  case $arg in
    p) # Option -p requires an argument
      echo "p is ${OPTARG}"
      ;;
    s) # Option -s requires an argument (strength)
      strength=${OPTARG}
      # Numeric validation for strength
      [ $strength -eq 45 -o $strength -eq 90 ] \
        && echo "Strength set to $strength." \
        || { echo "Validation Error: Strength must be 45 or 90. Found '$strength'."; usage; exit 1; }
      ;;
    h) # Display help on -h
      usage
      exit 0
      ;;
    \? | :) # Handle unknown options or missing arguments silently
      echo "Error: Invalid option or missing argument for -$OPTARG" >&2
      usage
      exit 1
      ;;
  esac
done

# Shift past processed options
shift $((OPTIND-1))

Solution 3: Employing getopt for Long Options

When scripts require options spanning multiple characters (e.g., --version), the external utility getopt is often necessary. getopt processes arguments and outputs a standardized list of options ready for processing by eval set -- "$options".

getopt Syntax Forms and Argument Types:

getopt defines options using an optstring where:

  • h: A flag option requiring no value.
  • v:: A key-value option where the value is mandatory.
  • t::: A key-value option where the value is optional (indicated by double colons).

Crucially, getopt separates the list of valid options from the actual parameters passed to the script using --.

Elaborate Script Example using getopt

This example demonstrates defining both short (-v, -r, -V, -d) and long options (--help, --espo-version, etc.) simultaneously.

#!/bin/bash

# filename: commandLineParser.sh
# author: ExpertTechnicalWriter

showHelp() {
# Use 'cat << EOF' for clean multi-line output
cat << EOF  
Usage: ./commandLineParser.sh -v <version> [-hrV]
Installs pre-requisites for an application in Development mode.

-h, --help                Display help information.
-v, --espo-version <ver>  Specify target application version.
-r, --rebuild             Trigger build process steps.
-V, --verbose             Enable detailed execution logging.

EOF
}

# Default variable states
version="latest"
verbose=0
rebuilt=0

# Define short and long options for getopt
# Short options: hv:Vrd (h and r take no arg, v and d take arg)
# Long options: help,version:,verbose,rebuild,dryrun
OPTIONS_SPEC=$(getopt -l "help,version:,verbose,rebuild,dryrun" -o "hv:Vrd" -a -- "$@")

if [ $? != 0 ]; then 
    echo "Error processing options." >&2
    showHelp
    exit 2
fi

# Reset positional parameters based on getopt's parsed output
eval set -- "${OPTIONS_SPEC}"

while true; do
    case "$1" in
        -h|--help) 
            showHelp
            exit 0
            ;;
        -v|--version) 
            shift
            version="$1"
            ;;
        -V|--verbose)
            verbose=1
            set -xv  # Activate script tracing
            ;;
        -r|--rebuild)
            rebuilt=1
            ;;
        --)
            shift
            break;; # End of options
        *)
            echo "Internal error: Unhandled option $1" >&2
            showHelp
            exit 1
            ;;
    esac
    shift
done

echo "

Solution 5: POSIX getopts Compliance Check

For maximum portability across Unix-like systems, adhering closely to the POSIX specification for getopts is recommended. This standard approach clearly separates option handling from remaining arguments via shift $(($OPTIND - 1)).

#!/bin/sh
# POSIX compliant example using getopts

aflag=0
bflag=0
bval=""

# Process options: 'a' takes no argument, 'b:' requires one argument
while getopts "ab:" name; do
    case $name in
    a)    aflag=1;;
    b)    bflag=1
          bval="$OPTARG";;
    \?)   printf "Usage: %s: [-a] [-b value] args\n" "$0" >&2
          exit 2;;
    esac
done

if [ "$aflag" -eq 1 ]; then
    printf "Flag -a activated.\n"
fi
if [ "$bflag" -eq 1 ]; then
    printf 'Flag -b specified with value "%s".\n' "$bval"
fi

# Remove processed options and shift to remaining positional arguments
shift $(($OPTIND - 1))
printf "Positional arguments left: %s\n" "$*"

Solution 7: Custom Non-getopts/getopt Parsing for Long Options

When the limitations of getopt (especially its handling of spaces within arguments or its output format) become restrictive, a manual loop over arguments ($@) combined with prefix checks (-- or -) can yield a highly customized solution. This method allows for very flexible argument formats, including arguments without spaces (e.g., --package=value) or arguments that are flags (set to 1).

Custom Argument Formatting and Parsing:

This function formats arguments for variable assignment (e.g., --package-name becomes ARG_PACKAGE_NAME).

function formatArgument() {
  # Capitalize, remove leading --, replace - with _
  local ARGUMENT="${1^^}"
  ARGUMENT="${ARGUMENT/--/}"
  ARGUMENT="${ARGUMENT//-/_}"
  echo "${ARGUMENT}"
}

function parseArguments() {
  local PREVIOUS_ITEM=''
  local COUNT=0
  for CURRENT_ITEM in "${@}"
  do
    if [[ ${CURRENT_ITEM} == "--"* ]]; then
      # Argument starting with -- is treated as a flag (set to 1) unless the next item is an argument.
      printf -v "ARG_$(formatArgument "${CURRENT_ITEM}")" "%s" "1"
    else
      if [[ ${PREVIOUS_ITEM} == "--"* ]]; then
        # Previous item was a flag-like option, so CURRENT_ITEM is its value
        printf -v "ARG_$(formatArgument "${PREVIOUS_ITEM}")" "%s" "${CURRENT_ITEM}"
      else
        # Positional argument
        printf -v "ARG_${COUNT}" "%s" "${CURRENT_ITEM}"
      fi
    fi

    PREVIOUS_ITEM="${CURRENT_ITEM}"
    (( COUNT++ ))
  done
}

Solution 8: POSIX-Compliant Manual Argument Handling

An alternative to getopts that supports long options without relying on the external getopt utility involves manually checking prefixes (-s vs --sopt). This tends to be more POSIX-compliant than custom looping based on $@ but requires more case logic to manage argument consumption (using shift).

#!/bin/bash

usage() { 
    # Note: This usage function requires arguments to be space-separated from options
    printf "Usage: %s <req> [-s|--sopt <45|90>] [-p|--popt <string>]\n" "$0"
    return 1 
} 

main() { 
    # Check for the first required argument ($1)
    req="${1:?$(usage)}";
    shift; 
    s="";
    p="";
    
    while [ "$#" -ge 1 ]; do
        case "$1" in 
            # Handling short option -s or long option --sopt
            -s|--sopt) 
                shift;
                s="${1:?$(usage)}";
                # Validation
                [ "$s" -eq 45 ] || [ "$s" -eq 90 ] || { usage; return 1; } 
                ;; 
            # Handling option -p or --popt, requires argument
            -p|--popt) 
                shift; 
                p="${1:?$(usage)}";
                ;; 
            # Any other input is an error
            *) 
                usage;
                return 1; 
                ;;
        esac; 
        shift; # Move to the next argument after consuming the option and its value
    done; 
    
    printf "req = %s\ns = %s\np = %s\n" "$req" "$s" "$p"; 
};

main "$@"

FAQs on Bash Script Argument Parsing

Q: What is the main difference between getopts and getopt in Bash

ANS: getopts is a shell built-in that only handles single-character options (like -a, -b:). getopt is an external utility that supports long options (like --all, --backup=value) but requires specific command structuring and use of eval.

Q: How do I make an option optional in getopts

ANS: getopts itself does not natively support optional arguments for a single flag definition; if an argument is required (e.g., s:), getopts will raise an error if it’s missing. Optional arguments are best handled by getopt (using ::) or manual parsing.

Q: Why use eval set -- after running getopt

ANS: getopt reformats the arguments into a space-separated string that follows standard positional parameter conventions. eval set -- "$TEMP" resets the script’s positional parameters ($1, $2, etc.) to this standardized, parsable output.

Q: How can I handle long options without using the external getopt utility

ANS: You must implement manual parsing by looping through $@ and using case statements with prefix matching (e.g., checking if $1 starts with -- or -) and then explicitly shifting options and arguments as demonstrated in Solution 8.

#!/bin/bash

# A small example program for using the new getopt(1) program.
# This program will only work with bash(1)
# An similar program using the tcsh(1) script language can be found
# as parse.tcsh

# Example input and output (from the bash prompt):
# ./parse.bash -a par1 'another arg' --c-long 'wow!*\?' -cmore -b &quot; very long &quot;
# Option a
# Option c, no argument
# Option c, argument 'more'
# Option b, argument ' very long '
# Remaining arguments:
# --&gt; 'par1'
# --&gt; 'another arg'
# --&gt; 'wow!*\?'

# Note that we use `&quot;$@&quot;' to let each command-line parameter expand to a 
# separate word. The quotes around '$@' are essential!
# We need TEMP as the `eval set --' would nuke the return value of getopt.
TEMP=$(getopt -o ab:c:: --long a-long,b-long:,c-long:: \
              -n 'example.bash' -- &quot;$@&quot;)

if [ $? != 0 ] ; then echo &quot;Terminating...&quot; &gt;&amp;2 ; exit 1 ; fi

# Note the quotes around '$TEMP': they are essential!
eval set -- &quot;$TEMP&quot;

while true ; do
    case &quot;$1&quot; in
        -a|--a-long) echo &quot;Option a&quot; ; shift ;;
        -b|--b-long) echo &quot;Option b, argument '$2'&quot; ; shift 2 ;;
        -c|--c-long) 
            # c has an optional argument. As we are in quoted mode,
            # an empty parameter will be generated if its optional
            # argument is not found.
            case &quot;$2&quot; in
                &quot;&quot;) echo &quot;Option c, no argument&quot;; shift 2 ;;
                *)  echo &quot;Option c, argument '$2'&quot; ; shift 2 ;;
            esac ;;
        --) shift ; break ;;
        *) echo &quot;Internal error!&quot; ; exit 1 ;;
    esac
done
echo &quot;Remaining arguments:&quot;
for arg do echo '--&gt; '&quot;'$arg'&quot; ; done
