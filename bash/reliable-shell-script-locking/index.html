“Reliable Shell Script Locking: Comparing Atomic Methods to Prevent Concurrent Execution”

How can system administrators and developers ensure that only a single instance of a shell script runs concurrently? Implementing a reliable, atomic locking mechanism is crucial to prevent data corruption, race conditions, and unexpected behavior. Naive approaches often fail due to race conditions between checking for a lock and creating it. This exploration details several accepted, robust methods for achieving single-instance execution in shell environments.

Atomic Locking Strategies

The core requirement for dependable locking is atomicity—the operation to check and establish the lock must occur as a single, indivisible step.

1. Utilizing flock for Exclusive File Descriptor Locking (Solution 1, 4, 10, 12, 16, 21, 24)

The flock(1) utility, which wraps the flock(2) system call, is highly recommended for its kernel-level reliability, especially on local filesystems. It manages the lock directly on a file descriptor, avoiding many pitfalls associated with file system metadata checks.

Example using flock with a timeout:

This method attempts to secure an exclusive lock on file descriptor 200 pointing to a lock file for up to 10 seconds. If the lock is acquired, the enclosed code block runs; otherwise, it exits.

2. Atomic Directory Creation with mkdir (Solution 2, 6)

Creating a directory is an atomic operation on most modern filesystems. If mkdir succeeds, no other process has created that specific directory name at that instant; if it fails due to existence, the lock is held elsewhere. This method is often cited as more portable than flock across various UNIX-like systems.

3. Atomic File Creation with noclobber (Solution 8, 19, 22)

The shell option set -o noclobber prevents redirection (>) from overwriting an existing file. When combined with file creation, the operation becomes atomic because the shell uses open(pathname, O_CREAT|O_EXCL) internally.

This method pairs the atomic file creation with a trap to ensure cleanup, even upon signals like INT.

Handling Stale Locks and Portability

A significant challenge across many lock file methods is dealing with processes that terminate unexpectedly, leaving behind lock files or directories.

  • PID Checks: Storing the Process ID (PID) in a lock file (e.g., Solution 3, 11, 29) allows a new instance to check if the recorded PID is still active using kill -0. If the PID is dead, the lock is considered stale and can be reclaimed. Solution 19 improves this by storing a unique identifier (pid,ppid,lstart) to prevent PID wrap-around issues.
  • NFS Resistance (Solution 15): For environments where the lock needs to survive on NFS, atomic operations like ln (hard link) following an mktemp creation are suggested, relying on NFSv2/v3 atomicity guarantees for symlink and rename.

Portable Locking Function (Solution 15)

This function leverages mktemp to create a temporary file, writes the PID, and then attempts an atomic ln (hard link) to the final lock location. Success in linking confirms lock acquisition.

obtain_lock() {
  LOCK="${1}"
  LOCKDIR="$(dirname "${LOCK}")"
  LOCKFILE="$(basename "${LOCK}")"

  TMPLOCK=$(mktemp -p "${LOCKDIR}" "${LOCKFILE}XXXXXX" 2> /dev/null)
  if test "x${TMPLOCK}" == "x"; then
     echo "Unable to create temporary file." 1>&2
     return 1
  fi
  echo "$$" > "${TMPLOCK}"

  # Atomic attempt to obtain lock via hard link
  ln "${TMPLOCK}" "${LOCK}" 2> /dev/null
  if test $? -ne 0; then
     rm -f "${TMPLOCK}"
     echo "Unable to obtain lockfile." 1>&2
     if test -f "${LOCK}"; then
        echo "Current lock info held by: $(cat "${LOCK}")" 1>&2
     fi
     return 2
  fi
  rm -f "${TMPLOCK}"
  return 0
};

Comparison of Non-Atomic Methods

Some simpler methods exist but carry inherent risks:

  1. Naive File Existence Check (Solution 2, 26, 27): Checking if [ -e $LOCKFILE ] followed by creating it is vulnerable to race conditions where two processes pass the check almost simultaneously before either creates the file.
  2. Process Lookup by Name (Solution 20): Relying on pgrep or parsing ps output based on script name ($(basename $0)) is generally unreliable due to parsing complexities and cases where unrelated processes might match the name.

FAQs on Reliable Shell Script Locking

Q: Which shell locking method is considered most atomic

ANS: Methods leveraging kernel primitives like flock(2) (via flock(1)) or filesystem operations guaranteed to be atomic, such as mkdir, are significantly more reliable than simple file existence checks.

Q: How to clean up a lock file if the script terminates unexpectedly

ANS: Use the trap command in shell scripts. For instance, trap 'rm -f "$LOCKFILE"; exit $?' INT TERM EXIT ensures cleanup upon most standard exits or interruptions. Note that kill -9 (SIGKILL) cannot be trapped.

Q: Why is checking 'if [ -e lockfile ]' and then writing to it flawed

ANS: This sequence is not atomic. Two processes can execute the check simultaneously, both find the file absent, and then both proceed to write the lock file, leading to concurrent execution, defeating the purpose of the lock.

Q: Can flock locks be used reliably across NFS mounts

ANS: flock behavior on NFS is often unreliable, especially with older versions (pre-NFSv4). For cross-host or NFS locking, methods relying on atomic file creation/linking (like Solution 15) might offer better portability if the underlying NFS implementation supports atomic operations like rename or symlink.
