“Rust Non-Lexical Lifetimes Explained: Understanding Borrowing”

Rust’s non-lexical lifetimes (NLL) significantly refine how the compiler manages data borrowing, leading to more flexible and often more efficient code. To grasp NLL, it’s beneficial to first consider the concept of lexical lifetimes and the limitations they presented.

The Challenge of Lexical Lifetimes

In earlier Rust versions, borrows were governed by lexical lifetimes. This meant a borrow was considered valid from its point of creation until the end of the scope in which it was defined, regardless of whether the borrowed value was actually still in use.

Consider this Rust code snippet:

fn main() {
    let mut data_container = vec![10, 20, 30];
    let first_element_ref = &data_container[0]; // Immutable borrow
    data_container.push(40); // Attempt to mutate
}

With lexical lifetimes, the compiler would issue an error:

error[E0502]: cannot borrow `data_container` as mutable because it is also borrowed as immutable
 --> src/main.rs:4:5
  |
3 |     let first_element_ref = &data_container[0];
  |

## Solutions
-- immutable borrow occurs here
4 |     data_container.push(40);
  |     ^^^^^^^^^^^^^^^^^^^^^^^^ mutable borrow occurs here
5 | }
  | - immutable borrow ends here

The compiler correctly identified that data_container was immutably borrowed by first_element_ref. However, it conservatively assumed this borrow persisted until the end of the main function’s scope. A human reader can easily see that first_element_ref is never actually used after its creation.

The NLL Solution: Precise Borrow Tracking

Non-lexical lifetimes enable the Rust compiler to be more intelligent. Instead of a strict lexical boundary, NLL tracks the actual usage of a borrow. If a borrowed value is no longer in use, the borrow is considered ended, even if the scope hasn’t concluded.

This improved analysis allows the previous example to compile successfully:

fn main() {
    let mut data_container = vec![10, 20, 30];
    let first_element_ref = &data_container[0]; // Immutable borrow
    // first_element_ref is not used after this point
    data_container.push(40); // Now this is allowed
}

The compiler, with NLL, recognizes that first_element_ref is not used after its declaration, and therefore, the immutable borrow of data_container effectively ends before data_container.push(40) is called.

The goal of NLL is to make such borrow checking so natural that developers cease to think about the underlying mechanism, allowing Rust’s safety guarantees to work seamlessly.

Why Were Lexical Lifetimes Necessary?

The conservative nature of lexical lifetimes was a pragmatic choice during Rust’s development. The primary driver was the relative ease of implementation. Understanding scope boundaries (“blocks”) is simpler for a compiler than analyzing intricate data flow. Implementing precise borrow checking required a significant compiler overhaul, including the introduction of a mid-level intermediate representation (MIR) and a rewrite of the borrow checker to operate on MIR rather than the abstract syntax tree (AST). This allowed for more granular borrow rules.

While lexical lifetimes could sometimes impede programming flow, developers devised workarounds, often involving extra code blocks or temporary variables, to navigate these limitations. These patterns, though sometimes verbose, enabled Rust 1.0 to be a robust and usable language for many years before NLL became standard.

Interestingly, the constraints of lexical lifetimes also fostered the development of elegant and efficient programming patterns. A prime example is the entry API for HashMap:

Before NLL (and workaround for lexical lifetimes):

use std::collections::HashMap;

fn update_or_insert_value(mut data_map: HashMap<i32, i32>, key: i32) {
    match data_map.get_mut(&key) {
        Some(value) => *value += 1,
        None => {
            data_map.insert(key, 1);
        }
    }
}

This approach works but involves hashing the key twice. The lexical lifetime rules for get_mut would require the map to remain borrowed for the entire scope.

With NLL (or the efficient pattern inspired by NLL’s eventual arrival):

use std::collections::HashMap;

fn update_or_insert_value(mut data_map: HashMap<i32, i32>, key: i32) {
    *data_map.entry(key).or_insert(0) += 1;
}

This concise and efficient idiom leverages the entry API, avoiding double hashing and demonstrating how compiler design choices can influence programming paradigms.

Clarifying the Name: “Non-Lexical Borrowing”

The term “non-lexical lifetimes” can be a bit misleading. The feature doesn’t alter the actual lifespan of a value in memory. Instead, it refines how and when borrows are checked. A more precise, though perhaps less catchy, name might be “non-lexical borrowing” or refer to the underlying “MIR-based borrow checking.” The naming was primarily for internal compiler development and was not prioritized for external marketing.

Enabling and Using Non-Lexical Lifetimes

For projects targeting Rust 1.31 and later, migrating to the Rust 2018 Edition (by setting edition = "2018" in Cargo.toml) automatically enables non-lexical lifetimes.

[package]
name = "my_project"
version = "0.1.0"
edition = "2018" # This line enables NLL

From Rust 1.36 onwards, even the Rust 2015 edition benefits from NLL.

Initially, NLL was implemented in a “migration mode.” If the NLL borrow checker passed, compilation proceeded. If it failed, the older borrow checker was used. If the older checker permitted the code, a warning was issued, signaling that the code might break in future Rust versions and recommended updating.

For users of nightly Rust, you can explicitly opt into stricter NLL enforcement with the following attribute:

#![feature(nll)]

Experimental versions of NLL can be accessed via the compiler flag -Z polonius.

Real-World Scenarios Improved by NLL

Non-lexical lifetimes address many common issues developers encounter, including:

  • Returning references from data structures like Vec or HashMap without extended borrows.
  • Preventing HashMap::get_mut() from consuming the map for an entire scope.
  • Resolving errors related to borrowing immutably and mutably in function arguments.
  • Facilitating more efficient update-or-insert operations on collections.
  • Allowing bindings to be released earlier than their scope’s end.
  • Resolving borrow conflicts when iterating and modifying recursive data structures.
  • Correctly handling borrows when returning results from operations like StdinLock.
  • Fixing “collaterally moved” errors during complex data structure deconstruction.

FAQs on Rust Non-Lexical Lifetimes

Q: What is the primary benefit of non-lexical lifetimes in Rust

ANS: Non-lexical lifetimes allow the Rust compiler to more precisely track borrow usage, enabling code that was previously rejected due to conservative lexical lifetime rules. This leads to increased flexibility and often more efficient code without sacrificing safety.

Q: How do I enable non-lexical lifetimes in my Rust project

ANS: For Rust 1.31 and later, migrating your project to the Rust 2018 edition by setting edition = "2018" in your Cargo.toml file automatically enables non-lexical lifetimes. From Rust 1.36 onwards, the Rust 2015 edition also supports them.

Q: Is there a difference between non-lexical lifetimes and lexical lifetimes

ANS: Yes, lexical lifetimes consider a borrow valid until the end of its scope. Non-lexical lifetimes, however, analyze the actual usage of the borrow, ending it as soon as the borrowed data is no longer referenced, even if the scope has not ended.

Q: Can non-lexical lifetimes make my Rust code unsafe

ANS: No, non-lexical lifetimes are designed to enhance the precision of Rust’s existing safety guarantees. They allow more safe code to compile, rather than introducing new vulnerabilities.

Q: What is MIR in the context of Rust's borrow checker

ANS: MIR stands for Mid-level Intermediate Representation. Rust’s borrow checker, especially with non-lexical lifetimes, operates on this MIR representation of the code to perform more detailed and accurate borrow analysis compared to working directly with the Abstract Syntax Tree (AST).
