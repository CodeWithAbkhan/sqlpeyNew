“Implementing Heterogeneous Collections in Rust: Trait Objects vs Enums”

Handling Different Types with a Shared Trait

When designing systems where multiple, unrelated types must be treated uniformly via a shared interface (a trait), Rust offers powerful mechanisms. The core challenge lies in ensuring the compiler can manage storage and method calls for these disparate types within a single container.

Pattern 1: Using Trait Objects with Boxing

The most flexible approach for an open-ended set of types implementing a trait is the use of trait objects. A trait object essentially erases the concrete type information at compile time, allowing the collection to hold pointers to data that satisfy the trait constraints.

To store these trait objects on the heap, preventing size issues within a Vec, they are typically wrapped in a smart pointer like Box.

The structure looks like this: Vec<Box<dyn TraitName + TraitBounds>>.

  1. Box<dyn ThingTrait + 'static>: This signifies a pointer to heap-allocated data that implements ThingTrait. The 'static bound means the data does not contain any non-static references. This is the most common implementation for general collections.
  2. Box<dyn ThingTrait + 'a>: If the underlying data must borrow from its context for a specific lifetime 'a, you must specify that lifetime bound on the trait object itself.

Alternatively, you can store references directly, though this imposes strict lifetime constraints on the collection itself:

  • Vec<&dyn ThingTrait>: A vector of references to dynamically dispatched trait implementations.

Trait objects fundamentally introduce indirection and rely on dynamic dispatch (vtable lookups at runtime) to invoke the correct method implementation for the underlying concrete type.

Consider the scenario where Monster1 and Monster2 both implement ThingTrait:

trait ThingTrait {
    fn attack(&self);
}

struct ThingRecord { x: i32, y: i32 }

struct Monster1 {
    thing_record: ThingRecord,
    num_arrows: u32,
}

impl ThingTrait for Monster1 {
    fn attack(&self) {
        println!("Monster 1 unleashes an attack!");
    }
}

struct Monster2 {
    thing_record: ThingRecord,
    num_fireballs: u32,
}

impl ThingTrait for Monster2 {
    fn attack(&self) {
        println!("Monster 2 casts a massive fireball!");
    }
}

fn main_trait_object() {
    let m1 = Monster1 {
        thing_record: ThingRecord { x: 10, y: 5 },
        num_arrows: 5,
    };

    let m2 = Monster2 {
        thing_record: ThingRecord { x: 20, y: 15 },
        num_fireballs: 100,
    };

    // The collection holds heap-allocated, dynamically dispatched trait objects
    let things: Vec<Box<dyn ThingTrait>> = vec![Box::new(m1), Box::new(m2)];

    for entity in &things {
        entity.attack();
    }
}

Other forms of smart pointers used for trait objects include Rc<dyn SomeTrait> or Arc<dyn SomeTrait> when shared ownership or thread safety is required, respectively.

Pattern 2: Using Enums for Fixed Alternatives

If the set of types that can appear in the collection is known and finite at compile time, using an enum is often a cleaner, and sometimes more performant, alternative to trait objects.

An enum encapsulates all possible concrete types into a single, known structure.

enum Monster {
    One(Monster1),
    Two(Monster2),
}

impl Monster {
    fn attack(&self) {
        // Match statement handles dynamic dispatch logic at runtime
        match self {
            Monster::One(_) => println!("Monster 1 attacks via enum match"),
            Monster::Two(_) => println!("Monster 2 attacks via enum match"),
        }
    }
}

fn main_enum() {
    let m1 = Monster1 {
        thing_record: ThingRecord { x: 42, y: 32 },
        num_arrows: 2,
    };

    let m2 = Monster2 {
        thing_record: ThingRecord { x: 42, y: 32 },
        num_fireballs: 65,
    };

    // The collection holds the actual enum variants
    let things = vec![Monster::One(m1), Monster::Two(m2)];

    for entity in &things {
        entity.attack();
    }
}

While enums still involve a runtime check (the match statement) to determine which variant is active, they avoid the indirection overhead associated with trait object vtables, potentially offering better cache locality. However, adding a new type requires modifying the enum definition and all associated match arms—making it less extensible than trait objects.

FAQs on Implementing Heterogeneous Collections in Rust

Q: What is the main trade-off when using boxed trait objects

ANS: The primary trade-offs are the introduction of indirection (heap allocation via Box and vtable lookups for dispatch) compared to non-indirected structures, although this cost allows for greater runtime flexibility and extensibility.

Q: Can I use a Vec of references to traits without boxing

ANS: Yes, you can use Vec<&dyn ThingTrait>, but this necessitates that all items stored live at least as long as the collection itself (i.e., they must satisfy the lifetime parameter bound, often 'static or a specific borrowed lifetime 'a).

Q: When is an enum superior to a trait object collection

ANS: An enum is generally preferred when the set of concrete types is fixed and small. Enums can offer better performance by avoiding heap allocation for every item (if small enough to fit within the enum discriminant) and leveraging pattern matching over vtable lookups.
