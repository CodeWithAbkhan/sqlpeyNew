“Rust Iterators: Differentiating iter, iter_mut, and into_iter Behavior”

In Rust development, particularly when dealing with collections like Vec<T>, correctly choosing how to iterate is paramount for managing ownership and mutation. The methods iter(), iter_mut(), and into_iter() offer distinct ways to traverse data, each impacting the ownership of the elements yielded.

What is the fundamental difference in the items yielded by the iterators returned by iter(), iter_mut(), and into_iter()?

The item type yielded depends heavily on the context and the specific implementation of the IntoIterator trait for the object you are calling the method on:

  • iter(): By convention, this method yields immutable references (&T) to the elements. It borrows the collection immutably.
  • iter_mut(): By convention, this method yields mutable references (&mut T) to the elements, allowing in-place modification. It borrows the collection mutably.
  • into_iter(): This method, derived from the IntoIterator trait, can yield owned values (T), immutable references (&T), or mutable references (&mut T), depending on how the collection is passed to it.

Diving Deep into IntoIterator

The behavior of into_iter() is determined by the IntoIterator trait definition:

pub trait IntoIterator 
where
    <Self::IntoIter as Iterator>::Item == Self::Item, 
{
    type Item;
    type IntoIter: Iterator;
    fn into_iter(self) -> Self::IntoIter;
}

If a type implements this trait, it defines how it is converted into an iterator. For a Vec<T>, the Vec type implements IntoIterator three times, corresponding to different ways it can be consumed or borrowed:

  1. Consuming the Vec<T> (by value): When called on Vec<T> directly (taking self), it consumes the vector, and the resulting iterator yields owned items (T).

    // Example of consuming Vec<T>
impl<T> IntoIterator for Vec<T> {
    type Item = T; // Yields owned values
    type IntoIter = IntoIter<T>;
    fn into_iter(mut self) -> IntoIter<T> { /* ... */ }
}

  2. Borrowing Vec<T> immutably: When called on an immutable reference &'a Vec<T>, the iterator yields immutable references (&'a T).

    // Example of immutable borrow
impl<'a, T> IntoIterator for &'a Vec<T> {
    type Item = &'a T; // Yields immutable references
    type IntoIter = slice::Iter<'a, T>;
    fn into_iter(self) -> slice::Iter<'a, T> { /* ... */ }
}

  3. Borrowing Vec<T> mutably: When called on a mutable reference &'a mut Vec<T>, the iterator yields mutable references (&'a mut T).

    // Example of mutable borrow
impl<'a, T> IntoIterator for &'a mut Vec<T> {
    type Item = &'a mut T; // Yields mutable references
    type IntoIter = slice::IterMut<'a, T>;
    fn into_iter(self) -> slice::IterMut<'a, T> { /* ... */ }
}

iter() vs. into_iter(): Context Dependency vs. Inherent Methods

What makes into_iter() potentially surprising compared to iter() and iter_mut()?

The key differentiator lies in convention versus contract:

  • iter() and iter_mut() are inherent methods on the collection type. Their return type is fixed by definition: iter() always returns something yielding &T, and iter_mut() always returns something yielding &mut T.
  • into_iter() is defined via the IntoIterator trait, whose Item type is chosen by the implementer. This leads to context dependency. If you use a raw for loop construct (for item in collection { ... }), Rust implicitly calls collection.into_iter().

Prior to Rust version 1.53.0, arrays ([T; N]) behaved surprisingly, only implementing IntoIterator for references (&[T; N] and &mut [T; N]), forcing implicit borrowing. Modern Rust handles arrays more consistently, but the core concept remains: into_iter() adapts based on the reference status of self.

Ergonomics: When to Use &collection vs. collection.iter()

If &v (which calls v.as_ref().into_iter()) is equivalent to v.iter(), why keep both methods?

This exists for ergonomics and clarity:

  1. For loops: Using for item in &v is syntactically cleaner than for item in v.iter(). Similarly, for item in &mut v is concise for mutable iteration.

  2. Method Chaining: When chaining iterator adaptors like map or filter, v.iter() is generally clearer than (&v).into_iter().

Consider this clarity comparison:

let v = vec![10, 20, 30];

// Clearer use of iter() for chaining
let squared_immutable: Vec<i32> = v.iter()
    .map(|x| x * x)
    .collect();

// Less idiomatic, though functionally equivalent due to IntoIterator implementation on &Vec<T>
let squared_alternative: Vec<i32> = (&v).into_iter()
    .map(|x| x * x)
    .collect();

Implementing Iterators: Conventions for Custom Types

When creating a custom collection type, how should one decide whether to implement Iterator directly or use the IntoIterator pattern?

If your type has only a single, obvious way to iterate, implement both the Iterator trait directly on the type and the IntoIterator trait to produce the associated iterator structure.

However, if multiple distinct iteration patterns exist (e.g., iterating by bytes vs. iterating by characters), it is better practice to provide specific methods for each pattern (like String::bytes() or String::chars()) rather than relying solely on into_iter() or iter().

For scenarios where an iteration requires an intermediate structure (like traversing a linked list), you define a separate iterator struct (e.g., ListIter<T>) that implements Iterator, and then implement IntoIterator for your main collection (List<T>) to return an instance of that iterator struct.

Custom Iterator Structure Example

If we define a custom Structure<T> that we want to iterate over immutably:

struct CustomList<T> { /* ... internal structure ... */ }

// 1. Define the specific iterator structure
struct CustomListIterator<'a, T> {
    // Holds a reference to track position
    cursor: &'a CustomList<T>, 
}

impl<'a, T> Iterator for CustomListIterator<'a, T> {
  type Item = &'a T;
  fn next(&mut self) -> Option<Self::Item> {
    // Logic to advance cursor and yield next element reference
    None // Placeholder
  }
}

// 2. Implement IntoIterator for the container to produce the iterator
impl<'a, T> IntoIterator for &'a CustomList<T> {
    type Item = &'a T;
    type IntoIter = CustomListIterator<'a, T>;
    
    fn into_iter(self) -> Self::IntoIter { 
        CustomListIterator { cursor: self } 
    }
}

This pattern allows generic functions to consume any structure implementing IntoIterator via a for loop:

fn consume_iterable<I>(container: I) 
where 
    I: IntoIterator // This trait bound accepts anything usable in a 'for' loop
{
    for element in container {
        println!("Processing element: {:?}", element);
    }
}

Here are unit tests illustrating the item types received:

#[test]
fn demonstration_iter_behavior() {
    let source_vector = vec![101, 102, 103];
    let mut iterator = source_vector.iter();

    // iter() yields immutable references
    assert_eq!(iterator.next(), Some(&101));
    assert_eq!(iterator.next(), Some(&102));
    // source_vector remains valid here
}

#[test]
fn demonstration_into_iter_ownership_transfer() {
    let source_vector = vec![201, 202, 203];
    let mut iterator = source_vector.into_iter();

    // into_iter() yields owned values, consuming the vector
    assert_eq!(iterator.next(), Some(201));
    assert_eq!(iterator.next(), Some(202));
    // If we tried to use source_vector here, it would fail compilation due to move
}

#[test]
fn demonstration_iter_mut_mutation() {
    let mut source_vector = vec![301, 302, 303];
    let mut iterator = source_vector.iter_mut();

    // iter_mut() yields mutable references, allowing modification
    if let Some(val) = iterator.next() {
        *val *= 10; // Mutates the element inside the vector
    }
    
    // Check mutation effect
    assert_eq!(source_vector[0], 3010);
}

FAQs on Rust Iterators Differentiation

Q: What does iter() return when used on a Vec

ANS: By convention, iter() on a Vec<T> returns an iterator yielding immutable references, specifically of type &T.

Q: Can into_iter() ever return a reference

ANS: Yes, if into_iter() is called on a reference type (like &Vec<T> or &mut Vec<T>), its implementation of IntoIterator is set up to yield references (&T or &mut T respectively).

Q: Why is iter_mut not covered by IntoIterator convention

ANS: iter_mut() is an inherent method whose contract is always to provide mutable references (&mut T), whereas into_iter() uses the IntoIterator trait which allows flexibility in the yielded item type based on context.

Q: Is using &v in a for loop the same as v.iter()

ANS: For iteration over a reference to a collection like Vec, using for x in &v implicitly calls (&v).into_iter(), which is conventionally equivalent to v.iter(), yielding immutable references.
