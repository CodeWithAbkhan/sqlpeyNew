“Rust Method Resolution: Dereferencing, Auto-Referencing, and Receiver Types”

How Rust Resolves Method Calls

The mechanism behind method resolution in Rust is designed to be intuitive, often performing what you intend through a series of checks and potential automatic adjustments.

The fundamental algorithm can be broken down into these steps:

  1. Iterate through Dereference Steps: For a given receiver expression (e.g., foo in foo.bar()), Rust repeatedly dereferences its type. For each dereferenced type U, it checks for a matching method.
  2. Exact Match (By Value): If a method named bar exists where its receiver parameter (the self parameter) exactly matches U, that method is selected. This is often referred to as a “by value” method.
  3. Auto-Reference: If an exact match isn’t found, Rust attempts to add a single auto-reference (either & for an immutable reference or &mut for a mutable reference) to the current receiver type U. If a method exists that accepts &U or &mut U as its receiver, that method is chosen. These are “autorefd methods.”
  4. Inherent vs. Trait Methods: Inherent methods (those defined directly within an impl block for a type) take precedence over trait methods. If both an inherent method and a trait method match, the inherent method is called.
  5. Ambiguity and Errors: It’s an error if multiple trait methods are valid at any step. Similarly, it’s an error if the process completes without finding any matching method. Recursive Deref implementations are also disallowed to prevent infinite loops.

Key Consideration: Receiver Type vs. Self Type It’s crucial to note that the matching process considers the receiver type of the method, not the Self type of the trait. For instance, in impl MyTrait for MyStruct { fn my_method(&self) {} }, the method looks for a receiver of type &MyStruct.

Practical Examples and Scenarios

Let’s illustrate this with several scenarios. We’ll define a simple struct X and traits M and RefM to demonstrate.

// Define a sample struct

struct X {
    val: i32,
}

// Define traits for method calls
trait M {

}

    fn m(&self) { println!("&X::m() called"); }
}

impl M for &mut X {
    fn m(&self) { println!("&mut X::m() called"); }
}


impl RefM for i32 {
    fn refm(&self) { println!("i32::refm() called"); }
}

impl RefM for X {
    fn refm(&self) { println!("X::refm() called"); }
}

impl RefM for &X {
    fn refm(&self) { println!("&X::refm() called"); }
}

impl RefM for &mut X {
    fn refm(&self) { println!("&mut X::refm() called"); }
}

impl RefM for &&X {
    fn refm(&self) { println!("&&X::refm() called"); }
}

impl RefM for &&&X {
    fn refm(&self) { println!("&&&X::refm() called"); }
}

impl RefM for &&&&X {
    fn refm(&self) { println!("&&&&X::refm() called"); }
}

Scenario 1: Calling m()

Consider the call foo.m() where foo has different types:

  • (*Box::new(X { val: 42 })).m();

    • The receiver type starts as X.
    • The list of candidate receiver types: [X, &X, &mut X, i32, &i32, &mut i32] (after dereferencing Box and potential coercion of i32).
    • X::m() is found first.

  • let x_instance = X { val: 42 }; x_instance.m();

    • The receiver type is X.
    • The candidate list starts with [X, &X, &mut X, i32, &i32, &mut i32].
    • X::m() is matched directly.

  • let x_ref = &X { val: 42 }; x_ref.m();

    • The receiver type is &X.
    • The candidate list starts with [&X, &&X, &mut &X, X, &X, &mut X, i32, &i32, &mut i32].
    • &X::m() is matched directly.

  • let x_double_ref = &&X { val: 42 }; x_double_ref.m();

    • Receiver type is &&X.
    • Candidate list: [&&X, &&&X, &mut &&X, &X, &&X, &mut &X, X, &X, &mut X, i32, &i32, &mut i32].
    • &&X::m() is matched.

Scenario 2: Calling refm()

Now, let’s analyze calls to refm():

  • let x_instance = X { val: 42 }; x_instance.refm();

    • Receiver type: X.
    • Candidate list: [X, &X, &mut X, i32, &i32, &mut i32].
    • X::refm() is selected.

  • let x_ref = &X { val: 42 }; x_ref.refm();

    • Receiver type: &X.
    • Candidate list: [&X, &&X, &mut &X, X, &X, &mut X, i32, &i32, &mut i32].
    • &X::refm() is selected.

  • let x_double_ref = &&X { val: 42 }; x_double_ref.refm();

    • Receiver type: &&X.
    • Candidate list: [&&X, &&&X, &mut &&X, &X, &&X, &mut &X, X, &X, &mut X, i32, &i32, &mut i32].
    • The exact match &&X::refm() is not found.
    • An auto-reference is attempted on &&X to get &&&X.
    • &&&X::refm() is found and called.

  • let x_quad_ref = &&&&X { val: 42 }; x_quad_ref.refm();

    • Receiver type: &&&&X.
    • Candidate list begins with &&&&X. No direct match.
    • Dereference to &&&X.
    • &&&X::refm() is found and called.

Scenario 3: Value vs. Reference Behavior

Consider example.m() where M::m has different receiver types:

  • impl M for X { fn m(&self) { ... } }

    • This method takes &self.
    • When called as x_instance.m(), X::m(&x_instance) is invoked.

  • impl M for X { fn m(self) { ... } } (If X was Copy or Clone, this could work)

    • This method takes self by value.
    • If called as x_instance.m(), this would try to move x_instance. A subsequent use of x_instance would cause a compile-time error.
    • If X is Copy, x_instance.m() would effectively become M::m(x_instance) where x_instance is copied.

The behavior of methods taking self by value can differ significantly. If the type is not Copy, it involves a move. If it is Copy, it behaves more like a clone.

Alternative Perspective on Method Resolution

Another way to think about it, as described in Solution 3, is to focus on the parameter type of the method signature itself.

For a call like (&X{val:42}).refm();:

  1. The expression before the dot is &X{val:42}.

  2. Consider the trait RefM and its method refm. Let’s look at the signatures of potential refm implementations:

    • impl RefM for i32 { fn refm(&self) } -> expects &i32
    • impl RefM for X { fn refm(&self) } -> expects &X
    • impl RefM for &X { fn refm(&self) } -> expects &&X
    • impl RefM for &&X { fn refm(&self) } -> expects &&&X

  3. The call (&X{val:42}).refm() has an expression of type &X.

  4. The method signature fn refm(&self) for impl RefM for X requires an &X. This matches the type of the expression &X{val:42} directly. Therefore, X::refm is chosen.

If the receiver type doesn’t directly match any method’s parameter type, Rust will then try automatic dereferencing or auto-referencing.

Summary of Method Call Resolution Rules

  • Dereference First: Rust walks down the chain of references.
  • Auto-Ref Second: If no direct match, it tries adding a reference.
  • Inherent Methods First: Methods defined directly on a type have priority.
  • Exact Receiver Match: The method’s self parameter type is the key.

This systematic process ensures that method calls are resolved correctly, even across complex type hierarchies. For more in-depth details on how Rust handles expressions and type coercion, refer to the Rustonomicon or the Rust Reference .

FAQs on Rust Method Resolution

Q: How does Rust find the correct method when calling something like obj.method()

ANS: Rust systematically checks the type of obj. It first looks for methods defined directly on obj’s type. If not found, it considers methods from traits implemented for that type. It also considers potential auto-referencing (& or &mut) and dereferencing operations on obj’s type to find a matching method signature.

Q: What happens if obj is a reference like &my_struct

ANS: If obj is &my_struct, Rust first checks for methods that take &self (an immutable reference to my_struct). If that doesn’t exist, it might try methods that take &&self (an immutable reference to &my_struct), or even dereference obj to my_struct and look for methods taking self by value.

Q: Do inherent methods have priority over trait methods

ANS: Yes, inherent methods defined directly on a type (impl MyStruct { fn my_method(&self) { ... } }) take precedence over methods with the same name provided by traits that MyStruct implements.

Q: What is an auto-reference in Rust method calls

ANS: An auto-reference is when Rust automatically adds a & or &mut to the receiver type if a direct method match isn’t found. For example, if you call my_val.method() and method is defined for &my_val but not my_val itself, Rust might insert &my_val to call the appropriate method.

Q: Can Rust auto-dereference multiple times

ANS: Rust’s primary mechanism is auto-referencing. While it can dereference through multiple layers of references to find a match (e.g., &&&T might be dereferenced to &T or T), the auto-referencing step typically applies only once to add a reference, not multiple references like &&.
