“Spring Security CORS Issues: Preflight OPTIONS Requests and Configuration”

When building modern web applications, especially those involving frontend frameworks like Angular or React communicating with a Spring Boot backend, you often encounter Cross-Origin Resource Sharing (CORS) challenges. A common stumbling block is the handling of preflight requests, which use the HTTP OPTIONS method. These requests are sent by browsers before the actual request (like GET, POST, etc.) to determine if the server permits the cross-origin request. If not configured correctly, these preflight requests can fail, leading to various errors in your browser’s developer console.

Understanding the Preflight Request Process

The preflight request is a mechanism to ensure a server is aware of and permits cross-origin requests before the browser sends the actual, potentially sensitive, request. Here’s how it typically works:

  1. Initiation: The browser detects a cross-origin request (different domain, protocol, or port).
  2. Preflight Request: Before the main request, the browser sends an HTTP OPTIONS request to the target URL. This request includes specific headers:
    • Access-Control-Request-Method: Indicates the HTTP method of the actual request (e.g., GET, POST).
    • Access-Control-Request-Headers: Lists the HTTP headers that will be included in the actual request.
  3. Server Response: The server inspects these headers and responds with Access-Control-Allow-Origin, Access-Control-Allow-Methods, Access-Control-Allow-Headers, and potentially Access-Control-Max-Age.
  4. Authorization: If the response indicates that the origin, method, and headers are allowed, the browser proceeds to send the actual request. Otherwise, it blocks the request and logs a CORS error.

Failure often stems from Spring Security intercepting the OPTIONS request before CORS configuration is applied, leading it to believe the request is unauthenticated or unauthorized.

How to Configure Spring Security for CORS Preflight Requests

Several approaches can be employed to correctly configure Spring Security to handle CORS preflight requests. The key is to ensure that OPTIONS requests are permitted before other security constraints are applied.

Solution 1: Permitting OPTIONS Method in configure(HttpSecurity)

For older versions of Spring Security (like those used with Spring Security 3), you could explicitly permit OPTIONS requests within your HttpSecurity configuration.

// Spring Security 3 Example
@Override
protected void configure(HttpSecurity http) throws Exception {
   http
       .authorizeRequests()
           .antMatchers(HttpMethod.OPTIONS, "/**").permitAll() // Allow OPTIONS requests
           .antMatchers("/login").permitAll()
           .anyRequest().fullyAuthenticated()
           .and()
       .httpBasic()
           .and()
       .sessionManagement()
           .sessionCreationPolicy(SessionCreationPolicy.STATELESS)
           .and()
       .csrf().disable();
}

// Ensure your CORS configuration is also present (e.g., via WebMvcConfigurer)
@Configuration
@EnableWebMvc
public class CORSConfig extends WebMvcConfigurerAdapter  {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("*"); // Or more specific mappings
    }
}

Solution 2: Using CorsFilter (Spring Security 4.2.0+)

Spring Security provides first-class support for CORS, typically via a CorsFilter. This filter should be processed before Spring Security’s main security filters because preflight requests often lack session cookies, which Spring Security might interpret as unauthenticated.

// Spring Security 4.x and Spring Boot 1.4/1.5
@Configuration
@EnableWebSecurity
public class WebSecurityConfig extends WebSecurityConfigurerAdapter {

  @Override
  protected void configure(HttpSecurity http) throws Exception {
      // By default, Spring Security uses a Bean named corsConfigurationSource
      http.cors().and()
          // Other security configurations...
          // .antMatchers(...).permitAll()
          // .anyRequest().authenticated()
          // ...
          ;
  }

  @Bean
  CorsConfigurationSource corsConfigurationSource() {
      CorsConfiguration configuration = new CorsConfiguration();
      configuration.setAllowedOrigins(Arrays.asList("https://example.com")); // Restrict to specific origins
      configuration.setAllowedMethods(Arrays.asList("GET", "POST", "PUT", "DELETE", "OPTIONS")); // Include OPTIONS
      UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
      source.registerCorsConfiguration("/**", configuration);
      return source;
  }
}

Solution 3: Spring Security 5/6 Configuration

For newer versions of Spring Security, the integration is streamlined. You can enable CORS support directly in the HttpSecurity configuration.

// Spring Security 5/6
@Configuration
@EnableWebSecurity
public class WebSecurityConfig {

  @Bean
  public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
      http
          // By default, Spring Security uses a Bean named corsConfigurationSource
          .cors(withDefaults()) // Enables CORS support
          // Other security configurations...
          // .authorizeHttpRequests(auth -> auth
          //     .requestMatchers("/api/public/**").permitAll()
          //     .anyRequest().authenticated()
          // )
          // ...
      return http.build();
  }

  @Bean
  CorsConfigurationSource corsConfigurationSource() {
      CorsConfiguration configuration = new CorsConfiguration();
      configuration.setAllowedOrigins(Arrays.asList("https://example.com"));
      configuration.setAllowedMethods(Arrays.asList("GET", "POST", "PUT", "DELETE", "OPTIONS"));
      UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
      source.registerCorsConfiguration("/**", configuration);
      return source;
  }
}

Important Note: When using Spring MVC’s CORS support (e.g., WebMvcConfigurer), Spring Security 5/6 can often pick up that configuration automatically, eliminating the need to configure it twice.

Solution 4: Simplified CORS Configuration with WebMvcConfigurer

A common and effective way to manage CORS is by implementing WebMvcConfigurer and defining CORS mappings.

@Configuration
@EnableWebMvc // Important for WebMvcConfigurer to be picked up
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/**") // Apply to all paths
                .allowedOrigins("*") // Or specify allowed origins like "https://your-frontend.com"
                .allowedHeaders("*") // Or specify allowed headers
                .allowedMethods("HEAD", "GET", "PUT", "POST", "DELETE", "PATCH", "OPTIONS"); // Include OPTIONS
    }
}

If you’re using Spring Boot 2.3.1 or later, you can define this as a @Bean:

@SpringBootApplication
public class RestServiceCorsApplication {

    public static void main(String[] args) {
        SpringApplication.run(RestServiceCorsApplication.class, args);
    }

    @Bean
    public WebMvcConfigurer corsConfigurer() {
        return new WebMvcConfigurer() {
            @Override
            public void addCorsMappings(CorsRegistry registry) {
                registry.addMapping("/**").allowedOrigins("*").allowedHeaders("*").allowedMethods("*");
            }
        };
    }
}

Solution 5: Customizing CorsConfigurationSource Bean

You can manually create and configure the CorsConfigurationSource Bean to have finer control over allowed methods and origins.

@Bean
CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration cors = new CorsConfiguration();
    // Default methods include POST, HEAD, GET. Add others as needed.
    cors.setAllowedMethods(Arrays.asList("POST", "GET", "PUT", "HEAD", "DELETE", "OPTIONS"));
    // Apply default values, or set others explicitly
    // cors.applyPermitDefaultValues() or manually configure like:
    // cors.setAllowedOrigins(Arrays.asList("*"));
    // cors.setAllowedHeaders(Arrays.asList("Authorization", "Cache-Control", "Content-Type"));

    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", cors); // Apply to all paths
    return source;
}

Solution 6: Enforcing Custom CORS Configuration with HttpSecurity

In some cases, you might need to explicitly tell HttpSecurity to use your custom CORS configuration.

@Override
protected void configure(HttpSecurity http) throws Exception {
   http
       // ... other configurations
       .cors(cors -> cors.configurationSource(customCorsConfigurationSource())) // Use your custom source bean
       // ...
   ;
}

// Define your customCorsConfigurationSource() bean as shown in Solution 5

Solution 7: Using CorsFilter with Highest Precedence

When dealing with complex filter chains or issues with OAuth security, ensuring the CorsFilter is processed with the highest precedence can resolve conflicts.

@Bean
public FilterRegistrationBean<CorsFilter> corsFilter() {
    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowCredentials(true);
    config.addAllowedOrigin("*"); // Consider restricting this in production
    config.addAllowedHeader("*");
    config.addAllowedMethod("*"); // Or list specific methods including OPTIONS
    source.registerCorsConfiguration("/**", config);
    FilterRegistrationBean<CorsFilter> bean = new FilterRegistrationBean<>(new CorsFilter(source));
    bean.setOrder(Ordered.HIGHEST_PRECEDENCE); // Key for ensuring it runs first
    return bean;
}

Solution 8: Combined FilterRegistrationBean and CorsFilter

A robust approach for early filter execution:

@Component
public class CorsFilterConfig {

    public static final List<String> allowedOrigins = Arrays.asList("*"); // Or specific origins

    @Bean
    public FilterRegistrationBean<CorsFilter> initCorsFilter() {
        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        CorsConfiguration config = new CorsConfiguration();
        config.setAllowCredentials(true);
        config.setAllowedHeaders(Arrays.asList("Authorization", "Cache-Control", "Content-Type"));
        config.addAllowedMethod("*"); // Covers OPTIONS
        config.setAllowedOrigins(allowedOrigins);
        source.registerCorsConfiguration("/**", config);

        FilterRegistrationBean<CorsFilter> bean = new FilterRegistrationBean<>(new CorsFilter(source));
        bean.setOrder(Ordered.HIGHEST_PRECEDENCE);
        return bean;
    }
}

Solution 9: @CrossOrigin Annotation and HttpSecurity Configuration

For specific controllers or methods, the @CrossOrigin annotation can be used. Combined with enabling CORS in HttpSecurity, this is a powerful approach.

@CrossOrigin(origins = "*") // Apply to the controller or specific methods
@RestController
public class MyController {
    // ... controller methods
}

// In SecurityConfig:
@Configuration
@EnableWebSecurity
public class SecurityConfig extends WebSecurityConfigurerAdapter {
    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
            .csrf().disable()
            // Ensure CORS is enabled in security config
            .cors().and()
            // ... other configurations
            .authorizeRequests()
                .antMatchers(HttpMethod.OPTIONS, "/**").permitAll() // Explicitly permit OPTIONS if not handled by @CrossOrigin implicitly
                .antMatchers("/api/login").permitAll()
                .anyRequest().authenticated();
    }
}

For Spring Security 5/6, you’d use http.cors(withDefaults()) or http.cors(cors -> cors.configurationSource(corsConfigurationSource())).

Solution 10: Verifying Origin Server Health and Reachability

In cloud environments, especially with CDNs like CloudFront, the issue might not be with Spring Security’s CORS configuration itself but with the CloudFront distribution’s ability to reach the origin API server. Ensure your API server is running, accessible, and not experiencing network issues.

Solution 11: Global CORS Mapping in WebMvcConfigurer

A straightforward global configuration for all origins, methods, and headers:

@Configuration
@EnableWebMvc
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/**")
                .allowedOrigins("*") // Use a specific origin in production
                .allowedHeaders("*")
                .allowedMethods("*"); // Ensure OPTIONS is covered
    }
}

Incorrect Approaches to Avoid

It’s important to note what doesn’t typically work and can lead to confusion:

  • http.authorizeRequests().antMatchers(HttpMethod.OPTIONS, "/**").permitAll(); without a proper CorsFilter or WebMvcConfigurer CORS setup.
  • web.ignoring().antMatchers(HttpMethod.OPTIONS); which might bypass the entire security chain incorrectly.

FAQs on Spring Security CORS Issues

Q: What is a preflight request in CORS

ANS: A preflight request is an HTTP OPTIONS request sent by the browser before the actual cross-origin request. It informs the server about the origin, HTTP method, and headers of the upcoming request, allowing the server to decide if it permits the cross-origin access.

Q: Why does my Spring Security block OPTIONS requests

ANS: Spring Security might intercept OPTIONS requests before the CORS configuration is applied. If the OPTIONS request isn’t explicitly permitted or handled by a CorsFilter that runs early, Spring Security might treat it as an unauthorized request.

Q: How to make Spring Security process CORS before other security filters

ANS: Use the spring-security-config’s .cors().and() in HttpSecurity, or explicitly register a CorsFilter with FilterRegistrationBean and set its order to Ordered.HIGHEST_PRECEDENCE. This ensures CORS is evaluated before other security constraints.

Q: Can I use both Spring MVC CORS and Spring Security CORS

ANS: Yes, for Spring Security 5/6, Spring Security can often leverage your WebMvcConfigurer’s CORS settings automatically. If not, ensure your CorsConfigurationSource bean is correctly configured and picked up by Spring Security.

Q: What are the most common wrong ways to configure CORS in Spring Security

ANS: Incorrectly applying permitAll() only to OPTIONS without a comprehensive CORS setup, or using web.ignoring() for OPTIONS requests, are common pitfalls. The core issue is usually the order of filter processing.
