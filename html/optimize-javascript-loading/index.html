Solved: How to Optimize JavaScript Loading for Faster Web Performance

When a browser encounters a <script> tag referencing an external JavaScript file without defer, async, or type="module", it follows a specific, often performance-hindering, process:

  1. Fetch HTML: The browser requests and receives the HTML document (e.g., index.html).
  2. Parse HTML: As the HTML is parsed, the parser encounters a <script src="your-script.js"> tag.
  3. Block Parsing: Crucially, the HTML parser stops processing the rest of the HTML document.
  4. Request Script: The browser requests the external JavaScript file.
  5. Download & Execute: Once downloaded, the script is executed.
  6. Resume Parsing: Finally, the HTML parser resumes processing the remainder of the document.

This blocking behavior, especially in step 4, significantly impacts user experience. Users dislike waiting for websites to load, and this sequential download and execution of scripts can create noticeable delays.

Why Does This Blocking Occur?

The browser has to assume that any script it fetches could potentially alter the HTML structure using methods like document.write(). To ensure the integrity of the document, it pauses parsing until the script is downloaded and executed, allowing for any DOM manipulations to be incorporated safely.

Consider this standard HTML structure:

<!-- index.html -->
<html>
<head>
    <title>Optimizing Scripts</title>
    <script src="my-script.js"></script>
</head>
<body>
    <div id="user-greeting">Welcome back, user</div>
</body>
</html>

And a typical JavaScript file:

// my-script.js
document.addEventListener("DOMContentLoaded", function() {
    document.getElementById("user-greeting").textContent = "Welcome back, Bart";
});

Even though my-script.js only modifies the DOM after it’s ready, the browser still blocks parsing until my-script.js is downloaded and executed.

The Antiquated Approach: Scripts at the Bottom

An older recommendation was to place all <script> tags just before the closing </body> tag. This ensured that the HTML was fully parsed before any scripts were encountered.

The Drawback: This method delays script downloads. The browser won’t start downloading scripts until the entire HTML document has been parsed. For websites with substantial scripts or many external resources, this can still lead to slower load times, as parallel downloads are delayed. Swift loading is critical; studies show users abandon sites that don’t load within a couple of seconds.

An ideal scenario would allow scripts to download as early as possible while the browser continues parsing the HTML.

The Modern & Efficient Approach: async, defer, and Modules

Modern browsers offer attributes that significantly improve script loading efficiency.

Using async

Scripts with the async attribute are executed asynchronously. The browser downloads the script without blocking parsing, and executes it as soon as it’s downloaded.

<script src="path/to/script1.js" async></script>
<script src="path/to/script2.js" async></script>

Key Points about async:

  • Parallel Download: Scripts download in parallel with HTML parsing.
  • Asynchronous Execution: Scripts execute as soon as they are ready, without waiting for the HTML to finish parsing.
  • Execution Order: The order of execution is not guaranteed. script2.js might execute before script1.js if it downloads faster.
  • Browser Support: Widely supported by over 97.78% of browsers.

Use async when:

  • Scripts are independent of each other and do not rely on the execution order of other scripts.
  • Scripts do not need to modify the DOM before it’s fully parsed, or they handle DOM readiness themselves (e.g., using DOMContentLoaded).

Using defer

The defer attribute allows scripts to download in parallel with HTML parsing but guarantees execution only after the entire HTML document has been parsed.

<script src="path/to/script1.js" defer></script>
<script src="path/to/script2.js" defer></script>

Key Points about defer:

  • Parallel Download: Scripts download in parallel with HTML parsing.
  • Deferred Execution: Scripts execute only after the HTML document has been fully parsed.
  • Execution Order: Scripts are executed in the order they appear in the HTML. script1.js will execute before script2.js.
  • Browser Support: Also widely supported.

Use defer when:

  • Scripts depend on the DOM being fully parsed.
  • You have multiple scripts that must execute in a specific order.
  • You want scripts to execute after parsing but don’t need them immediately upon parsing completion.

Combining async and defer

A script with both async and defer attributes will behave like a defer script in browsers that support defer, and like an async script in browsers that don’t support defer but do support async.

<script src="path/to/script.js" async defer></script>

Using type="module"

Scripts with type="module" are treated as JavaScript modules. By default, they behave like deferred scripts: they are downloaded in parallel with HTML parsing and executed in order after the document has finished parsing.

<script type="module" src="path/to/script-module.js"></script>

Key Points about type="module":

  • Module Loading: Enables modern JavaScript module features.
  • Deferred Behavior: Loads and executes like deferred scripts by default.
  • Place Anywhere: Can be placed in the <head> or <body> without blocking parsing.

Use type="module" when:

  • You are using modern JavaScript modules and the import/export syntax.
  • You want the benefits of deferred loading for your modules.

Best Practices and Considerations

  • Place scripts in the <head>: With async, defer, or type="module", placing scripts in the <head> allows them to download as early as possible without blocking rendering.

  • jQuery and $(document).ready(): If you use libraries like jQuery, placing your script tags in the <head> is fine, as $(document).ready() or similar constructs ensure your code executes only after the DOM is ready. This keeps your code organized and allows for potentially earlier script downloads.

    <!-- In the <head> -->
<script src="https://ajax.googleapis.com/ajax/libs/jquery/3.6.0/jquery.min.js"></script>
<script src="my-app.js"></script>

    // my-app.js
$(document).ready(function() {
    // Your jQuery code here, ensuring DOM is ready
    $('#myElement').on('click', function() {
        // ...
    });
});

  • Dynamic Script Loading: For scripts not immediately required for rendering, you can dynamically load them using document.createElement("script") after window.onload or within specific event handlers. This ensures they don’t impact the initial page load time at all.

    window.addEventListener('load', function() {
    const script = document.createElement('script');
    script.src = 'optional-feature.js';
    script.async = true; // Or defer
    document.body.appendChild(script);
});

  • Browser Compatibility: While async and defer are widely supported, for older browsers (like Internet Explorer < 10), placing scripts at the very end of the <body> or wrapping your script logic in window.onload is a safer fallback.

Q: Why is it important to optimize JavaScript loading

ANS: Optimizing JavaScript loading prevents “render-blocking” behavior, where scripts halt the rendering of your HTML and CSS. This leads to faster page load times and a smoother user experience, as users see content sooner and interact with the page more quickly. It’s crucial for core web vitals like “Largest Contentful Paint” and “First Input Delay.”

Q: What is render-blocking JavaScript

ANS: Render-blocking JavaScript refers to JavaScript files that prevent the browser from parsing and rendering the rest of the HTML and CSS until the script has been downloaded and executed. This typically happens when <script> tags are placed in the <head> without async or defer attributes.

Q: How do async and defer attributes differ

ANS: Both async and defer allow scripts to download in parallel with HTML parsing without blocking. The key difference is execution: async scripts execute as soon as they are downloaded, potentially out of order, while defer scripts execute in order after the entire HTML document has been parsed.

Q: When should I use async versus defer

ANS: Use async for independent scripts where execution order doesn’t matter, like analytics or third-party ad scripts. Use defer for scripts that depend on the DOM being fully parsed or require a specific execution order with other scripts, such as initialization scripts or those manipulating page elements.

Q: What is the benefit of using type module for scripts

ANS: Using type="module" for scripts leverages modern JavaScript module features (like import/export) and, by default, behaves like defer scripts. This means they download in parallel with HTML parsing and execute in order after the document has been fully parsed, offering both improved performance and modular code organization.

Q: Are there any downsides to async or defer

ANS: While generally beneficial, async scripts execute as soon as they download, which might be before the DOM is ready if they need to interact with specific elements. defer scripts execute only after the DOM is fully parsed, which might be later than strictly necessary for some scripts. Compatibility with very old browsers might also require fallback strategies.

Q: Can I place JavaScript in the head tag

ANS: Yes, you can place JavaScript in the <head> tag, especially when using the async or defer attributes. This allows scripts to start downloading earlier without blocking the initial rendering of your page, which is generally a good practice for performance.
