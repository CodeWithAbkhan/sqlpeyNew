“Implementing Swift Delegate Pattern for Inter-ViewController Communication”

The Delegate Pattern in Swift is a fundamental design pattern where one object delegates (assigns responsibility) some of its tasks or notifications to another object. This promotes loose coupling between components, allowing one class to notify another when a specific action or event occurs without knowing the concrete type of the receiver, only that it conforms to a required protocol.

How does one accurately structure and deploy the delegate pattern across various scenarios, such as communication between two UIViewController instances or handling asynchronous results in a service layer?

Core Mechanics of Setting Up a Delegate

Implementing this pattern consistently involves a few key structural components. Consider the scenario where a secondary view controller (FooTwoViewController) needs to send some text data back to the presenting view controller (ViewController) upon completion.

Step 1: Define the Contract (Protocol)

The sending class’s delegate contract must clearly specify the methods the receiving class must implement to handle the delegated task. Crucially, the protocol should inherit from class (or AnyObject) to ensure only class types can adopt it, enabling the use of weak references later.

protocol DataTransferDelegate: class {
    func dataSenderDidFinish(_ sender: UIViewController, transmittedData: String)
}

Step 2: Declare the Delegate in the Sending Class

The class initiating the communication (the sender) must hold a reference to its delegate. This reference must be declared as weak to prevent strong reference cycles, especially in parent-child or presenter-delegate relationships.

class FooTwoViewController: UIViewController {
    // MUST be weak to avoid retain cycles
    weak var delegate: DataTransferDelegate?
    // ... other properties and methods
}

Step 3: Triggering the Delegation

When the required action completes in the sending class, it invokes the protocol method on its delegate. The optional chaining operator (?) is used because the delegate might not be assigned.

@IBAction func saveAction(_ sender: UIBarButtonItem) {
    // Assume colorLabel.text holds the data to send
    let dataToSend = colorLabel.text ?? "Default Data"
    
    // Fire the notification through the delegate
    delegate?.dataSenderDidFinish(self, transmittedData: dataToSend)
    
    // Close the view controller
    navigationController?.popViewController(animated: true)
}

Step 4: Adopting the Protocol in the Receiving Class

The class that needs to receive the communication (the receiver) must conform to the defined protocol.

class ViewController: UIViewController, DataTransferDelegate {
    // ... other code
}

Step 5: Implementing the Delegate Method

The receiver implements the required method from the protocol, defining how it will react to the delegated notification.

// Implementation within ViewController
func dataSenderDidFinish(_ sender: UIViewController, transmittedData: String) {
    // Update UI element in the receiver
    colorLabel.text = "Received: \(transmittedData)"
    // Note: Popping the controller here might be redundant if dismissal is handled elsewhere
    // sender.navigationController?.popViewController(animated: true) 
}

Step 6: Establishing the Connection (Setting the Delegate)

This assignment usually happens just before the sending view controller is presented, often within prepare(for:sender:) during a storyboard segue.

override func prepare(for segue: UIStoryboardSegue, sender: Any?) {
    if segue.identifier == "SegueToSender" {
        if let destinationVC = segue.destination as? FooTwoViewController {
            // 1. Pass any necessary initial data to the destination
            destinationVC.colorString = colorLabel.text
            // 2. Establish the link: self (ViewController) becomes the delegate
            destinationVC.delegate = self
        }
    }
}

Alternative Perspectives on Delegation

The concept can be abstract, but several interpretations help clarify its role:

The Worker Analogy (Conceptual View)

A delegate acts as a designated worker assigned to perform specific tasks for a “boss” class. The boss class defines what needs to be done via a protocol, and the worker class dictates how it gets done by conforming to that protocol.

This structure is excellent for decoupled communication, such as:

  1. Data Transfer: Sending input from a custom control back to a parent view.
  2. Customization Hooks: Allowing a receiving class to modify behavior (e.g., determining if a notification should present).

Simulating Native Delegates (e.g., UITextFieldDelegate)

You can replicate system functionality, like creating a simplified UITextField that notifies its delegate whenever its text changes.

// Contract definition
protocol CustomInputDelegate: class {
    func inputFieldContentChanged(_ textField: UITextField, newText: String)
}

class CustomTextField {
    weak var delegate: CustomInputDelegate?
    private var internalText: String = ""
    
    var text: String? {
        get { return internalText }
    }
    
    func setTextAndNotify(_ newText: String) {
        internalText = newText
        // Triggering the event notification
        delegate?.inputFieldContentChanged(self as! UITextField, newText: newText)
    }
}

// Implementation in a main application class
class ApplicationController {
    let myField = CustomTextField()
    
    func setup() {
        myField.delegate = self as? CustomInputDelegate // Needs casting or careful typing
        myField.setTextAndNotify("Initial Value")
    }
}

Using NSObjectProtocol (Objective-C Interoperability)

When interfacing with older frameworks or preferring compatibility with Objective-C runtime features, protocols can inherit from NSObjectProtocol.

protocol StatusReporter: NSObjectProtocol {
    func reportUpdate(isFinished: Bool)
}

class BackgroundTask {
    weak var statusDelegate: StatusReporter?
    
    func completeTask() {
        // Invoking the method on the delegate
        statusDelegate?.reportUpdate(isFinished: true)
    }
}

Advanced Approach: Generic Type Erasure

For scenarios requiring stricter type safety across varying delegate types while maintaining generic flexibility, techniques involving generic wrappers can be employed. This allows the delegate to be strongly typed to a specific DataType without tightly coupling the source and target classes beyond the protocol definition.

If you are dealing with different data types across multiple delegation tasks, exploring generic type erasure patterns can offer more reusable and type-safe delegate structures, avoiding the need to create many specific protocol variations. This approach abstracts the specific generic requirements of the base protocol.

FAQs on Swift Delegate Pattern Implementation

Q: Why must a delegate variable be declared as weak

ANS: Declaring the delegate as weak prevents strong reference cycles (retain cycles). If both objects held strong references to each other, neither would ever be deallocated, leading to memory leaks.

Q: What is the purpose of inheriting from class in a protocol definition

ANS: Inheriting from class (or AnyObject) ensures that only classes can adopt the protocol. This is necessary because only class instances can be stored as weak references, which is required for delegate implementation to prevent retain cycles.

Q: How does optional chaining relate to calling delegate methods

ANS: Optional chaining (delegate?.methodCall()) safely calls the delegate method only if the delegate variable is not nil. If delegate is nil, the call is skipped, preventing a runtime crash.

Q: Can structs be used as delegates

ANS: No, structs cannot typically be used as delegates because they are value types and cannot conform to protocols requiring AnyObject or class, which is necessary for using the weak keyword.
