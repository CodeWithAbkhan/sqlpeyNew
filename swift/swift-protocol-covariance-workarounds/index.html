“Swift Protocol Read-Only Property Covariance Limitation Workarounds”

A central topic in Swift protocol design concerns the ability for a conforming implementation of a read-only property requirement to return a type that is more specific (covariant) than the type specified in the protocol. While logically sound—a ConformsToB instance satisfies a requirement for ProtocolB—Swift’s compiler currently imposes restrictions here.

The Core Issue: Why Swift Blocks Covariant Properties

Why does returning a ConformsToB instance from a property declared as ProtocolB face resistance from the Swift compiler when defined as a read-only requirement?

The difficulty lies in how Swift manages protocol witnesses. If a property requirement is covariant, the compiler would need to introduce boilerplate code—a thunk—to manage the necessary type boxing. Specifically, a value of the concrete type (ConformsToB) must be wrapped within an existential container to be presented to the caller as the less specific protocol type (ProtocolB). Since the caller often remains unaware of the concrete implementation type, it cannot perform this boxing itself, leaving the burden on the compiler implementation, which it currently avoids generating for this specific scenario.

Members of the Swift team have indicated interest in supporting function conversion for protocol witnesses and method overrides universally, suggesting this limitation might evolve in future language versions.

Workaround 1: Employing associatedtype

One established technique to navigate this restriction involves using an associatedtype within the protocol definition. This delegates the specificity requirement to the conforming type.

// Define the protocol the return type must satisfy
protocol ProtocolB {}
class ConformsToB: ProtocolB {}

// ProtocolA uses an associated type constrained to ProtocolB
protocol ProtocolA {
    associatedtype SomeProperty: ProtocolB
    var someProperty: SomeProperty { get }
}

class SomeClass: ProtocolA {
    // We specify the concrete type here, satisfying the constraint
    var someProperty: ConformsToB

    init(someProperty: ConformsToB) {
        self.someProperty = someProperty
    }
}

Critique of associatedtype: While functional, this approach significantly alters the protocol’s usability. ProtocolA can no longer be used as a standalone type because it carries an unfulfilled associated type requirement. Furthermore, it shifts the contract from “returns anything conforming to ProtocolB” to “returns one specific, concrete type conforming to ProtocolB.”

Workaround 2: The Dummy Property Thunk

A more direct, albeit syntactically noisy, workaround involves manually creating the thunk the compiler avoids. This means implementing two properties: one that satisfies the protocol requirement exactly, and another that holds the actual, covariant implementation.

protocol ProtocolB {}
class ConformsToB: ProtocolB {}

protocol ProtocolA {
    // The requirement as stated in the protocol
    var someProperty: ProtocolB { get }
}

class SomeClass: ProtocolA {

    // The actual, specific property holding the desired type
    var actualSomeProperty: ConformsToB

    // The dummy property that satisfies ProtocolA's requirement by forwarding
    var someProperty: ProtocolB {
        return actualSomeProperty
    }

    init(someProperty: ConformsToB) {
        self.actualSomeProperty = someProperty
    }
}

This method forces the implementer to create an intermediary property, which can clutter the public API of the conforming class.

Workaround 3: Leveraging Opaque Return Types (Swift 5.1+)

For situations involving both read-only and read/write properties, Swift 5.1 introduced opaque return types (some ProtocolA). When combined with associatedtype, this often resolves the issue, particularly when the underlying type must conform to another protocol that has its own requirements.

Consider a scenario where ProtocolA requires a property someProperty returning a type T which must satisfy ProtocolB, and both protocols have mutable properties like x.

protocol ProtocolB {
    var x: Int { get set }
}

protocol ProtocolA {
    associatedtype T: ProtocolB
    var someProperty: T { get }
    var x: Int { get set } // Requirement on ProtocolA itself
}

struct ConformsToB: ProtocolB {
    var x: Int
}

class SomeClass: ProtocolA {
    var someProperty: ConformsToB

    init(someProperty: ConformsToB) {
        self.someProperty = someProperty
    }

    // Implementation for ProtocolA's 'x' requirement, proxied through the specific type
    var x: Int {
        get {
            return someProperty.x
        }
        set {
            someProperty.x = newValue
        }
    }
}

// Usage demonstrates successful covariance with opaque types
var protocolAInstance: some ProtocolA = SomeClass(someProperty: ConformsToB(x: 100))

print("Initial X: \(protocolAInstance.x)") // Output: 100
protocolAInstance.x = 200
print("Updated X: \(protocolAInstance.x)") // Output: 200

This allows the conforming class to maintain the specific type (ConformsToB) for someProperty while satisfying the broader contract of ProtocolA.

Advanced Hiding Technique with Extensions

If the goal is to maintain the same property name for both the concrete implementation and the protocol conformity while hiding the implementation detail, an extension combined with a differently named internal property can be used:

protocol ProtocolB {}

protocol ProtocolA {
    // Use a distinct name for the requirement storage
    var _internalPropertyStorage: ProtocolB { get }
}

extension ProtocolA {
    // Provide a convenient, readable property using the extension
    var someProperty: ProtocolB {
        return _internalPropertyStorage
    }
}

class ConformsToB: ProtocolB {}

class SomeClass: ProtocolA {
    // The actual implementation holding the specific type
    var actualSpecificProperty: ConformsToB

    // Satisfying the protocol requirement using the internal storage name
    var _internalPropertyStorage: ProtocolB {
        return actualSpecificProperty
    }

    // Optional: Provide the specific property as well, but be careful of name clashes
    var someProperty: ConformsToB {
      return actualSpecificProperty
    }

    init(property: ConformsToB) {
        self.actualSpecificProperty = property
    }
}

let instance = SomeClass(property: ConformsToB())
// instance.someProperty accesses the implementation's specific property (ConformsToB)
// (instance as ProtocolA).someProperty accesses the extension's forwarding getter (ProtocolB)

This technique cleverly uses name mangling potential (by using _ prefixes or distinct names) to satisfy the compiler while presenting a unified or cleaner interface externally.

FAQs on Swift Protocol Read-Only Property Covariance Limitations Workarounds

Q: Why does Swift not allow returning a more specific type in a protocol property getter

ANS: The compiler avoids automatically generating the necessary type boxing (wrapping the concrete type into an existential container) required when presenting a specific type as a general protocol type, which is needed for covariant read-only properties.

Q: Is the associatedtype workaround completely satisfactory

ANS: No, it is often unsatisfactory because it forces the protocol to rely on a concrete type, preventing the protocol from being used as a type itself, as it still has an unfulfilled associated type requirement.

Q: Do opaque return types fix this for all property types

ANS: Opaque return types, when used with associated types in Swift 5.1 and later, help resolve this for both read-only and read/write properties in many structured scenarios.
protocol ProtocolA {
    // allow the conforming type to satisfy this with a concrete type
    // that conforms to ProtocolB.
    associatedtype SomeProperty : ProtocolB
    var someProperty: SomeProperty { get }
}

protocol ProtocolB {}
class ConformsToB: ProtocolB {}

class SomeClass: ProtocolA {

    // implicitly satisfy the associatedtype with ConformsToB.
    var someProperty: ConformsToB

    init(someProperty: ConformsToB) {
        self.someProperty = someProperty
    }
}
protocol ProtocolA {
    var someProperty: ProtocolB { get }
}

protocol ProtocolB {}
class ConformsToB: ProtocolB {}

class SomeClass: ProtocolA {

    // dummy property to satisfy protocol conformance.
    var someProperty: ProtocolB {
        return actualSomeProperty
    }

    // the *actual* implementation of someProperty.
    var actualSomeProperty: ConformsToB

    init(someProperty: ConformsToB) {

    }
}
