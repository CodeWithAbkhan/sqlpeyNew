Swift Protocols: Why Can’t They Conform to Themselves?

Swift’s design prohibits protocols from conforming to themselves, particularly when static requirements like initializers or static methods/properties are involved. This behavior stems from the need for concrete types to fulfill these requirements, which protocols, as abstract definitions, cannot inherently provide. Let’s delve into why this limitation exists and explore available workarounds.

The Challenge with Static Protocol Requirements

Static requirements present a fundamental obstacle. When you define a generic type that constrains its element type T to conform to a protocol P (i.e., T: P), you can access static members through T. However, you cannot access these same members directly through the protocol type P itself because P lacks a concrete instance to provide the implementation.

Consider this scenario:

protocol RequirementProtocol {
  init() // Static requirement
}

struct ConcreteStruct: RequirementProtocol {}
struct AnotherStruct: RequirementProtocol {}

extension Array where Element: RequirementProtocol {
  mutating func addNewElement() {
    // Attempting to append a new instance of Element, but Element is RequirementProtocol
    // Swift doesn't know how to instantiate a protocol directly.
    append(Element())
  }
}

var protocolArray: [RequirementProtocol] = [ConcreteStruct(), AnotherStruct()]

// This will cause a compile-time error:
// "Using 'RequirementProtocol' as a concrete type conforming to protocol 'RequirementProtocol' is not supported"
// protocolArray.addNewElement()

In this example, Element() fails because RequirementProtocol is not a concrete type. The addNewElement function must operate on an array with a known, concrete element type that conforms to RequirementProtocol. The same logic applies to static methods and properties:

protocol StaticPropertyProtocol {
  static var value: Int { get }
  static func displayValue()
}

struct GenericContainer<T: StaticPropertyProtocol> {
  func showDetails() {
    // Accessing static members via T is fine.
    print(T.value)
    T.displayValue()
  }
}

// This would also fail:
// let container = GenericContainer<StaticPropertyProtocol>()
// container.showDetails()

Here, T.value and T.displayValue() require a concrete type T. If T is StaticPropertyProtocol, Swift cannot resolve the implementation of value or displayValue() because the protocol itself doesn’t provide one. Even extensions with static requirements for StaticPropertyProtocol are only applied to concrete types that conform to it, not the protocol type itself.

This inability to provide concrete implementations for static members is why Swift prevents protocols with static requirements from conforming to themselves.

The Role of @objc Protocols

A notable exception is @objc protocols. When an @objc protocol lacks static requirements, it can conform to itself. This works because @objc protocols rely on the Objective-C runtime for dispatching method calls using objc_msgSend. This mechanism is more forgiving with protocol types.

import Foundation

@objc protocol OptionalProtocol {
  func performAction()
}

class MyClass: OptionalProtocol {
  func performAction() {
    print("MyClass action performed!")
  }
}

func processProtocol(_ item: OptionalProtocol) {
  item.performAction()
}

let instance: OptionalProtocol = MyClass()
processProtocol(instance) // This works seamlessly.

However, if you introduce a static requirement to an @objc protocol:

import Foundation

@objc protocol ProtocolWithStatic {
  static func staticMethod()
  func instanceMethod()
}

class AnotherClass: ProtocolWithStatic {
  static func staticMethod() {
    print("AnotherClass static method called.")
  }
  func instanceMethod() {
    print("AnotherClass instance method called.")
  }
}

func callStaticMethodOnProtocol(_ item: ProtocolWithStatic) {
  // This will fail if ProtocolWithStatic has static requirements
  // ProtocolWithStatic.staticMethod() // Error: static member 'staticMethod' cannot be used on protocol type 'ProtocolWithStatic'
}

The compiler prevents direct calls to static members on the protocol type itself. This behavior aligns with the general rule: static requirements necessitate concrete types.

The advantage of @objc protocols in this context is their simpler internal representation, essentially acting as class references. This allows Swift to treat them more like concrete generic types, enabling self-conformance when static requirements aren’t present.

Workarounds for Non-@objc Protocols

For non-@objc protocols, several strategies can help mitigate the limitations of self-conformance:

1. Extensions with Specific Type Constraints

You can define extensions using a precise == constraint to match a protocol type directly, or a more general : constraint for types conforming to the protocol.

protocol MyComparable {
  func isGreaterThan(_ other: Self) -> Bool
}

struct NumberWrapper: MyComparable {
  let value: Int
  func isGreaterThan(_ other: NumberWrapper) -> Bool {
    return value > other.value
  }
}

// Extension for when the Element is precisely 'MyComparable' (not directly usable for [MyComparable])
extension Array where Element == MyComparable {
  // This specific extension might not be directly callable as intended due to protocol type limitations.
}

// Extension for when the Element conforms to 'MyComparable'
extension Array where Element: MyComparable {
  func filterGreater(_ threshold: Element) -> [Element] {
    return self.filter { $0.isGreaterThan(threshold) }
  }
}

let numbers = [NumberWrapper(value: 10), NumberWrapper(value: 5), NumberWrapper(value: 15)]
let greaterThan10 = numbers.filterGreater(NumberWrapper(value: 10))
// greaterThan10 will be [NumberWrapper(value: 15)]

To bridge the gap, you can create a forwarding extension:

// Forwarding extension to call the Element: MyComparable extension
extension Array where Element: MyComparable {
  func processAsProtocol() -> [Element] {
    // This might involve boxing or other indirections.
    // For demonstration, let's assume a scenario where forwarding is useful.
    // A direct call to an extension on [MyComparable] would require boxing.
    // For example, if you had a specific extension on [MyComparable], you might do:
    // return (self as [MyComparable]).processGeneric()
    return self // Placeholder for actual forwarding logic
  }
}

let processedNumbers = numbers.processAsProtocol()

Be aware that casting to [MyComparable] can involve boxing each element, leading to potential performance overhead (O(n) conversion). Re-implementing the logic directly within the : P extension is often more efficient.

2. Bridging Protocol-Typed Instances with Generic Placeholders

You can create wrapper methods within a protocol extension that utilize the implicit Self generic placeholder. This allows you to pass a protocol-typed instance to a function expecting a concrete conforming type.

protocol ValueProtocol {
  var identifier: String { get }
  func describe()
}

struct ItemA: ValueProtocol {
  let identifier = "A"
  func describe() { print("Item A") }
}

struct ItemB: ValueProtocol {
  let identifier = "B"
  func describe() { print("Item B") }
}

func processSpecificValue<T: ValueProtocol>(_ value: T) {
  print("Processing: \(value.identifier)")
  value.describe()
}

extension ValueProtocol {
  // This method acts as a trampoline.
  // The implicit 'self: Self' uses the concrete type.
  func callProcessSpecific() {
    processSpecificValue(self)
  }
}

let protocolInstance: ValueProtocol = ItemA()
protocolInstance.callProcessSpecific() // Calls processSpecificValue with ItemA

This approach effectively “opens” the existential ValueProtocol to expose its underlying concrete type to the generic processSpecificValue function. However, this doesn’t resolve issues with heterogeneous collections where elements have different concrete types.

// This scenario highlights the limitation with heterogeneous collections.
func processArrayOfSpecificValues<T: ValueProtocol>(_ values: [T]) {
  // T must be a single concrete type.
}

let mixedArray: [ValueProtocol] = [ItemA(), ItemB()]

// This would fail because 'T' cannot be determined for a mix of ItemA and ItemB.
// processArrayOfSpecificValues(mixedArray)
3. Type Erasure

Type erasure is a robust solution for handling heterogeneous collections and generalizing protocol usage. It involves creating a concrete wrapper type that conforms to the protocol, forwarding all its requirements to an underlying private instance.

struct AnyValue: ValueProtocol {
  private var base: ValueProtocol

  init<P: ValueProtocol>(_ wrappedValue: P) {
    self.base = wrappedValue
  }

  var identifier: String {
    return base.identifier
  }

  func describe() {
    base.describe()
  }
}

// Now, use AnyValue for mixed collections:
let wrappedArray: [AnyValue] = [AnyValue(ItemA()), AnyValue(ItemB())]

// You can now process these as a single concrete type (AnyValue).
// If processSpecificValue accepted AnyValue, it would work.
func processAnyValueArray(_ values: [AnyValue]) {
  values.forEach { $0.describe() }
}

processAnyValueArray(wrappedArray)

Type erasure is particularly powerful for instance-based protocol requirements. For static requirements, you would need to define a specific, often arbitrary, implementation within the type eraser, as the underlying concrete types’ static implementations are not universally known.

4. Extending CollectionType (Swift 3.1 and earlier context)

Historically, extending CollectionType with a Generator.Element == P constraint was a pattern, though direct protocol self-conformance remains the core issue.

protocol OldProtocol {}
struct OldStruct: OldProtocol {}

let oldArray: [OldProtocol] = [OldStruct()]

extension Collection where Element == OldProtocol {
    func performOldAction<T>() -> [T] {
        // Implementation would involve boxing or specific logic.
        return []
    }
}

// let result: [OldStruct] = oldArray.performOldAction() // Illustrative, actual usage complex.

The core problem persists: Swift aims for concrete types for operations involving static members or other complex generic constraints.

Future Possibilities

The Swift team acknowledges the desire for more direct protocol self-conformance, especially for non-@objc protocols. As indicated in developer comments, lifting this restriction is an ongoing consideration, though complex to implement. The goal is to make Swift’s protocol system more flexible and less reliant on explicit workarounds like type erasure for common patterns.

FAQs on Swift Protocols Self Conformance

Q: Why does Swift restrict protocols from conforming to themselves

ANS: Swift restricts protocols from conforming to themselves, especially those with static requirements (like static methods or initializers). This is because static requirements need concrete implementations, which protocols, as abstract definitions, cannot provide. Swift needs to know how to instantiate or call static members, and a protocol type doesn’t offer this concrete information.

Q: Are there any exceptions to this rule

ANS: Yes, @objc protocols that do not have static requirements can conform to themselves. This is due to their reliance on the Objective-C runtime for method dispatch, which handles protocol types more flexibly in such cases.

Q: How can I work around this limitation for non-objc protocols

ANS: Common workarounds include using type erasure (creating a wrapper type that conforms to the protocol), implementing extensions with precise == constraints, or using trampoline methods within protocol extensions to leverage implicit Self generic placeholders when passing protocol-typed values to generic functions.

Q: Will Swift ever allow protocols to conform to themselves directly

ANS: The Swift team has indicated that this is an area of consideration for future language versions. While it’s a complex challenge, the goal is to enhance the flexibility of the protocol system, potentially reducing the need for manual workarounds like type erasure in certain scenarios.
