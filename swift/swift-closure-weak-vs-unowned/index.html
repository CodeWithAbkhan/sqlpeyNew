“Swift Closures: When to Choose [unowned self] vs [weak self]?”

When dealing with closures in Swift, especially those marked as @escaping, managing object ownership becomes paramount to prevent memory leaks caused by strong reference cycles. The choice between capturing self as [unowned self] or [weak self] hinges entirely on the expected lifetime relationship between the object containing the closure and the closure itself.

How do we definitively decide when to employ [unowned self] and when [weak self] is the safer, more appropriate selection?

The Core Problem: Strong Reference Cycles

A strong reference cycle occurs when two or more objects hold strong references to each other, directly or indirectly, forming a closed loop of ownership. Because neither object’s strong reference count will ever drop to zero, both objects are prevented from being deallocated, leading to a memory leak.

In the context of closures, when a closure captures a variable (like self), it establishes a strong reference to that variable for the duration the closure exists.

If a class instance owns a closure, and that closure strongly captures the instance (self), a cycle is formed unless an unowned or weak capture is explicitly specified.

For instance, in a scenario where a component like TempNotifier holds a closure property:

class TempNotifier {
    var onChange: (Int) -> Void = {_ in }
    var currentTemp = 72
    
    init() {
        // Without explicit capture control, this creates a cycle if 'onChange' 
        // is stored and outlives 'self' temporarily.
        onChange = { temp in
            self.currentTemp = temp // Strong capture of self
        }
    }
}

The solution involves breaking this anticipated cycle by instructing the closure how to reference self.

When is Capturing self Desirable?

It is important to note that there are legitimate times when you do want the closure to capture a strong reference to self. This ensures that the object remains allocated and valid throughout the execution of the closure’s task.

A prime example is an asynchronous operation, such as a network request. If the request takes time, the object initiating the request might otherwise be deallocated before the response arrives. By capturing self strongly (the default behavior if no capture list is provided), you guarantee self is present to handle the completion block.

// Example: Network request where 'self' MUST remain alive
networkManager.fetchData { 
    // Default strong capture [self] is implicitly used if no capture list is present, 
    // ensuring self is valid until fetch completes.
    self.processResponse(data) 
}

Distinguishing [unowned self] and [weak self]

The decision boils down to the expected relationship between the lifetime of the referenced object (self) and the lifetime of the closure.

Using [unowned self]

Use [unowned self] when you are certain that the referenced object (self) will always have an equal or longer lifetime than the closure capturing it.

  • Lifetime Equality: The closure will only ever be executed while self is guaranteed to exist. Once self is deallocated, the closure is implicitly also considered invalid or destroyed, preventing execution.
  • Performance Edge (Historical/Conceptual): Traditionally, unowned references were considered slightly faster because they don’t require the overhead of managing optional states or side-tables (though modern Swift optimizations blur this line).
  • Immutability: Since unowned references are not optionals, they allow direct, non-optional access within the closure body (e.g., self.method()), provided you are positive the object persists.

Practical Scenario for unowned: Handling immediate UI events where the closure scope is tightly coupled to the lifecycle of the view controller or component. If the view controller disappears, the button handler closure is no longer needed.

class MyViewController: UIViewController {
    let buttonPressHandler: (() -> Void)?

    override func viewDidLoad() {
        super.viewDidLoad()
        
        // If the button handler closure cannot possibly outlive the ViewController:
        buttonPressHandler = { [unowned self] in
            self.updateButtonAppearance() // Safe access, self guaranteed to exist
        }
        
        // ... attach handler to a button
    }
}

Using [weak self]

Use [weak self] when the closure has an independent or potentially longer lifetime than the object being referenced, meaning self might be deallocated before the closure executes.

  • Lifetime Independence: The closure might persist (e.g., held by a global manager, completed asynchronously after navigation), while self is gone.
  • Safety Mechanism: A weak capture results in an optional reference to self. If self is deallocated, the weak reference automatically becomes nil. This necessitates checking for nil before accessing properties or methods.

Practical Scenario for weak: Asynchronous operations like network fetches, observers, or delegates where callbacks can fire long after the initiating object is gone.

class MyViewController: UIViewController {
    let networkManager = NetworkService()

    override func fetchData() {
        networkManager.retrieveData { [weak self] (data, error) in
            // Safety check is mandatory: if self is gone, we return early.
            guard let strongSelf = self else {
                print("ViewController was deallocated before response arrived.")
                return
            }
            // Use strongSelf for guaranteed safe access
            strongSelf.displayResults(data)
        }
    }
}

The Difference Between weak and unowned Internals

The fundamental technical divergence relates to how the reference is handled upon deallocation:

  1. weak: When the last strong reference to an object drops to zero, the system finds all associated weak references and sets them to nil. This process is necessary because weak variables must be optionals.
  2. unowned: An unowned reference does not trigger the setting to nil. If an unowned reference is accessed after the object is deallocated, it results in a program crash due to accessing invalid memory (a dangling pointer). This is why certainty about lifetime is required.

Apple documentation strongly advises: “Use a weak reference whenever it is valid for that reference to become nil at some point during its lifetime. Conversely, use an unowned reference when you know that the reference will never be nil once it has been set during initialisation.”

Given the complexity and potential danger of introducing crashes via dangling pointers from unowned self, many developers adopt the conservative default of using [weak self] everywhere asynchronous code is involved, prioritizing stability over marginal performance gains.

FAQs on Swift Closures Weak Vs Unowned

Q: What happens if I use [unowned self] when self could become nil

ANS: Accessing an unowned reference that has become dangling (because its object was deallocated) results in a runtime crash, as unowned references are not automatically set to nil.

Q: Is [unowned self] always faster than [weak self]

ANS: Historically, unowned references had performance advantages. However, recent Swift implementations have significantly optimized weak references, minimizing this performance gap in most real-world scenarios.

Q: When is the default strong capture appropriate

ANS: The default strong capture is appropriate when the closure is short-lived and must ensure that ‘self’ remains alive for the entire duration of the closure’s execution, such as immediate synchronous tasks.

Q: How do I safely use [weak self] inside a closure

ANS: You should assign the weak reference to a temporary, strongly referenced local variable (often named strongSelf) within the closure body using optional binding (guard let strongSelf = self else { return }).
