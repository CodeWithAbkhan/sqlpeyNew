“iOS Data Transfer Between View Controllers: Best Practices and Code Examples”

How does one reliably transfer data between different UIViewController instances in an iOS application? Since the requirements for data sharing vary greatly—from simple point-to-point transfers to global state management—a single solution rarely fits all needs. Below are several established patterns for facilitating this communication.

Passing Data During Segue Transitions (Storyboard or Programmatic)

When navigating sequentially, especially when using Storyboards, the prepare(for:sender:) method is the designated mechanism for one-way data flow to the destination view controller.

If utilizing Storyboards and a specific segue identifier:

override func prepare(for segue: UIStoryboardSegue, sender: Any?) {
    // Check if the segue matches the expected identifier
    if segue.identifier == "NavigateToDetail" {
        if let destinationVC = segue.destination as? DetailViewController {
            // Assume 'sharedPayload' is a property on DetailViewController
            destinationVC.sharedPayload = self.currentData
        }
    }
}

For programmatic presentation without Storyboards (loading from a NIB):

func initiateProgrammaticTransition() {
    let destination = DetailViewController(nibName: "DetailViewController", bundle: nil)
    // Assign data before showing the view controller
    destination.sharedPayload = self.currentData
    self.show(destination, sender: self)
}

In both scenarios, the data (e.g., currentData or sharedPayload) must be defined as a property on the receiving view controller.

Sharing Data Across Tab Bar or Navigation Stacks

For data that needs persistence across an entire navigation hierarchy or across sibling tabs managed by a container controller, subclassing the container itself offers a clean way to hold shared state.

  1. Subclass the Container: Create a custom subclass (e.g., CustomTabBarController or CustomNavigationController) and introduce properties to hold the shared information.

    class CustomTabBarController: UITabBarController {
    var globalAppData: [String: Any]? // Property to hold shared state
}

  2. Update Storyboard/Instantiation: Ensure your application uses an instance of this custom class instead of the default UITabBarController.

  3. Accessing Shared Data: View controllers within that structure can then cast the container to access the shared property:

    if let tabContainer = self.tabBarController as? CustomTabBarController {
    // Safely access or modify sharedAppData
    _ = tabContainer.globalAppData?["userToken"]
}

// Similar approach for UINavigationController subclassing
if let navStack = self.navigationController as? CustomNavController {
    // Use navStack.globalAppData
}

Utilizing a Data Container Singleton for Global State

When application-wide data needs to be persistently available and modifiable across numerous, potentially unrelated classes, a Singleton design pattern serves as a centralized data repository. This object lives for the entire lifespan of the application.

A sample Swift Singleton structure demonstrating access and persistence via UserDefaults:

struct AppDefaultsKeys {
    static let appSettingInt  = "PersistentIntValue"
    static let appSettingText = "PersistentStringValue"
}

class GlobalDataStore {
    static let shared = GlobalDataStore()

    var appSpecificInt: Int?
    var appSpecificText: String?

    private init() {
        // Attempt to load saved state upon initialization
        let defaults = UserDefaults.standard
        self.appSpecificText = defaults.string(forKey: AppDefaultsKeys.appSettingText)
        self.appSpecificInt = defaults.integer(forKey: AppDefaultsKeys.appSettingInt)

        // Observe app lifecycle events to save state
        NotificationCenter.default.addObserver(forName: UIApplication.willResignActiveNotification, object: nil, queue: .main) { _ in
            self.saveStateToDisk()
        }
    }

    func saveStateToDisk() {
        let defaults = UserDefaults.standard
        defaults.set(self.appSpecificText, forKey: AppDefaultsKeys.appSettingText)
        defaults.set(self.appSpecificInt, forKey: AppDefaultsKeys.appSettingInt)
        defaults.synchronize()
    }
}

// Usage Example in a ViewController:
override func viewDidAppear(_ animated: Bool) {
    super.viewDidAppear(animated)
    // Reading data
    let currentCount = GlobalDataStore.shared.appSpecificInt ?? 0
    print("Current shared count is: \(currentCount)")
}

func updateCount(newValue: Int) {
    // Writing data
    GlobalDataStore.shared.appSpecificInt = newValue
}

Data Transfer via Delegate Protocols (Two-Way or Parent-Child)

The Delegate pattern establishes a formal contract for communication, primarily useful for child view controllers needing to inform a parent or presenting controller about an event or data change.

Child View Controller (Sender of Data):

protocol DataSendingContract {
    func didFinishWithData(result: String)
}

class ChildVC: UIViewController {
    var delegate: DataSendingContract? // The required reference

    @IBAction func actionComplete(_ sender: UIButton) {
        let outgoingData = "Success from Child!"
        self.delegate?.didFinishWithData(result: outgoingData)
        self.dismiss(animated: true)
    }
}

Parent View Controller (Receiver of Data):

class ParentVC: UIViewController, DataSendingContract {

    @IBAction func presentChild(_ sender: UIButton) {
        if let child = self.storyboard?.instantiateViewController(withIdentifier: "ChildVC_ID") as? ChildVC {
            // Register self as the delegate
            child.delegate = self 
            self.present(child, animated: true)
        }
    }

    // Fulfilling the contract method
    func didFinishWithData(result: String) {
        self.statusLabel.text = result // Update parent UI
    }
}

Using Dependency Injection with Protocols (Decoupled Architecture)

An advanced approach favors defining a DataController protocol. Instead of a true singleton, you inject an instance conforming to this protocol into view controllers. This supports dependency inversion and easier testing by allowing different implementations of the controller interface to be swapped in.

protocol DataService {
    var sessionID: String { get set } 
    var cachedItems: [String] { get }
}

class ConcreteDataService: DataService {
    var sessionID: String = "INIT_ID"
    var cachedItems: [String] = ["ItemA", "ItemB"]
}

class PresentingVC: UIViewController {
   // The dependency is held via the protocol type
   var dataManager: DataService? 

   override func viewDidLoad() {
       super.viewDidLoad()
       print("Current Session: \(dataManager?.sessionID ?? "N/A")")
   }
}

Using UINavigationControllerDelegate for Flow Events

When navigating using a UINavigationController, the delegate methods provide precise timing hooks for when a view controller appears or disappears from the stack.

To utilize this, the UINavigationController instance must adopt the UINavigationControllerDelegate protocol and set its delegate to itself:

class FlowNavigationController: UINavigationController, UINavigationControllerDelegate {

    override func viewDidLoad() {
        super.viewDidLoad()
        self.delegate = self
    }

    // Called right before a view controller transition completes
    func navigationController(_ navigationController: UINavigationController, willShow viewController: UIViewController, animated: Bool) {
        // Logic executes as navigation occurs (push or pop)
        if viewController is NextStepViewController {
            print("About to show the Next Step screen.")
        }
    }
}

FAQs on Swift View Controller Data Exchange Strategies

Q: When should I use a Data Singleton versus a Delegate for communication

ANS: Use a Data Singleton when you need global, persistent state access across many components of the application. Use the Delegate pattern for targeted, event-driven communication, typically between a child and its immediate parent controller, where the child needs to report back an action.

Q: Is it simple to pass data back from the destination VC to the source VC using prepareForSegue

ANS: No, prepareForSegue is strictly for passing data to the destination. To send data back, consider using Delegates, Notifications, or implementing an Unwind Segue handler in the source view controller.

Q: What is the benefit of using a protocol for a Data Controller implementation

ANS: Using a protocol decouples the view controllers from the specific data implementation (ConcreteDataService). This allows you to easily substitute the data source (e.g., switch from local storage to a network service) without altering any VC code that relies only on the DataService protocol methods.

Q: How do I handle data when using a UITabBarController

ANS: The most direct method is to create a subclass of UITabBarController where you define properties for the shared data, making that data accessible to all child view controllers via casting.
