“PostgreSQL UPSERT Strategies Avoiding Side Effects with ON CONFLICT DO NOTHING”

When implementing an UPSERT operation in PostgreSQL, utilizing ON CONFLICT DO UPDATE offers a straightforward approach. However, this strategy introduces potential negative side effects, especially when dealing with identical incoming rows where no data actually changes. These undesirable consequences include:

  1. Trigger Activation: Unnecessary execution of triggers defined on the table.
  2. Write-Locking: Incurring write-locks on “innocent” rows, impacting concurrent transactions.
  3. MVCC Overhead: For every target row, PostgreSQL writes a new row version, regardless of whether the data modified. This contributes significantly to table bloat, index bloat, and increased VACUUM costs, becoming a substantial performance issue with frequent duplicates.

Furthermore, ON CONFLICT DO UPDATE requires specifying a conflict_target, which becomes impractical or impossible when multiple unique indexes or constraints exist that might trigger the conflict.

How can we achieve the effect of an UPSERT—inserting if new, selecting the existing ID if present—while strictly avoiding these overheads associated with needless row updates, particularly when using ON CONFLICT DO NOTHING?

Avoiding Unnecessary Updates: Solutions Without Side Effects

Several methods exist to obtain the ID of a row upon insert or selection, avoiding the performance penalties of empty updates.

Solution A: CTE-Based Insert with Select Backfill (Best for Bulk Operations without Concurrent Writes)

This method uses Common Table Expressions (CTEs) to attempt an insert with ON CONFLICT DO NOTHING and then explicitly selects the existing rows that were not inserted. This ensures we get an ID for every input row, differentiating between inserted (‘i’) and selected (’s’) origins.

The key concept relies on the fact that newly inserted rows from a data-modifying CTE are not immediately visible to subsequent SELECT operations within the same SQL statement, allowing a join back to the original input data to find existing records.

WITH input_data(usr, contact, user_name) AS (
   -- Explicit type casts are often needed when VALUES is used freestanding
   VALUES
      (text 'alpha1', text 'beta1', text 'Alice1')
    , ('alpha2', 'beta2', 'Bob2')
    -- Add more input rows here
   )
, attempt_insert AS (
   INSERT INTO chats (usr, contact, user_name) 
   SELECT usr, contact, user_name FROM input_data
   ON CONFLICT (usr, contact) DO NOTHING
   RETURNING id  -- Retrieve ID only for successfully inserted rows
   )
SELECT 'i' AS operation_source
     , id
FROM   attempt_insert
UNION ALL
SELECT 'e' AS operation_source  -- 'e' for existing
     , c.id
FROM   input_data
JOIN   chats c USING (usr, contact); -- Select IDs of rows that already existed

Type Casting Notes: When using VALUES outside an INSERT context (like in a standalone CTE), PostgreSQL needs help determining data types. Explicit casts (text '...') on the first row often suffice to set the type for subsequent rows. Alternatively, you can template the types from the target table itself to avoid manual casting, as shown in external resources on PostgreSQL type coercion.

Solution B: Brute Force Recovery for Concurrency Issues (Handling Race Conditions)

When concurrent write load exists, a race condition might occur where one transaction commits an insert just before another transaction’s ON CONFLICT DO NOTHING runs, causing the second transaction to miss the newly written row in its SELECT backfill.

To guard against this, an extra CTE (ups) can be introduced as a rare fallback. This CTE attempts a full UPSERT (ON CONFLICT DO UPDATE) only on rows identified as missing in the initial ins and sel steps.

WITH input_data(usr, contact, user_name) AS (
    VALUES ('userA', 'contactX', 'NameA'), ('userB', 'contactY', 'NameB')
)
, ins AS (
   INSERT INTO chats AS c (usr, contact, user_name) 
   SELECT * FROM input_data
   ON     CONFLICT (usr, contact) DO NOTHING
   RETURNING id, usr, contact
)
, sel AS (
   SELECT 'i'::"char" AS source, id, usr, contact
   FROM   ins
   UNION ALL
   SELECT 'e'::"char" AS source, c.id, usr, contact
   FROM   input_data
   JOIN   chats c USING (usr, contact)
   WHERE  NOT EXISTS (SELECT 1 FROM ins i WHERE i.usr = input_data.usr AND i.contact = input_data.contact)
)
, recovery_upsert AS ( -- RARE corner case recovery step
   INSERT INTO chats AS c (usr, contact, user_name)
   SELECT i.*
   FROM   input_data i
   LEFT   JOIN sel s USING (usr, contact)
   WHERE  s.usr IS NULL -- Missing row identified post-initial attempt
   ON     CONFLICT (usr, contact) DO UPDATE
   SET    user_name = c.user_name -- Update with existing value to satisfy DO UPDATE requirement
   RETURNING 'r'::"char" AS source, id
)
SELECT source, id FROM sel
UNION ALL
TABLE  recovery_upsert;

Solution C: Locking Existing Rows for Strict Visibility (Concurrency Issue 2)

If you must ensure that rows identified during the initial process remain locked against concurrent modifications until your transaction commits, you can use ON CONFLICT DO UPDATE SET column = column WHERE FALSE. This forces a write-lock without modifying data. Combining this with SELECT ... FOR UPDATE in the selection phase provides robust protection.

-- Example focusing on locking during conflict resolution
INSERT INTO chats (usr, contact, user_name) 
VALUES ($1, $2, $3)
ON CONFLICT (usr, contact) DO UPDATE
  SET user_name = EXCLUDED.user_name 
  WHERE FALSE -- Perform the lock, but prevent data update
RETURNING id;

Alternative Approaches for Single Row UPSERTs

For simpler, single-row operations, other concise patterns emerge:

Alternative 1: COALESCE on RETURNING (Single Row Focus)

This uses COALESCE to pick the ID from the successful insert attempt or fall back to selecting the existing ID if the insert returned nothing (due to DO NOTHING).

WITH attempted_insert AS (
    INSERT INTO chats (usr, contact, user_name)
    VALUES ($1, $2, $3)
    ON CONFLICT(usr, contact) DO NOTHING
    RETURNING id
) 
SELECT COALESCE(
    (SELECT id FROM attempted_insert),
    (SELECT id FROM chats WHERE usr = $1 AND contact = $2)
);

Alternative 2: Pre-check with EXISTS (No Sequence Increment)

This avoids ON CONFLICT entirely, relying on an EXISTS check within the INSERT statement’s WHERE clause. This ensures no row versioning occurs, sequence generation is skipped for existing rows, and no write locks are held unnecessarily (unless explicitly added via FOR UPDATE).

WITH existing_check AS (
    SELECT id FROM chats WHERE (usr, contact) = ($1, $2)
),
new_insertion AS (
    INSERT INTO chats (usr, contact, user_name)
    SELECT $1, $2, $3
    WHERE NOT EXISTS (SELECT FROM existing_check)
    RETURNING id
)
SELECT id, TRUE AS was_inserted FROM new_insertion
UNION ALL
SELECT id, FALSE AS was_inserted FROM existing_check;

PostgreSQL 18 Feature Note

With PostgreSQL version 18 or later, the RETURNING old.id syntax simplifies returning the ID of the row that caused the conflict when using ON CONFLICT DO NOTHING.

INSERT INTO chats (usr, contact, user_name) 
VALUES ($1, $2, $3)
ON CONFLICT(usr, contact) DO NOTHING
RETURNING old.id;

When implementing these techniques, remember to use safe identifiers (e.g., usr instead of the reserved word user) and ensure proper transaction isolation for high-concurrency scenarios, potentially requiring SERIALIZABLE isolation if strict atomicity against concurrent operations is paramount, though this brings the risk of transaction aborts.

FAQs on PostgreSQL UPSERT Strategies Avoiding Side Effects

Q: What is the main performance issue with ON CONFLICT DO UPDATE when no data changes

ANS: The primary performance cost is due to PostgreSQL’s MVCC architecture; even if data is identical, every target row receives a new version, leading to table bloat, index bloat, and increased VACUUM overhead.

Q: Can ON CONFLICT DO NOTHING return the ID of the existing row

ANS: No, by default, ON CONFLICT DO NOTHING returns zero rows. You must combine it with a subsequent SELECT or use a CTE structure to fetch the ID of the row that already existed.

Q: How to avoid type casting issues when using VALUES in a CTE for bulk input

ANS: You can template the data types by selecting the column definitions from the target table using (SELECT * FROM chats LIMIT 0) UNION ALL VALUES (...) or by casting the values explicitly in the first row of the VALUES list.
