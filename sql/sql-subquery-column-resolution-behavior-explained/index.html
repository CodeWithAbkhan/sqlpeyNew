“SQL Subquery Column Resolution Behavior Explained”

A peculiar behavior in SQL arises when an unqualified column reference exists within a subquery’s SELECT list, especially in contexts like DELETE statements. How does the SQL engine decide which table this column belongs to when it’s not explicitly named within the subquery itself? This specific mechanism, involving scope resolution, can lead to non-obvious side effects.

Correlated Subqueries and Scope Lookups

Consider a scenario where a subquery seemingly selects nothing from the table it’s supposed to be operating on, yet it affects the outer query.

Q: How does an unqualified column reference in a subquery select list affect an outer DELETE operation

When a subquery lacks a specific column reference, the SQL parser resolves unqualified column names by looking outward from the closest scope to the outermost scope. If a column name in the subquery’s SELECT clause matches a column name available in the outer query, the engine binds that reference to the outer query’s column.

This effectively transforms the subquery into a correlated subquery, even if it appears non-correlated initially, provided the WHERE clause of the outer query links the tables.

For instance, if we execute:

SELECT 10
FROM HotelSupplier
WHERE id = 142;

If the HotelSupplier table has rows matching id = 142, this query returns a result set populated with the value 10 for every matching row. The number of rows returned is dependent only on the outer WHERE clause’s condition.

Now, look at how this impacts a DELETE statement:

DELETE FROM Photo
WHERE hs_id IS NOT NULL
  AND EXISTS (
    SELECT hs_id  -- Unqualified reference!
    FROM HotelSupplier
    WHERE id = 142
  );

(Note: The original example used a slightly different structure, but the principle remains: the subquery returns rows based on an outer condition, or in the problematic case, uses an outer column.)

The original example structure that demonstrates the issue is:

-- Example scenario leading to unexpected correlation
DELETE FROM Photo
WHERE Photo.hs_id IN (
    SELECT Photo.hs_id  -- This reference is resolved to Photo.hs_id from the outer query
);

In this specific formulation:

  1. The engine evaluates the subquery: SELECT Photo.hs_id. Since Photo.hs_id is not bound by a FROM clause inside this specific subquery, it looks outward.
  2. It finds Photo.hs_id in the outer query’s scope (DELETE FROM Photo).
  3. The subquery effectively becomes equivalent to selecting the column from the table being deleted: SELECT Photo.hs_id FROM Photo WHERE Photo.hs_id IS NOT NULL (implicitly correlated via the WHERE clause it is used in).

This results in deleting every row from Photo where Photo.hs_id is not null, provided the outer conditions (if any) are met, because the subquery always returns a non-empty set if any row exists in Photo that satisfies the condition tested by the IN clause.

Illustrative Code Examples

To solidify the concept of projection without selecting projected columns:

Example 1: Projection of a Constant

This returns multiple rows, each containing the value 10, if one row matches the WHERE clause in HotelSupplier:

-- Shows the correlation effect based on outer table matching
SELECT 10
FROM HotelSupplier
WHERE id = 142;

Example 2: Equivalent to Identity Comparison

The scenario described often simplifies to an identity check when applied within a WHERE clause predicate:

-- This DELETE statement effectively deletes everything where hs_id is not null
-- because the subquery resolves to selecting the outer row's hs_id
DELETE FROM Photo
WHERE Photo.hs_id IN (SELECT Photo.hs_id);

This is behaviorally identical to:

DELETE FROM Photo
WHERE Photo.hs_id = Photo.hs_id; -- Always true if hs_id is not null

Alternative Resolution Strategy: Explicit Qualification

The strong argument here points towards consistency. To avoid this ambiguity, always qualify columns explicitly when they belong to a specific table in a multi-table context or complex subquery structure.

If the intent was genuinely to check if any row in Photo has a matching hs_id (which seems redundant), the query might be clearer if you used EXISTS or enforced qualification:

Alternative using EXISTS (If checking for existence based on an outer condition):

If you intended to use an outer table’s ID, you must explicitly alias and reference it in the subquery’s WHERE clause (making it truly correlated):

-- Assuming 'outer_hs_id' is a column in Photo being evaluated
DELETE FROM Photo p_outer
WHERE EXISTS (
    SELECT 1
    FROM Photo p_inner
    WHERE p_inner.hs_id = p_outer.hs_id -- Explicit correlation
);

The main takeaway is that SQL prioritizes finding the name match starting from the innermost scope outwards; if not found, it checks the outer scope, treating an unqualified reference as correlated if a match is found there. Maintaining consistent naming conventions across tables lessens the chance of these subtle bugs surfacing, as noted by Erland Sommarskog’s suggestion for stricter checking.

FAQs on SQL Subquery Column Resolution Behavior Explained

Q: How does SQL resolve unqualified column names in a subquery

ANS: SQL resolves unqualified column names by checking scopes starting from the innermost scope outwards. If a match is found in an outer scope (like the main query), the subquery becomes correlated to that outer scope.

Q: Can a query select no columns from its target table

ANS: Yes, a query can have an empty set of columns projected in its SELECT list relative to its FROM clause, for example, SELECT 10 FROM TableName WHERE condition. The result set will contain rows matching the WHERE clause, all populated with ‘10’.

Q: Is using a subquery equivalent to checking hs_id = hs_id

ANS: If the subquery is structured to select an unqualified hs_id that resolves to the outer query’s Photo.hs_id, then WHERE Photo.hs_id IN (SELECT Photo.hs_id) becomes logically equivalent to WHERE Photo.hs_id = Photo.hs_id, which is true for all non-null values.
