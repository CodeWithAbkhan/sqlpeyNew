“PostgreSQL LIKE Query Speedup: Indexes & Strategies”

When optimizing PostgreSQL database performance, particularly for LIKE queries, understanding how to effectively leverage indexes is crucial. Standard B-tree indexes in PostgreSQL are highly efficient for prefix matching (e.g., column LIKE 'prefix%') but struggle with leading wildcards (e.g., column LIKE '%substring%') or when functions are applied to indexed columns. This comprehensive look explores various indexing strategies and techniques to accelerate your LIKE operations.

The Challenge with Standard Indexes and LIKE

Standard B-tree indexes are designed for ordered data and efficiently handle range queries and prefix matches. However, when a LIKE pattern includes a leading wildcard (%), the database cannot utilize the ordered nature of a B-tree index to narrow down the search space, often resulting in a full table scan. Similarly, applying functions like LOWER() or UPPER() to a column in a WHERE clause prevents the direct use of a standard index on that column.

Solution 1: Trigram Indexes for Full LIKE Support

For scenarios requiring efficient matching of patterns with leading wildcards, the pg_trgm extension is an excellent solution. It provides trigram (three-character substring) indexing, enabling effective use of both GIN and GiST indexes for arbitrary LIKE and ILIKE patterns.

Installation: First, install the pg_trgm extension if it’s not already available:

CREATE EXTENSION pg_trgm;

Index Creation: You can create GIN or GiST indexes on your columns using pg_trgm operators:

  • GIN Index (generally faster for searches, larger index size):

    CREATE INDEX tbl_col_gin_trgm_idx ON tbl USING gin (col gin_trgm_ops);

  • GiST Index (good balance, can be faster for updates):

    CREATE INDEX tbl_col_gist_trgm_idx ON tbl USING gist (col gist_trgm_ops);

Querying with Trigram Indexes: Once the index is in place, you can use LIKE and ILIKE with leading wildcards, and the index will be utilized:

-- Left-anchored prefix matching
SELECT * FROM tbl WHERE col LIKE 'foo%';

-- Leading wildcard matching (works with trigram indexes)
SELECT * FROM tbl WHERE col LIKE '%foo%';

-- Case-insensitive matching
SELECT * FROM tbl WHERE col ILIKE '%foo%';

Considerations for Short Strings: The pg_trgm extension handles words of any length by converting them into trigrams. The PostgreSQL manual notes that “Each word is considered to have two spaces prefixed and one space suffixed when determining the set of trigrams contained in the string.” For search patterns with fewer than three characters, the index might still work, but performance gains may be less pronounced if the pattern is not selective enough to significantly reduce the scan.

Solution 2: B-tree Indexes for Anchored Patterns

For LIKE queries that are always left-anchored (e.g., column LIKE 'prefix%'), a standard B-tree index is highly effective. PostgreSQL offers specific operator classes for text types that optimize B-tree indexes for pattern matching.

Operator Classes:

  • text_pattern_ops: For text columns.
  • varchar_pattern_ops: For varchar columns.

Index Creation:

-- For text columns
CREATE INDEX tbl_col_text_pattern_ops_idx ON tbl(col text_pattern_ops);

-- For varchar columns
CREATE INDEX tbl_col_varchar_pattern_ops_idx ON tbl(col varchar_pattern_ops);

Querying: These indexes efficiently support queries without leading wildcards:

SELECT * FROM tbl WHERE col LIKE 'prefix%';

Solution 3: Functional Indexes for Case-Insensitive and Function-Based Searches

When your LIKE queries involve functions like LOWER() or UPPER() to achieve case-insensitivity, you can create functional indexes. These indexes store the result of the function, allowing the query planner to use them.

Example: Case-Insensitive Search If you frequently use LOWER(column) LIKE LOWER('%pattern%'), you can create an index on the LOWER() expression:

-- For text columns
CREATE INDEX ix_tblname_col_lower ON tblname (LOWER(col) text_pattern_ops);

-- For varchar columns
CREATE INDEX ix_tblname_col_lower_varchar ON tblname (LOWER(col) varchar_pattern_ops);

Then, your query will efficiently use this index:

SELECT * FROM tblname WHERE LOWER(col) LIKE LOWER('%some name%');

Django ORM, for instance, often uses UPPER(text) for case-insensitive LIKE queries, making an index on UPPER(column::text) very beneficial.

Solution 4: The ^@ Operator and starts_with() Function (PostgreSQL 11+)

PostgreSQL 11 introduced the ^@ operator for prefix matching, which is supported by SP-GiST indexes and, since PostgreSQL 15, also by B-tree indexes with the C collation. The starts_with() function offers similar functionality.

Index Creation (for SP-GiST):

CREATE INDEX tbl_col_spgist_idx ON tbl USING spgist (col);

Querying with ^@:

SELECT * FROM tbl WHERE col ^@ 'foo'; -- Equivalent to col LIKE 'foo%'

Using starts_with():

SELECT * FROM tbl WHERE starts_with(col, 'foo');

B-tree Support (PostgreSQL 15+): For B-tree indexes to support ^@ and starts_with(), ensure you are using the C collation:

CREATE INDEX tbl_col_c_collation_idx ON tbl(col COLLATE "C");
SELECT * FROM tbl WHERE col LIKE 'foo%'; -- Will use the B-tree index with C collation

The COLLATE "C" setting effectively performs byte-order sorting, which aligns with how text_pattern_ops and varchar_pattern_ops work for prefix matching.

Solution 5: Custom Function-Based Indexes (e.g., position())

For specific or more complex pattern matching needs, you can create custom functional indexes. One example is using the position() function to find substrings.

Example: Finding a fixed substring within a string If you need to find a specific word within a larger string and LIKE '%word%' is too slow, consider this approach:

Original query:

SELECT owner1 FROM parcels
WHERE lower(owner1) LIKE lower('%someones name%');

Create a functional index on position():

CREATE INDEX ix_parcels ON parcels(position(lower(owner1) in 'someones name'));

Modified query:

SELECT owner1 FROM parcels
WHERE position(lower(owner1) in 'someones name') > 0;

This approach can be highly effective when the substring you’re searching for is fixed, allowing the index to pinpoint relevant rows.

Solution 6: Wildspeed (Third-Party)

While not a built-in PostgreSQL feature, extensions like “Wildspeed” are designed to support %word% wildcards efficiently. However, be aware that Wildspeed indexes can become very large, impacting storage and potentially write performance.

Summary of Strategies

  • No leading wildcard (LIKE 'prefix%'): Use standard B-tree indexes with text_pattern_ops or varchar_pattern_ops, or B-tree indexes with COLLATE "C".
  • Any wildcard (LIKE '%substring%', ILIKE '%substring%'): Employ pg_trgm with GIN or GiST indexes.
  • Case-insensitive searches (ILIKE, LOWER()): Use functional indexes on LOWER() or UPPER().
  • Prefix matching (col LIKE 'prefix%'): Consider the ^@ operator or starts_with() function with SP-GiST or B-tree indexes (PostgreSQL 15+ with C collation).

When a function is applied to a column in your WHERE clause, PostgreSQL typically cannot use a standard index directly on that column. Creating a functional index that matches the exact expression used in the WHERE clause is key.

FAQs on PostgreSQL LIKE Query Speedup

Q: Can PostgreSQL LIKE queries use standard indexes

ANS: Standard B-tree indexes are efficient for LIKE queries with no leading wildcard (e.g., column LIKE 'prefix%'). For patterns with leading wildcards (e.g., column LIKE '%substring%'), standard indexes are generally not used, leading to full table scans.

Q: How to speed up LIKE queries with leading wildcards

ANS: Use the pg_trgm extension to create GIN or GiST indexes. These indexes are specifically designed to accelerate LIKE and ILIKE queries, even those with leading wildcards.

Q: Does LIKE with functions like LOWER or UPPER use indexes

ANS: No, applying functions like LOWER() or UPPER() to a column in a WHERE clause prevents the direct use of standard indexes on that column. To optimize these queries, create a functional index on the expression itself (e.g., CREATE INDEX ON mytable (LOWER(mycolumn))).

Q: What is the difference between GIN and GiST indexes with pg_trgm

ANS: GIN indexes are generally faster for searches but can be larger and slower for updates. GiST indexes offer a good balance between search performance and update efficiency, and their index size is typically smaller than GIN. The choice often depends on your read/write workload.

Q: How can I speed up case-insensitive LIKE queries

ANS: Create a functional index on LOWER(column) or UPPER(column) if your queries use ILIKE or LOWER(column) LIKE LOWER('%pattern%'). For example: CREATE INDEX ON your_table (LOWER(your_column) text_pattern_ops);.

Q: What is the ^@ operator in PostgreSQL

ANS: The ^@ operator, introduced in PostgreSQL 11, is a prefix-matching operator that works efficiently with SP-GiST indexes. Since PostgreSQL 15, it also supports B-tree indexes if a C collation is used on the indexed column. It’s an alternative to column LIKE 'prefix%' that can be more efficient.
