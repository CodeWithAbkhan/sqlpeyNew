“Effective SQL Server Paging Strategies Beyond Basic OFFSET FETCH”

How can developers efficiently paginate data in Microsoft SQL Server, given the different versions and performance characteristics of various techniques? A variety of methods exist, from newer T-SQL features to established patterns utilizing window functions and specialized cursor emulation.

Utilizing SQL Server 2012+ OFFSET and FETCH NEXT

For SQL Server 2012 and later, the OFFSET and FETCH NEXT clauses provide a very direct approach to paging, much simpler than older methods.

Example: Retrieving the second page of 10 rows, ordered by id:

SELECT * 
FROM TableName 
ORDER BY id 
OFFSET 10 ROWS 
FETCH NEXT 10 ROWS ONLY;

Key implementation constraints when using OFFSET ... FETCH:

  • An ORDER BY clause is mandatory for the OFFSET ... FETCH expression to be valid.
  • The OFFSET clause is required if FETCH is present; you cannot use just ORDER BY ... FETCH.
  • TOP cannot coexist with OFFSET and FETCH within the same query expression.

If you need to calculate the offset dynamically based on page number and size, a stored procedure can encapsulate this logic.

Stored Procedure Example with Dynamic Paging:

CREATE PROCEDURE Paginate_Data_Dynamic
(
 @PageNumber INT,
 @RowsPerPage INT
)
AS
BEGIN
    SET NOCOUNT ON;
    
    DECLARE @OffsetCount INT = (@PageNumber - 1) * @RowsPerPage;
    
    SELECT 
        DataColumn1, 
        DataColumn2 
    FROM SourceTable 
    ORDER BY DataColumn1 ASC  -- ORDER BY is essential
    OFFSET @OffsetCount ROWS 
    FETCH NEXT @RowsPerPage ROWS ONLY;
END
GO

-- Execution example: Get page 2, 15 rows per page
EXEC Paginate_Data_Dynamic @PageNumber = 2, @RowsPerPage = 15;

This pattern is also suitable for implementation within stored procedures for cleaner application integration, as shown in some examples here .

Pagination Using ROW_NUMBER() and Subqueries/CTEs

Before SQL Server 2012, or when needing greater control over sorting and filtering within the paging mechanism, employing the ROW_NUMBER() window function within a Common Table Expression (CTE) or subquery is a robust alternative.

This technique requires two steps: first, assigning a row number based on the desired ordering, and second, filtering based on that calculated row number.

Example: Retrieving rows 1 through 19 using ROW_NUMBER():

Consider the base query: SELECT * FROM Orders WHERE OrderDate >= '1980-01-01' ORDER BY OrderDate.

  1. Counting Total Records (Separate Operation): To display total page counts, you execute a count query separately:

    SELECT COUNT(*) 
FROM Orders 
WHERE OrderDate >= '1980-01-01';

  2. Fetching Paged Results:

    SELECT *
FROM    
    ( 
        SELECT    
            ROW_NUMBER() OVER (ORDER BY OrderDate) AS RowNum, 
            *
        FROM      Orders
        WHERE     OrderDate >= '1980-01-01'
    ) AS RowConstrainedResult
WHERE   RowNum >= 1
    AND RowNum < 20 -- Represents rows 1 to 19
ORDER BY RowNum;

Alternative using CTE: This is often preferred for readability.

WITH OrderedResults AS
(
    SELECT
        ROW_NUMBER() OVER(ORDER BY FirstName DESC) AS RowNumber, 
        FirstName, 
        LastName, 
        ROUND(SalesYTD, 2, 1) AS "Sales_YTD"
    FROM [dbo].[vSalesPerson]
) 
SELECT RowNumber, 
    FirstName, 
    LastName, 
    "Sales_YTD" 
FROM OrderedResults 
WHERE RowNumber > 50 AND RowNumber < 60; -- Gets rows 51 through 59

If you lack a deterministic sorting column, using CURRENT_TIMESTAMP in the ORDER BY can provide sequential numbering, though this implies insertion order, which isn’t guaranteed for stable paging across transactions unless the table structure enforces it.

SELECT TOP 20 
    col1, col2
FROM (
    SELECT 
         tbl.col1
        ,tbl.col2
        ,ROW_NUMBER() OVER (ORDER BY CURRENT_TIMESTAMP) AS sort_row
    FROM dbo.MyTable tbl
    ) AS query
WHERE query.sort_row > 10 -- Rows 11 to 30
ORDER BY query.sort_row;

The High-Performance Keyset / Seek Method

When dealing with very large result sets and deep page numbers, the offset-based methods (both OFFSET/FETCH and ROW_NUMBER on the entire filtered set) can become slow because the database must still scan and discard the initial rows. The “seek method,” also termed keyset pagination, offers superior performance by using the values from the last row of the previous page as a starting point.

This method relies on indexed columns being unique or having composite uniqueness. It allows fetching the next page in near constant time relative to the page size, assuming good indexing.

Keyset Pagination Logic (Fetching the Next Page):

If the previous page ended on a record where score was 100 and player_id was 42:

SELECT TOP 10 first_name, last_name, score, COUNT(*) OVER() AS TotalRecords
FROM players
WHERE (score < 100) -- Criteria on the primary sort column
   OR (score = 100 AND player_id < 42) -- Tie-breaker criteria
ORDER BY score DESC, player_id DESC;
  • The COUNT(*) OVER() window function can optionally return the total record count across the entire filtered set alongside the paged data.
  • If the ordering direction is ASC, the comparison operators (<, =) should be swapped to (>, =) respectively.
  • A limitation is that this approach does not easily permit jumping directly to an arbitrary page (e.g., page 50) without iterating through the preceding pages.

Solutions for Older SQL Server Versions (Pre-2008/2000)

For environments restricted to older versions, simulating sequence generation is necessary.

Simulating ROW_NUMBER() with a Table Variable (SQL Server 2000)

This approach uses a temporary table variable with an IDENTITY column to enforce row numbering based on the desired order, effectively mimicking the ROW_NUMBER() function.

Example (Simulating page 51, size 20, based on Orders.ID):

DECLARE @PageNo INT = 51;
DECLARE @PageSize INT = 20;

DECLARE @FirstRecord INT = (@PageNo - 1) * @PageSize + 1; -- 1001
DECLARE @LastRecord INT = @FirstRecord + @PageSize - 1;   -- 1020

-- Table variable to hold ordered keys
DECLARE @OrderedKeys TABLE (
  RowNum INT IDENTITY NOT NULL PRIMARY KEY CLUSTERED,
  TableKey INT NOT NULL
);

-- Use SET ROWCOUNT to limit inserts, necessary because TOP does not accept variables in SQL 2000
SET ROWCOUNT @LastRecord;
INSERT INTO @OrderedKeys (TableKey) 
SELECT ID 
FROM Orders 
WHERE OrderDate >= '1980-01-01' 
ORDER BY OrderDate;

SET ROWCOUNT 0; -- Reset ROWCOUNT

SELECT t.*
FROM Orders t
INNER JOIN @OrderedKeys o ON o.TableKey = t.ID
WHERE o.RowNum >= @FirstRecord
ORDER BY o.RowNum;

Using TOP with Subqueries

A less ideal, but functional, method for older systems involves nested TOP clauses, though this can lead to complex execution plans and poor performance compared to keyset pagination.

-- Variables @offset (records to skip) and @limit (rows per page) are assumed set
SELECT TOP @limit a.*
FROM (
    SELECT TOP @limit b.*, COUNT(*) OVER() AS TotalRows 
    FROM TABLENAME b 
    ORDER BY id ASC
) a
ORDER BY id DESC; -- This structure is complex and often unstable without appropriate keys/ordering

This specific example seems designed to retrieve the last page or is conceptually flawed for standard sequential paging; standard TOP methods usually rely on calculated offsets or key lookups.

Dynamic Sorting and Filtering with sp_executesql

When complex dynamic sorting, filtering (like containment checks on different columns), and paging are required, building the SQL string dynamically and using sp_executesql is powerful, especially for SQL 2008 and earlier environments where parameterizing sorts/filters is tricky.

This approach separates counting total rows from fetching the data chunk. The data fetching uses a nested NOT IN logic to skip previously fetched IDs.

-- Snippet demonstrating the structure for SQL 2008+ with dynamic sorting
-- ... Variable declarations for @PageSize, @SkippedRows, @SortBy, @Filter ...

-- Total Rows Count
SET @sql =  'SELECT Count(' + @strID + ')  FROM ' + @strFROM + @strFilter;
EXEC sp_executesql @sql;

-- Paging Query (Using nested NOT IN logic)
SET @sql = 'SELECT ' + @strFields + ' FROM ' + @strFROM +
    ' WHERE ' + @strID +  ' IN ' + 
   '  (SELECT TOP ' + @strPageSize + ' ' + @strID + ' FROM ' + @strFROM + @strFilter + 
             ' AND  ' + @strID + ' NOT IN ' + '
          (SELECT TOP ' + @strSkippedRows + ' ' + @strID + ' FROM ' + @strFROM + @strFilter + @SortBy + ') ' 
   + @SortBy + ') ' + @SortBy;
EXEC sp_executesql @sql;

The benefit here is that sp_executesql caches execution plans if parameters are passed consistently.

Determining Total Records for Display

For UI elements that need to show total page counts (e.g., “Page 5 of 20”), obtaining the total count without slowing down the primary data retrieval is crucial.

If you use the ROW_NUMBER() technique, you can include a window function for the total count in the inner query.

Example incorporating total count:

WITH DataWithTotal AS
(  
  SELECT 
    TABLE_ID, 
    ROW_NUMBER() OVER (ORDER BY TABLE_ID) AS RN,
    -- Calculate total count across all rows meeting the WHERE criteria
    (SELECT COUNT(TABLE_ID) FROM TABLE) AS TOTAL_ROWS 
  FROM TABLE (NOLOCK)
)
SELECT 
    T2.FIELD1, 
    T2.FIELD2, 
    T2.FIELD3, 
    T.TOTAL_ROWS  -- Total count is now available in every returned row
FROM TABLE T2 (NOLOCK)
INNER JOIN DataWithTotal T ON T2.TABLE_ID = T.TABLE_ID
WHERE T.RN >= 100 AND T.RN < 200;

This allows fetching the page data and the total count in a single query, provided the total count subquery is performant (ideally using indexed columns).

FAQs on SQL Server Paging Strategies

Q: Is ORDER BY mandatory when using OFFSET FETCH

ANS: Yes, when utilizing the OFFSET … FETCH clause in SQL Server, an ORDER BY clause is mandatory to define the sequence from which rows are skipped and fetched.

Q: Can TOP and OFFSET FETCH be used together

ANS: No, the TOP clause cannot be combined with the OFFSET and FETCH clauses in the same query expression.

Q: What is keyset pagination

ANS: Keyset pagination, also known as the seek method, is a high-performance paging technique that uses the key values of the last record from the preceding page to efficiently locate the starting point of the next page, avoiding sequential row scanning.

Q: How to paginate in SQL Server 2000

ANS: For SQL Server 2000, pagination typically involves using SET ROWCOUNT combined with an intermediate table variable that uses an IDENTITY column to simulate the row numbering provided by ROW_NUMBER() in later versions.
SELECT * FROM TableName ORDER BY id OFFSET 10 ROWS FETCH NEXT 10 ROWS ONLY;
