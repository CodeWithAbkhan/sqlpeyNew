Emulating FULL OUTER JOIN in MySQL

The core challenge in MySQL is replicating the behavior of a FULL OUTER JOIN, which returns all rows from both the left and right tables. When a match is found, the rows are combined. When no match exists on either side, the columns from the non-matching table are filled with NULL.

Here are several accepted solutions and explanations for emulating this functionality:

Solution 1: UNION of LEFT JOIN and RIGHT JOIN (with conditional filtering)

This is a common approach that leverages UNION ALL to combine the results of a LEFT JOIN and a RIGHT JOIN. To avoid duplicate rows (especially where matches exist), the second part of the UNION ALL is filtered to include only rows where the left table’s joining key is NULL.

  • Concept: A LEFT JOIN gets all rows from the left table and matching rows from the right. A RIGHT JOIN gets all rows from the right table and matching rows from the left. By combining these and ensuring unmatched rows from the right are included (while filtering out duplicates from the left match), you achieve the FULL OUTER JOIN effect.

  • Example:

    SELECT * FROM table1
LEFT JOIN table2 ON table1.id = table2.id
UNION ALL
SELECT * FROM table1
RIGHT JOIN table2 ON table1.id = table2.id
WHERE table1.id IS NULL;

Solution 2: UNION of LEFT JOIN and filtered RIGHT JOIN (more explicit)

Similar to Solution 1, this method uses UNION (which implicitly removes duplicates) to combine a LEFT OUTER JOIN and a RIGHT OUTER JOIN. It explicitly adds a WHERE clause to the RIGHT OUTER JOIN to select rows where the joining key from the left table is NULL. This ensures that rows present in the right table but not in the left are captured, without duplicating matched rows.

  • Example:

    SELECT *
FROM `table1`
LEFT OUTER JOIN `table2` ON `table1`.`id` = `table2`.`id`
UNION
SELECT *
FROM `table1`
RIGHT OUTER JOIN `table2` ON `table1`.`id` = `table2`.`id`
WHERE `table1`.`id` IS NULL;

Solution 3: UNION ALL with Anti-Join Pattern

This approach is often preferred for its efficiency and clarity in handling duplicate rows correctly. It uses UNION ALL to combine a LEFT OUTER JOIN with another query that specifically selects rows present only in the second table (using an anti-join pattern).

  • Concept: The first part performs a LEFT OUTER JOIN. The second part finds rows in table2 that do not have a corresponding id in table1, using WHERE t1.value IS NULL after a RIGHT JOIN (effectively selecting rows only in table2). UNION ALL is crucial here to preserve all rows, including potential duplicates that a standard FULL OUTER JOIN would maintain.

  • Example:

    SELECT
    t1.value, t2.value
FROM table1 t1
LEFT OUTER JOIN table2 t2
  ON t1.value = t2.value
UNION ALL
SELECT
    t1.value, t2.value
FROM table2 t2
LEFT OUTER JOIN table1 t1
  ON t1.value = t2.value
WHERE
    t1.value IS NULL;

Solution 4: UNION of LEFT JOIN and filtered RIGHT JOIN (alternative syntax)

This variation demonstrates another way to structure the UNION ALL approach. It explicitly selects matching rows from table1 and table2 using a LEFT JOIN, and then uses a RIGHT JOIN with a WHERE clause on the left table’s joining column to capture rows only present in table2.

  • Example:

    SELECT * FROM table1
LEFT JOIN table2 ON table1.id = table2.id
UNION ALL
SELECT * FROM table1
RIGHT JOIN table2 ON table1.id = table2.id
WHERE table1.id IS NULL;

    (Note: This is identical to Solution 1, highlighting that different phrasing can lead to the same effective query).

Solution 5: UNION ALL with Exclusionary WHERE Clauses

This method also uses UNION ALL but applies WHERE clauses to exclude specific matches in each part of the union. The first query selects all LEFT JOIN results. The second query selects all RIGHT JOIN results but filters out rows where the left table’s primary key exists, effectively capturing only the unmatched rows from the right.

  • Example:

    (SELECT
    *
FROM
    table1 t1
        LEFT JOIN
    table2 t2 ON t1.id = t2.id
WHERE
    t2.id IS NULL)
UNION ALL
 (SELECT
    *
FROM
    table1 t1
        RIGHT JOIN
    table2 t2 ON t1.id = t2.id
WHERE
    t1.id IS NULL);

Solution 6: Using NOT EXISTS for Unmatched Rows

This robust solution combines a LEFT JOIN with NOT EXISTS clauses to construct the FULL OUTER JOIN behavior. The LEFT JOIN covers all rows from the left table and matching rows from the right. The NOT EXISTS clauses then add rows that are exclusively in the right table.

  • Concept: It first performs a LEFT JOIN. Then, it uses UNION ALL to append rows from the right table that do not have a corresponding entry in the left table, verified using NOT EXISTS. This precisely mirrors the FULL OUTER JOIN semantics.

  • Example:

    select l.*, r.*
from employee as l
left join department as r on l.fk = r.id

union all

select null, null, null, r.*
from department as r
where not exists (
  select 1
  from employee as l
  where l.fk = r.id
);

Solution 7: Comprehensive UNION ALL for All Cases

This approach is presented as a more comprehensive emulation, particularly addressing edge cases with duplicate values that standard UNION might mask. It involves a LEFT JOIN and a RIGHT JOIN combined with UNION ALL, but with careful consideration for predicate placement and potential NULL values.

  • Example:

    SELECT t1.*, t2.*
FROM (SELECT * FROM t1 UNION SELECT name FROM t2) tmp
LEFT JOIN t1 ON t1.id = tmp.id
LEFT JOIN t2 ON t2.id = tmp.id;

    This query cleverly uses a preliminary UNION to create a distinct set of all possible join keys, then performs LEFT JOINs against both original tables.

Solution 8: Handling Duplicate Values with UNION ALL and NOT EXISTS

This strategy explicitly addresses scenarios where duplicate values in the join columns can lead to incorrect results with simple UNION or UNION ALL based LEFT/RIGHT JOIN combinations. It constructs the result by combining matching rows (via JOIN), rows only in table1 (via WHERE NOT EXISTS), and rows only in table2 (via WHERE NOT EXISTS).

  • Example:

    -- (t1 ∩ t2): all in both t1 and t2
select t1.value, t2.value
from t1 join t2 on t1.value = t2.value
union all  -- And plus
-- all in t1 that not exists in t2
select t1.value, null
from t1
where not exists( select 1 from t2 where t2.value = t1.value)
union all  -- and plus
-- all in t2 that not exists in t1
select null, t2.value
from t2
where not exists( select 1 from t1 where t2.value = t1.value);

Solution 9: Emulating with LEFT JOIN and RIGHT JOIN (simplified)

This solution provides a concise way to emulate FULL OUTER JOIN using LEFT JOIN and RIGHT JOIN with UNION. It’s important to note that MySQL converts RIGHT JOIN to LEFT JOIN internally by swapping table order, which can have implications for predicate optimization.

  • Example:

    SELECT t1.name, t2.name FROM t1
LEFT JOIN t2 ON t1.id = t2.id
UNION
SELECT t1.name, t2.name FROM t2
LEFT JOIN t1 ON t1.id = t2.id;

Solution 10: Handling Predicates and Optimization Nuances

When using FULL OUTER JOIN emulation in MySQL, especially with WHERE clauses, it’s crucial to be aware of how the query optimizer handles predicates. A WHERE clause that might be applied to a table in a RIGHT JOIN could become NULL-rejected if that table is reordered by the optimizer. This can inadvertently convert outer joins into inner joins.

  • Example demonstrating the issue:

    -- Potentially problematic query
SELECT * FROM table1
LEFT JOIN table2 ON table1.id = table2.id
WHERE table1.col1 = 'someValue'
UNION
SELECT * FROM table1
RIGHT JOIN table2 ON table1.id = table2.id
WHERE table1.col1 = 'someValue';

-- Optimized (and potentially incorrect) translation
SELECT * FROM table1
LEFT JOIN table2 ON table1.id = table2.id
WHERE table1.col1 = 'someValue'
UNION
SELECT * FROM table2
LEFT JOIN table1 ON table2.id = table1.id
WHERE table1.col1 = 'someValue';

    If table1.col1 is NOT NULL, the second part of the UNION can be NULL-rejected, leading to unexpected results.

Solution 11: Aggregation with UNION ALL

This advanced technique utilizes UNION ALL in conjunction with aggregation (SUM) to achieve a result similar to a FULL OUTER JOIN when dealing with aggregated data. It’s particularly useful when you need to combine values from the same columns across two tables based on a common key.

  • Example:

    select
    name, sum(num1) num1, sum(num2) num2
from
(
select name, num1, 0 num2 from table1
union all
select name, 0 num1, num2 from table2
) t
group by name;

Solution 12: UNION of LEFT JOIN and RIGHT JOIN (Column Alignment)

When using UNION to combine LEFT JOIN and RIGHT JOIN for FULL OUTER JOIN emulation, ensure that the selected columns are aligned in both parts of the query. This means selecting the same number of columns with compatible data types.

  • Example:

    SELECT
    a.name,
    b.title
FROM
    author AS a
LEFT JOIN
    book AS b
    ON a.id = b.author_id
UNION
SELECT
    a.name,
    b.title
FROM
    author AS a
RIGHT JOIN
    book AS b
    ON a.id = b.author_id;

Solution 13: Handling Duplicates with UNION and LEFT JOIN

This method addresses the edge case where standard UNION or UNION ALL might not correctly handle duplicate entries in the join columns, as demonstrated with a specific test case involving CTEs. It proposes a structure using a UNION of all distinct keys, followed by LEFT JOINs to both tables.

  • Example:

    SELECT t1.*, t2.*
FROM (SELECT * FROM t1 UNION SELECT name FROM t2) tmp
LEFT JOIN t1 ON t1.id = tmp.id
LEFT JOIN t2 ON t2.id = tmp.id;

FAQs on Emulating FULL OUTER JOIN in MySQL

Q: What is the primary challenge in MySQL regarding FULL OUTER JOIN

ANS: MySQL does not have a native FULL OUTER JOIN clause. This necessitates using alternative methods to combine data from two tables, including unmatched rows from both.

Q: Which method is generally considered efficient for FULL OUTER JOIN emulation

ANS: Methods employing UNION ALL with careful filtering or NOT EXISTS clauses are often more efficient, especially on large datasets, as they can avoid the overhead of duplicate removal that UNION might incur.

Q: Can standard UNION handle duplicate rows correctly in FULL OUTER JOIN emulation

ANS: Standard UNION removes duplicate rows, which can lead to incorrect results when your FULL OUTER JOIN logic is intended to preserve all data, including duplicates. Using UNION ALL with specific filtering is generally preferred.

Q: What precautions should be taken with WHERE clauses in FULL OUTER JOIN emulation

ANS: Be mindful of how MySQL’s optimizer handles predicates in outer joins. A WHERE clause applied to a table involved in a RIGHT JOIN might be reordered, potentially leading to NULL-rejection and conversion to an INNER JOIN if the column is NOT NULL.
