“SQL Server String Aggregation Techniques: FOR XML PATH vs STRING_AGG”

How can database developers aggregate multiple rows of string data into a single comma-separated value within SQL Server, especially when dealing with older versions that lack the native STRING_AGG function, and what are the critical differences when handling special characters using the prevalent FOR XML PATH technique?

The primary method for this task in SQL Server versions preceding SQL Server 2017 relies on a clever application of FOR XML PATH('') combined with the STUFF function.

Basic Row Concatenation with STUFF and FOR XML PATH

For a simple scenario involving a single table, the approach focuses on prepending a delimiter to every element and then trimming the leading delimiter using STUFF.

Consider a table named tabel with an id column.

Original Technique Example:

SELECT STUFF(
    (
        SELECT ',' + CAST(t.id AS VARCHAR(MAX))
        FROM tabel t
        FOR XML PATH('')
    ), 
    1, 1, ''
);

Explanation:

  1. SELECT ',' + CAST(t.id AS VARCHAR(MAX)) FROM tabel t FOR XML PATH(''): This generates a single XML node containing all concatenated values separated by commas (e.g., <row>1</row><row>2</row><row>3</row>). FOR XML PATH('') collapses the output into one continuous string, prefixed by the comma we added.
  2. STUFF(..., 1, 1, ''): This function removes the very first character (the redundant leading comma) by starting at position 1, removing 1 character, and replacing it with an empty string.

Handling Special Characters and XML Escaping

A significant pitfall when using FOR XML PATH is how it automatically escapes characters that have special meaning in XML (like <, >, and &). If you do not intend for this escaping to occur, the resulting string may not be what you expect.

Example of Undesired Escaping:

If your data contains strings like '7 > 5' or 'Salt & pepper', the raw FOR XML PATH might yield: 7 &amp;gt; 5,Salt &amp;amp; pepper,2&#x0D;lines

Alternative Solution: Using .value() with TYPE to Bypass Escaping

To prevent the XML serialization process from escaping these characters, you can append .value('(./text())[1]', 'varchar(MAX)') to the FOR XML PATH clause. This forces the result to be treated as pure text content rather than fully formed XML nodes.

Refined Technique Example (Preventing Escaping):

SELECT STUFF(
    (
        SELECT ',' + V.String
        FROM (VALUES 
            ('7 > 5'),
            ('Salt & pepper'),
            ('2' + CHAR(13) + 'lines') -- Representing a newline scenario
        ) AS V(String)
        FOR XML PATH(''), TYPE
    ).value('(./text())[1]', 'varchar(MAX)')
, 1, 1, '');

This refined approach yields the desired output, mirroring the behavior of the modern STRING_AGG function in this context: 7 > 5,Salt & pepper,2\r\nlines

Implementing Group-Specific Aggregation with Correlated Subqueries

Often, string aggregation is required within groups, for instance, concatenating characters belonging to the same GroupID. In versions without STRING_AGG, a correlated subquery within the main SELECT statement is necessary.

Setup for Grouped Example:

CREATE TABLE dbo.MyTable (
    ID INT IDENTITY(1,1) PRIMARY KEY,
    GroupID INT,
    SomeCharacter CHAR(1)
);

INSERT INTO dbo.MyTable (GroupID, SomeCharacter)
VALUES 
(1,'A'), (1,'B'), (1,'D'),
(2,'C'), (2,NULL), (2,'Z');

Correlated Subquery for Group Aggregation:

This method links the outer query’s group identifier to the inner subquery’s filtering condition (WHERE sq.GroupID = MT.GroupID).

SELECT 
    MT.GroupID,
    STUFF(
        (
            SELECT ',' + sq.SomeCharacter 
            FROM dbo.MyTable sq
            WHERE sq.GroupID = MT.GroupID -- Correlation point
            FOR XML PATH(''), TYPE
        ).value('(./text())[1]', 'varchar(MAX)')
    , 1, 1, '') AS Characters
FROM dbo.MyTable MT
GROUP BY MT.GroupID;

This achieves the same result as:

SELECT 
    MT.GroupID,
    STRING_AGG(MT.SomeCharacter, ',')
FROM dbo.MyTable MT
GROUP BY MT.GroupID;

Grouping on Multiple Columns: If grouping involves two columns (e.g., SomeColumn and AnotherColumn), the correlation condition in the subquery’s WHERE clause must include both checks: WHERE sq.SomeColumn = MT.SomeColumn AND sq.AnotherColumn = MT.AnotherColumn. The outer query must also group by both columns.

Aggregating Across Tables (One-to-Many): If aggregating strings from a different table (dbo.YourTable) based on a foreign key relationship (MyID), the correlation happens on the key columns:

SELECT 
    MT.MyID,
    STUFF((
        SELECT ',' + YT.SomeString
        FROM dbo.YourTable YT
        WHERE YT.MyID = MT.MyID -- Correlation based on FK
        FOR XML PATH(''), TYPE
    ).value('(./text())[1]','varchar(MAX)'), 1, 1, '')
FROM dbo.MyTable MT;

This is functionally similar to a join followed by STRING_AGG and GROUP BY.

Enforcing Specific Order in Aggregation

To dictate the order of elements in the resulting concatenated string, an ORDER BY clause must be included inside the subquery feeding FOR XML PATH.

Example Enforcing Descending Order by ID:

SELECT 
    MT.GroupID,
    STUFF(
        (
            SELECT ',' + sq.SomeCharacter 
            FROM dbo.MyTable sq
            WHERE sq.GroupID = MT.GroupID
            ORDER BY sq.ID DESC -- Ordering enforced here
            FOR XML PATH(''), TYPE
        ).value('(./text())[1]','varchar(MAX)')
    , 1, 1, '') AS OrderedCharacters
FROM dbo.MyTable MT
GROUP BY MT.GroupID;

This replicates the functionality of STRING_AGG(..., ',') WITHIN GROUP (ORDER BY mt.id DESC).

Performance Considerations and Alternatives

The FOR XML PATH method involves repeated execution of the subquery for every row in the outer result set, making it inherently less performant than the set-based STRING_AGG function, especially on large datasets or when multiple aggregations are needed.

If performance becomes a major bottleneck, one should scrutinize whether the required aggregation is strictly necessary or consider upgrading the SQL Server instance to gain access to STRING_AGG.

Concatenating Non-String Data

When combining data types other than strings (like numbers or dates), the + concatenation operator requires explicit casting. An alternative is using the CONCAT function, which performs implicit type conversion to string. However, be cautious: implicit conversion for types like DATETIME or FLOAT might result in less predictable string formats. For precise formatting, use CONVERT before concatenation.

FAQs on SQL Server String Aggregation Techniques

Q: What is the primary function of STUFF when used with FOR XML PATH for concatenation

ANS: The STUFF function’s purpose is to surgically remove the leading comma that is redundantly introduced by the concatenation inside the FOR XML PATH subquery.

Q: Does FOR XML PATH automatically escape special XML characters

ANS: Yes, by default, FOR XML PATH escapes characters like &, >, and <. Using .value(’(./text())[1]’,‘varchar(MAX)’) after the XML generation circumvents this escaping behavior.

Q: Is FOR XML PATH as efficient as STRING_AGG

ANS: No, FOR XML PATH often performs worse because it typically relies on correlated subqueries, leading to multiple executions compared to the set-based operation of STRING_AGG.
