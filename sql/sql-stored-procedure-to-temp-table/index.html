“SQL Stored Procedure Results into Temporary Tables: Methods and Best Practices”

When working with SQL Server, there are several scenarios where you need to execute a stored procedure and then utilize its returned data within a temporary table. This is common for data manipulation, reporting, or when integrating stored procedure output into other SQL queries. This question explores various methods to achieve this, offering different approaches based on SQL Server versions and specific requirements.

Storing Stored Procedure Output in Temp Tables

Several methods exist to insert the results of a stored procedure into a temporary table. The choice of method often depends on the SQL Server version, the complexity of the stored procedure’s output, and whether parameters are involved.

Solution 1: Using OPENROWSET with Ad Hoc Distributed Queries

This approach leverages OPENROWSET to execute a stored procedure on the same server and direct its output into a temporary table. It requires enabling ‘Ad Hoc Distributed Queries’.

Prerequisites:

Ensure ‘Ad Hoc Distributed Queries’ is enabled:

sp_configure 'Show Advanced Options', 1;
GO
RECONFIGURE;
GO
sp_configure 'Ad Hoc Distributed Queries', 1;
GO
RECONFIGURE;
GO

Code Example:

-- Define a sample stored procedure
CREATE PROC GetBusinessLineHistory
AS
BEGIN
    SELECT * FROM sys.databases
END
GO

-- Execute the stored procedure and insert results into a temporary table
SELECT * INTO #MyTempTable
FROM OPENROWSET('SQLNCLI', 'Server=(local)\SQL2008;Trusted_Connection=yes;',
     'EXEC GetBusinessLineHistory')

-- Display the contents of the temporary table
SELECT * FROM #MyTempTable;
GO

-- Clean up the sample stored procedure
DROP PROC GetBusinessLineLineHistory;
GO

Considerations:

  • OPENROWSET is intended for ad hoc, one-time connections to OLE DB data sources. For frequent access, linked servers are preferred.
  • It incurs overhead for opening local connections and marshalling data.
  • Requires ‘Ad Hoc Distributed Queries’ permission, which can be a security consideration.
  • Cannot handle stored procedures returning multiple result sets.

Solution 2: Using INSERT ... EXEC

This is a straightforward method where you create a temporary table with the expected schema and then use INSERT ... EXEC to populate it with the stored procedure’s results.

Code Example:

-- Assume 'SpGetRecords' is a stored procedure that returns data
-- Create a temporary table with a defined schema
CREATE TABLE #tmpBus
(
   COL1 INT,
   COL2 VARCHAR(100) -- Example column, adjust based on sproc output
);

-- Insert data from the stored procedure
INSERT INTO #tmpBus
EXEC SpGetRecords 'SomeParameter'; -- Replace with actual parameters

-- View the data
SELECT * FROM #tmpBus;
GO

-- Clean up
DROP TABLE #tmpBus;
GO

Alternative (Table Variable):

You can also use a table variable instead of a temporary table:

DECLARE @tmpBusTableVar TABLE
(
   COL1 INT,
   COL2 VARCHAR(100) -- Example column, adjust based on sproc output
);

INSERT INTO @tmpBusTableVar
EXEC SpGetRecords 'SomeParameter'; -- Replace with actual parameters

SELECT * FROM @tmpBusTableVar;
GO

Solution 3: Using Inline Table-Valued User-Defined Functions (TVFs)

For scenarios where a stored procedure’s logic can be encapsulated in a function, inline TVFs offer a clean way to return a table. This function can then be used with SELECT INTO.

Code Example:

-- Create an inline table-valued function
CREATE FUNCTION dbo.CustomersByRegion
(
    @RegionID INT
)
RETURNS TABLE
AS
RETURN
  SELECT CustomerID, CustomerName
  FROM dbo.Customers -- Replace with your actual customer table
  WHERE RegionID = @RegionID;
GO

-- Use the function with SELECT INTO
SELECT * INTO #CustomerList FROM dbo.CustomersByRegion(1);

-- Display the results
SELECT * FROM #CustomerList;
GO

-- Clean up
DROP FUNCTION dbo.CustomersByRegion;
DROP TABLE #CustomerList;
GO

You can wrap this function within a stored procedure if the requirement is strictly for a stored procedure interface.

Solution 4: Dynamically Generating Temporary Table Definitions

When the stored procedure’s output schema is complex or unknown beforehand, dynamic SQL can be used to first determine the schema and then create a temporary table.

Method using sys.dm_exec_describe_first_result_set_for_object (SQL Server 2012+):

This dynamic management view (DMV) can describe the result set of a stored procedure.

-- Declare variables for procedure name and temporary table name
DECLARE @ProcedureName NVARCHAR(128) = 'dbo.YourStoredProcedure'; -- Replace with your procedure
DECLARE @TempTableName NVARCHAR(128) = '#DynamicTempTable';
DECLARE @SQL NVARCHAR(MAX);

-- Stored procedure to generate CREATE TABLE statement (from Solution 11)
-- Assumes you have the dbo.usp_GetStoredProcTableDefinition proc from Solution 11
-- If not, it needs to be created first.

-- Example of generating the CREATE TABLE statement
SET @SQL = 'CREATE TABLE ' + @TempTableName + ' ('

SELECT @SQL = @SQL + '['+name +'] '+ system_type_name + ','
        FROM sys.dm_exec_describe_first_result_set_for_object
        (
          OBJECT_ID(@ProcedureName),
          NULL
        );

-- Remove trailing comma
SET @SQL = SUBSTRING(@SQL,0,LEN(@SQL))
SET @SQL =  @SQL +')'

-- Execute the CREATE TABLE statement
EXEC (@SQL);

-- Insert results into the dynamically created temp table
INSERT INTO #DynamicTempTable
EXEC @ProcedureName; -- Add parameters if your procedure requires them

-- Display the results
SELECT * FROM #DynamicTempTable;
GO

-- Clean up
DROP TABLE #DynamicTempTable;
GO

Alternative Dynamic Method using sp_describe_first_result_set:

This system stored procedure can also be used to get the result set definition.

DECLARE @ProcName VARCHAR(100) = 'PROCEDURENAME'; -- Replace with your procedure name
DECLARE @Params VARCHAR(MAX) = '''Param1'', ''Param2'''; -- Replace with your parameters
DECLARE @ExecStr NVARCHAR(MAX) = N'exec ' + @ProcName + ' ' + @Params;
DECLARE @Qry NVARCHAR(MAX);

-- Temporary table to hold the result set definition
CREATE TABLE #ResultSetDefinition
(
    name sysname NULL,
    system_type_name nvarchar(256) NULL
);

-- Get result set definition of your procedure
INSERT INTO #ResultSetDefinition
EXEC sp_describe_first_result_set @ExecStr, NULL, 0;

-- Build the CREATE TABLE statement dynamically
SELECT @Qry = 'CREATE TABLE ##MyDynamicTempTable (' +
STUFF(
    (SELECT ',' + name + ' ' + system_type_name + ' NULL'
    FROM #ResultSetDefinition
    FOR XML PATH('')),
    1, 1, ''
) + ');';

-- Execute the CREATE TABLE statement
EXEC sp_executesql @Qry;

-- Insert data into the dynamically created global temp table
EXEC('INSERT INTO ##MyDynamicTempTable EXEC ' + @ProcName + ' ' + @Params);

-- Select data from the global temp table into a local temp table
SELECT *
INTO #MyTempTable FROM ##MyDynamicTempTable;

-- Display results
SELECT * FROM #MyTempTable;

-- Clean up
DROP TABLE ##MyDynamicTempTable;
DROP TABLE #MyTempTable;
DROP TABLE #ResultSetDefinition;
GO

Solution 5: Using OPENQUERY with Linked Servers

If the stored procedure resides on a different SQL Server instance, OPENQUERY can be used in conjunction with a linked server.

Prerequisites:

  1. Create a Linked Server:

    -- If a linked server isn't already configured
-- EXEC sp_addlinkedserver 'LinkedServerName', 'SQL Server';
-- EXEC sp_addlinkedsrvlogin 'LinkedServerName', 'FALSE', NULL, 'YourLogin', 'YourPassword';

  2. Enable ‘Data Access’ for the Linked Server:

    EXEC sp_serveroption 'LinkedServerName', 'DATA ACCESS', TRUE;

Code Example:

-- Execute a stored procedure on a linked server and insert results
DECLARE @ServerName SYSNAME = 'LinkedServerName'; -- Your configured linked server name
DECLARE @ProcedureCall NVARCHAR(MAX) = 'EXEC YourDatabase.dbo.YourStoredProcedure @Param1 = 1'; -- Adjust as needed

SELECT * INTO #LinkedServerResults
FROM OPENQUERY(@ServerName, @ProcedureCall);

-- Display results
SELECT * FROM #LinkedServerResults;
GO

-- Clean up
DROP TABLE #LinkedServerResults;
GO

Note: OPENQUERY does not directly support passing parameters within the OPENQUERY string itself. You might need to use dynamic SQL or construct the call carefully.

Handling Stored Procedures with Parameters

When your stored procedure requires parameters, ensure they are correctly passed in your chosen method.

  • INSERT ... EXEC: Pass parameters directly after the stored procedure name. 
    INSERT INTO #MyTempTable EXEC [dbo].[usp_MySproc] @Param1 = 10, @Param2 = 'Value';
  • OPENROWSET / OPENQUERY: Embed parameters within the command string passed to the EXEC statement. 
    -- Example with OPENROWSET and parameters
SELECT * INTO #ParamTable
FROM OPENROWSET('SQLNCLI', 'Server=localhost;Trusted_Connection=yes;',
    'EXEC YourDatabase.dbo.YourSprocWithParams 123, ''SomeText''');
  • Dynamic SQL: Construct the full EXEC statement string with parameters.

Alternative Approaches and Best Practices

  • Table-Valued Functions (TVFs): If the logic doesn’t strictly require a stored procedure, consider creating table-valued functions. They are often more flexible and easier to integrate into SELECT statements. Learn more about SQL Server Functions .
  • sp_helptext: While not for capturing results, sp_helptext can be useful for examining the definition of a stored procedure to anticipate its output schema.
  • Avoid OPENROWSET for frequent access: If you frequently query data from another server, set up a linked server .
  • Schema Definition: Manually defining the temporary table schema for INSERT ... EXEC is often the most reliable and performant method if the schema is known. Use sp_help or sys.dm_exec_describe_first_result_set_for_object to help generate the CREATE TABLE statement if needed.
  • Error Handling: Implement appropriate error handling (e.g., TRY...CATCH blocks) when executing stored procedures, especially when using dynamic SQL or external connections.
  • Performance: For large result sets, consider indexing your temporary tables if you will be performing multiple operations on them.

FAQs on SQL Stored Procedure Results into Temporary Tables

Q: What is the simplest way to insert stored procedure results into a temporary table

ANS: The most direct method is to first create a temporary table (or table variable) with a schema that matches the stored procedure’s output, and then use INSERT INTO YourTempTable EXEC YourStoredProcedure;.

Q: Can I use a stored procedure that returns multiple result sets with temporary tables

ANS: Standard INSERT INTO ... EXEC or SELECT * INTO ... FROM OPENROWSET methods typically capture only the first result set. Handling multiple result sets usually requires more complex dynamic SQL or processing each result set separately if possible within the stored procedure.

Q: What if I don't know the schema of the stored procedure's output

ANS: You can dynamically generate the CREATE TABLE statement using system views like sys.dm_exec_describe_first_result_set_for_object (SQL Server 2012+) or sp_describe_first_result_set to inspect the procedure’s output schema before creating the temporary table.

Q: Are there security implications when using OPENROWSET or OPENQUERY

ANS: Yes, OPENROWSET requires enabling ‘Ad Hoc Distributed Queries’, which can be a security risk if not managed properly. OPENQUERY relies on linked server configurations and credentials, which also need secure management.

Q: How do I pass parameters to a stored procedure when inserting into a temporary table

ANS: For INSERT ... EXEC, parameters are passed directly after the stored procedure name. For OPENROWSET or dynamic SQL, parameters are embedded within the EXEC command string.
