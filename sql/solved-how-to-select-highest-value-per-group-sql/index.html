Method 1: Leveraging DISTINCT ON (PostgreSQL Specific)

For PostgreSQL users, the DISTINCT ON clause offers a concise and often highly performant solution. This PostgreSQL extension allows you to specify a list of expressions, and for each unique combination of these expressions, only the first row (as determined by the ORDER BY clause) is returned.

Practical Implementation

Consider a customer_orders table with columns order_id, customer_identifier, and order_total_amount. To find the highest order_total_amount for each customer_identifier, along with its order_id:

SELECT DISTINCT ON (customer_identifier)
       order_id, customer_identifier, order_total_amount
FROM   customer_orders
ORDER  BY customer_identifier, order_total_amount DESC, order_id;

In this query:

  • DISTINCT ON (customer_identifier) ensures that for each unique customer, only one row is selected.
  • ORDER BY customer_identifier, order_total_amount DESC, order_id dictates which row is considered “first” within each customer group. We order by order_total_amount in descending order to pick the highest total. The order_id is included as a tie-breaker, ensuring a consistent result if multiple orders have the same maximum total (e.g., picking the one with the smallest order_id).

You can also use ordinal numbers for brevity, though it might reduce clarity:

SELECT DISTINCT ON (2) -- Refers to the second column: customer_identifier
       order_id, customer_identifier, order_total_amount
FROM   customer_orders
ORDER  BY 2, 3 DESC, 1; -- 2: customer_identifier, 3: order_total_amount DESC, 1: order_id

Handling Null Values

If order_total_amount can be NULL and you wish to prioritize non-null values, NULLS LAST can be appended to the ORDER BY clause:

SELECT DISTINCT ON (customer_identifier)
       order_id, customer_identifier, order_total_amount
FROM   customer_orders
ORDER  BY customer_identifier, order_total_amount DESC NULLS LAST, order_id;

This ensures that NULL totals are sorted after non-null totals when ordering in descending fashion.

Key Aspects of DISTINCT ON

  • PostgreSQL Extension: This feature is specific to PostgreSQL and not part of the standard SQL specification.
  • Column Relationship: The expressions in DISTINCT ON must be the leftmost expressions in the ORDER BY clause. You can freely rearrange their order within the DISTINCT ON set and add more columns for tie-breaking in ORDER BY.
  • Tie-breaking: Adding additional expressions to ORDER BY (like order_id in the example) is crucial for deterministic results when multiple rows within a group share the same “highest” value.
  • Select List Flexibility: The SELECT list is not constrained by DISTINCT ON or ORDER BY expressions. You can include any column or expression, making it a versatile tool for complex queries.
  • Version Support: DISTINCT ON has been a stable feature in PostgreSQL since version 7.1.

Indexing for Performance

For optimal performance with DISTINCT ON, a multi-column index that matches the ORDER BY clause is highly beneficial. For the example query, a suitable index would be:

CREATE INDEX idx_customer_order_value ON customer_orders (customer_identifier, order_total_amount DESC, order_id);

If your query includes NULLS LAST, the index definition should mirror that:

CREATE INDEX idx_customer_order_value_nulls ON customer_orders (customer_identifier, order_total_amount DESC NULLS LAST, order_id);

Such an index allows PostgreSQL to retrieve pre-sorted data efficiently, potentially using an Index Only Scan if the index is smaller than the underlying table. Performance is generally excellent for groups with few rows (high cardinality in customer_identifier).

Future Performance Enhancements

Excitingly, PostgreSQL 18 (Beta 1 released 2025-05-08) introduces index skip scans for B-tree indexes. This significant enhancement will make queries like DISTINCT ON even more efficient, particularly when non-referenced columns contain few unique values. This advancement may render some traditional workarounds for “loose index scans” obsolete.

Method 2: Utilizing Common Table Expressions (CTEs) and Window Functions

Window functions, specifically ROW_NUMBER(), provide a highly portable solution supported by most modern SQL databases, including PostgreSQL , SQL Server , Oracle , and MySQL 8.0+. This method assigns a sequential rank to rows within each group based on a specified ordering.

Standard ROW_NUMBER() Approach

WITH customer_summary AS (
    SELECT co.order_id,
           co.customer_identifier,
           co.order_total_amount,
           ROW_NUMBER() OVER(PARTITION BY co.customer_identifier
                                 ORDER BY co.order_total_amount DESC, co.order_id) AS row_rank
      FROM customer_orders co
)
SELECT order_id, customer_identifier, order_total_amount
FROM customer_summary
WHERE row_rank = 1;

Here:

  • PARTITION BY co.customer_identifier divides the dataset into logical groups for each customer.
  • ORDER BY co.order_total_amount DESC, co.order_id defines the sorting order within each partition, ensuring the row with the highest total (and smallest ID for ties) gets rank 1.
  • The outer query then filters to retrieve only those rows where row_rank is 1.

This pattern is widely applicable across various SQL systems.

ROW_NUMBER() in a Subquery

For PostgreSQL (and often other databases), placing the ROW_NUMBER() logic directly in a subquery can yield identical execution plans to a CTE, especially with PostgreSQL 12 and later, where CTEs are inlined by default.

SELECT ranked_orders.order_id, ranked_orders.customer_identifier, ranked_orders.order_total_amount
FROM   (
   SELECT order_id, customer_identifier, order_total_amount,
          ROW_NUMBER() OVER (PARTITION BY customer_identifier ORDER BY order_total_amount DESC, order_id) AS row_num_alias
   FROM   customer_orders
   ) AS ranked_orders
WHERE  ranked_orders.row_num_alias = 1;

SQL Server Specific ROW_NUMBER()

For SQL Server , the ROW_NUMBER() approach is very common:

SELECT *
FROM (
    SELECT ROW_NUMBER() OVER(PARTITION BY customer_identifier ORDER BY order_total_amount DESC) AS CustRank, *
    FROM Purchases
) AS ranked_purchases
WHERE CustRank = 1;

This effectively groups by customer_identifier, orders by order_total_amount in descending order, assigns a serial number (CustRank), and then selects only the first ranked entry from each group.

Method 3: Employing Joins with Aggregates

This approach uses a self-join or a join with a subquery that calculates the maximum value for each group. It is broadly supported across SQL databases, although it may require careful tie-breaking logic.

Join with Max Aggregate Subquery

This classic technique finds the maximum total for each customer in a subquery, then joins it back to the original table.

SELECT po.order_id,
       po.customer_identifier,
       po.order_total_amount
FROM   customer_orders po
JOIN   (SELECT customer_identifier,
               MAX(order_total_amount) AS max_order_value
        FROM   customer_orders
        GROUP BY customer_identifier) AS max_cust_totals
ON     max_cust_totals.customer_identifier = po.customer_identifier
AND    max_cust_totals.max_order_value = po.order_total_amount;

A crucial point here is how ties are handled. If multiple orders from the same customer have the identical max_order_value, this query would return all of them. To resolve ties deterministically (e.g., pick the smallest order_id in case of a tie), you would need to add further logic, such as a MIN(order_id) within the subquery and a corresponding join:

SELECT mo.order_id,
       mo.customer_identifier,
       mo.order_total_amount
FROM customer_orders mo
JOIN (
    SELECT sub_co.customer_identifier,
           MAX(sub_co.order_total_amount) AS max_value_for_customer
    FROM customer_orders sub_co
    GROUP BY sub_co.customer_identifier
) AS max_per_customer
ON mo.customer_identifier = max_per_customer.customer_identifier
AND mo.order_total_amount = max_per_customer.max_value_for_customer
LEFT JOIN customer_orders AS tie_breaker
ON tie_breaker.customer_identifier = mo.customer_identifier
AND tie_breaker.order_total_amount = mo.order_total_amount
AND tie_breaker.order_id < mo.order_id
WHERE tie_breaker.order_id IS NULL; -- Ensures we pick the smallest ID among tied max totals

A more refined version for any database, explicitly handling ties, might look like this:

SELECT MIN(co_alias.order_id),  -- Change to MAX if you prefer highest ID for ties
       co_alias.customer_identifier,
       co_alias.order_total_amount
FROM customer_orders co_alias
JOIN (SELECT co_sub.customer_identifier,
             MAX(co_sub.order_total_amount) AS max_value
        FROM customer_orders co_sub
        GROUP BY co_sub.customer_identifier) AS max_values_per_cust
ON max_values_per_cust.customer_identifier = co_alias.customer_identifier
AND max_values_per_cust.max_value = co_alias.order_total_amount
GROUP BY co_alias.customer_identifier, co_alias.order_total_amount;

This version uses MIN(order_id) in the outer SELECT and GROUP BY to ensure only one row is returned per customer, even if ties exist.

Self-Join for Exclusion (The “Anti-Join” Pattern)

This technique leverages a LEFT JOIN to identify and exclude rows that are not the highest within their group.

SELECT main_purchase.*
FROM customer_orders AS main_purchase
LEFT JOIN customer_orders AS higher_purchase
ON higher_purchase.customer_identifier = main_purchase.customer_identifier
AND main_purchase.order_total_amount < higher_purchase.order_total_amount
WHERE higher_purchase.order_total_amount IS NULL;

How it operates:

  1. The LEFT JOIN attempts to find a higher_purchase record for every main_purchase record where the customer is the same and the higher_purchase.order_total_amount is greater.
  2. If main_purchase is not the highest (i.e., there exists a higher_purchase with a greater total), the LEFT JOIN will find a match, and higher_purchase.order_total_amount will be non-NULL.
  3. If main_purchase is the highest (i.e., no higher_purchase record has a greater total for that customer), the LEFT JOIN will not find a match, and higher_purchase.order_total_amount will be NULL.
  4. The WHERE higher_purchase.order_total_amount IS NULL clause then filters for only those main_purchase records that had no higher counterpart, effectively selecting the rows with the maximum total for each customer.

This method is elegant because it doesn’t require explicit grouping, but like other join methods, it needs additional logic for tie-breaking if multiple records share the exact same maximum total.

Join with a MIN(id) Subquery

This approach focuses on directly identifying the id of the row with the minimum ID for each customer and then joining back.

SELECT main_order.*
FROM customer_orders AS main_order
JOIN (
    SELECT customer_identifier, MIN(order_id) AS min_order_id_in_group
    FROM customer_orders
    GROUP BY customer_identifier
) AS grouped_ids
USING (order_id); -- Note: 'USING' clause may not be supported in all DBs (e.g., SQL Server, Oracle)

This query is very fast if the table is indexed by order_id:

CREATE INDEX idx_orders_on_id ON customer_orders (order_id);

However, this method specifically retrieves the row with the minimum ID for each customer, not necessarily the one with the highest total. It would need modification to ensure it targets the highest total.

Method 4: Advanced Aggregate Functions (ARRAY_AGG, FIRST_VALUE)

PostgreSQL offers powerful aggregate functions like ARRAY_AGG and window functions like FIRST_VALUE that can solve this problem.

Using ARRAY_AGG with ORDER BY

ARRAY_AGG allows you to collect values into an array, and crucially, you can specify an ORDER BY clause within the aggregate function to control the order of elements in the array.

SELECT co_main.customer_identifier,
       (ARRAY_AGG(co_main.order_id ORDER BY co_main.order_total_amount DESC, co_main.order_id))[1] AS highest_order_id,
       MAX(co_main.order_total_amount) AS highest_total_amount
FROM   customer_orders co_main
GROUP  BY co_main.customer_identifier;

Here’s how this works:

  1. GROUP BY co_main.customer_identifier creates groups for each customer.
  2. ARRAY_AGG(co_main.order_id ORDER BY co_main.order_total_amount DESC, co_main.order_id) builds an array of order_id values for each customer. The ORDER BY ensures that the order_id corresponding to the highest order_total_amount (and smallest order_id for ties) comes first in the array.
  3. [1] accesses the first element of the generated array (PostgreSQL arrays are 1-indexed).
  4. MAX(co_main.order_total_amount) directly gets the maximum total for the group.

This method keeps your GROUP BY clause, which can be beneficial if you need to perform other aggregates (like SUM or AVG) on the groups simultaneously.

Employing FIRST_VALUE Window Function

FIRST_VALUE is a window function that returns the value of the expression from the first row in the window frame.

SELECT DISTINCT customer_identifier,
                FIRST_VALUE(ROW(order_id, order_total_amount)) OVER(PARTITION BY customer_identifier ORDER BY order_total_amount DESC, order_id) AS best_order_info
FROM customer_orders;

This query returns a composite ROW type (id, total) representing the FIRST_VALUE. You could also apply FIRST_VALUE twice to get order_id and order_total_amount separately if a composite type is not desired:

SELECT DISTINCT customer_identifier,
                FIRST_VALUE(order_id) OVER(PARTITION BY customer_identifier ORDER BY order_total_amount DESC, order_id) AS best_order_id,
                FIRST_VALUE(order_total_amount) OVER(PARTITION BY customer_identifier ORDER BY order_total_amount DESC, order_id) AS best_order_total
FROM customer_orders;

Custom Aggregate Functions (first_agg, last_agg)

While less common for this specific problem due to the power of DISTINCT ON and window functions, PostgreSQL allows defining custom aggregates.

First, define the aggregate functions:

-- Function to return the first non-NULL item
CREATE OR REPLACE FUNCTION public.first_value_agg_func ( anyelement, anyelement )
RETURNS anyelement LANGUAGE sql IMMUTABLE STRICT AS $$
        SELECT $1;
$$;

-- Aggregate for the first item
CREATE AGGREGATE public.first_item (
        sfunc    = public.first_value_agg_func,
        basetype = anyelement,
        stype    = anyelement
);

-- Function to return the last non-NULL item
CREATE OR REPLACE FUNCTION public.last_value_agg_func ( anyelement, anyelement )
RETURNS anyelement LANGUAGE sql IMMUTABLE STRICT AS $$
        SELECT $2;
$$;

-- Aggregate for the last item
CREATE AGGREGATE public.last_item (
        sfunc    = public.last_value_agg_func,
        basetype = anyelement,
        stype    = anyelement
);

Then, use them with GROUP BY and internal ORDER BY:

SELECT first_item(order_id ORDER BY order_total_amount DESC),
       customer_identifier,
       MAX(order_total_amount)
FROM customer_orders
GROUP BY customer_identifier
ORDER BY MAX(order_total_amount) DESC; -- Ordering the final results

This first_item function, with its ORDER BY clause, specifies which order_id (the one corresponding to the highest total) should be returned for each customer group. It’s also possible to use the first_last_agg extension for PostgreSQL , which can be installed from PGXN.

Method 5: Recursive CTEs with LATERAL Join

For scenarios with many rows per group (low cardinality in the grouping column), a Recursive CTE combined with a LATERAL subquery can be very efficient, especially if a separate customer lookup table exists.

Recursive CTE with LATERAL

WITH RECURSIVE customer_max_order AS (
   (  -- Parentheses are essential for the initial seed query
   SELECT order_id, customer_identifier, order_total_amount
   FROM   customer_orders
   ORDER  BY customer_identifier, order_total_amount DESC
   LIMIT  1
   )
   UNION ALL
   SELECT next_order.*
   FROM   customer_max_order AS current_max
   ,      LATERAL (
      SELECT order_id, customer_identifier, order_total_amount
      FROM   customer_orders
      WHERE  customer_identifier > current_max.customer_identifier  -- Lateral reference to the previous customer
      ORDER  BY customer_identifier, order_total_amount DESC
      LIMIT  1
      ) AS next_order
   )
SELECT order_id, customer_identifier, order_total_amount
FROM   customer_max_order
ORDER  BY customer_identifier;

This query “skips” through the sorted index, finding the first entry for each subsequent customer_identifier.

LATERAL Join with a Customer Lookup Table

If you have a dedicated customer_details table (e.g., CREATE TABLE customer_details AS SELECT DISTINCT customer_identifier, customer_name FROM customer_orders;), this method can be a top performer:

SELECT lco.order_id, lco.customer_identifier, lco.order_total_amount
FROM   customer_details AS cd_main
,      LATERAL (
   SELECT order_id, customer_identifier, order_total_amount
   FROM   customer_orders
   WHERE  customer_identifier = cd_main.customer_identifier  -- Lateral reference
   ORDER  BY order_total_amount DESC, order_id
   LIMIT  1
   ) AS lco;

This approach leverages the LATERAL join to execute a subquery for each row of the customer_details table, effectively finding the top order for each customer efficiently.

Method 6: Database-Specific Syntactic Sugar (QUALIFY, CROSS APPLY)

Some modern database systems provide specialized syntax that simplifies the “greatest N per group” problem.

Snowflake/Teradata QUALIFY Clause

For databases like Snowflake and Teradata , the QUALIFY clause offers a clean way to filter results from window functions, similar to HAVING for aggregate functions.

SELECT order_id, customer_identifier, order_total_amount
FROM customer_orders
QUALIFY ROW_NUMBER() OVER(PARTITION BY customer_identifier ORDER BY order_total_amount DESC, order_id) = 1;

This is very concise and readable.

SQL Server CROSS APPLY

SQL Server provides CROSS APPLY (and OUTER APPLY) which behaves like a LATERAL join, executing a subquery for each row of the left table. This can be highly efficient, especially when combined with a list of group identifiers.

WITH customer_ids AS ( -- Sample list of customer IDs to process
    SELECT cust_id FROM (VALUES (101),(105),(120)) AS c(cust_id)
),
source_data AS (
    SELECT * FROM Purchases -- Filter your main table if needed
)
SELECT top_order.*
FROM customer_ids
CROSS APPLY (
    SELECT TOP(1) *
    FROM source_data
    WHERE customer_identifier = customer_ids.cust_id
    ORDER BY order_total_amount DESC, order_id
) AS top_order;

This pattern excels at processing a specific set of groups by efficiently fetching the top record for each using the TOP(1) clause within the APPLY operator. A clustered index on the joining columns further boosts its speed.

Performance Analysis Across Methods

Extensive benchmarking reveals that the optimal method often depends on factors like the database system, data distribution (number of rows per group), and available indexes.

Testing Methodology: Benchmarks were conducted on a customer_orders table with varying customer_identifier distinct counts and total row counts. A typical setup involved:

CREATE TABLE customer_orders (
  order_id          SERIAL PRIMARY KEY,
  customer_identifier INT,
  order_total_amount INT,
  order_details_text TEXT
);

INSERT INTO customer_orders (customer_identifier, order_total_amount, order_details_text)
SELECT (random() * 10000)::INT AS customer_identifier,
       (random() * random() * 100000)::INT AS order_total_amount,
       'details: ' || repeat('x', (random()^2 * random() * random() * 500)::INT)
FROM generate_series(1,200000) AS s;

-- Add primary key and potentially some dead rows to simulate real-world scenarios
ALTER TABLE customer_orders ADD CONSTRAINT pk_customer_orders PRIMARY KEY (order_id);
DELETE FROM customer_orders WHERE random() > 0.9;
INSERT INTO customer_orders (customer_identifier, order_total_amount, order_details_text)
SELECT (random() * 10000)::INT, (random() * random() * 100000)::INT, 'more details: ' || repeat('x', (random()^2 * random() * random() * 500)::INT)
FROM generate_series(1,20000) AS s;

CREATE INDEX idx_customer_order_value ON customer_orders (customer_identifier, order_total_amount DESC, order_id);
VACUUM ANALYZE customer_orders;

Key Performance Observations:

  • DISTINCT ON (PostgreSQL): Consistently performs very well, especially for data with few rows per customer_identifier (high cardinality in customer_identifier). It effectively utilizes matching indexes. Even with many rows per group, its performance is decent.
  • LATERAL Join (with separate customer table): This method often emerges as the overall winner, particularly when customer_identifier has high cardinality (few rows per customer). It efficiently fetches data for each customer individually.
  • Recursive CTE with LATERAL: Performs exceptionally well for scenarios with many rows per customer_identifier (low cardinality in customer_identifier), emulating an index skip scan.
  • Window Functions (ROW_NUMBER(), FIRST_VALUE): While highly compatible and readable, ROW_NUMBER() frequently shows mediocre performance compared to DISTINCT ON or LATERAL joins, especially in older PostgreSQL versions. Improvements in PostgreSQL 12+ (due to CTE inlining) have made CTE and subquery versions of ROW_NUMBER() perform similarly. Their performance does not scale terribly but is not optimal for most cases.
  • Join with MAX Subquery: Performance varies. While a common pattern, it often requires extra tie-breaking logic and may not be as optimized by the query planner as DISTINCT ON or LATERAL joins in PostgreSQL .

Summary of Benchmark Results (General Trends):

  • Few rows per group (High customer_identifier cardinality): DISTINCT ON and LATERAL joins (especially with a separate lookup table) are often the fastest.
  • Many rows per group (Low customer_identifier cardinality): Recursive CTEs with LATERAL can be superior. DISTINCT ON still performs reasonably.
  • ROW_NUMBER() based solutions: Provide broad compatibility but generally don’t lead the performance charts in PostgreSQL .

To gauge the exact performance for your specific workload and data distribution, EXPLAIN ANALYZE (or equivalent in your database) is indispensable. Pay attention to work_mem settings in PostgreSQL to ensure sorting operations occur in RAM rather than spilling to disk.

Other Approaches

Correlated Subquery with MAX

This method involves a subquery that depends on the outer query’s row, checking if the current order_total_amount is the MAX for that customer.

SELECT co_outer.*
FROM customer_orders co_outer
WHERE co_outer.order_total_amount = (
    SELECT MAX(co_inner.order_total_amount)
    FROM customer_orders co_inner
    WHERE co_inner.customer_identifier = co_outer.customer_identifier
);

While functional, correlated subqueries can be inefficient, as the inner query is executed for each row in the outer query. Performance can degrade rapidly with larger datasets.

Grouping by All Selected Columns (A Common Misconception)

A query like SELECT id, customer, MAX(total) FROM purchases GROUP BY id, customer ORDER BY total DESC; does not solve the “greatest N per group” problem where you want one row per customer with their highest total. If id is a primary key or unique identifier, grouping by id and customer will simply return every distinct (id, customer) pair, effectively showing all individual purchase records. The MAX(total) in this context would just be the total for that specific (id, customer) combination. This query does not achieve the goal of selecting the highest total per customer.

Using SUM with FILTER (Advanced Window Functions)

For more complex scenarios where you need to perform other aggregates while picking specific rows, a combination of window functions and FILTER can be used.

WITH partitioned_data AS (
    SELECT
        agreement_id,
        order_id,
        suma, -- Assuming 'suma' is a relevant numeric column like 'total'
        ROW_NUMBER() OVER (PARTITION BY agreement_id, order_id) AS row_num_per_order,
        (SUM(suma) OVER (PARTITION BY agreement_id, order_id))::NUMERIC(10, 2) AS order_sum_calc
    FROM some_table
)
SELECT
    agreement_id,
    order_id,
    suma,
    row_num_per_order,
    order_sum_calc,
    SUM(order_sum_calc) FILTER (WHERE row_num_per_order = 1) OVER (PARTITION BY agreement_id) AS total_agreement_sum
FROM partitioned_data;

This advanced pattern focuses on summing values across a partition but only considering the ‘first’ row within a sub-partition, demonstrating the flexibility of window functions with FILTER.

FAQs on Solved How to Select the Row with the Highest Value Per Group in SQL

Q: What is the greatest N per group problem

ANS: The greatest N per group problem involves retrieving the top N rows (often N=1 for the highest value) for each distinct group within a dataset. For example, finding the student with the highest score in each class.

Q: Which SQL method is best for finding the highest value per group

ANS: The best SQL method depends on your database system and data distribution. For PostgreSQL, DISTINCT ON is highly efficient. Window functions like ROW_NUMBER() are very portable across databases like SQL Server Oracle and MySQL. For very large groups, Recursive CTEs with LATERAL joins or specialized syntax like Snowflake’s QUALIFY can be optimal.

Q: How do I handle ties when selecting the highest value per group

ANS: To handle ties (when multiple rows have the same highest value within a group), you need to include additional tie-breaking criteria in your ORDER BY clause. For instance, you might order by a primary key or timestamp to ensure a consistent single result.

Q: Can I use ARRAY AGG to find the highest value per group

ANS: Yes, in PostgreSQL you can use ARRAY_AGG combined with an ORDER BY clause inside the aggregate function. This allows you to create an array of values sorted as desired, from which you can then select the first element to get the highest value.

Q: Is the ROW NUMBER window function supported in all databases

ANS: The ROW_NUMBER() window function is widely supported in modern relational database management systems, including PostgreSQL SQL Server Oracle MySQL 80 and many others. It is a highly portable solution for ranking rows within partitions.

FROM   purchases
ORDER  BY customer, total DESC, id;

       id, customer, total
FROM   purchases
