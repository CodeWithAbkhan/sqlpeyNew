“PostgreSQL Dynamic SQL Functions: Returning Variable Columns”

When constructing PostgreSQL functions that need to return results where the number or type of columns isn’t fixed at function creation, you’re stepping into the realm of dynamic SQL. This often arises when the exact structure of the data to be returned depends on runtime conditions, such as specific input parameters or the contents of other tables.

The core challenge lies in PostgreSQL’s requirement for a function to explicitly declare its return type. For dynamic scenarios, this presents a hurdle because the columns might vary in name, count, or data type. Let’s delve into effective strategies for handling these situations.

The RETURNS record Approach and Its Limitations

A fundamental way to address returning undefined types is by using RETURNS SETOF record.

CREATE FUNCTION data_of(input_id integer)
  RETURNS SETOF record AS $$
-- Function body
$$ LANGUAGE plpgsql;

However, this method comes with a significant caveat: you must provide a column definition list with every call to the function.

SELECT * FROM data_of(17)
AS foo (column_name1 integer, column_name2 text, column_name3 real);

This becomes impractical when the column structure itself is unknown beforehand. For such cases, PostgreSQL offers more structured data types like json, jsonb, hstore, or xml, which can store semi-structured data effectively. For more detailed exploration of storing tabular data, see How to store a data table in database? .

However, if the goal is to return individual, correctly typed, and named columns as much as possible, alternative methods are more suitable.

Solution 1: Dynamic SQL with Explicit RETURNS TABLE and Type Casting

This approach involves defining a RETURNS TABLE clause with generic column names and casting all dynamic columns to text. This provides a well-defined structure while accommodating varying column types.

CREATE OR REPLACE FUNCTION data_of_typed(_id integer)
  RETURNS TABLE (datahora timestamp, col2 text, col3 text)
  LANGUAGE plpgsql AS
$func$
DECLARE
   _sensors text := 'sensor_reading1::text, sensor_reading2::text'; -- Cast each column to text
   _table_name text := 'sensor_data';
BEGIN
   RETURN QUERY EXECUTE format('
      SELECT datahora, %s
      FROM   %I
      WHERE  id = $1
      ORDER  BY datahora'
    , _sensors, _table_name)
   USING _id;
END
$func$;

Key Points:

  • RETURNS TABLE: Defines a fixed structure for the output.
  • Type Casting: Columns are cast to text to handle varying data types.
  • RETURN QUERY EXECUTE: The preferred method for executing dynamic SQL and returning its results.
  • format() function: Simplifies string construction for dynamic SQL, especially with %I for identifiers, which automatically handles quoting and prevents SQL injection. For more on handling SQL syntax and injection, explore SQL Injection Prevention .
  • quote_ident(): Essential for safely including table and column names in dynamic SQL, preventing SQL injection vulnerabilities.

Handling Variable Number of Columns of the Same Type:

If you have a scenario where the number of columns varies but they all share the same data type (e.g., double precision or float8), you can leverage PostgreSQL’s ARRAY type. This allows you to return an array of values and an accompanying array of column names.

CREATE OR REPLACE FUNCTION data_of_array(_id integer)
  RETURNS TABLE (datahora timestamp, names text[], values float8[])
  LANGUAGE plpgsql AS
$func$
DECLARE
   _sensor_columns text := 'col1, col2, col3';  -- Plain list of column names
   _table_name text := 'measurement_log';
BEGIN
   RETURN QUERY EXECUTE format('
      SELECT datahora
           , string_to_array($1)  -- AS names
           , ARRAY[%s]            -- AS values
      FROM   %s
      WHERE  id = $2
      ORDER  BY datahora'
    , _sensor_columns, _table_name)
   USING _sensor_columns, _id;
END
$func$;

Solution 2: Leveraging anyelement for Complete Table Structures

For scenarios where you need to return all columns of a table whose structure is determined at runtime, the anyelement polymorphic type is a powerful solution.

CREATE OR REPLACE FUNCTION data_of_any(_tbl_type anyelement, _id int)
  RETURNS SETOF anyelement
  LANGUAGE plpgsql AS
$func$
BEGIN
   RETURN QUERY EXECUTE format('
      SELECT *
      FROM   %s  -- pg_typeof returns regtype, quoted automatically
      WHERE  id = $1
      ORDER  BY datahora'
    , pg_typeof(_tbl_type))
   USING _id;
END
$func$;

Calling this function requires specifying a table type:

SELECT * FROM data_of_any(NULL::your_table_name, 17);

Replace your_table_name with an actual table name. The anyelement pseudo-type acts as a placeholder that adopts the data type provided at runtime. pg_typeof() is used to dynamically get the table’s type name, which is automatically quoted and schema-qualified, providing robust protection against SQL injection. This method is also effective for temporary tables.

Solution 3: Using refcursor for Flexible Result Sets

A refcursor (reference cursor) allows a function to return a pointer to a result set that can be iterated over by the calling application. This is particularly useful when the client application expects a cursor-like behavior.

CREATE OR REPLACE FUNCTION data_of_cursor(input_id integer)
  RETURNS refcursor AS
$BODY$
DECLARE
      -- Declaring variables
      result_cursor refcursor;
      _sensors text := 'column_a, column_b'; -- Ensure these are valid column names
      _table_name text := 'dynamic_data';    -- Ensure this is a valid table name
BEGIN
      -- Ensure `_sensors`, `_table_name`, and `$1` variable have valid values
      OPEN result_cursor FOR format('SELECT datahora, %s FROM %s WHERE id = $1 ORDER BY datahora', _sensors, _table_name)
      USING input_id;
      RETURN result_cursor;
END;
$BODY$
LANGUAGE 'plpgsql' VOLATILE;

Example Usage with Cursors:

The following example demonstrates how to create and use a function that returns a cursor variable, allowing for dynamic selection of columns.

-- Setup a sample table
begin;

create table test_data (id serial, data1 text, data2 text);

insert into test_data(data1, data2) values('one', 'un');
insert into test_data(data1, data2) values('two', 'deux');
insert into test_data(data1, data2) values('three', 'trois');

-- Function to generate a query and return a refcursor
create function generate_dynamic_query(query_name refcursor, columns text[])
returns refcursor
as $$
begin
  open query_name for execute
    'select id, ' || array_to_string(columns, ',') || ' from test_data order by id';
  return query_name;
end;
$$ language plpgsql;

-- Fetching data with different column sets
select generate_dynamic_query('english_data', array['data1']);
fetch all in english_data;

select generate_dynamic_query('french_data', array['data2']);
fetch all in french_data;
move absolute 0 from french_data; -- Rewind the cursor
fetch all in french_data;

select generate_dynamic_query('all_data', array['data1','data2']);
fetch all in all_data;

-- Example of a query that would fail if a column doesn't exist
-- select generate_dynamic_query('broken_query', array['data3']);

rollback;

This provides flexibility, but the calling application needs to be aware of how to handle and fetch data from refcursor types. For general PostgreSQL interaction, consider the benefits of libraries like psycopg2 for Python, which you can learn more about at What is Python? and What is Pandas? .

Solution 4: Defining a Fixed Return Table with RETURNS TABLE

In some cases, even with dynamic data, you might have a predictable set of columns that can be defined directly within the function’s RETURNS TABLE clause. This is the simplest and often most efficient approach if the column names and types are known, even if the data itself varies.

Consider a function to retrieve user roles:

CREATE OR REPLACE FUNCTION func_get_all_users_roles()
  -- Define the return type of the result set as a table
  -- These data types must match the ones in the source tables
  RETURNS TABLE (
                 user_id           bigint
               , user_email        varchar(200)
               , user_password     varchar(200)
               , assigned_role     varchar(100)) AS
$func$
BEGIN
   RETURN QUERY
   -- Start the select clause
   SELECT u.id, u.email, u.password, r.name as assigned_role
   FROM user_roles ur
   LEFT JOIN roles r ON (r.guid = ur.roles_guid)
   LEFT JOIN users u ON (u.guid = ur.users_guid)
   -- Stop the select clause
;
END
$func$  LANGUAGE plpgsql;

Executing this function:

You can execute this function directly from psql or any SQL client.

# Create the function
psql -d your_database_name -c "CREATE OR REPLACE FUNCTION func_get_all_users_roles() RETURNS TABLE(...) AS $$ ... $$ LANGUAGE plpgsql;"

# Call the function
psql -d your_database_name -c "select * from func_get_all_users_roles()"

This method provides a static return signature, making it easier for calling applications to work with the function’s output. For a foundational understanding of SQL, What is SQL? is a great starting point.

FAQs on PostgreSQL Dynamic SQL Functions

Q: How can I return columns with unknown names or types from a PostgreSQL function

ANS: You can use RETURNS SETOF record and specify the column list during the SELECT call, or cast all dynamic columns to text within a RETURNS TABLE definition. Alternatively, anyelement can return all columns of a table dynamically. For more structured but flexible data, consider json or jsonb.

Q: Is there a way to dynamically select columns in PostgreSQL

ANS: Yes, by using dynamic SQL with the EXECUTE statement in PL/pgSQL. You can construct the SELECT statement with variable column lists and then use RETURN QUERY EXECUTE or OPEN FOR EXECUTE with a refcursor.

Q: What is the risk of SQL injection when using dynamic SQL in PostgreSQL

ANS: Dynamic SQL is inherently susceptible to SQL injection. Always use functions like quote_ident() for table and column names and quote_literal() for string values, or preferably use the format() function with %I and %L specifiers to safely embed identifiers and literals. For more on this, see SQL Injection Prevention .

Q: When should I use `RETURNS TABLE` versus `RETURNS SETOF record`

ANS: Use RETURNS TABLE when you can define a fixed structure for your output, even if some data needs casting. It’s generally more robust and easier for calling applications. Use RETURNS SETOF record only when the column structure is truly unknown and must be defined entirely by the caller.

Q: Can I return an array of values for dynamic columns in PostgreSQL

ANS: Yes, if the dynamic columns share the same data type, you can aggregate them into an ARRAY and return that array along with an array of their corresponding names within a RETURNS TABLE definition.

Q: What is `anyelement` in PostgreSQL functions

ANS: anyelement is a polymorphic type in PostgreSQL that allows a function to accept any non-array data type as an input and return a value of that same type. This is powerful for functions that need to operate on data of unknown but consistent types, such as returning all columns of a table.

Q: How do I handle `refcursor` results in my application

ANS: Handling refcursor results typically involves fetching data from the cursor within your application code using specific cursor operations provided by your database driver or ORM. For Python, libraries like psycopg2 provide methods to manage and retrieve data from cursors.
