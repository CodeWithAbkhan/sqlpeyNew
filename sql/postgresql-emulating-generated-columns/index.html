“PostgreSQL Emulating Generated Columns in Older Versions”

How does one implement functionality similar to generated columns (or computed columns) in PostgreSQL, especially when operating on versions older than 12, or explore alternatives for newer releases? This feature, where a column’s value is derived automatically from other columns in the same row, is present in standard SQL implementations like DB2, MySQL, and Oracle.

PostgreSQL 12 and Newer: Native STORED Generated Columns

For PostgreSQL version 12 and later, native support for STORED generated columns is available, mirroring SQL standards. These values are computed upon data modification (INSERT/UPDATE) and physically stored on disk.

A straightforward implementation appears like this:

CREATE TABLE inventory_item (
  base_quantity    INT,
  inventory_count  INT,
  total_value      BIGINT GENERATED ALWAYS AS (base_quantity * inventory_count) STORED
);

It is noted that VIRTUAL generated columns (computed only during read) were not present in Postgres 16 but are slated for future iterations. For users on PostgreSQL 18 or higher, native VIRTUAL generated columns are introduced as the default, calculating values just-in-time during query execution, with stored columns also supported and eligible for logical replication.

Pre-PostgreSQL 12 Solutions: Emulating Virtual Behavior

Prior to Postgres 12, explicit support for generated columns was absent. Several techniques can emulate this behavior, particularly the VIRTUAL style:

1. Using Functions with Attribute Notation (Syntax Oddity)

You can mimic a virtual computed column using a function called with attribute notation (table_alias.column). This relies on a historical quirk in PostgreSQL syntax that aligns well with virtual computation needs.

If you have a formula you wish to represent:

-- Define the computed expression as a function (must be IMMUTABLE for indexing)
CREATE FUNCTION calculate_derived_field(t specific_table) RETURNS numeric AS $$
    SELECT t.col_a * t.col_b / 2.0;
$$ LANGUAGE sql IMMUTABLE;

-- Emulation in a query (though not strictly a column definition)
SELECT 
    t.col_a, 
    t.col_b, 
    calculate_derived_field(t) AS computed_result 
FROM specific_table t;

Limitation: This expression is not included when using SELECT * FROM tbl; it requires explicit listing in every query.

2. Expression Indexes Paired with Views

A performant way to accelerate queries based on a computed value is through an expression index. If the calculation is repeatable and deterministic (e.g., hashing a string), an index on that expression can be beneficial.

For example, optimizing lookups based on an MD5 hash:

CREATE TABLE user_data (
    user_id SERIAL PRIMARY KEY,
    secret_key TEXT NOT NULL
);

-- Create an index on the computed expression
CREATE INDEX user_secret_key_hash_idx ON user_data (MD5(secret_key));

-- Queries using the expression will now leverage the index:
SELECT user_id FROM user_data GROUP BY MD5(secret_key);

To make this computed value appear seamlessly as a column without manual repetition in queries, couple the index with a VIEW:

CREATE VIEW user_data_augmented AS 
   SELECT 
       *, 
       MD5(secret_key) AS secret_key_hash 
   FROM user_data;

The view does not duplicate storage, offering performance gains via the underlying index while simplifying access through the augmented column name. Be aware that query planner decisions regarding index usage can sometimes be data-dependent, as noted in some observations regarding competing indices.

3. Implementing STORED Behavior via Triggers

For pre-12 versions, persisting the computed value (like a STORED column) is achievable using BEFORE INSERT OR UPDATE triggers. The trigger function modifies the incoming row (NEW record) before it is written to the table.

Consider calculating two as twice the value of one:

CREATE TABLE calculation_source (
    one SERIAL,
    two INT NOT NULL
);

CREATE OR REPLACE FUNCTION compute_two_value_trg()
RETURNS trigger
LANGUAGE plpgsql
SECURITY DEFINER
AS $$
BEGIN
    -- Calculate the value and assign it to the 'two' column of the incoming row
    NEW.two = NEW.one * 2;

    RETURN NEW;
END;
$$;

CREATE TRIGGER enforce_two_computation
BEFORE INSERT OR UPDATE
ON calculation_source
FOR EACH ROW
EXECUTE PROCEDURE compute_two_value_trg();

When data is inserted or updated in calculation_source.one, the two column is automatically populated by the trigger logic.

4. Alternative Structures: Views and Materialized Views

A simple VIEW can present the calculated result without altering the base table structure. If frequent reads necessitate pre-calculation and durability, Materialized Views (available since Postgres 9.3) serve a similar purpose to STORED columns, though they require manual refreshing or scheduled maintenance.

If you need the calculation to occur only once upon table creation based on existing data, a simple UPDATE statement can achieve this before using the column permanently:

-- Initial setup:
CREATE TABLE table_data (
    col_a INT,
    col_b INT,
    derived_product BIGINT  -- Initially empty or NULL
);

-- One-time calculation execution:
UPDATE table_data
SET derived_product = col_a * col_b;

Further Examination of Related Concepts

What if the objective is not derived calculation but data validation on input? A CHECK constraint can enforce specific values, though it does not compute dynamic results:

CREATE TABLE controlled_input (
    identifier_code INTEGER DEFAULT 0 NOT NULL CHECK (identifier_code = 0)
);

For environments where standard SQL syntax for generated columns is not supported or behaves differently (like some derived database services), relying on database-specific emulation techniques such as triggers or views remains essential for maintaining data integrity and derivation logic. FAQs on PostgreSQL Emulating Generated Columns

Q: What version introduced native generated columns in Postgres

ANS: PostgreSQL 12 is the version that introduced native STORED generated columns.

Q: Are virtual generated columns supported in Postgres 16

ANS: Virtual generated columns were not implemented in PostgreSQL 16 but are expected in later versions, with Postgres 18 supporting them natively.

Q: Can expression indexes be used without a view

ANS: Yes, expression indexes can be used directly in queries to boost performance on computed expressions, but users must then know the exact expression syntax to query against.

Q: Do triggers affect SELECT *

ANS: Triggers calculate values before the write operation occurs, effectively storing the result, making the calculated value visible when using SELECT *.
