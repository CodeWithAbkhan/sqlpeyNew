“Efficient PostgreSQL Strategies for Selecting Random Rows from Large Tables”

Selecting a truly random sample of rows from an indexed, high-volume PostgreSQL table requires careful consideration to avoid performance degradation associated with full table scans or sorting operations. When dealing with large datasets, methods relying on ORDER BY random() become prohibitively slow.

What are the most effective, high-speed approaches to obtain a specified number of genuinely random rows from a very large table, particularly when a numeric ID column with minimal gaps is available?

Approach 1: Leveraging Indexed IDs with Generated Series (Fastest for Gappy IDs)

This technique is optimized for tables having an integer Primary Key (id) that is indexed and possesses only a few gaps. The core idea is to generate a slightly larger set of random ID candidates, leveraging the index for swift lookups, and then trimming the results.

Initial Statistics Gathering

Before selecting random IDs, obtaining quick estimates for the ID range is helpful. While COUNT(*) on huge tables is expensive, you can get a fast estimate:

-- Estimate row count (ct) based on statistics, very fast for large tables
SELECT (reltuples / relpages * (pg_relation_size(oid) / 8192))::bigint AS ct
FROM   pg_class
WHERE  oid = 'big'::regclass;  -- Replace 'big' with your actual table name

You might also quickly query min/max IDs:

SELECT min(id) AS min_id, max(id) AS max_id
FROM big;

Generating Random IDs via generate_series

To account for a few missing IDs (gaps), we generate slightly more random ID candidates than the target limit (e.g., 1100 attempts for a 1000-row limit).

Detailed Implementation:

This method uses a Common Table Expression (CTE) to generate candidates, group them to remove duplicates generated by chance, join against the indexed table, and finally limit the output.

WITH params AS (
   -- Set a reasonable minimum ID and calculate the span needed for random generation
   SELECT 1       AS min_id,
        5100000 AS id_span -- (max_id - min_id + buffer)
    )
SELECT r.*
FROM  (
   -- Generate 1100 candidates, trim duplicates via GROUP BY 1
   SELECT p.min_id + trunc(random() * p.id_span)::integer AS id
   FROM   params p
        , generate_series(1, 1100) g
   GROUP  BY 1
) r
JOIN   big USING (id) -- Fast index lookup
LIMIT  1000;

Simplified Query (Removing CTE):

If you prefer brevity over the named parameters, this is equivalent:

SELECT *
FROM  (
   -- Generate candidates, use DISTINCT to remove chance duplicates
   SELECT DISTINCT 1 + trunc(random() * 5100000)::integer AS id
   FROM   generate_series(1, 1100) g
   ) r
JOIN   big USING (id)
LIMIT  1000;

Refinement Using Recursive CTE (rCTE) for Guaranteed Limit Fulfillment

If gaps are significant or you need a stronger guarantee that the final LIMIT will be met, an rCTE can iteratively probe for missing IDs.

WITH RECURSIVE random_pick AS (
   SELECT *
   FROM  (
      -- Initial probe (e.g., 1030 attempts for 1000 desired)
      SELECT 1 + trunc(random() * 5100000)::int AS id
      FROM   generate_series(1, 1030)
      LIMIT  1030
      ) r
   JOIN   big b USING (id) -- Eliminate IDs that do not exist

   UNION
   -- Recursive step: find more IDs if initial probe was insufficient
   SELECT b.*
   FROM  (
      SELECT 1 + trunc(random() * 5100000)::int AS id
      FROM   random_pick r -- Recursively draw from previous successful picks
      LIMIT  999           -- Aim for slightly less than 1000 total
      ) r
   JOIN   big b USING (id)
   )
TABLE  random_pick
LIMIT  1000; -- Final limit application

Encapsulation in a PL/pgSQL Function

For reusability across different parameters:

CREATE OR REPLACE FUNCTION f_random_sample_by_id(_limit int = 1000, _gaps real = 1.03)
  RETURNS SETOF big -- Assuming 'big' is the return type structure
  LANGUAGE plpgsql VOLATILE ROWS 1000 AS
$func$
DECLARE
   _surplus  int := _limit * _gaps;
   _estimate int := (
      SELECT (reltuples / relpages * (pg_relation_size(oid) / 8192))::bigint
      FROM   pg_class
      WHERE  oid = 'big'::regclass);
BEGIN
   RETURN QUERY
   WITH RECURSIVE random_pick AS (
      SELECT *
      FROM  (
         SELECT 1 + trunc(random() * _estimate)::int AS id
         FROM   generate_series(1, _surplus) g
         LIMIT  _surplus
         ) r (id)
      JOIN   big USING (id)

      UNION
      SELECT *
      FROM  (
         SELECT 1 + trunc(random() * _estimate)::int AS id
         FROM   random_pick
         LIMIT  _limit
         ) r (id)
      JOIN   big USING (id)
   )
   TABLE  random_pick
   LIMIT  _limit;
END
$func$;

-- Example Call:
SELECT * FROM f_random_sample_by_id(500, 1.05);

Making the Function Generic:

To apply this logic to any table structure dynamically, use anyelement and EXECUTE with format():

CREATE OR REPLACE FUNCTION f_generic_random_sample(_tbl_type anyelement
                                         , _id text = 'id'
                                         , _limit int = 1000
                                         , _gaps real = 1.03)
  RETURNS SETOF anyelement
  LANGUAGE plpgsql VOLATILE ROWS 1000 AS
$func$
DECLARE
   _tbl text := pg_typeof(_tbl_type)::text;
   _estimate int := (SELECT (reltuples / relpages
                          * (pg_relation_size(oid) / 8192))::bigint
                     FROM   pg_class
                     WHERE  oid = _tbl::regclass);
BEGIN
   RETURN QUERY EXECUTE format(
   $$
   WITH RECURSIVE random_pick AS (
      SELECT *
      FROM  (
         SELECT 1 + trunc(random() * $1)::int
         FROM   generate_series(1, $2) g
         LIMIT  $2
         ) r(%2$I)
      JOIN   %1$s USING (%2$I)

      UNION
      SELECT *
      FROM  (
         SELECT 1 + trunc(random() * $1)::int
         FROM   random_pick
         LIMIT  $3
         ) r(%2$I)
      JOIN   %1$s USING (%2$I)
   )
   TABLE  random_pick
   LIMIT  $3;
   $$
 , _tbl, _id
   )
   USING _estimate
       , (_limit * _gaps)::int
       , _limit
   ;
END
$func$;

-- Call using a null placeholder of the table type:
SELECT * FROM f_generic_random_sample(null::big);

This dynamic approach mitigates SQL injection risks through the use of format() specifiers like %1$s and %2$I.

Approach 2: Utilizing TABLESAMPLE (PostgreSQL 9.5+)

For simple, non-perfectly random samples, PostgreSQL versions 9.5 and newer offer the TABLESAMPLE clause, which performs block-level sampling and is significantly faster than row-by-row processing.

Sampling by Percentage:

This retrieves approximately 5% of rows; the exact count varies.

SELECT * FROM big TABLESAMPLE SYSTEM (5);

To estimate roughly 1000 rows from a table spanning 5,100,000 ID space:

SELECT * FROM big TABLESAMPLE SYSTEM ((1000 * 100) / 5100000.0);

Sampling by Exact Row Count (Requires Extension):

If you need exactly $N$ rows, install the tsm_system_rows extension first:

CREATE EXTENSION tsm_system_rows;

Then use the dedicated syntax (still block-level sampling, not perfectly random):

SELECT * FROM big TABLESAMPLE SYSTEM_ROWS(1000);

Approach 3: Pre-calculated Random Index (Materialized View)

If you require lightning-fast, repeated access to a static set of random rows, periodically rebuild a set:

  1. Create a materialized view that pre-calculates a full random ordering: 
    CREATE MATERIALIZED VIEW random_picks_cache AS
  SELECT * FROM big ORDER BY random();
  2. Accessing data is instantaneous: 
    SELECT * FROM random_picks_cache LIMIT 1000;
  3. For consumption without duplicates, use an UPDATE...RETURNING pattern on a separate tracking table, referencing this view for the random order, as detailed in Solution 11.

--in between nightly tasks, so to solve the problem of a missing row, 
--you try again until you succeed.  In the event the big_data_mapper 
--is broken, it tries 25 times then gives up and returns -1. 
CREATE or replace FUNCTION get_random_big_data_id()  
RETURNS int language plpgsql AS $$ 
declare  
    response int; 
BEGIN
    --Loop is required because big_data_mapper could be old
    --Keep rolling the dice until you find one that hits.
    for counter in 1..25 loop
        SELECT big_data_id 
        FROM big_data_mapper OFFSET floor(random() * ( 
            select max(id) biggest_value from big_data_mapper 
            )
        ) LIMIT 1 into response;
        if response is not null then
            return response;
        end if;
    end loop;
    return -1;
END;  
$$;

When comparing performance via EXPLAIN:

EXPLAIN select * from big where random() < 0.01;     -- Shows sequential scan
EXPLAIN select * from big order by random() limit 1000; -- Shows Sort operation on full table

The best choice hinges on index availability, gap distribution, and randomness requirements. For indexed, gappy data, Approach 1 (ID generation) is superior. For general tables where minor non-uniformity is acceptable, TABLESAMPLE (Approach 2) is the simplest fast path.

EXPLAIN select * from table where random() &lt; 0.01;
EXPLAIN select * from table order by random() limit 1000;
select * from table where random() &lt; 0.01 limit 1000;

FAQs on Efficient PostgreSQL Random Selection

Q: Why is ORDER BY random() slow on large tables

ANS: Because PostgreSQL must calculate a random value for every row and then sort the entire dataset based on those generated values, which is an $O(N \log N)$ operation requiring significant disk I/O for sorting large results.

Q: Can I use OFFSET floor(random() * COUNT(*)) LIMIT 1

ANS: While conceptually simple, this method is often not faster than ORDER BY random() because calculating the count takes time, and the OFFSET might still require scanning the initial portion of the table.

Q: What is the primary benefit of using generated IDs for random sampling

ANS: When the ID column is indexed, generating random IDs within the known range allows PostgreSQL to use index lookups rather than full table scans, making row retrieval extremely fast, approaching $O(1)$ per retrieved row after the initial setup.

Q: Is TABLESAMPLE SYSTEM perfectly random

ANS: No, TABLESAMPLE SYSTEM performs block-level sampling. This means that rows located near each other on disk (clustering effects) have a higher chance of being selected together, making the sample less uniformly random than ID-based generation.
