“SQL Merge Statement Alternatives: Efficient Upsert Strategies”

When dealing with relational databases, the requirement to either insert a new record or update an existing one based on a condition (commonly termed an “upsert”) is frequent. While the SQL MERGE statement offers a unified approach, several scenarios and performance considerations suggest alternative patterns. This deep dive explores utilizing MERGE with the DUAL table, client-side execution, exception-based logic, row count checks, and strategies for managing concurrency risks inherent in these operations.

Utilizing Oracle’s MERGE Statement with DUAL

The MERGE command is designed to combine INSERT and UPDATE logic into a single atomic SQL statement. A common pattern, particularly within PL/SQL procedures, involves leveraging the DUAL pseudo-table to drive the operation when the source of the data is a single value or variable.

Consider the following PL/SQL procedure example designed to increment a counter (B) for an existing key (A) or insert a new entry if the key is absent:

CREATE OR REPLACE PROCEDURE upsert_counter(p_key_value IN NUMBER)
AS
BEGIN
    MERGE INTO merge_test m
    USING DUAL
    ON (m.a = p_key_value)
    WHEN NOT MATCHED THEN
        INSERT (a, b) VALUES (p_key_value, 1)
    WHEN MATCHED THEN
        UPDATE SET m.b = m.b + 1;
END upsert_counter;
/

-- Setup and Execution Example
DROP TABLE merge_test;
CREATE TABLE merge_test(a NUMBER, b NUMBER);

CALL upsert_counter(10);
CALL upsert_counter(10);
CALL upsert_counter(20);

SELECT a, b FROM merge_test;
-- Expected Output:
-- A | B
-- --|--
-- 10| 2
-- 20| 1

This PL/SQL approach is concise for database-side operations. However, as noted in some client contexts (like C# application logic), executing this directly might be slower than separated UPDATE and INSERT commands, depending on the application’s architecture and network latency.

Client-Side MERGE Execution

The MERGE statement can also be issued directly from a client application layer, such as C# code interacting with Oracle:

MERGE INTO Employee e
USING DUAL
ON (e.id = 2097153)
WHEN MATCHED THEN
    UPDATE SET e.last = 'smith', e.name = 'john'
WHEN NOT MATCHED THEN
    INSERT (id, last, name)
    VALUES (2097153, 'smith', 'john');

When performance benchmarking reveals slower execution times compared to procedural checks (Update then Insert), developers sometimes revert to the traditional two-step client-side approach.

Alternative 1: Exception Handling for Upserts (The “Try to Insert” Method)

Before MERGE became prevalent, a standard pattern involved attempting an INSERT and catching the specific error raised when a unique constraint (like a primary key violation) occurs, then executing an UPDATE inside the exception block. This relies on the DUP_VAL_ON_INDEX exception.

BEGIN
    -- Attempt the insert first
    INSERT INTO t (mykey, mystuff)
    VALUES ('X', 123);
EXCEPTION
    WHEN DUP_VAL_ON_INDEX THEN
        -- If it failed due to a duplicate key, execute the update
        UPDATE t
        SET mystuff = 123
        WHERE mykey = 'X';
END;
/

Application Consideration: The choice between attempting an INSERT first versus an UPDATE first often depends on the expected frequency of inserts versus updates in your application’s workload. Choose the operation you expect to succeed most often to minimize exception handling overhead.

Alternative 2: Conditional Logic Based on Row Count

A procedural approach that avoids explicit exception catching involves executing an UPDATE and then checking the value of the implicit cursor attribute SQL%ROWCOUNT. If zero rows were affected by the UPDATE, it implies the record did not exist, prompting an INSERT.

UPDATE tablename
SET val1 = :in_val1,
    val2 = :in_val2
WHERE val3 = :in_val3;

IF (SQL%ROWCOUNT = 0) THEN
    INSERT INTO tablename (val1, val2, val3) -- Assuming val3 is included in the insert tuple
    VALUES (:in_val1, :in_val2, :in_val3);
END IF;

A related variation checks SQL%NOTFOUND (which is equivalent to SQL%ROWCOUNT = 0 for a single DML statement):

UPDATE tablename SET val1 = :in_val1, val2 = :in_val2
    WHERE val3 = :in_val3;

IF (SQL%NOTFOUND) THEN
    INSERT INTO tablename
        VALUES (:in_val1, :in_val2, :in_val3);
END IF;

When comparing this to MERGE, some developers favor the UPDATE/IF/INSERT structure for single-row operations due to its familiarity, although MERGE theoretically performs only a single index lookup internally, whereas this method might involve two lookups (one for UPDATE, one for INSERT).

Alternative 3: Leveraging WHERE NOT EXISTS for Inserts

This method separates the insertion attempt from the update attempt using a conditional INSERT combined with a subsequent unconditional UPDATE.

-- Attempt to insert only if the record does not exist
INSERT INTO mytable (id1, t1)
SELECT 11, 'x1'
FROM DUAL
WHERE NOT EXISTS (SELECT id1 FROM mytable WHERE id1 = 11);

-- Always attempt to update if the record exists (this will only affect rows that exist)
UPDATE mytable SET t1 = 'x1' WHERE id1 = 11;

This can be effective but requires two separate DML statements.

Alternative 4: Using MINUS for Set Difference

For scenarios where you are trying to ensure a specific dataset combination exists in a target table, the MINUS set operator can be employed, although this is less a traditional upsert and more of a synchronization mechanism:

INSERT INTO b_building_property (col1, col2, col3, col4, col5, id)
SELECT
    'AREA_IN_COMMON_USE_DOUBLE', 'Area in Common Use', 'DOUBLE', NULL, 9000, 9
FROM DUAL
MINUS
(
    SELECT col1, col2, col3, col4, col5, id
    FROM b_building_property
    WHERE id = 9
);

This inserts rows from the left side that do not appear on the right side.

Alternative 5: Multi-Table INSERT Statements (Oracle 9i+)

Oracle introduced sophisticated conditional INSERT statements that allow inserting into multiple target tables based on complex conditions applied to a single source dataset. This is particularly useful when branching logic dictates where the source data should land.

INSERT FIRST
    WHEN credit_limit >= 100000
    THEN INTO rich_customers VALUES (cust_id, cust_credit_limit)
    INTO customers -- If the rich_customers insert happened, this next line is skipped due to FIRST
WHEN
    ELSE INTO customers SELECT * FROM new_customers; -- This acts as the final catch-all

Addressing Concurrent Access Safety

A significant drawback of the simple UPDATE/IF INSERT or the initial MERGE patterns is vulnerability to race conditions under high concurrency. If two sessions execute the logic simultaneously, both might see that a row does not exist (or fails the initial update), leading to both sessions inserting the same row, potentially violating unique constraints or creating duplicate data.

To achieve transaction safety against concurrent operations, the logic must be wrapped in a retry loop:

PROCEDURE safe_upsert_employee (
    p_id IN NUMBER,
    p_last IN VARCHAR2,
    p_name IN VARCHAR2
) IS
BEGIN
 LOOP
  BEGIN
    -- Attempt the MERGE operation
    MERGE INTO Employee e
    USING DUAL
    ON (e.id = p_id)
    WHEN MATCHED THEN
        UPDATE SET e.last = p_last, e.name = p_name
    WHEN NOT MATCHED THEN
        INSERT (id, last, name)
        VALUES (p_id, p_last, p_name);

    EXIT; -- Success: exit the loop
  EXCEPTION
    WHEN NO_DATA_FOUND THEN
      -- Typically happens if the row was deleted by another transaction *after* the initial check
      NULL; -- Retry the operation
    WHEN DUP_VAL_ON_INDEX THEN
      -- Another session inserted the row concurrently *after* our check but before our commit/write
      NULL; -- Retry the operation
    -- Note: Avoid SERIALIZABLE transaction isolation mode unless necessary, as it can lead to ORA-08177 errors.
  END;
 END LOOP;
END safe_upsert_employee;

This retry mechanism ensures that if an external transaction interferes during the upsert attempt, the current session catches the resulting exception and retries the entire atomic MERGE block, guaranteeing that the final state reflects the intended update or insertion.

FAQs on SQL Merge Statement Alternatives

Q: How does MERGE differ from two separate UPDATE and INSERT statements

ANS: MERGE combines the conditional logic into a single statement, which the database engine can often optimize for a single data access pass (index lookup) compared to potentially two separate operations, especially in the procedural UPDATE/IF INSERT structure.

Q: Is using DUAL in MERGE safe for updates

ANS: Yes, using DUAL in MERGE is a standard Oracle pattern for driving an update or insert based on constants or parameters passed to the procedure. However, it does not inherently protect against concurrent writes from other sessions unless wrapped in a robust retry mechanism.

Q: Which upsert strategy handles concurrent inserts best

ANS: The strategy involving wrapping the MERGE or the INSERT/EXCEPTION/UPDATE block inside a LOOP that retries upon specific constraint violation exceptions (DUP_VAL_ON_INDEX) provides the highest level of safety against race conditions.
