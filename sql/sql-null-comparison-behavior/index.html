“SQL NULL = NULL Behavior: Three-Valued Logic vs. ANSI Settings”

The comparison NULL = NULL in SQL is a frequent source of confusion, often contrasting sharply with intuition derived from two-valued logic (2VL) where any item is always equal to itself ($x=x$ is always true). Why does SQL treat this comparison as UNKNOWN or, depending on settings, FALSE? This behavior stems directly from SQL’s reliance on Three-Valued Logic (3VL).

The Core Tenet: NULL Signifies “Unknown”

Fundamentally, in standard SQL, NULL represents missing or unknown information, not a zero or an empty string.

If you ask: “How old is Frank?” and the answer is unknown ($\text{NULL}$), and you ask the same for Shirley, also $\text{NULL}$. Are their ages equal? The correct logical answer is I don’t know ($\text{UNKNOWN}$), not No ($\text{FALSE}$), because they might be the same age—you simply lack the data to confirm equality.

In 3VL, the possible outcomes for any logical expression are TRUE, FALSE, or UNKNOWN ($\text{NULL}$ when used in a result set context).

When comparing two unknown quantities: $$\text{NULL} = \text{NULL} \rightarrow \text{UNKNOWN}$$

This aligns with the reflexive property of equality ($x=x$), but in 3VL, the result is $\text{UNKNOWN}$ because the underlying values are unknown.

Impact of ANSI_NULLS Setting (SQL Server Context)

The final outcome of NULL = NULL in practical execution heavily depends on the specific database configuration, particularly the ANSI_NULLS setting in environments like SQL Server.

  1. SET ANSI_NULLS ON (Default in many systems): When this setting is active, SQL adheres strictly to the ANSI SQL-92 standard where comparisons involving NULL result in UNKNOWN. Because the WHERE clause only returns rows where the predicate evaluates to TRUE, any predicate evaluating to UNKNOWN results in the row being omitted. Thus, practically, NULL = NULL acts like FALSE in a WHERE clause context.

    -- Example demonstrating ANSI_NULLS ON behavior
SET ANSI_NULLS ON;

IF NULL = NULL
    SELECT 'TRUE' AS Result;
ELSE
    SELECT 'FALSE' AS Result; -- This branch executes practically for DML

  2. SET ANSI_NULLS OFF: When disabled, the behavior reverts to a legacy or non-standard mode where NULL = NULL evaluates to TRUE.

    -- Example demonstrating ANSI_NULLS OFF behavior
SET ANSI_NULLS OFF;

IF NULL = NULL
    SELECT 'TRUE' AS Result; -- This branch executes
ELSE
    SELECT 'FALSE' AS Result;

SET ANSI_NULLS ON; -- Resetting for safety

Expert Opinions on Avoiding NULL Pitfalls

Many database theorists and experts strongly advise minimizing or completely avoiding NULLable columns in base tables due to the complexity it introduces.

  • Joe Celko emphasizes that NOT NULL constraints should be the default, treating NULL as a marker for missing data that complicates querying and reporting significantly. He notes that GROUP BY treats all NULLs as equal for grouping purposes, overriding the 3VL comparison rule.
  • C. J. Date advocates for total avoidance, noting that SQL’s implementation of NULL is often inconsistent and problematic.
  • Fabian Pascal points out inconsistencies, such as x IS NOT NULL not being equivalent to NOT(x IS NULL) as expected in 2VL.

Developer Perspective: When NULL Means “Known Absent”

From a pragmatic developer standpoint (Solution 4), NULL is frequently used to signify a known state of absence rather than pure uncertainty. Examples include:

  • deletedAt column being NULL means the record has not been deleted.
  • A new client’s LastPurchase being NULL means they have not purchased yet.
  • In tree structures, a root node having Parent = NULL.

In these scenarios, comparing two instances of “known absence” should intuitively yield TRUE.

Alternative Comparison Methods

When the standard IS NULL or = operators do not provide the desired outcome (especially when you want two NULLs to behave as equal), specific vendor functions or standard SQL alternatives exist:

  1. Using IS NOT DISTINCT FROM (PostgreSQL/Standard SQL): This operator treats NULL as a regular value. $$\text{NULL IS NOT DISTINCT FROM NULL} \rightarrow \text{TRUE}$$

    SELECT 1
WHERE nullParam1 IS NOT DISTINCT FROM nullParam2;

  2. Using ISNULL or COALESCE (Workaround): Substitute NULL with a known, non-conflicting placeholder value for comparison.

    -- Substitutes NULL with -1 before comparison
SELECT 1
WHERE ISNULL(nullParam1, -1) = ISNULL(nullParam2, -1);

  3. Using INTERSECT: In some contexts, INTERSECT can demonstrate the identity of two NULLs.

    SELECT 1
WHERE EXISTS (
    SELECT NULL
    INTERSECT
    SELECT NULL
); -- Returns a row if both sides resolve to NULL

  4. Checking Self-Equality (Non-SQL context example): In certain programming languages (like JavaScript, Solution 21), checking if a variable equals itself is a definitive test for null (since null == null is false for the value comparison in 3VL systems).

FAQs on SQL Null Comparison Behavior

Q: What does NULL = NULL evaluate to in standard SQL

ANS: It evaluates to UNKNOWN (or NULL in result sets), which causes rows to be excluded from a standard WHERE clause filter.

Q: How do I make NULL = NULL return TRUE

ANS: You must use vendor-specific syntax like IS NOT DISTINCT FROM (e.g., PostgreSQL) or set the database session setting SET ANSI_NULLS OFF (e.g., SQL Server).

Q: Is UNKNOWN the same thing as NULL in SQL logic

ANS: In DML contexts like the WHERE clause, the logical result UNKNOWN is represented by NULL, causing rows to be filtered out. However, UNKNOWN is a logical value, while NULL is a data marker/value.

Q: Does GROUP BY treat NULLs as equal

ANS: Yes, for the purpose of aggregation, GROUP BY treats all NULL values as being equal to each other, forming a single group.
