“SQL Upsert Concurrency: Avoiding Duplicate Inserts During High Volume Transactions”

When implementing an upsert (update if exists, insert if not) stored procedure, especially under conditions of high transaction volume, developers frequently encounter race conditions leading to duplicate primary key insertions. This occurs when multiple concurrent transactions simultaneously check for the existence of a record, both find it absent (NOT EXISTS), and subsequently both attempt to insert, violating a unique constraint.

How can we architect an SQL routine to ensure atomicity and prevent these concurrency-induced duplicates, even when dealing with high throughput? Several well-established patterns address this challenge.

Pattern 1: Just F***ing Do It (JFDI) with Error Handling

The JFDI approach relies on attempting the insertion immediately and then using a TRY...CATCH block to handle the expected primary key violation error, switching to an update operation if the insert fails due to a duplicate key.

A critical observation from developing procedures around this pattern is that simple IF EXISTS checks are often insufficient under high concurrency. When tuning indexes, initial reliance on IF EXISTS (SELECT...) can fail because two parallel transactions might both see no row and proceed to insert, creating duplicates before any index lock can fully prevent it. The solution lies in leveraging the unique index constraint itself as the final gatekeeper.

Implementation focusing on Error Code 2627 (Primary Key Violation):

BEGIN TRY
   -- Attempt the insert directly
   INSERT INTO TargetTable (PrimaryKeyColumn, DataColumn1) 
   VALUES (@inputKey, @inputValue1);
END TRY
BEGIN CATCH
    -- Check if the error code signifies a primary key violation (Error 2627)
    IF ERROR_NUMBER() <> 2627
      -- If it's another error, re-raise it
      RAISERROR ('An unexpected error occurred during insert or update.', 16, 1);
END CATCH

Addressing Lock Escalation Concerns:

A common concern with locking hints is whether an UPDLOCK might escalate to a table lock, inhibiting other operations. In the context of using error trapping for upsert, we rely on the instantaneous check provided by the constraint, making explicit row/page locks less of a primary focus than in pure pessimistic locking scenarios.

Pattern 2: Pessimistic Locking with HOLDLOCK

If a purely transactional locking mechanism is preferred over relying on exception handling for flow control, employing robust locking hints within the existence check is necessary. Including HOLDLOCK (which is equivalent to SERIALIZABLE) forces the transaction to hold shared locks until commitment, preventing other transactions from reading or modifying the inspected data range until this transaction completes, thus ensuring that if the first transaction inserts, the second transaction attempting the existence check will see the newly inserted row.

Upsert using UPDLOCK and HOLDLOCK:

INSERT INTO TheTable 
SELECT 
    @primaryKey, 
    @value1, 
    @value2 
WHERE 
    NOT EXISTS 
    (
        SELECT 0
        FROM TheTable WITH (UPDLOCK, HOLDLOCK) -- HoldLock ensures isolation until commit
        WHERE PrimaryKey = @primaryKey
    );

Note: If the goal is strictly to update if it exists and insert if it does not, examining specific upsert patterns related to this query structure might be beneficial. See external resources on optimal SQL Server upsert techniques.

Pattern 3: Using the MERGE Statement

The MERGE statement in SQL Server is designed precisely for this conditional insert or update logic. It combines the checking, updating, and inserting into a single, atomic operation handled by the engine, often resulting in cleaner code than complex IF/ELSE or TRY/CATCH logic for this specific task.

Example SQL MERGE Implementation:

MERGE INTO TargetTable AS Target
USING (VALUES (@inputKey, @inputValue1, @inputValue2)) AS Source (key, value1, value2)
ON Target.key = Source.key
WHEN MATCHED THEN
    -- Row exists: Update the values
    UPDATE SET Target.value1 = Source.value1, Target.value2 = Source.value2
WHEN NOT MATCHED BY TARGET THEN
    -- Row does not exist: Insert the new row
    INSERT (key, value1, value2) 
    VALUES (Source.key, Source.value1, Source.value2);

Enhancing Error Trapping Logic

When using Solution 1 (JFDI), simply ignoring error 2627 might not be enough if other errors occur during the failed insert attempt. A more thorough approach involves capturing and re-raising all relevant, unexpected errors.

Advanced Error Trapping Structure:

If the error number is not 2627 (PK violation), we capture the system error details and re-raise them appropriately, instead of just relying on a generic RAISERROR.

BEGIN TRY
   INSERT INTO etc (columns) VALUES (@params);
END TRY
BEGIN CATCH
    IF ERROR_NUMBER() <> 2627
      BEGIN
            DECLARE @ErrorMessage NVARCHAR(4000);
            DECLARE @ErrorSeverity INT;
            DECLARE @ErrorState INT;

            -- Capture error context
            SELECT 
                @ErrorMessage = ERROR_MESSAGE(),
                @ErrorSeverity = ERROR_SEVERITY(),
                @ErrorState = ERROR_STATE();

            -- Re-raise the captured error
            RAISERROR (
                @ErrorMessage,
                @ErrorSeverity,
                @ErrorState
            );
      END
    -- Implicitly ignore error 2627 (duplicate key) and allow flow to proceed (or transition to update logic if necessary)
END CATCH

Handling Multiple Duplicate Key Errors

Often, both error code 2627 (Primary Key violation) and 2601 (Unique Index violation, for non-PK unique constraints) indicate a condition where the record already exists and an insert should be avoided or changed to an update. It is advisable to check for both in the CATCH block.

Ignoring 2601 and 2627 Errors:

-- Within a CATCH block:
IF ERROR_NUMBER() NOT IN (2601, 2627) 
    THROW; -- Use THROW for SQL Server 2012+ for better error propagation

Alternative Logic: Check First, Then Act (Less Concurrent)

A different methodology involves explicitly checking for existence first, although this is generally less performant or reliable under high load than the exception-based approach.

Check-then-Act Logic:

  1. Declare a variable to store the primary key found status.
  2. Execute a SELECT to check if the record exists based on key parameters.
  3. Use an IF statement: if the key variable is populated (not NULL), perform an UPDATE; otherwise, perform an INSERT.

Example Check-then-Act (Conceptual):

DECLARE @existingKey VARCHAR(10);

SET @existingKey = (
    SELECT primaryKey 
    FROM TargetTable 
    WHERE param1field = @param1 AND param2field = @param2
);

IF @existingKey IS NOT NULL
BEGIN
    -- Row exists: Update it
    UPDATE TargetTable SET someValue = @newValue WHERE primaryKey = @existingKey;
END
ELSE
BEGIN
    -- Row does not exist: Insert
    INSERT INTO TargetTable(param1Field, param2Field, someValue) 
    VALUES(@param1, @param2, @newValue);
END

Note: This pattern is susceptible to race conditions unless strong isolation levels are used.

C#/.NET Client-Side Exception Handling

For applications using ADO.NET or frameworks like Dapper, the logic can sometimes be cleanly shifted to the application layer to avoid complex SQL logic for simple error ignoring.

Example C# Exception Handling (Dapper with SQL Server):

try
{
    connection.Execute("INSERT INTO TargetTable (PrimaryKeyColumn, DataColumn1) VALUES (@Key, @Value)", new { Key = inputKey, Value = inputValue1 });
}
catch (SqlException ex) when (ex.Number == 2601 || ex.Number == 2627)
{
    // Gracefully handle the "duplicate key" error by ignoring it, 
    // or transition logic here to execute an UPDATE statement instead.
    Console.WriteLine("Duplicate key encountered, ignoring insert attempt.");
}

FAQs on SQL Upsert Concurrency Avoiding Duplicate Inserts

Q: What is the primary issue when using IF EXISTS for upsert operations

ANS: Under high concurrency, multiple transactions can simultaneously evaluate NOT EXISTS as true before any one transaction successfully commits its insertion, leading to race conditions and subsequent duplicate key errors.

Q: Which SQL error numbers relate to unique constraint violations

ANS: Error 2627 typically signifies a Primary Key violation, while Error 2601 indicates a violation of a general Unique Index constraint. Both may need to be handled during an upsert retry logic.

Q: Is the MERGE statement always the most performant upsert method

ANS: The MERGE statement is highly readable and atomic. Performance relative to the JFDI pattern depends heavily on indexing and workload characteristics; it should always be benchmarked against the specific environment.

Q: What does the HOLDLOCK hint achieve in a SELECT statement

ANS: HOLDLOCK (equivalent to SERIALIZABLE isolation level for the duration of the statement) ensures that locks acquired during the SELECT statement are held until the transaction commits, preventing other transactions from interfering with the data range being checked.
