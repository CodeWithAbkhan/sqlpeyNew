“SQL NULL Comparison: Why Use IS NULL Instead of = NULL or <> NULL”

This discussion delves into the inherent nature of NULL in SQL and provides effective methods for testing for its presence or absence.

The Nature of NULL in SQL Comparisons

In standard SQL, NULL signifies an absence of a value or an unknown value. Because it represents an unknown state, it cannot be reliably compared to any scalar value, including another NULL.

Why does MyColumn = NULL fail to return expected rows?

Standard SQL dictates that any comparison involving NULL results in the three-valued logic state: UNKNOWN.

  • If you test WHERE MyColumn = NULL, the result is UNKNOWN.
  • If you test WHERE MyColumn <> NULL or WHERE MyColumn != NULL, the result is also UNKNOWN.

The WHERE clause only selects rows where the condition evaluates to TRUE. Since comparisons against NULL yield UNKNOWN, those rows are excluded.

Standard Operators vs. NULL

The standard SQL comparison operator for inequality is <>. Many SQL implementations, like SQL Server, also widely support != as a non-standard equivalent for backwards compatibility or programmer familiarity from other languages.

However, both <> and != operate on the principle of comparing values. Since NULL is the absence of a value, the comparison fails logically:

-- Example demonstrating standard comparison failure (Result: UNKNOWN)
SELECT *
FROM SampleData
WHERE SomeColumn <> 'TargetValue';

-- If SomeColumn is NULL, the above query will not return the row.

The only accepted way to test if a column is this unknown placeholder is using the dedicated predicate:

  • To check if a value is absent: WHERE SomeColumn IS NULL
  • To check if a value is present: WHERE SomeColumn IS NOT NULL

This behavior aligns with the ANSI SQL-92 standard.

Alternative Approaches and Context Adjustments

While the standard dictates using IS NULL, certain practical requirements sometimes necessitate treating NULL as if it were an empty string or zero for application-level logic.

1. Using Built-in Functions to Substitute NULLs

To handle cases where application users might confuse NULL with an empty string (''), functions like ISNULL (SQL Server specific) or COALESCE (ANSI standard) can be employed. These functions substitute NULL with a specified default value during the evaluation of the expression.

Consider a scenario where you want rows where the column is NULL OR an empty string:

-- Alternative using ISNULL (SQL Server example)
SELECT *
FROM MyTable
WHERE ISNULL(MyColumn, ' ') = ' ';
-- This retrieves rows where MyColumn is NULL (substituted as ' ') or where it literally is ' '.

The COALESCE function offers ANSI standard compatibility across many platforms:

-- Alternative using COALESCE (ANSI Standard)
SELECT *
FROM MyTable
WHERE COALESCE(MyColumn, '') = '';

2. Forcing Comparison Behavior (ANSI_NULLS Setting)

It is important to note that the strict adherence to NULL comparison rules is usually enforced by the SET ANSI_NULLS ON setting in environments like SQL Server. If this setting is explicitly disabled:

SET ANSI_NULLS OFF;

The database engine might allow comparisons like WHERE MyColumn <> NULL to behave differently (sometimes returning rows where it would otherwise return UNKNOWN). However, relying on SET ANSI_NULLS OFF is discouraged as it deviates from the standard and may be deprecated in future database versions.

3. Creating Custom Equality Logic (User-Defined Functions)

When comparing two columns (ColumnA and ColumnB) and needing a specific outcome where NULL = NULL is treated as TRUE (i.e., they are “equal” in their state of being null), a custom function can define this precise logic.

For instance, one approach defines a function that returns TRUE only if both are null or if both are non-null and equal:

-- Custom function logic for checking equality including NULLs
CREATE FUNCTION dbo.fn_CompareWithNulls (@Val1 sql_variant, @Val2 sql_variant)
RETURNS bit
AS
BEGIN
    DECLARE @Val1IsNull bit = CASE WHEN @Val1 IS NULL THEN 1 ELSE 0 END
    DECLARE @Val2IsNull bit = CASE WHEN @Val2 IS NULL THEN 1 ELSE 0 END

    -- If null status differs, they are not equal (0)
    IF @Val1IsNull <> @Val2IsNull
        RETURN 0

    -- If both are null, they are considered equal (1)
    IF @Val1IsNull = 1 AND @Val2IsNull = 1
        RETURN 1

    -- If both are not null, compare their actual values
    IF @Val1 = @Val2
        RETURN 1

    RETURN 0
END

Using this custom logic allows for behavior outside the standard SQL comparison model:

SELECT *
FROM Orders
WHERE dbo.fn_CompareWithNulls(DeliveredDate, OrderedDate) = 1;
-- This would now select rows where DeliveredDate = OrderedDate AND rows where both are NULL.

FAQs on SQL NULL Comparison

Q: Why does SELECT * FROM MyTable WHERE SomeCol <> NULL return zero rows

ANS: Because NULL represents an unknown value, any comparison operator (=, <>, !=) used against it evaluates to UNKNOWN, which the WHERE clause rejects. You must use the specialized predicate IS NOT NULL.

Q: Is the <> operator standard SQL

ANS: Yes, <> is the SQL-92 standard operator for “not equal to.” The != operator is widely supported but is often considered a non-standard extension provided for compatibility.

Q: How do I check if two columns are both NULL

ANS: You should use WHERE ColumnA IS NULL AND ColumnB IS NULL. Direct comparison like WHERE ColumnA = ColumnB will fail when both are NULL because NULL = NULL evaluates to UNKNOWN.

Q: Can I use the inequality operator to check for non-null values

ANS: You can use it to check if a column differs from a known value (e.g., WHERE MyColumn <> 5). However, you cannot reliably use it to check against NULL itself; you must use WHERE MyColumn IS NOT NULL to confirm the column holds some value.
