“SQL Server Query Execution Plan: Methods and Analysis”

Understanding how SQL Server processes queries is crucial for identifying and resolving performance bottlenecks. Execution plans provide a detailed roadmap of the operations SQL Server undertakes to retrieve or modify data. Several methods exist to capture these plans, ranging from built-in tools to advanced techniques.

Methods for Obtaining Execution Plans

There are multiple ways to capture query execution plans in SQL Server. The choice often depends on your environment, access privileges, and whether you need an estimated or actual plan.

1. Using SQL Server Management Studio (SSMS)

SSMS offers a user-friendly graphical interface for obtaining execution plans.

  • Estimated Execution Plan:

    • Press Ctrl + L.
    • Click the “Display Estimated Execution Plan” button in the query toolbar.
    • This generates a plan without actually running the query, useful for initial analysis.

  • Actual Execution Plan:

    • Press Ctrl + M.
    • Click the “Include Actual Execution Plan” button in the query toolbar before executing your query.
    • The actual execution plan runs the query and shows what actually happened, including resource consumption and row counts, making it invaluable for diagnosing performance issues.

  • Live Query Plan (SSMS 2016+):

    • Click the “Include Live Query Plan” button in the query toolbar before executing your query.
    • This provides a real-time, dynamic view of the query’s execution as it progresses, updating statistics dynamically.

When using SSMS, after executing a query with the actual execution plan enabled, an additional “Execution plan” tab will appear in the results pane, displaying the graphical representation of the plan. You can right-click this plan to save it as an XML file.

2. Using SHOWPLAN Options

For scenarios where SSMS might not be available or for scripting purposes, T-SQL commands can be used. These are connection-level settings.

  • SET SHOWPLAN_TEXT ON: Provides a basic text-based estimated execution plan without executing the query.
  • SET SHOWPLAN_ALL ON: Offers a text-based estimated execution plan with cost estimations, also without execution.
  • SET SHOWPLAN_XML ON: Generates an XML-based estimated execution plan with cost estimations. This is equivalent to SSMS’s “Display Estimated Execution Plan.”
  • SET STATISTICS PROFILE ON: Executes the query and displays a text-based actual execution plan.
  • SET STATISTICS XML ON: Executes the query and provides an XML-based actual execution plan, mirroring SSMS’s “Include Actual Execution Plan.” This is generally the recommended option due to its richness of information.

To disable these options, use SET <option> OFF. For example, SET SHOWPLAN_ALL OFF.

Example using SET STATISTICS XML ON:

SET STATISTICS XML ON;
GO

-- Your SQL Query here
SELECT
    p.Name AS ProductName,
    NonDiscountSales = (OrderQty * UnitPrice),
    Discounts = ((OrderQty * UnitPrice) * UnitPriceDiscount)
FROM Production.Product AS p
INNER JOIN Sales.SalesOrderDetail AS sod
    ON p.ProductID = sod.ProductID
ORDER BY ProductName DESC;
GO

SET STATISTICS XML OFF;
GO

The output will include the XML representation of the actual execution plan.

3. Using SQL Server Profiler

SQL Server Profiler can capture execution plans by tracing specific events. This is useful if you cannot directly run the query or want to monitor plans in a production environment with caution.

  1. Open SQL Server Profiler and create a new trace.
  2. On the “Events Selection” tab, check “Show all events.”
  3. Under “Performance,” select “Showplan XML.”
  4. Run the trace.
  5. Execute your slow-running query.
  6. Stop the trace. You can then right-click the captured plan XML and select “Extract event data…” to save it.

Caveats: Profiler can introduce performance overhead. Careful filtering is necessary in busy environments. Always consult your DBA before using Profiler on production systems.

4. Inspecting the Query Plan Cache (DMVs)

You can query Dynamic Management Views (DMVs) to retrieve cached query plans. This is helpful if a query has run recently and you cannot re-execute it.

SELECT
    qs.creation_time,
    qs.last_execution_time,
    qs.execution_count,
    st.text AS SQL_Text,
    qp.query_plan AS Query_Plan
FROM sys.dm_exec_query_stats AS qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS st
CROSS APPLY sys.dm_exec_query_plan(qs.plan_handle) AS qp
WHERE st.text LIKE '%your_query_text%'; -- Filter for your specific query

You can also use sys.dm_exec_text_query_plan to get the plan as text, which can be more manageable for complex plans or for selecting specific statements within a batch.

SELECT
    r.session_id,
    r.status,
    r.command,
    r.wait_type,
    r.wait_time,
    st.text AS SQL_Text,
    qp.query_plan AS Query_Plan
FROM sys.dm_exec_requests AS r
OUTER APPLY sys.dm_exec_text_query_plan(r.plan_handle, r.statement_start_offset, r.statement_end_offset) AS qp
LEFT JOIN sys.dm_exec_sql_text(r.plan_handle) AS st ON 1=1
WHERE r.session_id = @@SPID; -- Get plan for the current session

To display the XML plan directly in SSMS from a single row result, a specific FOR XML EXPLICIT format can be used:

-- Assuming @plan_handle, @statement_start_offset, @statement_end_offset are set
SELECT
    Tag = 1,
    Parent = NULL,
    [ShowPlanXML!1!!XMLTEXT] = query_plan
FROM sys.dm_exec_text_query_plan(
    @plan_handle,
    @statement_start_offset,
    @statement_end_offset)
FOR XML EXPLICIT;

5. Using Extended Events (XEvents)

Extended Events provide a more flexible and lightweight way to capture performance data, including execution plans.

Example XEvent Session to capture query plans:

CREATE EVENT SESSION [GetExecutionPlan] ON SERVER
ADD EVENT sqlserver.query_post_execution_showplan(
    ACTION(package0.event_sequence, sqlserver.plan_handle, sqlserver.query_hash, sqlserver.query_plan_hash, sqlserver.session_id, sqlserver.sql_text, sqlserver.tsql_frame, sqlserver.tsql_stack)),
ADD EVENT sqlserver.sql_batch_completed(
    ACTION(package0.event_sequence, sqlserver.client_app_name, sqlserver.database_id, sqlserver.plan_handle, sqlserver.query_hash, sqlserver.query_plan_hash, sqlserver.session_id, sqlserver.sql_text, sqlserver.tsql_frame, sqlserver.tsql_stack))
-- Add other relevant events as needed
ADD TARGET package0.ring_buffer
WITH (
    MAX_MEMORY = 4096 KB,
    EVENT_RETENTION_MODE = ALLOW_SINGLE_EVENT_LOSS,
    MAX_DISPATCH_LATENCY = 30 SECONDS,
    MAX_EVENT_SIZE = 0 KB,
    MEMORY_PARTITION_MODE = NONE,
    TRACK_CAUSALITY = ON,
    STARTUP_STATE = OFF
);
GO

-- Start the session
ALTER EVENT SESSION [GetExecutionPlan] ON SERVER STATE = START;
GO

-- Watch live data in SSMS
-- Right-click session -> Watch Live Data

-- Execute your query
USE AdventureWorks;
GO
SELECT p.Name AS ProductName,
    NonDiscountSales = (OrderQty * UnitPrice),
    Discounts = ((OrderQty * UnitPrice) * UnitPriceDiscount)
FROM Production.Product AS p
INNER JOIN Sales.SalesOrderDetail AS sod
    ON p.ProductID = sod.ProductID
ORDER BY ProductName DESC;
GO

-- Stop the session
ALTER EVENT SESSION [GetExecutionPlan] ON SERVER STATE = STOP;
GO

In SSMS, you can navigate to “Management” -> “Extended Events” -> “Sessions,” right-click the created session, and select “Watch Live Data” to view captured events and their associated query plans.

6. Third-Party Tools

Several external tools enhance the process of obtaining and analyzing execution plans:

  • ApexSQL Plan: Integrates with SSMS to provide enhanced visualization and analysis of estimated and actual execution plans.
  • SQL Sentry Plan Explorer: A popular free tool known for its user-friendly interface and detailed analysis capabilities, offering more insights than SSMS alone.

7. Query Store (SQL Server 2016+)

Query Store is a database-level feature that tracks query performance, plan changes, and execution statistics over time. It’s excellent for identifying performance regressions after schema or data changes.

  • Enabling Query Store: It’s database-specific and not enabled by default for new databases. You can enable it via SSMS or T-SQL.
  • DMVs for Query Store: Use DMVs like sys.query_store_query, sys.query_store_plan, and sys.query_store_runtime_stats to retrieve historical performance data, including execution plans.

8. Using PowerShell

PowerShell can be scripted to capture actual execution plans using SET STATISTICS XML ON. This is particularly useful for automating the capture of plans for stored procedures or complex scripts.

# Script Variables
[string]$server = '.\SQLServerInstance'
[string]$database = 'YourDatabase'
[string]$sqlCommand = 'EXEC YourStoredProcedure'
[string]$XMLOutputFileName = 'YourStoredProcedure'
[string]$XMLOutputPath = 'C:\SQLDumps\ActualPlans\'

# Connection setup
$connectionString = "Persist Security Info=False;Integrated Security=true;Connection Timeout=0;Initial Catalog=$database;Server=$server"
$connection = New-Object System.Data.SqlClient.SQLConnection($connectionString)

# Commands
$command = New-Object System.Data.SqlClient.SQLCommand($sqlCommand, $connection)
$command.CommandTimeout = 0
$commandXMLActPlanOn = New-Object System.Data.SqlClient.SQLCommand("SET STATISTICS XML ON", $connection)
$commandXMLActPlanOff = New-Object System.Data.SqlClient.SQLCommand("SET STATISTICS XML OFF", $connection)

$connection.Open()

# Enable XML plan
$commandXMLActPlanOn.ExecuteNonQuery()

# Execute SP and get results
$adapter = New-Object System.Data.sqlclient.sqlDataAdapter $command
$dataset = New-Object System.Data.DataSet
$adapter.Fill($dataset) | Out-Null

# Save XML plans
[string]$fileNameDateStamp = Get-Date -f yyyyMMdd_HHmmss
[string]$XMLOutputFilePath = "$XMLOutputPath$XMLOutputFileName`_$fileNameDateStamp.sqlplan"

[int]$cntr = 1
ForEach ($table in $dataset.Tables) {
    if ($table.Columns[0].ColumnName -eq "Microsoft SQL Server 2005 XML Showplan") {
        [string]$fullXMLPlan = $table.rows[0]."Microsoft SQL Server 2005 XML Showplan"
        if ($cntr -eq 1) {
            [regex]$rxStart = "\<ShowPlanXML xmlns\=.{1,}\<Statements\>"
            [string]$startXMLPlan = $rxStart.Match($fullXMLPlan).Value
            [regex]$rxEnd = "\<\/Statements\>.{1,}\<\/ShowPlanXML\>"
            [string]$endXMLPlan = $rxEnd.Match($fullXMLPlan).Value
            $startXMLPlan | Out-File -Append -FilePath $XMLOutputFilePath
        }
        [regex]$rxBody = "\<StmtSimple.{1,}\<\/StmtSimple\>"
        [string]$bodyXMLPlan = $rxBody.Match($fullXMLPlan).Value
        $bodyXMLPlan | Out-File -Append -FilePath $XMLOutputFilePath
        $cntr++
    }
}
$endXMLPlan | Out-File -Append -FilePath $XMLOutputFilePath

# Disable XML plan
$commandXMLActPlanOff.ExecuteNonQuery()

$connection.Close()

9. Other Tools

  • DataGrip: Offers an “Explain Plan” feature. Right-click an SQL statement, select “Explain Plan,” then click “Plan” in the output pane. A visualization can be accessed via Ctrl+Shift+Alt+U.

“Actual” vs. “Estimated” Execution Plans

  • Estimated Plan: Generated without running the query. It’s based on SQL Server’s statistics and cost-based optimization. Useful for initial checks and understanding the intended execution path.
  • Actual Plan: Generated after running the query. It reflects the real operations performed, including actual row counts, I/O, and CPU costs. This is far more valuable for diagnosing performance issues where estimations might be inaccurate due to stale statistics or other factors.

Key Considerations for Execution Plans

  • Environment Specificity: Always capture execution plans from the environment experiencing performance issues, as factors like data volume, indexing, and server load can significantly alter plans.
  • Encrypted Stored Procedures: You cannot capture execution plans for encrypted stored procedures.
  • Plan Interpretation: Analyzing execution plans is a deep topic. Look for high-cost operators (e.g., table scans, key lookups), large row counts processed, and significant I/O or CPU usage. Tools like SQL Sentry Plan Explorer offer advanced visualization and analysis features.

FAQs on SQL Server Query Execution Plans

Q: What is an execution plan in SQL Server

ANS: An execution plan is a detailed representation of how SQL Server intends to execute a given SQL query. It outlines the steps, operations, and their associated costs, helping to identify performance bottlenecks.

Q: How to view an estimated execution plan in SSMS

ANS: In SQL Server Management Studio (SSMS), you can generate an estimated execution plan by pressing Ctrl+L or clicking the “Display Estimated Execution Plan” icon in the query toolbar before running your query.

Q: How to view an actual execution plan in SSMS

ANS: To view an actual execution plan in SSMS, press Ctrl+M or click the “Include Actual Execution Plan” icon in the query toolbar before executing your query. The plan will appear in a separate tab after execution.

Q: What is the difference between estimated and actual execution plans

ANS: An estimated execution plan is generated without running the query, based on statistics. An actual execution plan is generated after the query runs and shows what actually occurred, including actual row counts and resource usage, making it more accurate for problem diagnosis.

Q: Can I get execution plans programmatically

ANS: Yes, you can obtain execution plans programmatically using T-SQL commands like SET SHOWPLAN_XML ON or SET STATISTICS XML ON, querying DMVs such as sys.dm_exec_query_plan, or by using Extended Events.

Q: Which method is best for capturing execution plans

ANS: For most cases, using SSMS to generate an actual execution plan (Ctrl+M) is the most straightforward and informative. For automated or advanced scenarios, DMVs or Extended Events are powerful options.

Q: What are some tools for analyzing execution plans

ANS: Besides SSMS, tools like SQL Sentry Plan Explorer and ApexSQL Plan offer enhanced visualization and analysis features that can provide deeper insights into query performance.

Q: How does Query Store help with execution plans

ANS: Query Store, available in SQL Server 2016+, tracks query performance history, including execution plans. It’s useful for identifying performance regressions and comparing plans over time.
