“PostgreSQL SQL Variable Alternatives: Methods to Define and Use Values in Queries”

PostgreSQL, in its plain SQL dialect, lacks a direct, native mechanism for declaring and utilizing scalar variables within a single query block, unlike procedural languages such as PL/pgSQL. This limitation often forces developers to employ workarounds to introduce constants or dynamic values directly into SELECT, UPDATE, or DELETE statements.

What are the viable, accepted strategies for introducing temporary, query-scoped values (often called ‘variables’) when writing standard PostgreSQL SQL?

Workarounds Using Common Table Expressions (CTEs)

One of the most idiomatic ways to define values intended for use within a single query is by leveraging the Common Table Expression (CTE) structure, often referred to as WITH clauses. This approach effectively creates a single-row, multi-column virtual table that can be cross-joined or referenced throughout the main query.

Defining Simple Scalar Values via CTE

You can define named constants directly within a CTE. While technically a cross-join, this is highly readable for introducing a few constants.

For instance, setting var1 to 5 and var2 to 'foo':

WITH query_constants (c_id, c_label) AS (
   VALUES (5, 'foo')
)
SELECT s.*
FROM sales_data s, query_constants qc
WHERE s.related_id = qc.c_id
   OR s.description_tag = qc.c_label;

CTEs for Derived or Complex Initial Values

CTEs excel when the “variable” needs to be derived from a subquery before being applied to the main query logic. This is often cleaner than embedding complex subqueries repeatedly.

Example illustrating the calculation of an average and its use in filtering:

WITH calculated_metrics AS (
    SELECT
      '2024-01-01'::date AS filter_start,
      '2024-12-31'::date AS filter_end,
      (SELECT AVG(user_score) FROM performance_logs) AS average_score
)
SELECT u.*
FROM users u
CROSS JOIN calculated_metrics cm  -- CROSS JOIN is often implied by the comma syntax
WHERE u.registration_date BETWEEN cm.filter_start AND cm.filter_end
  AND u.score < cm.average_score;

A variation using single-value CTEs that can be referenced easily:

WITH
    string_constant AS (VALUES ('System_Admin')),
    integer_limit AS (VALUES (100))
SELECT t.*
FROM transactions t
WHERE t.type = (SELECT * FROM string_constant)
LIMIT (SELECT * FROM integer_limit);

Utilizing Temporary Tables

When you need the defined values to persist across multiple sequential SQL statements within the same session (but outside a stored procedure body), temporary tables offer a robust solution.

Creating and Populating a Session-Scoped Temporary Table

This method persists for the duration of the session or transaction, depending on creation scope.

BEGIN;

-- Create a temporary table holding the values we need
SELECT 42 AS magic_number, 'Active' AS status
INTO TEMPORARY TABLE session_vars (val_int integer, val_text text)
ON COMMIT DROP; -- Automatically drops the table when the transaction commits

-- Now, use the temp table as a constant source
SELECT o.*
FROM order_details o
JOIN session_vars sv ON o.status_code = sv.val_text
WHERE o.related_id = sv.val_int;

COMMIT;

An alternative outside an explicit BEGIN/COMMIT block (if supported by the client environment for immediate cleanup):

SELECT 5::int AS temp_id INTO TEMPORARY TABLE single_var_table;

SELECT *
FROM report_table rt
JOIN single_var_table svt ON rt.config_id = svt.temp_id;
-- If using ON COMMIT DROP, the table disappears after this block.

Session Configuration Variables (Dynamic Settings)

PostgreSQL allows setting custom configuration parameters for the current session using SET SESSION. These values are stored as strings and must be explicitly retrieved using current_setting(), requiring a cast for numeric use. This requires PostgreSQL version 9.2 or newer.

Setting and Retrieving Session Variables

-- 1. Set the variable (must use a prefix like 'my.var.')
SET session my.app.region_code = 'EU-WEST-1';
SET session my.app.batch_size = '500';

-- 2. Use the variable in a query after retrieval and casting
SELECT *
FROM audit_logs
WHERE region = current_setting('my.app.region_code')
  AND count < current_setting('my.app.batch_size')::int;

Client/Tool-Specific Features (psql and DBeaver)

Certain PostgreSQL clients offer proprietary syntax for defining variables that act as macros or substitution tokens.

psql Meta-Commands

The psql command-line utility supports the \set command to create session variables that are substituted during query execution (macro-style).

-- Define a value. If the value contains spaces, quote it.
\set target_user_name 'service_account_x'
\set max_limit 50

-- Use the variable with a leading colon
SELECT *
FROM user_profiles
WHERE username = :'target_user_name'
LIMIT :max_limit;

-- Note: psql variables are evaluated at execution time, not creation time.
-- \set macro_subquery '(SELECT COUNT(*) FROM error_logs WHERE is_critical = TRUE)'
-- SELECT :macro_subquery;

DBeaver Parameter Substitution

Tools like DBeaver support named parameters that prompt the user for input upon execution.

SELECT *
FROM documents
WHERE document_status = :status_param; -- DBeaver prompts for the value of status_param

Procedural Language Workarounds (PL/pgSQL)

If the logic requires multiple sequential steps where variables are assigned and modified, the standard approach is to move the logic into an anonymous code block or a stored procedure.

Anonymous PL/pgSQL Block

This uses declarative variables within the DECLARE section and assigns values using SELECT ... INTO.

DO $$
DECLARE
    threshold_value INTEGER := 1000;
    result_table_name TEXT := 'high_value_orders';
BEGIN
    -- Create a temporary table populated using the declared variable
    CREATE TEMP TABLE IF NOT EXISTS temp_results ON COMMIT DROP AS
    SELECT *
    FROM orders
    WHERE order_total > threshold_value;

    RAISE NOTICE 'Results stored in temporary table.';

END $$;

-- Query the results outside the block
SELECT * FROM temp_results;

Preparing Statements

The PREPARE command allows defining a query template with positional parameters ($1, $2, etc.), which can then be executed with specific values.

-- Define the structure with a positional placeholder for the ID
PREPARE fetch_record (INTEGER) AS
    SELECT transaction_id, amount
    FROM financial_records
    WHERE user_id = $1;

-- Execute the prepared statement with the value 12345
EXECUTE fetch_record(12345);

-- Clean up the prepared statement definition
DEALLOCATE fetch_record;

FAQs on PostgreSQL SQL Variable Alternatives

Q: Can I use standard SQL variables in PostgreSQL like in T-SQL or PLSQL

ANS: No, standard PostgreSQL SQL does not natively support declaration and use of scalar variables directly within a single SQL batch outside of procedural language blocks like PL/pgSQL.

Q: Is the CTE method efficient for defining constants

ANS: Yes, for query-scoped constants, the CTE approach using WITH clauses is often considered efficient and highly readable, as it integrates seamlessly with standard SQL execution plans.

Q: How long do session configuration variables last

ANS: Variables set using SET SESSION persist for the entire duration of the current database session until the client disconnects, or until explicitly unset.

Q: What is required to use PREPARE statements

ANS: You must use positional parameters like $1 instead of named variables, and you must EXECUTE the prepared statement with values. They are generally session-scoped.
