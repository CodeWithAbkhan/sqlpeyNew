“PostgreSQL Concurrent Tag Insertion: Preventing Race Conditions with UPSERT Strategies”

When managing unique identifiers like tags, a common requirement is to either fetch the existing ID if the tag is present or insert a new record and retrieve its newly generated ID, all while contending with multiple simultaneous transactions. This scenario, often an “UPSERT” (Insert or Select), introduces race conditions, even when utilizing PostgreSQL’s INSERT ... ON CONFLICT clause (available from version 9.5 onwards).

How can we architect a PostgreSQL function to reliably return a tag_id for a given text tag, ensuring atomicity and correctness under high concurrency?

Solution Approach 1: Direct PL/pgSQL Implementation with Looping

The simplest approach attempts a SELECT first, falling back to an INSERT ... ON CONFLICT DO NOTHING if the row isn’t found.

Initial Implementation (Potential Race Condition)

This initial structure prioritizes speed when the row exists but leaves a small window open for a conflict.

CREATE OR REPLACE FUNCTION get_or_create_tag_id_v1(_tag text, OUT _tag_id int)
  LANGUAGE plpgsql AS
$func$
BEGIN
   -- Attempt to select the ID first (faster path)
   SELECT tag_id
   FROM   tag
   WHERE  tag = _tag
   INTO   _tag_id;

   IF NOT FOUND THEN
      -- If not found in the SELECT, attempt insertion
      INSERT INTO tag AS t (tag)
      VALUES (_tag)
      ON     CONFLICT (tag) DO NOTHING -- If another session inserted it right before
      RETURNING t.tag_id
      INTO   _tag_id;
   END IF;
END
$func$;

Loop-Based Robustness Against Race Conditions

To absolutely guarantee an ID is returned, even if a concurrent transaction inserts the record immediately after the initial SELECT but before the INSERT attempt, we introduce a loop that continues until an ID is successfully retrieved.

CREATE OR REPLACE FUNCTION get_or_create_tag_id_v2(_tag text, OUT _tag_id int)
  LANGUAGE plpgsql AS
$func$
BEGIN
   LOOP
      -- Try to find the existing ID
      SELECT tag_id
      FROM   tag
      WHERE  tag = _tag
      INTO   _tag_id;

      EXIT WHEN FOUND; -- Success if ID was found

      -- If not found, attempt insertion
      INSERT INTO tag AS t (tag)
      VALUES (_tag)
      ON     CONFLICT (tag) DO NOTHING -- If race occurs, this inserts nothing
      RETURNING t.tag_id
      INTO   _tag_id;

      EXIT WHEN FOUND; -- Success if insertion returned an ID
      
      -- If we reached here, the conflict happened and we loop again
   END LOOP;
END
$func$;

-- Example Call:
-- SELECT get_or_create_tag_id_v2('new_feature_tag');

Locking Consideration: If subsequent operations within the same transaction depend critically on this row’s existence and must prevent concurrent modification or deletion, the initial SELECT can employ FOR SHARE locking. This locks the existing row until transaction commit.

Solution Approach 2: Pure SQL with CTEs (Snapshot Issues)

A pure SQL approach using Common Table Expressions (CTEs) with UNION ALL seems concise, but it suffers from PostgreSQL’s MVCC (Multi-Version Concurrency Control) snapshotting limitations.

CREATE OR REPLACE FUNCTION get_or_create_tag_id_sql_cte(_tag text, OUT _tag_id int)
  LANGUAGE sql AS
$func$
WITH ins AS (
   INSERT INTO tag AS t (tag)
   VALUES (_tag)
   ON     CONFLICT (tag) DO NOTHING
   RETURNING t.tag_id
   )
SELECT tag_id FROM ins
UNION  ALL
SELECT tag_id FROM tag WHERE tag = _tag
LIMIT  1;
$func$;

Why this can fail: If Transaction B inserts the tag just before Transaction A executes, and Transaction B has not committed, Transaction A’s snapshot sees no change. The INSERT ... ON CONFLICT DO NOTHING returns empty. The subsequent SELECT tag_id FROM tag also returns empty because it uses the same pre-change snapshot. Result: NULL. This is counter-intuitive but mandated by MVCC consistency. Therefore, looping until a row is retrieved (as in Solution 1, v2) is necessary to wait for the concurrent transaction to complete or to successfully insert.

Solution Approach 3: Separating Concerns with Exception Handling

This method structures the insert operation into its own function that explicitly handles the UNIQUE_VIOLATION exception, allowing the main function to loop only if necessary.

Helper Insert Function (Handles Failure Gracefully)

This function attempts insertion; if it fails due to a duplicate key, it returns NULL instead of raising an error outside the function scope.

CREATE OR REPLACE FUNCTION insert_tag_safe(_tag text, OUT tag_id int)
  RETURNS int
  LANGUAGE plpgsql AS
$func$
BEGIN
   INSERT INTO tag(tag) VALUES (_tag) RETURNING tag.tag_id INTO tag_id;

   EXCEPTION WHEN UNIQUE_VIOLATION THEN
      -- Catch violation; tag_id remains NULL (or undefined)
      RETURN; 
END
$func$;

Main Function Utilizing the Helper

The primary function loops, prioritizing a fast SELECT. If no row is found, it calls the safe insert function.

CREATE OR REPLACE FUNCTION get_or_create_tag_id_v3(_tag text, OUT _tag_id int)
   LANGUAGE plpgsql AS
$func$
BEGIN
   LOOP
      -- Attempt to select first
      SELECT tag_id FROM tag WHERE tag = _tag
      UNION  ALL
      -- Only execute this if the SELECT found nothing (due to UNION ALL behavior)
      SELECT insert_tag_safe(_tag)
      LIMIT  1
      INTO   _tag_id;

      EXIT WHEN _tag_id IS NOT NULL;  -- Loop until an ID is successfully set
   END LOOP;
END
$func$;

This structure is often considered more efficient when the target tag exists most of the time, as the more expensive block involving explicit EXCEPTION handling in insert_tag_safe is rarely executed. PostgreSQL optimizes UNION ALL such that execution stops as soon as the INTO _tag_id condition is satisfied.

Addressing Transaction Isolation Side Effects (Repeatable Read/Serializable)

When raising the transaction isolation level to REPEATABLE READ or SERIALIZABLE, concurrent operations that attempt to read a row subsequently inserted by another committed transaction can lead to a could not serialize access due to concurrent update error.

If Session 1 commits an insert, and Session 2 (running at a higher isolation level) calls f_tag_id('a') which results in NULL because of the MVCC behavior described, Session 2 must retry the entire transaction.

Similarly, deadlocks can occur if transactions lock resources out of sequence (e.g., Session 1 locks Tag A, Session 2 locks Tag B, then both try to lock the other’s tag). Deadlock errors should also typically be caught and retried by the application logic.

Optimizing Bulk Operations

If you need to process an array of tags, avoid looping in your calling code. Leverage set operations like unnest with the robust function:

-- Assuming InsertedPostId is known, processing an array of tags $3
INSERT INTO taggings (PostId, TagId)
SELECT InsertedPostId, get_or_create_tag_id_v2(tag) -- Or v3
FROM   unnest($3) AS tag;

FAQs on PostgreSQL Concurrent Tag Insertion Race Conditions

Q: What is the primary issue when inserting or selecting unique IDs concurrently

ANS: The primary issue is a race condition where one transaction reads that a row doesn’t exist, but before it can insert it, a second transaction inserts the row. The first transaction’s subsequent INSERT ... ON CONFLICT DO NOTHING fails silently, potentially leading to a NULL return value unless looping logic is implemented to re-read or retry the insert.

Q: Should I use SELECT FOR UPDATE in the loop approach

ANS: Using FOR SHARE or FOR UPDATE in the initial SELECT guarantees locking the row if found, preventing concurrent deletion or modification. However, if the row is not found, it doesn’t prevent the race condition during the subsequent non-locked INSERT step; hence, looping remains essential for full protection against concurrent insertion attempts.

Q: Why does the pure SQL CTE approach fail under concurrency

ANS: The pure SQL approach fails because both the INSERT (via ON CONFLICT DO NOTHING) and the subsequent SELECT operate under the same PostgreSQL transaction snapshot. If a concurrent transaction inserts the required row but hasn’t committed, neither statement in the current transaction can see the new row, resulting in an empty result set.
