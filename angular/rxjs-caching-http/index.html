“RxJS Caching: Strategies for Efficient HTTP Request Handling”

When building modern web applications, efficiently managing HTTP requests is crucial for performance and user experience. A common pattern involves fetching data from an API and ensuring that subsequent requests for the same data do not trigger redundant network calls. This can be achieved through various caching strategies within RxJS, particularly when working with Angular. How can we implement effective caching for HTTP responses in RxJS to ensure a single request is made for repeated data fetches?

The core challenge lies in transforming a “cold” observable, which executes anew for each subscriber, into a “hot” observable that shares a single execution among multiple subscribers, effectively caching the result. Several RxJS operators and patterns address this.

Solution 1: Native shareReplay (Recommended for RxJS 5.4+)

The shareReplay operator, introduced in RxJS 5.4, is specifically designed for this purpose. It multicasts the source observable values to one or more ReplaySubject instances, allowing late subscribers to receive previously emitted values.

import { Injectable } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { Observable } from 'rxjs';
import { shareReplay } from 'rxjs/operators';

interface Customer {
  id: number;
  name: string;
}

@Injectable({
  providedIn: 'root'
})
export class CustomerService {
  private readonly customers$: Observable<Customer[]>;

  constructor(private http: HttpClient) {
    // The http.get observable is "cold" by default.
    // shareReplay(1) makes it "hot" and replays the last emitted value.
    this.customers$ = this.http.get<Customer[]>('/api/customers').pipe(
      shareReplay(1)
    );
  }

  getCustomers(): Observable<Customer[]> {
    return this.customers$;
  }
}

Explanation:

  • http.get('/api/customers'): This initiates a standard HTTP GET request, returning a cold observable.
  • .pipe(shareReplay(1)): This operator is applied to the observable.
    • shareReplay(1): This is the key. It ensures that only one underlying HTTP request is made. If multiple components subscribe to getCustomers(), they all receive the same observable stream. Crucially, if a component subscribes after the initial HTTP request has completed, shareReplay(1) will replay the last emitted value (the cached HTTP response) to that new subscriber without making another request.

Solution 2: publishReplay(1).refCount() (RxJS 5 Pre-shareReplay)

Before shareReplay was available, publishReplay(1).refCount() served a similar purpose.

import { Injectable } from '@angular/core';
import { Http } from '@angular/http'; // Note: Using older Http for demonstration if needed
import { Observable } from 'rxjs';
import 'rxjs/add/operator/publishReplay';
import 'rxjs/add/operator/refCount';

@Injectable()
export class OldCustomerService {
  private readonly customerObservable: Observable<any>;

  constructor(private http: Http) {
    // publishReplay(1) makes the observable multicasted and replays the last value.
    // refCount() manages the subscription lifecycle: connects when there's a subscriber, disconnects when none are left.
    this.customerObservable = this.http.get('/api/customers')
      .map((response: any) => response.json())
      .publishReplay(1)
      .refCount();
  }

  getCustomerData(): Observable<any> {
    return this.customerObservable;
  }
}

Explanation:

  • .publishReplay(1): This operator transforms the observable into a connectable observable that multicasts emissions from its source to its subscribers, replaying the latest value to new subscribers.
  • .refCount(): This operator automatically manages the connection and disconnection to the underlying observable. It connects when the first subscriber appears and disconnects when the last subscriber unsubscribes, helping to prevent memory leaks and unnecessary ongoing requests.

Solution 3: Manual Caching with ReplaySubject

A more manual but flexible approach involves using ReplaySubject directly to manage the cache. This gives fine-grained control over the caching mechanism.

import { Injectable } from '@angular/core';
import { Http } from '@angular/http';
import { Observable, ReplaySubject, Subscriber } from 'rxjs';
import 'rxjs/add/operator/map';

@Injectable()
export class ManualCacheService {
  private cache = new ReplaySubject<any>(1); // Buffer size of 1 caches the last emitted value
  private isFetching = false;

  constructor(private http: Http) {}

  fetchData(): Observable<any> {
    if (!this.isFetching) {
      this.isFetching = true;
      this.http.get('/api/data')
        .map(response => response.json())
        .subscribe(
          (data) => {
            this.cache.next(data); // Emit the fetched data to the ReplaySubject
            this.cache.complete(); // Mark the subject as complete after data is emitted
            this.isFetching = false;
          },
          (error) => {
            this.cache.error(error); // Emit error if fetching fails
            this.isFetching = false;
          }
        );
    }
    return this.cache.asObservable(); // Return the observable from the ReplaySubject
  }
}

Explanation:

  • ReplaySubject(1): A ReplaySubject can store a buffer of previous emissions. Setting the buffer size to 1 means it will only store the last emitted value.
  • When fetchData is called for the first time (!this.isFetching), it triggers the HTTP request.
  • The result of the HTTP request is piped to next() on the cache subject.
  • Subsequent calls to fetchData will find isFetching as true (or the data already emitted by the ReplaySubject) and directly return the cache.asObservable(), which will immediately provide the cached value.

Solution 4: Using sessionStorage or In-Memory Cache for Persistent Caching

For scenarios where you need the cache to persist across component re-initializations or even browser sessions (using sessionStorage), you can implement a dedicated caching service.

In-Memory Cache:

import { Injectable } from '@angular/core';
import { Http } from '@angular/http';
import { Observable, of } from 'rxjs';
import { map } from 'rxjs/operators';

@Injectable({
  providedIn: 'root'
})
export class HttpCacheService {
  private cache: { [key: string]: any } = {};

  constructor(private http: Http) {}

  get(url: string): Observable<any> {
    if (this.cache[url]) {
      console.log(`Cache HIT for ${url}`);
      return of(this.cache[url]); // Return cached data as an observable
    } else {
      console.log(`Cache MISS for ${url}, fetching...`);
      return this.http.get(url).pipe(
        map(response => {
          const data = response.json();
          this.cache[url] = data; // Store fetched data in the cache
          return data;
        })
      );
    }
  }

  clearCache(): void {
    this.cache = {};
  }
}

sessionStorage Cache (with limitations):

import { Injectable } from '@angular/core';
import { Http } from '@angular/http';
import { Observable, of } from 'rxjs';
import { map } from 'rxjs/operators';

@Injectable({
  providedIn: 'root'
})
export class SessionStorageCacheService {
  constructor(private http: Http) {}

  get(url: string): Observable<any> {
    const cachedItem = sessionStorage.getItem(url);
    if (cachedItem) {
      console.log(`sessionStorage HIT for ${url}`);
      return of(JSON.parse(cachedItem));
    } else {
      console.log(`sessionStorage MISS for ${url}, fetching...`);
      return this.http.get(url).pipe(
        map(response => {
          const data = response.json();
          sessionStorage.setItem(url, JSON.stringify(data)); // Store in sessionStorage
          return data;
        })
      );
    }
  }

  clearSessionCache(): void {
    sessionStorage.clear();
  }
}

Considerations for sessionStorage:

  • Size Limit: sessionStorage has a limited capacity (typically around 5MB), making it unsuitable for large datasets.
  • Browser Session: Data is only available for the duration of the browser session.

Solution 5: Using Decorators for Declarative Caching

Decorators can provide a more declarative way to implement caching. A decorator can wrap a method that performs an HTTP call, managing the caching logic behind the scenes.

import { Injectable } from '@angular/core';
import { Http } from '@angular/http';
import { Observable } from 'rxjs';
import 'rxjs/add/operator/publishReplay';
import 'rxjs/add/operator/connect';

// Decorator definition
export function CacheObservableArgsKey(target: Object, name: string, descriptor: PropertyDescriptor) {
  const originalMethod = descriptor.value;
  const cacheMap = new Map<string, Observable<any>>();

  descriptor.value = function(...args: any[]): Observable<any> {
    const key = JSON.stringify(args); // Create a cache key from arguments

    let cachedObservable = cacheMap.get(key);
    if (cachedObservable) {
      console.log(`Decorator Cache HIT for ${name} with key: ${key}`);
      return cachedObservable;
    }

    console.log(`Decorator Cache MISS for ${name} with key: ${key}, initiating request...`);
    const observable = originalMethod.apply(this, args)
      .publishReplay(1); // Use publishReplay for caching
    observable.connect(); // Manually connect to start the request

    cacheMap.set(key, observable);
    return observable;
  };
  return descriptor;
}

// Example Usage
@Injectable()
export class DecoratorService {
  constructor(private http: Http) {}

  @CacheObservableArgsKey
  getThingById(id: string): Observable<any> {
    return this.http.get(`/api/things/${id}`).map(res => res.json());
  }
}

Explanation:

  • The CacheObservableArgsKey decorator intercepts method calls.
  • It creates a unique key based on the method’s arguments.
  • If an observable for that key exists in cacheMap, it’s returned.
  • Otherwise, the original method is called, its observable is processed with publishReplay(1) and connect(), stored in the cacheMap, and then returned.

Solution 6: Using BehaviorSubject for State Management and Caching

BehaviorSubject can also be leveraged. It holds a value and emits it to new subscribers. By updating a BehaviorSubject with the results of an HTTP call, you can effectively cache the data.

import { Injectable } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { BehaviorSubject, Observable } from 'rxjs';
import { tap, catchError } from 'rxjs/operators';

interface User {
  id: number;
  name: string;
}

@Injectable({
  providedIn: 'root'
})
export class UserService {
  private usersSubject = new BehaviorSubject<User[]>([]);
  public users$: Observable<User[]> = this.usersSubject.asObservable();

  constructor(private http: HttpClient) {}

  loadUsers(): void {
    this.http.get<User[]>('/api/users')
      .pipe(
        tap(users => this.usersSubject.next(users)), // Update the BehaviorSubject with new data
        catchError(error => {
          console.error('Error loading users:', error);
          // Optionally emit an error or a default value
          // this.usersSubject.error(error);
          return []; // Return an empty array or handle error appropriately
        })
      )
      .subscribe(); // Subscribe to trigger the HTTP request
  }

  // Method to refresh data
  refreshUsers(): void {
      this.loadUsers();
  }
}

Usage:

Components can subscribe to userService.users$ to get the latest user data. Calling loadUsers() fetches new data and updates the BehaviorSubject.

FAQs on RxJS Caching HTTP Responses

Q: What is the primary benefit of caching HTTP responses in RxJS

ANS: The main advantage is performance optimization. By caching responses, you avoid making redundant network requests for data that has already been fetched, which saves bandwidth and reduces server load, leading to a faster and more responsive application.

Q: Which RxJS operator is best for caching HTTP responses in Angular

ANS: For RxJS versions 5.4 and later, shareReplay(1) is generally the most recommended operator. It effectively caches the last emitted value and replays it to late subscribers without making new HTTP requests. If you’re on an older RxJS version (prior to 5.4), publishReplay(1).refCount() is a suitable alternative.

Q: How does shareReplay(1) differ from share()

ANS: While share() makes an observable hot and allows multiple subscribers to share a single execution, it doesn’t replay values. If a subscriber subscribes after the observable has completed or an error occurred, it won’t receive any value. shareReplay(1), on the other hand, caches the last emitted value and replays it to any subsequent subscribers, making it ideal for caching.

Q: Can I cache API calls that require different parameters

ANS: Yes, you can. When using techniques like decorators or manual caching with Map objects, you can create unique cache keys based on the method arguments (e.g., by stringifying the arguments). This ensures that requests with different parameters are cached separately.

Q: How can I invalidate or refresh cached data

ANS: You can implement a refresh mechanism. This might involve creating a separate observable or subject that, when triggered (e.g., by a button click or an update operation), signals the caching logic to discard the old cache and fetch new data. For instance, using a CacheBuster decorator with ngx-cacheable or manually clearing a cache service property.

Q: What are the limitations of using sessionStorage for caching

ANS: sessionStorage has a limited storage capacity (typically around 5MB) and the data is only available for the duration of the browser session. It’s not suitable for large datasets or persistent caching across browser restarts. In-memory caches or more robust solutions are better for larger or more persistent caching needs.
