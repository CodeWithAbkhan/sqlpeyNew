“Firestore Text Search Strategies: Prefix, Substring, and Full-Text Querying Methods”

Cloud Firestore is a powerful NoSQL database, but it lacks native full-text search operators like LIKE %term% found in SQL databases. When dealing with string fields, developers often seek methods to implement prefix matching, substring containment, or more complex full-text searches. This discussion compiles various expert-suggested workarounds, ranging from leveraging Firestore’s inherent query capabilities to integrating external services.

How Can We Achieve Prefix Searching in Firestore?

Prefix searching—finding documents where a field starts with a specific query—is achievable using Firestore’s range operators (>= and <=) combined with a specific Unicode character.

Method 1: Utilizing the High Code Point Character (\uf8ff)

The character \uf8ff has a very high Unicode value. By setting the upper bound of a range query using this character appended to the search term, you effectively capture all strings beginning with that term.

For a collection reference collectionRef and a search text queryText, the implementation looks like this:

// Searching for records where 'name' starts with queryText
collectionRef
    .where('name', '>=', queryText)
    .where('name', '<=', queryText + '\uf8ff')
    .get();

This technique mirrors the functionality of using startAt() and endAt() with the tilde (~) character, which also acts as a high-value character for lexicographical sorting:

// Equivalent using startAt/endAt (often used in older Firebase Realtime Database patterns but applicable here)
ref.orderBy('title').startAt(term).endAt(term + '~');

Method 2: Using Range Filters with ‘z’ Suffix (Alternative for specific engines/SDKs)

In some SDK environments (like Flutter/Dart), appending ‘z’ to the upper bound can sometimes act as a practical boundary for ASCII/Latin characters when searching simple strings.

// Example using Dart/Flutter syntax
String search = "ca";
Firestore.instance.collection("categories")
    .orderBy("name")
    .where("name", isGreaterThanOrEqualTo: search)
    .where("name", isLessThanOrEqualTo: search + "z")
    .get();

Method 3: Combining Range Queries for Case Insensitivity (Firestore OR Queries)

If prefix searches need to handle mixed casing, the newer OR query feature can be leveraged to check for lowercase, uppercase, and original casing variants simultaneously.

// Conceptual representation using newer Firestore JS SDK features (check official docs for current implementation)
query(
  collection(DB, 'some/collection'),
  or(
    // Case 1: Original query string
    and(
      where('name', '>=', queryString),
      where('name', '<=', queryString + '\uf8ff')
    ),
    // Case 2: Capitalized first letter variant
    and(
      where('name', '>=', queryString.charAt(0).toUpperCase() + queryString.slice(1)),
      where('name', '<=', queryString.charAt(0).toUpperCase() + queryString.slice(1) + '\uf8ff')
    ),
    // Case 3: Lowercase variant
    and(
      where('name', '>=', queryString.toLowerCase()),
      where('name', '<=', queryString.toLowerCase() + '\uf8ff')
    )
  )
);

What Workarounds Exist for True Substring or Full-Text Search?

When the requirement moves beyond simple prefix matching to finding text within a field (substring search), the built-in operators fail. Several client-side pre-processing techniques or external services are necessary.

Workaround A: Storing All Substrings in an Array (array-contains)

This method involves pre-calculating every possible substring of a text field and storing them in an array field within the same document. A search query then checks if the desired search term exists in this array using array-contains.

Data Structure Example (Conceptual):

{
  "title": "Cloud Computing Basics",
  "titleSubstrings": [
    "c", "cl", "clo", "cloud", "l", "lo", "lou", "loud", 
    // ... all other substrings
    "computing", "basics"
  ]
}

Query Example (Conceptual JS):

// Searching for "cloud"
collectionRef
    .where("titleSubstrings", "array-contains", "cloud")
    .get();

Considerations:

  1. Document Size: For long texts (like paragraphs), this can rapidly exceed Firestore’s 1MB document limit, as seen when testing methods like Ken Tan’s approach.
  2. Indexing: This requires an index on the titleSubstrings array field.

A similar, but often more manageable, approach is generating Trigrams (groups of three consecutive characters) and using array-contains-any if the search term is short.

Workaround B: Storing Search Keywords in a Map (==)

For searching discrete, known keywords, you can store them as keys in a map, setting their value to true.

Data Structure Example:

{
  "searchKeywordsMap": {
    "reebok": true,
    "mens": true,
    "tennis": true,
    "racket": true
  }
}

Query Example (JavaScript):

// Search for documents containing the exact term 'tennis'
collectionRef.where('searchKeywordsMap.tennis', '==', true);

Limitation: This requires an index for every unique search term if you combine this query with other conditions (like status === "active"). This makes it impractical for open-ended user input searches.

Workaround C: Client-Side Filtering After Initial Fetch

For small collections or very simple searches, you can retrieve a larger set of relevant documents (perhaps using a prefix query) and then apply complex contains() filtering on the client side.

Example (Kotlin/Android with client-side check):

firestoreDB.collection("products")
    .get().addOnCompleteListener { task ->
        if (task.isSuccessful){
            val document = task.result
            if (document != null && !document.isEmpty) {
                for (documents in document) {
                    val name = documents.getString("name")
                    val type = documents.getString("type")
                    if (name != null && type != null) {
                        // Client-side substring check
                        if (name.contains(text, ignoreCase = true) || type.contains(text, ignoreCase = true)) {
                            // Process matching document
                        } else {
                            showNoProductsMsg()
                        }
                    }
                }
                binding.progressBarSearch.visibility = View.INVISIBLE
            } else {
                showNoProductsMsg()
            }
        } else {
            showNoProductsMsg()
        }
    }

Major Drawback: This scales poorly. You pay for reads of all documents fetched, even if most are discarded client-side, violating best practices for large datasets.

Workaround D: Creating Reversed Fields for Suffix Search

To support searching for the end of a string, you can maintain a second, reversed version of the field (e.g., titleRev). You then execute two prefix searches—one on the original field and one on the reversed field—and merge the results client-side.

async function searchTitle(term) {
  // Reverse the search term
  const termR = term.split("").reverse().join("");

  // Define queries for forward and reverse text
  const titles = postRef.orderBy('title').startAt(term).endAt(term + '~').get();
  const titlesR = postRef.orderBy('titleRev').startAt(termR).endAt(termR + '~').get();

  const [titleSnap, titlesRSnap] = await Promise.all([
    titles,
    titlesR
  ]);
  // Combine and de-duplicate results
  return (titleSnap.docs).concat(titlesRSnap.docs);
}

Recommended Production Solutions

For applications requiring robust, flexible text search functionality, external dedicated search engines are typically the superior path, avoiding Firestore limitations and excessive read costs.

  1. Algolia or ElasticSearch: These services are built specifically for high-performance text indexing and searching. Firebase offers official extensions to synchronize Firestore data directly into Algolia, streamlining implementation. See Algolia documentation for details .
  2. Typesense: An open-source alternative that integrates well with Firebase Cloud Functions for real-time synchronization and provides excellent substring search capabilities.
  3. External Databases with Free Tiers: Utilizing services like PostgreSQL or MySQL on Google Cloud (GCP) via Cloud Functions for data synchronization provides full SQL search capabilities while keeping initial costs low.

Leveraging Firebase Extensions

Google provides the Firestore Algolia Search Extension, which automatically keeps your Algolia index updated when documents change in Firestore. This is the recommended path for production systems prioritizing speed and rich features over cost management for search.

FAQs on Firestore Text Search Strategies

Q: Can Firestore directly search for strings containing a term like SQL LIKE

ANS: No, Firestore does not support native substring searching (i.e., field LIKE '%term%'). You must use workarounds like pre-calculating all substrings, using external search engines, or relying on prefix matching.

Q: Is the \uf8ff character reliable for prefix searches

ANS: Yes, the \uf8ff character, due to its high Unicode value, reliably creates an inclusive upper bound when combined with range operators (>=, <=) for prefix matching in Firestore string fields.

Q: What is the main constraint when storing all substrings in an array

ANS: The primary constraint is the 1MB document size limit in Firestore. Storing every possible substring for long text fields can quickly exceed this limit.

Q: Does using array-contains on a keyword map require manual indexing for every search term

ANS: If you combine a query using where('mapField.term', '==', true) with another inequality or range filter, Firestore often requires a specific composite index for that term combination, making dynamic searches difficult without external tooling.

Q: Can I search across multiple fields with prefix queries simultaneously

ANS: Standard Firestore queries restrict range filters (>=, <=) to a single field per query. To search multiple fields, you typically need multiple parallel queries (one for each field) and merge the results client-side, or use newer OR query features if available and applicable.
