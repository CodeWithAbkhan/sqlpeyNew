“Fixing Firebase FCM onMessageReceived Not Triggering in Background or Killed States”

This breakdown presents several proven strategies to achieve consistent message handling.

The Core Distinction: Notification vs. Data Messages

Firebase provides two primary message types, and their handling differs significantly based on the app state:

  1. Notification Messages (Display Messages):

    • These messages contain a notification payload.
    • Foreground App: onMessageReceived() is called, and your app handles the message.
    • Background/Killed App: The operating system handles the display, showing the message in the system tray. The onMessageReceived() method is not called, and custom data in the data block is inaccessible via this method. Tapping the system notification launches the launcher activity, and data must be retrieved via getIntent().getExtras().

  2. Data Messages:

    • These messages contain only a data payload (no top-level notification block).
    • Foreground/Background/Killed App: onMessageReceived() is always triggered, allowing your app to process the data payload directly.

Strategies for Reliable Data Retrieval

Several approaches exist to circumvent the background limitations imposed on standard Notification messages.

Strategy 1: Utilize Data Messages Exclusively (Recommended for Custom Handling)

The most direct method is to send only Data Messages. When only the data block is present, onMessageReceived() is executed consistently, whether the app is foregrounded or backgrounded/killed.

If you need a visible notification while in the background, you must construct it manually within onMessageReceived() using the data payload (Solution 5 and 7 illustrate this).

Server Payload Example (Data Message Only):

{
  "data": {
    "id": "101",
    "action_type": "update_ui",
    "payload_detail": "Check this important data"
  },
  "to": "fcm_device_token_here",
  "priority": "high" 
}

Retrieval in Java:

@Override
public void onMessageReceived(RemoteMessage message) {
    Map<String, String> data = message.getData();
    if (data.size() > 0) {
        String action = data.get("action_type");
        if ("update_ui".equals(action)) {
            String detail = data.get("payload_detail");
            // Manually build and display notification or process data
            displayCustomNotification(data.get("title"), detail); 
        }
    }
}

Note on Priority: Data messages are sometimes sent with normal priority, potentially delaying arrival. Including "priority": "high" (as shown in the example above) can help ensure faster delivery for data-only messages (Solution 2).

Strategy 2: Combining Notification and Data Payloads for Background Tapping

If the server must send a notification block (for default tray display), you can include a data block as well.

  • Background State: The system displays the notification from the notification block. When the user taps it, the main launcher activity starts, and the custom data from the data block is available in the launch intent’s extras (Solution 4, 13, 28).
  • Foreground State: onMessageReceived() handles both payloads.

Combined Server Payload Example:

{
 "notification": {
    "title": "System Alert",
    "body": "Tap to see details.",
    "click_action": "LAUNCH_CUSTOM_ACTIVITY" 
 },
 "data": {
    "custom_data_key": "payload_for_app_foreground",
    "activity_to_launch": "NotificationActivity",
    "user_id": "9988"
 },
 "to": "device_token_xyz"
}

Retrieval in Launched Activity (e.g., MainActivity.onCreate):

If the app was backgrounded and the notification was tapped, retrieve the data from the intent extras:

@Override
protected void onCreate(Bundle savedInstanceState) {
    super.onCreate(savedInstanceState);
    
    if (getIntent().getExtras() != null) {
        Log.d("FCM_DATA", "Data received from background click:");
        for (String key : getIntent().getExtras().keySet()) {
            Object value = getIntent().getExtras().get(key);
            Log.d("FCM_DATA", "Key: " + key + " Value: " + value);
            
            // Access specific data sent in the 'data' block
            if (key.equals("user_id") && value != null) {
                // Handle user_id retrieval
            }
        }
    }
    // ... rest of onCreate
}

If click_action is set (e.g., to LAUNCH_CUSTOM_ACTIVITY), the system launches the activity specified by that action, and the extras are attached to that intent (Solution 6). If no click_action is set, the main launcher activity receives the extras (Solution 1).

Strategy 3: Manually Re-routing the Intent in FirebaseMessagingService

A more advanced technique involves overriding the service’s internal intent handling to force all messages (regardless of type) through onMessageReceived(). This requires overriding handleIntent(Intent intent) in your service extending FirebaseMessagingService. This re-packages the intent extras into a RemoteMessage object (Solutions 10, 12, 15, 30).

Kotlin Implementation (Overriding handleIntent):

import com.google.firebase.messaging.FirebaseMessagingService
import com.google.firebase.messaging.RemoteMessage

class CustomFCMService : FirebaseMessagingService() {

    override fun handleIntent(intent: Intent) {
        try {
            val extras = intent.extras
            if (extras != null) {
                val builder = RemoteMessage.Builder("CustomFCMService")
                
                // Reconstruct RemoteMessage from Intent extras
                for (key in extras.keySet()) {
                    key?.let {
                        extras.get(key)?.let { value ->
                            builder.addData(it, value.toString())
                        }
                    }
                }
                
                // Manually invoke onMessageReceived with the built message
                onMessageReceived(builder.build())
            } else {
                super.handleIntent(intent)
            }
        } catch (e: Exception) {
            super.handleIntent(intent)
        }
    }

    override fun onMessageReceived(remoteMessage: RemoteMessage) {
        // Your standard message processing logic here for all states
        if (remoteMessage.data.isNotEmpty()) {
            println("Data payload received: ${remoteMessage.data}")
        }
        // ... custom notification logic if needed
    }
}

Prerequisite: Ensure you are using a sufficiently recent version of com.google.firebase:firebase-messaging (e.g., 10.2.1 or newer) for this override to function reliably (Solution 15).

Data Message Handling Specifics

When using Data Messages, developers sometimes miss the required parameter naming for standard notification fields if they still desire those attributes to be processed or visualized (Solution 16). While the system doesn’t automatically build a tray notification, if you are building your own (Solution 5, 7), be mindful of which keys you use for titles and bodies within the data block, as the system doesn’t look for the standard notification.title key when processing a pure data message.

For instance, if using a data-only payload, use keys like "text" or custom keys in the data block, and retrieve them programmatically (Solution 16).

Handling Default Notification Clicks on Backgrounded App

When the app is backgrounded or killed, tapping the default system tray notification launches the main launcher activity. If you are relying on the default behavior (i.e., not using a custom click_action or using a Data Message), the payload data resides in the launching activity’s intent extras (Solution 8, 25). Always check getIntent().getExtras() != null in onCreate() or onResume() of your primary activity (Solution 14).

FAQs on FCM Message Handling

Q: Why does onMessageReceived not run when my Android app is closed

ANS: When the app is closed or backgrounded, Firebase Cloud Messaging defaults to displaying Notification Messages via the operating system tray. Only Data Messages or Notification Messages sent while the app is foregrounded trigger onMessageReceived().

Q: How to make onMessageReceived always trigger

ANS: Send the payload containing only a data block (a Data Message), completely omitting the top-level notification block. Ensure you include "priority": "high" for faster delivery.

Q: What happens if I send both notification and data payloads

ANS: If the app is in the background, the system shows the notification tray item. onMessageReceived is skipped. Tapping the notification launches the launcher activity, and custom data is found in getIntent().getExtras() of that activity.

Q: Where do I retrieve data if the app was killed and the user tapped the notification

ANS: Check the Bundle returned by getIntent().getExtras() within the onCreate() method of your main/launcher activity.

Q: Can I force my custom notification logic in the background

ANS: Yes, by sending a Data Message only, you can implement custom notification building logic inside onMessageReceived(), which runs even when the app is backgrounded or killed (Solution 5).
