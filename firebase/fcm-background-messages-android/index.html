“FCM Data vs Notification: Handling Background Messages in Android”

Firebase Cloud Messaging (FCM) offers two primary message types: Display Messages and Data Messages. Understanding their behavior is crucial for effective notification handling.

Display Messages vs. Data Messages

  • Display Messages: These messages trigger the onMessageReceived() callback only when your app is in the foreground. When the app is in the background or killed, FCM handles displaying these messages directly in the system tray.
  • Data Messages: These messages trigger the onMessageReceived() callback irrespective of your app’s state (foreground, background, or killed). This makes them ideal for custom handling and logic execution when a notification arrives.

It’s important to note that the Firebase console currently does not provide a direct UI for sending data-only messages. You will typically need to use your server-side application or an HTTP POST request to send these messages.

Sending Data Messages via HTTP POST

To send data messages, you can perform a POST request to the FCM endpoint.

URL: https://fcm.googleapis.com/fcm/send

Headers:

  • Content-Type: application/json
  • Authorization: key=<your-server-key>

You can find your server key in your Firebase project settings under “Cloud Messaging.”

Body (using topics):

{
    "to": "/topics/my_topic",
    "data": {
        "customKey": "customValue",
        "anotherKey": true
     }
}

Body (for specific devices):

{
    "data": {
        "customKey": "customValue",
        "anotherKey": true
     },
    "registration_ids": ["{device-token}","{device2-token}","{device3-token}"]
}

Important Note: When sending data messages to ensure onMessageReceived is triggered in all app states, do not include the JSON key notification in your request body.

Handling Received Messages in Android

The way you handle received FCM messages depends on your app’s state and the payload you’ve sent.

App in Foreground

When your app is in the foreground, the onMessageReceived(RemoteMessage remoteMessage) method within your FirebaseMessagingService will be invoked. You can retrieve the data payload as a Map<String, String>:

@Override
public void onMessageReceived(RemoteMessage remoteMessage) {
    super.onMessageReceived(remoteMessage); // Important for some Firebase versions

    Map<String, String> data = remoteMessage.getData();
    if (data.size() > 0) {
        String customValue = data.get("customKey");
        Log.d("FCM", "Custom data value: " + customValue);
        // Process your custom data here
    }
}

App in Background or Killed

When your app is in the background or has been killed, FCM typically displays the notification in the system tray. To process the data payload when the user taps the notification, you need to configure your Android application correctly.

Method 1: Using data payload with click_action (Recommended for custom handling)

By sending a message with only a data payload (and no notification payload), the data will be delivered to the extras of the intent for your launcher Activity when the app is in the background. You can then extract this data in your Activity’s onCreate() or onNewIntent() methods.

To achieve a more direct handling or to launch a specific activity, you can include a click_action in the notification payload. This tells FCM which activity to launch when the notification is tapped.

  1. Manifest Configuration: Define an intent filter for the activity you want to handle the notification.

    <activity android:name=".MainActivity">
    <intent-filter>
        <action android:name="OPEN_SPECIFIC_ACTIVITY" />
        <category android:name="android.intent.category.DEFAULT" />
    </intent-filter>
</activity>

  2. Sending the Message (using click_action):

    {
  "to": "/topics/my_topic",
  "notification": {
    "title": "New Update Available",
    "body": "Check out the latest features!",
    "icon": "ic_notification",
    "click_action": "OPEN_SPECIFIC_ACTIVITY"
  },
  "data": {
    "featureId": "update123",
    "version": "2.0"
  }
}

  3. Handling in Activity:

    @Override
protected void onCreate(Bundle savedInstanceState) {
    super.onCreate(savedInstanceState);
    setContentView(R.layout.activity_main);

    handleIntent(getIntent());
}

@Override
protected void onNewIntent(Intent intent) {
    super.onNewIntent(intent);
    handleIntent(intent);
}

private void handleIntent(Intent intent) {
    if (intent != null && intent.getExtras() != null) {
        Bundle extras = intent.getExtras();
        if (extras.containsKey("featureId")) {
            String featureId = extras.getString("featureId");
            String version = extras.getString("version");
            Log.d("FCM", "Feature ID: " + featureId + ", Version: " + version);
            // Process the featureId and version
        }
    }
}

Method 2: Sending only data payload

If you send only a data payload, the onMessageReceived method will be called regardless of the app’s state. However, if the app is killed, the notification might not be displayed by default without additional handling.

To ensure that onMessageReceived is called even when the app is killed, and to process data messages, you should send a message with only the data field.

Example Payload (Data Only):

{
    "to": "/topics/my_topic",
    "data": {
        "message": "Your custom message content",
        "title": "Notification Title",
        "specialFlag": "true"
     }
}

Handling in FirebaseMessagingService:

Your onMessageReceived method will receive this data. If the app is killed, you might need to manually create and display a notification within onMessageReceived if you want it to appear in the system tray.

@Override
public void onMessageReceived(RemoteMessage remoteMessage) {
    super.onMessageReceived(remoteMessage); // Crucial for some Firebase versions

    if (remoteMessage.getData().size() > 0) {
        Map<String, String> data = remoteMessage.getData();
        String message = data.get("message");
        String title = data.get("title");
        String specialFlag = data.get("specialFlag");

        Log.d("FCM", "Received data: Message=" + message + ", Title=" + title + ", Flag=" + specialFlag);

        // If the app is killed, you might need to create a notification manually here
        // to display it in the system tray.
        if (!isAppInForeground(this)) { // You'll need a helper to check app state
            showNotification(title, message);
        }
    }
}

Note on handleIntent: Some older versions of Firebase might provide a handleIntent(Intent intent) method. If your firebase-messaging dependency is older (e.g., 10.2.1), this method might be available and called for all messages. However, relying on onMessageReceived and explicit data payload handling is the more current and recommended approach.

Server Key Authorization (OAuth 2.0)

For newer FCM implementations, especially when using server-side SDKs or direct HTTP calls, you might need to use OAuth 2.0 for authentication. This involves obtaining a service account key (JSON file) and using it to generate access tokens.

Example using Node.js:

const admin = require('firebase-admin');
const serviceAccount = require('./path/to/your/serviceAccountKey.json');

admin.initializeApp({
  credential: admin.credential.cert(serviceAccount)
});

const message = {
  notification: {
    title: 'New Message!',
    body: 'Check out this update.'
  },
  data: {
    customDataKey: 'customValue'
  },
  token: 'DEVICE_REGISTRATION_TOKEN' // Target device's token
};

admin.messaging().send(message)
  .then((response) => {
    console.log('Successfully sent message:', response);
  })
  .catch((error) => {
    console.log('Error sending message:', error);
  });

You can also use tools like curl or Postman with the appropriate Authorization: Bearer <YOUR_ACCESS_TOKEN> header for direct API calls.

Considerations for Specific Scenarios

  • Battery Optimization: Some device manufacturers include aggressive battery optimization features that might prevent background app processes, including FCM message handling. Ensure your app is not overly restricted by these settings on target devices.
  • Firebase Console Limitations: As mentioned, the Firebase console is primarily for sending display messages or messages with both notification and data payloads. For precise control over data-only messages, server-side implementation is necessary.
  • launchMode="singleTop": If your launcher activity has android:launchMode="singleTop", receiving a notification while the app is in the background will typically call onNewIntent() on that activity, where you can retrieve extras.

Testing

When testing, it’s crucial to send messages that align with your intended handling strategy:

  • To test onMessageReceived for background/killed states: Send messages with only a data payload.
  • To test system tray display and launch behavior: Send messages with both notification and data payloads, or use the Firebase Console. Include click_action if you want to direct the user to a specific activity.

FAQs on FCM Data vs Notification Handling in Android

Q Firebase notification payloads work differently when my app is in background or killed

ANS: When your app is in the background or killed, FCM delivers notification messages to the system tray. Data messages, or messages with both notification and data payloads, send the data to your launcher Activity’s extras. To process this data, you typically need to check getIntent().getExtras() in your launcher Activity’s onCreate() or onNewIntent() methods. Using a click_action in the payload helps direct this to a specific activity. For guaranteed onMessageReceived callback in all states, send only a data payload.

Q How to send data messages to FCM

ANS: You can send data messages via an HTTP POST request to https://fcm.googleapis.com/fcm/send. Ensure your request body contains only the "data" field and not the "notification" field. The headers should include Content-Type: application/json and Authorization: key=<your-server-key>.

Q What is the difference between FCM display messages and data messages

ANS: Display messages trigger onMessageReceived only when the app is in the foreground. Data messages trigger onMessageReceived regardless of the app’s state (foreground, background, or killed).

Q How do I get FCM data when my Android app is killed

ANS: When your app is killed and a notification is tapped, the data is delivered to the extras of the intent for your launcher Activity. You must access these extras in the onCreate() method of that activity. If you want to handle the message directly without relying on the system tray’s default behavior, consider sending a data-only message and manually creating a notification within onMessageReceived.

Q Can I use the Firebase console to send data-only messages

ANS: The Firebase Console is primarily designed for sending messages with a notification payload, which FCM displays directly. For sending only data payloads, you will typically need to use your server-side application or the FCM API via HTTP POST requests.

Q What is click_action in FCM payloads

ANS: click_action is a field within the notification payload that specifies an action to be performed when the user taps the notification. This action can be an Android Intent action, allowing you to launch a specific Activity or perform a custom task. It’s particularly useful for directing background message handling.
