Firebase Security Rules: Preventing Enumeration While Allowing Selective Data Access

The initial approach of placing a blanket .read: true under a top-level collection, like "nominations", overrides all subsequent restrictive rules on its children. Firebase security rules operate on an “allow if any rule allows” basis; if one rule grants read access to a location, all data beneath that location becomes readable, irrespective of lower-level restrictions.

To achieve granular control—allowing record creation while segmenting visibility (public vs. private data) and controlling enumeration—a common and robust pattern involves separating the data into distinct paths or lists.

Recommended Structure: Three Separate Lists

Instead of storing everything in one large node and relying on complex, potentially leaky rules, segment the data into three distinct locations:

  1. nominations: Stores the actual, complete nomination records, indexed by a unique ID ($id).
  2. approved_list: A lightweight list containing only the IDs of nominations visible to everyone.
  3. pending_list: A lightweight list containing IDs of nominations awaiting moderation, visible only to authenticated users.

This structure avoids direct enumeration of the main nominations collection while using the lightweight lists for controlled access and visibility.

Proposed Security Ruleset

This ruleset enforces creation by anyone but granular read permissions:

{
  "rules": {
    // 1. The core nomination data store
    "nominations": {
      "$id": {
        // Allow creation, prevent overwriting existing records
        ".write": "!data.exists()", 
        "public_data": {
          // Data visible to everyone
          ".read": true 
        },
        "phone": {
          // Sensitive data visible only if authenticated
          ".read": "auth != null" 
        }
      }
    },
    // 2. List for publicly visible approved nominations
    "approved_list": {
      ".read": true, // Allows public enumeration of this list's keys
      "$id": {
        // Only authenticated users can mark an ID as approved, provided the original nomination exists.
        ".write": "auth != null && root.child('nominations').child($id).exists() && newData.val() == true"
      }
    },
    // 3. List for nominations awaiting authentication review
    "pending_list": {
      ".read": "auth != null", // Only authenticated users see what is pending
      "$id": {
        // Any user can signal intent to create (set true); authenticated users can delete (moderate).
        ".write": "root.child('nominations').child($id).exists() && (newData.val() == true || auth != null)"
      }
    }
  }
}

Practical Application Workflow

1. Submitting a New Nomination (Unauthenticated User):

A user creates the full record and immediately flags it as pending:

// Assume 'ref' is the Firebase Database reference
const nominationRef = ref.child('nominations').push();
const nominationId = nominationRef.key;

// Set the actual data (phone remains private due to rules)
nominationRef.set({ 
    public_data: "Project Idea Submission", 
    phone: "555-1234" 
});

// Add ID to the pending list (validated by pending_list write rule)
ref.child('pending_list').child(nominationId).set(true);

2. Approving a Nomination (Authenticated Moderator):

An admin user removes the record from pending review and moves it to the approved list:

const nominationIdToApprove = "the_id_from_the_pending_list";

// Remove from pending queue
ref.child('pending_list').child(nominationIdToApprove).remove();

// Add ID to the approved queue (validated by approved_list write rule)
ref.child('approved_list').child(nominationIdToApprove).set(true);

3. Reading Approved Data (Public Enumeration):

To display the list of approved nominations publicly, you read the approved_list. Since this list only contains IDs, you must perform a secondary read to fetch the public data associated with each ID from the main nominations node.

// Client-side JavaScript example for reading approved public data
ref.child('approved_list').on('child_added', function(snapshot) {
  const nominationId = snapshot.name();
  
  // Fetch the public data portion of the actual record
  ref.child('nominations').child(nominationId).child('public_data').on('value', function(dataSnapshot) {
    console.log("Approved Public Data:", dataSnapshot.val());
  });
});

This mechanism achieves the goal: the main nominations node is not directly enumerable, only specific, approved IDs are visible via approved_list to the public, and sensitive fields like phone remain protected.

Alternative Structure: Public and Private Children

Another concept, often simpler if ownership isn’t strictly defined by the ID, involves structuring data inside the record itself using public/private prefixes:

{
  "rules": {
    "nominations": {
      "$id": {
        // ... write rules remain ...
        "public": {
          ".read": true // Everyone sees this
        },
        "private": {
          ".read": "auth != null" // Only logged-in users see this
        }
      }
    }
  }
}

However, this structure still faces enumeration difficulties. If you must allow enumeration of all nominations (approved or not), and only restrict reading the private data, you might still need the list pattern above, as a public read on $id grants access to both public and private nodes unless the rule structure is carefully layered—which often leads back to the list separation technique being superior for preventing enumeration entirely.

A major pitfall to avoid is when using nested structures like the second suggestion: if you set .read: true on the main nomination node ("nominations": { ".read": true }), then all records, including their private children, are exposed, violating the security objective. This reinforces the Firebase guidance: Security rules are permission gates, not data filters. You must structure your data so that the permission structure aligns with the desired visibility.

FAQs on Firebase Security Rules Enumeration Control

Q: What happens if I set .read true on the parent node of nominations

ANS: Setting a .read: true rule on a parent node, such as nominations, grants read access to every child node beneath it, regardless of any more restrictive rules defined deeper in the structure. Access is granted if any rule allows it.

Q: Can I use security rules to filter query results dynamically

ANS: No, security rules cannot filter results from a query (like orderByChild or limitToFirst). They only determine if a read operation to a specific path is permitted. If you read a path, you get all the data at that path permitted by the rules.

Q: Why use separate approved and pending lists

ANS: Using separate lists allows you to control enumeration easily. The public can read approved_list (which is small and only contains keys), but they cannot read the main nominations collection, thus preventing them from listing all submissions.
{
  "rules": {
    // The actual nominations.  Each will be stored with a unique ID.
    "nominations": {
      "$id": {
        ".write": "!data.exists()", // anybody can create new nominations, but not overwrite existing ones.
        "public_data": {
          ".read": true // everybody can read the public data.
        },
        "phone": {
          ".read": "auth != null", // only authenticated users can read the phone number.
        }
      }
    },
    "approved_list": {
      ".read": true, // everybody can read the approved nominations list.
      "$id": {
        // Authenticated users can add the id of a nomination to the approved list 
        // by creating a child with the nomination id as the name and true as the value.
        ".write": "auth != null &amp;&amp; root.child('nominations').child($id).exists() &amp;&amp; newData.val() == true"
      }
    },
    "pending_list": {
      ".read": "auth != null", // Only authenticated users can read the pending list.
      "$id": {
        // Any user can add a nomination to the pending list, to be moderated by
        // an authenticated user (who can then delete it from this list).
        ".write": "root.child('nominations').child($id).exists() &amp;&amp; (newData.val() == true || auth != null)"
      }
    }
  }
}
var id = ref.child('nominations').push({ public_data: "whatever", phone: "555-1234" });
ref.child('pending_list').child(id).set(true);
ref.child('pending_list').child(id).remove();
ref.child('approved_list').child(id).set(true);
ref.child('approved_list').on('child_added', function(childSnapshot) {
  var nominationId = childSnapshot.name();
  ref.child('nominations').child(nominationId).child('public_data').on('value', function(nominationDataSnap) {
    console.log(nominationDataSnap.val());
  });
});
