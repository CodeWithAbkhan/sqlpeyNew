“Solved: How to Use INT 0x80 System Calls from 64-Bit Linux”

The int 0x80 instruction, historically the primary mechanism for invoking system calls in 32-bit x86 Linux, can still be utilized from 64-bit user-space. However, this approach comes with specific behaviors and limitations that are crucial to grasp for successful implementation. This guide delves into the mechanics of int 0x80 when called from a 64-bit context, offering practical insights and a detailed example.

How INT 0x80 Works in 64-Bit Linux

When int 0x80 is executed in a 64-bit process, it interacts with the Linux kernel through a compatibility layer. The kernel dispatches these calls using a table of function pointers, similar to how 32-bit processes operate.

Key Behaviors:

  • System Call Number: The system call number is passed in the lower 32 bits of the RAX register (i.e., EAX).
  • Argument Passing: Only the lower 32 bits of general-purpose registers (RBX, RCX, RDX, RSI, RDI, RBP) are used for passing arguments. The upper 32 bits of these registers are preserved but ignored by the system call handler.
  • Register Preservation and Zeroing: The kernel saves and restores most registers, including RFLAGS and the upper halves of integer registers. However, R8 through R11 are consistently zeroed by the int 0x80 mechanism.
  • Return Value: The system call’s return value is sign-extended to fill the 64-bit RAX register. For pointer return values, this means zero-extension is necessary for correct 64-bit interpretation.
  • Compatibility Mode: The kernel entry point for int 0x80 from 64-bit processes is typically entry_INT80_compat in arch/x86/entry/entry_64_compat.S. This entry point ensures that 32-bit system calls are handled correctly within the 64-bit kernel environment.
  • Error Handling: Passing invalid pointers to system calls via int 0x80 typically results in an -EFAULT error, returned in RAX. It’s imperative to check these return values to prevent silent failures.

Limitations and Considerations:

  • 32-Bit Addressability: int 0x80 is inherently limited to 32-bit arguments. This means pointers must fit within 32 bits. Code that relies on addresses outside the 32-bit range, such as position-independent executables (PIE) with modern ASLR, may encounter issues.
  • WSL1 and Kernel Configuration: Not all environments support int 0x80. Windows Subsystem for Linux version 1 (WSL1) is strictly 64-bit and does not support int 0x80. Similarly, Linux kernels can be compiled without IA-32 emulation, disabling 32-bit executables and system calls. Ensure your system is using WSL2 if you are in a WSL environment.
  • strace Decoding: Older versions of strace might incorrectly decode int 0x80 calls made from 64-bit processes, potentially misinterpreting the system call arguments. Newer versions (e.g., Linux kernel 5.5 / strace 5.5 and later) provide more accurate decoding.

Practical Example: Using INT 0x80 from 64-Bit Assembly

The following NASM assembly code demonstrates invoking the write and exit system calls using int 0x80 from a 64-bit process. It highlights the correct usage of 32-bit registers for arguments and showcases the behavior of register zeroing.

; File: abi32_from_64.asm

section .data
    hello_msg db "Hello World!", 0xa
    hello_len equ $ - hello_msg

section .text
    global _start

_start:
    ; Initialize registers with distinct upper 32 bits to observe zeroing
    mov rax, 0x123456789abcdef
    mov rbx, rax
    mov rcx, rax
    mov rdx, rax
    mov rsi, rax
    mov rdi, rax
    mov rbp, rax
    mov r8, rax
    mov r9, rax
    mov r10, rax
    mov r11, rax
    mov r12, rax
    mov r13, rax
    mov r14, rax
    mov r15, rax

    ;
