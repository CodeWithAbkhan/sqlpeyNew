“How to Invoke System Calls: A Deep Dive into x86 Assembly Calling Conventions”

System calls are the fundamental interface between user-space programs and the operating system kernel. Understanding how these calls are made, particularly at the assembly level, is crucial for low-level programming, reverse engineering, and performance optimization. This post delves into the intricacies of system call and function calling conventions on x86-32 and x86-64 architectures, providing detailed explanations and practical examples.

The Mechanics of System Calls: x86 Architectures

The way system calls are invoked and parameters are passed varies significantly between different x86 architectures and operating systems. We’ll examine the conventions used by Linux and BSD variants.

x86-32 Linux System Call Convention

On x86-32 Linux, system calls are primarily initiated using the int $0x80 instruction.

  • System Call Number: Placed in the %eax register.
  • Arguments: The first six arguments are passed through the following registers in order: %ebx, %ecx, %edx, %esi, %edi, and %ebp.
  • Return Value: The result of the system call is returned in the %eax register.
  • Register Preservation: All registers other than %eax are preserved across an int $0x80 interrupt.
  • More Than Six Arguments: If a system call requires more than six arguments, the %ebx register must contain the memory address of a list where these arguments are stored. However, this scenario is uncommon.

A Faster Alternative: sysenter

A more performant method for 32-bit system calls is the sysenter instruction. This leverages the kernel’s virtual dynamically shared object (vDSO), which maps a page of memory into user space. This vDSO facilitates the sysenter operation, coordinating with the kernel to find the correct return address. The argument-to-register mapping remains the same as with int $0x80. It’s generally recommended to call into the vDSO rather than using sysenter directly.

x86-32 [Free|Open|Net|DragonFly]BSD UNIX System Call Convention

BSD-based Unix systems adopt a different approach for x86-32 system calls:

  • Arguments: Parameters are pushed onto the stack in reverse order (last parameter first).
  • System Call Invocation: After pushing arguments, a 32-bit value (which is not truly dummy data, but rather specific to the convention) is pushed, followed by the int $0x80 instruction.

For a deeper dive into this convention, refer to the BSD Assembly documentation .

x86-64 Linux System Call Convention

The x86-64 architecture, particularly on Linux, employs the syscall instruction for system calls. This method is generally more efficient than its 32-bit counterparts.

  • System Call Number: Placed in the %rax register.
  • Arguments: The first six arguments are passed through the following registers in order: %rdi, %rsi, %rdx, %rcx, %r8, and %r9.
  • Return Value: The system call result is returned in the %rax register. A return value in the range of -4095 to -1 signifies an error, represented as -errno.
  • Registers Clobbered: The syscall instruction affects %rcx and %r11 (which stores saved rflags) in addition to %rax. Other registers are preserved.
  • Argument Limits: System calls are limited to six arguments; no arguments are passed directly on the stack.

Important Note: The 32-bit int $0x80 ABI is usable in 64-bit code but is highly not recommended. It truncates inputs to 32-bit, making it unsuitable for pointers, and it zeros out registers %r8 through %r11.

Kernel Interface Details:

The Linux kernel source code in arch/x86/entry/entry_64.S provides specific insights:

/*
 * 64-bit SYSCALL instruction entry. Up to 6 arguments in registers.
 * ...
 * Registers on entry:
 * rax  system call number
 * rcx  return address
 * r11  saved rflags (note: r11 is callee-clobbered register in C ABI)
 * rdi  arg0
 * rsi  arg1
 * rdx  arg2
 * r10  arg3 (needs to be moved to rcx to conform to C ABI)
 * r8   arg4
 * r9   arg5
 */

And for the 32-bit sysenter:

/*
 * 32-bit SYSENTER entry.
 * ...
 * Arguments:
 * eax  system call number
 * ebx  arg1
 * ecx  arg2
 * edx  arg3
 * esi  arg4
 * edi  arg5
 * ebp  user stack
 * 0(%ebp) arg6
 */

System Calls from C using Inline Assembly (x86-64)

The GNU C Library (glibc) implementation offers a practical example of how system calls are handled in C. The internal_syscall6 macro illustrates the register allocation:

#undef internal_syscall6
#define internal_syscall6(number, err, arg1, arg2, arg3, arg4, arg5, arg6) \
({                                  \
    unsigned long int resultvar;                    \
    TYPEFY (arg6, __arg6) = ARGIFY (arg6);              \
    TYPEFY (arg5, __arg5) = ARGIFY (arg5);              \
    TYPEFY (arg4, __arg4) = ARGIFY (arg4);              \
    TYPEFY (arg3, __arg3) = ARGIFY (arg3);              \
    TYPEFY (arg2, __arg2) = ARGIFY (arg2);              \
    TYPEFY (arg1, __arg1) = ARGIFY (arg1);              \
    register TYPEFY (arg6, _a6) asm ("r9") = __arg6;            \
    register TYPEFY (arg5, _a5) asm ("r8") = __arg5;            \
    register TYPEFY (arg4, _a4) asm ("r10") = __arg4;           \
    register TYPEFY (arg3, _a3) asm ("rdx") = __arg3;           \
    register TYPEFY (arg2, _a2) asm ("rsi") = __arg2;           \
    register TYPEFY (arg1, _a1) asm ("rdi") = __arg1;           \
    asm volatile (                          \
    "syscall\n\t"                           \
    : "=a" (resultvar)                          \
    : "0" (number), "r" (_a1), "r" (_a2), "r" (_a3), "r" (_a4),     \
      "r" (_a5), "r" (_a6)                      \
    : "memory", REGISTERS_CLOBBERED_BY_SYSCALL);            \
    (long int) resultvar;                       \
})

This macro precisely maps arguments to the required registers (%rdi, %rsi, etc.) before executing the syscall.

Manual System Calls in Assembly (x86-64 Example)

Here’s a minimal, runnable example demonstrating how to make system calls directly in x86-64 assembly:

.section .data
msg:
    .ascii "Hello, System Call!\n"
len = . - msg

.section .text
.global _start

_start:
    # write system call
    mov $1, %rax        # syscall number for write
    mov $1, %rdi        # file descriptor 1 (stdout)
    mov $msg, %rsi      # pointer to the message buffer
    mov $len, %rdx      # number of bytes to write
    syscall             # invoke kernel

    # exit system call
    mov $60, %rax       # syscall number for exit
    mov $0, %rdi        # exit status 0
    syscall             # invoke kernel

This code performs a write system call to print a message to standard output, followed by an exit system call to terminate the program.

User-Space Function Calling Conventions

Beyond system calls, the way functions pass parameters and manage their execution context is defined by calling conventions, often dictated by the Application Binary Interface (ABI).

x86-32 Function Calling Convention

Historically, x86-32 function calls on Linux (following the System V ABI) involved passing parameters on the stack.

  1. Push arguments onto the stack in reverse order.
  2. Execute the call instruction.
  3. The called function accesses arguments via the stack pointer (%esp).
  4. Callee-saved registers must be preserved by the called function.

Modern i386 System V ABIs require 16-byte stack alignment before a call, enabling callees to use SSE instructions that fault on unaligned access. Older conventions might only require 4-byte alignment.

x86-64 System V User-Space Function Calling Convention

The x86-64 System V ABI significantly improves efficiency by passing arguments in registers. This avoids the overhead of stack operations for parameter passing.

  1. Argument Classification: Parameters are classified (e.g., INTEGER, MEMORY, SSE).
  2. Register Assignment: Arguments are assigned to registers in a specific order based on their class. For INTEGER class parameters (integers and pointers), the registers used are: %rdi, %rsi, %rdx, %rcx, %r8, and %r9.
  3. Stack Usage: If there are more than six INTEGER arguments, subsequent arguments are passed on the stack.
  4. Stack Alignment: The stack pointer (%rsp) must be 16-byte aligned when the call instruction is executed.
  5. Floating-Point Arguments: The first eight floating-point arguments are passed in %xmm0 through %xmm7; subsequent arguments go on the stack.
  6. Variadic Functions: For functions like printf, the number of floating-point arguments passed in registers must be specified in %al.
  7. Struct Returns: Structs can be returned in registers (e.g., rdx:rax for larger structures) or on the stack, depending on their size and the ABI rules.

Performance Benefits: Register-based argument passing reduces latency and improves CPU out-of-order execution capabilities compared to the older stack-based methods.

Windows x64 Differences: It’s important to note that the Windows x64 calling convention differs notably from the x86-64 System V ABI, including the requirement for “shadow space” reserved by the caller and different register usage rules.

Architecting for Calls: ABI Standards

Calling conventions are standardized by ABIs. Each architecture and operating system family typically has its own ABI.

  • x86-64 System V ABI: This is the standard for Linux and many other Unix-like systems. Key resources include the System V Application Binary Interface AMD64 Architecture Processor Supplement .
  • ARM Architectures: ARM processors have various ABIs, including the ARM Architecture Procedure Call Standard (AAPCS) for ARM64.
  • Other Architectures: Conventions also exist for PowerPC, SPARC, and others.

The choice of ABI influences how efficiently programs can be compiled and how they interact with the operating system and libraries. Often, the same ABI is used for both user-space and kernel-space code for consistency.

Key Takeaways on System Calls and Calling Conventions

  • Architecture Matters: System call and function calling conventions are highly dependent on the CPU architecture (x86-32, x86-64, ARM, etc.) and the operating system.
  • Registers are Key: Modern architectures leverage registers extensively for passing arguments, enhancing performance.
  • ABIs Standardize: Application Binary Interfaces (ABIs) provide the rules for these conventions, ensuring interoperability.
  • Low-Level Control: Direct assembly programming allows fine-grained control over system call invocation and function calls.

For a comprehensive overview of various calling conventions across different architectures, the document “Calling Conventions ” by Agner Fog is an excellent resource.

FAQs on How to Invoke System Calls Assembly

Q: What is the primary instruction used for system calls on x86-64 Linux

ANS: The primary instruction used for system calls on x86-64 Linux is syscall.

Q: How are arguments passed to system calls on x86-32 Linux

ANS: On x86-32 Linux, the first six arguments to system calls are passed using the registers %eax for the system call number and %ebx, %ecx, %edx, %esi, %edi for the parameters.

Q: Which register holds the system call number on x86-64 Linux

ANS: The system call number is placed in the %rax register on x86-64 Linux.

Q: What is the difference between sysenter and int 0x80 for x86-32 system calls

ANS: sysenter is generally faster than int 0x80 for 32-bit system calls as it is designed to reduce overhead by leveraging the vDSO. However, int 0x80 is a more general interrupt mechanism.

Q: How does the x86-64 System V ABI handle more than six arguments for function calls

ANS: If a function call in the x86-64 System V ABI has more than six integer or pointer arguments, the subsequent arguments are passed on the stack.

Q: What registers are used for the first six arguments in x86-64 Linux system calls

ANS: The registers used for the first six arguments in x86-64 Linux system calls are %rdi, %rsi, %rdx, %rcx, %r8, and %r9.

Q: Is the x86-64 ABI the same for Windows and Linux

ANS: No, the x86-64 ABI for Windows has significant differences from the x86-64 System V ABI used on Linux, including register usage and stack management.
