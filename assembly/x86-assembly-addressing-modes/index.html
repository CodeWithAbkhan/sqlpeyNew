“x86 Assembly Addressing Modes Explained: A Deep Dive”

Delving into the intricacies of x86 assembly programming reveals a rich set of addressing modes that dictate how the processor accesses memory. These modes provide flexibility in specifying memory locations, enabling efficient data manipulation and program control. Understanding these mechanisms is fundamental for anyone working with low-level code or optimizing performance.

At its core, x86 (both 32-bit and 64-bit) offers several ways to form a memory address, generally represented as:

[base_reg + index_reg*scale + displacement]

A significant 64-bit addition is the RIP-relative addressing:

[RIP + displacement] (RIP-relative: 64-bit only. No index register is permitted).

All other forms, excluding RIP-relative, are subsets of the primary equation, allowing for omission of certain components. This means that accessing [rsi] directly does not necessitate a zeroed index register.

In assembly source code, the order of components within the brackets is irrelevant. The assembler computes all constant additions at assembly time, resulting in a single displacement value. For example: [5 + rax + rsp + 15*4 + MY_ASSEMBLER_MACRO*2] is perfectly valid.

It’s important that all registers involved in an addressing mode are of the same size. If you need to use a byte-sized register like al as an array index, it must first be zero- or sign-extended to the pointer width. A common practice to achieve this is ensuring the upper bits of the destination register (e.g., rax) are already zeroed before manipulating the byte registers.

The limitations observed in these addressing modes are a direct reflection of what can be encoded into machine code. The scale factor, for instance, is represented by a 2-bit shift count. The ModRM byte (and the optional SIB byte) can encode a maximum of two registers. Furthermore, these bytes only support addition of registers, not subtraction. Any register can serve as a base. With the exception of ESP/RSP, any register can function as an index. For detailed encoding specifics, such as why [rsp] consistently requires a SIB byte, consult resources detailing ModRM and SIB byte structures.

Every possible subset of the general addressing mode is encodable, with the notable exception of forms like e/rsp*scale which are generally considered useless in standard code that maintains a pointer to stack memory in ESP.

The typical code size for these encodings is:

  • 1 Byte: For single-register modes (using ModRM).
  • 2 Bytes: For two-register modes (using ModRM and the SIB byte).

The displacement can be 0, 1, or 4 bytes. If the displacement fits within a signed 8-bit value ([-128 to +127]), the more compact disp8 encoding is used, saving 3 bytes compared to disp32. The ModRM byte always indicates whether a SIB byte is present, similar to how it signals the presence of a disp8/disp32.

Code Size Exceptions:

  • [reg*scale] by itself necessitates a 32-bit displacement, which can be zero. Assemblers often circumvent this by encoding lea eax, [rdx*2] as lea eax, [rdx + rdx]. In both scenarios, a SIB byte is required alongside ModRM.
  • Encoding e/rbp or r13 as a base register without a displacement is not possible. Consequently, [ebp] is encoded as [ebp + byte 0]. Encodings without displacement using ebp as a base essentially mean no base register is present, as seen in [disp + reg*scale].
  • [e/rsp] invariably requires a SIB byte, even if no index register is present and regardless of a displacement. The ModRM encoding that would normally specify [rsp] instead signals the presence of a SIB byte.

For exhaustive details on these special cases, refer to Intel’s reference manuals, specifically Table 2-5 and surrounding sections. These special cases remain consistent between 32-bit and 64-bit modes. The introduction of RIP-relative encoding did not conflict with any other encoding, even without a REX prefix.

From a performance standpoint, expending an extra instruction solely for smaller x86 machine code is rarely beneficial. On CPUs featuring a uop cache, code size is often less critical than minimizing fused-domain micro-operations (uops), which are a more precious resource.

How Addressing Modes are Utilized

While this discussion primarily uses MASM syntax examples, NASM syntax is also relevant, particularly concerning differences in x86-64 RIP-relative addressing. AT&T syntax is a different representation of the same machine code, implying identical limitations.

Distinguishing between using a label (for global or static data) and a small constant displacement is key when examining how addressing modes map to hardware.

Consider accessing array elements. If you have an int* (pointer to an integer), you’d typically use the scale factor to multiply an index by the array’s element size when you have an element index rather than a byte offset. For code-size efficiency and certain performance scenarios, especially on Intel CPUs where indexed addressing can impact micro-fusion, preferring byte offsets or pointers is advisable.

Let’s illustrate with a char array* pointer in esi:

  • mov al, [esi] loads the byte pointed to by esi (equivalent to array[0] or *array).
  • mov al, [esi + ecx] loads array[ecx].
  • mov al, [esi + 10] loads array[10].
  • mov al, [esi + ecx*8 + 200] loads array[ecx*8 + 200].

Accessing global data like mov al, [global_array + 10] loads from global_array[10]. In 64-bit mode, this should ideally be a RIP-relative address. Using NASM DEFAULT REL is recommended for automatic RIP-relative address generation, rather than manually specifying [rel global_array + 10]. MASM typically defaults to this behavior. Direct indexing with RIP-relative addresses is not supported; the common approach involves lea rax, [global_array] followed by mov al, [rax + rcx*8 + 10] or similar.

For more on RIP-relative references, consult resources detailing their syntax across different assemblers.

Loading an immediate constant into a register can be achieved by embedding it directly within the instruction, like mov al, 0ABh. The preceding 0 is necessary for the assembler to recognize it as a constant.

To load a symbol’s address into a register:

  • NASM: mov esi, global_array assembles to mov esi, imm32, placing the address in esi.
  • MASM: Requires mov esi, OFFSET global_array for the same outcome. Conversely, mov esi, global_array in MASM assembles to a memory load: mov esi, dword [global_array].

In 64-bit mode, the standard method for loading a symbol address is a RIP-relative LEA. Assembler syntax varies; MASM handles this by default. NASM requires the DEFAULT REL directive or [rel global_array]. GAS necessitates explicit specification in each addressing mode.

As an optimization, when addresses can be represented as a 32-bit absolute value (instead of a rel32 offset), mov reg, imm32 remains optimal, similar to 32-bit code. However, in 32-bit mode, lea eax, [array] is less efficient, consuming an extra byte for code size and potentially running on fewer execution ports than mov eax, imm32. 32-bit mode lacks RIP-relative addressing.

It’s crucial to note that macOS loads all code outside the lower 32 bits, rendering 32-bit absolute addressing impractical. While position-independent code isn’t mandatory for executables, it’s generally advantageous, as 64-bit absolute addressing is less efficient than RIP-relative. The Mach-O 64-bit format doesn’t support 32-bit absolute address relocations like Linux ELF. Avoid using label names as 32-bit constants; effective-address expressions like [global_array + constant] are permissible as they can be assembled into RIP-relative addressing.

All these addressing modes can be leveraged with LEA for integer arithmetic. A notable advantage is that LEA does not affect flags, irrespective of whether the operand represents a valid memory address. Using LEA on non-address values is a common technique for performing arithmetic operations efficiently. For instance, [esi*4 + 10] is typically only useful with LEA unless the displacement is a symbol.

Segment overrides, such as mov al, [fs:esi] (NASM syntax), add a prefix byte to the standard encoding, with all other aspects remaining unchanged. Segment overrides can even be used with RIP-relative addressing.

When the operand size is ambiguous, explicitly use byte, word, dword, or qword to specify it.

  • NASM: mov dword [rsi + 10], 123
  • MASM and GNU .intel_syntax: mov dword ptr [rsi + 10], 123
  • GNU (AT&T): movl $123, 10(%rsi) (operand size from mnemonic suffix)

For further details, consult assembler-specific documentation and resources like the Wikipedia entry on x86 addressing modes.

16-Bit Addressing Modes

16-bit addressing modes are considerably more restrictive. The address size cannot accommodate a SIB byte, meaning all single and double register addressing modes are encoded within the single ModRM byte. Registers like BX or BP can be used as base registers, and SI or DI as index registers. Scaling is not supported. 16-bit code is largely obsolete, making it less critical to learn unless specifically required. These 16-bit restrictions apply whenever a 16-bit address size is used, even within 32-bit code with an address-size override prefix. For example, lea eax, [dx + cx*2] for arithmetic and truncation/zero-extension is not possible. However, lea eax, [edx + ecx*2] will correctly set ax = dx + cx*2, as garbage in the upper bits of source registers doesn’t impact the lower 16 bits.

For a deeper dive into 16-bit addressing, explore available resources that explain the fundamentals of x86 address usage, as some concepts remain consistent across different modes.

FAQs on x86 Assembly Addressing Modes

Q: What is the basic structure of an x86 memory address calculation

ANS: The general structure is [base_reg + index_reg*scale + displacement], with RIP + displacement being a 64-bit specific variant.

Q: Can any register be used as an index in x86 addressing

ANS: No, registers like ESP/RSP cannot be used as index registers.

Q: What is the purpose of the SIB byte in x86 addressing

ANS: The SIB (Scale-Index-Base) byte is used in conjunction with the ModRM byte to encode more complex addressing modes involving an index register and a scale factor.

Q: How does RIP-relative addressing differ from other modes

ANS: RIP-relative addressing is exclusive to 64-bit mode and uses the Instruction Pointer (RIP) as the base, adding a displacement. It does not permit an index register.

Q: What are the limitations of 16-bit addressing modes

ANS: 16-bit addressing modes do not support SIB bytes and have restrictions on which registers can be used as base or index, with no scaling capabilities.
