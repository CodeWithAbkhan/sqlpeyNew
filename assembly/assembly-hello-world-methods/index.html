“Assembly Language ‘Hello World’ - NASM, MASM, FASM Comparison”

How can one construct a basic “Hello World” program using assembly language on the Windows platform, and what are the variations when employing different assemblers like NASM, MASM, or FASM, especially concerning dependency on external libraries or direct OS interaction?

Various techniques exist to achieve this foundational task, ranging from direct invocation of the Windows API to leveraging the standard C runtime library.

Method 1: Direct Windows API Calls (NASM, Avoiding C Standard Library)

This approach bypasses the C standard library entirely, communicating directly with the Windows kernel through system functions like GetStdHandle and WriteFile. This results in smaller binaries that do not require linking against libc.

To implement this with NASM for a 32-bit console application, one needs to interact with the required Win32 API functions explicitly:

; File: direct_winapi_32bit.asm
global _main
extern  _GetStdHandle@4
extern  _WriteFile@20
extern  _ExitProcess@4

section .text
_main:
    ; Setup stack frame for local variables (e.g., 'bytes' counter)
    mov     ebp, esp
    sub     esp, 4

    ; hStdOut = GetStdHandle( STD_OUTPUT_HANDLE = -11 )
    push    -11
    call    _GetStdHandle@4
    mov     ebx, eax    ; Store handle in EBX

    ; WriteFile( hStdOut, message, length(message), &bytes, 0);
    push    0
    lea     eax, [ebp-4] ; Address of local 'bytes' variable
    push    eax
    push    (message_end - message) ; Length of message
    push    message     ; Pointer to message buffer
    push    ebx         ; Handle
    call    _WriteFile@20

    ; ExitProcess(0)
    push    0
    call    _ExitProcess@4

    ; Execution should never reach here
    hlt
message:
    db      'Hello, World via direct API', 10
message_end:

Compilation and Linking Requirements (Windows): This requires the Netwide Assembler (nasm) and the Microsoft linker (link.exe) from Visual Studio:

  1. Assemble: nasm -fwin32 direct_winapi_32bit.asm (Produces direct_winapi_32bit.obj)
  2. Link: link /subsystem:console /nodefaultlib /entry:main direct_winapi_32bit.obj

The option /nodefaultlib is crucial here as it prevents linking with the default C libraries.

Method 2: Linking with C Standard Library (NASM)

Alternatively, you can link against the C standard library (libc) and use familiar C functions like printf. This simplifies the output logic but adds external dependencies.

32-bit Example using printf:

; File: libc_printf_32bit.asm
global  _main
extern  _printf

section .text
_main:
    push    message     ; Push argument for printf
    call    _printf
    add     esp, 4      ; Clean up stack space for the argument
    ret                 ; Return from main
message:
    db  'Hello, World using printf', 10, 0 ; Null terminator needed by C functions

Compilation and Linking Requirements (Windows):

  1. Assemble: nasm -fwin32 libc_printf_32bit.asm
  2. Link (using GCC/MinGW linker or VS linker with C Runtime): If using the GCC toolchain for linking: gcc libc_printf_32bit.obj or specifically linking the C runtime library if using only link.exe: link.exe libc_printf_32bit.obj libcmt.lib (as shown in one accepted solution).

Legacy DOS Approach (16-bit)

For historical context or execution within DOS emulators (like DOSBox), 16-bit MS-DOS interrupts can be used. This code runs at CS:100h and uses interrupt 21h:

org 100h
mov dx, msg       ; Pointer to message string
mov ah, 9         ; DOS function: Write string
int 21h           ; Execute system call

mov ah, 4Ch       ; DOS function: Exit program
int 21h
msg db 'Hello, World in DOS!', 0Dh, 0Ah, '$' ; '$' is terminator for AH=9

Method 3: Using MASM with Win32/Win64 API (MessageBox)

Microsoft’s Assembler (MASM) offers directives that abstract some calling convention details, notably the invoke directive. A common variation is displaying output in a GUI message box instead of the console.

Win32 MASM Example (Using MessageBoxA)

; File: message_win32.asm
.386
.model flat, stdcall
include kernel32.inc
includelib kernel32.lib
include user32.inc
includelib user32.lib

.data
title db 'MASM Win32', 0
msg db 'Hello World via MessageBox', 0

.code

Main:
    ; invoke MessageBoxA, hWnd, lpText, lpCaption, uType
    push 0            ; uType = MB_OK
    push offset title 
    push offset msg   
    push 0            ; hWnd = HWND_DESKTOP
    call MessageBoxA
    
    ; ExitProcess(uExitCode) where uExitCode is the return value of MessageBoxA (EAX)
    push eax          
    call ExitProcess

End Main

Assembly and Linking (MASM):

  • 32-bit: ml.exe message_win32.asm /link /subsystem:windows /defaultlib:kernel32.lib /defaultlib:user32.lib /entry:Main

Win64 MASM Considerations: Shadow Space

64-bit Windows uses the x64 calling convention, which mandates reserving shadow space (32 bytes, or 0x28) on the stack before calling external functions (MessageBoxA, ExitProcess). This space is for the function caller to store arguments passed in registers RCX, RDX, R8, R9.

; File: message_win64.asm (Excerpt focusing on stack setup)
main proc
  sub rsp, 28h  ; Reserve 32 bytes of shadow space; ensures RSP is 16-byte aligned
  mov rcx, 0       ; hWnd = HWND_DESKTOP
  lea rdx, msg     ; LPCSTR lpText (Argument 2)
  lea r8,  title   ; LPCSTR lpCaption (Argument 3)
  mov r9d, 0       ; uType = MB_OK (Argument 4)
  call MessageBoxA
  
  add rsp, 28h  ; Clean up shadow space before cleanup/return (though ExitProcess handles termination)
  mov ecx, eax     ; Exit code = return value of MessageBoxA
  call ExitProcess
main endp

Assembly and Linking (MASM 64-bit):

  • 64-bit: ml64.exe message_win64.asm /link /subsystem:windows /defaultlib:kernel32.lib /defaultlib:user32.lib /entry:main

MASM Cross-Platform (using ifdef and invoke)

MASM allows defining code that adapts based on architecture:

ifdef rax ; Check if architecture supports 64-bit registers (presence of RAX)
    extrn MessageBoxA: PROC
    extrn ExitProcess: PROC
else ; Assume 32-bit environment setup
    .386
    .model flat, stdcall
    include kernel32.inc
    ; ... other includes ...
endif
.data
caption db 'WinAPI', 0
text    db 'Hello World', 0
.code
main proc
    ; 'invoke' handles argument pushing based on convention known to the assembler
    invoke MessageBoxA, 0, offset text, offset caption, 0
    invoke ExitProcess, eax
main endp
end

Method 4: Using FASM (Flat Assembler)

Flat Assembler (FASM) is often favored because it handles the PE (Portable Executable) header creation internally, eliminating the need for a separate linker step for simple programs. It uses directives like FORMAT PE CONSOLE and the invoke macro similar to MASM.

FASM Example (Console Output):

; File: fasm_hello.asm
include 'win32ax.inc' ; Includes necessary structures and definitions

FORMAT PE CONSOLE ; Defines executable format and subsystem

section '.idata' import data readable writeable
    ; Setup import table automatically handled by FASM directives in this basic usage
    ; If explicit imports were required, the .idata section definition would be more verbose
    
section '.text' code executable readable writable
  start:
    ; invoke MessageBox, hWnd, lpText, lpCaption, uType
    invoke  MessageBox, HWND_DESKTOP, "Hi! I'm the FASM example program!", invoke GetCommandLine, MB_OK
    invoke  ExitProcess, 0

end start

Compilation (FASM):

  • Assemble: fasm fasm_hello.asm

FASM directly generates the executable (e.g., fasm_hello.exe), neatly packaging the necessary headers.

Method 5: NASM 64-bit Direct API Call

This mirrors Method 1 but targets 64-bit Windows executables, which uses the WinMain entry point convention for windowed apps or requires careful setup for console entry point (__tmainCRTStartup or similar if linking CRT). Using WinMain is common when bypassing the C runtime for 64-bit GUI apps:

default rel         ; Enables RIP-relative addressing for static data access
global WinMain
extern ExitProcess  
extern MessageBoxA

section .data 
title:  db 'Win64 NASM', 0
msg:    db 'Hello world via NASM 64-bit API', 0

section .text
WinMain:
    sub rsp, 28h      ; Reserve 64-bit shadow space (0x28) and align stack
    mov rcx, 0       ; Arg 1: hWnd = HWND_DESKTOP
    lea rdx,[msg]    ; Arg 2: LPCSTR lpText
    lea r8,[title]   ; Arg 3: LPCSTR lpCaption
    mov r9d, 0       ; Arg 4: uType = MB_OK
    call MessageBoxA

    mov  ecx, eax     ; Set exit status from MessageBoxA return value
    call ExitProcess

    add rsp, 28h      ; Restore RSP (though ExitProcess terminates)
    hlt

Assembly and Linking (NASM 64-bit):

  1. Assemble: nasm -f win64 test64.asm (Produces test64.obj)
  2. Link: link.exe test64.obj /subsystem:windows /entry:WinMain /nodefaultlib kernel32.lib user32.lib /largeaddressaware:no

Method 6: ARM Windows Assembly (WinMainCRTStartup)

For completeness, generating code for different architectures like ARM requires adhering to that specific Application Binary Interface (ABI), which involves different register usage and data directives.

AREA    data, DATA

Text    DCB     "Hello world(text)", 0
Caption DCB   "Hello world(caption)", 0

    EXPORT  WinMainCRTStartup
    IMPORT  __imp_MessageBoxA
    IMPORT  __imp_ExitProcess

    AREA    text, CODE
WinMainCRTStartup   PROC
            movs        r3,#0                   ; uType = 0
            ldr         r2,Caption_ptr          ; Arg 3
            ldr         r1,Text_ptr             ; Arg 2
            movs        r0,#0                   ; Arg 1: hWnd = 0
            ldr         r4,MessageBoxA_ptr      ; Load address of MessageBoxA stub
            ldr         r4,[r4]
            blx         r4                      ; Call MessageBoxA

            movs        r0,#0                   ; Exit code = 0
            ldr         r4,ExitProcess_ptr      ; Load address of ExitProcess stub
            ldr         r4,[r4]
            blx         r4                      ; Call ExitProcess

MessageBoxA_ptr DCD __imp_MessageBoxA       
ExitProcess_ptr DCD __imp_ExitProcess
Text_ptr    DCD Text
Caption_ptr DCD Caption

    ENDP
    END

Why Discuss These Differences?

The complexity lies not just in syntax but in the ABI:

  • Direct API Calls (Method 1/5): Requires manual management of handles and specific OS functions (GetStdHandle, WriteFile).
  • C Library Linking (Method 2/6): Leverages high-level functions like printf but forces linkage with the C Runtime Library (libcmt.lib or similar).
  • FASM (Method 4): Abstracts the linker complexity away entirely by generating the complete PE structure itself.
  • x64 ABI (Method 3/5): Demands stack setup (shadow space) for register arguments passed to external DLL functions.

The choice between these methods dictates the resulting binary size, runtime dependencies, and the directness of interaction with the operating system kernel.

FAQs on Assembly Hello World Methods

Q: Which assembler results in the smallest executable for 'Hello World'

ANS: Generally, the method that calls the Windows API directly (Solution 1 or 5) and uses /nodefaultlib will produce the smallest executable because it avoids linking any substantial portion of the C Standard Library.

Q: What is shadow space in x64 assembly linking

ANS: Shadow space, required by the Microsoft x64 calling convention, is a mandatory 32-byte area reserved on the stack by the caller to store the first four arguments (RCX, RDX, R8, R9) passed to called functions, even if those arguments are registers.

Q: Can NASM be used on Linux to create executables

ANS: Yes, NASM supports various output formats including ELF formats for Linux, allowing the creation of native executables there, which utilize different system call conventions than Windows.
