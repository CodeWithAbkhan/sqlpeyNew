“Register Preservation Across Function Calls in C: A Deep Dive”

When writing code in C, particularly when interacting with low-level operations or optimizing performance, understanding how functions manage registers is crucial. This topic delves into the nuances of register preservation across function calls, focusing on the roles of callee-saved and scratch registers, and how compilers like GCC adhere to (or deviate from) the established Application Binary Interface (ABI).

What are Callee-Saved and Scratch Registers?

In the context of function calls, registers are temporary storage locations within the CPU. To ensure that functions can call each other without corrupting critical data, a convention is established for how registers should be treated.

  • Callee-Saved Registers: These registers must maintain their original values after a function call. If a function intends to use a callee-saved register, it must first save its current value (typically onto the stack) before modifying it, and then restore the original value before returning to the caller. This ensures that the calling function’s state remains intact.
  • Scratch Registers: These registers can be freely used by a function without any obligation to preserve their values. The calling function must assume that the values in scratch registers might be altered by any function it calls.

In the widely adopted System V AMD64 ABI (used by GCC on Linux and macOS), the following registers are generally categorized:

  • Callee-Saved: rbx, rbp, rsp, r12, r13, r14, r15.
  • Scratch (or Caller-Saved): rax, rcx, rdx, rsi, rdi, r8, r9, r10, r11, and SIMD/FP registers like ymm0 through ymm15.

Practical Demonstration with GCC Inline Assembly

To solidify this concept, we can examine how GCC handles register preservation when explicitly instructed to use certain registers within inline assembly. Consider a simple C function that increments a 64-bit unsigned integer.

Solution 1: Referencing Documentation

The most direct way to identify which registers are callee-saved is by consulting the official ABI documentation. For the x86-64 architecture, these registers are typically marked with a “Yes” in the “Preserved across function calls” column. The commonly cited callee-saved registers include r12, r13, r14, r15, rbx, rsp, and rbp.

Solution 2: Experimental Approach with GCC Inline Assembly

We can experimentally verify this by using GCC’s inline assembly to explicitly list registers that the compiler should consider “clobbered” (i.e., modified). This forces GCC to save and restore them if they are callee-saved.

Let’s examine the following C code:

#include <inttypes.h>

uint64_t increment_register(uint64_t value) {
    __asm__ __volatile__(
        // Empty body for the inline assembly, focus is on clobber list
        : "+m" (value) // Constraint: 'm' for memory operand, '+' for read-write
        : // Input operands (none)
        : "rax", "rbx", "rcx", "rdx", "rsi", "rdi", // General purpose scratch registers
          "rbp", "rsp", // Base and stack pointers (callee-saved)
          "r8", "r9", "r10", "r11", // More scratch registers
          "r12", "r13", "r14", "r15", // Callee-saved registers
          "ymm0", "ymm1", "ymm2", "ymm3", "ymm4", "ymm5", // SIMD registers
          "ymm6", "ymm7", "ymm8", "ymm9", "ymm10", "ymm11",
          "ymm12", "ymm13", "ymm14", "ymm15"
    );
    return value + 1; // The increment operation itself
}

int main(int argc, char **argv) {
    (void)argv; // Suppress unused variable warning
    return increment_register(argc);
}

To observe the compiler’s behavior, we compile and then disassemble the code:

gcc -std=gnu99 -O3 -ggdb3 -Wall -Wextra -pedantic -o main_program main.c
objdump -d main_program

The disassembly of the increment_register function (<increment_register>):

00000000000011a0 <increment_register>:
   11a0:       55                      push   %rbp             // Save rbp
   11a1:       48 89 e5                mov    %rsp,%rbp        // Set up stack frame
   11a4:       41 57                   push   %r15             // Save r15 (callee-saved)
   11a6:       41 56                   push   %r14             // Save r14 (callee-saved)
   11a8:       41 55                   push   %r13             // Save r13 (callee-saved)
   11aa:       41 54                   push   %r12             // Save r12 (callee-saved)
   11ac:       53                      push   %rbx             // Save rbx (callee-saved)
   11ad:       48 83 ec 08             sub    $0x8,%rsp        // Allocate space on stack for 'value'
   11b1:       48 89 7d d0             mov    %rdi,-0x30(%rbp) // Save input 'value' (passed in rdi)
   11b5:       48 8b 45 d0             mov    -0x30(%rbp),%rax // Load 'value' into rax for operation
   11b9:       48 8d 65 d8             lea    -0x28(%rbp),%rsp // Adjust rsp to match expected state after pops
   11bd:       5b                      pop    %rbx             // Restore rbx
   11be:       41 5c                   pop    %r12             // Restore r12
   11c0:       48 83 c0 01             add    $0x1,%rax        // Perform the increment
   11c4:       41 5d                   pop    %r13             // Restore r13
   11c6:       41 5e                   pop    %r14             // Restore r14
   11c8:       41 5f                   pop    %r15             // Restore r15
   11ca:       5d                      pop    %rbp             // Restore rbp
   11cb:       c3                      retq                    // Return
   11cc:       0f 1f 40 00             nopl   0x0(%rax)        // No-operation padding

Observing the disassembly, we see the following callee-saved registers being pushed onto the stack and then popped back: rbx, r12, r13, r14, r15, and rbp.

The stack pointer (rsp) is also managed:

  1. sub $0x8, %rsp allocates 8 bytes for saving the input argument %rdi.
  2. lea -0x28(%rbp), %rsp effectively restores %rsp to its state before the function’s prologue, aligning with the pops that follow.

There are six push operations and six corresponding pop operations, confirming that the callee-saved registers explicitly listed in the __asm__ clobber list are indeed preserved by GCC. The stack pointer (rsp) is meticulously handled to maintain the integrity of the stack frame.

Solution 3: Understanding the ABI’s Role

The Application Binary Interface (ABI) acts as a contract, defining how software components interact at the binary level. For authors of compilers, linkers, and other language processing tools, the ABI dictates essential communication protocols between functions. This includes:

  • Argument Passing: How function arguments are transmitted from the caller to the callee.
  • Return Values: How results are passed back from the callee to the caller.
  • Register Usage: Which registers are designated as preserved across calls (callee-saved) and which are available for temporary use (scratch).

A key ABI rule is that a function using a callee-saved register must save its original value before modification and restore it before returning. This guarantees that the caller’s context remains unchanged. Scratch registers, conversely, offer no such guarantee; their contents may be altered.

When you write assembly code, you essentially adopt the role of the compiler. If your assembly code modifies a callee-saved register, you are responsible for implementing the save-and-restore mechanism. Similarly, when calling external functions, your assembly must adhere to the standard argument-passing conventions and can rely on the ABI’s promise that callee-saved registers will be preserved.

The ABI ensures interoperability among standard-conforming software. However, it’s entirely permissible to deviate from these rules in specific scenarios. Compilers frequently do this, especially when optimizations are possible. For instance, a static C function whose address is never taken can be safely inlined by the compiler. Since the compiler has complete knowledge of all callers and can guarantee the function’s scope, it can optimize the calling convention or even eliminate the call entirely.

As an assembly code author, you can employ similar private agreements between routines. As long as these agreements do not conflict with or violate the expectations of standard-conforming software, they are valid.

FAQs on Register Preservation in C

Q: What is the main purpose of callee-saved registers

ANS: Callee-saved registers must retain their original values across a function call. If a function uses them, it must save their values before modification and restore them before returning, ensuring the caller’s context is unaffected.

Q: Are all registers callee-saved

ANS: No, not all registers are callee-saved. There are also scratch registers (or caller-saved registers) that a function can modify without the obligation to restore them.

Q: How does the System V AMD64 ABI define register usage

ANS: The System V AMD64 ABI categorizes registers into callee-saved (e.g., rbx, rbp, r12-r15) and scratch (e.g., rax, rcx, rdx, rsi, rdi, r8-r11). This defines how functions should interact to maintain program state.

Q: Can I ignore callee-saved register rules in my assembly code

ANS: You can, but only if your assembly code has a private agreement with the functions it calls and does not interfere with standard-conforming software. Generally, adhering to the ABI for external calls is advisable.

Q: Why does GCC sometimes push and pop registers that seem like scratch registers in the disassembly

ANS: Even scratch registers might be saved and restored by the compiler for optimization purposes or due to specific constraints within the inline assembly. The explicit clobber list in __asm__ informs the compiler of registers that might be modified, prompting it to manage them accordingly.
