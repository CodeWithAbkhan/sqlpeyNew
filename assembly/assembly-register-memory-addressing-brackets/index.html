“Differentiating Register and Memory Addressing in Assembly: Brackets Explained”

In low-level programming, precise control over data movement between registers and memory is paramount. A common point of contention arises when using the MOV instruction: what is the functional difference when an operand is specified directly versus when it is enclosed in square brackets, indicating memory dereferencing?

Let’s dissect the implications of using the square bracket notation ([ ]) in assembly operations, specifically contrasting it with its absence.

The Core Distinction: Value vs. Address Content

Consider the fundamental structure of the MOV instruction: MOV destination, source. The presence of brackets around the source operand fundamentally shifts the instruction’s interpretation:

Direct Operand (No Brackets)

When a source operand is not enclosed in brackets, the assembler interprets it as either an immediate constant or the value already held within a register or label:

  • Immediate Value: MOV REG, value moves the literal constant value into REG.
  • Register Content: MOV REG1, REG2 transfers the data inside REG2 into REG1.
  • Label Value (Address): If x is a label, MOV REG, x moves the address associated with the label x into REG.

Indirect Operand (With Brackets)

When the source operand is enclosed in brackets, it signals indirect addressing—the instruction accesses the memory location pointed to by the value within the brackets:

  • Dereferencing: MOV REG, [x] moves the content stored at the memory address specified by x into REG. If x is a label, its value is the address; thus, the instruction fetches the data residing at that address.

Solutions

Evaluating Register Content in Specific Scenarios

Assume we have the following setup in memory, perhaps defined by buffer db 5 (where buffer is a label pointing to a memory location holding the value 5).

If you execute:

  1. MOV BL, 5 (Assuming BL is the 8-bit low part of a general-purpose register like EBX or RBX)
  2. MOV CL, buffer
  3. MOV CL, [buffer]

Question: Does BL end up containing the value 5, and does CL end up containing the memory address of buffer?

Answer Verification:

Yes, your assessment that BL holds the value 5 (from the first conceptual operation) is generally correct. Furthermore, the interpretation of MOV CL, buffer is that CL receives the memory address associated with the label buffer.

However, a critical limitation emerges when using an 8-bit register like CL to store an address:

Caution Regarding Register Width: Since CL is an 8-bit register, it can only store the least significant byte (8 bits) of the memory address of buffer. Modern systems typically use 32-bit or 64-bit addresses, making CL insufficient to hold the complete address. You would typically use a wider register (like RCX or ECX) for storing full addresses.

Conversely, MOV CL, [buffer] instructs the processor to look at the memory location labeled buffer and transfer the byte stored there (which is 5, in our example) into CL.

| Instruction | Source Interpretation | Destination CL Content (if buffer holds 5) | | :

mov REG, x
mov REG, [x]

| :

| :

| | MOV CL, buffer | Address of buffer | The lowest 8 bits of the address of buffer | | MOV CL, [buffer] | Value at the address of buffer | 5 (the value stored at that address) |

Moving Data Related to Constants and Indirect Addressing

Labels themselves are immediate values representing a memory address. You cannot generally move a register into an immediate value because immediate values are fixed constants.

What you can do is move data to a memory location that a constant points to:

; Move the content of REG into the memory location pointed to by the constant 'MyConfigPtr'
MOV [MyConfigPtr], REG

This highlights the necessity of indirect addressing when the destination is specified by an address constant.

Indirect Register Addressing: The operation MOV REG2, [REG1] is fundamental. If REG1 already holds a valid memory address, this instruction loads the data residing at that address into REG2.

The Role of Size Specifiers in Memory Writes

When writing an immediate value or a register content to a memory location using an address constant, the assembler often requires explicit size information if the constant itself is ambiguous or if the target memory structure size is unclear. This ensures the correct number of bytes are modified.

Consider the data definition:

MyArray DB 0FFh, 0FFh, 0FFh, 0FFh  ; DB defines 4 bytes (Bytes)

The instruction needs context for how many bytes to overwrite:

; Overwrites only the first byte (0FFh becomes 03h)
MOV BYTE [MyArray], 3 
; Result: MyArray -> 03h, 0FFh, 0FFh, 0FFh

; Overwrites the first two bytes (0FFh, 0FFh becomes 03h, 00h because 3 = 00000003h)
MOV WORD [MyArray], 3 
; Result: MyArray -> 03h, 00h, 0FFh, 0FFh

; Overwrites the first four bytes
MOV DWORD [MyArray], 3
; Result: MyArray -> 03h, 00h, 00h, 00h

This explicit sizing prevents ambiguity when dealing with memory access where the target size isn’t inherently known from the destination operand’s context alone.

Synthesis on Addressing Terminology

  1. Brackets ([a]): Always signify accessing the data stored at the address a. If a is a numeric constant (like F5B1h), it references RAM location F5B1h.
  2. Labels: Labels (like buffer) are inherently addresses—the starting address assigned to the data structure they represent.
  3. Registers: Registers hold values directly. They are considered immediate storage locations and do not require dereferencing (i.e., you use REG, not [REG], to access the value in the register).

Potential External Factors

While the assembly instructions define the operation, external code execution can affect outcomes:

  • Concurrency/Interrupts: If interrupt service routines or other threads operate on the data stored at the location referenced by the label (buffer), the value retrieved by MOV BL, [buffer] could change between executions, even if the primary code path seems constant. Ensure atomicity if necessary.
  • Register Corruption: Faulty interrupt handlers might alter the contents of general-purpose registers without restoring their prior state, affecting any subsequent operations relying on those registers.
array db 0FFh, 0FFh, 0FFh, 0FFh
mov byte [array], 3
array db 03h, 0FFh, 0FFh, 0FFh
mov word [array], 3
array db 03h, 00h, 0FFh, 0FFh
mov dword [array], 3
