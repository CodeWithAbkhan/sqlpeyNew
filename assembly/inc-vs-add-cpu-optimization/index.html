“CPU Performance: INC vs. ADD for Register Increment Optimization”

When optimizing code for maximum performance on modern processors, the choice between using INC and ADD for simple register increments can have subtle yet significant impacts. While both achieve the same functional outcome, their underlying micro-architectural behavior differs, leading to performance variations across different CPU families. This exploration delves into these differences, focusing on aspects like micro-operation (uop) costs, partial-flag stalls, and overall efficiency.

The Core Dilemma: INC vs. ADD reg, 1

At a fundamental level, INC reg and ADD reg, 1 both increment a register by one. However, the way processors handle these instructions can vary:

  • INC reg: This instruction, while often more compact in terms of code size (saving a byte compared to ADD reg, 1 in 64-bit mode), can have different performance characteristics. Historically, it modified flags differently than ADD, leading to issues like “partial-flag stalls” on certain older Intel architectures.
  • ADD reg, 1: This instruction is more explicit and generally considered safer from a performance perspective across a wider range of CPUs. It writes to all condition flags, thus avoiding the potential pitfalls associated with partial flag updates.

Performance Considerations and CPU Microarchitectures

The performance implications of INC versus ADD are heavily dependent on the specific CPU microarchitecture:

General Advice for Modern CPUs:

For most modern CPUs, ADD reg, 1 is generally recommended as it is never slower than INC (except for indirect code-size effects) and avoids potential issues. While INC reg is often preferred for code-size optimization, especially in scenarios where repetition occurs frequently, its performance advantage is not guaranteed and can even be a disadvantage on certain architectures.

Intel Alder Lake and Silvermont Family:

  • Alder Lake E-cores: These cores seem to run INC instructions less efficiently, potentially due to how they handle Gracemont microarchitecture. Performance testing indicates INC might be slower in this context.
  • Silvermont Family (including Knight’s Landing): This family, found in some netbooks, Chromebooks, and NAS servers, decodes INC/DEC as one uop but expands them to two in the allocate/rename stage. This expansion is for partial flag merging. While out-of-order execution can mitigate some latency, it can lead to a throughput penalty. For optimal performance on Silvermont-family CPUs, ADD 1 is generally preferred.

Intel P6 Family (Core2, Nehalem, Sandy Bridge, Ivy Bridge, Haswell, Skylake):

  • P6 Family (Pre-Sandy Bridge): These architectures could experience “partial-flag stalls” if an instruction following INC or DEC read flags that were not updated by the INC/DEC instruction (specifically, the Carry Flag, CF). This could introduce significant delays.
  • Sandy Bridge (SnB) Family: Introduced a more efficient way to handle partial flags. A merging uop is inserted with minimal or no stall. INC/DEC can even macro-fuse with conditional jumps on these CPUs, similar to ADD/SUB.
  • Skylake: Notably, Skylake processors do not have partial-flag merging costs. The CF flag is treated as a separate register. This means ADC (which only reads CF) can be a single uop with no interaction penalty with INC or DEC.

AMD CPUs:

AMD CPUs generally treat INC and ADD similarly regarding partial register renaming, except for flags. They rename different parts of flags separately, effectively performing a write-only update to all flags except CF. This avoids the partial-flag merging slowdowns seen on some Intel CPUs when reading the full register.

Scenarios Where ADD Offers Advantages

Beyond the general preference for ADD, specific scenarios highlight its superiority:

  1. Memory Destinations: When incrementing memory operands, ADD [rdi], 1 can micro-fuse the store and the load+add on Intel Core2 and SnB-family, resulting in fewer uops. INC [rdi], however, can only micro-fuse the store, leading to more uops. (Note: AMD and Silvermont handle memory-destination INC and ADD similarly).

    ; Optimized for Intel Core2/SnB-family when incrementing memory
; Using ADD is often better here due to micro-fusion
mov rax, [mem_location]
add rax, 1
mov [mem_location], rax

; Potentially fewer uops on Core2/SnB-family for memory destination
; add qword ptr [rdi], 1

  2. Breaking Flag Dependencies: Instructions like variable-count shifts (SHL reg, CL) can have an input dependency on the flags. Using ADD reg, 1 before such instructions can break this dependency, potentially improving performance by preventing a partial-flag stall or extra uop.

    ; Example scenario: Breaking flag dependency for SHL
; Assume 'edx' holds the shift count and 'eax' is the value to shift
; For performance on some architectures, it might be beneficial to ensure FLAGS are fully updated
; before a potentially problematic shift instruction.

; Instead of:
; mov rcx, [some_value]
; shl eax, cl
; jnz loop_end

; Consider:
mov rcx, [some_value]
add rcx, 0        ; Ensure all flags are updated, even if no effective change
shl eax, cl       ; Now less likely to have a dependency issue with flags
jnz loop_end

; Alternatively, using lea to avoid flag modification entirely:
lea rax, [rax + 1] ; Efficiently increments without affecting flags

LEA as an Alternative

For situations where you need to perform arithmetic without affecting flags, LEA (Load Effective Address) can be a performant alternative. For instance, LEA EAX, [EAX+1] achieves the same result as ADD EAX, 1 but does not modify the flags register. This can be useful in complex code where flag preservation is critical.

; Increment EAX without modifying flags
lea eax, [eax + 1]

Avoiding Partial-Flag Stalls

Partial-flag stalls occur when an instruction depends on flag values that are only partially updated by a previous instruction (like INC/DEC). On architectures like Nehalem and earlier, this could cause stalls of around 7 cycles. While Sandy Bridge and later CPUs mitigate this with merging uops, it’s still a factor to consider.

  • The adc scenario: In loops involving ADC (Add with Carry), which reads the Carry Flag (CF), an preceding INC can cause issues. INC updates many flags but leaves CF unchanged. If the ADC instruction’s loop condition relies on this un-updated CF, performance can suffer. Replacing INC with ADD reg, 1 or SUB reg, 1 ensures all flags are written, avoiding the stall.

    ; Illustrative example of a potential partial-flag stall scenario
; (For specific CPUs, refer to microarchitecture guides)
; loop:
;    adc   eax, [memory_address]   ; Reads CF
;    inc   rcx                     ; Leaves CF unchanged
;    jnz   loop                    ; Jumps based on ZF/SF/etc., but indirectly relies on loop counter updates
;
; To mitigate on older CPUs:
; loop:
;    adc   eax, [memory_address]
;    add   rcx, 1                  ; Updates all flags, including CF
;    jnz   loop

Code Size and Instruction Cache

INC reg is shorter than ADD reg, 1. In 64-bit mode, INC rax is one byte, while ADD rax, 1 is three bytes. This difference in code size can impact:

  • Instruction Cache Hit Rate: Smaller code occupies less space in the instruction cache, potentially leading to more cache hits and faster instruction fetching.
  • iTLB Hit Rate: Reduced code size can improve Translation Lookaside Buffer (iTLB) hit rates.
  • Page Loading: Fewer pages need to be loaded from disk.

For code that is executed very frequently, these small code size savings can accumulate and contribute to overall performance gains.

Tooling and Compiler Behavior

Modern compilers often use INC when optimizing for size (-Os) and may also use it when optimizing for speed (-O3) on many architectures, recognizing that the performance penalty is often negligible or non-existent on contemporary CPUs. Compilers like Clang 5.0 and Intel’s ICC 17 have been observed to use INC even for speed optimizations. However, specific tuning flags like -mtune=pentium4 can instruct compilers to avoid INC/DEC due to their historical issues on that architecture. For KNL (Knight’s Landing), which is based on Silvermont, avoiding INC is a reasonable default.
