“Efficient Horizontal Vector Summation Techniques Explained”

When working with Single Instruction, Multiple Data (SIMD) instructions, a common operation is the horizontal reduction, such as summing all elements within a vector. This process allows for efficient aggregation of data, particularly in performance-critical applications like scientific computing, signal processing, and machine learning. This post delves into various strategies for achieving efficient horizontal vector summation across different SIMD instruction sets and data types.

The core idea behind horizontal reduction involves taking elements from different lanes of a SIMD register and combining them. This is typically achieved through a series of shuffle and arithmetic operations, progressively reducing the vector’s width until a single result is obtained.

General Approach to Horizontal Reduction

For any horizontal reduction, a general strategy involves:

  1. Extraction/Shuffling: High-half elements are aligned with low-half elements.
  2. Vertical Operation: A vertical add (or min/max/or/and/xor/multiply) is performed.
  3. Iteration: Steps 1 and 2 are repeated until only a single element remains.

If you start with vectors wider than 128 bits, you can narrow them by half until you reach 128 bits, allowing you to then use specific functions for that width. If the final result needs to be broadcast to all elements, full-width shuffles can be utilized throughout.

Summing Across Different Vector Types

The specifics of horizontal summation vary depending on the SIMD instruction set (SSE, AVX, AVX2, AVX-512) and the data type (float, double, integers).

Floating-Point Vectors

  • __m128 (SSE/SSE2): For summing __m128 (single-precision floats), a common approach involves shuffling and adding.

    // Sums elements of v = [ D C | B A ]
__m128 hsum_ps_sse1(__m128 v) {
    // Shuffle to get [ C D | A B ]
    __m128 shuf = _mm_shuffle_ps(v, v, _MM_SHUFFLE(2, 3, 0, 1));
    // Add: sums = [ D+C C+D | B+A A+B ]
    __m128 sums = _mm_add_ps(v, shuf);
    // Shuffle high half of sums to low half, using shuf as a temporary register to avoid an extra move
    shuf = _mm_movehl_ps(shuf, sums); // [ C D | D+C C+D ]
    // Add the two remaining pairs: [ D+C C+D | B+A+D+C A+B+C+D ]
    sums = _mm_add_ss(sums, shuf);
    return sums;
}

    Compiler Output (gcc 5.3 -O3):

    movaps  xmm1, xmm0
shufps  xmm1, xmm0, 177
addps   xmm0, xmm1
movhlps xmm1, xmm0
addss   xmm0, xmm1

  • __m128 (SSE3): SSE3 introduced _mm_hadd_ps (horizontal add packed single-precision), which simplifies the process.

    __m128 hsum_ps_sse3(__m128 v) {
    // Broadcast elements 3,1 to 2,0
    __m128 shuf = _mm_movehdup_ps(v);
    // Add: sums = [ D+C C+D | B+A A+B ]
    __m128 sums = _mm_add_ps(v, shuf);
    // Move high half to low half
    shuf = _mm_movehl_ps(shuf, sums);
    // Add the two remaining pairs
    sums = _mm_add_ss(sums, shuf);
    return sums;
}

    Advantages of SSE3 _mm_hadd_ps:

    • Minimal code size.
    • Avoids extra MOVAPS instructions on many architectures.
    • _mm_movehdup_ps is a single uop on many CPUs, and _mm_movehl_ps is also efficient.

    A simpler SSE3 approach for summing all elements:

    __m128 v_sum_all = _mm_hadd_ps(v, v);
v_sum_all = _mm_hadd_ps(v_sum_all, v_sum_all);

  • __m256 (AVX): For AVX, you typically extract the high 128-bit lane and combine it with the low 128-bit lane using SSE instructions.

    #ifdef __AVX__
float hsum256_ps_avx(__m256 v) {
    // Extract low 128 bits
    __m128 vlow  = _mm256_castps256_ps128(v);
    // Extract high 128 bits
    __m128 vhigh = _mm256_extractf128_ps(v, 1);
    // Add the two 128-bit lanes
    vlow  = _mm_add_ps(vlow, vhigh);
    // Use the SSE3 approach for the final sum
    return hsum_ps_sse3(vlow); // Inline the SSE3 version for optimal AVX use
}
#endif

    AVX Example using _mm_extractf128_ps and SSE3 summation:

ret
Double-Precision Floating-Point Vectors

  • __m128d (SSE2): For double-precision, there isn’t a direct _mm_hadd_pd. You can use _mm_movehl_ps after casting, or store to memory.

    __m128d hsum_pd_sse2(__m128d vd) { // vd = [ B | A ]
    // Use _mm_undefined_ps as a dummy; only addSD matters
    __m128 undef  = _mm_undefined_ps();
    // Extract high 64 bits using a cast and _mm_movehl_ps
    __m128 shuftmp= _mm_movehl_ps(undef, _mm_castpd_ps(vd));
    __m128d shuf  = _mm_castps_pd(shuftmp);
    // Add the two 64-bit doubles
    return _mm_add_sd(vd, shuf);
}

    Compiler Output (gcc 5.3.0 -O3):

    pxor    xmm1, xmm1          # Zero register xmm1 (for _mm_undefined_ps)
movhlps xmm1, xmm0          # Move high half of xmm0 to low half of xmm1
addsd   xmm0, xmm1          # Add the two doubles

    Alternative using _mm_hadd_pd (SSE3): _mm_hadd_pd is available in SSE3 and offers a more direct approach:

    // Using SSE3's _mm_hadd_pd
__m128d sum_pd_sse3(__m128d vd) {
    vd = _mm_hadd_pd(vd, vd);
    return _mm_hadd_pd(vd, vd); // Sum is now in all elements
}

    Storing to memory: This can sometimes be faster if shuffle ports are a bottleneck.

    double hsum_pd_scalar_sse2(__m128d vd) {
    double tmp;
    // Store the high half to memory
    _mm_storeh_pd(&tmp, vd);
    // Get the low half and add the stored high half
    double lo = _mm_cvtsd_f64(vd);
    return lo + tmp;
}
Integer Vectors

  • __m128i (32-bit Integers): Summing 32-bit integers can be done using integer shuffle and add instructions.

    int hsum_epi32_sse2(__m128i x) {
    // Combine 64-bit halves by shuffling
#ifdef __AVX__
    // AVX 3-operand instructions can save a byte
    __m128i hi64  = _mm_unpackhi_epi64(x, x);
#else
    // SSE2 shuffle for 64-bit halves
    __m128i hi64  = _mm_shuffle_epi32(x, _MM_SHUFFLE(1, 0, 3, 2));
#endif
    // Add the 64-bit halves
    __m128i sum64 = _mm_add_epi32(hi64, x);
    // Shuffle the lower two 32-bit elements
    __m128i hi32  = _mm_shufflelo_epi16(sum64, _MM_SHUFFLE(1, 0, 3, 2));
    // Add the final two 32-bit elements
    __m128i sum32 = _mm_add_epi32(sum64, hi32);
    // Extract the final 32-bit integer
    return _mm_cvtsi128_si32(sum32); // SSE2 movd
}

    Compiler Output (gcc 5.3 -O3):

    pshufd xmm1, xmm0, 0x4e
paddd  xmm0, xmm1
pshuflw xmm1, xmm0, 0x4e
paddd  xmm0, xmm1
movd   eax, xmm0

Alternative Summation Strategies

  • Pairwise Iterative Reduction: For tasks performed repeatedly in time-critical loops, an iterative, pairwise reduction can amortize costs. This involves updating a context vector with incoming data, effectively performing a reduction across iterations.

    // Conceptual example of pairwise reduction
inline __m128 update_context(__m128 context, __m128 data) {
    __m128 evens = _mm_shuffle_ps(context, data, _MM_SHUFFLE(2, 0, 2, 0)); // Interleave evens
    __m128 odds  = _mm_shuffle_ps(context, data, _MM_SHUFFLE(3, 1, 3, 1)); // Interleave odds
    return _mm_add_ps(evens, odds); // Vertical addition
}

    This method is particularly beneficial for smaller element types where multiple rounds of reduction are needed.

  • SSE 4.2 dot4: For summing multiple vectors, consider pre-loading a vector of ones and using _mm_dp_ps (dot product). While it involves extra multiplications, the optimized implementation of dot4 might offer performance benefits by reducing horizontal dependencies.

Performance Considerations

When choosing a method, consider:

  • Code Size: Smaller code is better for instruction cache locality.
  • UOP Cache: Fewer micro-operations (uops) are generally preferred for uop cache efficiency.
  • Latency: The time taken for a single operation.
  • Throughput: How many operations can be performed per clock cycle.

Modern CPUs often handle all SSE shuffles as single uops. For older CPUs, instructions like _mm_movhl_ps might be faster than _mm_shuffle_ps. Careful selection of intrinsics and understanding compiler output (e.g., via tools like Compiler Explorer) are crucial.

Specific Optimizations:
  • Avoiding MOVAPS: On architectures without AVX, carefully chosen shuffles can act as copy-and-shuffles, reducing the need for explicit data copies. Using a temporary register that is no longer needed can save a MOVAPS.
  • Integer Domain vs. FP Domain: On some older CPUs, integer-domain shuffles might have different performance characteristics than floating-point ones.

For a deeper dive into compiler optimizations and intrinsic usage, exploring resources like Agner Fog’s microarchitecture guides and libraries can be highly beneficial. You can often find detailed performance comparisons and assembly output for various intrinsic combinations.

FAQs on Horizontal Vector Summation Techniques

Q: What is the primary goal of horizontal vector summation

ANS: The main objective is to efficiently combine elements spread across different lanes within a SIMD register into a single scalar value or a reduced vector. This is essential for operations like summing array elements, finding maximum/minimum values, or performing dot products across vector lanes.

Q: How does SSE3 simplify horizontal sums compared to SSE1

ANS: SSE3 introduces the _mm_hadd_ps instruction, which directly performs a horizontal addition of packed single-precision floating-point values. This simplifies the code and can be more efficient than the multi-instruction sequences required in SSE1/SSE2 for floating-point types.

Q: Are there differences in summing floating-point and integer vectors

ANS: Yes, the available SIMD instructions and optimal strategies differ. Floating-point summation often uses shuffle and add operations (_mm_add_ps, _mm_add_pd), while integer summation might leverage instructions like _mm_add_epi32, _mm_sad_epu8, or specific shuffle instructions designed for integer data. The absence of overflow in integer operations also requires different handling.

Q: What is the role of `_mm_movehl_ps` in horizontal summation

ANS: _mm_movehl_ps is crucial for moving the high 64 bits of a 128-bit register to the low 64 bits of another. This allows for aligning elements that need to be added together in horizontal reduction operations, especially when direct horizontal add instructions are not available or efficient for the specific data type (like __m128d).

Q: Can AVX instructions improve horizontal summation performance

ANS: AVX extends SIMD registers to 256 bits. For horizontal sums, AVX typically involves extracting the high 128-bit lane using _mm256_extractf128_ps and then combining it with the low 128-bit lane using SSE instructions. This two-stage process can be efficient, especially when AVX’s wider registers reduce the number of overall operations needed for a larger dataset.

Q: What is the `_mm_sad_epu8` instruction used for

ANS: _mm_sad_epu8 (Sum of Absolute Differences of unsigned 8-bit integers) is often used as an initial step for summing 8-bit integer vectors without overflow. It calculates the sum of absolute differences between corresponding bytes in two vectors, producing two 64-bit results. These results can then be further combined.

Q: How can I achieve a horizontal sum in a loop efficiently

ANS: For operations within loops, consider iterative or pairwise reduction techniques. These methods update an accumulator register with new data in each iteration, effectively performing a horizontal reduction across multiple iterations. This can amortize some of the overhead associated with shuffling and adding.

Q: Are there differences in performance based on CPU architecture for these operations

ANS: Yes, performance can vary significantly between different CPU architectures (e.g., Intel vs. AMD, different microarchitectures like Skylake, Zen) due to variations in instruction decoding, execution ports, uop caches, and internal latencies. It’s often recommended to benchmark your code on target hardware.

Q: What are the trade-offs when choosing a horizontal summation method

ANS: Key trade-offs include code size, uop cache utilization, instruction latency, and throughput. For instance, a method with fewer instructions but more uops might be slower on CPUs with limited uop cache. Conversely, a method with larger code size might benefit from better instruction cache locality.

Q: What is `_mm_madd_epi16` used for in horizontal summation

ANS: _mm_madd_epi16 performs a multiply-and-add operation on packed 16-bit integers. It can be used as a widening horizontal add, where it multiplies adjacent pairs of 16-bit integers and then adds the results, producing 32-bit sums. This is a component in summing 16-bit integer vectors.

// Use dummy = a recently-dead variable that vec depends on,
//  so it doesn't introduce a false dependency,
//  and the compiler probably still has it in a register
__m128d highhalf_pd(__m128d dummy, __m128d vec) {
#ifdef __AVX__
    // With 3-operand AVX instructions, don't create an extra dependency on something we don't need anymore.
    (void)dummy;
    return _mm_unpackhi_pd(vec, vec);
#else
    // Without AVX, we can save a MOVAPS with MOVHLPS into a dead register
    __m128 tmp = _mm_castpd_ps(dummy);
    __m128d high = _mm_castps_pd(_mm_movehl_ps(tmp, _mm_castpd_ps(vec)));
    return high;
#endif
}
