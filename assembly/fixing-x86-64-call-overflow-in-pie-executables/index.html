“Fixing x86-64 Call Overflow in PIE Executables: PLT vs GOT Strategies”

How can we properly resolve calls to external dynamic library functions (puts in this case) when compiling with PIE enabled, and what are the alternatives to avoid this 32-bit address space limitation?

Analyzing the Default PIE Behavior and Overflow

By default, recent gcc compilers generate PIE code. When an assembly routine compiled under these settings uses a simple call puts, the linker generates a R_X86_64_PC32 relocation. At runtime, the dynamic linker attempts to resolve puts directly to its address in libc and fix up the relative call. If the distance between the call site and the resolved puts address exceeds the 32-bit signed offset limit ($2^{31}$), the relocation fails or causes a warning, leading the call to jump to an incorrect address because only the lower 32 bits of the target address are correct.

A key observation is that when not using PIE (-no-pie), the linker automatically rewrites the call to use the Procedure Linkage Table (PLT) entry, e.g., call puts@plt. With PIE enabled, this automatic translation often doesn’t occur for direct calls in hand-written assembly, even though a PLT entry exists.

Workarounds for PIE and PIC Code Generation

To ensure correct function resolution in PIE executables or shared libraries, you must explicitly tell the assembler/linker how to reference the external function, bypassing the problematic direct relative call or forcing the use of the PLT or Global Offset Table (GOT) indirectly.

There are three primary methods to handle calls to external functions in PIE-enabled environments, derived from explicit instruction choices:

1. Forcing PLT Indirection (wrt ..plt)

This method explicitly directs the call through the PLT stub, which is designed for lazy dynamic linking.

; Explicitly call through the PLT entry for 'puts'
lea    rdi, [rel message]      ; Load argument (assuming System V ABI)
call   puts WRT ..plt          ; Forces the use of the PLT stub

This mirrors the indirect jump mechanism designed for PIE/PIC code where link-time addresses are unknown.

2. Using the GOT Entry Directly (wrt ..got or [rel puts wrt ..got])

This technique performs an indirect call using the entry for puts already populated (or to be populated) in the Global Offset Table (GOT). This is generally considered slightly more efficient as it avoids the PLT indirection overhead. It utilizes a RIP-relative addressing mode to reach the GOT entry.

; PIE approach similar to gcc -fno-plt style code-gen
lea   rdi, [rel message]
call  [rel  puts wrt ..got]    ; Indirect call via the GOT entry address

The wrt ..got (or using default rel and [rel puts wrt ..got]) ensures the assembler uses the appropriate RIP-relative addressing mode to access the GOT slot containing the final function address.

3. Building Non-PIE Executables (Position-Dependent Code)

The simplest solution, if PIE support is not strictly required, is to instruct the compiler to generate a traditional position-dependent executable. This allows the linker to automatically handle the call puts instruction by rewriting it into call puts@plt.

gcc -no-pie -fno-pie call-lib.c libcall.o -o program

When using -no-pie, the linker resolves the puts symbol to puts@plt automatically for dynamic linking, resolving the overflow issue by using the PLT stub mechanism correctly for static linking or relocatable code. In this non-PIE context, a direct call puts or jmp puts is often sufficient and results in smaller code size when statically linking libc (where the call can resolve directly to the function).

Assembly Best Practices and Alternatives

Several related improvements can enhance the assembly code structure:

  • Data Placement: Place read-only constants like strings in the .rodata section rather than .data.
  • Stack Alignment: Before calling functions that adhere to the System V AMD64 ABI, the stack pointer (RSP) must be 16-byte aligned. A simple sub rsp, 8 (or a dummy push rax if not using a preceding instruction that already adjusted RSP) achieves this if the function caller guarantees alignment on entry.
  • Tail Calling: Instead of call, using jmp puts implements tail-call optimization. This is valid if RSP is correctly positioned (pointing at the return address) upon entry to the current function, as the return address stack slot is effectively overwritten by the target function’s return.

Example Assembly Fragment (NASM Syntax with PIE Options)

For environments where PIE is mandatory, explicitly using the GOT method (-fno-plt equivalent) is favored for performance:

; Ensure RIP-relative addressing is the default for convenience
default rel

section .rodata
message:
  db 'Function invoked successfully', 0

section .text
global entry_point
entry_point:
    ; Align stack (8 bytes used for alignment below)
    sub    rsp, 8                

    ; Setup argument for puts (RDI for first argument)
    lea    rdi, [rel message]      

    ; Solution using GOT for PIE/PIC code (like gcc -fno-plt)
    call  [rel  puts wrt ..got]    ; Indirect call via GOT entry

    ; Restore stack alignment
    add   rsp, 8                  
    ret

C Prototype Consideration

For optimal code generation, especially avoiding unnecessary zeroing of the EAX register before a call, be specific about the function prototype.

  • extern void foo(); implies extern void foo(...); (unspecified arguments).
  • extern void foo(void); explicitly declares no arguments, which can sometimes prevent the compiler from inserting unnecessary setup code, mimicking C++ declaration style.

FAQs on Fixing x86-64 Call Overflow in PIE Executables

Q: Why does gcc default to PIE builds now

ANS: Modern operating systems often enforce Position Independent Executables (PIE) for enhanced security measures like Address Space Layout Randomization (ASLR), making it the default build type for executables.

Q: What is the difference between using WRT ..plt and WRT ..got

ANS: WRT ..plt forces the call through the stub in the Procedure Linkage Table. WRT ..got forces an indirect call using the address stored in the Global Offset Table entry corresponding to the function.

Q: Can I use call puts directly in PIE code

ANS: You can, but it often results in a 32-bit relative jump (rel32) which causes the R_X86_64_PC32 relocation overflow if the target address is too far, unless you statically link the target function into the executable.
