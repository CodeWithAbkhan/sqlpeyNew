“Intel Micro-Fusion: Addressing Modes & Performance Impact”

Delving into the intricate world of CPU microarchitectures, particularly Intel’s processors, reveals fascinating behaviors related to micro-fusion. This process involves combining multiple instructions into a single micro-operation (uop) to enhance execution efficiency. A key factor influencing this behavior is the addressing mode used by instructions. How do different addressing modes impact micro-fusion, and what are the observed performance implications across various Intel microarchitectures like Sandybridge, Haswell, and Skylake?

The core of the matter lies in how instructions are decoded and processed internally. When an instruction uses a simple addressing mode, it might remain fused as a single micro-op throughout its journey. However, more complex addressing modes, such as those involving multiple registers or specific offsets, can trigger un-lamination, where a fused uop is broken back down into multiple uops before execution. This un-lamination can affect the number of uops processed per clock cycle, potentially impacting overall performance, especially in tight loops.

Intel’s optimization manuals, like Section E.1.5 in the Haswell manual and Section E.2.2.4 for Sandybridge, provide insights into this process. However, the exact rules and their evolution across microarchitectures require empirical testing.

How Addressing Modes Influence Micro-Fusion

The impact of addressing modes on micro-fusion can be categorized based on observed behaviors:

  • Simple Addressing Modes: Generally tend to remain micro-fused. Examples include single register addressing or RIP-relative addressing without an immediate.
  • Indexed Addressing Modes: These, which involve a base register, an index register, and potentially a scale factor, are often points of divergence.
    • Sandybridge (SnB) & Ivy Bridge (IvB): Indexed addressing modes are typically un-laminated.
    • Haswell (HSW) & Skylake (SKL): These architectures exhibit more nuanced behavior. They may keep an indexed ALU instruction fused if it has two operands and treats the destination register as a read-modify-write. However, VEX-encoded instructions or those with write-only destinations often do not fuse.

Instructions that May Not Micro-Fuse

Certain instructions, regardless of their addressing mode, are known to never micro-fuse even at the decoder stage. These include instructions with an immediate control operand alongside their typical operands, such as shufps or vinsertf128 when memory operands are involved. Vector shift count instructions accessing memory (PSRLW/D/Q xmm,[mem]) and PMULLD also fall into this category.

Performance Implications: Micro-Fusion vs. Un-lamination

When instructions un-laminate, the number of fused-domain uops processed by the out-of-order core can be affected. Performance counters are crucial for measuring these effects. For instance, the UOPS_ISSUED and UOPS_RETIRED events can reveal differences in fused-domain uop counts.

A loop bottlenecked by the 4-uops-per-cycle issue limit can clearly demonstrate the impact. If an instruction that would normally fuse becomes un-laminated due to its addressing mode, it consumes more resources, potentially leading to a performance degradation. Testing with tools like perf and ocperf.py on Linux, or similar performance analysis tools on other operating systems, allows for direct measurement of these differences.

Practical Code Examples and Testing Methodology

To illustrate these concepts, let’s consider test scenarios using assembly code. The goal is to create loops that are sensitive to the number of fused-domain uops.

Test Program Structure

The provided test program typically involves a loop with simple operations, often padded with nop instructions to control the total number of uops per iteration. Two primary loop variations are usually tested: one using simple addressing modes and another using indexed addressing modes.

Example Assembly Snippet (Illustrative):

section .text
global _start

_start:
    ; Initialization
    xor eax, eax
    xor ebx, ebx
    xor edx, edx
    xor edi, edi
    lea rsi, [rel mydata]   ; Load pointer to data
    mov ecx, 10000000       ; Loop counter

    ; Conditional jump to choose loop type
    cmp dword [rsp], 2      ; Check for command-line arguments
    jge .loop_indexed_address ; Use indexed if args exist

.loop_simple_address:
    ; Simple addressing mode operations
    or eax, [rsi + 0]       ; Access data at offset 0
    or ebx, [rsi + 4]       ; Access data at offset 4
    dec ecx
    nop
    nop
    nop
    nop
    jg .loop_simple_address ; Jump if ECX > 0

    jmp .exit_program

.loop_indexed_address:
    ; Indexed addressing mode operations
    or eax, [rsi + 0 + rdi] ; Indexed access
    or ebx, [rsi + 4 + rdi] ; Indexed access
    dec ecx
    nop
    nop
    nop
    nop
    jg .loop_indexed_address ; Jump if ECX > 0

.exit_program:
    ; Exit syscall
    xor edi, edi
    mov eax, 231    ; sys_exit
    syscall

section .rodata
mydata:
db 0xff, 0xff, 0xff, 0xff, 0xff, 0xff, 0xff, 0xff

When compiled and run, this code can be profiled using performance counters to observe differences in cycle counts and uop issuance based on whether the .loop_indexed_address is taken.

Performance Counter Analysis

The analysis often involves comparing the output of perf stat with specific event counters. Key events to monitor include:

  • task-clock: Total time in milliseconds.
  • cycles: Total CPU cycles.
  • instructions: Total instructions retired.
  • r10e (or similar, depending on the tool): Represents UOPS_ISSUED (fused-domain uops issued to the execution engine).
  • r2c2 (or similar): Represents UOPS_RETIRED:RETIRE_SLOTS (fused-domain uops retired).
  • r1c2 (or similar): Represents UOPS_RETIRED:ALL (all uops retired, including unfused).
  • stalled-cycles-frontend: Cycles where the frontend pipeline was stalled.
  • stalled-cycles-backend: Cycles where the backend execution units were stalled.

Hypothetical Counter Results Comparison:

  • Simple Addressing Mode Loop: Might show a lower cycle count and UOPS_ISSUED count closer to the number of instructions.
  • Indexed Addressing Mode Loop (on older CPUs): Could exhibit a higher cycle count and a UOPS_ISSUED count significantly greater than the instruction count, indicating un-lamination.
  • Indexed Addressing Mode Loop (on newer CPUs): May show cycle counts and UOPS_ISSUED similar to the simple addressing mode, suggesting successful fusion.

Alternative Approaches to Testing

While the above assembly approach is direct, higher-level languages can also be used to explore these concepts, albeit with less direct control over the generated machine code. For instance, writing C or C++ loops with different memory access patterns and analyzing their performance using profiling tools can provide insights.

However, for precise microarchitectural analysis, assembly is often preferred. Tools like Intel’s IACA (Integrated Intel Architecture Code Analyzer) can also predict the performance of code snippets, though empirical testing remains the definitive validation.

Specific Microarchitecture Behaviors

The behavior of micro-fusion across different Intel microarchitectures has evolved:

  • Sandybridge (SnB) & Ivy Bridge (IvB): Indexed addressing modes are generally un-laminated.
  • Haswell (HSW) & Skylake (SKL): These architectures show improved fusion capabilities for some indexed addressing modes, especially two-operand ALU instructions that perform read-modify-write operations. However, VEX-encoded instructions and others with specific operand counts might still un-laminate.
  • Broadwell: Generally expected to behave similarly to Skylake in this regard.

Instructions that persist as multiple uops:

  • mov [rax], edi (store): Typically 1 fused-domain, 2 unfused (SnB/HSW/SKL).
  • add edx, [rsp+rsi] (normal ALU + memory): SnB un-laminates, HSW/SKL fuses.
  • vfmadd213ps xmm0,xmm0,[0+rdi*4] (indexed memory): Un-laminated on HSW/SKL.
  • blsi edi, [rdi+rsi] (indexed memory): Un-laminated on HSW/SKL.
  • adc eax, [rdi+rsi] / cmove ebx, [rdi+rax]: Behavior varies significantly between SnB, HSW, and SKL.
  • add [rdi+rsi], eax (memory destination): HSW/SKL shows 3 fused-domain, 4 unfused.

RIP-Relative Addressing:

  • RIP-relative addressing with an immediate constant often fails to micro-fuse even in the decoders/uop cache on modern Intel CPUs (Agner Fog’s testing).
  • RIP-relative addressing without an immediate constant can micro-fuse.

Macro-fusion: Combinations like cmp/jcc or dec/jcc can undergo macro-fusion, resulting in a single uop that is preserved even in the unfused domain.

Addressing Micro-Fusion Challenges

When aiming for peak performance, understanding these fusion behaviors is critical for optimizing loops and critical code paths. Strategies may include:

  1. Prioritizing Simple Addressing Modes: Where possible, favor single-register addressing or RIP-relative addressing without immediates.
  2. Loop Unrolling: For complex addressing modes that un-laminate, judicious loop unrolling might help manage the increased number of uops per iteration, especially if the loop body is short.
  3. Register Allocation: Careful register allocation can influence addressing mode choices.
  4. Compiler Flags: Experiment with compiler optimization flags (e.g., -O3 in GCC/Clang) to see how the compiler handles these scenarios. Sometimes, the compiler might automatically choose simpler addressing modes when beneficial.

FAQs on Intel Micro-Fusion and Addressing Modes

Q: What is micro-fusion in Intel CPUs

ANS: Micro-fusion is a technique where Intel CPUs combine multiple instructions into a single micro-operation (uop) during the decoding stage to improve processing efficiency and reduce the number of internal operations.

Q: How do addressing modes affect micro-fusion

ANS: The complexity of an addressing mode can influence whether an instruction remains fused or gets un-laminated into multiple uops. Simple addressing modes are more likely to stay fused, while indexed or complex modes might cause un-lamination on certain Intel microarchitectures.

Q: Which Intel CPU generations are discussed regarding micro-fusion

ANS: The content discusses Sandybridge (SnB), Ivy Bridge (IvB), Haswell (HSW), and Skylake (SKL) microarchitectures, noting the evolution of micro-fusion behavior across these generations.

Q: What is un-lamination

ANS: Un-lamination is the process where a micro-fused instruction is broken back down into multiple individual micro-operations before being dispatched to the execution units. This often happens with complex addressing modes on older Intel CPUs.

Q: Are there instructions that never micro-fuse

ANS: Yes, some instructions like shufps with memory operands or those with immediate control operands may never micro-fuse, regardless of the addressing mode.

Q: How can I measure the impact of micro-fusion

ANS: Performance counters, such as UOPS_ISSUED and UOPS_RETIRED, combined with profiling tools like perf on Linux, can be used to measure the number of fused-domain uops and assess performance differences.

Q: Does micro-fusion increase instruction latency

ANS: Micro-fusion itself does not typically increase the latency of an instruction; it’s a way to streamline internal processing. Latency is more related to the instruction’s inherent execution time and pipeline dependencies.

Q: What is the difference between micro-fusion and macro-fusion

ANS: Micro-fusion combines instructions into uops internally. Macro-fusion combines simple instructions (like compare and branch) into a single, larger uop that is treated as one unit throughout the pipeline.

Q: Are RIP-relative addressing modes with immediates fused

ANS: Generally, RIP-relative addressing modes that include an immediate constant tend not to micro-fuse, even at the decoder stage, according to experimental data.

Q: What are the performance counter events for tracking uops

ANS: Key events include UOPS_ISSUED (fused-domain uops issued) and UOPS_RETIRED:RETIRE_SLOTS (fused-domain uops retired). The exact names or aliases might vary slightly based on the performance monitoring unit (PMU) and the profiling tool used.
