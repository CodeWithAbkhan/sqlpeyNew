“x86-64: Efficiently Load Static Addresses into Registers”

Q: What are the primary considerations for loading static addresses into registers on x86-64

ANS: On x86-64, most immediates and displacements are kept at 32-bits to conserve code size. This affects how static addresses are loaded into registers. Using full 64-bit addresses can significantly increase the instruction cache footprint and fetch/decode bandwidth, impacting performance. Understanding these trade-offs is crucial for efficient code generation. For more on x86 architecture, see the x86 tag wiki .

Q: How does LEA with RIP-relative addressing work for static data

ANS: RIP-relative LEA is the standard and efficient method. It uses a 32-bit relative displacement from the instruction pointer’s current position, similar to how jmp or call instructions operate. This approach can access any static data within .data, .bss, .rodata, or functions in .text, provided the total size of static code and data stays within the typical 2GiB limit. This method is compatible with address space layout randomization (ASLR).

Q: What are the syntax variations for RIP-relative LEA across different assemblers

ANS: The syntax for RIP-relative LEA varies. Here are common examples:

  • AT&T syntax (GAS): 
      lea main(%rip), %r10
  • GAS with Intel syntax (.intel_syntax noprefix): 
      lea  r10, [rip+main]
  • NASM: 
      lea  r10, [rel main]
    (NASM also defaults to RIP-relative for [main])
  • FASM: 
      lea  r10, [main]
    (FASM defaults to RIP-relative)
  • MASM: Syntax is similar to NASM, often defaulting to RIP-relative.

For a deeper dive into these syntaxes, refer to How do RIP-relative variable references like “[RIP + _a]” in x86-64 GAS Intel-syntax work? . The reasons behind RIP-relative addressing are explained in Why are global variables in x86-64 accessed relative to the instruction pointer? .

Q: When can 32-bit absolute addressing be used and what are its benefits

ANS: In position-dependent code (like executables built with gcc -fno-pie -no-pie), 32-bit absolute addressing can be employed on Linux to reduce code size. The mov r32, imm32 instruction generally has better throughput on Intel/AMD CPUs compared to RIP-relative LEA, potentially allowing for better overlap with surrounding instructions in out-of-order execution. While code size optimization is often secondary, it can be beneficial when all other factors are equal or favorable.

It’s important to note that modern Linux distributions often default to Position Independent Executables (PIE), which rely on relative addressing. If you encounter link errors related to -fPIC when using 32-bit absolute addresses, it’s likely due to this PIE default. Check out 32-bit absolute addresses no longer allowed in x86-64 Linux? .

Q: What are the most efficient ways to use 32-bit absolute addresses

ANS: In a non-PIE executable on Linux, using mov imm32 into a 32-bit register is highly efficient, mirroring practices in 32-bit code.

Here are examples:

  • GAS AT&T syntax: 
    mov  $main, %r10d        # 6 bytes
mov  $main, %edi         # 5 bytes (no REX prefix needed for legacy registers)
  • GAS Intel syntax: 
    mov  edi, OFFSET main
  • NASM/FASM: 
    mov  edi, main

Writing to any 32-bit register automatically zero-extends the value into the full 64-bit register (e.g., R10 or RDI). Using lea main, %edi or lea main, %rdi also works in non-PIE Linux executables, but mov is generally preferred over lea with disp32 absolute addressing for performance. For clarity, the operand-size suffix (like l or q) is often omitted when the register operand implies it.

Q: What are the inefficient methods for loading static addresses and why should they be avoided

ANS: The most inefficient method is using a 10-byte movabs $imm64, %reg instruction. This explicitly encodes the full 64-bit absolute address as an immediate, leading to significantly larger code.

  • Inefficient Example: 
    movabs  $main, %r10

This is often produced by assemblers like NASM when mov rdi, main is used instead of mov edi, main. While Linux dynamic linking can handle runtime fixups for 64-bit absolute addresses, this is typically for jump tables, not for general immediate values.

Another less efficient approach is movq $sign_extended_imm32, %reg (7 bytes). This uses a 32-bit absolute address but involves a sign-extended move to a 64-bit register, which is less optimal than the implicit zero-extension achieved by writing to a 32-bit register (mov r32, imm32). This encoding is primarily relevant for kernel code targeting the upper 2GiB of virtual address space. For standard user-space code within the lower 2GiB, mov r32, imm32 is superior.

You can explore the differences between movq and movabsq in x86-64 at Difference between movq and movabsq in x86-64 .

Q: How does Windows handle static address loading compared to Linux

ANS: On Windows, executables can be built as “large address aware.” If not flagged as such, addresses are typically constrained to fit within 32 bits. While RIP-relative LEA works on Windows for address space layout randomization (ASLR) compatibility, the behavior of mov $imm32, %r32 with runtime fixups in Windows x64 executables and DLLs isn’t as definitively documented as in Linux. For scenarios requiring the use of 64-bit absolute addresses, such as in specific memory or code models beyond the “small” or “small-PIC” models, movabs $imm64 might be necessary, though it’s less common. For JIT compilation scenarios, consider placing the JIT buffer near existing code to leverage relative calls, otherwise, movabs a pointer into a register.

The choice between RIP-relative LEA and 32-bit absolute addressing depends on your target environment (OS, PIE status) and your primary optimization goal (code size, execution speed, or both). RIP-relative LEA offers broad compatibility and is the modern standard for accessing static data, while 32-bit absolute mov can provide minor performance and size benefits in specific, non-PIE contexts.
