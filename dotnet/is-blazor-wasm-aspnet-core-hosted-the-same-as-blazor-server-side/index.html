Is Blazor WASM ASP.NET Core Hosted the Same as Blazor Server Side?

Are you wondering whether Blazor WebAssembly (WASM) hosted with ASP.NET Core is similar to Blazor Server Side? Both models are used in Blazor applications, but they function quite differently in terms of server interaction and client-side processing. This deep dive will explain how each model works and how they differ, especially when scaling to a large number of simultaneous users.

Summary

In this post, we compare the Blazor WASM ASP.NET Core Hosted and Blazor Server Side models. These two approaches handle requests in distinct ways, especially when dealing with high user concurrency. This article breaks down how each model interacts with the server, the client, and Web APIs, and whether your server will create multiple instances when handling several users.

Practical Examples

What Happens on the Server Side for Blazor Server?

Blazor Server runs the entire application logic on the server. When a user interacts with the Blazor app, the server creates an instance to handle the request. But is it true that the server creates an entirely new instance for each interaction?

The answer is no. While each user establishes a SignalR connection with the server, the server does not create a fresh instance for every action. Instead, the server creates a circuit object for each user connection, which keeps track of the user’s session and app state.

// Server-side Blazor: Managing app state via SignalR connection
@page "/counter"
<h1>Counter</h1>
<p>Current count: @_a.CurrentCount</p>
<button class="btn btn-primary" @onclick="_b.IncrementCount">Click me</button>

@functions {
    private readonly ClassA _a = new ClassA();
    private readonly ClassB _b = new ClassB(_a);

    class ClassA
    {
        public int CurrentCount { get; set; }
    }

    class ClassB
    {
        private readonly ClassA _classA;

        public ClassB(ClassA classA)
        {
            _classA = classA;
        }

        public void IncrementCount() => _classA.CurrentCount++;
    }
}

Here, the server creates a Circuit for each client, which allows the app state to persist across multiple interactions, avoiding the need to reload the entire app for each click.

How Does the Blazor WASM ASP.NET Core Hosted Model Work?

Blazor WebAssembly (WASM) in the ASP.NET Core hosted model is quite different. The server only provides the app files (HTML, CSS, JS) to the client’s browser when they first request the app. Once the app is loaded, the execution happens entirely on the client-side.

When users send requests to the server (for example, calling a Web API), the client browser makes an HTTP request, much like an AJAX call.

// Example of calling an API from Blazor WebAssembly
async function fetchData() {
  const response = await fetch('/api/values');
  const data = await response.json();
  console.log(data);
}

In the case of Blazor WASM, the WebAssembly app uses the Fetch API under the hood to interact with Web API endpoints. The server isn’t involved in processing these requests or maintaining app state.

How Are Server Resources Managed for Each Approach?

With Blazor Server, every user’s app state is managed on the server. If there are thousands of users, the server maintains separate circuits for each connection, but doesn’t recreate the app for each user interaction. This can be resource-intensive, but the server is optimized to handle large numbers of connections simultaneously.

In contrast, with Blazor WASM, the app runs entirely in the browser, and each user interacts with the server as a stateless Web API, meaning the server doesn’t need to manage a circuit or track session data.

Answering Key Questions

Q1: Is the server in the Blazor WASM hosted model similar to a .NET Core API?

Yes, the server in the Blazor WASM hosted model functions like a traditional .NET Core Web API. It serves static content (the Blazor app) and handles HTTP requests from the client but doesn’t maintain state or manage user sessions. This is different from Blazor Server, where the server manages app state and user connections.

Q2: Does Blazor WASM hosted model offer any advantages over Blazor Server?

One advantage of the Blazor WASM hosted model is that the app runs entirely in the user’s browser, reducing the server’s workload. This can be beneficial for scaling to a large number of users without burdening the server with managing app state for each user. It’s ideal for situations where you want a more client-heavy architecture.

Q3: How do the two models differ in terms of performance?

Blazor Server may face performance bottlenecks when handling a high number of users because it requires SignalR connections and maintains the app state on the server. On the other hand, Blazor WASM is lighter on the server but may lead to increased initial loading times as the app is downloaded and executed in the browser.

Q4: Can you use Blazor Server for millions of users?

Blazor Server is not ideal for handling millions of simultaneous users. The server needs to maintain a circuit for each user, and this can be demanding on server resources. If scaling is a priority, you may need to look into more specialized solutions or use Blazor WASM.

Q5: Which Blazor model should you use for your project?

  • If you need real-time interactions and want to manage app state server-side, Blazor Server is a good option.
  • If you want to minimize server load and run the app entirely on the client, Blazor WASM hosted is better, particularly for apps with heavy client-side logic.

FAQs on Blazor WASM vs Blazor Server

Q: Is Blazor WASM better for high traffic apps?

ANS: Blazor WASM is better for handling high traffic because it moves most of the processing to the client, reducing the load on the server. This makes it more scalable compared to Blazor Server, where each user interaction requires resources from the server.

Q: How does the Blazor Server model manage multiple users?

ANS: The Blazor Server model uses SignalR connections and creates a circuit for each user, allowing the server to manage multiple users by maintaining their individual sessions without creating a new instance for every interaction.

Q: What is the Fetch API in Blazor WASM?

ANS: The Fetch API in Blazor WASM allows the client-side Blazor application to make HTTP requests to a Web API, similar to traditional JavaScript applications. It enables asynchronous communication between the client and the server without reloading the page.

Q: Does Blazor WASM require SignalR for real-time updates?

ANS: No, Blazor WASM does not use SignalR for real-time communication. It relies on regular HTTP requests to interact with the server, unlike Blazor Server, which uses SignalR for real-time updates and interactions.

Q: Can I host Blazor WASM and Blazor Server on the same server?

ANS: Yes, you can host both Blazor WASM and Blazor Server on the same server, but they will operate independently. Blazor WASM runs client-side, while Blazor Server operates server-side and uses SignalR for communication.
