Solved: How to Implement Graph API in Blazor Server with .NET 6

Summary

Are you struggling to integrate the Microsoft Graph API into your Blazor Server app using .NET 6? Many developers face challenges when transitioning from older versions of .NET or Blazor WebAssembly (WASM) to the latest Blazor Server setups. This post provides a detailed solution to the common issues encountered when working with Graph API in Blazor Server, offering step-by-step guidance on how to resolve errors and make the integration work smoothly.

How Do You Integrate Microsoft Graph API in a Blazor Server App with .NET 6?

If you are working with Blazor Server apps and .NET 6, you may have encountered some issues with Microsoft Graph API integration, especially when searching for relevant documentation. The integration steps that worked in .NET 5 or older versions may not directly apply to .NET 6. So, how do you resolve these issues and implement Graph API in a Blazor Server app with .NET 6?

Why Is the Microsoft Graph API Integration in Blazor Server Different in .NET 6?

Blazor Server apps in .NET 6 have evolved from previous versions, and one of the significant changes is the shift from Startup.cs to Program.cs for configuration. In older versions, the Graph API and authentication services were set up in the Startup.cs file, but in .NET 6, this configuration has been moved to the Program.cs file.

This transition can create issues, especially when developers try to use older documentation, which relies on the Startup.cs file, or when they attempt to follow Blazor WebAssembly-specific tutorials.

What Common Errors Are Encountered During Integration?

A frequent error that developers face when trying to integrate Graph API in Blazor Server apps with .NET 6 is:

“There is no registered service of type ‘Microsoft.Identity.Web.ITokenAcquisition’”

This error typically occurs when authentication services are not properly registered in the dependency injection (DI) container, or when Graph API integration steps are not correctly followed. The solution involves configuring the appropriate services in Program.cs.

How to Correctly Configure Microsoft Graph API in Blazor Server with .NET 6

Let’s break down how to configure Graph API and Microsoft.Identity.Web in a Blazor Server app with .NET 6. The solution involves adding the necessary services and authentication configurations to Program.cs.

Step 1: Install Required NuGet Packages

Before proceeding, ensure that you have the following NuGet packages installed:

  • Microsoft.Identity.Web
  • Microsoft.Graph

These packages are essential for Graph API integration and authenticating users with Azure Active Directory (AAD).

dotnet add package Microsoft.Identity.Web
dotnet add package Microsoft.Graph

Step 2: Modify Program.cs to Add Required Services

In .NET 6, all configurations are done in Program.cs, not Startup.cs. Below is an updated code snippet to show how you can configure Graph API services:

using Microsoft.Identity.Web;
using Microsoft.Graph;

var builder = WebApplication.CreateBuilder(args);

// Add authentication services
builder.Services.AddMicrosoftIdentityWebAppAuthentication(builder.Configuration)
    .EnableTokenAcquisitionToCallDownstreamApi()
    .AddMicrosoftGraph(builder.Configuration.GetSection("GraphAPI"))
    .AddInMemoryTokenCaches();

// Add Blazor services
builder.Services.AddRazorComponents()
    .AddInteractiveServerComponents();

// Build the application
var app = builder.Build();

// Middleware for authentication
app.UseAuthentication();
app.UseAuthorization();

app.MapBlazorHub();
app.MapFallbackToPage("/_Host");

app.Run();

Code Explanation:

  • Authentication Setup (AddMicrosoftIdentityWebAppAuthentication): Registers Microsoft Identity Web authentication middleware with your Blazor Server app. This ensures that users can authenticate via Azure AD.
  • Token Acquisition (EnableTokenAcquisitionToCallDownstreamApi): Configures token acquisition, enabling your app to acquire tokens to call Graph API.
  • Graph API Service (AddMicrosoftGraph): Registers Graph API services to interact with Microsoft Graph. You can configure specific API settings in the app’s appsettings.json file.
  • Token Caching (AddInMemoryTokenCaches): Caches tokens in memory for faster retrieval.
  • Blazor Services (AddRazorComponents): Configures services required for Blazor Server, including server-side Blazor components.

Step 3: Configure appsettings.json for Graph API

Next, configure your appsettings.json file to include your Graph API details:

{
  "GraphAPI": {
    "Scopes": [
      "User.Read",
      "Mail.Read"
    ]
  }
}
  • Scopes: The permissions your app needs to access data through Microsoft Graph (such as reading user profile or email data).

Step 4: Implementing Graph API Calls in Components

Once the configuration is set up, you can call the Graph API from your Blazor components. Here’s an example of fetching user details from Microsoft Graph:

@page "/graph"

@using Microsoft.Graph
@inject ITokenAcquisition TokenAcquisition
@inject GraphServiceClient GraphServiceClient

<h3>Microsoft Graph API Example</h3>

<button class="btn btn-primary" @onclick="GetUserData">Get User Info</button>

@if (user != null)
{
    <p>Name: @user.DisplayName</p>
    <p>Email: @user.UserPrincipalName</p>
}

@code {
    private User? user;

    private async Task GetUserData()
    {
        var accessToken = await TokenAcquisition.GetAccessTokenForUserAsync(new[] { "User.Read" });
        GraphServiceClient.AuthenticationProvider = new DelegateAuthenticationProvider(
            requestMessage => {
                requestMessage.Headers.Authorization = new System.Net.Http.Headers.AuthenticationHeaderValue("Bearer", accessToken);
                return Task.CompletedTask;
            });

        user = await GraphServiceClient.Me.Request().GetAsync();
    }
}

Code Breakdown:

  • ITokenAcquisition: Injected to acquire tokens for API calls.
  • GraphServiceClient: Used to interact with Microsoft Graph API.
  • GetUserData: Fetches the authenticated user’s data (such as name and email) from Graph API when the button is clicked.
  • DelegateAuthenticationProvider: Sets the authentication header with the acquired access token for making Graph API requests.

Alternative Ways to Implement Graph API in Blazor Server

If you don’t want to use the Microsoft.Identity.Web library or you face compatibility issues, there are alternative approaches for integrating Graph API with Blazor Server:

  1. Manual Authentication with OAuth2 – Implement OAuth2 flow manually using libraries like IdentityModel for authentication, but this requires more setup and management.
  2. Server-Side Token Management – Store access tokens server-side and pass them to Blazor components via a service to reduce client-side complexities.

FAQs on How to Implement Graph API in Blazor Server with .NET 6

Q: Why is Graph API integration difficult in Blazor Server with .NET 6?

ANS: The integration process changed from earlier versions due to the move from Startup.cs to Program.cs in .NET 6. Additionally, older documentation may not be fully compatible with .NET 6-specific configurations.

Q: How do I resolve the 'No registered service' error in Blazor?

ANS: This error occurs when Microsoft Identity services are not registered correctly. Make sure to configure services properly in Program.cs and add the required packages like Microsoft.Identity.Web.

Q: What permissions should I request for Graph API?

ANS: It depends on your app’s needs. For basic user information, the User.Read scope is sufficient. You can extend it to other scopes like Mail.Read or Mail.Send depending on the functionality you need.

Q: Can I use Blazor Server with Graph API for large-scale production applications?

ANS: Yes, Blazor Server with Graph API can scale for larger applications, but you should ensure proper error handling, caching, and performance optimization for production use.

Q: Is it necessary to use Microsoft.Identity.Web for Graph API?

ANS: While not strictly necessary, Microsoft.Identity.Web simplifies authentication with Azure AD and token management, making it a preferred choice for most developers.
