Deploying a Blazor application in a web farm environment can lead to issues with antiforgery tokens. These tokens are crucial for preventing cross-site request forgery (CSRF) attacks. However, when multiple servers are involved, token validation can fail if not handled properly. This guide will walk you through five steps to manage antiforgery tokens effectively in a Blazor web farm setup using .NET 8.

Top 5 Steps to Handle Antiforgery Tokens in Blazor Web Farms

Step 1: Understanding the Antiforgery Token Issue

In a web farm environment, each server generates its own set of antiforgery tokens. If a user’s request is processed by a different server than the one that generated the token, validation fails, resulting in errors.

Step 2: Setting Up Data Protection for Key Sharing

To ensure all servers can validate antiforgery tokens consistently, they need to share a common set of keys.

## Install the required NuGet package
dotnet add package Microsoft.AspNetCore.DataProtection

Explanation: This installs the Data Protection library, which is essential for sharing keys across multiple servers.

Step 3: Configuring Data Protection to Use a Common Storage

Store the Data Protection keys in a shared location like a database, Azure Key Vault, or a network share.

Using Azure Key Vault

public void ConfigureServices(IServiceCollection services)
{
    services.AddDataProtection()
        .PersistKeysToAzureBlobStorage(new Uri("https://<storage-account-name>.blob.core.windows.net/<container-name>/keys.xml"))
        .ProtectKeysWithAzureKeyVault(new Uri("https://<key-vault-name>.vault.azure.net/keys/<key-name>"), new DefaultAzureCredential());
}

Explanation: This configuration uses Azure Blob Storage to persist the keys and Azure Key Vault for key encryption.

Using SQL Server

public void ConfigureServices(IServiceCollection services)
{
    services.AddDataProtection()
        .PersistKeysToDbContext<DataProtectionKeyContext>();
}

Explanation: This configuration uses SQL Server to store the keys. The DataProtectionKeyContext is a custom DbContext that you define to manage key storage.

Step 4: Setting Up the Database Context for Data Protection Keys

If using SQL Server, define the DataProtectionKeyContext.

public class DataProtectionKeyContext : DbContext
{
    public DataProtectionKeyContext(DbContextOptions<DataProtectionKeyContext> options) : base(options) { }

    public DbSet<DataProtectionKey> DataProtectionKeys { get; set; }
}

public class Startup
{
    public void ConfigureServices(IServiceCollection services)
    {
        services.AddDbContext<DataProtectionKeyContext>(options =>
            options.UseSqlServer(Configuration.GetConnectionString("DefaultConnection")));

        services.AddDataProtection()
            .PersistKeysToDbContext<DataProtectionKeyContext>();
    }
}

Explanation: This context is responsible for storing and retrieving Data Protection keys from the database.

Step 5: Configuring Antiforgery Services

Ensure the antiforgery services are correctly set up to use the shared keys.

public void ConfigureServices(IServiceCollection services)
{
    services.AddControllersWithViews()
        .AddRazorRuntimeCompilation();

    services.AddAntiforgery(options =>
    {
        options.Cookie.Name = "X-CSRF-TOKEN";
        options.FormFieldName = "AntiforgeryField";
        options.HeaderName = "X-CSRF-TOKEN";
    });
}

Explanation: This configuration sets up antiforgery token options to ensure consistent naming across requests.

Practical Example

Here’s a complete example incorporating all steps for a SQL Server-based solution:

public class DataProtectionKeyContext : DbContext
{
    public DataProtectionKeyContext(DbContextOptions<DataProtectionKeyContext> options) : base(options) { }

    public DbSet<DataProtectionKey> DataProtectionKeys { get; set; }
}

public class Startup
{
    public void ConfigureServices(IServiceCollection services)
    {
        services.AddDbContext<DataProtectionKeyContext>(options =>
            options.UseSqlServer(Configuration.GetConnectionString("DefaultConnection")));

        services.AddDataProtection()
            .PersistKeysToDbContext<DataProtectionKeyContext>();

        services.AddControllersWithViews()
            .AddRazorRuntimeCompilation();

        services.AddAntiforgery(options =>
        {
            options.Cookie.Name = "X-CSRF-TOKEN";
            options.FormFieldName = "AntiforgeryField";
            options.HeaderName = "X-CSRF-TOKEN";
        });
    }

    public void Configure(IApplicationBuilder app, IWebHostEnvironment env)
    {
        if (env.IsDevelopment())
        {
            app.UseDeveloperExceptionPage();
        }
        else
        {
            app.UseExceptionHandler("/Home/Error");
            app.UseHsts();
        }
        app.UseHttpsRedirection();
        app.UseStaticFiles();

        app.UseRouting();

        app.UseAuthentication();
        app.UseAuthorization();

        app.UseEndpoints(endpoints =>
        {
            endpoints.MapControllerRoute(
                name: "default",
                pattern: "{controller=Home}/{action=Index}/{id?}");
        });
    }
}

Explanation: This example configures a Blazor application to use SQL Server for storing Data Protection keys and sets up antiforgery token services.

Alternative Ways

Using File System for Key Storage

For simpler setups, you can use the file system to store keys.

public void ConfigureServices(IServiceCollection services)
{
    services.AddDataProtection()
        .PersistKeysToFileSystem(new DirectoryInfo(@"\\server\share\keys\"));
}

Explanation: This configuration uses a network share to store Data Protection keys, which is suitable for smaller deployments.

FAQs on “Top 5 Steps to Handle Antiforgery Tokens in Blazor Web Farms”

Q: Can I use different storage options for Data Protection keys?

ANS: Yes, you can use Azure Blob Storage, Azure Key Vault, SQL Server, or a network share to store Data Protection keys.

Q: How does Data Protection work in a web farm?

ANS: Data Protection ensures all servers in a web farm use the same set of keys for encrypting and decrypting data, enabling consistent antiforgery token validation.

Q: What are the common issues with antiforgery tokens in a web farm?

ANS: The most common issue is the failure to validate tokens when different servers handle requests without shared keys.

Q: How can I store Data Protection keys in SQL Server?

ANS: Use the PersistKeysToDbContext method with a custom DbContext to store keys in SQL Server.

Q: Can I use the file system for Data Protection key storage?

ANS: Yes, you can use a file system or network share for key storage, though it is more suitable for smaller setups.
