Solved How to Use Blazor Server Side and WebAssembly for Different Authentication

In this article, we explore how to upgrade your Blazor application to use Blazor Server-Side for your back-office system and Blazor WebAssembly for your client-facing application, while also incorporating separate authentication mechanisms for both. This setup is an excellent way to modernize your system and utilize the full power of .NET 5 with Blazor.

Summary

As a beginner working with Blazor, you may be asking if it’s possible to use Blazor Server-Side for your back office system and Blazor WebAssembly (WASM) for the client-facing system while setting up different authentication models. The short answer is yes—this is a feasible approach. In this post, we will explain how the two flavors of Blazor differ and how to integrate them with distinct authentication mechanisms.

What are the differences between Blazor Server-Side and Blazor WebAssembly?

1. Blazor Server-Side

In Blazor Server-Side, the application runs on the server and uses SignalR to establish a real-time connection between the client and server. User interactions are sent to the server over this connection, where processing happens, and the updated UI is sent back to the client.

  • How does it work?

    • The browser acts as a thin client, meaning the processing is done entirely on the server.
    • The UI is updated on the client side via SignalR connections.

  • Advantages:

    • Lower resource consumption on the client side, making it ideal for less powerful devices.
    • Easier to manage authentication and state across users as everything resides on the server.

  • Disadvantages:

    • Requires a constant and low-latency connection. If the client’s connection quality is poor or the ping exceeds 200 ms, it could result in a suboptimal experience.
    • Scalability may be an issue for large numbers of concurrent users due to server load.

2. Blazor WebAssembly (WASM)

On the other hand, Blazor WebAssembly (WASM) allows you to run Blazor code directly in the browser. It compiles your Blazor app into WebAssembly, allowing the client to execute most of the logic locally.

  • How does it work?

    • The application is downloaded and executed on the client side, which means the server only provides the initial setup and any necessary APIs (e.g., for data).

  • Advantages:

    • Less dependency on server resources, as most of the logic is handled on the client.
    • It offers the potential for offline usage since the application runs fully in the browser.

  • Disadvantages:

    • Larger initial download sizes, as the Blazor WebAssembly app needs to be downloaded to the client.
    • Limited access to system resources compared to a server-side environment, as it operates within the sandboxed environment of the browser.

Can I use Blazor Server-Side for the Back Office and WebAssembly for the Client User App?

Yes, this is absolutely possible. By using Blazor Server-Side for the back office, you can ensure that all sensitive operations, such as database management and business logic, are securely processed on the server. The Blazor WebAssembly front-end allows for a more interactive and faster user experience, processing locally on the client’s device.

How to integrate Blazor Server-Side and WebAssembly:

  • You can design your back office system to use Blazor Server-Side. Here, the server will handle user input and output processing.
  • Your client-facing app can be developed using Blazor WebAssembly, which runs directly in the browser, reducing the dependency on the server.

In this setup, you can still use SignalR for real-time communication between the back office (server-side) and the client-side application. The two will communicate via REST APIs or other services, such as gRPC, ensuring they remain decoupled.

Can I use Different Authentication Models for Blazor Server-Side and WebAssembly?

Yes, you can implement different authentication methods for Blazor Server-Side and WebAssembly. Here’s how:

1. Authentication for Blazor Server-Side

In Blazor Server-Side, the authentication can be managed using ASP.NET Core Identity or any other server-side authentication mechanism. Since the application is running on the server, it’s straightforward to implement session-based or cookie-based authentication.

Example of a basic authentication setup:

@using Microsoft.AspNetCore.Components.Authorization
@inject AuthenticationStateProvider AuthenticationStateProvider

<button @onclick="Login">Login</button>

@code {
    private async Task Login()
    {
        var authState = await AuthenticationStateProvider.GetAuthenticationStateAsync();
        if (!authState.User.Identity.IsAuthenticated)
        {
            // Perform login action (e.g., using external identity providers)
        }
    }
}

2. Authentication for Blazor WebAssembly

In contrast, WebAssembly applications require client-side authentication, which often means using OAuth, OpenID Connect, or JWT (JSON Web Tokens) to manage authentication and authorization.

You can use external identity providers (like Google, Facebook, or Azure AD) in your WebAssembly app. For example:

@inject IAccessTokenProvider TokenProvider

<button @onclick="LoginWithGoogle">Login with Google</button>

@code {
    private async Task LoginWithGoogle()
    {
        var tokenResult = await TokenProvider.RequestAccessToken();
        if (tokenResult.TryGetToken(out var token))
        {
            // Handle token and make authenticated API requests
        }
    }
}

This ensures that the authentication flow is separate between the back office (Blazor Server-Side) and the client-facing app (WebAssembly), each handling it according to their environment.

Practical Example of Combining Blazor Server-Side and WebAssembly

  1. Blazor Server-Side Back Office:
    The server is used for managing admin tasks such as product management, employee records, and other data-sensitive tasks.

  2. Blazor WebAssembly Client App:
    The client-facing app provides users with a modern, fast experience by offloading processing to the browser while still using REST APIs for data.

// Server-side component
@page "/admin"
@inject NavigationManager Navigation
<button @onclick="NavigateToClientApp">Go to Client App</button>

@code {
    private void NavigateToClientApp()
    {
        Navigation.NavigateTo("https://clientapp.com");
    }
}

Alternative Ways: What other methods can I use for this setup?

  1. Single Authentication Mechanism for Both:
    You could opt for a unified authentication model where both Blazor Server-Side and WebAssembly share the same authentication system (e.g., using JWT across both environments). This could simplify the overall system.

  2. Shared API between Server-Side and WebAssembly:
    You can create a shared API that both Blazor Server and WebAssembly can call for data. This API could be based on REST or gRPC, providing a clean separation between front-end and back-end.

FAQs on Blazor Server-Side and WebAssembly Authentication

Q: Can I use Blazor Server-Side for the back office and Blazor WebAssembly for the client?

ANS:
Yes, you can use Blazor Server-Side for the back office and WebAssembly for the client-facing app, allowing for separation of concerns between server-side and client-side functionality.

Q: How can I authenticate users differently on Blazor Server and WebAssembly?

ANS:
You can use different authentication mechanisms: Blazor Server can use session or cookie-based authentication, while Blazor WebAssembly can use OAuth, JWT, or other client-side authentication mechanisms.

Q: What are the benefits of using Blazor Server-Side for the back office?

ANS:
Blazor Server-Side allows for more secure handling of sensitive data and provides a centralized point for managing authentication and user interactions, making it ideal for back-office systems.

Q: How does Blazor WebAssembly differ from Blazor Server?

ANS:
Blazor WebAssembly runs entirely in the browser, offering a more responsive and interactive user experience with reduced server dependencies. In contrast, Blazor Server relies on the server for processing, with user interactions sent over a SignalR connection.

Q: How can I handle real-time communication between the back office and client app?

ANS:
You can use SignalR for real-time communication between Blazor Server and WebAssembly, or use REST APIs to communicate between the server and client-side application.
