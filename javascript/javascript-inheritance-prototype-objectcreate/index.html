JavaScript Inheritance: WeatherWidget Prototype vs. Object.create

When implementing inheritance in JavaScript, particularly when trying to mimic class-based structures, developers often encounter different approaches for setting up the prototype chain. A common pattern involves assigning a new instance of a parent constructor to the child’s prototype, such as WeatherWidget.prototype = new Widget;. However, modern JavaScript offers more direct and often preferred methods like Object.create().

Let’s delve into why WeatherWidget.prototype = new Widget; is used and explore its implications, alongside more contemporary solutions for achieving prototype-based inheritance.

The new Keyword’s Role in Constructor Invocation

The new keyword in JavaScript plays a pivotal role when used with functions intended as constructors. It orchestrates a specific sequence of events:

  1. Object Creation: A brand-new, empty object is created.
  2. this Binding: The this keyword within the constructor function is bound to this newly created object.
  3. Inheritance Setup: The new object’s internal [[Prototype]] property (often accessible via __proto__) is set to the prototype property of the constructor function. This establishes the crucial link in the prototype chain.
  4. Constructor Execution: The constructor function is executed with this pointing to the new object. Properties and methods are typically added to this within the constructor.
  5. Return Value: If the constructor doesn’t explicitly return an object, the newly created and initialized object is implicitly returned.

Without the new keyword, a function call behaves differently. If Widget() is called directly, this would typically refer to the global object (like window in browsers) or undefined in strict mode. This distinction is vital when assigning to prototype.

Solution 1: WeatherWidget.prototype = new Widget; Explained

This approach leverages the new keyword to create an instance of Widget. This instance then becomes the prototype object for WeatherWidget.

// Original Widget constructor
function Widget() {
  this.version = "1.0";
}
Widget.prototype.show = function() { console.log(`Widget version: ${this.version}`); };

// WeatherWidget constructor to inherit from Widget
function WeatherWidget(city) {
  Widget.call(this); // Call parent constructor
  this.city = city;
}

// Solution 1: Setting the prototype using 'new Widget'
WeatherWidget.prototype = new Widget();
WeatherWidget.prototype.constructor = WeatherWidget; // Correct the constructor property

// Example usage
const myWeatherWidget = new WeatherWidget("London");
myWeatherWidget.show(); // Output: Widget version: 1.0
console.log(myWeatherWidget instanceof Widget); // Output: true
console.log(myWeatherWidget instanceof WeatherWidget); // Output: true

Implications:

  • Prototype Chain: The chain becomes [new WeatherWidget()] → [new Widget()] → [Widget.prototype] → ....
  • Shared Instance Properties: All instances of WeatherWidget will inherit properties from the same Widget instance created for the prototype. If Widget had mutable instance properties (not just prototype methods), changes made through one WeatherWidget instance could affect others via this shared Widget instance.
  • Constructor Call: The new Widget() call automatically invokes the Widget constructor. This is generally what’s desired for setting up inheritance, but it means the Widget constructor is executed even if you don’t explicitly need its internal logic to run at that specific moment of prototype assignment.
  • Potential Issues:
    • If the Widget constructor requires arguments, this approach will fail unless default values are handled.
    • It can lead to unexpected behavior if Widget has side effects upon construction that you don’t intend for every WeatherWidget’s prototype setup.

Solution 2: The “Proper” Pre-ES5 Way with a Dummy Constructor

Before ECMAScript 5, a common pattern to avoid executing the parent constructor directly when setting prototypes was to use an intermediate “dummy” constructor.

// Using the same Widget and WeatherWidget constructors as above

// Pre-ES5 proper inheritance
function Dummy() {}
Dummy.prototype = Widget.prototype;
WeatherWidget.prototype = new Dummy();
WeatherWidget.prototype.constructor = WeatherWidget; // Fix constructor

const myWeatherWidgetES5 = new WeatherWidget("Paris");
myWeatherWidgetES5.show(); // Output: Widget version: 1.0

Implications:

  • Prototype Chain: [new WeatherWidget()] → [new Dummy()] → [Widget.prototype] → ....
  • No Parent Constructor Call: The Widget constructor is not executed when WeatherWidget.prototype is set. This avoids potential side effects from the parent constructor.
  • Inheritance via Widget.prototype: WeatherWidget instances inherit directly from Widget.prototype, rather than an instance of Widget. This means they don’t share any instance-specific properties that might have been on new Widget().

Solution 3: The Modern ECMAScript 5+ Approach with Object.create()

ECMAScript 5 introduced Object.create(), which is a more direct and semantically clear way to establish prototype relationships.

// Using the same Widget and WeatherWidget constructors as above

// ES5+ approach using Object.create
WeatherWidget.prototype = Object.create(Widget.prototype, {
  constructor: {
    value: WeatherWidget,
    writable: true,
    configurable: true,
    enumerable: false // By default, constructor is not enumerable
  }
});

// Example usage
const myWeatherWidgetModern = new WeatherWidget("New York");
myWeatherWidgetModern.show(); // Output: Widget version: 1.0

Implications:

  • Prototype Chain: [new WeatherWidget()] → [Widget.prototype] → ....
  • No Parent Constructor Call: Similar to the dummy constructor, Object.create() does not invoke the parent constructor.
  • Explicit Control: The second argument to Object.create() allows fine-grained control over the properties of the new prototype object, including making the constructor property non-writable, non-enumerable, and non-configurable, which is generally best practice.
  • Preferred Method: This is the most recommended approach in modern JavaScript for setting up prototype inheritance.

Calling Parent Constructors Explicitly

Regardless of the prototype assignment method, you often need to call the parent constructor explicitly within the child constructor to initialize instance-specific properties inherited from the parent. This is typically done using call() or apply().

function WeatherWidget(city, tempUnit) {
  // Explicitly calling the parent constructor
  Widget.call(this); // or Widget.apply(this, arguments);

  this.city = city;
  this.tempUnit = tempUnit; // Example of a WeatherWidget-specific property
}

Libraries often provide helper methods like extend to simplify this process. For example, a custom Function.prototype.extend could streamline the prototype setup and even offer mechanisms to call superclass methods.

// Hypothetical extend method for demonstration
Function.prototype.extend = function(Parent, protoProps) {
  // ... implementation to set up prototype chain and constructor ...
  // For example, WeatherWidget.prototype = Object.create(Parent.prototype, { constructor: { value: this } });

  if (protoProps) {
    Object.assign(this.prototype, protoProps);
  }

  // A common pattern to make calling super easier
  this.prototype._super = Parent.prototype;
};

function Widget() { this.version = "1.0"; }
Widget.prototype.show = function() { console.log(`Widget version: ${this.version}`); };

function WeatherWidget(city) {
  // Using the hypothetical extend with _super for parent constructor call
  WeatherWidget._super.call(this);
  this.city = city;
}

// Using the extend helper
WeatherWidget.extend(Widget, {
  getWeather: function() {
    return `Weather in ${this.city}`;
  }
});

const myWeatherWidgetExtended = new WeatherWidget("Tokyo");
myWeatherWidgetExtended.show(); // Output: Widget version: 1.0
console.log(myWeatherWidgetExtended.getWeather()); // Output: Weather in Tokyo

Alternative: Direct Object Extension

You don’t always need constructors to establish relationships. Prototypes can be any object, and you can directly assign properties from one object to another’s prototype.

var appendages = {
  legs : 2
};

var Features = function() {
   this.ears = 4;
   this.eyes = 1;
}

// Extending Features.prototype directly with an object
Features.prototype = appendages;
var sara = new Features();

console.log(sara.legs); // Output: 2

// Properties on the prototype can be modified on the fly
appendages.hair = true;
console.log(sara.hair); // Output: true

This demonstrates that the prototype is simply an object, and modifying that object affects all objects that inherit from it.

The __proto__ Property

While not a standard or recommended way to establish inheritance for production code (as it’s an internal, non-standard property widely adopted), __proto__ can be used for direct object linking:

var foo = {name : 'bob'};
var bar = {nachos : 'cheese'};

// Directly linking foo's prototype to bar
foo.__proto__ = bar;

console.log(foo.nachos); // Output: "cheese"

This is more akin to setting the prototype of an existing object rather than defining a constructor’s inheritance.

FAQs on JavaScript Inheritance

Q: Why does WeatherWidget.prototype = new Widget work

ANS: WeatherWidget.prototype = new Widget; works by creating a new instance of the Widget constructor using the new keyword. This new Widget instance then serves as the prototype for WeatherWidget. This means any WeatherWidget instance will first look for properties on its own instance, then on the Widget instance assigned to WeatherWidget.prototype, and finally up the Widget.prototype chain. The new operator ensures the Widget constructor is executed, setting up the Widget instance with its own properties and linking it to Widget.prototype.

Q: What is the difference between WeatherWidget.prototype = new Widget and Object.create Widget prototype

ANS: The key difference lies in how the parent constructor is handled. WeatherWidget.prototype = new Widget; executes the Widget constructor, creating a full instance. This instance becomes WeatherWidget’s prototype. In contrast, WeatherWidget.prototype = Object.create(Widget.prototype); creates a new object whose [[Prototype]] is explicitly set to Widget.prototype. The Widget constructor is not executed in this case, making it a cleaner way to set up prototype inheritance without unintended side effects from the parent constructor.

Q: What happens if I forget the new keyword in WeatherWidget prototype assignment

ANS: If you write WeatherWidget.prototype = Widget; (without new), you are assigning the Widget function itself to WeatherWidget.prototype, not an instance of Widget. This breaks the expected prototype chain for inheritance. When you then try to access methods or properties on a WeatherWidget instance that are defined on Widget.prototype, JavaScript won’t find them because the chain leads to the Widget function, not its prototype object.

Q: How do I correctly set the constructor property after prototype assignment

ANS: After assigning a new object to Child.prototype, the constructor property of the child’s prototype still points to the parent’s constructor. To fix this, you should explicitly reset it: Child.prototype.constructor = Child;. This ensures that (new Child()).constructor === Child evaluates to true, which is important for introspection and for methods that rely on the constructor property.

Q: Can I extend a JavaScript prototype with a plain object

ANS: Yes, you can assign a plain JavaScript object directly to a constructor’s prototype property, like Features.prototype = { legs: 2 };. This makes the properties of that plain object available to all instances created by the constructor. Any object assigned to the prototype becomes the link in the prototype chain.
