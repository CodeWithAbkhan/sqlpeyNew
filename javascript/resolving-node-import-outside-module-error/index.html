“Resolving Node.js ‘Cannot use import statement outside a module’ Syntax Error”

Encountering the SyntaxError: Cannot use import statement outside a module in a Node.js context signals a conflict between the required JavaScript module system (ES Modules, or ESM) and the environment’s default interpretation (typically CommonJS, or CJS). This situation arises when using the modern import/export syntax in files that Node.js expects to be CJS modules.

What are the robust methods to configure a Node.js project to correctly handle ECMAScript Module (import/export) syntax?

Primary Configuration Approaches for Enabling ESM

Several validated techniques exist to signal to Node.js that a file or project should be treated as an ES Module, thus enabling the use of import statements.

Method 1: Setting the Top-Level type: "module" in package.json

The most direct way to make Node.js interpret all .js files in a directory as ESM is by explicitly declaring it in the root package.json file.

If you are running Node.js version 13.2.0 or newer, implementing this structure in your package.json is often sufficient:

// package.json example for ESM context
{
  "name": "my-project",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "start": "node index.js"
  },
  "dependencies": {
    // ... your dependencies
  }
}

Note on Interoperability: When "type": "module" is set, any file intended to be interpreted as traditional CommonJS must use the .cjs file extension.

Method 2: Explicit File Extension Declaration

Alternatively, you can avoid setting the global "type": "module" and instead use explicit file extensions:

  1. Use .mjs: Rename your JavaScript files utilizing import/export syntax to use the .mjs extension (e.g., app.mjs). Node.js recognizes .mjs files as ES Modules by default, regardless of the package.json settings.
  2. Use .cjs: Files intended for CommonJS syntax (require/module.exports) should retain or adopt the .cjs extension if "type": "module" is set globally.

For instance, if your file is named utility.js, renaming it to utility.mjs will enable import usage within it.

Handling Mixed Module Environments (Import and Require)

A common complication arises when older dependencies rely on require() while newer code uses import. This necessitates bridging the two systems within an ESM file.

If you must use both import and require within an ES Module file, you can dynamically create a local require function using built-in Node.js capabilities:

// In your .mjs file:
import { createRequire } from 'module';
const require = createRequire(import.meta.url);

// Now you can use require for CJS modules:
const legacyModule = require('some-cjs-package');

// And use import for ESM modules:
import modernFeature from 'some-esm-module';

Transpilation Solutions (Babel and TypeScript)

When working with environments that require code transformation before execution (like older Node versions, or when using TypeScript), transpilation tools are key.

Solution via Babel

Babel can convert modern ES syntax to a format compatible with the target runtime, often CommonJS, even when using import.

  1. Install Dependencies: Ensure you have Babel core utilities: 
    npm install --save-dev @babel/cli @babel/core @babel/preset-env
  2. Configure Babel: Create a .babelrc or babel.config.json file to specify the preset: 
    // babel.config.json
{
  "presets": ["@babel/preset-env"]
}
  3. Execution: Use @babel/node or a custom build step:
    • Direct Execution (Development): 
      npx babel-node --presets @babel/preset-env ./yourscript.js
    • Build and Run: Define scripts in package.json to transpile first: 
      "scripts": {
  "build": "babel index.js -d dist",
  "start": "npm run build && node dist/index.js"
}
    • Babel Register (For initialization): For configuration files (like .sequelizerc), you can use @babel/register: 
      npm install @babel/register
# Add require("@babel/register") at the top of the target file

Solution via TypeScript Configuration (tsconfig.json)

If the error occurs during TypeScript compilation or execution, the module setting in tsconfig.json is crucial. Setting it to "esnext" can sometimes be problematic if the runtime doesn’t fully support it yet. Switching to "commonjs" often resolves the issue by forcing compatibility with environments expecting CJS structure.

Solution via SWC

For projects utilizing the Speedy Web Compiler (SWC), a configuration file like .swcrc must define the module output type correctly.

// .swcrc configuration for CommonJS output from TypeScript sources
{
    "jsc": {
      "parser": {
        "syntax": "typescript",
        "tsx": false,
        "dynamicImport": true,
        "decorators": true
      },
      "target": "es2020"
    },
    "module": {
      "type": "commonjs" // Ensures CJS output even if TS uses imports
    }
}

Runtime Flag Adjustments

For development or testing environments where configuration files are difficult to adjust, runtime flags can temporarily force ESM execution.

Using --experimental-modules

In older Node versions, or specific scenarios, explicitly invoking Node.js with the experimental flag can enable ESM features:

node --experimental-modules your_file.js

This flag is often superseded by the "type": "module" setting in recent Node versions.

For Jest Testing Environments

If the error occurs during Jest tests that utilize ESM syntax:

  1. Install Support: 
    npm install --save-dev cross-env
  2. Update package.json scripts: Use cross-env to pass the necessary flag to Jest, alongside configuring Jest to expect modules: 
    "scripts": {
    "test": "cross-env NODE_OPTIONS=--experimental-vm-modules jest"
},
"jest": {
    "transform": {},
    "type": "module" // Or ensure Jest configuration handles ESM
}

Dealing with Specific Tools and Environments

Node.js with esm Package

For environments requiring flexibility or supporting older Node versions, the external esm package provides a wrapper:

npm i esm --save
# Then modify your start script:
"scripts": {
  "start": "node -r esm src/index.js"
}

Netlify Functions

If deploying to serverless environments like Netlify Functions, ensure the bundler supports ESM. Updating netlify.toml to use esbuild resolves these conflicts:

[functions]
  node_bundler = "esbuild"

Using nodemon

When using nodemon for development restarts, you may need to pass the required experimental flag:

nodemon --experimental-modules server.js

FAQs on Resolving Node Import Outside Module Error

Q: What is the quickest way to fix the import statement error

ANS: Rename the affected JavaScript file from .js to .mjs, or add "type": "module" to your project’s root package.json.

Q: Can I use both import and require in the same file

ANS: Yes, within an ES Module file (.mjs or when "type": "module" is active), import createRequire from the ‘module’ built-in to generate a local require function.

Q: Do I need to change anything if I use TypeScript

ANS: Check your tsconfig.json file. Switching "module" from "esnext" to "commonjs" often resolves conflicts when Node.js executes the compiled output.

Q: What if I get the error in a Vite React project with SWC

ANS: Babel configurations will not apply. Install @types/jest and treat testing functions like describe and expect as global variables instead of importing them directly.

Q: How do I run Node scripts with Babel support

ANS: Install @babel/core and @babel/node, then execute your entry file using npx babel-node --presets @babel/preset-env ./entry_file.js.
