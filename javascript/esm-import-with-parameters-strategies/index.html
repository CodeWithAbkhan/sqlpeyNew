“ESM Import with Parameters: Strategies for Dynamic Module Loading”

A frequent necessity when transitioning from CommonJS’s require() function to ECMAScript Modules’ (ESM) import syntax is the inability to directly pass arguments during the static import declaration. CommonJS modules often export a function that is immediately invoked upon requiring the module, or the module itself is executed with parameters passed via the require call in certain setups. How can we achieve analogous parameterized module loading within the modern ESM ecosystem?

It is important to state upfront: There is no direct syntax to achieve invocation within a static import statement. The static import is designed for declarative dependency resolution, not runtime function calls. However, several powerful patterns emulate this behavior, leveraging module factories or dynamic imports.

Pattern 1: The Module Factory Approach (Simulating CJS Invocation)

The most idiomatic and recommended way to handle required configuration parameters is by structuring your module to export a factory function. This function accepts the necessary options and returns the actual module object or class instance.

Module Definition (moduleFactory.js)

Instead of exporting the final module object, export a function that creates the module based on input options.

// moduleFactory.js
/**
 * Exports a function that acts as a factory for the module functionality.
 * @param {object} options - Configuration parameters for the module setup.
 * @returns {object} The initialized module interface.
 */
export default function setupModule(options) {
    console.log("Module initialized with options:", options);
    // Actual module logic returns here
    return {
        execute: () => `Operation successful with ${JSON.stringify(options)}`
    };
}

Importing and Invoking (main.js)

You import the default export (the factory) and then immediately invoke it with your runtime parameters.

// main.js
import setupModule from './moduleFactory.js';

const runtimeConfig = { connectionTimeout: 5000, retries: 3 };

// Invoke the factory function to get the operational module instance
const operationalModule = setupModule(runtimeConfig);

console.log(operationalModule.execute());

This pattern closely mimics what happens when a CJS module exports a function that consumers call immediately after require.

Pattern 2: Leveraging Dynamic Import with Promises

When execution context requires imports that depend on runtime conditions (e.g., loading a module only after a specific user action or condition is met), dynamic import() is the tool. This returns a Promise that resolves to the module namespace object.

If the module exports a default function factory (as in Pattern 1), you can chain the invocation onto the resolution promise:

// Dynamic invocation using dynamic import and promise chaining
const dynamicPromise = import('./moduleFactory.js')
    .then(moduleNamespace => {
        const factory = moduleNamespace.default;
        return factory({ featureFlag: 'A' }); // Invoking the factory
    })
    .then(initializedModule => {
        console.log("Dynamically loaded and initialized:", initializedModule.execute());
    });

For environments supporting top-level await (e.g., modern bundler configurations or ES Modules in browsers/Node.js):

// Using top-level await for cleaner dynamic loading
const moduleNamespace = await import('./moduleFactory.js');
const x = moduleNamespace.default({ apiEndpoint: '/data' });

Pattern 3: Parameterized Module Specifiers (Bypassing Initialization)

A less conventional, though sometimes useful, technique involves passing configuration through the module specifier itself, relying on bundlers or runtime environments to reload or re-evaluate the module source if the URL changes. This treats the parameter as part of the dependency identity, forcing re-import.

If a module’s top-level execution logic checks the URL:

Service Definition (service.js)

// service.js
// Extract context from the import metadata URL if available (requires environment support)
let context = 'default_context';
if (typeof import.meta !== 'undefined' && import.meta.url) {
    try {
        const url = new URL(import.meta.url);
        context = url.searchParams.get('context') || context;
    } catch (e) {
        // Handle environments where URL parsing might fail or import.meta is restricted
    }
}
console.log(`Service initialized in context: ${context}`);

// This module runs once unless the specifier changes
export const initialContext = context;

Invocation Scenarios

Module A imports it normally:

// Module A
import * as S from './service.js'; // Logs: Service initialized in context: default_context
console.log(S.initialContext); // 'default_context'

Module C forces a specific context reload:

// Module C
import * as S_Special from './service.js?context=special_instance'; // Logs: Service initialized in context: special_instance
console.log(S_Special.initialContext); // 'special_instance'

Caveat: This method re-fetches/re-evaluates the module file based on the full specifier (./service.js?context=special_instance). Use this sparingly, as it violates the expected singleton nature of static ESM imports and might behave unpredictably depending on caching layers.

Pattern 4: Adapting Third-Party Modules (e.g., Debug Utility)

Some libraries, particularly those ported from CommonJS, use the argument passed to require() (e.g., require('debug')('namespace')) to configure the resulting export. In ESM, this configuration often needs to be separated.

If the CJS code looked like this:

// CJS original
var debug = require('debug')('http');

The corresponding ESM adaptation uses named or default imports followed by an invocation:

// ES6 Adaptation
import * as DebugModule from 'debug'; // Import the entire module interface
// Destructure or reference the specific function needed (e.g., 'debug')
const { debug } = DebugModule; 
const httpDebugger = debug('http'); // Now invoke with parameters

httpDebugger('Event logged successfully!');

Alternatively, if the package exports the utility function directly as default:

import debugFactory from 'debug';
const httpDebugger = debugFactory('http');

Alternative: Decorator/Wrapper Pattern for Classes

When you need to pass parameters specifically for class instantiation rather than module loading, the factory pattern (Pattern 1) is again the standard.

Class Factory Definition (MyClassFactory.js)

// MyClassFactory.js
/**
 * Exports a function that generates a class definition based on provided parameters.
 * @param {string} Param1 - Config value one.
 * @param {string} Param2 - Config value two.
 * @returns {class} The generated class constructor.
 */
export default (Param1, Param2) => class MyParametrizedClass {
    constructor() {
        console.log(`Class created using Params: ${Param1} and ${Param2}`);
    }
};

Usage

// main.js
import MyClassFactory from './MyClassFactory.js';

// Generate the specific class needed
let ConfigurableClass = MyClassFactory('foo_value', 'bar_value');

// Instantiate the generated class
let myInstance = new ConfigurableClass(); // Outputs: Class created using Params: foo_value and bar_value

This flexible pattern is highly valuable in building isomorphic frameworks where dependency injection of configuration into class definitions is required upon setup.

FAQs on ESM Import with Parameters

Q: Can I use static import statement to pass arguments directly

ANS: No, the static import statement does not support direct invocation or argument passing because it is resolved statically before runtime execution begins.

Q: What is the standard way to pass configuration to an ESM module

ANS: The standard method involves exporting a factory function from the module, which is then imported and executed with the required parameters.

Q: How does dynamic import differ from static import regarding parameters

ANS: Dynamic import('modulePath') returns a Promise that resolves to the module namespace object, allowing subsequent runtime invocation of an exported factory function.
// module.js
export default function(options) {
    return {
        // actual module
    }
}

// main.js
import m from 'module';
var x = m(someoptions);
System.import('module').ap(someoptions).then(function(x) {
    …
});
const promise = import('module').then(m =&gt; m.default(someoptions));
const x = (await import('module')).default(someoptions)
