“JavaScript Techniques to Determine Previous Page URL or Navigate Back”

When developing modern web applications, especially Single Page Applications (SPAs), precisely tracking the URL from which a user navigated to the current page presents unique challenges. Security and privacy restrictions prevent direct access to the browser’s complete navigation history. How can developers reliably ascertain the source URL or navigate backward within the session history? This exploration details several robust techniques to address this requirement.

Relying on Browser-Provided Referrer Information

The document.referrer property is often the first point of investigation for identifying the source URL.

What does document.referrer offer?

In many standard navigation scenarios where a user clicks a hyperlink, document.referrer furnishes the URL of the page visited immediately prior to the current one. This adheres to DOM Level 2 specifications.

It is critical to note that window.history is deliberately restricted from exposing the full URL history stack due to inherent security and privacy considerations—allowing such access would permit websites to track user journeys across different domains. For managing state within your own site, conventional methods like URL parameters, cookies, or server-side session data are typically more dependable than relying solely on referrer data.

A direct JavaScript snippet to retrieve this value appears as:

const sourceUrl = document.referrer;
console.log(`The originating page was: ${sourceUrl}`);

Limitations of document.referrer

While convenient, document.referrer is not universally reliable for all circumstances. If a user navigates directly (typing the URL) or in specific form submission cases, this value might be an empty string. Furthermore, its interpretation can become complex when dealing with framing structures, as noted in certain frame interactions where a history.back() action might reload the document.referrer rather than a specific state within a frameset.

If targeting older environments, be aware that older versions of Internet Explorer (prior to IE9) may not support document.referrer reliably. An older method to output this content directly to the DOM involves:

<script type="text/javascript">
    document.write(document.referrer);
</script>

Leveraging the HTML5 History API for Navigation Control

For controlling sequential navigation within the application flow, the modern History API provides methods to move backward and forward within the current browser session stack without needing to know the exact preceding URL.

Programmatic Navigation with history object

The history object allows for basic stack manipulation:

  • Go Back: Navigates to the previous entry in the session history. 
    history.back(); // Equivalent to pressing the browser's back button
  • Go Forward: Moves to the next entry in the stack. 
    history.forward();
  • Go by Index: Moves relative to the current position. 
    // Move two steps back in history
history.go(-2); 
// Move one step forward
history.go(1);

This API does not permit reading the contents of the history stack for security reasons, and its functionality is contingent on HTML5 support in the browser. For more specifics on its capabilities, consulting the MDN documentation on History Interface is recommended.

Maintaining State During SPA Routing with pushState

In SPAs where routing occurs client-side, you can actively store state associated with navigation events using pushState. This allows you to explicitly save the originating URL before navigating to a new internal route.

When moving to a new path:

// Store the current URL before pushing the new state
const currentState = { prevUrl: window.location.href };
window.history.pushState(currentState, null, "/new/path/in/your/app");

Upon arrival at the new route, the previous URL can be reliably retrieved from the state object:

// In the new component/route lifecycle hook
const previousLocation = window.history.state.prevUrl;
console.log(`Retrieved previous location from state: ${previousLocation}`);

Persistent Storage for Cross-Navigation Context

When simple back navigation (history.back()) is insufficient or when dealing with complex application flows (like leaving and returning to an application context), storing the desired destination in persistent client-side storage like localStorage or sessionStorage offers an alternative.

Using localStorage for Cross-Screen Navigation (e.g., React/Vue)

In frameworks utilizing client-side routing, you can save the target URL when initiating navigation and retrieve it upon returning, potentially after navigating away from the application entirely.

A pattern involving React’s useEffect and localStorage might look like this for saving a selected project URL:

// Function called when navigating to a new internal project view
function selectProject(customerId: string, projectId: string){
    const projectUrl = `/customer/${customerId}/project/${projectId}`;
    localStorage.setItem("selected-project", projectUrl);
    history.push(projectUrl); // Assuming 'history' is available from a routing library
}

// In the component loaded after an external navigation or initial load
useEffect(() => {
    const projectUrl = localStorage.getItem("selected-project");
    if (projectUrl) {
      history.push(projectUrl); // Navigates user back to the saved spot
    }
}, [history]);

// When exiting the project view, clear the saved link
const exitProject = () => {
    localStorage.removeItem("selected-project");
    history.push("/");
}

Fallback Strategy with sessionStorage

If document.referrer is empty, a more intricate workaround involving sessionStorage can be implemented to capture the URL before a potential navigation away, using history.back() and history.forward() as a mechanism to capture the current location if the referrer is missing.

let previousUrl = null;

if (document.referrer) {
  previousUrl = document.referrer;
  sessionStorage.setItem("isTrickApplied", "false");
} else {
  let isTrickApplied = sessionStorage.getItem("isTrickApplied");
  if (isTrickApplied === "true") {
    previousUrl = sessionStorage.getItem("prev");
    sessionStorage.setItem("isTrickApplied", "false");
  } else {
    // This attempts to capture the current location if no referrer exists,
    // forcing a history entry before moving forward again.
    history.back(); 
    sessionStorage.setItem("prev", window.location.href);
    sessionStorage.setItem("isTrickApplied", "true");
    history.forward(); 
  }
}
console.log(`Determined previous URL: ${previousUrl}`);

Server-Side Referrer Tracking (e.g., Node.js/Express)

For server-rendered applications or to maintain referrer information across multiple non-consecutive requests, server-side middleware can capture and store the URL in session data.

In an Express application, utilizing middleware placed after session initialization:

// Middleware added after express-session setup
app.use((req, res, next) => {
    // Construct the full URL from request components
    req.session.referrer = req.protocol + '://' + req.get('host') + req.originalUrl;
    next();
});

// Later, in a request handler:
if (req.session.referrer) {
    console.log(`Server tracked previous URL: ${req.session.referrer}`);
}

Caution is warranted: session state might be lost if the session expires, the user clears cookies, or if the initial navigation originated from an external site, as the session might not be established on the first server hit.

Monitoring Browser Navigation Events

For SPAs, the popstate event is crucial. It fires when the active history entry changes, typically due to a user clicking the browser’s back or forward buttons after an operation that utilized history.pushState() or history.replaceState().

You can listen for this event to react precisely when the browser navigates away from or back into a state managed by your application:

window.addEventListener("popstate", (event) => {
  console.log(
    `Navigation occurred. Current location: ${document.location}, State Data: ${JSON.stringify(event.state)}`,
  );
  // Use event.state to access data pushed via pushState
});

This allows your application logic to handle state transitions correctly, even when the browser’s native navigation controls are used. If your history length is one or less, it suggests the user is on the first entry of the current session stack:

if (window.history.length <= 1) {
    console.log("Currently at the beginning of the visible history stack.");
}

Retrieving Data from history.state.usr (React Router Example)

In certain configurations, particularly those using libraries like React Router which might utilize a specific structure within history.state, the previous URL might be embedded here:

// Caution: This path is specific to certain routing library implementations
const previousUrl = `${window.location.host}${window.history.state.usr.from}`;

FAQs on JavaScript Previous Page URL Techniques

Q: How to get previous URL when document referrer is empty

ANS: When document.referrer is empty (e.g., direct navigation), utilize sessionStorage in conjunction with controlled navigation (history.back() followed by history.forward()) to capture and store the current location as the previous location for subsequent checks, as detailed in Solution 8.

Q: Is window history accessible for reading all visited URLs

ANS: No, for security and privacy, JavaScript cannot read the complete URL history stack stored in window.history. Only the length of the stack is reliably accessible, or specific state data pushed via history.pushState can be retrieved.

Q: Which technique works best for Single Page Applications

ANS: For SPAs, using window.history.pushState to explicitly store the previous URL in the state object during internal navigation (Solution 3) is the most reliable method, complemented by listening to the popstate event (Solution 12).

Q: What is the limitation of using document.write with document.referrer

ANS: Using document.write() is generally discouraged, and specifically, support for document.referrer via this method was inconsistent in older browsers, notably lacking support in Internet Explorer versions before IE9.
