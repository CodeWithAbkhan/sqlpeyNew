“Resolving Mocking Issues for Functions Called Within the Same Module in JavaScript/TypeScript”

When testing functions that rely on other functions exported from the same module in JavaScript environments like Jest, standard mocking techniques often fail. This failure arises because the internal call inside foo() binds to the original, unmocked version of bar() at the time of module evaluation, even if you successfully spy on the exported module.bar reference later.

What approaches exist to inject a mock or spy into a dependency function that resides within the very module being tested?

Effective Solutions for Internal Function Mocking

Several distinct patterns offer paths around this module-level binding issue, ranging from structural code changes to leveraging specific module system features.

Technique 1: Leveraging ES6 Cyclic Imports for Self-Referencing

ES6 module resolution supports cyclic dependencies gracefully. By importing the module itself into its own scope, the internal function (foo) can reference the exported entities via the imported namespace (thisModule), allowing the test environment to replace the exported function reference successfully.

Module File (./module.js or .ts):

import * as thisModule from './module';

export function bar() {
    return 'bar';
}

export function foo() {
    // Calls the version available in the imported namespace
    return `I am foo. bar is ${thisModule.bar()}`;
}

Test File Example:

import * as module from '../src/module';

describe('module with self-reference', () => {
    it('foo uses the spied bar', () => {
        // Spy on the exported reference available via the module import
        jest.spyOn(module, 'bar').mockReturnValue('fake bar');
        
        const result = module.foo();
        
        expect(result).toEqual('I am foo. bar is fake bar');
        expect(module.bar).toHaveBeenCalled();
    });
});

This technique makes importing the module into its own definition appear unconventional but resolves testing challenges smoothly due to ES6 module specification behavior.

Technique 2: Encapsulation via Class or Instance Export

If functions are tightly coupled, bundling them into a class instance makes mocking straightforward. The dependent function (foo) references its dependency (this.bar()) via the instance context (this), which is easily spied upon in tests.

Module File (Module.js or .ts):

export class MyModule {
  function bar(): string {
    return 'bar';
  }

  function foo(): string {
    // Uses 'this' context for dependency resolution
    return `I am foo. bar is ${this.bar()}`;
  }
}

Test File Example:

import { MyModule } from '../src/module';

describe('MyModule Class Test', () => {
    const sut: MyModule = new MyModule();
    let barSpy: jest.SpyInstance;

    beforeEach(() => {
        // Spy directly on the instance method
        barSpy = jest.spyOn(sut, 'bar').mockImplementation(jest.fn());
    });

    afterEach(() => {
        barSpy.mockRestore();
    });

    it('foo resolves with mocked bar value', () => {
        sut.bar.mockReturnValue('fake bar');
        const result = sut.foo();
        expect(result).toEqual('I am foo. bar is fake bar');
    });
});

This approach requires modifying the module structure to export a class or an instance rather than standalone functions.

Technique 3: Utilizing Function Expressions vs. Declarations

Function declarations are hoisted, which can interfere with mocking tools trying to intercept the reference during module loading. Converting the function to a function expression (especially an arrow function assigned to a const) prevents hoisting, making it readily interceptable by testing frameworks like Jest.

Original (Problematic Declaration): export function bar() { return 'bar'; }

Revised (Testable Expression):

export const bar = () => {
  return "bar";
};

export function foo() {
    return `I am foo. bar is ${bar()}`; // This call may still reference the original
}

While this helps in some testing setups, Solution 1 or 4 often provides more reliable interception for functions used internally via direct name resolution.

Technique 4: Dependency Injection via Default Parameter (Recommended for Flexibility)

This non-breaking approach allows the consumer (the test suite) to supply the dependency (_bar) explicitly, while keeping the original function (bar) as the default for standard use cases.

Module File (./module.js or .ts):

export function bar() {
    return 'bar';
}

// Default parameter injects 'bar' if not provided, otherwise uses the passed dependency
export function foo(_bar = bar) {
    return `I am foo. bar is ${_bar()}`;
}

Test File Example:

import { foo } from '../src/module';

describe('module with dependency injection', () => {
    it('foo uses the injected mock bar', () => {
        const dummyBarMock = jest.fn().mockReturnValue('fake bar');
        
        // Pass the mock directly as the first argument
        const result = foo(dummyBarMock);
        
        expect(result).toEqual('I am foo. bar is fake bar');
        expect(dummyBarMock).toHaveBeenCalledTimes(1);
    });
});

This method keeps the API clean while providing the easiest path for test isolation. See related discussions on dependency injection patterns here: Top 5 Methods to Ping Servers in Python .

Technique 5: Using Rewiring Plugins (Babel)

If your project utilizes Babel, tools like babel-plugin-rewire-plugin or babel-plugin-explicit-exports-references can transparently rewrite module exports during transpilation, making the internal references point to a modifiable object, which Jest can then intercept.

Using a rewire plugin, you might use an API like this in tests:

import __RewireAPI__, * as module from '../module';

describe('foo using rewire plugin', () => {
  it('calls bar internally', () => {
    const barMock = jest.fn();
    
    // Rewire makes 'bar' within the module point to barMock
    __RewireAPI__.__Rewire__('bar', barMock);
    
    module.foo();

    expect(barMock).toHaveBeenCalledTimes(1);
  });
});

Technique 6: Adjusting CommonJS Exports Structure

For legacy CommonJS environments, if foo references the bare function name bar() instead of the imported container reference (e.g., module.bar()), the binding is direct. By changing the internal call to explicitly use the module reference (myModule.bar()), you can intercept the property on the exported object.

Modified CommonJS Module (myModule.js):

function bar() {
  return "bar";
}

function foo() {
  // Crucially change from bar() to myModule.bar()
  return `I am foo. bar is ${myModule.bar()}`;
}

const myModule = { bar, foo };
module.exports = myModule;

Test:

const myModule = require("./myModule");

describe("myModule CJS Test", () => {
  test("foo uses mocked bar", () => {
    // Spy on the exported property
    jest.spyOn(myModule, "bar").mockReturnValueOnce("bar-mock");

    const result = myModule.foo();
    expect(result).toBe("I am foo. bar is bar-mock");
  });
});

This requires ensuring the module structure maintains a self-reference to the export object internally.

Technique 7: Testing Behavior Over Implementation Details (The Purest Approach)

Often, the need to spy on an internal function suggests testing implementation details rather than external behavior. If foo and bar operate together to produce a defined output via the public API (foo()), test that final output directly.

Module Code:

export function bar() {
    return 'bar';
}

export function foo() {
    return `I am foo. bar is ${bar()}`;
}

Test Focus:

Test the contract: what does foo() return when bar() returns its standard value?

import { bar, foo } from "path/to/module";

describe("module behavior contract", () => {
    it("foo returns expected string based on bar's default output", () => {
        // Test the combined result directly
        expect(foo()).toBe('I am foo. bar is bar');
    });

    // If refactoring bar doesn't change the output of foo, the tests remain valid.
});

If a dependency must be mocked because it performs side effects (like API calls), extract that dependency into its own separate module and mock the module import (a technique better supported by ES Modules).

Technique 8: Using Babel Plugin for Automatic Rewiring

For Babel users, the babel-plugin-explicit-exports-references package can transparently address the issue by ensuring exported references are rewritten to point to the main export object during compilation. This provides an elegant solution at the build step.

Technique 9: Revisit Function Expression for Interception

Reinforcing Technique 3: If you strictly use arrow functions assigned to const exports, Jest often finds it easier to intercept the binding compared to traditional declarations due to differences in how they are processed relative to hoisting.

Technique 10: Explicitly Using Exported Object Properties (CommonJS Style)

If you structure your CommonJS module to explicitly assign functions to the exports object, tests can more reliably overwrite these properties.

Module (module.js):

exports.bar = () => {
    return 'bar';
}

exports.foo = () => {
    return `I am foo. bar is ${exports.bar()}`;
}

Test:

describe('MyModule CJS Property Test', () => {
  it('foo calls overwritten bar property', () => {
    let module = require('./module');
    
    // Overwrite the property directly on the required object reference
    module.bar = jest.fn(() => { return 'fake bar'; });

    expect(module.foo()).toEqual('I am foo. bar is fake bar');
  });
});

Technique 11: CommonJS Self-Reference Rewrite

Similar to Technique 6, this involves altering the internal call site to reference the externally exported object in CommonJS.

Technique 12: Testing via requireActual and Overwriting Exports

If you import the module using the structure that brings all exports into the current scope, you can use jest.requireActual to get the real module object and then mock its properties directly on that object before calling the function under test.

Module Structure:

export const A = () => 'A';
export const B = () => 'B';
export const C = () => A() + ' ' + B();

Test Example:

import { A, B, C } from './module';

describe('module exports testing', () => {
    it('C returns combined mocked A and B', () => {
        // Get the actual module object resolved by the runtime
        const module = jest.requireActual('./module');
        
        // Directly mock the functions on the actual module object
        module.A = jest.fn().mockReturnValue('AA');
        module.B = jest.fn().mockReturnValue('BB');
        
        // Calling C will now use the mocked properties on the module object
        expect(module.C()).toEqual('AA BB');
        expect(module.B).toHaveBeenCalledExactlyOnceWith();
    });
});

FAQs on Resolving Mocking Issues Internal Functions

Q: Why does spying on an exported function fail when called internally in the same module

ANS: Standard imports often create a copy or bind to the original function reference when the module is first loaded. Subsequent spying on the exported name doesn’t update the internal reference already established during module initialization.

Q: Is using ES6 cyclic imports (Solution 1) considered standard practice

ANS: While it looks strange, it adheres to ES6 module specifications for handling mutual dependencies and is a reliable method to ensure internal calls resolve to the dynamic mock set in the test scope.

Q: Which solution minimizes required code changes

ANS: Solution 4 (Dependency Injection via Default Parameter) usually requires the least invasive change to the source code while offering excellent testability.

Q: Should I always prefer testing external behavior over internal mocks

ANS: Yes, Solution 7 suggests prioritizing testing the external API’s behavior. Mocking internal functions should generally be reserved for dependencies that cause side effects (like network I/O) or are extremely complex, preferably by extracting them to separate modules.
