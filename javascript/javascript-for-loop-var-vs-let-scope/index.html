“JavaScript For Loop: Var vs Let Scope Differences Explained”

When constructing loops in JavaScript, the choice between var and let for loop control variables significantly impacts how your code behaves, especially when dealing with asynchronous operations or closures. This exploration aims to clarify these distinctions with practical examples and technical insights.

Is let in a for loop just syntactic sugar for ES6?

No, let in a for loop is more than just syntactic sugar. The underlying mechanics are detailed in specifications like §13.6.3.9 CreatePerIterationEnvironment.

When you use let in a for statement, it binds variables within a new lexical environment for each iteration. This means a fresh binding is created for the initializer expression and for each subsequent iteration before the increment expression is evaluated. Values from one environment are then copied to the next.

Consider the difference in behavior when using process.nextTick (a Node.js function that executes a callback asynchronously after the current event loop phase):

A loop using var:

for (var i = 0; i < 3; i++) {
    process.nextTick(_ => console.log(i));
}

This effectively “desugars” to:

// Omitting braces when they don't introduce a block
var i;
i = 0;
if (i < 3) {
    process.nextTick(_ => console.log(i));
}
i++;
if (i < 3) {
    process.nextTick(_ => console.log(i));
}
i++;
if (i < 3) {
    process.nextTick(_ => console.log(i));
}
i++;
// ...and so on

In this var scenario, all asynchronous callbacks reference the same i variable from the outer scope. By the time the callbacks execute, i has already reached its final value.

Contrast this with a loop using let:

for (let i = 0; i < 3; i++) {
    process.nextTick(_ => console.log(i));
}

This translates to a more complex structure:

// Using braces to explicitly denote block scopes
{
    let i;
    i = 0;
    // __status variable (internal detail of spec)
    // captures the current state of i
}
{
    let {i} = __status; // Get i from previous iteration's state
    if (i < 3) {
        process.nextTick(_ => console.log(i));
    }
    // __status updated with current i
}
{
    let {i} = __status; // Get i from previous iteration's state
    i++; // Increment i for the next iteration
    if (i < 3) {
        process.nextTick(_ => console.log(i));
    }
    // __status updated with current i
}
// ...and so on

Here, each iteration creates a new binding for i. The process.nextTick callbacks capture the value of i from their respective iteration’s scope, resulting in each callback logging the correct, distinct value of i at the time it was scheduled.

How does var vs. let affect loop variable behavior in closures?

The fundamental difference lies in how var and let handle variable bindings, particularly concerning closures.

Using var:

When you declare a variable with var in the head of a for loop, a single binding (storage location) is created for that variable. All closures created within the loop body reference this same binding.

const arrVar = [];
for (var i = 0; i < 3; i++) {
    arrVar.push(() => i); // Capturing the same 'i'
}

// All functions in arrVar refer to the final value of 'i'
console.log("Results from 'var' loop closures:", arrVar.map(callback => callback())); // Expected output: [3, 3, 3]

In this example, each function pushed to arrVar captures the var i variable. Since var has function scope and not block scope, the i they reference is the same one declared outside the loop. By the time arrVar.map is called, the loop has completed, and i holds its final value (3). Consequently, all functions return 3.

Using let:

Conversely, let declares a new binding for each loop iteration. This means each closure created within the loop captures the value of i specific to that iteration.

const arrLet = [];
for (let i = 0; i < 3; i++) {
    arrLet.push(() => i); // Capturing 'i' unique to each iteration
}

// Each function in arrLet refers to its iteration's specific 'i'
console.log("Results from 'let' loop closures:", arrLet.map(callback => callback())); // Expected output: [0, 1, 2]

Here, let i creates a new i for each pass of the loop. The arrow functions created within the loop capture these distinct i bindings. When arrLet.map is executed, each callback returns the value of i that was current during its creation.

What is the underlying specification detail for let’s block scoping?

The behavior of let is rooted in its introduction of block scoping, similar to how functions establish scope with closures. Key sections of the ECMAScript specification are relevant here:

  • Section 13.2.1 (LexicalBinding): let declarations are part of a LexicalBinding, and both reside within a Lexical Environment.
  • Section 13.2.2 (VariableEnvironment): In contrast, var declarations are attached to a VariableEnvironment, not a LexicalBinding.

MDN Web Docs further clarifies this: “let binds zero or more variables in the lexical scope of a single block of code.” This implies that variables declared with let are bound to the specific block (in this case, the loop iteration). Each iteration requires a new LexicalBinding, distinct from the surrounding Lexical Environment or VariableEnvironment which remain constant for the loop’s duration.

When using let, the closure operates at the loop body level, and the variable is unique to each iteration. This necessitates re-capturing the variable with each iteration. With var, the variable exists in the surrounding function scope, eliminating the need for re-capture, and the same reference is passed along.
