“Rails Turbolinks JavaScript Execution Solutions Explained”

When working with Ruby on Rails and the Turbolinks gem, developers often encounter challenges with JavaScript execution. Turbolinks enhances performance by loading only necessary parts of a page, but this can lead to JavaScript functions being executed multiple times or not at all. This post delves into various strategies to ensure your JavaScript behaves as expected with Turbolinks, covering common issues and providing practical code examples.

The Challenge of Turbolinks and JavaScript

Turbolinks intercepts clicks on links and form submissions, fetching new HTML from the server and replacing the page’s <body> and <title> with the new content. While efficient, this process doesn’t trigger a full page reload, meaning traditional JavaScript event listeners like $(document).ready() might not execute on subsequent page transitions. This necessitates adapting JavaScript execution to work with Turbolinks’ page change events.

Solution Approaches for Turbolinks JavaScript Execution

Several methods have been developed to address this, each with its nuances.

Solution 1: Direct Event Binding (CoffeeScript & JavaScript)

A fundamental approach involves directly binding your JavaScript to Turbolinks’ events.

  • CoffeeScript Example:

    ready = ->
  # Your coffeescript code here
  console.log("CoffeeScript ready function executed")

$(document).ready(ready)
$(document).on('page:load', ready)

  • JavaScript Equivalent:

    var ready;
ready = function() {
  // Your javascript code here
  console.log("JavaScript ready function executed");
};

$(document).ready(ready);
$(document).on('page:load', ready);

    The $(document).on('page:load', ready) line is crucial for catching Turbolinks’ page transitions.

  • For Rails 5+ (with Turbolinks 5+): The page:load event is superseded by turbolinks:load.

    $(document).on('turbolinks:load', function() {
  // Your javascript code here for Turbolinks 5+
  console.log("Turbolinks 5+ load event executed");
});

    This event fires on initial load and subsequent Turbolinks transitions.

Solution 2: Utilizing the jquery-turbolinks Gem

The jquery-turbolinks gem provides a simpler way to integrate jQuery with Turbolinks. It automatically binds Turbolinks events to $(document).ready.

  1. Add to Gemfile:

    gem 'jquery-turbolinks'

  2. Install:

    bundle install

  3. Include in app/assets/javascripts/application.js:

    Ensure //= require jquery.turbolinks is included after //= require jquery.

    // app/assets/javascripts/application.js
//= require jquery
//= require jquery_ujs
//= require jquery-turbolinks // Add this line
//= require turbolinks
//= require_tree .

    With this gem, you can often write your jQuery as if Turbolinks wasn’t present, using $(document).ready().

Solution 3: Combined Event Binding and Delegated Events

This approach offers a clean way to handle multiple events and correctly manages delegated events.

  • Combined Binding:

    $(document).on('ready page:load', function() {
  // Actions to do on initial load and page transitions
  console.log("Combined ready and page:load event triggered");
});

  • Handling Delegated Events: It’s vital to place delegated event listeners outside the ready function to prevent them from being rebound multiple times.

    • Incorrect:

      $(document).on('ready page:load', function() {
  // ... other initializations ...
  $(document).on('click', '.my-button', function() {
    // This will run multiple times if inside ready
    console.log("Button clicked (inside ready)");
  });
  // ...
});

    • Correct:

      $(document).on('ready page:load', function() {
  // ... other initializations ...
});

// Delegated event listener placed outside the ready function
$(document).on('click', '.my-button', function() {
  console.log("Button clicked (outside ready)");
});
Solution 4: Using page:change

An alternative event for handling page transitions is page:change.

$(document).on('page:change', function() {
  // Actions to perform on page change
  console.log("page:change event detected");
});

If you’re migrating existing JavaScript that relies on $(document).ready(), the jquery-turbolinks gem (mentioned in Solution 2) is a good option to maintain compatibility.

Solution 5: The Modern Approach with turbolinks:load

As noted in Solution 1, for Rails 5 and later, turbolinks:load is the recommended event.

$(document).on('turbolinks:load', function() {
   console.log('$(document).turbolinks:load executed');
});

In CoffeeScript:

$(document).on "turbolinks:load", ->
  alert "Page has loaded via turbolinks:load!"

This method is straightforward and generally preferred for newer Rails applications, as it avoids redundant executions.

Solution 6: Custom onLoad Function

Creating a global onLoad function can centralize your event handling.

  1. In application.js:

    // application.js
window.onLoad = function(callback) {
  // Binds both $(document).ready and $(document).on('page:load')
  $(document).ready(callback);
  $(document).on('page:load', callback);
};

  2. Using onLoad:

    • CoffeeScript:

      onLoad ->
  $('a.clickable').click ->
    alert('link clicked!');

    • JavaScript:

      onLoad(function() {
  $('a.clickable').click(function() {
    alert('link clicked');
  });
});

    This pattern ensures your callbacks are executed reliably on both initial loads and Turbolinks transitions.

Solution 7: Native addEventListener

For those avoiding jQuery or seeking a more native approach, addEventListener works effectively with turbolinks:load.

document.addEventListener("turbolinks:load", function() {
  // Your code here using native DOM APIs
  console.log("Native addEventListener for turbolinks:load");
});

This is a clean and efficient method, particularly if your project doesn’t heavily rely on jQuery.

Solution 8: Combined ready and turbolinks:load

A concise way to handle both scenarios is direct combination.

$(document).on('ready turbolinks:load', function() {
  console.log('$(document).turbolinks:load or ready');
});

This shorthand ensures your code runs when the DOM is ready and also when Turbolinks loads a new page.

Solution 9: Strict turbolinks:load Adherence

From Turbolinks’ official documentation, relying solely on turbolinks:load is recommended for consistency.

document.addEventListener("turbolinks:load", function() {
  // Your code here
  console.log("Strict turbolinks:load execution");
});

This approach avoids potential double executions by focusing on the event specifically designed for Turbolinks page transitions.

Solution 10: Using .on() for Event Delegation

Leveraging jQuery’s .on() method for event delegation is a robust practice, especially when combined with Turbolinks.

// Attaching a handler to a specific event on page load
$(document).on("page:load", attachRatingHandler);

// Using event delegation for clicks on dynamically added elements
$(document).on('click', 'span.star', attachRatingHandler);

This pattern is excellent for ensuring event handlers for elements that might be re-rendered by Turbolinks are correctly managed. For more details, see Rails 4: My first run in with Turbolinks .

Solution 11: Transitioning to Hotwired Turbo (2021+)

With the archiving of Turbolinks and its evolution into Hotwired Turbo, the event names have changed.

document.documentElement.addEventListener("turbo:load", (e) => {
  console.log("turbo:load event detected", e);
});

Hotwired Turbo broadcasts a range of events on document.documentElement, including:

  • turbo:click
  • turbo:before-visit
  • turbo:visit
  • turbo:submit-start
  • turbo:before-fetch-request
  • turbo:before-fetch-response
  • turbo:submit-end
  • turbo:before-cache
  • turbo:before-render
  • turbo:before-stream-render
  • turbo:render
  • turbo:load
  • turbo:before-frame-render
  • turbo:frame-render
  • turbo:frame-load
  • turbo:frame-missing
  • turbo:fetch-request-error

This modern approach is recommended for new projects or when upgrading.

Solution 12: Triggering ready on page:load

An interesting method is to manually trigger the ready event when page:load occurs.

$(document).on('page:load', function() {
  $(document).trigger('ready');
});

This can help ensure that code expecting a ready event fires even during Turbolinks transitions.

Solution 13: Preventing Double Execution with page:change

To avoid functions running twice, especially during development, you can manage event detachment.

$(document).on("page:change", function() {
     // Initialize things, but avoid rebinding events
     console.log("Initializing on page:change");
     // Detach the listener to prevent multiple executions
     $(document).off("page:change");
});

This strategy offers a way to control execution flow precisely, though using turbolinks:load or turbo:load is often cleaner.

Solution 14: Binding page:change with $(document).ready

This method combines the standard ready event with the page:change event for comprehensive coverage.

var load_this_javascript = function() {
  // do some things
  console.log("Executing load_this_javascript");
};
$(document).ready(load_this_javascript);
$(window).bind('page:change', load_this_javascript);

This ensures that your JavaScript runs both on the initial page load and subsequent Turbolinks navigations.

Solution 15: Adapting to Turbolinks 5+ Transitions

When upgrading to Turbolinks 5+, the transition from page:load to turbolinks:load is key.

  • Old Way (Turbolinks < 5):

    var ready;
ready = function() {
  // Your JS here
};
$(document).ready(ready);
$(document).on('page:load', ready);

  • New Way (Turbolinks 5+):

    var ready;
ready = function() {
  // Your JS here
};
$(document).on('turbolinks:load', ready);

    This simplifies your event handling for newer Turbolinks versions.

Solution 16: Concise ready and turbolinks:load Binding

A direct binding for both events is efficient.

$(document).ready(ready); // For initial load
$(document).on('turbolinks:load', ready); // For Turbolinks page changes

This is a straightforward way to ensure your ready function is called in both contexts.

Solution 17: Preventing Duplicates with a Flag

A common technique to prevent code from running multiple times is using a flag.

var has_loaded = false;
var ready = function() {
  if (!has_loaded) {
    has_loaded = true;
    // YOURJS here
    console.log("Executing JS for the first time");
  }
};

$(document).ready(ready);
$(document).bind('page:change', ready);

This ensures that the critical part of your ready function executes only once.

Solution 18: Centralized Event Handling with onInit

Creating a helper function like onInit can streamline your event management.

// In application.js
function onInit(callback) {
    $(document).ready(callback);
    $(document).on('page:load', callback);
}

// In other .js files, use onInit instead of $(function(){})
onInit(function() {
  console.log("Callback executed via onInit");
});

This promotes cleaner code by abstracting the event binding logic.

Solution 19: Gem and Script Placement for Speed Optimization

For speed optimizations involving placing JavaScript at the end of the <body>, the jquery-turbolinks gem and correct script placement are key. Ensure your application’s JavaScript is included in the <head> section of your application.html.erb when using this gem to avoid execution issues.

Solution 20: Conditional Binding based on Turbolinks Support

You can conditionally bind events based on whether Turbolinks is supported.

var ready = function() {
  // your code goes here
  console.log("Conditional execution based on Turbolinks support");
};

if (Turbolinks.supported == false) {
  $(document).on('ready', ready);
}
if (Turbolinks.supported == true) {
  $(document).on('turbolinks:load', ready);
};

This approach gracefully handles environments with and without Turbolinks enabled.

FAQs on Rails Turbolinks JavaScript Execution

Q: What is the primary issue when using JavaScript with Turbolinks

ANS: The main challenge is that Turbolinks replaces page content without a full browser reload, meaning traditional JavaScript event listeners like $(document).ready() might not execute on subsequent page transitions, leading to duplicated or missing script behavior.

Q: Which event should I use for Turbolinks page transitions

ANS: For older versions of Turbolinks, page:load or page:change were common. For Turbolinks 5 and later, turbolinks:load is the recommended event. If you’re using Hotwired Turbo, listen for turbo:load.

Q: How can I avoid JavaScript functions running multiple times

ANS: You can use a flag variable to ensure critical code executes only once, or detach event listeners after they’ve served their purpose. Alternatively, using the turbolinks:load event exclusively for page transitions often prevents duplication.

Q: Is there a gem to simplify jQuery and Turbolinks integration

ANS: Yes, the jquery-turbolinks gem automatically binds Turbolinks events to $(document).ready(), simplifying integration and allowing you to write jQuery more conventionally.

Q: How do I handle dynamically added elements with Turbolinks

ANS: Employ event delegation using jQuery’s .on() method. Attach the listener to a persistent parent element (like document) and specify the selector for the dynamic elements. For example: $(document).on('click', '.dynamic-button', function() { ... });.
