“Configuring Cross-Origin Resource Sharing (CORS) with Spring Security: Multiple Solutions”

When deploying web applications, especially those involving separate frontend and backend services, encountering Cross-Origin Resource Sharing (CORS) restrictions is frequent. Browsers enforce these policies for security, which is why tools like curl might work while browser-initiated AJAX requests fail. If you are using Spring Security, you must explicitly configure CORS support to prevent Spring Security from blocking these requests before they reach Spring MVC handlers.

How can one correctly enable and fine-tune CORS settings across different versions of Spring Boot and Spring Security? Several configuration strategies exist, ranging from leveraging annotations to providing custom Bean definitions.

Enabling CORS When Using Spring Security Configuration Adapters (Older Styles)

For applications using WebSecurityConfigurerAdapter (prior to Spring Security 5.x/6.x updates), explicit configuration within the security setup is necessary.

Strategy 1: Leveraging Spring MVC CORS Support via Security Configuration

If you utilize @CrossOrigin annotations at the controller level, enabling Spring Security’s CORS support allows it to defer to the existing Spring MVC configuration.

@EnableWebSecurity
public class WebSecurityConfig extends WebSecurityConfigurerAdapter {

    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http.cors().and().authorizeRequests()
            // ... other authorization rules
            ;
    }
}

Strategy 2: Global CORS Configuration via a Bean

Alternatively, you can define a global CORS configuration source as a Spring Bean, which Spring Security will utilize.

@EnableWebSecurity
public class WebSecurityConfig extends WebSecurityConfigurerAdapter {

    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http.cors().and().authorizeRequests()
            // ... other authorization rules
            ;
    }

    @Bean
    CorsConfigurationSource corsConfigurationSource() {
        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        // Permits all origins, methods, and exposes default values
        source.registerCorsConfiguration("/**", new CorsConfiguration().applyPermitDefaultValues());
        return source;
    }
}

Strategy 3: Concise Lambda Configuration (JDK 8+)

If you are on JDK 8 or newer, a more compact approach uses a lambda expression directly in the security configuration:

@EnableWebSecurity
public class WebSecurityConfig extends WebSecurityConfigurerAdapter {

    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http.cors().configurationSource(request -> 
            new CorsConfiguration().applyPermitDefaultValues()
        );
        // ...
    }
}

Modern Approaches for Spring Boot 2.7+ and Spring Security 6+

Newer versions of Spring Security utilize SecurityFilterChain beans rather than extending WebSecurityConfigurerAdapter.

Strategy 4: Customizing CORS within SecurityFilterChain

When defining the SecurityFilterChain, you can apply CORS configuration directly:

@Configuration
public class WebSecurityConfig {
    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            // Enable CORS support using default configuration source bean
            .cors(withDefaults())
            .authorizeRequests(authorizeRequests ->
                authorizeRequests
                    .antMatchers("/**").permitAll() // Example rule
                    .anyRequest().authenticated()
            )
            .csrf(HttpSecurityDsl::disable)
            .build();
        return http.build();
    }

    // Provide the CorsConfigurationSource bean referenced by http.cors(withDefaults())
    @Bean
    CorsConfigurationSource corsConfigurationSource() {
        CorsConfiguration configuration = new CorsConfiguration();
        configuration.setAllowedHeaders(List.of("*")); 
        configuration.setAllowedOrigins(List.of("*"));
        configuration.setAllowedMethods(List.of("*"));
        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/**", configuration);
        return source;
    }
}

Strategy 5: Dedicated Configuration Class using WebMvcConfigurer

For configuring CORS behavior independent of Spring Security’s direct integration, defining a bean implementing WebMvcConfigurer is a standard Spring MVC technique. This often works seamlessly with Spring Security if security is configured to use the MVC settings (as shown in Strategy 1 and 14).

@Configuration
public class WebMvcConfig implements WebMvcConfigurer {
    
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/**")
                .allowedOrigins(
                        "http://localhost:5173",
                        "http://localhost:8080"
                )
                .allowedMethods("GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS")
                .allowedHeaders("*")
                .allowCredentials(true)
                .maxAge(3600L); // MAX_AGE_SECS
    }
}
// In SecurityConfig:
// http.cors(Customizer.withDefaults());

Strategy 6: Global Configuration with Specific Permissions (Spring Boot 2.7+)

For a custom setup in modern Spring Boot, explicitly defining headers, methods, and origins within a SecurityFilterChain configuration is precise:

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        CorsConfiguration corsConfiguration = new CorsConfiguration();
        corsConfiguration.setAllowedHeaders(List.of("Authorization", "Cache-Control", "Content-Type"));
        corsConfiguration.setAllowedOrigins(List.of("*")); // Use specific domains in production
        corsConfiguration.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS", "PATCH"));
        corsConfiguration.setAllowCredentials(true);
        corsConfiguration.setExposedHeaders(List.of("Authorization"));

        return http
                .cors(cors -> cors.configurationSource(request -> corsConfiguration)) // Applying the custom config
                .authorizeRequests(authorizeRequests ->
                        authorizeRequests
                                .antMatchers("/**").permitAll()
                                .anyRequest().authenticated()
                )
                .csrf(HttpSecurityDsl::disable)
                .build();
    }
}

Alternative Methods and Edge Cases

Method A: Annotation-Based Configuration Per Endpoint

For granular control on specific methods, the @CrossOrigin annotation suffices, although it bypasses global configurations for that endpoint:

@CrossOrigin(origins = "*") // Use specific origin(s) instead of "*" in production
@RequestMapping(value="/schedulerActive")
public String isSchedulerActive(){
  // Service logic
}

Method B: Manual Filter Implementation

In cases where framework integration proves difficult, a custom Filter can be employed to manually inject necessary headers, though this often requires careful ordering via @Order(Ordered.HIGHEST_PRECEDENCE):

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class MyCorsFilterConfig implements Filter {

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) throws IOException, ServletException {
        final HttpServletResponse response = (HttpServletResponse) res;
        response.setHeader("Access-Control-Allow-Origin", "*");
        response.setHeader("Access-Control-Allow-Methods", "POST, PUT, GET, OPTIONS, DELETE");
        response.setHeader("Access-Control-Allow-Headers", "Authorization, Content-Type, enctype");
        response.setHeader("Access-Control-Max-Age", "3600");
        
        if (HttpMethod.OPTIONS.name().equalsIgnoreCase(((HttpServletRequest) req).getMethod())) {
            response.setStatus(HttpServletResponse.SC_OK);
        } else {
            chain.doFilter(req, res);
        }
    }
    // init and destroy methods implementation omitted for brevity
}

Method C: WebFlux (Reactive) Configuration

For reactive stacks (WebFlux), security configuration differs significantly:

@Bean
public SecurityWebFilterChain securityWebFilterChain(ServerHttpSecurity http) {
  return http.cors().and().build();
}

@Bean
public CorsWebFilter corsFilter() {
  CorsConfiguration config = new CorsConfiguration();
  config.applyPermitDefaultValues();
  config.addAllowedHeader("Authorization");
  
  UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
  source.registerCorsConfiguration("/**", config);

  return new CorsWebFilter(source);
}

Handling Pre-Flight Requests with Authentication (Axios Gotcha)

A common pitfall involves authenticated requests (e.g., using Authorization headers). The pre-flight OPTIONS request may fail if Spring Security does not explicitly permit it and the allowed headers list does not include Authorization.

For older Spring Security versions (e.g., 4.2.4), you must permit OPTIONS requests specifically:

// In HttpSecurity configuration:
http.cors().and().
        authorizeRequests()
        .requestMatchers(CorsUtils::isPreFlightRequest).permitAll() // Crucial for OPTIONS
        .anyRequest().authenticated()
        // ...

If using Authorization header, ensure it’s in the allowedHeaders list for the CorsConfiguration.

Edge Layer Consideration

It is critical to note that if your application is behind proxies (Nginx, API Gateways like Kong, or Istio), these components might strip or overwrite CORS headers from the backend response. In production, configuring CORS handling at the edge layer is often the best practice to ensure consistency across all ingress points.

FAQs on Configuring CORS with Spring Security

Q: Why do requests work in Postman but fail in the browser

ANS: This occurs because CORS restrictions are enforced by the web browser for security. Tools like Postman, cURL, or Swagger do not adhere to these same-origin policies, hence they succeed while browser AJAX calls fail due to missing Access-Control-Allow-Origin headers.

Q: Should I use '*' for allowedOrigins in production

ANS: While using * allows any origin, it is strongly discouraged for production environments handling sensitive data. Specify the exact domains hosting your frontend application(s) instead. The wildcard is generally suitable only for public APIs or development stages.

Q: Is CORS configuration sufficient to prevent API misuse

ANS: No. CORS policies are browser-side mechanisms intended to prevent accidental cross-origin data leakage. They are not a robust security measure against malicious attacks, as they can be bypassed via proxies or different client types. Proper authentication and authorization checks within Spring Security remain the primary defense.

Q: What is the purpose of the OPTIONS method in CORS

ANS: The OPTIONS method is used by browsers to perform a “pre-flight” check before sending complex requests (like PUT, DELETE, or requests with non-standard headers, such as Authorization). Your server must explicitly allow the OPTIONS method in its CORS configuration to respond successfully to these pre-flight requests.
