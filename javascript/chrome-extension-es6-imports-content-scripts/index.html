“Chrome Extension Content Scripts: How to Use ES6 Imports for Modular Code”

Content scripts in Chrome Extensions operate in an isolated JavaScript environment, which historically presented a hurdle for utilizing modern ES6 module syntax (import/export) directly as native support was absent (as noted around early 2018). Developers require techniques to structure their content scripts modularly while maintaining access to extension APIs like chrome.runtime.

What robust techniques exist to implement ES6 modularity within Chrome Extension content scripts, specifically addressing the limitations of static imports?

Solution 1: Asynchronous Dynamic import() Function

A preferred, safer method involves using the asynchronous import() function within an Immediately Invoked Function Expression (IIFE) to dynamically load ES modules. This approach executes within the content script’s safe JS environment, allowing the imported module access to global variables and built-in Chrome APIs, such as chrome.runtime.sendMessage.

Important Caveat: This dynamic loading mechanism might encounter issues if blocked by the website’s service worker.

Implementation Details:

The primary content script (content_script.js) initiates the load:

// content_script.js: Initiating dynamic import
(async () => {
  const moduleSource = chrome.runtime.getURL("modules/content_main.js");
  try {
    const contentMain = await import(moduleSource);
    contentMain.initializeLogic(); // Assuming 'initializeLogic' is the entry point
  } catch (error) {
    console.error("Failed to load dynamic module:", error);
  }
})();

For this to function, the script file (modules/content_main.js) must be explicitly declared in the extension’s manifest under web_accessible_resources.

Manifest V3 Declaration:

// manifest.json (V3)
"web_accessible_resources": [{
   "matches": ["<all_urls>"],
   "resources": ["modules/content_main.js"]
}],

Manifest V2 Declaration:

// manifest.json (V2)
"web_accessible_resources": [
   "modules/content_main.js"
]

If you need to load a non-module script synchronously, list its name in the content_scripts.js array before your main script runs.

Solution 2: Injecting a <script type="module"> Tag (Use with Caution)

This technique directly injects an ES module script tag into the webpage’s DOM from the content script.

⚠️ Security Warning: This method runs the module script in the page’s JavaScript context, not the isolated content script context. This exposure means page scripts or other extensions can potentially exploit prototype setters/getters or proxy global objects, compromising your code and data. The dynamic import() method (Solution 1) is generally safer.

Workaround Steps:

  1. Declare all necessary scripts (main.js, my-script.js) in web_accessible_resources.
  2. In your entry content script (content.js), create and insert the module tag:
// content.js: Injecting the module
'use strict';

const scriptElement = document.createElement('script');
scriptElement.setAttribute("type", "module");
scriptElement.setAttribute("src", chrome.extension.getURL('main.js'));

const insertionPoint = document.head || document.getElementsByTagName("head")[0] || document.documentElement;
if (insertionPoint) {
    insertionPoint.insertBefore(scriptElement, insertionPoint.lastChild);
}

If main.js imports other modules (like my-script.js), they must also be in web_accessible_resources.

Example usage demonstrating separation:

my-script.js (Exports functionality):

// my-script.js
'use strict';

export const triggerAlert = () => { 
    window.alert('Module content executed!'); 
};

main.js (Imports and executes):

// main.js
'use strict';

import { triggerAlert } from './my-script.js';
triggerAlert();
// Logic continues here...

The manifest configuration needs to list content.js under content_scripts.

Solution 3: Leveraging Content Script Globals (Isolated World)

Content scripts share a specific isolated global namespace inaccessible to the page, except in Manifest V3 when running in the MAIN world (which exposes globals). If operating in the isolated world, you can structure dependency loading sequentially to share data via globalThis.

This avoids import syntax by loading files in dependency order, where preceding scripts define global variables used by subsequent scripts.

Implementation Example:

manifest.json:

// manifest.json
"content_scripts": [
  {
    "matches": ["<all_urls>"],
    "js": [
      "scripts/global_setup.js",
      "scripts/feature_a.js",
      "scripts/main_script.js"
    ]
  }
],

scripts/global_setup.js (Defines shared variables):

// global_setup.js
'use strict';
globalThis.APP_CONFIG = { version: "1.0", debug: true };
globalThis.logValue = (val) => console.log(`[Config Value]: ${val}`);

scripts/feature_a.js (Uses defined variables):

// feature_a.js
'use strict';
if (globalThis.APP_CONFIG.debug) {
    globalThis.logValue("Configuration loaded successfully.");
}

If external libraries are needed, bundling (see Solution 4) is necessary to consolidate dependencies into one file listed here.

Solution 4: Using Build Tools (Webpack or Rollup)

The most conventional path for complex projects utilizing modular patterns is adopting a bundler like Webpack or Rollup. These tools resolve ES modules dependencies locally and output a single, optimized JavaScript bundle compatible with content scripts.

Webpack Configuration Snippet:

A basic Webpack configuration can define multiple entry points (e.g., for background scripts and content scripts):

// webpack-ext.config.js
const path = require('path');

module.exports = {
  entry: {
    background: './src/background.js',
    content: './src/content_entry.js', // Entry point for content logic
  },
  output: {
    filename: '[name].js',
    path: path.resolve(__dirname, '../build'),
  }
};
// Command: webpack --config ./ext/webpack-ext.config.js

Solution 5: Leveraging Immediately Invoked Function Expressions (IIFE) for Encapsulation

This approach mimics modularity by using IIFEs to encapsulate scope and expose specific functions or data structures via a single entry point listed in the manifest. This prevents variables from polluting the global scope unnecessarily while still allowing controlled sharing between scripts loaded sequentially.

If helpers/helpers.js defines functionality:

// helpers/helpers.js
var SharedUtils = (function() {
  function calculateHash(input) {
    // Complex hashing logic here
    return input.length * 101; 
  }
  return {
    hashData: calculateHash
  };
})();

Your main content script can access this via the assigned global name:

// main-content-script.js
const dataToProcess = "important_payload";
const hash = SharedUtils.hashData(dataToProcess);
console.log(`Calculated hash: ${hash}`);

The manifest must list helpers/helpers.js before any script that depends on SharedUtils.

Solution 6: Vite Users with @crxjs/vite-plugin (Manifest V3)

For developers using Vite, the @crxjs/vite-plugin simplifies bundling content scripts written using ES module syntax for Manifest V3 projects. This plugin integrates Vite’s capabilities, allowing standard imports in your script files.

  1. Install the plugin: npm install --save-dev @crxjs/vite-plugin
  2. Configure vite.config.ts:
// vite.config.ts
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import { crx } from '@crxjs/vite-plugin';
import manifest from './manifest.json';

export default defineConfig({
  plugins: [
    react(),
    crx({ manifest }), // Ensures bundling handles extension structure
  ],
});

Solution 7: Manual Export/Import Simulation via Global Storage

A clever, custom strategy involves creating a bootstrap script (modules-start.js) that defines global functions (exportVars and importVarsFrom) to manually manage state objects based on namespace strings. This simulates the behavior of import/export without relying on native module support in the browser environment of the content script.

modules-start.js:

let exportVars, importVarsFrom;
{
  const moduleRegistry = {};
  exportVars = (varsObject) => ({
    from(namespace) {
      moduleRegistry[namespace] || (moduleRegistry[namespace] = {});
      for (const [key, value] of Object.entries(varsObject)) {
        moduleRegistry[namespace][key] = value;
      }
    }
  });
  importVarsFrom = (namespace) => moduleRegistry[namespace];
}

Exporting Example (utilities.js):

{
  const secretKey = "f00";
  const processData = (data) => data.toUpperCase() + secretKey;
  
  exportVars({ processData }).from('data-processors');
}

Importing Example (ui_handler.js):

{
  const { processData: formatAndStamp } = importVarsFrom('data-processors');
  
  console.log(`Formatted result: ${formatAndStamp("test input")}`);
}

Manifest loading order is critical here: modules-start.js must load first, followed by exporters, and finally importers.

Solution 8: Using Rollup Bundler

Similar to Webpack, Rollup offers excellent control for building extension assets. Plugins like rollup-plugin-chrome-extension help manage manifest inclusion and structure.

Required Packages: npm i -D rollup rollup-plugin-chrome-extension @rollup/plugin-node-resolve @rollup/plugin-commonjs

rollup.config.js:

import resolve from '@rollup/plugin-node-resolve';
import commonjs from '@rollup/plugin-commonjs';
import { chromeExtension, simpleReloader } from 'rollup-plugin-chrome-extension';

export default {
  input: 'src/manifest.json', // Entry point based on manifest structure
  output: {
    dir: 'dist',
    format: 'esm',
  },
  plugins: [
    chromeExtension(), // Must precede other plugins
    simpleReloader(),
    resolve(),
    commonjs(),
  ],
};

Solution 9: Utilizing esbuild for Quick Bundling

esbuild provides a fast, zero-config solution for bundling JavaScript files, effectively resolving module imports into a single output file suitable for content scripts.

  1. Install: npm install --save-exact esbuild
  2. Bundle your entry point: esbuild src/content_entry.js --bundle --outfile=dist/content_bundle.js

Update your manifest.json to reference content_bundle.js instead of content.js in the content_scripts section. esbuild can also target specific browser compatibility levels using flags like --target.

Solution 11: Considering WXT Framework (Modern Alternative)

For contemporary development, frameworks built atop Vite, like WXT, handle the complexities of managing multiple entry points (content scripts, background workers) efficiently. WXT streamlines the build process, often negating the need for manual config gymnastics required by older Vite/Rollup setups, offering superior speed and simplified configuration management for modular codebases.

FAQs on Chrome Extension ES6 Imports Content Scripts

Q: Can I use static import statements like import { func } from './file.js' directly in content scripts

ANS: No, static ES module imports are not natively supported directly within standard content scripts. You must use workarounds like dynamic import(), bundlers, or global scope sharing.

Q: Which solution is safest for accessing chrome APIs after importing modules

ANS: The asynchronous dynamic import() function (Solution 1) is safest as it operates within the content script’s isolated world, preserving access to Chrome APIs like chrome.runtime. Injecting <script type="module"> (Solution 2) runs in the page’s context and is less secure.

Q: Do I need to declare imported scripts in web_accessible_resources

ANS: Yes, if you are using the dynamic import() function or injecting a <script type="module"> tag that points to a file within your extension, that resource must be listed in the web_accessible_resources section of your manifest file.
