“Fixing React Native Android Build Failures Post 0.71.0-rc0 Release”

Facing unexpected Android build failures in a React Native project, especially if the issue arose without recent code modifications? A known cause centers around the publication of React Native version 0.71.0-rc0. This situation often manifests as dependency resolution problems where Gradle fetches an incorrect or incompatible version of the React Native Android library from public repositories like Maven Central instead of the local one bundled with the npm package.

Before applying any fixes, it is strongly advised to revert any recent changes you might have made, as suggested in related discussions, such as those found on Stack Overflow .

Diagnosing the Core Issue: Dependency Precedence

The crux of the problem lies in how Gradle resolves dependencies when multiple repositories are defined, particularly when the dependency is specified using a flexible version specifier (like +).

The React Native team previously shipped Android binaries within the npm package (node_modules/react-native/android/). Libraries configured their build.gradle files to explicitly check this local directory first:

repositories {
  maven {
    url "$rootDir/../node_modules/react-native/android"
  }
  google()
  mavenLocal()
  mavenCentral()
}

dependencies {
  // Using '+' lets Gradle pick the 'latest' available version across declared repos
  implementation 'com.facebook.react:react-native:+'
}

When 0.71.0-rc0 (and subsequent versions) started being published to Maven Central, Gradle, honoring the + symbol, began selecting the version from Maven Central, which conflicted with local project setups or introduced newer dependencies (like a different Kotlin metadata version) causing compilation errors (e.g., “Class ‘kotlin.Unit’ was compiled with an incompatible version…”).

Methods to Force Local React Native Resolution

Several effective Gradle configurations can steer Gradle back to the correct, local React Native Android binaries located in node_modules.

Alternative 1: Employing exclusiveContent Resolution (Recommended Fix)

The most targeted solution is to use Gradle’s exclusiveContent block within allprojects to mandate that the resolution for the com.facebook.react group must only originate from the local node_modules/react-native/android directory. This prevents Gradle from looking at Maven Central for that specific artifact.

Apply this configuration to your android/build.gradle file:

// android/build.gradle excerpt

allprojects {
    repositories {
       exclusiveContent {
           filter {
               includeGroup "com.facebook.react"
           }
           forRepository {
               maven {
                   url "$rootDir/../node_modules/react-native/android"
               }
           }
       }
        // Other repositories follow...
        // google()
        // mavenCentral()
    }
}

This rule forces the resolution of the React Native Android library to its source within node_modules.

Alternative 2: Version Forcing via resolutionStrategy

If your Gradle version does not fully support or you prefer an explicit override, you can dynamically determine the installed React Native version and force Gradle to use it, sidestepping any newer version found elsewhere.

This approach requires reading the version from react-native/package.json:

// Calculate the current installed React Native version using Node
def REACT_NATIVE_VERSION = new File(['node', '--print', "JSON.parse(require('fs').readFileSync(require.resolve('react-native/package.json'), 'utf-8')).version"].execute(null, rootDir).text.trim())

allprojects {
    configurations.all {
          resolutionStrategy {
            // Explicitly force the version found locally
            force "com.facebook.react:react-native:" + REACT_NATIVE_VERSION
          }
    }
    // ... other configurations
}

Alternative 3: Upgrading React Native or Applying Patches

A non-configuration change solution involves upgrading the React Native version. Facebook has issued patch releases for versions >=0.63 that specifically address these repository conflicts. Checking the official React Native GitHub issue tracker for the latest recommended patch version for your base release might provide a permanent fix without code edits to build.gradle.

Alternative 4: Cleaning Bundle Output (For Subsequent APK Issues)

In separate but related build scenarios, sometimes an APK generated via ./gradlew assembleRelease shows no apparent changes even after version bumps. This often relates to the JavaScript bundle cache. Ensure you explicitly rebuild the bundle:

npx react-native bundle --platform android --dev false --entry-file index.js --bundle-output android/app/src/main/assets/index.android.bundle --assets-dest android/app/src/main/res

Follow this by cleaning the project build artifacts (./gradlew clean) and rebuilding. One user noted fixing a similar persistence issue by simply incrementing the versionName in android/build.gradle.

// Example change in android/build.gradle for build persistence:
android {
    defaultConfig {
        // ...
        versionName '4.0.3' // Changed from '4.0.2'
    }
}

Synthesis of Best Practices

For direct fixes related to the external Maven publication interfering with local dependencies, using the exclusiveContent block (Alternative 1) is often the cleanest way to isolate the React Native artifact resolution. After implementing any Gradle fix, always execute a gradle clean followed by a rebuild (react-native run-android or ./gradlew assembleRelease).

FAQs on Fixing React Native Android Build Failures

Q: Why is my React Native project suddenly failing Android builds

ANS: The failure is often linked to the publication of React Native version 0.71.0-rc.0 to Maven Central, causing Gradle to pull an incorrect version when using dependency specifiers like ‘+’.

Q: What does the exclusiveContent block achieve in build gradle

ANS: The exclusiveContent block forces Gradle to look only within the specified local repository path (node_modules/react-native/android) when resolving artifacts belonging to the com.facebook.react group, preventing resolution from external repositories like Maven Central.

Q: How can I check the Kotlin metadata version error source

ANS: The Kotlin metadata error usually stems from a mismatch caused by fetching a React Native version (or a dependency it pulls) that was compiled with a newer Kotlin version than expected by your project’s environment.

Q: Is upgrading React Native an acceptable alternative fix

ANS: Yes, applying recommended patch releases for your existing major version, or upgrading to a newer stable version that incorporates the fix upstream, is a valid alternative to applying manual Gradle configurations.
