“Python’s all: Controlling Module and Package Exports”

When developing Python modules and packages, managing what symbols are exposed to users is crucial for maintaining a clean and predictable interface. Python offers a mechanism to explicitly define these publicly accessible names using the __all__ variable. This variable plays a significant role in how modules and packages behave, particularly with wildcard imports (from module import *).

What exactly does __all__ do in Python, and how can it be leveraged to manage a module’s public API?

The primary function of __all__ is to declare the “publicly intended” names within a module. When defined, it acts as a definitive list of symbols that users are expected to interact with, providing an assurance that these names will remain stable. This explicit declaration also influences the behavior of certain import statements and documentation tools.

Core Functionality of __all__:

  • Defining Public Interface: __all__ serves as a curated list of names (functions, classes, variables) that constitute the module’s public API. This helps users identify intended entry points and prevents reliance on internal implementation details.
  • Controlling Wildcard Imports (from module import *): When __all__ is present in a module, a wildcard import will only bring the names specified in __all__ into the importing namespace. Without __all__, a wildcard import defaults to importing all names not starting with an underscore.
  • Influencing Documentation Tools: Tools like pydoc can inspect __all__ to determine which names to display as available within a module, aiding in generating clear documentation.
  • Package Structure Management: Within a package’s __init__.py file, __all__ can specify which submodules or objects from submodules should be exposed when using from package import *.

How __all__ Works with Modules

Consider a module, say calculator.py:

# calculator.py

__all__ = ['add', 'subtract'] # Explicitly defines public functions

PI = 3.14159
def add(a, b):
    """Adds two numbers."""
    return a + b

def subtract(a, b):
    """Subtracts the second number from the first."""
    return a - b

def _internal_helper():
    """An internal helper function."""
    print("This is an internal detail.")

When another script imports calculator using a wildcard import:

# main_script.py
from calculator import *

print(add(5, 3))
print(subtract(10, 4))
# print(PI) # This would raise a NameError
# _internal_helper() # This would also raise a NameError

The add and subtract functions are accessible because they are listed in __all__. However, PI and _internal_helper, while present in the module, are not imported by from calculator import * because they are not in __all__.

If __all__ were commented out in calculator.py, the wildcard import from calculator import * would have imported PI, add, subtract, and _internal_helper (as none start with an underscore).

__all__ in Packages

For packages, __all__ in the __init__.py file dictates which submodules or objects are exposed through a wildcard import from the package itself.

Let’s set up a simple package structure:

my_package/
├── __init__.py
├── module_a.py
└── module_b.py

my_package/__init__.py:

# my_package/__init__.py
from .module_a import public_func_a
from .module_b import PublicClassB

# Explicitly define what gets imported with 'from my_package import *'
__all__ = ['public_func_a', 'PublicClassB']

my_package/module_a.py:

# my_package/module_a.py
def public_func_a():
    """A public function from module A."""
    print("Hello from module A!")

def _private_func_a():
    """An internal function in module A."""
    pass

my_package/module_b.py:

# my_package/module_b.py
class PublicClassB:
    """A public class from module B."""
    def __init__(self):
        print("Instance of PublicClassB created.")

class _PrivateClassB:
    """An internal class in module B."""
    pass

Now, in another script:

# main_app.py
from my_package import *

public_func_a()
instance_b = PublicClassB()

# The following would fail because they are not in __all__ or the package's __init__.py
# from my_package import module_a # This is not exposed by wildcard import
# from my_package import _private_func_a # Also not exposed

By defining __all__ in my_package/__init__.py, we control what the from my_package import * statement makes directly available.

Alternative Approaches and Considerations

While __all__ is the standard way to manage public APIs and control wildcard imports, Python’s import system has other conventions:

  • Underscore Prefix: By default, names starting with an underscore (_) are considered internal implementation details and are not imported by from module import *. You can rely on this convention alone if you prefer not to use __all__, though it’s less explicit. For example, _internal_detail = 10 in a module won’t be imported by import *.

  • Decorators for Export: For a more dynamic approach, a custom decorator can be used to automatically add names to __all__. This can reduce redundancy if you define many functions or classes.

    # export_decorator.py
import sys

def export(func):
    """Decorator to add a function to __all__."""
    mod = sys.modules[func.__module__]
    if not hasattr(mod, '__all__'):
        mod.__all__ = []
    mod.__all__.append(func.__name__)
    return func

# example_module.py
from export_decorator import export

__all__ = [] # Initialize __all__

@export
def greet(name):
    return f"Hello, {name}!"

@export
def farewell(name):
    return f"Goodbye, {name}!"

def _internal_logic():
    pass

# Using the module:
# from example_module import *
# print(greet("World"))

When Might You Avoid __all__?

  • Rapid Prototyping: During the very early stages of development, when the API is highly fluid and there are no external users, the overhead of defining __all__ might seem unnecessary.
  • Internal Modules: If a module is strictly for internal use within a project and never intended for external consumption, managing __all__ might be less critical.

However, even in these cases, explicitly defining __all__ can improve code clarity and prevent accidental exposure of internal components as the project matures. It’s generally considered good practice to define __all__ for modules that form part of a public or semi-public API.

FAQs on Python’s __all__

Q: What is the main purpose of the __all__ variable in Python

ANS: The primary purpose of __all__ is to explicitly declare the public API of a Python module or package, controlling which names are exported during wildcard imports (from module import *).

Q: How does __all__ affect wildcard imports

ANS: When __all__ is defined in a module, from module import * will only import the names listed in __all__. If __all__ is not defined, from module import * imports all names not starting with an underscore.

Q: Can __all__ be used in Python packages

ANS: Yes, __all__ can be defined in a package’s __init__.py file to specify which submodules or objects from submodules should be imported when using from package import *.

Q: What happens if __all__ is defined as an empty list

ANS: If __all__ is defined as an empty list (__all__ = []), then from module import * will not import any names from that module, effectively making its public API empty for wildcard imports.

Q: Does __all__ affect normal imports like 'import module' or 'from module import name'

ANS: No, __all__ only influences the behavior of wildcard imports (from module import *). Regular imports like import module or from module import specific_name are not affected by __all__.

Q: Is it mandatory to define __all__

ANS: No, defining __all__ is optional. However, it is highly recommended for modules intended for broader use to clearly define their public interface and control import behavior.

Q: How does __all__ relate to names starting with an underscore

ANS: By default, names starting with an underscore are considered internal and are not imported by from module import *. If __all__ is defined, it overrides this default behavior, and only the names explicitly listed in __all__ are imported, regardless of whether they start with an underscore.
