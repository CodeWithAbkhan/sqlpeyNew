“Safely Evaluating User Input in Python: eval vs. ast.literal_eval”

The Perils of eval()

The eval() function in Python is designed to execute a string as a Python expression. While this flexibility is useful in specific controlled scenarios, it becomes a major security vulnerability when used with input that hasn’t been rigorously sanitized. Imagine a user inputting a string like __import__('os').system('rm -rf /'). If this string is passed to eval(), it can execute arbitrary, potentially destructive commands on your system.

# DANGEROUS EXAMPLE: Never use eval with untrusted input!
user_input = input("Enter some Python code: ")
eval(user_input)

As demonstrated by the following example, even restricting global and local variables using eval("__import__('os').system('rm -rf /')", {'__builtins__': {}}, {}) doesn’t fully safeguard against malicious code injection, as advanced techniques can still bypass these restrictions.

# Advanced exploitation example for eval
malicious_code = """

        if c.__name__ == n
    ][0]

fc("function")(
    fc("code")(
        0,0,0,0,"KABOOM",(),(),(),"","",0,""
    ),{}

"""
# Even with restricted builtins, this can be exploited
eval(malicious_code, {'__builtins__': {}})

Furthermore, Python’s evaluation process is eager. This means eval(input(...)) will execute the user’s input immediately when the eval() function is called, irrespective of subsequent data handling.

The Safe Haven: ast.literal_eval()

The ast module, specifically the ast.literal_eval() function, provides a much safer alternative for evaluating strings that represent Python literal data structures. It is designed to evaluate a string containing a Python literal or container display, but it strictly limits the allowed syntax.

ast.literal_eval() only permits strings, bytes, numbers (integers, floats, complex), tuples, lists, dictionaries, sets, booleans, and None. It will raise a ValueError if the input contains anything else, such as function calls or expressions that could lead to code execution.

Syntax:

import ast

# For evaluating a string containing a literal
ast.literal_eval(node_or_string)

Key behaviors:

  • Python 2.x vs. Python 3.x: In earlier Python versions (2.x), ast.literal_eval() did not accept operators within strings. For example, ast.literal_eval('1+1') would result in a ValueError. In Python 3.0-3.6, it could evaluate simple arithmetic like ast.literal_eval("1+1").
  • Python 3.7+ Strictness: Starting from Python 3.7, ast.literal_eval() became even stricter, disallowing the addition and subtraction of arbitrary numbers within string literals.
  • Safe for Literals: It safely evaluates expressions that consist solely of these literal structures. Attempting to evaluate potentially harmful code like __import__('os').system('rm -rf /') will result in an error.

Code Examples:

import ast

# Safe evaluation of a list
safe_list = ast.literal_eval('[1, 2, 3]')
print(f"Evaluated list: {safe_list}, Type: {type(safe_list)}")

# Safe evaluation of a dictionary
safe_dict = ast.literal_eval("{'a': 2, 'b': 3, 3: 'xyz'}")
print(f"Evaluated dictionary: {safe_dict}, Type: {type(safe_dict)}")

# Attempting to evaluate an unsafe expression (will raise ValueError)
try:
    unsafe_expression = "__import__('os').system('echo malicious')"
    ast.literal_eval(unsafe_expression)
except ValueError as e:
    print(f"Caught expected error: {e}")

# Attempting to evaluate an arithmetic expression in newer Python versions
try:
    arithmetic_expression = "1+1"
    result = ast.literal_eval(arithmetic_expression)
    print(f"Evaluated arithmetic: {result}") # This might succeed in older Python 3 versions
except ValueError as e:
    print(f"Caught expected error for arithmetic: {e}")

Advanced Safe Evaluation with ast.parse()

For more complex scenarios where you need to evaluate expressions beyond simple literals, you can build a custom safe evaluation function using ast.parse(). This allows you to parse the input into an Abstract Syntax Tree (AST) and then recursively traverse the tree, only allowing specific operations and functions.

This approach provides granular control over what code can be executed. You can define allowed binary operations (addition, subtraction, multiplication, division), unary operations (negation), and even specific function calls (e.g., from the math module).

Here’s an example of a safe_eval function that restricts operations and allows calls to certain math functions:

import ast
import logging
import math
import operator

logger = logging.getLogger(__name__)

def safe_eval(s):
    """
    Safely evaluates a string containing mathematical expressions.
    Allows basic arithmetic operations and specific math functions.
    """
    def check_math_function(name, *args):
        """Validates and calls functions from the math module."""
        if name not in [func for func in dir(math) if not func.startswith("__")]:
            msg = f"Unknown function: {name}()"
            raise SyntaxError(msg)
        func = getattr(math, name)
        return func(*args)

    # Define allowed binary and unary operations
    allowed_bin_ops = {
        ast.Add: operator.add,
        ast.Sub: operator.sub,
        ast.Mult: operator.mul,
        ast.Div: operator.truediv,
        ast.Mod: operator.mod,
        ast.Pow: operator.pow,
    }

    allowed_un_ops = {
        ast.USub: operator.neg,
        ast.UAdd: operator.pos,
    }

    # Combine all allowed AST node types for checking
    allowed_node_types = tuple(allowed_bin_ops) + tuple(allowed_un_ops) + (ast.Call,)

    try:
        # Parse the input string into an AST, expecting an expression
        tree = ast.parse(s, mode="eval")
    except SyntaxError as e:
        raise SyntaxError(f"Invalid syntax in expression: {e}")

    def _evaluate_node(node):
        """Recursively evaluates AST nodes."""
        if isinstance(node, ast.Expression):
            return _evaluate_node(node.body)
        elif isinstance(node, ast.Constant): # For Python 3.8+ ast.Constant
            return node.value
        elif isinstance(node, ast.Num): # For older Python versions that used ast.Num
            return node.n
        elif isinstance(node, ast.Str): # For older Python versions that used ast.Str
            return node.s
        elif isinstance(node, ast.NameConstant): # For True, False, None
            return node.value
        elif isinstance(node, ast.BinOp):
            left = _evaluate_node(node.left)
            right = _evaluate_node(node.right)
            op_type = type(node.op)
            if op_type in allowed_bin_ops:
                return allowed_bin_ops[op_type](left, right)
            else:
                raise SyntaxError(f"Disallowed binary operation: {op_type.__name__}")
        elif isinstance(node, ast.UnaryOp):
            operand = _evaluate_node(node.operand)
            op_type = type(node.op)
            if op_type in allowed_un_ops:
                return allowed_un_ops[op_type](operand)
            else:
                raise SyntaxError(f"Disallowed unary operation: {op_type.__name__}")
        elif isinstance(node, ast.Call):
            # Ensure the function being called is a valid identifier
            if not isinstance(node.func, ast.Name):
                raise SyntaxError("Only direct function calls are allowed.")
            func_name = node.func.id
            args = [_evaluate_node(arg) for arg in node.args]
            # Allow calls to math functions
            return check_math_function(func_name, *args)
        else:
            raise SyntaxError(f"Unsupported AST node type: {type(node).__name__}")

    return _evaluate_node(tree)

Alternative: json.loads() for Dictionaries

If your primary goal is to parse user-provided dictionaries and you don’t need complex expressions, json.loads() is another excellent and safe option. The main constraint of JSON is that dictionary keys must be strings.

import json

user_dict_string = '{"name": "Alice", "age": 30, "city": "New York"}'
try:
    data = json.loads(user_dict_string)
    print(f"Parsed JSON data: {data}, Type: {type(data)}")
except json.JSONDecodeError as e:
    print(f"Error decoding JSON: {e}")

Considerations and Best Practices

  • Trust Boundaries: Always consider the source of your input. If it comes from an untrusted user, treat it with extreme caution.
  • Principle of Least Privilege: Only grant the necessary permissions and functionalities. ast.literal_eval() adheres to this by only allowing literal structures.
  • Specific Needs: If you need to evaluate mathematical expressions, a custom parser with ast.parse() is often the best approach. If you’re dealing with simple data structures, json.loads() or ast.literal_eval() are ideal.
  • Python Version Compatibility: Be mindful of changes in ast.literal_eval() behavior across different Python versions, especially regarding arithmetic operations.

By avoiding the direct use of eval() with untrusted input and opting for safer alternatives like ast.literal_eval() or carefully crafted AST parsers, you can significantly enhance the security and robustness of your Python applications.

FAQs on Safely Evaluating User Input in Python

Q: What is the primary security risk with Python's eval function

ANS: The primary security risk with Python’s eval() function is its ability to execute arbitrary code. If used with untrusted user input, a malicious user could inject code that performs harmful actions, such as deleting files or accessing sensitive data.

Q: When should I use ast.literal_eval instead of eval

ANS: You should use ast.literal_eval whenever you need to evaluate a string that represents a Python literal (like strings, numbers, lists, dictionaries, tuples, sets, booleans, or None) and you want to ensure safety by preventing code execution. It’s the go-to for safely processing data structures provided as strings from potentially untrusted sources.

Q: What types of data can ast.literal_eval safely evaluate

ANS: ast.literal_eval can safely evaluate strings containing Python literals such as strings, bytes, numbers (integers, floats, complex), tuples, lists, dictionaries, sets, booleans, and None. It will reject any input that tries to execute code or use disallowed syntax.

Q: Can ast.literal_eval execute arbitrary Python code

ANS: No, ast.literal_eval is specifically designed not to execute arbitrary Python code. It strictly parses and evaluates only valid Python literal structures, raising an error for anything else, which makes it a secure alternative to eval for handling user input.

Q: How does ast.parse offer a safer evaluation method

ANS: ast.parse allows you to build an Abstract Syntax Tree (AST) from a string. By then writing custom logic to traverse this tree and only permit specific operations and node types, you can create a controlled environment for evaluating expressions, effectively whitelisting allowed code constructs.

Q: What are the limitations of using JSON for parsing dictionaries

ANS: The main limitation of using JSON for parsing dictionaries is that all keys within JSON objects (dictionaries) must be strings. JSON also strictly adheres to its own data type definitions and does not support Python-specific types or constructs beyond what is defined in the JSON standard.
