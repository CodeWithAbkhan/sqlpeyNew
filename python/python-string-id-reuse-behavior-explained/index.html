“Python String ID Reuse Behavior Explained: Interning and Optimization”

A frequent observation in Python development involves checking the identity (id()) of two seemingly identical, immutable string literals, only to find they sometimes yield the same memory address and sometimes do not. Why does CPython exhibit this seemingly inconsistent string object reuse behavior?

The core reason lies in string interning mechanisms and compile-time optimizations, rather than a strict guarantee that all string literals are interned by default.

The Role of CPython Interning and Constant Folding

CPython internals utilize functions analogous to sys.intern() extensively to reuse existing string objects. However, without hitting these specific internal code paths, two identical string literals compiled separately might resolve to distinct memory locations.

When running code directly in the Python REPL (interactive interpreter), several steps muddy the waters:

  1. Compilation and Constant Storage: The input line is compiled. String literals are stored as constants within the resulting code object.

    For example, executing id('alpha') in the REPL shows:

    >>> compile("id('alpha')", '<stdin>', 'single').co_consts
('alpha', None)

    This reveals the string 'alpha' alongside the None singleton stored as constants for later bytecode execution.

  2. Execution and ID Retrieval: Upon execution, the string loads from the code constants, and id() returns its memory address.

    The disassembly reveals the loading process:

    >>> import dis
>>> dis.dis(compile("id('alpha')", '<stdin>', 'single'))
  1           0 LOAD_NAME                0 (id)
              3 LOAD_CONST               0 ('alpha')
              6 CALL_FUNCTION            1
              9 PRINT_EXPR          
             10 LOAD_CONST               1 (None)
             13 RETURN_VALUE

  3. Code Object Cleanup: After execution, if the code object is no longer referenced, its reference count drops, leading to its deletion, and consequently, the deletion of the string object it contained.

If you immediately repeat the exact same REPL command, Python might reuse the freed memory location, resulting in the same printed ID. This reuse depends heavily on the system’s memory state and garbage collection activity. Memory address reuse through this mechanism is not dependable.

Identifier-Like String Interning

A significant factor leading to predictable reuse involves how the Python code object factory (PyCode_New) handles specific strings within code objects. It automatically interns strings destined for constant pools if they conform to strict naming rules:

If a string object v qualifies (containing only ASCII letters, digits, or underscores), the system attempts to intern it in place:

if (all_name_chars(v)) {
    PyObject *w = v;
    PyUnicode_InternInPlace(&v);
    if (w != v) {
        PyTuple_SET_ITEM(tuple, i, v);
        modified = 1;
    }
}
/* all_name_chars(s): true iff s matches [a-zA-Z0-9_]* */

Because strings like 'so' satisfy all_name_chars, they are interned. Once this interned version survives, subsequent references to the literal 'so'—even in different scopes or code blocks—will reuse that single object. This explains why in certain tests, 'so' yields a consistent ID, while longer strings with punctuation do not.

Special Case: Variable Name vs. Value Interning

When both the identifier name and the string value meet the intern criteria (e.g., so = 'so'), Python often reuses the same interned object for both the name metadata (co_names) and the constant value (co_consts) within the compiled code object:

>>> compile("so = 'so'", '<stdin>', 'single').co_names[0] is compile("so = 'so'", '<stdin>', 'single').co_consts[0]
True

When Interning Fails: Complex Strings and Concatenation

If strings do not fit the identifier criteria or are not stored as code object constants, reuse is less likely or non-existent:

>>> some_var = 'Look ma, spaces and punctuation!'
>>> some_other_var = 'Look ma, spaces and punctuation!'
>>> id(some_var)
4493058384
>>> id(some_other_var)
4493058456  # Different IDs
>>> so == some_other_var
True # Content is identical

Furthermore, string concatenation results in new objects unless optimization steps intervene:

>>> foo = 'Concatenating_' + 'also_helps_if_long_enough'
>>> bar = 'Concatenating_' + 'also_helps_if_long_enough'
>>> foo is bar
False
>>> foo == bar
True

Compiler Optimizers and String Folding Limits

The optimization layer—either the peephole optimizer (pre-Python 3.7) or the AST optimizer (3.7+)—can pre-calculate (fold) the results of simple constant expressions.

  • AST Optimizer (3.7+): Imposes a limit, often around 4096 characters, for folding string operations like multiplication into a single constant.
  • Peephole Optimizer (older versions): Had stricter limits, sometimes folding only up to 6 repetitions of a short string.

For example, in Python 3.7+, 'foo' * 20 is calculated at compile time, resulting in one interned constant:

>>> import sys
>>> sys.version_info
sys.version_info(major=3, minor=7, micro=4, releaselevel='final', serial=0)
>>> import dis
>>> dis.dis("'foo' * 20")
  1           0 LOAD_CONST               0 ('foofoofoofoofoofoofoofoofoofoofoofoofoofoofoofoofoofoofoofoo')
              2 RETURN_VALUE

If the result exceeds the optimizer’s folding limit, the operation executes at runtime, potentially creating new objects:

>>> dis.dis("'foo' * 7")
  1           0 LOAD_CONST               0 ('foo')
              2 LOAD_CONST               1 (7)
              4 BINARY_MULTIPLY
              6 RETURN_VALUE

Alternative View: Behavior in Script Execution

The interactive shell’s special handling of the _ variable and immediate compilation context differs from running a standard Python script (.py file). When executing a script, string constants within the bytecode are consistently loaded from the same constant pool reference, leading to identical IDs for identical literals across sequential lines, as they reference the same compiled constant slot.

Consider a script containing:

# script_test.py
print(id('so'))
print(id('so'))
print(id('so'))

Execution yields the same ID thrice because the constant 'so' is loaded from the code object repeatedly:

2888960
2888960
2888960

The bytecode confirms loading the same constant slot:

  2           0 LOAD_GLOBAL              0 (id)
              3 LOAD_CONST               1 ('so')  <-- Same constant slot
              6 CALL_FUNCTION            1
             ...

Forcing New String Instances

To explicitly avoid interning or optimization reuse and guarantee a new object ID, one must perform an operation that forces reconstruction, even if the value remains the same. In Python 2.6+, string formatting achieves this:

>>> so = 'so'
>>> new_so = '{0}'.format(so)
>>> so is new_so 
False
>>> id(so)
102596064
>>> id(new_so)
259679968
>>> so == new_so
True

Critical takeaway: Reliance on is or id() for string equality checks is unreliable because Python’s memory management and internal optimizations (like interning) can substitute objects behind the scenes. Always use the equality operator (==) for comparing string values.

FAQs on Python String ID Reuse Behavior Explained

Q: Does Python intern all string literals automatically

ANS: No, CPython does not promise to intern all strings by default. Interning primarily occurs when strings are used internally by Python or when literals fit the criteria for identifier-like strings stored as code object constants.

Q: What causes two identical string literals to have the same ID

ANS: This typically happens because the string is interned (if it matches identifier rules) or because the execution environment (like the REPL or a compiled script) loads the identical constant object from memory, leading to reuse of the same memory address.

Q: How can I force Python to create a new string object even if the content is the same

ANS: Operations that force string reconstruction, such as using string formatting like new_so = '{0}'.format(so), will generally produce a new object with a distinct ID, even if so == new_so remains true.

Q: Is string ID reuse predictable

ANS: No, ID reuse is not predictable. It depends on factors like memory availability, garbage collection cycles, and the context of execution (REPL versus script).

Q: What is the condition for a string literal to be interned during compilation

ANS: A string literal constant is typically interned if it contains only ASCII letters, digits, or underscores, as verified by the all_name_chars check during code object creation.
