The LEGB Rule: Python’s Foundation for Name Lookup

Python employs a well-defined rule set for resolving variable names, often referred to as the LEGB rule. This acronym outlines the order in which Python searches for a name:

  • L (Local): Names assigned within the current function (using def or lambda), provided they are not declared global in that function. This is the innermost scope.
  • E (Enclosing-function Local): Names found in the local scopes of any and all statically enclosing functions, from the innermost to the outermost. This applies to nested function definitions.
  • G (Global/Module): Names assigned at the top-level of a module file, or explicitly declared global within a function inside that file. This is the module-level scope.
  • B (Built-in): Names preassigned in Python’s builtins module, such as open, range, str, SyntaxError, etc. This is the outermost scope.

When Python encounters a variable name, it checks these scopes sequentially. The first instance of the name it finds is the one it uses.

Consider a practical scenario:

# G: Global (module) scope begins here
module_data_label = "Global data here!"

class DataProcessor:
    # This is the class scope, but not directly 'E' for methods
    processor_config_id = "Default ID"

    def analyze_dataset(self):
        # L: Local scope for analyze_dataset method
        current_item_val = "Local to analyze_dataset"

        for loop_counter_var in range(3):
            # The 'for' loop does NOT create a new scope.
            # loop_counter_var is local to analyze_dataset.
            print(f"Processing loop step: {loop_counter_var}")
            # Where would 'perform_sub_action()' be found?
            try:
                perform_sub_action() # Call to a hypothetical function
            except NameError as e:
                print(f"Error referencing perform_sub_action: {e}")

# Try calling the method to demonstrate scope
data_manager = DataProcessor()
data_manager.analyze_dataset()

# Try accessing module_data_label from global scope
print(f"Outside method, module_data_label is: {module_data_label}")

In the above example, if perform_sub_action() were referenced, Python would search:

  1. L: The local scope of analyze_dataset (including loop_counter_var and current_item_val).
  2. E: Any enclosing functions (if DataProcessor or analyze_dataset were themselves nested within another function).
  3. G: The global module scope (where module_data_label is defined).
  4. B: The built-in namespace.

A critical point to remember is that loop constructs (like for or while), if/else statements, and try/except blocks do not introduce a new variable scope in Python. Variables defined inside them reside in the nearest enclosing function or global scope.

Functions: The Primary Scope Creators

In Python, the most common way to introduce a new scope is through a function definition (def or lambda). Classes also have a special kind of scope, which we’ll explore.

Anything defined directly within a function’s body lives within that function’s local scope.

def outer_scope_handler():
    # This is the local scope of outer_scope_handler
    enclosing_item_value = 100

    def inner_scope_display():
        # This is the local scope of inner_scope_display.
        # It can access 'enclosing_item_value' from outer_scope_handler's (enclosing) scope.
        print(f"Inside inner_scope_display: Enclosing value is {enclosing_item_value}")

    inner_scope_display() # Prints 100
    enclosing_item_value = 101 # Modify enclosing_item_value in outer_scope_handler's scope
    inner_scope_display() # Prints 101

Here, inner_scope_display can access enclosing_item_value from its enclosing outer_scope_handler scope.

Restrictions on Rebinding Variables

While variables from outer scopes (enclosing, global, built-in) can be accessed and read within an inner scope, directly assigning a new value to them within the inner scope will not modify the outer variable by default. Instead, it creates a new local variable with the same name, effectively shadowing the outer one. This is a frequent source of confusion.

# Global scope variables
system_log_entries = [1, 2]
system_event_count = 50

def primary_system_module():
    # This is fine: Modifies the global system_log_entries object.
    system_log_entries.append(3)
    print(f"Inside primary_system_module, system_log_entries: {system_log_entries}") # Output: [1, 2, 3]

    # This creates a NEW local variable 'system_event_count', does NOT affect the global one.
    system_event_count = 51
    print(f"Inside primary_system_module, local system_event_count: {system_event_count}") # Output: 51

    current_module_setting = 40
    def nested_configuration_utility():
        # This creates a NEW local variable 'current_module_setting' within nested_configuration_utility.
        current_module_setting = 50
        print(f"Inside nested_configuration_utility, current_module_setting: {current_module_setting}") # Output: 50

    nested_configuration_utility()
    print(f"Inside primary_system_module, current_module_setting: {current_module_setting}") # Output: 40 (unaffected)

primary_system_module()
print(f"Outside primary_system_module, global system_log_entries: {system_log_entries}")    # Output: [1, 2, 3]
print(f"Outside primary_system_module, global system_event_count: {system_event_count}") # Output: 50 (unaffected)

Notice how system_event_count and current_module_setting in the outer scopes remained unchanged.

Explicit Scope Modification: global and nonlocal Keywords

To explicitly modify variables in an outer scope, Python provides keywords:

The global Keyword

The global keyword allows you to modify a variable in the module (global) scope from within a function.

application_settings_value = 25

def update_application_settings():
    global application_settings_value # Declare intent to modify the global variable
    print(f"Before modification, global application_settings_value: {application_settings_value}")
    application_settings_value += 5 # This now modifies the global variable
    print(f"After modification, global application_settings_value: {application_settings_value}")

update_application_settings() # Prints 25, then 30
print(f"Outside function, final application_settings_value: {application_settings_value}") # Prints 30

Even if a variable with the same name exists in an enclosing function scope, global will target the module-level variable:

shared_data_A = 15 # Global variable
shared_data_B = 20 # Global variable

def create_nested_closure_scope():
    shared_data_A = 77 # This is an enclosing scope variable, not global
    shared_data_B = 888 # This is an enclosing scope variable

    def nested_variable_reporter():
        global shared_data_A # This refers to the module-level 'shared_data_A' (15)
        print(f"Inside nested_variable_reporter: shared_data_A={shared_data_A}, shared_data_B={shared_data_B}")
        shared_data_A += 1 # Modifies the global shared_data_A

    return nested_variable_reporter

reporter_function = create_nested_closure_scope()
reporter_function()      # Prints: shared_data_A=15, shared_data_B=888 (shared_data_A is global, shared_data_B is from enclosing scope)
print(f"After call: shared_data_A={shared_data_A}, shared_data_B={shared_data_B}") # Prints: shared_data_A=16, shared_data_B=20

The nonlocal Keyword (Python 3+)

Before Python 3, modifying variables in an enclosing non-global scope was cumbersome, often requiring mutable objects (like a list) to store the value. Python 3 introduced the nonlocal keyword for this purpose. It allows a nested function to modify a variable in its nearest enclosing function scope (excluding the global scope).

Python 2 (Mutable Object Workaround):

def setup_increment_by_list():
    count_holder_list = [0] # Using a mutable list to hold the count
    def get_next_list_value():
        count_holder_list[0] += 1 # Modify the item within the list
        return count_holder_list[0]
    return get_next_list_value

counter_py2_style = setup_increment_by_list()
print(counter_py2_style()) # Output: 1
print(counter_py2_style()) # Output: 2

Python 3 (nonlocal):

def setup_increment_nonlocal():
    current_increment_val = 0 # Variable in the enclosing scope
    def get_next_nonlocal_value():
        nonlocal current_increment_val # Declare intent to modify 'current_increment_val' from enclosing scope
        current_increment_val += 1
        return current_increment_val
    return get_next_nonlocal_value

counter_py3_style = setup_increment_nonlocal()
print(counter_py3_style()) # Output: 1
print(counter_py3_style()) # Output: 2

The nonlocal keyword is particularly useful for creating closures and maintaining state across function calls without resorting to global variables or class instances. It must refer to an already existing binding in an enclosing scope.

Class Scope Peculiarities

While classes define their own namespace, it behaves differently from function scopes. Names assigned directly in the class body are class variables, but they are not directly visible to methods (or nested classes) contained within it via simple name lookup (like LEGB). You typically access them using self. or ClassName..

starting_system_point = 0 # Global variable

class ConfigurationContainer(object):
    # Class scope begins here
    configuration_id_val = starting_system_point # 'configuration_id_val' is a class variable, gets 0 from global 'starting_system_point'
    starting_system_point = starting_system_point + 1 # This creates a *new* class variable 'starting_system_point', shadowing the global one for subsequent class-level assignments.
    derived_config_tag = starting_system_point # 'derived_config_tag' gets 1 from the *class's* starting_system_point

    def present_config_details(self):
        # Method scope begins here
        print(f"Inside method: self.configuration_id_val = {self.configuration_id_val}") # Access class variable via self
        print(f"Inside method: self.derived_config_tag = {self.derived_config_tag}")   # Access class variable via self
        print(f"Inside method: global starting_system_point = {starting_system_point}")            # Accesses the global 'starting_system_point' (0)
        try:
            # 'configuration_id_val' is not directly visible in method's LEGB lookup
            print(configuration_id_val)
        except NameError as e:
            print(f"Inside method: Cannot directly access class variable 'configuration_id_val': {e}")

# Create an instance
my_config_instance = ConfigurationContainer()

print(f"Outside: my_config_instance.configuration_id_val = {my_config_instance.configuration_id_val}") # Output: 0
print(f"Outside: my_config_instance.derived_config_tag = {my_config_instance.derived_config_tag}")   # Output: 1
print(f"Outside: global starting_system_point = {starting_system_point}")                           # Output: 0
my_config_instance.present_config_details()

The output clearly shows how starting_system_point within present_config_details refers to the global starting_system_point, and class variables like configuration_id_val require self. for access.

Comprehensions and Assignment Expressions

Python 3 also refined how comprehensions (list, set, dict, and generator expressions) handle scope, and Python 3.8 introduced the assignment expression (walrus operator :=).

Comprehension Scope (Python 3 vs. Python 2)

A significant change in Python 3 is that list comprehensions, set comprehensions, and dictionary comprehensions now create their own isolated scope. This prevents the loop variable from “leaking” into the enclosing scope, a behavior that occurred in Python 2.

Python 2 (Variable Leakage):

# In a Python 2 interpreter
# >>> [ data_entry_id for data_entry_id in range(7) ]
# >>> data_entry_id
# 6  # The variable 'data_entry_id' leaks into the global/enclosing scope

Python 3 (Isolated Scope):

# In a Python 3 interpreter
# >>> [ data_entry_id for data_entry_id in range(7) ]
# >>> data_entry_id
# NameError: name 'data_entry_id' is not defined # 'data_entry_id' is confined to the comprehension's scope

Assignment Expressions (:=)

The walrus operator := assigns a value to a variable as part of an expression. Its scoping behavior is quite specific:

  • It assigns to the nearest enclosing function, class, or global scope.
  • It does not create a new local variable if the name is already defined in an enclosing scope.
  • If used inside a comprehension, it assigns to the nearest enclosing scope of the comprehension itself, not the comprehension’s own temporary scope.
# Global scope
system_monitoring_status = False

def process_workflow_steps():
    current_workflow_phase = "initialized"
    print(f"Initial workflow phase (enclosing): {current_workflow_phase}")

    task_results_list = [
        # Here, 'current_workflow_phase' is read from the enclosing 'process_workflow_steps' scope
        # and then updated via assignment expression, modifying the *enclosing* variable.
        (current_workflow_phase := current_workflow_phase + "_" + item.upper())
        for item in ["step1", "step2", "step3"]
        if (system_monitoring_status := True) # This assigns to the global system_monitoring_status
    ]
    return current_workflow_phase, task_results_list

final_phase, executed_results = process_workflow_steps()
print(f"After workflow: final phase = {final_phase}")
print(f"Executed results: {executed_results}")
print(f"Global status updated: {system_monitoring_status}")

In this example, current_workflow_phase := ... inside the comprehension modifies the current_workflow_phase variable in process_workflow_steps’s scope, not a new local variable within the comprehension. Similarly, system_monitoring_status := True updates the global variable.

Common Pitfalls: UnboundLocalError

A frequent error related to scope is UnboundLocalError. This occurs when you attempt to read a local variable before it has been assigned a value in the current scope, but you also have an assignment to that same variable name later in the function. Python’s compiler, upon seeing the assignment, marks the variable as local to that function. If you try to use it before that assignment happens, it’s considered unbound.

system_metric_value = 7 # This is a global variable

def update_system_metric():
    # print(system_metric_value) # If uncommented, this line would cause UnboundLocalError
                       # because the next line 'system_metric_value += 1' makes 'system_metric_value'
                       # local to update_system_metric, but it hasn't been assigned yet.
    system_metric_value += 1   # This assignment makes 'system_metric_value' local to this function.
    print(f"Local updated metric: {system_metric_value}")

# Call the function
try:
    update_system_metric()
except UnboundLocalError as e:
    print(f"Caught an expected error: {e}")

print(f"Global system_metric_value remains: {system_metric_value}")

To fix this, if you intend to modify the global variable, use global system_metric_value. If you intend to use a new local variable, ensure you assign it a value before its first use.

Comprehensive Example: Unpacking Scopes

To bring all these concepts together, let’s examine a more complex scenario with its output:

from __future__ import print_function  # For Python 2 compatibility (though primarily Python 3 rules discussed)

global_service_limit = 99
print("1. Global service limit at start:", global_service_limit)

class ServiceOptimizer(object):
    # Class scope
    default_optim_factor = global_service_limit # 'default_optim_factor' becomes 99
    print("2. Class default optimization factor:", default_optim_factor)
    global_service_limit = global_service_limit + 1 # This creates a *new class variable* named 'global_service_limit', shadowing the actual global one.
    print("3. Class's shadowed global_service_limit:", global_service_limit)

    def retrieve_current_factors(self):
        # Method's local scope (L)
        print("4. Inside method: self.default_optim_factor =", self.default_optim_factor) # Accesses class variable
        print("5. Inside method: global_service_limit (global) =", global_service_limit) # Accesses module-level global_service_limit (99, not the class's 100)
        try:
            print(default_optim_factor) # Attempt to access class variable without self.
        except NameError as e:
            print("6. Inside method:", e) # Class variables are not directly in LEGB for methods

    def adjust_local_settings(self):
        try:
            print(temp_local_setting) # This line would cause UnboundLocalError due to the assignment below
        except UnboundLocalError as e:
            print("7. Inside method:", e)
        temp_local_setting = 200 # This creates a new local variable 'temp_local_setting'
        print("8. Inside method: Local temp_local_setting =", temp_local_setting)

# Create an instance and call methods
optimizer_instance = ServiceOptimizer()
optimizer_instance.retrieve_current_factors()
optimizer_instance.adjust_local_settings()

print(f"Final global_service_limit outside: {global_service_limit}") # Still 99, as class's assignment was local to class scope
print(f"Class level global_service_limit (via class name): {ServiceOptimizer.global_service_limit}") # 100

Output of the above code:

1. Global service limit at start: 99
2. Class default optimization factor: 99
3. Class's shadowed global_service_limit: 100
4. Inside method: self.default_optim_factor = 99
5. Inside method: global_service_limit (global) = 99
6. Inside method: name 'default_optim_factor' is not defined
7. Inside method: local variable 'temp_local_setting' referenced before assignment
8. Inside method: Local temp_local_setting = 200
Final global_service_limit outside: 99
Class level global_service_limit (via class name): 100

This output clearly illustrates:

  • The global_service_limit within the retrieve_current_factors method refers to the original module-level global (99), not the one shadowed within the ServiceOptimizer class body (100).
  • Class variables like default_optim_factor are not found through standard LEGB lookup inside methods; they require self. or ClassName. qualification.
  • The UnboundLocalError occurs because an assignment later in adjust_local_settings marks temp_local_setting as local, but it’s used before its assignment.

Other Key Aspects of Python Scope

  • Static Scoping: Python uses static (or lexical) scoping. This means that the scope of a variable is determined by its position in the source code where it is defined, not by where or when it is called.

    main_program_setting = 0

def process_data_phase1():
    main_program_setting = 1 # Shadows global main_program_setting
    def process_data_phase2():
        main_program_setting = 2 # Shadows process_data_phase1's main_program_setting
        def process_data_phase3():
            return main_program_setting # Refers to process_data_phase2's main_program_setting
        return process_data_phase3()
    return process_data_phase2()

print(process_data_phase1()) # Output: 2
print(main_program_setting)    # Output: 0 (global remains unchanged)

    process_data_phase3 sees the variable main_program_setting from its nearest containing scope, which is process_data_phase2. The other instances remain unaffected. This behavior has been consistent since Python 2.2 with nested scopes enabled. Before 2.2, without explicit from __future__ import nested_scopes, inner functions would often fall back to global scope.

  • Module Global Scope (__main__): The global keyword specifically refers to the module’s top-level scope. For the main script being executed, this is the __main__ module. You can even programmatically access attributes of other modules via sys.modules.

  • Built-in Module (builtins): Python’s built-in functions and types reside in the builtins module (named __builtin__ in Python 2). These are available implicitly without import. While possible to modify them (e.g., builtins.print = my_custom_print), it is strongly discouraged as it affects all modules and can lead to unpredictable behavior. For Python 2.x users needing Python 3’s print function, one could import __builtin__ to get a handle on it. However, using from __future__ import print_function is the preferred and much cleaner way as it simply disables the print statement parsing rules in the current module.

Summary of Scopes and Name Binding

In essence, any variable assigned a value in a block is considered local to that block unless explicitly declared global or nonlocal. If a name is referenced but not assigned in the current scope, Python climbs the LEGB hierarchy to find its definition.

The different kinds of scopes, building a hierarchy from innermost to outermost:

  • Function Local Scope
  • Function Closure Scope (Enclosing functions)
  • Class Scope (Note: not part of the LEGB search path for methods directly)
  • Module Global Scope
  • Built-in Scope

if, for, while, and with statements do not create new scopes. Only def, lambda, class, and in Python 3, comprehensions, introduce new execution contexts with distinct name binding rules.

To explicitly bind a name to an outer scope:

  • global: Binds to the module-level global scope.
  • nonlocal: Binds to the nearest enclosing function (closure) scope.

By carefully considering these rules, you can effectively manage variables and write predictable, maintainable, and robust Python code.

FAQs on Solved How to Master Python Scope Rules and Variable Resolution

Q: What is the LEGB rule in Python variable resolution

ANS: The LEGB rule defines the order in which Python searches for a variable name Local Enclosing Global Built-in It checks these scopes sequentially until the name is found.

Q: Do for loops create a new scope in Python

ANS: No for loops and other control flow statements like if or try do not create a new scope in Python Variables defined inside them belong to the nearest enclosing function or global scope.

Q: How do global and nonlocal keywords work in Python

ANS: The global keyword allows you to modify a variable in the module (global) scope from within a function The nonlocal keyword introduced in Python 3 allows modification of variables in an enclosing non-global function scope.

Q: What is the difference between class scope and function scope in Python

ANS: Function scope variables are looked up via the LEGB rule Class scope variables assigned directly in the class body are class attributes and not directly visible via LEGB lookup within methods They must be accessed using self or the class name.

Q: How do comprehensions handle scope in Python 3 versus Python 2

ANS: In Python 3 list set and dictionary comprehensions create their own isolated scope preventing loop variables from leaking into the enclosing scope In Python 2 these variables would leak into the surrounding scope.
