“Invoking Specific Python Versions When Multiple Installations Exist on Windows”

This scenario demands strategies to bypass the default %PATH% resolution or to create distinct, unambiguous invocation methods.

Executing Specific Python Binaries Directly

The most fundamental approach involves bypassing the reliance on the system %PATH% entirely by calling the executable using its full, explicit path.

If Python 2.5 and 2.6 are installed, instead of typing python, you specify the exact binary location:

c:\python\2.5\python.exe
c:\python\2.6\python.exe

Alternatively, to simplify invocation while retaining specificity, you can create shortcuts or rename executables, provided these new names are placed in a directory that is part of your system’s execution path.

Method using Symbolic Links (Windows):

For users familiar with shell utilities, symbolic links offer a clean way to alias executables. In a designated bin directory (e.g., c:\bin), which must be in your path, you can create links:

cd c:\bin
mklink python25.exe c:\python25\python.exe
mklink python26.exe c:\python26\python.exe

After setting up these links, you can invoke them directly:

python25
python26

Method using Executable Renaming (Windows):

A direct renaming approach involves duplicating the interpreter executable and giving it a version-specific name within its installation folder.

Suppose you have versions in C:\Program Files\Python36 and C:\Program Files\Python39.

  1. Navigate to the installation directories.
  2. Copy python.exe in the Python 3.6 folder and rename the copy to python36.exe.
  3. Copy python.exe in the Python 3.9 folder and rename the copy to python39.exe.

You then need to ensure the directories containing these renamed executables (and their corresponding Scripts folders) are in the user’s or system’s %PATH% variable.

To execute a specific version:

python36
python39

(Note: If relying on renaming, ensure you check how pip commands are affected; you might need to use pip36 or python36 -m pip install <package>.)

Leveraging the Official Python Launcher (py)

For Python installations version 3.3 and newer on Windows, the official Python Launcher (py.exe) provides robust version selection capabilities, eliminating the need for manual path management for simple execution.

If you run scripts, you can use shebang lines at the very top of your Python file to direct execution:

#! c:\path\to\Python 2.5\python.exe
# Script content follows...

or using the launcher style:

#! python2.5
# Script content follows...

When invoking from the command line, you use the py command followed by the specific version specifier:

| Command | Action | | :

Solutions

| :

| | py -2.6 my_script.py | Runs the script using the latest installed 2.6 interpreter. | | py -3 my_script.py | Runs the script using the latest installed 3.x interpreter. | | py -3.10-64 script.py | Explicitly calls the 64-bit version of Python 3.10. |

To see all installed versions known to the launcher:

py -0

This launcher is particularly effective when creating virtual environments, as it ensures the correct base interpreter is used.

# Create a virtual environment using Python 3.8 as the base
py -3.8 -m venv my_38_project_env

Isolating Environments with virtualenv

Creating isolated environments is a best practice for managing project dependencies and interpreter versions simultaneously. The virtualenv tool allows explicit selection of the base interpreter when creating the environment.

To target a specific interpreter path (e.g., Python 2.5 or 2.6):

# Create env using Python 2.5
virtualenv -p c:\python2.5\python.exe c:\venvs\py25_env

# Create env using Python 2.6
virtualenv -p c:\python2.6\python.exe c:\venvs\py26_env

Once created, activation switches the shell’s context to that specific environment:

c:\venvs\py25_env\Scripts\activate
# Now 'python' runs 2.5
deactivate
c:\venvs\py26_env\Scripts\activate
# Now 'python' runs 2.6

(Note: If using Python 3.3+, the built-in venv module often suffices, using the syntax shown with the py launcher.)

Environment Variable Control (Advanced/Specific Cases)

While relying on %PATH% order is usually fragile, some users configure environment variables to point directly to the desired installation root, overriding the standard path search for a specific session or user context.

If you define variables like PYTHON2_HOME and PYTHON3_HOME, you can include those in the system Path variable dynamically, ensuring specific directories are prioritized.

Example Environment Variable Setup (Illustrative):

This configuration allows for direct invocation via the environment variable paths, as demonstrated by renaming executables as mentioned previously (python2.exe or python3.exe within their respective folders).

Using pyenv-win

For users frequently switching between numerous versions across different projects, tools designed explicitly for version management offer the best long-term stability. The pyenv-win project provides Windows compatibility for the popular pyenv utility, allowing easy installation and global/local switching of active Python versions via shell commands.

Anaconda Navigator for Graphical Management

If working within data science or environments requiring complex package sets, the Anaconda Navigator allows users to create and manage distinct environments graphically, where each environment is explicitly linked to a specific Python interpreter version during its creation.

FAQs on Invoking Specific Python Versions When Multiple Installations Exist on Windows

Q: How does Windows decide which python executable runs when typing python

ANS: Windows searches directories listed in the %PATH% environment variable in order. It executes the first python.exe (or matching executable) it finds in that sequence.

Q: What is the py command for Windows

ANS: The py command refers to the official Python Launcher for Windows (available since Python 3.3), which intelligently selects the correct interpreter version based on flags or shebang directives.

Q: Can I use pip with a specific python version if I have multiple installed

ANS: Yes, you use the version-specific interpreter to invoke pip, such as py -3.8 -m pip install package or by renaming the executable to python3.8 and running python3.8 -m pip install package.

Q: Does installing a new Python version overwrite an existing one

ANS: Installing different major versions (like 2.5 and 2.6, or 3.6 and 3.10) typically does not overwrite existing installations; they coexist, though installations of patch versions (like 2.6.5 vs 2.6.6) might overwrite each other if they share the same installation directory.

Q: What is the Unix approach to avoid overwriting python

ANS: On Unix-like systems, using sudo make altinstall during compilation prevents the installation process from overwriting the generic python command, leaving it pointing to the system default while installing versioned binaries (e.g., python2.5).
