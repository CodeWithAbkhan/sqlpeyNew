“PowerShell Techniques for Generating UTF-8 Files Without a Byte Order Mark (BOM)”

How can a scripter reliably output file content as UTF-8 format completely devoid of the Byte Order Mark (BOM) when working with PowerShell, especially across different versions where default behaviors diverge?

PowerShell versions exhibit varied default file encodings. Specifically, older Windows PowerShell (version 5.1 and below) often defaults to an encoding that includes a BOM when using standard cmdlets like Out-File with -Encoding UTF8. Modern, cross-platform PowerShell (version 7+) sets utf8NoBOM as its default, simplifying this task significantly.

Here we examine several proven techniques to ensure output files are strictly UTF-8 without BOM, regardless of the environment constraints.

Method 1: Utilizing .NET’s UTF8Encoding Class with Constructor Flag

One explicit way to control the encoding object is by instantiating System.Text.UTF8Encoding and passing $False to its constructor, which explicitly disables the BOM. This object is then passed directly to the .NET method [System.IO.File]::WriteAllLines.

# Example: Writing content from $MyPath to itself without BOM
$MyRawString = Get-Content -Raw $MyPath
$Utf8NoBomEncoding = New-Object System.Text.UTF8Encoding $False
[System.IO.File]::WriteAllLines($MyPath, $MyRawString, $Utf8NoBomEncoding)

Method 2: Leveraging Direct .NET Calls (Concise Form)

For direct file writing, calling the static .NET method [IO.File]::WriteAllLines without specifying an encoding argument often defaults to a desirable behavior in many contexts, or you can rely on the underlying system default if a specific encoding isn’t provided. While the original context suggests this works well, modern best practice usually dictates explicit encoding control, as seen in Method 1.

# A cleaner call, relying on context or PowerShell defaults
[IO.File]::WriteAllLines($filename, $content)

Method 3: Forcing ASCII Encoding Output

A pragmatic, though potentially lossy, approach is piping content to Out-File and explicitly requesting -Encoding ASCII. If the source content only contains 7-bit ASCII characters, the resulting file will be UTF-8 compatible without a BOM, as ASCII is a subset of UTF-8. Caution: This method discards any non-ASCII characters.

# Outputting content to targetFile.ext as ASCII (effectively UTF-8 compatible without BOM for ASCII content)
Get-Content path/to/file.ext | Out-File -Encoding ASCII targetFile.ext

Method 4: Employing New-Item for Default BOM-less Output

In some environments, notably Windows PowerShell, the New-Item cmdlet curiously defaults to creating BOM-less UTF-8 files even when other cmdlets do not. This method reads the entire content raw and assigns it as the value. Note that this approach typically omits a trailing newline.

# Read raw content and assign it via New-Item (omits trailing newline)
$null = New-Item -Force $MyPath -Value (Get-Content -Raw $MyPath)

# To capture pipeline output (like from Get-ChildItem) correctly formatted:
$null = New-Item -Force Out.txt -Value (Get-ChildItem | Out-String)

Method 5: Explicit Encoding in PowerShell 7+

For users operating on PowerShell Core (v7.x or later), explicitly requesting UTF8NoBOM with cmdlets like Out-File or Set-Content is the cleanest and most direct solution, as the platform natively supports this switch.

# PowerShell 7+ syntax
$MyFile | Out-File -Encoding UTF8NoBOM $MyPath

Method 6: Writing Raw Bytes via Text.Encoding and Set-Content -Encoding Byte

This method provides fine-grained control by converting the string content into a byte array using [Text.Encoding]::UTF8.GetBytes() and then writing those bytes directly using Set-Content -Encoding Byte. Since you are writing raw bytes, no encoding header (BOM) is written by PowerShell.

# Setup: Create a UTF8 Encoding object
$utf8 = New-Object Text.UTF8Encoding

# Example using Get-Content -Raw
$GCRaw = Get-Content $MyPath -Raw

# Write the byte representation
Set-Content -Value $utf8.GetBytes($GCRaw) -Encoding Byte -PSPath $MyPath

# Compact alternative using the static constructor
Set-Content ([Text.UTF8Encoding]::new().GetBytes($GCRaw)) -Encoding Byte -PSPath $MyPath

Method 7: The Two-Step ASCII + UTF8 Append Trick

This technique works by first creating a file with a single character encoded in ASCII (which is BOM-less UTF-8 compatible) and then appending the main content using standard UTF-8 encoding. This insertion of a leading space/newline might be acceptable depending on the file’s final purpose (e.g., SQL or simple text files).

# Helper function logic for demonstration
function Out-File-UTF8-noBOM { param( $str, $dest )
  # Step 1: Create an empty/dummy first line using ASCII (no BOM)
  "" | Out-file -FilePath $dest -Encoding ascii -Force -NoNewline
  # Step 2: Append the actual content as UTF8
  $str | Out-file -FilePath $dest -Encoding UTF8 -Append
}

# Usage with content string $str and destination $dest
# Out-File-UTF8-noBOM $str, $dest

# Or, to process a source file ($src)
# Out-File-UTF8-noBOM (gc $src), $dest

Method 8: Custom Pipeline Function (Out-FileUtf8NoBom)

For a reusable, pipeline-friendly solution that mimics Out-File behavior (handling pipeline input objects via Out-String), an advanced function wrapping a .NET StreamWriter is effective. The StreamWriter defaults to UTF-8 without BOM unless configured otherwise. This method is preferred for large files as it can stream input without loading everything into memory at once (unless explicitly using Get-Content $MyPath in parentheses).

This function also includes a -UseLF switch to enforce Unix-style line endings (\n) instead of default CRLF. You can download and execute this function via irm:

# Download and define the advanced function
irm https://gist.github.com/mklement0/8689b9b5123a9ba11df7214f82a673be/raw/Out-FileUtf8NoBom.ps1 | iex

# Example usage (ensuring file is read completely before writing back to same path)
(Get-Content $MyPath) | Out-FileUtf8NoBom $MyPath # Use -UseLF for Unix newlines

Note: A module named WindowsOutFilePatch is also available to bring PowerShell 7 encoding features to Windows PowerShell.

Method 9: Batch File Conversion Using .NET

To convert multiple files in bulk, you can iterate through files and apply the .NET method from Method 1.

$Utf8NoBomEncoding = New-Object System.Text.UTF8Encoding $False
foreach($i in Get-ChildItem -Recurse -Filter "*.java") {
    # Read content, then write back with specified encoding
    $MyFile = Get-Content $i.FullName 
    [System.IO.File]::WriteAllLines($i.FullName, $MyFile, $Utf8NoBomEncoding)
}

Method 10: System-Wide Configuration or Session Overrides

  1. System Locale Change (Windows 10+): Enabling “Use Unicode UTF-8 for worldwide language support” in the Region settings can make Windows PowerShell use BOM-less UTF-8 more consistently.
  2. PowerShell Default Parameter Override: You can set a session default for the -Encoding parameter for specific cmdlets to ensure they behave consistently.
# Set the default encoding for Out-File to 'Default' (often results in ASCII/No-BOM UTF-8 depending on context)
$PSDefaultParameterValues['*:Encoding'] = 'Default'
# Or specifically target utf8 without BOM if PowerShell 5.1 allows inference:
# $PSDefaultParameterValues['*:Encoding'] = 'utf8'

Method 11: Handling Object Output with [System.IO.File]::WriteAllLines

When writing object output (like from ConvertTo-Csv), ensure the data is correctly cast or piped to maintain line structure required by WriteAllLines.

$Utf8NoBomEncoding = New-Object System.Text.UTF8Encoding $False
# Ensure content is an array of strings for WriteAllLines
$CsvData = Get-ChildItem | ConvertTo-Csv 
[System.IO.File]::WriteAllLines($ExecutionContext.SessionState.Path.GetUnresolvedProviderPathFromPSPath($MyPath), [String[]]$CsvData, $Utf8NoBomEncoding)

Method 12: Removing Existing UTF-8 BOMs

If the goal is to strip an existing BOM from a file, you must detect the initial bytes (0xEF, 0xBB, 0xBF) and then rewrite the file using a BOM-less encoding instance.

$FilePath = "path\to\bom_file.txt"
$file = Get-Item -Path $FilePath 
$sequenceBOM = New-Object System.Byte[] 3 
$reader = $file.OpenRead() 
$bytesRead = $reader.Read($sequenceBOM, 0, 3) 
$reader.Dispose() 

# Check for BOM bytes (239, 187, 191)
if ($bytesRead -eq 3 -and $sequenceBOM[0] -eq 239 -and $sequenceBOM[1] -eq 187 -and $sequenceBOM[2] -eq 191) 
{ 
    # Create encoding object *without* BOM ($False)
    $utf8NoBomEncoding = New-Object System.Text.UTF8Encoding($False) 
    [System.IO.File]::WriteAllLines($FilePath, (Get-Content $FilePath), $utf8NoBomEncoding) 
    Write-Host "Removed UTF-8 BOM successfully from $FilePath" 
} 
Else 
{ 
    Write-Warning "File $FilePath does not appear to have a UTF-8 BOM." 
}

Method 13: Custom Logging Function for BOM-less Output

A custom logging function can encapsulate the logic for initial file creation using ASCII (which prevents BOM creation) followed by appending content using UTF-8.

# Setup required variables before calling function: $LogFilePath, $SciptName
function myWriteLog{
    Param( [Parameter(Mandatory=$true, ValueFromPipeline=$true)]
           [string]$content
         )
    
    if ([string]::IsNullOrEmpty($content.Trim())){
        throw "Found 'EMPTY or NULL': must provide non-null content."
    } else { 
        if((Test-Path $LogFilePath) -eq $False){
            # Create file foundation using ASCII (no BOM)
            "" | Out-file -FilePath $LogFilePath -Encoding ascii -Force -NoNewline
            
            # Add header lines
            $header = "Logfile for : $SciptName"
            $separator = $header.PadLeft($header.Length,"#")
            Add-Content -path $LogFilePath -value "$separator"
            Add-Content -path $LogFilePath -value $header
            Add-Content -path $LogFilePath -value "LogFile Created: $(Get-date -F "yyyy-MM-dd-HH-mm-ss")"
            Add-Content -path $LogFilePath -value "$separator"
            Add-Content -path $LogFilePath -value ""
            
            # Add actual content with UTF8 encoding
            Add-Content -path $LogFilePath -value "$(Get-date -F "yyyy-MM-dd-HH-mm-ss") : $content" -Encoding UTF8 -force
        } else {
            Add-Content -path $LogFilePath -value "$(Get-date -F "yyyy-MM-dd-HH-mm-ss") : $content" -Encoding UTF8 -force
        }
    }
}

Method 14: Forcing Encoding via Command Line Execution

When scripting from external tools or batch files, you can invoke PowerShell with -Command and force encoding flags, often removing the BOM by reading as bytes, skipping the first three BOM bytes, and rewriting.

# Execute commands sequentially via command line invocation
powershell -Command "(gc '%CD%\myfile.txt' -Encoding Byte) | select -skip 3 | set-content '%CD%\myfile.txt' -Encoding Byte"

Alternatively, for environment-specific character sets (like Cyrillic), changing the console code page (chcp) and using -encoding default might resolve compatibility issues where true UTF-8 without BOM fails for legacy programs:

chcp 1251
powershell -Command "(gc '%CD%\myfile.txt') | Out-File -encoding default '%CD%\myfile.txt'"

Method 15: Using Out-File -Encoding ASCII for Redirection

When piping the output of external tools (like sqlplus), using Out-File -Encoding ASCII forces the output stream into a format compatible with UTF-8 without BOM, assuming the original output doesn’t contain high-bit characters that need preservation.

# Piping SQLPlus output to a new script file without BOM
sqlplus -s / as sysdba "@create_sql_script.sql" |
Out-File -FilePath new_script.sql -Encoding ASCII -Force

Method 16: Simple Redirection in PowerShell 5.1

In some instances on PS 5.1, a simple pipe to Set-Content without specifying encoding seems to default to UTF-8 without a BOM, as observed by checking file properties later. This is environment-dependent.

Get-Content .\Downloads\finddate.txt | Set-Content .\Downloads\anotherfile.txt
# Verification needed on the resulting file's encoding properties

Method 17: Splitting Content for Mixed Encoding Support

If the first line of a file requires strict UTF-8 handling (or has complex characters) but subsequent lines are simpler, you can handle the first line separately using full UTF-8 support and the remainder using ASCII redirection.

$file = Get-Content -Path "C:\temp\myfile.txt" -Encoding UTF8
$outputFile = "C:\temp\mynewfile.txt"

# Handle first line strictly (may still incur BOM if not careful, but sets context)
$file[0] | Out-File $outputFile -Encoding ascii -NoNewline 
# Append the rest of the content, skipping the first line processed
$file | Select-Object -Skip 1 | Out-File $outputFile -Append utf8

Method 18: String Replacement and ASCII Recoding

When modifying content, piping the result of a replacement operation to Out-File -Encoding ASCII forces the final output into a BOM-less format, similar to Method 3.

$fileD = "file.xml"
(Get-Content $fileD) | ForEach-Object { $_ -replace 'replace text',"new text" } | Out-File $fileD -Encoding ASCII

Method 19: Using ‘Default’ Encoding for ASCII Output

Using -Encoding "Default" in Out-File for simple content often results in ASCII encoding, which equates to UTF-8 without a BOM for that character set.

$MyFile = Get-Content $MyPath
$MyFile | Out-File -Encoding "Default" $MyPath

FAQs on PowerShell UTF-8 No BOM Generation

Q: Why does Out-File with -Encoding UTF8 add a BOM in Windows PowerShell

ANS: Windows PowerShell (v5.1) defaults to an encoding that includes the BOM when you specify UTF8. You must use UTF8NoBOM (if available, PS7+) or use .NET methods or workarounds like those involving System.Text.UTF8Encoding $False to suppress it.

Q: Is Set-Content a reliable way to write UTF-8 without BOM

ANS: In PowerShell 7+, Set-Content -Encoding utf8NoBOM works reliably. In older versions, Set-Content might default to UTF-16 Little Endian or include a BOM with UTF8 unless directed to write raw bytes (-Encoding Byte) after encoding the string yourself.

Q: What is the quickest way to get UTF-8 without BOM in PowerShell 7

ANS: Use -Encoding UTF8NoBOM with Out-File or Set-Content. For example: $content | Out-File -FilePath 'output.txt' -Encoding UTF8NoBOM

Q: Can I use ASCII encoding if I only have English text

ANS: Yes, if your text contains only 7-bit ASCII characters, using -Encoding ASCII with Out-File or Set-Content produces a file that is functionally identical to UTF-8 without BOM for those characters. Be aware this strips high-bit characters.

Q: How does New-Item compare to Out-File for creating BOM-less files

ANS: New-Item -Value sometimes defaults to BOM-less UTF-8 in older PowerShell versions where Out-File does not. However, New-Item usually omits a necessary trailing newline.
