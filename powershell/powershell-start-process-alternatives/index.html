“PowerShell Start-Process Alternatives for Console Apps”

When working with PowerShell and needing to execute external console applications, the Start-Process cmdlet might seem like a straightforward option. However, for synchronous execution within the same console, capturing output, and managing process streams effectively, alternative methods offer more control and predictability. This post delves into why and how to use direct invocation and the call operator (&) for these scenarios.

The Challenge with Start-Process for Console Apps

By default, Start-Process on Windows launches console programs in a new, separate console window. This behavior can lead to a few issues:

  • Brief Flashes: If a program finishes quickly, the new console window might only flash momentarily, making it difficult to see any output.
  • No Output Capture: The output from the invoked program doesn’t automatically appear in the calling PowerShell session’s console.
  • Asynchronous Execution: Start-Process typically runs asynchronously, meaning your script continues to execute without waiting for the external program to complete.

While adding -Wait to Start-Process enforces synchronous execution and -NoNewWindow attempts to run it in the same console, these options don’t resolve the core issue of capturing or redirecting the external program’s standard output (stdout) and standard error (stderr) streams back to your PowerShell session.

The Recommended Approach: Direct Invocation and the Call Operator

For running console programs synchronously, within the same console window, and with stdout/stderr streams connected to your PowerShell session, directly invoking the executable is the preferred method. This is achieved using the call operator (&).

Why Direct Invocation is Superior:

  • Synchronous Execution: By default, direct invocation waits for the external program to finish.
  • Stream Redirection: You can easily capture stdout and stderr back into PowerShell variables or redirect them to files.
  • Exit Code Access: The exit code of the external program is readily available via the $LASTEXITCODE automatic variable.

Practical Examples

Let’s illustrate with the mdoc.exe example, a tool often used for generating API documentation.

1. Installing the mdoc package (if needed):

nuget install mdoc -OutputDirectory packages -ExcludeVersion

This command installs the mdoc package into a local packages directory.

2. Executing mdoc.exe --version directly:

If the executable’s path or name doesn’t contain spaces, you can call it directly:

packages/mdoc/tools/mdoc.exe --version

3. Executing with quoted paths or variables:

When the path to the executable contains spaces, or you’re storing it in a variable, you must use the call operator (&):

  • Via a quoted string:

    & "packages/mdoc/tools/mdoc.exe" --version

  • Via a variable:

    $exePath = "packages/mdoc/tools/mdoc.exe"
& $exePath --version

A complete script snippet demonstrating successful execution:

# Install the tool if necessary
nuget install mdoc -OutputDirectory packages -ExcludeVersion

# Define the path to the executable
$exePath = "packages/mdoc/tools/mdoc.exe"

# Execute the command directly using the call operator
& $exePath --version

# Indicate completion
"done"

This sequence will print the mdoc version (e.g., mdoc 5.7.2) followed by done in your PowerShell console, confirming synchronous execution and output visibility.

Capturing stdout and stderr Output

To capture the output streams of the external program, you can assign the command to a variable.

  • Capturing stdout:

    Assigning the output to a variable will capture the stdout as an array of strings (one string per line of output). If there’s only one line, it might be a single string scalar.

    $version = & $exePath --version

    You can then inspect $version:

    Write-Host "mdoc Version: $($version -join ', ')" # Joins array elements for display

  • Capturing both stdout and stderr:

    To capture both streams, use output redirection 2>&1:

    [string[]] $allOutput = & $exePath --version 2>&1

    Casting to [string[]] ensures that all output lines, including those from stderr, are treated as strings. In older Windows PowerShell versions, stderr lines might initially be captured as [System.Management.Automation.ErrorRecord] objects. PowerShell Core has addressed some of these type-handling nuances.

    You can then process $allOutput to distinguish between stdout and stderr if needed, perhaps saving them to separate files.

Important Considerations

  • Character Encoding: Be aware of potential character encoding issues when PowerShell interacts with external programs. This is crucial for ensuring correct display and processing of output. For more details, refer to specific resources on PowerShell’s handling of external program encoding.
  • Underlying .NET API: Start-Process ultimately uses the System.Diagnostics.Process .NET class. Understanding when Start-Process is appropriate versus direct invocation is key to efficient scripting. For detailed guidance, exploring documentation on System.Diagnostics.Process and related issues (like GitHub issue #6239) can be beneficial.

FAQs on PowerShell Console Execution

Q: What is the main drawback of using Start-Process for console apps

ANS: By default, Start-Process launches console applications in a new, separate console window, and its output is not automatically captured by the calling PowerShell session.

Q: How can I run a console app synchronously in PowerShell

ANS: Use direct invocation or the call operator (&) instead of Start-Process. These methods execute the program in the current console and wait for completion by default.

Q: How do I capture the output of an external program in PowerShell

ANS: Assign the command executed with the call operator (&) to a variable. For example: $output = & "program.exe" --argument.

Q: Can I capture both standard output and standard error from an external program

ANS: Yes, use the 2>&1 redirection operator with the call operator: [string[]] $allOutput = & "program.exe" --argument 2>&1.

Q: What happens to the exit code of an external program

ANS: The exit code of the last executed external program is stored in the automatic PowerShell variable $LASTEXITCODE.

Q: When should I use Start-Process instead of direct invocation

ANS: Start-Process is more suitable when you need to launch an application in a new, independent window, or when you want to detach the process from your current PowerShell session, potentially with specific verbosity or file associations.
