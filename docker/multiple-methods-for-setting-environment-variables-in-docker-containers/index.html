“Multiple Methods for Setting Environment Variables in Docker Containers”

How can developers supply environment variables to Docker containers during runtime or build time, accommodating various security and configuration needs? This extensive set of solutions details numerous approaches using the docker run command, environment files, and docker-compose.

Utilizing the docker run Command Flags

The most direct way to inject configuration involves using flags with the docker run command.

Direct Environment Variable Assignment (-e or --env)

You can pass environment variables directly using the -e flag (or its longer alias --env).

Method A: Key-Value Assignment

To set a specific variable with a value:

docker run -e HOST_PORT=9090 -e SERVICE_TIMEOUT=300 my_application_image /start_service

Method B: Importing from the Current Shell Environment

If you omit the = assignment, Docker pulls the variable’s value from the shell session where you execute the command. This keeps secrets off the command line output visible via process listings (ps):

# Assuming SECRET_KEY is exported in the current shell
export SECRET_KEY="secure-random-value"
docker run -e SECRET_KEY my_secure_app_image

Practical Example with Multiple Settings

When configuring database access or service URLs upon container launch:

sudo docker run -d -t -i -e REDIS_NAMESPACE='staging' \
-e POSTGRES_ENV_POSTGRES_PASSWORD='secure_db_pass' \
-e POSTGRES_ENV_POSTGRES_USER='app_user' \
-e SITE_URL='staging.appdomain.net' \
-p 80:80 \
--name staging_web_app dockerhub_id/web_service:latest

Security Note on Command-Line Visibility

A significant drawback of direct -e assignment is that environment variables can sometimes be exposed in process listings on the host machine, posing a security risk for sensitive data.

Using Environment Files (--env-file)

For managing numerous variables or keeping secrets entirely out of the command line, an external environment file is preferred. The --env-file flag reads settings from a file, where each line follows the VAR=VAL format. Comment lines must start with #.

Example env.list file:

# Configuration for the staging environment
API_VERSION=v2
DB_HOST=database.internal.net
# Secret password kept in a separate secure location usually
DB_SECRET=file_level_secret

Running with an Environment File:

docker run --env-file ./env.list ubuntu bash

Alternative for Secure Variable Injection (Piping)

To dynamically select specific host environment variables and pipe them securely into an environment file context for the container, preventing the accidental dumping of all host variables:

# Assuming you have AWS_ACCESS_KEY and AWS_SECRET defined in your shell
# This securely filters and pipes only AWS variables into the container context
docker run --rm -it --env-file <(bash -c 'env | grep AWS_') amazon/aws-cli s3 ls

Ordering Options and Image Name

It is critical to place options like --env-file before the image name argument in the docker run command signature:

docker run [OPTIONS] IMAGE [COMMAND] [ARG...]

Incorrect Order: docker run -it --rm -p 8080:80 my_image --env-file ./config.env (This fails)

Correct Order: docker run --env-file ./config.env -it --rm -p 8080:80 my_image

Setting Variables via env Command Execution

You can leverage the host system’s /usr/bin/env command to set a variable for the duration of the container’s initial command execution:

docker run ubuntu env DEBUG=1 /path/to/script.sh

Passing Variables Referenced by Name Only (Shell Export)

If a variable is already exported in the host shell, you can instruct Docker to use its existing value without explicitly defining the value in the docker run command:

export VAR1=value1
export VAR2=value2

# Docker will pull the values for VAR1 and VAR2 from the host environment
docker run --env VAR1 --env VAR2 ubuntu env | grep VAR
# Output:
# VAR1=value1
# VAR2=value2

Configuration with Docker Compose

For multi-container setups, docker-compose offers cleaner syntax, especially when dealing with external configuration or build arguments.

Mapping Host Variables to Container Variables (Renaming)

In docker-compose.yml, you can pull an environment variable defined on the host machine and map it to a different name inside the container service definition:

# docker-compose.yml snippet
hapi_server:
  container_name: hapi_server
  image: node_image
  environment:
    # Map host's NODE_DB_CONNECT to container's HAPI_DB_CONNECT
    - HAPI_DB_CONNECT=${NODE_DB_CONNECT} 
  expose:
    - "3000"

Inheriting and Defaulting Variables in Compose and Dockerfiles

When using docker-compose build, you can pass host environment variables directly into the build context using the args directive, which can then be consumed by ARG in the Dockerfile.

docker-compose.yml:

version: '3.1'
services:
  my-service: 
    build:
      context: .
      # Use shell variable RAILS_ENV, defaulting to 'production' if unset
      args:
        - RAILS_ENV=${RAILS_ENV:-production}
    environment: 
      - RAILS_ENV=${RAILS_ENV:-production}

Dockerfile:

FROM ruby:2.3.4

# Define build argument with a default
ARG RAILS_ENV=production

# Map build argument to an active environment variable accessible at runtime
ENV RAILS_ENV $RAILS_ENV

# Container command execution uses the final ENV value
RUN if [ "$RAILS_ENV" = "production" ] ; then echo "production env"; else echo "non-production env: $RAILS_ENV"; fi

Execution proceeds via docker-compose build followed by docker-compose up.

Using .env Files with Compose

The dedicated .env file works seamlessly with compose, often preferred over command-line overrides for defining service-specific configuration:

# Using the CLI to specify the .env file path explicitly
docker-compose -f docker-compose.yml --env-file ./.env up

Note on Quoting in docker run --env-file vs. docker-compose: The standard docker run --env-file parser has quirks where surrounding quotes (") in the file are treated as part of the variable value. docker-compose, however, parses YAML which typically handles quoting more conventionally. For cross-compatibility or complex string injection via docker run, advanced scripting (like using entrypoint.bash to source a string variable) may be required to correctly interpret quoted values from a simple text file.

Alternative Configuration Strategies

Defining Environment Variables in the Dockerfile (ENV)

For variables that are static across all instances of an image (e.g., default configuration paths), define them directly in the Dockerfile using the ENV instruction.

FROM base_image

ENV APPLICATION_PORT=8080
ENV DEFAULT_LOG_LEVEL=INFO

This results in an image where these variables are always present.

Script Sourcing at Container Entrypoint

If you need to load variables from a script file inside the container before the main process starts, copy the script and use the ENTRYPOINT to execute it using source. This is often used when secrets are mounted as files.

Example env.sh:

#!/bin/bash
export FOO="BAR"
export DB_NAME="DATABASE_NAME"

Dockerfile Snippet:

COPY env.sh /env.sh
COPY app.jar /app.jar
# Source the file, verify variables (optional printenv), then execute the JAR
ENTRYPOINT ["/bin/bash" , "-c", "source /env.sh && printenv && java -jar /app.jar"]

JSON Serialization of Host Environment

If you need to pass the entire host environment into a single container variable, you can serialize it to JSON using tools like jq (if available) and pass that single JSON string:

# Requires jq 1.6+
env_as_json=$(jq -c -n env)
docker run -e HOST_ENV="$env_as_json" <image>
# Inside the container, HOST_ENV holds the serialized environment data.

Database Specific Configuration (MySQL Example)

For specific services like MySQL, environment variables map directly to setup parameters during initial container creation:

docker run -dit --name db1 \
 -e MYSQL_ROOT_PASSWORD=strong_root_pass \
 -e MYSQL_DATABASE=app_data \
 -e MYSQL_USER=app_user \
 -e MYSQL_PASSWORD=app_secret \
 mysql:5.7

Alternatively, for quick testing without setting passwords, use the random option:

sudo docker container run -p 3306:3306 -e MYSQL_RANDOM_ROOT_PASSWORD=yes --name temp_mysql -d mysql
# Check logs to retrieve the generated password
sudo docker container logs temp_mysql

AWS ECS Secret Management Alternative

In cloud environments like Amazon ECS, managing sensitive credentials often involves leveraging provider services (like S3 buckets for configuration files or AWS Secrets Manager) rather than relying solely on container launch parameters.

Utilizing /usr/bin/env to Set Variables

A straightforward method is directly preceding the command with env to define variables scope for that specific execution:

docker run ubuntu env DEBUG=true EXEC_SCRIPT=/run.sh

FAQs on Setting Docker Environment Variables

Q: How can I pass all my local environment variables automatically to Docker

ANS: You can use a shell command to pipe your current environment to an env file and then use --env-file to load it, though be cautious as this dumps all variables. A safer approach is to export specific variables and use the -e VAR_NAME syntax.

Q: What is the difference between ENV in Dockerfile and -e in docker run

ANS: ENV in the Dockerfile sets a default variable baked into the image. The -e flag in docker run overrides this default or sets a new variable at runtime.

Q: Can I use an env file with docker run without exposing secrets in the command history

ANS: Yes, using the --env-file ./path/to/file flag is the standard secure way to load multiple variables without listing them on the command line.

Q: Is it safe to use a configuration file for secrets in Docker

ANS: It is safer than command-line arguments because file access can be permission-controlled. If using docker-compose, the .env file is generally managed well. For docker run, ensure the external file is securely managed.

Q: Does docker-compose handle variable quoting issues better than docker run

ANS: Yes, docker-compose typically uses YAML parsing for its configuration, which handles quotes in environment variable values more predictably than the direct string parsing performed by the docker run --env-file utility.
