“Docker Container Name Resolution Techniques Within Custom Networks”

Resolving container names to their IP addresses is crucial for building distributed applications where services rely on service discovery rather than hardcoded IPs. Several mechanisms exist in the Docker ecosystem to facilitate this, evolving from legacy linking to modern custom networking features.

Solution 1: Utilizing User-Defined Bridge Networks (The Modern Standard)

The accepted contemporary approach leverages Docker’s built-in networking capabilities, specifically custom bridge networks. When containers connect to the same user-defined network, Docker’s embedded DNS service automatically enables name resolution between them using their container names.

To implement this:

  1. Establish a Custom Network: Create a new network instance where your containers will reside.

    $ docker network create app-shared-net

  2. Attach Containers to the Network: Run new containers attached to this network, assigning them unique names for easy identification.

    $ docker run -d --net=app-shared-net --name=service-alpha <image-name>
$ docker run -d --net=app-shared-net --name=service-beta <image-name>

    Alternative Connection Method: You can also connect an already running container:

    $ docker network connect app-shared-net service-alpha

  3. Test Name Resolution: Once connected, you can execute a command from one container to ping the other using its assigned name.

    Example Ping Test: Executing within service-alpha:

    docker exec -ti service-alpha ping service-beta

# Expected Output Snippet Indicating Success:
# 64 bytes from service-beta (172.18.0.4): icmp_seq=1 ttl=64 time=0.137 ms
# 64 bytes from service-beta (172.18.0.4): icmp_seq=2 ttl=64 time=0.073 ms

    Important Caveat: Unlike legacy linking mechanisms, this modern networking feature does not automatically inject environment variables for service discovery, nor does it support network aliases via this direct method (though aliases are supported via docker network connect with specific flags, see Solution 3). Refer to the official Docker documentation on networking drivers for further details on network scope limitations.

Solution 2: Implementing External Dynamic DNS via dnsmasq

If the native Docker DNS resolution is insufficient for specific requirements (or if dealing with older configurations), an alternative involves deploying a service on the host system to dynamically manage container IP mappings. This typically requires setting up a local DNS server like dnsmasq.

The process involves:

  1. Deploying a Dynamic Script: A script monitors running Docker containers (docker ps).
  2. Mapping Names to IPs: For every running container, the script fetches its IP address (docker inspect) and updates configuration files for dnsmasq.
  3. Service Restart: dnsmasq is periodically restarted to load the new host records.

Here is a representative shell script structure designed to update dnsmasq records every 10 seconds:

#!/bin/bash

# Configuration variables
INTERVAL=${INTERVAL:-10}
DNSMASQ_CONFIG=${DNSMASQ_CONFIG:-.}
DOCKER=${DOCKER:-docker}
SLEEP=${SLEEP:-sleep}
TAIL=${TAIL:-tail}

declare -A service_map

while true
do
    changed=false
    while read line
    do
        # Extract container name from 'docker ps' output tail
        name=${line##* }
        # Fetch current IP address
        ip=$(${DOCKER} inspect --format '{{.NetworkSettings.IPAddress}}' "$name")
        
        if [ -z ${service_map[$name]} ] || [ ${service_map[$name]} != "$ip" ] # IP address modification detected
        then
            service_map[$name]="$ip"
            echo "$name has a new IP Address $ip" >&2
            # Write host-record for dnsmasq configuration
            echo "host-record=$name,$ip"  > "${DNSMASQ_CONFIG}/docker-$name"
            changed=true
        fi
    done < <($(${DOCKER} ps | ${TAIL} -n +2))

    # If any change occurred, reload dnsmasq service
    if [ "$changed" = true ]
    then
        systemctl restart dnsmasq
    fi

    ${SLEEP} "$INTERVAL"
done

After setting this up, containers must be started using the --dns HOST_ADDRESS flag pointing to the host machine’s address where this mini DNS service operates, allowing them to query the dynamically updated records. Ensure your dnsmasq configuration binds correctly to the docker0 bridge interface if necessary, as referenced in related documentation on setting up dnsmasq with Docker.

Solution 3: Leveraging Legacy --link and Network-Scoped Aliases

Before the dominance of custom networks, the --link flag was the primary method for inter-container discovery, primarily by modifying the /etc/hosts file of the consuming container.

A. Legacy Linking Example

When launching a service container, the --link flag specifies the source container name and an optional alias to be used as the hostname in the target container’s /etc/hosts file:

  1. Launch the Service Container (e.g., LDAP):

    docker run -t --name openldap -d -p 389:389 larrycai/openldap

  2. Launch the Client Container with a Link: Use the alias internalopenldap to refer to openldap.

    docker run -it --rm --name ldp --link openldap:internalopenldap ldaptest

Inside ldp, connections attempting to resolve internalopenldap would successfully connect to the IP address of openldap, often reflected in /etc/hosts. This mechanism also sets environment variables (a behavior the newer network approach avoids).

B. Network-Scoped Aliases (Docker 1.10+)

With the introduction of libnetwork and Docker version 1.10, network-scoped aliases were introduced via the --alias flag during container connection or creation within a specific network.

While --link defines resolution from the consumer’s perspective, a network alias defines how the service container is discovered by others on that network using an alternate name.

You can assign an alias when running a container on a network:

$ docker run --net=isolated_nw -itd --name=container6 --alias app busybox

Any other container on isolated_nw can now resolve container6 using the name app.

C. Static IP Reservation

To ensure a container always uses a specific address upon reconnecting to a network, you can define subnets and IP ranges when creating the network, then explicitly assign an IP upon connection:

# Create network with a defined subnet and reserve an IP range
$ docker network create --subnet 172.20.0.0/16 --ip-range 172.20.240.0/20 multi-host-network

# Connect container2 and assign a static IP from outside the reserved range
$ docker network connect --ip 172.20.128.2 multi-host-network container2

Solution 4: Docker Compose Version 2 Networking

For users relying on docker-compose, the file format version 2 (which integrated libnetwork concepts) allows services defined in the same compose file to resolve each other by their service names automatically, similar to Solution 1 but managed declaratively.

Example docker-compose.yml (Version 2):

version: "2.4"
services:
  router:
    build: services/router/
    ports:
      - "8080:8080"
  auth:
    build: services/auth/
  todo:
    build: services/todo/
  data:
    build: services/data/

When started with docker-compose up, the auth service can resolve the todo service simply by using the hostname todo because Compose creates a default network connecting all services.

Solution 5: Overlay Networking Solutions (e.g., Kontena)

If native Docker features are bypassed, platform-level solutions like Kontena (which integrates network overlay technology like Weave) provide built-in service discovery, often mapping service names to fully qualified domain names (FQDNs) like service_name.kontena.local.

Example configuration snippet showcasing how a WordPress service connects to MariaDB using a custom FQDN:

wordpress:                                                                         
  image: wordpress:4.1                                                             
  # ... other configurations
  environment:                                                                     
    - WORDPRESS_DB_HOST=wordpress-mysql.kontena.local                              
    - WORDPRESS_DB_PASSWORD=secret                                                 
mysql:                                                                             
  image: mariadb:5.5                                                               
  # ... other configurations

This shifts the complexity of dynamic IP mapping and DNS updates to the container orchestration layer.

FAQs on Docker Container Name Resolution Techniques

Q: How does the new custom network resolution differ from legacy linking

ANS: New custom networks use built-in DNS for name resolution based on container names, unlike legacy links which primarily relied on modifying the consuming container’s /etc/hosts file and injecting environment variables.

Q: Can I use network aliases with docker network connect

ANS: Yes, you can often assign network-scoped aliases when connecting existing containers to a network using specific flags, providing alternate discovery names within that network scope.

Q: Is restarting dnsmasq always required in the dynamic script

ANS: Yes, if the script detects a change in container IP addresses, restarting or reloading the dnsmasq service is necessary for it to pick up the newly generated host records reflecting the current container IPs.
