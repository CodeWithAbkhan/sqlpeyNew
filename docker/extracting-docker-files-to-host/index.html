“Multiple Techniques for Extracting Files from Docker Containers to Host”

There are several established procedures for extracting artifacts from a Docker environment to the host system. The appropriate method often depends on whether the container is active, if you prefer working with images directly, or if volume management offers a cleaner approach.

Primary Method: Utilizing docker cp

The docker cp command is the most direct utility for copying files between a container and the local filesystem.

Copying from Container to Host

To pull an item from within a running container to your host machine, use the syntax:

docker cp <containerIdOrName>:/file/path/within/container /host/path/target

For instance, if you identify a container named goofy_roentgen using docker ps:

$ sudo docker ps

CONTAINER ID        IMAGE               COMMAND             CREATED             STATUS              PORTS                                            NAMES
1b4ad9311e93        bamos/openface      "/bin/bash"         33 minutes ago      Up 33 minutes       0.0.0.0:8000->8000/tcp, 0.0.0.0:9000->9000/tcp   goofy_roentgen

You can then extract a specific file:

$ sudo docker cp goofy_roentgen:/out_read.jpg .

The Container ID (or a truncated version) is interchangeable with the name:

$ sudo docker cp 1b4a:/out_read.jpg .

Note that docker cp functions even if the container is not running, provided you use the ID obtained from docker ps -a. For Windows PowerShell users, the syntax remains similar, substituting appropriate path separators:

docker cp {container id}:{container path}/error.html  C:\\error.html

Copying from Host to Container (For completeness)

The reverse operation, pushing files from the host into a container, follows a mirrored structure:

$docker cp C:/localMachineSourceFolder/someFile.txt containerId:/containerDestinationFolder

Important Caveat: The destination path inside the container must frequently pre-exist for the copy operation to succeed when pushing files into a container.

Alternative Strategy 1: Using docker create for Stopped Containers

If you need to copy files but do not wish to maintain a running container process, you can leverage docker create. This sets up the writable layer without starting the process, as documented by Docker.

  1. Create the container (it remains in the ‘created’ state): 
    docker create --name dummy_extractor IMAGE_NAME
  2. Copy the required artifact: 
    docker cp dummy_extractor:/path/to/file /dest/to/file
  3. Clean up the created container: 
    docker rm -f dummy_extractor

Alternative Strategy 2: Artifact Collection via Volume Mounting During Runtime

For continuous output generation during a build or process execution, volume mounting ensures artifacts land directly on the host.

Create a local directory to serve as the destination:

mkdir artifacts

Then, run the container, mapping the container’s output directory to the host’s artifacts directory:

docker run -i -v ${PWD}/artifacts:/artifacts ubuntu:14.04 sh << COMMANDS
# ... commands generating files ...
cp <artifact> /artifacts
# ...
COMMANDS

When the container exits, the files are already present in the host’s ./artifacts folder.

Addressing UID/GID Mismatches with Volumes

A common issue with volume mounts is file ownership on the host reflecting the container user’s UID/GID. To mitigate this, execute the container process using the calling user’s credentials:

docker run -i -v ${PWD}:/working_dir -w /working_dir -u $(id -u) \
    ubuntu:14.04 sh << COMMANDS
# Commands executed using host user ID
cp some_file /working_dir/artifacts/
COMMANDS

A refined approach for build contexts that avoids pre-creation or post-removal steps involves using docker run with a volume bind, user switching, and a heredoc:

# Build the image first
docker build -t my-image - <<EOF
FROM busybox
WORKDIR /workdir
RUN touch foo.txt bar.txt qux.txt
EOF

# Run, copy, and clean up in one step, ensuring host ownership
docker run --rm -iv${PWD}:/host-volume my-image sh -s <<EOF
chown $(id -u):$(id -g) *.txt
cp -a *.txt /host-volume
EOF

This benefits from the host shell evaluating $(id -u):$(id -g) before the commands are passed to the container.

Alternative Strategy 3: Extracting Files Directly from an Image (No Container Needed)

If the file exists within an image layer and the container does not need to run, you can stream its content using standard container utilities like cat.

docker run --rm <image_name> cat /path/to/container/file.txt > /path/to/host/file.txt

Drawback: This technique typically discards original file metadata such as permissions and modification times.

For larger files or specialized scenarios, consider compressing the output stream on the fly:

docker run --rm $IMAGE gzip --stdout $FILEPATH | gunzip > $FILE

Alternative Strategy 4: Using Python SDK for Retrieval

If integrating file extraction into an application, the Docker SDK for Python offers programmatic access via container.get_archive(path). This retrieves the content as a tar stream, which must then be unpacked locally.

import docker
import os
import tarfile

# Initialize client
client = docker.from_env()
# Get container object by name (e.g., "relaxed_pasteur")
container = client.containers.get("container_name_here")

local_archive_path = os.path.join(os.getcwd(), "output.tar")
local_extract_path = os.getcwd()

# Get the archive stream from the container's /output directory
bits, stat = container.get_archive('/output')

# Write the streamed bits to a local tar file
with open(local_archive_path, "wb") as f:
    for chunk in bits:
        f.write(chunk)

# Unpack the tar archive locally
with tarfile.open(local_archive_path, "r") as tar:
    tar.extractall(path=local_extract_path)

os.remove(local_archive_path)

Alternative Strategy 5: Using Podman/Buildah Mounting (If Applicable)

For environments using Podman, there is an option to mount the container’s filesystem directly, allowing use of the host’s native cp utility, often without needing root permissions via podman unshare:

podman create --name dummy_podman_extractor IMAGE_NAME
podman unshare -- bash -c '
  mnt=$(podman mount dummy_podman_extractor)
  cp -R ${mnt}/etc/foobar /tmp
  podman umount dummy_podman_extractor
'

Alternative Strategy 6: Temporary Network Transfer (For Small Files)

For small, isolated data transfers, one can establish temporary network access using netcat (nc) if available inside the container image:

Inside Container:

docker run -it -p 4122:4122 <container_ID>
nc -l -p 4122 < Output.txt

On Host Machine:

nc 127.0.0.1 4122 > Output.txt

Alternative Strategy 7: Using BuildKit Output Flags (Modern Docker Builds)

With Docker 19.03+ and BuildKit enabled (DOCKER_BUILDKIT=1), you can direct build artifacts out of a specific build stage directly to the host filesystem using the --output flag, bypassing image creation entirely for exported files.

DOCKER_BUILDKIT=1 docker build --target artifact --output type=local,dest=. .

This is highly effective when defining specific export stages within a multi-stage Dockerfile.

FAQs on Extracting Docker Files to Host

Q: What is the basic command to copy a file from a running container

ANS: Use docker cp <containerIdOrName>:/path/in/container /host/path.

Q: Can docker cp be used if the container is not running

ANS: Yes, provided you use the container ID obtained from docker ps -a.

Q: What is the drawback of using docker run cat image file > hostfile

ANS: File permissions and modification dates are generally not preserved with this streaming method.

Q: How to handle file ownership issues when using volume mounts for extraction

ANS: Run the container using the host user’s ID by specifying the -u $(id -u) flag during docker run.

Q: Is there a way to export build artifacts without creating a final image layer

ANS: Yes, enable BuildKit and use DOCKER_BUILDKIT=1 docker build --target <stage> --output type=local,dest=. ..
