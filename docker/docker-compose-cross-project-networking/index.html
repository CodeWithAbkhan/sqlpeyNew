“Docker Compose: Connecting Multiple Projects Across Networks”

When working with multiple distinct docker-compose.yml projects, facilitating communication between their respective containers often requires careful network configuration. The core principle involves ensuring that containers from different projects reside on the same Docker network, allowing them to discover and interact with each other using service names. This can be achieved through various methods, primarily by defining and utilizing shared or external networks.

Diverse Approaches to Cross-Project Docker Compose Networking

Several strategies exist to accomplish this, each with its own nuances. The primary goal is to bridge the network isolation that docker-compose typically enforces for each project.

Solution 1: Shared Bridge Network with Explicit Naming

This approach ensures that containers from different docker-compose projects are placed on the same network. By explicitly naming the network in each configuration, you enable inter-container communication.

Key Concept: Containers on the same network can resolve each other by service name.

front/docker-compose.yml

services:
  front:
    image: nginx:latest # Example image
    container_name: front_app
    ports:
      - "80:80"
    networks:
      - app_network

networks:
  app_network:
    driver: bridge

api/docker-compose.yml

services:
  api:
    image: python:3.9-slim # Example image
    container_name: api_service
    ports:
      - "5000:5000"
    networks:
      - app_network # Must match the network name in the other compose file

networks:
  app_network:
    driver: bridge

Explanation: Both docker-compose files define a network named app_network. When both are brought up, containers like front_app and api_service will be on this shared network. From within front_app, you can access the API using its service name: http://api:5000.

Solution 2: Leveraging External Networks (Compose File Version 3.5+)

Docker Compose allows you to declare networks as external, meaning they are managed outside the current docker-compose.yml file. This is particularly useful when one project defines a network that another project needs to join.

shared_network_project/docker-compose.yml

version: "3.5"
services:
  proxy:
    image: nginx:latest
    ports:
      - "80:80"
    networks:
      - custom_network # Internal name for the network definition

networks:
  custom_network:
    name: custom_shared_network # The actual name of the Docker network
    driver: bridge

Running docker-compose up -d for this will create a network named custom_shared_network.

another_project/docker-compose.yml

version: "3.5" # Or a compatible version
services:
  web:
    image: alpine:latest
    networks:
      - my_proxy_net # Internal name to reference the external network

networks:
  my_proxy_net:
    external:
      name: custom_shared_network # Must match the name defined in the other compose file

Explanation: The first docker-compose.yml creates and names the Docker network custom_shared_network. The second docker-compose.yml then declares that it wants to use an external network with that exact name.

Solution 3: Using the Default Network of Another Project

When you run a docker-compose command, it automatically creates a network for that project, typically prefixed with the project’s directory name. You can then reference this default network as an external one.

project1/docker-compose.yml

services:
  service1:
    image: alpine:latest
    container_name: service1_app
    networks:
      - default_net # Using 'default' keyword here

project2/docker-compose.yml

services:
  service2:
    image: nginx:latest
    container_name: service2_app
    networks:
      - project1_default_net # Reference the default network of project1
networks:
  project1_default_net:
    external: true

Explanation: If project1 is in a directory named project1, its default network will be named project1_default. In project2’s docker-compose.yml, you reference this external network. Ensure the external network name correctly matches the default network naming convention.

Solution 4: Explicitly Naming Networks for Shared Usage

This is a robust method where you define a network with a specific name that both docker-compose files reference.

projectA/docker-compose.yml

networks:
  my-shared-network:
    name: giveItANamePlease # The actual network name
    driver: bridge

services:
  app_a:
    image: alpine:latest
    networks:
      - my-shared-network

projectB/docker-compose.yml

networks:
  my-proxy-net:
    external:
      name: giveItANamePlease # Must match the name from projectA

services:
  app_b:
    image: nginx:latest
    networks:
      - my-proxy-net

Explanation: projectA defines and names a network giveItANamePlease. projectB then uses this giveItANamePlease network as an external resource.

Solution 5: Joining the Default Network of Another Project (Simplified)

A direct way to join another project’s default network.

api/docker-compose.yml

networks:
  default: # This keyword implies joining the project's default network
    external:
      name: front_default # Assuming 'front' is the directory name for the other project

Explanation: This configuration tells the api project’s containers to join the network named front_default, which is presumed to be the default network created by a docker-compose file in a directory named front.

Solution 6: Using external_links for Older Compose Versions or Specific Scenarios

While less common with newer Docker Compose versions, external_links can be used to link containers from different Compose projects, especially when direct network sharing isn’t ideal or feasible. This requires knowing the container names.

app1/docker-compose.yml

version: '2' # Required for external_links
services:
  svc11:
    container_name: container11
    image: alpine:latest
    networks:
      - app1_net
      - app2_network # External network to connect to app2
    external_links:
      - container22:alias_for_container22 # Link to a container in app2

networks:
  app1_net:
    driver: bridge
  app2_network:
    external: true

app2/docker-compose.yml

version: '2' # Required for external_links
services:
  svc21:
    container_name: container21
    image: nginx:latest
    networks:
      - app2_net
      - app1_network # External network to connect to app1
    external_links:
      - container11:alias_for_container11 # Link to a container in app1

networks:
  app2_net:
    driver: bridge
  app1_network:
    external: true

Explanation: This example sets up bidirectional linking. svc11 links to container22 (from app2) and svc21 links to container11 (from app1). Both projects define an external network to connect to the other. Note that the external_links target needs to be the container name, not the service name.

Solution 7: Standardizing Network Names to Avoid Project Prefixes

To prevent issues where Docker Compose automatically prefixes network names with project directory names (e.g., projectname_networkname), explicitly define the network name.

api/docker-compose.yml

version: '3'
services:
  api:
    container_name: api_service
    image: python:3.9-slim
    networks:
      - mynetwork # Using a custom, non-prefixed name

networks:
  mynetwork:
    name: mynetwork # Explicitly naming the network

front/docker-compose.yml

version: '3'
services:
  front:
    container_name: front_app
    image: nginx:latest
    networks:
      - mynetwork # Using the same custom name

networks:
  mynetwork:
    name: mynetwork # Explicitly naming the network

Explanation: By using name: mynetwork in the networks section of both files, you ensure that both projects use a network called mynetwork. This avoids the need to reference the project name when making the network external.

Solution 8: Centralized Network Definition

For Compose file version 3.5+, you can override the default network name for all participating Compose files.

networks:
  default:
    name: my-app # All services in this compose file will join 'my-app'

Explanation: This configuration snippet, when added to multiple docker-compose.yml files, directs all services within those files to join a network named my-app. This is a clean way to enforce a common network.

Solution 9: Joining Another Project’s Network by Name

Similar to Solution 2, but using the default keyword for referencing another project’s network.

ner/docker-compose.yml

version: '3'
services:
  ner:
    container_name: ner_api
    build: .
    networks:
      - default # Joins the network defined below
networks:
  default:
    external:
      name: scoring_default # Assumes 'scoring' project created this network

scoring/docker-compose.yml

version: '3'
services:
  api:
    build: .
    # ... other configurations

Explanation: The ner service is configured to join the scoring_default network, implying that the scoring project has created and is using this network. You can verify container membership using docker inspect scoring_default.

Solution 10: Using .env for Consistent Project Names

Project names are derived from directory names. By using a .env file with COMPOSE_PROJECT_NAME, you can unify the project names and thus their default network names.

.env file (in each project directory)

COMPOSE_PROJECT_NAME=unified_project

Explanation: With this .env file in place for all projects, Docker Compose will treat them as part of the same project, creating a unified network (e.g., unified_project_default) that all containers can join. Be aware of potential “orphaned” container warnings.

Solution 11: Explicit Network Creation and Referencing

Manually create a network or let Docker Compose create it, then reference it explicitly.

docker-compose.apline.yml

version: '3.8'
services:
  alpine:
    image: alpine:3.14
    container_name: alpine_container
    networks:
      - net-for-alpine # Internal network alias
    stdin_open: true
    tty: true

networks:
  net-for-alpine:
    name: test-db-net # The actual Docker network name

docker-compose.db.yml

version: '3.8'
services:
  db:
    image: postgres:13.4-alpine
    container_name: psql_container
    networks:
      - net-for-db # Internal network alias
  
networks:
  net-for-db:
    name: test-db-net # Must match the name from the other compose file

Testing Connectivity: After starting both, exec into the alpine_container:

docker exec -it alpine_container sh
# Then test connectivity to the 'psql_container'
nc -z psql_container <port>
ping psql_container

Explanation: Both docker-compose files define a network alias (net-for-alpine, net-for-db) that points to the same underlying Docker network named test-db-net. This allows containers from both projects to communicate.

Solution 12: Combining Compose Files with docker compose

A straightforward way to ensure containers are on the same network is to tell docker compose to use multiple compose files at once.

docker compose --file ~/project1/docker-compose.yml --file ~/project2/docker-compose.yml up -d

Explanation: This command merges the configurations from both files, treating them as a single logical project. Docker Compose will then create a common network (or join an existing one if specified) that spans services from both files.

Solution 13: Discovering and Using Existing Network Names

If a network is already created by another Docker Compose project, you can find its name and reference it.

second_docker-compose.yml

version: '3'
services:
  service-on-second-compose:
    # ... service configuration
    networks:
      - discovered_network # Internal alias

networks:
  discovered_network:
    external: true
    name: <put_network_name_here> # e.g., project1_default, or a custom name

How to find the network name: Run docker network ls to list all Docker networks and identify the one created by the first project.

Explanation: This method requires manual inspection of existing networks and then referencing the correct name using external: true.

Solution 14: Host IP for Inter-Project Communication (Non-Networked)

When direct network sharing is complex or undesirable (e.g., port conflicts), containers can communicate using the host machine’s IP address and the exposed ports of services in other projects. This bypasses direct Docker networking between projects.

Example Scenario: api_a needs to talk to api_b.

project_api_a/docker-compose.yml

services:
  api:
    container_name: api_a
    # ... runs Django app on 0.0.0.0:8000
    ports:
      - "8000:8000" # Exposes container port 8000 to host port 8000

project_api_b/docker-compose.yml

services:
  api:
    container_name: api_b
    # ... runs Django app on 0.0.0.0:8001
    ports:
      - "8001:8001" # Exposes container port 8001 to host port 8001

Communication from api_a to api_b: Inside the api_a container, you would make a request to http://<host_ip>:8001/, where <host_ip> is your machine’s IP address. You can find this programmatically using Python:

import socket
def get_local_ip():
    s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    try:
        s.connect(('10.255.255.255', 1)) # Connect to a dummy address
        IP = s.getsockname()[0]
    except Exception:
        IP = '127.0.0.1'
    finally:
        s.close()
    return IP

# In your application code within api_a container:
host_ip = get_local_ip()
api_b_url = f"http://{host_ip}:8001/"

Explanation: This method relies on the host machine acting as an intermediary. Services are exposed on the host, and other containers connect to the host’s IP address on those exposed ports. This is useful for debugging or when direct network integration is too complex.

Solution 15: Using Nginx Proxy Manager with a Public Network

For managing multiple services from different docker-compose files, especially in a production-like setup, using a reverse proxy like Nginx Proxy Manager is effective.

1. Create a public Docker network:

docker network create nginx-proxy-manager-net

2. docker-compose.yml for a service (e.g., domain1.com)

version: "3.9"
services:
  webserver:
    build: ./bin/php # Example
    container_name: domain1_com-webserver
    networks:
      - public_net
      - internal_net
  database:
    build: ./bin/mysql # Example
    container_name: domain1_com-database
    networks:
      - internal_net

networks:
  public_net:
    external: true
    name: nginx-proxy-manager-net # Connects to the public network
  internal_net:
    internal: true # Isolates services within this project

.env file for this project:

COMPOSE_PROJECT_NAME=domain1_com
PHPVERSION=php7.4
DATABASE=mysql8

Explanation: Services connect to the nginx-proxy-manager-net (making them accessible externally via the proxy) and an internal_net for inter-service communication within the same project. The COMPOSE_PROJECT_NAME helps in distinguishing services if needed. Nginx Proxy Manager can then route traffic to the correct service based on domain names.

Solution 16: Modern Compose File Versions and Hostnames

With newer Docker Compose versions, you can leverage hostnames for inter-container communication, especially within a defined network.

kafka_consumer/docker-compose.yml

version: "3.8"
services:
  zookeeper:
    image: zookeeper:3.4.10
    networks:
      - kafkaNet

  kafka:
    image: confluentinc/cp-kafka:4.1.4
    ports:
      - 9093:9093
    environment:
      KAFKA_ADVERTISED_LISTENERS: INTERNAL://kafka:19093,EXTERNAL://127.0.0.1:9093
      KAFKA_ZOOKEEPER_CONNECT: "zookeeper:2181"
    hostname: google.kafka.local.com # Custom hostname
    networks:
      - kafkaNet

networks:
  kafkaNet:
    driver: bridge
    name: kafkanetwork # Explicitly named network

kafka_producer/docker-compose.yml

version: '3.8'
services:
  awsapi:
    image: alpine:latest # Example
    networks:
      - awsapinetwork

networks:
  awsapinetwork:
    external: true
    name: kafkanetwork # Joins the same network as the consumer

Explanation: The awsapi container can communicate with the Kafka broker using the hostname google.kafka.local.com on port 9093, as both services are on the kafkanetwork. The hostname directive within the Kafka service configuration provides a stable alias.

Solution 17: Network Naming Conventions and Port Awareness

When connecting external networks, be mindful of Docker’s default network naming (prefixed with project directory) and use the container’s internal port, not the host-mapped port, for inter-container communication.

project1/docker-compose.yml

version: '2'
services:
  some-contr:
    image: alpine:latest
    networks:
      - somenet # Internal alias
    ports:
      - "8080:8080" # Host:Container
    expose:
      - "8080"
networks:
  somenet:
    driver: bridge

project2/docker-compose.yml

version: '2'
services:
  pushapiserver:
    image: nginx:latest
    working_dir: /app
    ports:
      - "8060:8066" # Host:Container
    networks:
      - project1_somenet # External reference to project1's default network
networks:
  project1_somenet:
    external: true

Explanation: The pushapiserver in project2 can reach some-contr in project1 using the URL http://some-contr:8080/. Here, 8080 is the container’s exposed port (from expose and ports), not the host-mapped port 8060. The network name project1_somenet assumes project1 is in a directory named project1.

Solution 18: Direct Network Name Specification (Compose v3.5+)

A simple method for shared networks using Compose file version 3.5 and above.

compose1.yml

networks:
  default:
    name: network-name # Explicitly names the network

compose2.yml

services:
  app:
    # ...
    networks:
      - network-name # References the shared network by its explicit name

# You might need to define it as external here if not defined in compose1
# networks:
#   network-name:
#     external: true

Explanation: This approach directly assigns a common name to the network, simplifying external referencing.

Solution 19: IP Address-Based Communication (for Testing/Local Dev)

For localized testing, you can identify the IP address of a container from one project and use it to connect from a container in another. This is less about shared networks and more about direct IP communication.

app1/docker-compose.yml

networks:
  new-network: # Define a network for app1
    external: true
    name: app1_shared_net # Name for the network
services:
  app:
    # ...

app2/docker-compose.yml

networks:
  new-network: # Joins the same network
    external: true
    name: app1_shared_net
services:
  app:
    # ...
    # Inside this container, you'd need to know the IP of app1's container
    # e.g., http://172.XX.0.10:port/

Explanation: This method involves inspecting app1’s container to find its IP within app1_shared_net and then hardcoding that IP in app2’s configuration or application code. It’s a practical but less maintainable solution for complex environments.

Solution 20: Overlay Networks in Docker Swarm

When using Docker Swarm, overlay networks are essential for multi-host communication and can be shared across stacks.

docker-compose.yml (Stack 1)

version: '3.9'
networks:
  net:
    driver: overlay
    attachable: true # Allows standalone containers to join

Deploy this stack with docker stack deploy -c docker-compose.yml -p app. The network will be named app_net.

docker-compose.yml (Stack 2)

version: '3.9'
networks:
  net-ref:
    external: true
    name: app_net # References the network from Stack 1

Deploy this stack with docker stack deploy -c docker-compose.yml mystack.

Explanation: Overlay networks enable containers across different nodes (or different compose deployments within a swarm) to communicate. By specifying attachable: true and referencing the network name, you can link services from distinct compose deployments.

Solution 21: IP Address Management (IPAM) with Custom Subnets

For fine-grained control, you can define custom IP address ranges for your networks.

nginx-proxy-manager/docker-compose.yml

version: "3"
services:
  app:
    image: "jc21/nginx-proxy-manager:latest"
    ports:
      - "80:80"
      - "81:81"
      - "443:443"
    networks:
      customnetwork:
        ipv4_address: 172.20.0.10 # Assign a specific IP
networks:
  customnetwork:
    ipam:
      config:
        - subnet: 172.20.0.0/24 # Define the subnet

portainer/docker-compose.yml

version: "3"
services:
  portainer:
    image: portainer/portainer-ce:latest
    container_name: portainer
    ports:
      - 9000:9000
      - 9443:9443
    networks:
      nginxproxymanager_customnetwork: # Reference network by project_name_network_name
        ipv4_address: 172.20.0.11 # Assign a specific IP
networks:
  nginxproxymanager_customnetwork:
    external: true # Assume the network was created by the first project

Explanation: This setup manually assigns static IP addresses within a defined subnet. The second compose file references the network created by the first, ensuring both containers reside on 172.20.0.0/24 and can communicate using their assigned IPs.

Solution 22: Multihomed Containers for Targeted Communication

Instead of putting entire networks together, you can make containers “multihomed” by attaching them to multiple networks, allowing controlled communication.

services:
  webserver:
    networks:
      webnet: # Isolated network for webserver
        ipv4_address: 172.20.0.2
  proxyserver:
    networks:
      proxynet: # Public network for proxy
        ipv4_address: 172.19.0.111
      webnet: # Also attached to the webserver's isolated network
        ipv4_address: 172.20.0.111
    ports:
      - "80:80"

networks:
  proxynet:
    driver: bridge
    internal: false
    ipam:
      config:
        - subnet: 172.19.0.0/16
  webnet:
    driver: bridge
    internal: true # Makes webnet traffic strictly internal
    ipam:
      config:
        - subnet: 172.20.0.0/17

Explanation: The proxyserver is attached to both proxynet (for external access) and webnet (to communicate with webserver). The webserver is only on the internal webnet. This provides granular control over network access.

Solution 23: Referencing External Networks by Name

A straightforward way to connect to a pre-existing network.

services:
  bot:
    # ...
    networks:
      - my-rede # Internal alias
networks:
  my-rede:
    external:
      name: name_rede_externa # The actual name of the external network

Explanation: This snippet indicates that the bot service should join an already existing Docker network named name_rede_externa.

FAQs on Docker Compose Cross-Project Networking

Q: How do I make containers from two different docker-compose files talk to each other?

ANS: The primary method is to ensure both sets of containers are on the same Docker network. This is often achieved by defining a shared network in both docker-compose.yml files or by having one project define a network that the other project references as external. You can then communicate between services using their service names.

Q: What is an 'external' Docker network in compose?

ANS: An ’external’ network is a Docker network that is created and managed independently of a specific docker-compose.yml file. When you specify a network as external in a compose file, you are telling Docker Compose to use an existing network rather than creating a new one. This is crucial for connecting services across different compose projects.

Q: Can I use service names to communicate between containers from different compose projects?

ANS: Yes, provided those containers are on the same Docker network. Docker’s DNS resolution within a network allows containers to find each other using their service names defined in the docker-compose.yml files.

Q: What happens if I don't specify a network name in docker-compose?

ANS: If you don’t explicitly define networks, Docker Compose typically creates a default network for each project. This default network is usually named by prefixing the project’s directory name with the network name you would have specified (e.g., myproject_default). If projects have different default network names, their containers won’t be able to communicate directly unless you configure them to join the same network.

Q: How do I find the name of a network created by another docker-compose project?

ANS: You can use the command docker network ls to list all available Docker networks. Look for network names that correspond to your other project’s directory or explicitly defined network names.

Q: Is it possible to connect containers from different compose projects without using shared networks?

ANS: Yes, it is possible by having containers communicate via the host machine’s IP address and the ports exposed by services. This bypasses direct Docker networking between the compose projects but requires careful management of exposed ports and host IP addresses. This is often used for debugging or simpler local setups.
