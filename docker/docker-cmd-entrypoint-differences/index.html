“Docker CMD vs ENTRYPOINT: Unpacking Container Execution Behavior”

When constructing Docker images, understanding the distinct roles of CMD and ENTRYPOINT is fundamental to controlling how your containers behave upon startup. While both instructions specify commands to be executed, their interaction and override mechanisms differ significantly. This exploration delves into these differences, providing clarity on their usage and impact.

The Core Functionality: What Do They Do?

At their heart, both CMD and ENTRYPOINT define the executable command within a Docker container. However, their intended purposes and how they interact with user-provided arguments during docker run are where the divergence lies.

  • ENTRYPOINT: This instruction is best suited for designating a container’s primary executable. When an ENTRYPOINT is defined, the container effectively acts as that executable. Any command-line arguments provided to docker run are treated as parameters to this ENTRYPOINT.

  • CMD: This instruction provides default commands and/or parameters for an ENTRYPOINT. It’s the mechanism for specifying default arguments that users can easily override when launching a container. If no ENTRYPOINT is defined, CMD will be executed as the container’s primary command.

How They Cooperate and Conflict

The interplay between CMD and ENTRYPOINT follows specific rules that dictate the final command executed.

  1. ENTRYPOINT with CMD: When both are present, the ENTRYPOINT is executed, and the CMD instructions are passed as arguments to it.
  2. ENTRYPOINT without CMD: The ENTRYPOINT executes with no additional arguments.
  3. CMD without ENTRYPOINT: The CMD instruction becomes the primary command to execute.
  4. Overriding:
    • CMD Override: Any arguments provided directly after the image name in docker run will override the CMD instruction.
    • ENTRYPOINT Override: To override the ENTRYPOINT, you must use the --entrypoint flag with the docker run command.

Key Differences Illustrated

Consider a scenario where you want a container to always run a sleep command.

Using CMD:

If your Dockerfile contains:

FROM ubuntu
CMD ["sleep", "10"]

When you run docker run myimage, the container will sleep for 10 seconds. However, to change the duration, you must override the entire CMD: docker run myimage sleep 20. This feels slightly redundant as you’re re-specifying sleep.

Using ENTRYPOINT:

If your Dockerfile contains:

FROM ubuntu
ENTRYPOINT ["sleep"]

Running docker run myimage 20 will cause the container to sleep for 20 seconds. The 20 is passed as an argument to the ENTRYPOINT.

To provide a default sleep duration, you can combine them:

FROM ubuntu
ENTRYPOINT ["sleep"]
CMD ["10"]

Now, docker run myimage will sleep for 10 seconds, and docker run myimage 30 will sleep for 30 seconds.

Advanced Scenarios and Best Practices

  • Executable-like Images: Use ENTRYPOINT when you want your container to behave like a specific executable. For example, an image designed to run ping could have ENTRYPOINT ["ping"]. Then, docker run mypingimage google.com would execute ping google.com.
  • Default Arguments: Use CMD to provide default flags or arguments to an ENTRYPOINT.
  • Shell vs. Exec Form: Dockerfiles support two forms for both CMD and ENTRYPOINT:
    • Shell Form: CMD command param1 param2. This is run through /bin/sh -c.
    • Exec Form: CMD ["executable", "param1", "param2"]. This is executed directly without a shell wrapper, which is generally preferred for clearer execution and signal handling.

Let’s look at an example of the exec form with ENTRYPOINT and CMD:

FROM debian:wheezy
ENTRYPOINT ["/bin/ping"]
CMD ["localhost"]
  • Running docker run myimage will execute /bin/ping localhost.
  • Running docker run myimage google.com will execute /bin/ping google.com.
  • To override the ENTRYPOINT itself, you’d use docker run --entrypoint /bin/bash myimage.

Understanding Execution Flow

Docker’s processing of CMD and ENTRYPOINT involves internal conversions to a JSON array format.

  • Shell form: ENTRYPOINT "mycommand arg1" gets converted to ENTRYPOINT ["/bin/sh", "-c", "\"mycommand arg1\""].
  • Exec/JSON form: ENTRYPOINT ["mycommand", "arg1"] remains as is.

These converted lists are then concatenated ( ENTRYPOINT first, then CMD). This combined list forms the final command executed by the container.

When ENTRYPOINT is defined in the shell form (e.g., ENTRYPOINT "echo"), it gets wrapped in /bin/sh -c. If CMD is also in shell form (e.g., CMD "foo"), it too gets wrapped. The concatenation can lead to unexpected shell interpretations. For instance, ENTRYPOINT "echo" and CMD "foo" might result in /bin/sh -c echo foo, where foo is interpreted as an argument to echo, not as a separate command. Using the JSON form for both is generally safer and more predictable.

Why the Distinction Matters

The choice between CMD and ENTRYPOINT impacts how your container is used and extended:

  • ENTRYPOINT for fixed executables: If your image is designed to run a specific tool, ENTRYPOINT ensures it’s always invoked. Users then provide arguments via CMD or the command line.
  • CMD for configurable defaults: CMD is ideal for setting default arguments to an ENTRYPOINT or providing a default ad-hoc command that’s easily replaced.

Practical Examples

Example 1: A Custom Tool Image

Consider an image that wraps a hypothetical mytool command.

FROM alpine
ENTRYPOINT ["/usr/local/bin/mytool"]
CMD ["--help"]
  • docker run mytoolimage executes /usr/local/bin/mytool --help.
  • docker run mytoolimage --version executes /usr/local/bin/mytool --version.
  • docker run --entrypoint /bin/sh mytoolimage starts a shell.

Example 2: A Web Server Base Image

For a base web server image, you might use ENTRYPOINT for the server executable and CMD for default configuration arguments.

FROM nginx
ENTRYPOINT ["nginx", "-g", "daemon off;"]
CMD ["-c", "/etc/nginx/nginx.conf"]
  • docker run mywebserver runs nginx -g "daemon off;" -c "/etc/nginx/nginx.conf".
  • docker run mywebserver -c "/etc/nginx/custom.conf" runs nginx -g "daemon off;" -c "/etc/nginx/custom.conf".

FAQs on Docker CMD vs ENTRYPOINT

Q: What is the primary function of Docker's CMD instruction

ANS: The CMD instruction in a Dockerfile is used to provide default commands or parameters that can be easily overridden by the user when running a container. If no ENTRYPOINT is defined, CMD specifies the main executable.

Q: When should I use ENTRYPOINT instead of CMD

ANS: Use ENTRYPOINT when you want your container to act as a specific executable. It defines the main command that runs when the container starts, and any arguments provided to ‘docker run’ are passed as parameters to this ENTRYPOINT.

Q: How do CMD and ENTRYPOINT interact when both are defined

ANS: When both CMD and ENTRYPOINT are defined in a Dockerfile, the ENTRYPOINT command is executed, and the CMD instruction’s value is passed as arguments to that ENTRYPOINT.

Q: Can I override the ENTRYPOINT of a Docker image

ANS: Yes, you can override the ENTRYPOINT of a Docker image by using the –entrypoint flag with the ‘docker run’ command, specifying the new executable.

Q: What happens if I use the shell form for ENTRYPOINT or CMD

ANS: Using the shell form (e.g., CMD command param1) causes the command to be executed through /bin/sh -c. While functional, the exec form (e.g., CMD [“command”, “param1”]) is generally preferred for better control over signal handling and direct execution.

Q: Is there a difference between docker run image arg1 and docker run image:tag arg1

ANS: The :tag specifies the image tag. docker run myimage arg1 and docker run myimage:latest arg1 will behave identically if latest is the default or only tag available for myimage. The arg1 is treated as a command-line argument passed to the container’s ENTRYPOINT or CMD.

Q: How does docker handle missing ENTRYPOINT and CMD

ANS: If neither ENTRYPOINT nor CMD is specified in a Dockerfile, Docker defaults to using /bin/sh -c as the ENTRYPOINT. Any command-line arguments passed to docker run will then be treated as the CMD for this default ENTRYPOINT.
