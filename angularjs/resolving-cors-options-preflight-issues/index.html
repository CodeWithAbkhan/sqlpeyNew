“Resolving Cross-Origin Resource Sharing OPTIONS Preflight Issues in Web Applications”

When building modern web applications, particularly those using JavaScript frameworks to communicate with APIs hosted on different domains (cross-origin requests), encountering mandatory HTTP OPTIONS requests—known as preflight requests—is a frequent hurdle. These requests are mandated by the Cross-Origin Resource Sharing (CORS) standard to ensure the request is safe to proceed.

How can developers effectively manage or bypass these preflight requests, which are often triggered by non-simple HTTP methods (like PUT, DELETE) or specific custom headers? Below are various expert-verified methods addressing this requirement across different technology stacks.

The Core Mechanism: Why the OPTIONS Request Appears

The browser automatically sends an HTTP OPTIONS request before the actual request (e.g., POST, PUT) if the actual request is deemed “not simple.” This preflight check solicits supported methods and headers from the server.

According to the specification, preflighting occurs if the request:

  1. Uses HTTP methods other than GET or POST.
  2. Uses POST with a Content-Type other than application/x-www-form-urlencoded, multipart/form-data, or text/plain (e.g., sending JSON payloads).
  3. Sets custom headers (like X-Requested-With).

To permit the subsequent request, the server hosting the resource must respond to the OPTIONS request with appropriate Access-Control-* headers. For detailed server-side header configuration advice, review tutorials on Adding CORS Support to the Server .

Frontend Client-Side Adjustments (AngularJS Focus)

When using AngularJS, the framework itself often injects headers that force preflights. Several strategies exist based on the AngularJS version being used:

1. Eliminating the X-Requested-With Header

In older setups, the automatic inclusion of the X-Requested-With header by AngularJS often forces the preflight. Removing this header can revert the request to a “simple request,” bypassing the OPTIONS check for GET requests.

Pre-AngularJS 1.2 Solutions:

// Configuration adjustment in AngularJS app setup
angular.module('myApp', []).config(['$httpProvider', function($httpProvider) {
    // Disable cross-domain requests using useXDomain (often deprecated or less reliable now)
    $httpProvider.defaults.useXDomain = true; 
    
    // Crucially, remove the header causing the preflight for many simple requests
    delete $httpProvider.defaults.headers.common['X-Requested-With']; 
}]);

A working example for pre-1.2 versions can be inspected here: JSBin Example Pre-1.2 .

2. Utilizing resourceUrlWhitelist (AngularJS 1.2+)

For versions 1.2 and higher, configuration shifted to delegating trust via $sceDelegateProvider.

AngularJS 1.2.0rc1 (RC Versions):

// For release candidate versions prior to 1.2.0 final
angular.module('myApp').config(['$sceDelegateProvider', function($sceDelegateProvider) {
     $sceDelegateProvider.resourceUrlWhitelist([
         'self', 
         /^https?:\/\/(cdn\.)?yourdomain\.com/ 
     ]);
 }]);

JSBin demonstrating this configuration: JSBin Example 1.2.0rc1 .

AngularJS 1.2.0 Release Version and Newer:

The need to escape regular expression strings was removed, allowing direct URL pattern specification. Note the use of ** for subfolders.

// For AngularJS 1.2.0 release and newer
angular.module('myApp').config(['$sceDelegateProvider', function($sceDelegateProvider) {
     // Use patterns like this:
     var allowedUrl = 'http://sub*.assets.example.com/**'; 
     $sceDelegateProvider.resourceUrlWhitelist([
         'self', 
         allowedUrl
     ]);
 }]);

A functional JSBin for version 1.2: JSBin Example 1.2 .

3. Modifying Content-Type to Avoid Preflight

If the issue stems from using a non-simple Content-Type during a POST request (like sending XML or specific JSON formats), explicitly setting the POST content type to text/plain might revert it to a simple request, thus avoiding the preflight.

$http.defaults.headers.post["Content-Type"] = "text/plain";

4. Bypassing Preflight by Resetting Headers (Use with Caution)

One drastic approach, though noted as potentially incompatible with the latest Angular versions, involves resetting common headers to prevent the browser from constructing the preflight request entirely:

angular.module('myApp').config(['$httpProvider', function ($httpProvider) {
  // WARNING: This aggressively removes headers that might be needed elsewhere
  $httpProvider.defaults.headers.common = {};
  $httpProvider.defaults.headers.post = {};
  $httpProvider.defaults.headers.put = {};
  $httpProvider.defaults.headers.patch = {};
}]);

Server-Side Configuration Solutions

If client-side adjustments are insufficient or inappropriate, the server hosting the API must be configured to correctly handle the incoming OPTIONS request.

5. General Server Response for OPTIONS

The responding service needs to return headers that explicitly permit the cross-origin request. The server must echo back the Origin header and specify allowed methods and requested headers.

Required Response Headers from the Server:

Access-Control-Allow-Origin: [the same origin from the request, or * for all]
Access-Control-Allow-Methods: GET, POST, PUT 
Access-Control-Allow-Headers: [the same ACCESS-CONTROL-REQUEST-HEADERS received in the request]

6. Node.js/Express Implementation

For Node.js servers using Express, integrating the cors middleware offers a straightforward resolution:

const express = require('express');
const cors = require('cors'); // npm install cors
const app = express();

app.use(cors()); // Apply globally, or configure per route

// npm update might be needed after installation.

External link for the cors library: https://github.com/expressjs/cors .

7. ASP.NET Web API 2 Solutions

In ASP.NET Web API projects, enabling CORS often involves NuGet package installation and configuration within WebApiConfig.cs, followed by attribute decoration on controllers.

Configuration (WebApiConfig.cs):

public static class WebApiConfig    
{
   public static void Register(HttpConfiguration config)
   {
      config.EnableCors();
      // ... other configuration
   }    
}

Controller Attribute:

[EnableCors(origins: "*", headers: "*", methods: "*")]
public class MyController : ApiController
{  
    [AcceptVerbs("POST")]
    public IHttpActionResult Post([FromBody]YourDataType data)
    {
         // ... logic
         return Ok(result);
    }
}

If posting JSON data, ensure Angular is sending application/json:

$http({
    method: 'POST',
    data: JSON.stringify(data),
    url: 'actionurl',
    headers: {
        'Content-Type': 'application/json; charset=UTF-8'
    }
}).then(...)

Reference: Enabling Cross-Origin Requests in ASP.NET Web API 2 .

8. OWIN/Katana Middleware for Preflight Handling (e.g., for Token Endpoints)

When using OWIN middleware (often for token endpoints in older ASP.NET projects), manual interception of the OPTIONS request can be necessary, especially after framework upgrades (e.g., AngularJS 1.2.6 to 1.3.3).

app.Use(async (context, next) =>
{
    IOwinRequest req = context.Request;
    IOwinResponse res = context.Response;
    if (req.Path.StartsWithSegments(new PathString("/Token")))
    {
        var origin = req.Headers.Get("Origin");
        if (!string.IsNullOrEmpty(origin))
        {
            res.Headers.Set("Access-Control-Allow-Origin", origin);
        }
        if (req.Method == "OPTIONS")
        {
            res.StatusCode = 200;
            res.Headers.AppendCommaSeparatedValues("Access-Control-Allow-Methods", "GET", "POST");
            res.Headers.AppendCommaSeparatedValues("Access-Control-Allow-Headers", "authorization", "content-type");
            return; // Stop processing here for OPTIONS
        }
    }
    await next();
});

9. Java Jersey Configuration

For Java REST APIs built with Jersey 2.x, a ContainerResponseFilter is the standard mechanism to inject CORS headers:

CorsResponseFilter.java:

import javax.ws.rs.container.*;
import java.io.IOException;

public class CorsResponseFilter implements ContainerResponseFilter {

    @Override
    public void filter(ContainerRequestContext requestContext, ContainerResponseContext responseContext)
        throws IOException {
            responseContext.getHeaders().add("Access-Control-Allow-Origin","*");
            responseContext.getHeaders().add("Access-Control-Allow-Methods", "GET, POST, DELETE, PUT");
            // Consider adding Access-Control-Allow-Headers if custom headers are used
      }
}

This filter must then be registered in the web.xml file via the Jersey servlet parameters:

<init-param>
    <param-name>jersey.config.server.provider.classnames</param-name>
    <param-value>YOUR_PACKAGE.CorsResponseFilter</param-value>
</init-param>

10. IIS Web.config Adjustments

For applications hosted on IIS (especially MVC/Web API environments), headers can be set globally in web.config under <system.webServer><httpProtocol><customHeaders>.

Example IIS Configuration Snippet:

<httpProtocol>
  <customHeaders>
    <clear />
    <add name="Access-Control-Allow-Origin" value="*" />
    <!-- Note: Ensure X-Requested-With is removed if forcing simple requests, or included if needed -->
    <add name="Access-Control-Allow-Headers" value="Content-Type, Authorization" /> 
    <add name="Access-Control-Allow-Methods" value="GET, POST, PUT, DELETE, OPTIONS"/>
  </customHeaders>
</httpProtocol>

Furthermore, explicitly handling OPTIONS requests at the IIS pipeline level via Application_BeginRequest in global.asax.cs can preempt the processing loop:

protected void Application_BeginRequest() {
  if (Request.Headers.AllKeys.Contains("Origin", StringComparer.OrdinalIgnoreCase) && Request.HttpMethod == "OPTIONS") {
    Response.StatusCode = 200;
    Response.Flush();
    Response.End();
  }
}

11. PHP Backend Solution

If the API backend is PHP, explicit header() calls within the relevant API script are required to permit the preflight check:

header("Access-Control-Allow-Origin: *");
header("Access-Control-Allow-Methods: PUT, GET, POST, OPTIONS, DELETE, PATCH");
header("Access-Control-Allow-Headers: Origin, X-Requested-With, Content-Type, Accept, Authorization");
// Only setting the methods header might suffice depending on the complexity, but often all three are necessary.

Alternative: Server-Side Proxy (The “Give Up” Method)

When faced with stubborn server configurations or rapidly changing client libraries, resorting to a simple, same-origin proxy handler can circumvent CORS restrictions entirely. The frontend calls a local endpoint, and the local endpoint makes the actual cross-origin call, blending the response into the local origin context.

ASP.NET Handler Example (Using HttpClient):

// In an IHttpHandler (.ashx) or MVC controller action
public class LoadJSONData : IHttpHandler
{
    public void ProcessRequest(HttpContext context)
    {
        context.Response.ContentType = "text/plain";
        string targetUrl = "......"; // The cross-origin URL

        using (var client = new HttpClient())
        {
            client.DefaultRequestHeaders.Accept.Add(new MediaTypeWithQualityHeaderValue("application/json"));
            client.DefaultRequestHeaders.Add("Authorization", "Basic AUTHORIZATION_STRING");

            HttpResponseMessage response = client.GetAsync(targetUrl).Result;
            if (response.IsSuccessStatusCode)
            {
                var content = response.Content.ReadAsStringAsync().Result;
                context.Response.Write("Success: " + content);
            }
            else
            {
                context.Response.Write(response.StatusCode + " : Message - " + response.ReasonPhrase);
            }
        }
    }
    // ... IsReusable property implementation
}

// Frontend Call:
$http.get("/Handlers/LoadJSONData.ashx").success(function (data) { ... });

FAQs on Resolving CORS Options Preflight Issues

Q: What triggers the mandatory HTTP OPTIONS request in CORS

ANS: The request is preflighted by the browser if the actual request uses HTTP methods other than GET or POST, or if it uses POST with a Content-Type outside of application/x-www-form-urlencoded, multipart/form-data, or text/plain, or if it sets any custom headers.

Q: Can I disable the OPTIONS request entirely in AngularJS

ANS: While you can attempt to remove headers that force the preflight (like X-Requested-With in older versions) or reset all $httpProvider headers, the standard way is to configure the backend server to correctly respond to the OPTIONS request or use AngularJS’s $sceDelegateProvider to whitelist specific domains.

Q: Is using Access-Control-Allow-Origin *

ANS: Setting Access-Control-Allow-Origin: * allows any origin to access the resource. While convenient for development, it should be used cautiously in production environments where access needs to be restricted to specific client domains.

Q: What header should I check if my AngularJS POST request triggers OPTIONS

ANS: Check the Content-Type header. If it is set to something like application/json without accompanying server configuration, it will trigger a preflight. Try setting it to text/plain as an alternative if the server supports it.

Q: What is the purpose of the preflight request

ANS: The preflight request allows the browser to verify with the server, using an OPTIONS method, that the actual subsequent cross-origin request (which might modify data) is permitted based on the server’s CORS configuration.
