“AngularJS Factory vs Service: Implementation Details and Use Cases”

When building applications with AngularJS, dependency injection (DI) is foundational. Two primary methods for defining injectable components are using .factory() and .service(). While both ultimately yield singletons shared across your application, their underlying construction mechanisms and intended usage patterns present distinct technical differences. How do these methods fundamentally differ in implementation and flexibility?

Core Construction Mechanism: Invocation vs. Instantiation

The most critical technical distinction lies in how AngularJS executes the provided function for each provider type.

AngularJS Factory (.factory())

A factory function is invoked, and the value it returns is what gets cached and subsequently injected into other components (controllers, directives, etc.).

Conceptual Flow:

// Factory definition logic
var injectedObject = myFactoryFunction(); 
// myFactoryFunction() is called directly.

Code Example: Returning an Object Literal API

This pattern is often favored for creating services that expose a specific public API via a returned object.

angular.module('myApp').factory('dataProcessorFactory', function() {
  let privateDataCache = []; // Private variable

  function processData(input) {
    // Perform complex logic
    privateDataCache.push(input.toUpperCase()); 
    return "Processed: " + input;
  }
  
  // Expose public interface
  return {
    transformAndStore: processData,
    getStoredCount: function() {
        return privateDataCache.length;
    }
  };
});

// Injection usage in a controller
// $scope.result = dataProcessorFactory.transformAndStore('testValue');

AngularJS Service (.service())

A service function is treated as a constructor function and is executed using the new keyword behind the scenes by the Angular injector. Whatever this refers to within that function is implicitly returned as the instance.

Conceptual Flow:

// Service definition logic
var injectedObject = new myServiceFunction(); 
// myServiceFunction is instantiated. 'this' refers to the new object.

Code Example: Utilizing this for Public Members

This closely mirrors classical object-oriented constructor patterns where properties and methods are attached to this.

angular.module('myApp').service('utilityService', function($log) {
  let internalCounter = 0; // Private state managed inside the closure

  this.logMessage = function(message) {
    internalCounter++;
    $log.info(`Service Log [${internalCounter}]: ${message}`);
  };

  this.getLogCount = function() {
      return internalCounter;
  };
});

// Injection usage in a controller
// utilityService.logMessage('Initialization complete');

Flexibility in Return Types

The return value dictates significant functional differences:

  1. Factory Flexibility: Because .factory() returns whatever the function yields, it can return an object, a primitive value (string, number), a function reference, or a constructor function.

  2. Service Constraint: The .service() approach mandates that the result is an instance of the constructor. While you can return a constructor function via a service, you must then manually instantiate it in the consumer, which is generally discouraged for DI simplicity:

    • Service Pattern (Less Desirable): If a service returns a constructor: 
      // Service returns a constructor
angular.module('myApp').service('CustomConstructorService', function() {
    function MyClass(val) { this.value = val * 2; }
    return MyClass; 
});
// In controller: var instance = new CustomConstructorService(5); // Requires 'new'
    • Factory Alternative (Cleaner Syntax): The factory handles this more elegantly if the goal is to return a constructor for later instantiation: 
      // Factory returns the constructor function directly
angular.module('myApp').factory('CustomConstructorFactory', function() {
    return function MyClass(val) { this.value = val * 2; };
});
// In controller: var instance = new CustomConstructorFactory(5); // Syntax is cleaner

Singleton Behavior and Mutation

It is important to note that both factories and services produce singletons. Whether you inject the result of a factory or the instance of a service, you receive the exact same reference every time it is requested (unless the factory explicitly returns a new value, like a number or string, in which case you receive the same value, not a reference).

If a service or factory holds state (e.g., the privateDataCache in the factory example), changes made via one injected instance are visible across all other instances because they all share the same underlying object/function reference.

angular.module('myApp').factory('userAugmenterFactory', function() {
    return function addLastName(userContext, newLastName) {
        // Return a brand new object to avoid side effects
        return { ...userContext, lastName: newLastName }; 
    };
});

// In Controller:

// baseUser remains { firstName: 'Alex' }

const baseUser = { firstName: 'Alex' };

angular.module('myApp').service('userAugmenterService', function() {
    this.addLastName = function(userContext, newLastName) {
        userContext.lastName = newLastName; // DIRECT MUTATION
        return userContext;
    };
});

// In Controller: 
// $scope.completeUser = userAugmenterService.addLastName(baseUser, 'Smith'); 
// baseUser IS NOW { firstName: 'Alex', lastName: 'Smith' }

Beyond Service and Factory: The Provider Chain

While factories and services cover most use cases, it’s relevant to note that they are abstractions built upon the more fundamental .provider() mechanism. Other built-in providers like .value() and .constant() exist, offering simpler patterns for configuration or static data injection, each with increasing levels of restriction compared to the flexibility of factories.

FAQs on AngularJS Factory vs Service Comparison

Q: Are AngularJS Services and Factories always singletons

ANS: Yes, generally both .service() and .factory() return singleton instances. This means the same object reference is provided every time the dependency is requested, preserving internal state across the application. The exception is if a factory returns a primitive value (like a string or number), where you always receive the same value, but not a shared reference.

Q: Q: Which AngularJS injection method is syntactically nicer

ANS: Many developers find the syntax of using a Service slightly cleaner when the goal is to create an object with methods, as you simply attach to this. However, if you need to return any arbitrary value or constructor, the Factory approach offers superior syntactic clarity.

Q: Q: Can a factory return a constructor function

ANS: Yes, a factory can return a constructor function. This allows the consuming component (like a controller) to use the new keyword on the injected factory result to create new instances, which is a common pattern for modeling data structures or classes.

  var service = {};
  var baseUrl = 'https://itunes.apple.com/search?term=';
  var _artist = '';
  var _finalUrl = '';

  var makeUrl = function(){
    _artist = _artist.split(' ').join('+');

  service.callItunes = function(){
    makeUrl();
    var deferred = $q.defer();
    $http({
      method: 'JSONP',
      url: _finalUrl
    }).success(function(data){
      deferred.resolve(data);
    }).error(function(){
      deferred.reject('There was an error')
    })
    return deferred.promise;
  }

  return service;
});
