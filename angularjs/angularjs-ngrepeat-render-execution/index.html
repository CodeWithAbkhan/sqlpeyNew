How can we reliably signal or execute a function immediately following the completion of an ng-repeat cycle, addressing both initial renders and dynamic updates?

Directive-Based Event Emission Using $timeout

A robust method involves creating a custom directive that checks if the current iteration is the last one ($last === true) and then uses $timeout to emit an event. Using $timeout ensures the execution occurs at the end of the current digest cycle, guaranteeing elements are present, and it automatically invokes $apply.

Custom Directive Implementation (onFinishRender):

var app = angular.module('testApp', []);

app.directive('onFinishRender', function ($timeout) {
    return {
        restrict: 'A',
        link: function (scope, element, attr) {
            // Check if this is the very last element in the iteration
            if (scope.$last === true) {
                $timeout(function () {
                    // Emit an event specified by the attribute value
                    scope.$emit(attr.onFinishRender);
                });
            }
        }
    };
});

Controller Event Listener:

The controller must listen for this emitted event:

app.controller('MyController', function($scope) {
    // ... your data setup ...

    $scope.$on('ngRepeatFinishedSignal', function(event) {
        // This code runs only after all items rendered.
        console.log("ng-repeat cycle complete via event emission.");
        // Perform DOM manipulations or library initialization here.
    });
});

HTML Usage:

Apply the directive to the repeated element and specify the event name:

<div ng-repeat="item in dataCollection" on-finish-render="ngRepeatFinishedSignal">
    <div>{{ item.value }}</div>
</div>

Alternative: Decoupling with $evalAsync or $eval

Instead of emitting an event, the directive can directly evaluate an expression or call a function defined on the scope, reducing coupling between the directive and the controller logic.

  1. Using $evalAsync: Executes the expression after the DOM construction but before the browser paints, which helps prevent visual flicker.

    // Inside the directive link function:
if (scope.$last) {
   scope.$evalAsync(attr.onFinishRenderCallback); // attr.onFinishRenderCallback holds 'test()'
}

  2. Using $timeout with $eval: If execution must occur after rendering/painting is complete, wrap $scope.$eval() inside a $timeout.

    // Inside the directive link function:
if (scope.$last) {
   $timeout(function() { 
      scope.$eval(attr.onFinishRenderCallback);
   });
}

Handling Dynamic Re-renders with a Custom Filter (Hack)

The previous methods typically trigger only on the initial render. If the ng-repeat list is filtered, added to, or deleted from dynamically, you need a mechanism that fires on every re-render. Solution 3 proposes a “hacky” custom filter applied directly to the array binding to detect changes.

Custom Filter:

This filter attaches a temporary property to the data array. On first application, it schedules an $emit via $timeout(0, false). The delete operation scheduled in $timeout signals the completion of that specific digest cycle involving the array mutation.

app.filter('ngRepeatFinishTracker', function($timeout){
    return function(data){
        var context = this;
        var flag = '__renderingCompleteFlag__';
        
        if(!data[flag]){
            Object.defineProperty(
                data, 
                flag, 
                {enumerable:false, configurable:true, writable: false, value:{}});
                
            $timeout(function(){
                    delete data[flag];                        
                    context.$emit('ngRepeatFinishedSignal'); // Using the same event name
                }, 0, false);                
        }
        return data;
    };
});

HTML Usage for Dynamic Tracking:

The filter must be the first filter applied to the array source:

<!-- CORRECT USAGE: tracker filter runs first -->
<li ng-repeat="item in (sourceArray | ngRepeatFinishTracker) | filter:{name:query}">
    {{ item.name }}
</li>

<!-- INCORRECT USAGE: Other filters run first, preventing the tracker from detecting array mutation -->
<!-- <li ng-repeat="item in (sourceArray | filter:{name:query}) | ngRepeatFinishTracker"> -->

Critical Warning: Do not call $scope.$apply() inside the function handling the ngRepeatFinishedSignal event when using this filter method, as it risks triggering an infinite digest loop. Also, avoid using this for scope property updates, as changes won’t reflect immediately without an explicit $apply.

Managing Multiple ng-repeats on One Controller

To differentiate which ng-repeat finished when multiple loops exist under one controller, customize the event name broadcasted by the directive using an additional attribute:

Directive Modification (Solution 4):

// Inside link function:
if (scope.$last === true) {
    $timeout(function () {
        // Use the custom attribute or default to 'ngRepeatFinishedSignal'
        scope.$emit(attr.broadcastEventName ? attr.broadcastEventName : 'ngRepeatFinishedSignal');
    });
}

Controller Setup:

$scope.$on('customBroadcast1', function() { /* Handle list 1 completion */ });
$scope.$on('customBroadcast2', function() { /* Handle list 2 completion */ });

HTML Template:

<!-- List 1 -->
<div ng-repeat="c1 in collection1" on-finish-render broadcasteventname="customBroadcast1">
    {{ c1.data }}
</div>

<!-- List 2 -->
<div ng-repeat="c2 in collection2" on-finish-render broadcasteventname="customBroadcast2">
    {{ c2.data }}
</div>

Invoking Callbacks During Model Changes (Watching Data)

If the requirement is to run code whenever the underlying data source (ng-repeat model) changes, watching the model in the controller using $watch combined with $timeout is the direct path:

app.controller('MyController', function ($scope, $timeout) {
    $scope.data = [/* initial items */];

    $scope.$watch("data", function (newValue, oldValue) {
        if (newValue !== oldValue) { // Prevent execution on initial setup if not desired
            $timeout(function () {
               // Execute function, e.g., test();
               console.log("Data array updated, re-executing logic.");
            });
        }
    }, true); // Deep watch
});

Utilizing ng-init with $last (Simplest Approach for Initial Render)

For static lists where only the initial render completion matters, the most succinct way leverages the built-in $last variable within ng-init:

<div ng-app="testApp" ng-controller="myC">
    <!-- The expression only executes if $last is true -->
    <p ng-repeat="t in items" ng-init="$last && callMyFunction()">{{ t }}</p>
</div>

<script>
    app.controller('myC', function($scope) {
        $scope.callMyFunction = function() {
            console.log("ng-init executed on the final element!");
        }
    });
</script>

Direct Watch on Child Scope Lifecycle ($$childTail.$last)

For directives whose sole purpose is containing a repeat, one can observe the lifecycle of the child scope created by ng-repeat using internal Angular properties (though this is generally less recommended due to reliance on internal structure):

// Inside directive link function:
const deregisterWatcher = scope.$watch('$$childTail.$last', (isLast) => {
    if (isLast) {
        deregisterWatcher(); // Clean up the watcher immediately
        // Action here (might still benefit from $timeout)
    }
});

Monitoring DOM Modifications Post-Filter

For filtered scenarios, if methods relying on $last fail due to the nature of the filter, one experimental approach involves hooking into the DOM mutation methods (insertBefore, removeChild) of the parent element, triggering a debounced $timeout to signify filtering completion.

FAQs on AngularJS NgRepeat Render Execution

Q: Which method works best for firing code after ANY ng-repeat update not just initial load

ANS: The custom filter approach (Solution 3) designed to hook into the array binding is specifically crafted to fire an event on subsequent re-renders caused by filtering or data changes, provided the filter is placed first in the binding chain.

Q: Can I use document dot ready in AngularJS ng-repeat contexts

ANS: No traditional JavaScript DOM ready functions like $(document).ready() are reliable inside ng-repeat because Angular manipulates the DOM asynchronously within its own lifecycle. You must use Angular mechanisms like $timeout or directive lifecycle hooks.

Q: What is the main drawback of using the ng-init trick

ANS: The primary limitation of the ng-init="$last && myFunction()" approach is that it only fires when the list is initially rendered or when the entire source array changes structure, not reliably after intermediate filtering or item additions/removals without a full array replacement.

Q: Why is using $timeout preferred over native setTimeout in directives

ANS: $timeout is integrated into Angular’s digest cycle. It automatically calls $apply() if necessary, ensuring scope changes triggered within it are reflected in the view, unlike native setTimeout.
