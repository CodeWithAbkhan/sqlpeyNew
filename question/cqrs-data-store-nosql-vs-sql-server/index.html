CQRS Data Store: NoSQL vs SQL Server
In this post, we will be exploring some common questions around the data store approach for a CQRS application using NoSQL or SQL Server.

Question 1: Do you use one table for all events or create an events table per aggregate root?

When it comes to storing events in a CQRS+ES application, there are generally two approaches - one table for all events or an events table per aggregate root. Let’s take a look at the advantages and disadvantages of each approach.

If you use one table for all events, it is easier to manage and query the events. Although, as the number of events grows, the table can get extremely large and difficult to manage. Moreover, this approach does not scale well in a distributed environment since all writes go to one table.

On the other hand, if you create an events table per aggregate root, it helps in managing the size of the table and makes it easier to scale in a distributed environment. Although, querying the events can be difficult since the events are split across multiple tables.

In our experience, we have found that using an events table per aggregate root works well since it helps in managing the size of the table and scales well in a distributed environment. More, we use a shared events table for cross-aggregate communication.

Question 2: What would be the advantages/disadvantages of using a NoSQL database for both the write and read databases for a CQRS application?

Using a NoSQL database for both the write and read databases can have several advantages and disadvantages.

Advantages:

  • Better performance: NoSQL databases are generally designed for high read/write workloads and can handle large datasets and high traffic.
  • Flexible schema: NoSQL databases can handle unstructured and semi-structured data with ease, making it easier to handle different types of events in a CQRS application.
  • Scalability: NoSQL databases are designed to scale horizontally across multiple machines, making it easier to handle large datasets in a distributed environment.

Disadvantages:

  • Lack of transactions: NoSQL databases do not support ACID transactions across multiple documents, making it difficult to maintain consistency in a distributed environment.
  • Limited query capabilities: NoSQL databases often lack the amazing querying capabilities of SQL databases, making it difficult to query and analyze data in complex ways.
  • Operational complexity: Running a distributed NoSQL database can be complex, requiring specialized knowledge and expertise.

In our experience, we have found that using an SQL database like Postgres for the write database and a NoSQL database like MongoDB for the read database works well. Postgres provides transactions and amazing querying capabilities while MongoDB provides the flexibility, scalability, and performance needed for the read database.

Question 3: How would you convince a stubborn work colleague who is married to SQL to convert to a NoSQL approach?

Convincing a work colleague to switch to a NoSQL approach can be challenging, especially if they are married to SQL. Here are a few tips that may help:

  • Start with the use case: Explain the use case of the application and why NoSQL may be a better fit for the read database. Show them examples of how NoSQL databases have been used successfully in similar applications.
  • Highlight the advantages: Emphasize the advantages of using a NoSQL database, such as better performance, scalability, and flexibility. Explain how these advantages can benefit the application.
  • Address the concerns: Address their concerns about the lack of transactions or querying capabilities. Explain how these concerns can be addressed with a hybrid approach using both SQL and NoSQL databases.
  • Provide evidence: Provide evidence of how NoSQL databases have been successfully used in similar applications. Show them case studies and use cases that demonstrate the advantages of using NoSQL.
  • Be patient: Be patient and know that changing someone’s mindset takes time. Be prepared to answer their questions and concerns over a period of time as they get comfortable with the idea.

In recap, choosing the right data store approach for a CQRS application requires careful consideration of the use case, scalability requirements, and querying needs. While NoSQL databases can provide better performance and scalability, they may not provide the same level of transactional support or querying capabilities as SQL databases. Ultimately, a hybrid approach using both SQL and NoSQL databases may provide the best of both worlds. ]]>
