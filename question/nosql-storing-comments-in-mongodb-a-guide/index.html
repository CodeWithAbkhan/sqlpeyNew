NOSQL: Storing Comments in MongoDB: A Guide Storing Comments in NoSQL - MongoDB
In this blog post, we will discuss two ways to store comments in MongoDB and explain which method is better.

Method 1: Embed Comments in Post Document

In this method, comments are embedded in the Post document. Here is an example:

{
  "_id": ObjectId(12345),
  "title": "Cat ate elephant!",
  "body": "Lorem ipsum dolor sit amet, consectetur adipiscing elit. Aenean convallis pretium vulputate.",
  "comments": [
    {"name": "Cat", "body": "MEOW!"},
    {"name": "Elephant", "body": "I was eaten by cat, lol!"},
    {"name": "Human", "body": "I am hungry!"}
  ]
}

The comments are stored as an array of objects within the Post document. This method has several advantages:

  • No need for joins, which means faster access to data.
  • The NoSQL way of doing it.
  • Every comment is just related to that post, so it makes sense to store them together.

Although, if you have large documents (>15.5 Megabytes) and receive a lot of comments, you may need to store them somewhere else since the maximum document size is 16 Megabytes.

Method 2: Relationship between Post and Comments

The second method involves creating a relationship between Post and Comments documents. Here is an example:

// POST //
{
  "_id": ObjectId(12345),
  "title": "Cat ate elephant!"
  "body": "Lorem ipsum dolor sit amet, consectetur adipiscing elit. Aenean convallis pretium vulputate."
}

// Comments //
{
  "_id": ObjectId(...),
  "post_id": ObjectId(12345),
  "name": "Cat",
  "body": "MEOW!"
}

{
  "_id": ObjectId(...),
  "post_id": ObjectId(12345),
  "name": "Elephant",
  "body": "I was eaten by cat, lol!"
}

{
  "_id": ObjectId(...),
  "post_id": ObjectId(12345),
  "name": "Human",
  "body": "I am hungry!"
}

In this method, each Comment document is related to a Post document through the use of a post_id field. This method has its advantages:

  • The RDBMS way of doing it.
  • No limit on document size.

Although, since MongoDB doesn’t have built-in joins, the second method may require additional queries and can be slower in retrieving Post documents with Comments.

Which Way is Better?

The first method is preferred since no Comment document belongs to more than one Post. Therefore, it makes more sense to embed them in the Post document. More, this method provides faster access to data and requires fewer queries.

Although, if your documents are write-heavy or you receive a significant amount of comments, you may need to consider the second method.

Practical Examples

Suppose you have a blog post with several comments. Using Method 1, retrieving the post with comments in a single query would look like this:

db.posts.find({_id: ObjectId(12345)})

The result will include the Post and its Comments:

{
  "_id": ObjectId(12345),
  "title": "Cat ate elephant!",
  "body": "Lorem ipsum dolor sit amet, consectetur adipiscing elit. Aenean convallis pretium vulputate.",
  "comments": [
    {"name": "Cat", "body": "MEOW!"},
    {"name": "Elephant", "body": "I was eaten by cat, lol!"},
    {"name": "Human", "body": "I am hungry!"}
  ]
}

If you were to use Method 2, to retrieve the same Post and its Comments, you would need to use two separate queries:

var post = db.posts.find({_id: ObjectId(12345)})
var comments = db.comments.find({post_id: ObjectId(12345)})

The result will be two sets of data: one with the Post and another with its Comments.

Alternative Ways

There isn’t one-size-fits-all solution when it comes to storing data, and MongoDB provides several ways of doing it. One alternative to Method 1 is to store comments as separate documents but limit the number per post. This way, you could keep comments within the document, but avoid surpassing the maximum size limit.

Summary

Storing comments in MongoDB can be done in two ways: embedded in the Post document or as separate Comment documents. The preferred method is Method 1 since it provides faster access to data, requires fewer queries, and is the NoSQL way of doing it. Although, if your documents are write-heavy or receive a significant amount of comments, you may need to consider Method 2. It’s essential to choose the right method to ensure scalability and performance. ]]>
