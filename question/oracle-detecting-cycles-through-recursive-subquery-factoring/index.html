ORACLE: Detecting Cycles through Recursive Subquery Factoring Cycle detection is a crucial task in database systems to avoid infinite loops when querying hierarchical data. Oracle SQL has provided hierarchical queries using CONNECT BY syntax since version 2. In their latest Oracle 11g release 2, they introduced recursive subquery factoring, also known as the recursive with clause. This clause follows the ANSI standard and has been implemented in several RDBMS vendors.

In this blog post, we will explore the behavior of cycle detection using recursive subquery factoring in Oracle SQL and see if it follows the ANSI standard or not. We will also see if this behavior is consistent across different databases that support the recursive with clause.

Let’s begin by clarifying the task of cycle detection in hierarchical data. Consider the following table t, which represents a hierarchical relationship between parent and child nodes.

create table t
( id        number
, parent_id number
);
insert into t values (1, 2);
insert into t values (2, 1);
commit;

				  The query using CONNECT BY syntax for cycle detection looks like the following:  
				  

select id, parent_id, connect_by_iscycle
from t
connect by nocycle parent_id = prior id
start with id = 1;

The output of this query is:

    ID  PARENT_ID CONNECT_BY_ISCYCLE
------ ---------- ------------------
     1          2                  0
     2          1                  1

This output seems intuitive, as it returns two rows indicating the hierarchical relationship between nodes and a flag that indicates if there is any cycle. The first row indicates the parent-child relationship between node 1 and node 2, and the second row indicates a loop in the hierarchy from node 2 to node 1. Let’s now see how we can perform cycle detection using recursive subquery factoring in Oracle SQL. The query looks like the following:

with tr (id,parent_id) as
( select id, parent_id
  from t
  where id = 1
  union all
  select t.id, t.parent_id
  from t
  join tr on t.parent_id = tr.id
)
cycle id set is_cycle to '1' default '0'
select id, parent_id, is_cycle
from tr;

This query uses a recursive subquery factoring clause to traverse the hierarchical relationship between nodes. The “tr” common table expression (CTE) initializes with the starting node (node 1), and it joins with the “t” table to get the child nodes recursively. The “cycle” keyword enables cycle detection by assigning a flag to the rows where a cycle occurs. The output of this query is:

    ID  PARENT_ID I
------ ---------- -
     1          2 0
     2          1 0
     1          2 1

This output is different from the previous query using CONNECT BY syntax. It returns an additional row indicating a loop between nodes 1 and 2, which seems redundant. We can see that the behavior of cycle detection is not consistent across both queries. The query using CONNECT BY syntax seems more intuitive and correct, as it returns only the rows representing the hierarchical relationship and the loops. It is not clear whether this behavior is an implementation mistake in Oracle SQL or a difference in the ANSI standard for recursive subquery factoring. Let’s see if this behavior is consistent across other databases that support the recursive with clause. We can use PostgreSQL and MySQL to check the behavior of cycle detection using recursive subquery factoring. PostgreSQL supports SQL recursive common table expressions since version 8.4, while MySQL only supports recursive CTEs using its non-standard syntax. Let’s see the equivalent queries for our example in PostgreSQL and MySQL. In PostgreSQL, the query looks like the following:

with recursive tr(id, parent_id, is_cycle) as
( select id, parent_id, false
  from t
  where id = 1
  union all
  select t.id, t.parent_id, t.id = tr.parent_id or tr.is_cycle
  from tr
  join t on t.parent_id = tr.id
)
select id, parent_id, is_cycle
from tr;

In MySQL, the query looks like the following:

with recursive tr(id, parent_id, is_cycle) as
( select id, parent_id, false
  from t
  where id = 1
  union all
  select t.id, t.parent_id, t.id = tr.parent_id or tr.is_cycle
  from t
  join tr on t.parent_id = tr.id
)
select id, parent_id, is_cycle
from tr;

Both queries return the same output as the Oracle SQL query using recursive subquery factoring. They return an additional row indicating a loop between nodes 1 and 2, which seems redundant. Therefore, it seems that this behavior in cycle detection when using recursive subquery factoring is consistent across different database systems. It is not clear if this behavior is a mistake in the implementation or a difference in the ANSI standard. Although, it is clear that the behavior using CONNECT BY syntax is more intuitive and correct. In recap, cycle detection is an important task in hierarchical data, and it is essential to use the correct syntax and queries to avoid infinite loops. Oracle SQL provides two syntaxes for hierarchical queries, CONNECT BY and recursive subquery factoring. While cycle detection works well using CONNECT BY syntax, using recursive subquery factoring may produce redundant rows. Therefore, it is recommended to use CONNECT BY syntax for cycle detection in hierarchical data.]]>
