Choosing Between SQL and NoSQL for Your Schema SQL vs NoSQL: Choosing the Right Database for Your Project

The Project: A Reporting System with Nested Data

You have a new project: a reporting system that requires nested data. Specifically, the data are organized in an organization-event hierarchy. Each organization has one or more regions, each region has one or more campuses, each campus has one or more events, and each event has a set of records that must be reported on. The report interface is designed to extract information from the records entered into the system and report it to clients.

You have two concerns. First, the database schema is deeply nested, and you don’t want to have to deal with lots of joins to get to the bottom of the tree. Second, you’re worried that reporting on the records may be difficult without resorting to some heavy map/reduce stuff that you’re not familiar with.

The Schema


The organization-event hierarchy is represented in the schema as follows:

  1. Organization
  2. Region (belonging to an organization)
  3. Campus (belonging to a region)
  4. Event (belonging to a campus)
  5. Record (belonging to an event)

Note that each record consists of a set of metrics for a given event.

Should You Choose SQL or NoSQL?

The next big question is which type of database to use. Should you go with a traditional SQL database, or should you opt for a NoSQL solution?

At first glance, the schema appears to be deeply nested, which would suggest a NoSQL solution. Although, it’s important to note that NoSQL databases are not always the best choice for hierarchical data. The key advantage of NoSQL databases is speed, but this only matters when dealing with very large data sets that traditional SQL databases can’t handle.

In this case, the schema is relatively small and the data are nested, making it a good candidate for a traditional SQL database.

Alternative Schema Design

If you’re concerned about the number of joins required to access the records table, there is an alternative schema design that could simplify things. You could collapse the organization, region, campus, and event tables into a single hierarchical table with a self-referential key. This would reduce the number of tables and make querying the records table simpler:

CREATE TABLE hierarchical (id SERIAL PRIMARY KEY,name VARCHAR(100) NOT NULL,parent_id INTEGER REFERENCES hierarchical(id)
);

The parent_id column would hold the ID of the parent record in the same table. For example, an event record might have a parent_id pointing to the campus record it belongs to.

Reporting on the Records

You’re also worried about how reporting on the records will work. It’s true that querying nested data using SQL can be complicated. If you go with SQL, you’ll have to use several JOIN clauses to navigate the hierarchy. Here’s an example query that retrieves all the records for a given organization:

SELECT *
FROM organization
LEFT JOIN region ON region.organization_id = organization.id
LEFT JOIN campus ON campus.region_id = region.id
LEFT JOIN event ON event.campus_id = campus.id
LEFT JOIN record ON record.event_id = event.id
WHERE organization.id = ?

This query joins the five tables together and filters the results by organization ID. Note that the query retrieves all columns from all tables. You’ll want to limit the columns returned to just the ones you need to reduce network overhead.

If you go with a NoSQL database, querying the nested data will be simpler. Although, you’ll still need to ensure that your data is properly denormalized to make querying efficient.

Recap

In recap, this project is a good candidate for a traditional SQL database. While the schema is deeply nested, NoSQL is not necessarily the best choice for hierarchical data. Instead, you can collapse the hierarchy into a single hierarchical table with a self-referential key to simplify querying. Reporting on the records will require several JOIN clauses if you go with SQL, but querying nested data will be simpler if you opt for a NoSQL database.
