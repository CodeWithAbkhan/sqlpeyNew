ORACLE: Deadlock Detected: ORA-00060 Question: I am getting the ORA-00060 error while running scripts concurrently in Oracle 10g. The scripts are performing updates on the same table but different records. Can this cause the error? Should I avoid concurrent updates on a table at all times? Also, can the error happen regardless of where the updates are performed on a table? Lastly, does the message “PL/SQL successfully completed” mean that Oracle has recovered from the deadlock and completed the updates successfully or should I rerun the scripts serially?

Learning the ORA-00060 Deadlock Error

The ORA-00060 error is a deadlock error that occurs when two or more sessions are blocked waiting for resources held by each other, resulting in a cyclic dependency that cannot be resolved. It is a common error in concurrent applications, especially those that involve complex transactions with multiple tables.

In Oracle, a deadlock can occur due to various resources, including but not limited to:

  • Row-level locks on tables
  • Shared locks on database objects such as indexes, partitions, or tables
  • Resources held by parallel DML statements such as direct-path inserts, updates or deletes
  • Exclusive locks on system resources such as undo segments, temporary segments, or latches

When a deadlock is detected, Oracle resolves it automatically by rolling back one of the involved transactions and allowing the others to proceed. The error message indicates which session was rolled back and which resources were involved in the deadlock.

Although, it’s important to note that even though Oracle can resolve deadlocks automatically, it’s still a good practice to avoid them in the first place, as they can cause performance degradation and application downtime.

Concurrent Updates on Different Records of the Same Table

In your case, you mentioned that the scripts are performing updates on the same table but different records based on the WHERE clause. While it’s true that concurrent updates on the same table can cause deadlocks, it’s not necessarily the case in your scenario.

Assuming that the updates are on different rows and do not overlap, it’s unlikely that they would cause a deadlock due to table-level locks. Although, there may be other resources at play, such as indexes or referential integrity constraints, that can cause the deadlock.

For example, if the updates are on a table that has foreign key constraints, and the referential integrity is not enforced by an index, then Oracle may have to lock the entire parent table to ensure the updates do not violate the constraints. This can cause deadlocks if different transactions are trying to update different rows in the parent table simultaneously.

Similarly, if the updates are on a table that has no indexes, or the indexes are not selective enough, then Oracle may have to lock more rows than necessary, which can cause contention and eventually a deadlock.

Investigating and Resolving Deadlocks

To investigate and resolve deadlocks, you can start by examining the trace files generated by Oracle when the ORA-00060 error occurs. The trace files contain detailed information about the involved transactions, the resources that were locked, and the timing of the lock requests and releases. By analyzing the trace files, you can identify the root cause of the deadlock, such as missing indexes, non-selective indexes, or unoptimized SQL statements.

To prevent deadlocks from occurring in the first place, you can employ various techniques, such as:

  • Optimizing SQL statements to reduce the locking granularity and avoid unnecessary locks
  • Tuning the database and application to balance concurrency and throughput
  • Implementing row-level locking schemes such as “select for update” or “optimistic locking” to minimize blocking
  • Enforcing referential integrity constraints by indexes or triggers
  • Using specific hints or directives to control the locking behavior of Oracle
