Finding Current Open Cursors in Oracle: A Guide How to Find Current Open Cursors in Oracle

To find the number of current open cursors in an Oracle instance, you can use the following queries:

  1. Total Cursors Open, By Session: This query provides the total number of opened cursors for each session.
SELECT a.value, s.username, s.sid, s.serial#
FROM v$sesstat a, v$statname b, v$session s
WHERE a.statistic# = b.statistic#  AND s.sid=a.sid
AND b.name="opened cursors current";

Here, we are selecting values for opened cursors, username, session id, and serial number from v$sesstat, v$statname, and v$session tables. The accuracy of this data is based on pseudo-tables (“x$” tables) that point directly to the relevant portions of the SGA; hence you cannot get more accurate than that.

  1. Open Cursors With Parsed SQL Text: This query provides the number of Open Cursors with parsed SQL text details for each user.
SELECT sql_text, COUNT(*) AS "OPEN CURSORS", user_name FROM v$open_cursor
GROUP BY sql_text, user_name ORDER BY COUNT(*) DESC;

In this query, we are selecting sql_text, count of opened cursors, and username from v$open_cursor table, grouping it by sql text and username, and finally ordering the output by the count in descending order.

  1. Open Cursors With Parsed SQL Text along with session details: This query provides the number of Open Cursors with parsed SQL text details along with the session machine name for each user.
COLUMN USER_NAME FORMAT A15

SELECT s.machine, oc.user_name, oc.sql_text, COUNT(1) 
FROM v$open_cursor oc, v$session s
WHERE oc.sid = s.sid
GROUP BY user_name, sql_text, machine
HAVING COUNT(1) > 2 ORDER BY COUNT(1) DESC; ```  In this query, we are selecting the machine name, username, sql_text, and count of cursors opened for each combination of username, sql_text, and machine for sessions where the cursor count is greater than two. The accuracy of the data from these queries is based on pseudo-tables ("x$" tables) that point directly to the relevant portions of the SGA, and hence is point-in-time (i.e., dirty read).  Overall, these queries are helpful in identifying leaky applications and can be useful for performance tuning.
