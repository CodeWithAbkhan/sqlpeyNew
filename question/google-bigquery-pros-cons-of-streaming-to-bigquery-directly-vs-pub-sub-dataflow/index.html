Streaming into BigQuery directly vs through Google Pub/Sub + Dataflow

Introduction

We have a NodeJS API hosted on Google Kubernetes Engine and would like to start logging events into BigQuery. There are various ways to achieve this, but primarily two methods are commonly used: Insert Each event directly into BigQuery or Pub/Sub + Dataflow.

Direct streaming into BigQuery

The first method is to insert each event directly into BigQuery using the Node BigQuery SDK as described in the official document. This method can be achieved with the following code:

const bigquery = new BigQuery();
const datasetId = 'my_dataset';

// "my_table" is the name of a table in the "my_dataset" dataset.
const tableId = 'my_table';

// Insert data into a table
bigquery 
  .dataset(datasetId)
  .table(tableId)
  .insert(rows)
  .then(() => {
    console.log(`Inserted ${rows.length} rows`);
  })
  .catch((err) => {
    console.error('ERROR:', err);
  });

Pros: - This method is straightforward and easy to implement. - It doesn’t require additional infrastructure, such as Pub/Sub and Dataflow. - It can handle streaming small amounts of data in real-time. Cons: - If the rate of incoming events is too high, it may not be able to handle it. - If the Node application encounters issues and stops streaming, data may be lost.

Pub/Sub + Dataflow

The second method is to publish each event to a Cloud Pub/Sub topic, then write a Cloud Dataflow pipeline to stream that data into BigQuery. In this method, the Pub/Sub service between the Node application and Dataflow pipeline acts as a message broker. A sample code to publish data to Pub/Sub topic:

// Publish a message to a topic
async function publishMessage() {
  // [START pubsub_publish]
  // Imports the Google Cloud client library
  const {PubSub} = require('@google-cloud/pubsub');

  // Creates a client; cache this for further use
  const pubSubClient = new PubSub();

  /**
   * TODO(developer): Uncomment the following lines to run the sample.
   */
  const topicName = 'my-topic';
  const data = JSON.stringify({foo: 'bar'});
  const dataBuffer = Buffer.from(data);

  // Publishes the message as a string, e.g. "Hello, world!" or JSON.stringify(someObject)
  const messageId = await pubSubClient.topic(topicName).publish(dataBuffer);
  console.log(`Message ${messageId} published.`);
  // [END pubsub_publish]
}

publishMessage().catch(console.error);

And a sample Dataflow pipeline code:

options = {
  "project": "my-project-id",
  "region": "us-central1",
  "input_topic": "projects/my-project-id/topics/my-input-topic",
  "output_table": "my_project_id:my_dataset.my_table",
}

p = beam.Pipeline(options=options)

(p
  | "ReadData" >> beam.io.ReadFromPubSub(topic=options["input_topic"])
  | "TransformData" >> beam.ParDo(MyTransformDoFn())
  | "WriteData" >> beam.io.WriteToBigQuery(
      table=options["output_table"],
      schema="field1:STRING,field2:FLOAT",
      create_disposition=beam.io.BigQueryDisposition.CREATE_IF_NEEDED,
      write_disposition=beam.io.BigQueryDisposition.WRITE_APPEND,
  )
)

result = p.run()
result.wait_until_finish()

Pros: - This method can handle a very high rate of incoming data as it uses a message broker (Pub/Sub) - It allows more flexibility as the Dataflow pipeline can transform the data before streaming to BigQuery. - It reduces the load on the Node application server as it doesn’t have to handle streaming. Cons: - This method is complicated to implement compared to the direct streaming method. - It requires additional infrastructure, such as Pub/Sub and Dataflow, which may add to the cost. - It may introduce additional latency because of the message broker (Pub/Sub).
