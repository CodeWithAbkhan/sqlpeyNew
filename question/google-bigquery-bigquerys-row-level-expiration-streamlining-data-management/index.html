BigQuery Row-Level Expiration
BigQuery is a cloud-based data warehousing platform by Google that enables companies to store, query, and analyze their data using SQL-like queries. While BigQuery is a amazing tool for data management, there are certain limitations to what it can do. One of these limitations is that it does not support row-level expiration out-of-the-box.

What is row-level expiration in BigQuery?

Row-level expiration in BigQuery is the ability to set an expiration time on individual rows in a table. With row-level expiration, you can specify that a row should be deleted automatically after a certain period of time has elapsed. This is useful for scenarios where you have data that is only relevant for a specific period of time, such as session data or logs.

Is row-level expiration possible in BigQuery?

Unfortunately, row-level expiration is not possible in BigQuery at this time. Although, there are alternative solutions you can use to achieve similar results. One of these solutions is partitioned tables.

Partitioned Tables

Partitioned tables in BigQuery are tables that are divided into partitions based on a timestamp or date column. Partitioned tables support more efficient querying and cost-effective storage by allowing users to only process the data that is relevant to their analysis.

Setting an Expiration Time on Partitions

If your table is a partitioned table, you can set an expiration time on the partitions within the table using the timePartitioning.expirationMs field. This setting sets a maximum time for how long a partition can exist before it is automatically deleted.

For example, the following code sets the expiration time for partitions in a table to 31 days after their creation.

bq update --time_partitioning_expiration 2678400000 mydataset.mytable

This code sets the expiration time for partitions in the mydataset.mytable table to 31 days (in milliseconds) after their creation.

With this setting in place, any partition that is older than 31 days will be automatically deleted.

Creating a Partitioned Table

To create a partitioned table in BigQuery, you need to specify the column that will be used to partition the data. This is typically a date or timestamp column that represents the data’s creation time or some other time-based attribute.

The following SQL code creates a partitioned table in BigQuery using a date column for partitioning.

CREATE TABLE `mydataset.mytable`
PARTITION BY DATE(created_date)
OPTIONS(
  expiration_timestamp=TIMESTAMP_ADD(CURRENT_TIMESTAMP(), INTERVAL 31 DAY)
)
AS SELECT * FROM `mydataset.myunpartitionedtable`

This code creates a new partitioned table called mydataset.mytable that is partitioned by the created_date column. It also sets the expiration time for the table to be 31 days after the current timestamp. Lastly, it populates the table with data from an existing table called mydataset.myunpartitionedtable.

Querying Partitioned Tables

With a partitioned table in place, querying the data becomes more efficient and less costly. When you query a partitioned table, BigQuery will only scan the partitions that are relevant to your query, rather than scanning the entire table. This can significantly reduce your query costs and improve performance.

The following SQL code demonstrates how to query a partitioned table in BigQuery.

SELECT *
FROM `mydataset.mytable`
WHERE created_date BETWEEN DATE_SUB(CURRENT_DATE(), INTERVAL 31 DAY) AND CURRENT_DATE()

This code retrieves all rows from the mydataset.mytable table that were created within the last 31 days.
