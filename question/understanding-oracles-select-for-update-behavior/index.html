Understanding Oracle’s Select for Update Behavior In this Q&A Session, we will discuss the behavior of Oracle’s SELECT FOR UPDATE statement and how to overcome the problems that can arise from it. More, we will try out some code examples to demonstrate the issues.

Problem Statement Suppose we have a table with rows representing cards, and we want to assign a card to a client as part of a reservation transaction. We need to ensure that a card can only belong to a single client and that the reserved cards are returned to the pool of available resources after some time.

We are using Oracle database for storing the data, and as a solution, we are assigning a status to the card and storing its reservation date. While reserving a card, we use the SELECT FOR UPDATE statement to find available cards and those that were reserved a long time ago. Although, we are experiencing problems with the query, which is not working as expected.

Code Explanation To demonstrate the issue with SELECT FOR UPDATE, let us consider a simplified example. We have a table named card_numbers with non-null id numbers, and we want to lock some of them.

In session 1, we run the following code to lock a row:

set autocommit off;

select id from card_numbers
where id is not null
and rownum <= 1
for update skip locked;

Here, we are using the FOR UPDATE SKIP LOCKED clause to avoid waiting for a locked row. We do not commit the transaction, and the row must be locked.

Later, in session 2, we run the same code to lock another row:

set autocommit off;

select id from card_numbers
where id is not null
and rownum <= 1
for update skip locked;

In theory, we expect to get a single, different row that satisfies the query conditions in both sessions simultaneously. But, this code does not work as expected.

Solution As per Oracle, the FOR UPDATE clause is evaluated after the WHERE clause. The SKIP LOCKED clause is like an additional filter that guarantees that none of the rows that were returned is locked.

The behavior that we encountered for SELECT FOR UPDATE SKIP LOCKED has been defined in this blog.

The solution is to either remove the SKIP LOCKED clause or replace FOR UPDATE SKIP LOCKED with LOCK TABLE before the WHERE clause.

Code Examples To test this behavior, we can run the following code:

– first, in session 1 set autocommit off;

select id from card_numbers
where id is not null
and rownum <= 1
for update;

– later, in session 2 set autocommit off;

select id from card_numbers
where id is not null
and rownum <= 1
for update;

Here, we removed the SKIP LOCKED clause and ran the code in two different sessions. In session 2, the code is waiting for the transaction to be committed or rolled back in session 1.

To use LOCK TABLE, we can modify the code as follows:

– first, in session 1 set autocommit off;

lock table card_numbers in exclusive mode;

select id from card_numbers
where id is not null
and rownum <= 1;

– later, in session 2 set autocommit off;

lock table card_numbers in exclusive mode;

select id from card_numbers
where id is not null
and rownum <= 1;

Here, we have replaced FOR UPDATE SKIP LOCKED with LOCK TABLE, and the behavior is as expected. Both sessions get a single, different row that satisfies query conditions.

Recap In recap, Oracle’s SELECT FOR UPDATE statement can have some unexpected behavior when used with SKIP LOCKED clause. To solve this, we can either remove the SKIP LOCKED clause or use LOCK TABLE instead of FOR UPDATE SKIP LOCKED.
