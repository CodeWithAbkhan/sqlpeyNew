Why does direction of index matter in MongoDB? MongoDB Indexes: Why Direction Matters
Indexes are an important part of any MongoDB database. Indexes help us quickly retrieve data by providing an optimized data structure, usually a B+ Tree, that allows us to quickly find the data that we are looking for. But when creating an index, the number associated with a key specifies the direction of the index, so it should always be 1 (ascending) or -1 (descending). But why does the direction of the index matter in MongoDB?

To understand why direction matters in MongoDB, it is important to understand how the index is structured. When creating an index in MongoDB, the index created is a B+ Tree. A B+ Tree is a type of data structure used to store and retrieve data quickly. It is composed of nodes, which can be thought of as buckets that hold the data. The tree is composed of parent and child nodes, where each node contains multiple keys and values.

The keys are used to order the data in the tree, and the values are the data that is being stored. The order of the keys is important because it determines the order in which the data is stored in the tree. When creating an index in MongoDB, the number associated with a key specifies the direction of the index, so it should always be 1 (ascending) or -1 (descending).

When finding single items, the order of the nodes in the tree is irrelevant. However, if you are returning a range of nodes, the elements close to each other will be down the same branches of the tree. The closer the nodes are in the range the quicker they can be retrieved. With a single field index, the order won’t matter. If they are close together in ascending order they will also be close together in descending order.

Compound Indexes

When you have a compound key, the order starts to matter. For example, if the key is A ascending B ascending the index might look something like this:

Row   A B
1     1 1
2     2 6
3     2 7 
4     3 4
5     3 5
6     3 6
7     5 1

A query for A ascending B descending will need to jump around the index out of order to return the rows and will be slower. For example it will return Row 1, 3, 2, 6, 5, 4, 7

A ranged query in the same order as the index will simply return the rows sequentially in the correct order.

Finding a record in a BTree takes O(Log(n)) time. Finding a range of records in order is only OLog(n) + k where k is the number of records to return. If the records are out of order, the cost could be as high as OLog(n) * k

Conclusion

To summarize, the direction only matters when you are sorting on two or more fields. If you are sorting on {a : 1, b : -1}, index {a : 1, b : 1} will be slower than index {a : 1, b : -1}.

Understand two key points - while an index is better than no index, the correct index is much better than either. MongoDB will only use one index per query, making compound indexes with proper field ordering what you probably want to use.

Indexes aren’t free. They take memory, and impose a performance penalty when writing. But, when used correctly, indexes can help speed up reads considerably, leading to better query performance and lower latency.
