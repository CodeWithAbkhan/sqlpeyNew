Handling Random ORA-12570 Errors with Oracle.ManagedDataAcess
If you are migrating from the unmanaged version of ODP.NET to Oracle.ManagedDataAcess and experiencing random ORA-12570 TNS:packet reader failure errors, you are not alone. This error occurs when the TNS listener process cannot read the incoming network packet completely, and can be caused by various factors such as network issues, server load, client application issues, and misconfigured protocols. In this post, we will discuss some approaches to diagnose and fix this error, specifically in the context of the ManagedDataAcess version 12.1.2400 (4.121.2.20150926).

The Environment

Before we dive into the solutions, let’s first set the stage for the problem. Our environment consists of:

  • Oracle.ManagedDataAcess version 12.1.2400 (4.121.2.20150926) (nuget) (no gac reference installed on server that could override the bin version)
  • Oracle Server Oracle Database 12c Enterprise Edition Release 12.1.0.2.0 - 64bit Production
  • Windows 2012 (Windows Update ok)

The Symptoms

The ORA-12570 error occurs randomly and affects subsequent requests for about 10-30 minutes, after which the requests may work again for another 10-30 minutes and so on. This behavior suggests that the error is not caused by a simple configuration issue or a permanent network outage, but rather some transient network or server load problem. Here are some symptoms that may help us diagnose the issue:

  • The same connection string works perfectly with the unmanaged version of ODP.NET.
  • The error occurs on different machines including local, Azure WebApp, and AWS EC2 instances.
  • The error does not appear to be caused by firewall, interference, or encryption issues. The network stack seems to be functioning normally.
  • The error persists even when we test exactly the same request every time, indicating that it is not related to data format or content.

The Diagnosis

The ORA-12570 error is notoriously hard to diagnose, as it can be caused by various factors and can manifest themselves seemingly randomly. Here are some steps we can take to diagnose the issue:

  • Check the Oracle alert log for any errors or warnings related to TNS listener or network issues. This log can provide valuable clues as to the cause of the problem.
  • Enable SQL tracing or ODP.NET tracing in the ManagedDataAcess client to capture low-level network activity and diagnose the issue. This may reveal packet loss, timeouts, or other network anomalies.
  • Use network diagnostic tools such as ping, tracert, Wireshark, or tcpdump to monitor the network traffic between the client and the server. This can help determine if the issue is related to packet loss, network congestion, or faulty hardware.
  • Try to reproduce the error outside of the ManagedDataAcess environment, using other clients or protocols such as SQL*Plus, JDBC, or ODBC. This can narrow down the scope of the issue and rule out application-specific problems.

The Solutions

Once we have diagnosed the issue, we can take different approaches to fix it. Here are some possible solutions:

Upgrade to the latest version of Oracle.ManagedDataAcess.

Oracle releases new versions of the ManagedDataAcess client regularly, each containing bug fixes, performance improvements, and new features. Upgrading to the latest version may fix the ORA-12570 error, especially if it was caused by a known bug that has been fixed in a newer version. You can download the latest version from the Oracle website or install it via the NuGet package manager in Visual Studio.

Configure connection pooling settings.

Connection pooling is a technique that allows the client to reuse existing connections to the database, rather than creating a new connection for each request. This can improve performance and reduce network overhead. Although, if the pool size is too small or too large, it can cause issues such as ORA-12570 errors, as the client may not be able to acquire or release connections in a timely manner. To configure connection pooling, you can use the following parameters in the connection string:

Data Source=(description=(address=(protocol=tcp)(host=hostname)(port=1521))(connect_data=(service_name=servicename)));User ID=username;Password=password;Pooling=true;Min Pool Size=1;Max Pool Size=100;Connection Lifetime=300;

Here, we set the minimum pool size to 1, the maximum pool size to 100, and the connection lifetime to 300 seconds. These values can be adjusted according to your server and workload requirements. You can also configure connection pooling settings via the OracleConnection class in C# code.

Set a higher value for the SQLNET.INBOUND_CONNECT_TIMEOUT parameter.

The SQLNET.INBOUND_CONNECT_TIMEOUT parameter controls the time to wait for a client connection to be established. If the client does not establish a connection within this timeout, the server terminates the connection attempt. By default, the value of this parameter is 60 seconds, which may not be enough in some cases. To increase the timeout, you can add the following line to the sqlnet.ora file on the server:

SQLNET.INBOUND_CONNECT_TIMEOUT=360

Here, we set the timeout to 360 seconds (6 minutes), but you can adjust it according to your needs. Note that this parameter affects all incoming connections to the server, not just those from the ManagedDataAcess client.

Reduce the MTU size of the network interface.

The MTU size controls the maximum size of a network packet. If the packet size exceeds the MTU size of the network interface, it may be fragmented or dropped, causing errors such as ORA-12570. To mitigate this issue, you can reduce the MTU size of the network interface on both the client and the server. This can be done via the network adapter settings in Windows or Linux. The recommended MTU size for Oracle databases is 1500 bytes, but you can experiment with smaller sizes if necessary. Note that reducing the MTU size may impact network performance, so it should be done cautiously.
