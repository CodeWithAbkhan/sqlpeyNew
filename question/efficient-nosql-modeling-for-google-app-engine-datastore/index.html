Efficient NoSQL modeling for Google App Engine Datastore Efficient NoSQL modeling in Google App Engine Datastore
If you’re building an application on Google App Engine and planning to persist your data in the Datastore, you need to find an efficient way to model your data. Your goal is to create a data model that allows you to store and retrieve data quickly and efficiently, with minimal maintenance overhead. Let’s take a closer look at how you can model your data in an efficient way, by answering some frequently asked questions.

How would this handle hundreds of comments and hundreds of thousands of votes?

It’s important to note that Datastore is a NoSQL database, which means you don’t need to worry about the traditional relational database issues like normalization or schema design. In general, you should aim to create a model that optimizes for reads, as writes are generally much more expensive in NoSQL than reads.

Lazy loading is a great option for handling the volume of comments. This means that you’ll only load comments as they’re requested, rather than loading all comments for a story. This can reduce the overhead of loading all the comments and improve overall performance.

When it comes to handling large volumes of votes, you can pre-process the data. When a user votes on a comment, you can simply increment the comment’s like counter by one, and record the user’s vote somewhere else. This allows you to show users the total number of likes immediately, without the overhead of querying for all of the likes and dislikes for each comment.

To improve performance, consider using caching to store frequently accessed data. You can use Google Cloud Memorystore to store your cache in-memory, which is much faster than accessing it from disk.

What is a common way of modeling concepts in NoSQL?

The best way to model your data in NoSQL generally involves denormalizing your data. In other words, store redundant data across multiple documents or entities to make querying and updating data faster and easier.

One common approach is to use a document-based schema. This means that a single document contains all of the related data for an object, rather than being split across multiple tables, as would be the case in a traditional relational database schema. Document-based schemas allow for more flexible querying and indexing, enabling faster, more efficient data retrieval.

You can also use entities, which are similar to document-based schemas, but are part of Google’s Datastore. Entities allow you to store all of the data for a single object in one place, enabling faster querying and indexing. With entities, you can also use ancestor relationships to create a hierarchical structure for your data.

Example code:

Let’s take a look at some sample code for modeling data using Google App Engine Datastore.

Example 1:

class Story {
    Comment[] comments;
    ...
}

class Comment {
    User[] likes;
    User[] hates;
    ...
}

The above code defines the Story and Comment classes. A Story contains an array of comments, and each comment contains an array of users who have liked or disliked the comment.

To handle queries for this data, you might use the following code:

def get_comment_likes(comment_id):
    comment = Comment.query(comment_id)
    likes = len(comment.likes)
    dislikes = len(comment.hates)
    return (likes, dislikes)

This code retrieves the comment by its ID, and then counts the number of likes and dislikes it has. As you can see, this code is simple and straightforward.

Example 2:

class User(ndb.Model):
    name = ndb.StringProperty()
    email = ndb.StringProperty()

class Comment(ndb.Model):
    content = ndb.StringProperty()
    posted_by = ndb.StructuredProperty(User)
    likes = ndb.IntegerProperty(default=0)
    dislikes = ndb.IntegerProperty(default=0)

class Story(ndb.Model):
    title = ndb.StringProperty()
    content = ndb.TextProperty()
    posted_by = ndb.StructuredProperty(User)
    comments = ndb.KeyProperty(Comment, repeated=True)

This code defines the User, Comment, and Story classes using Google’s ndb library. The User and Comment classes are entities, which means they’re part of Google’s Datastore. The Story class has an array of comments, which are stored as keys. This allows you to retrieve a Story and its associated Comments with a single query.

To retrieve a Story and its associated Comments, you could use code like this:

story = Story.get_by_id(story_id)
comments = ndb.get_multi(story.comments)

This code retrieves the Story by its ID, and then retrieves the associated Comments. Since the Comments are stored as keys, this can be done with a single query, which is much more efficient than querying for each Comment individually.

Alternative ways:

There are many ways to model data in NoSQL, and the best approach depends on your specific needs. Here are a few alternative approaches:

  • Use a graph database like Neo4j for highly connected data
  • Use a key-value store like Redis for caching frequently accessed data
  • Use a time-series database like InfluxDB for monitoring and analyzing time-series data
  • Use a document-oriented database like MongoDB for flexible, unstructured data storage

Recap

Modeling data in NoSQL can be a bit different from modeling data in traditional relational databases. The key is to denormalize your data and store redundant data across multiple documents or entities to make querying and updating data faster and easier. Use techniques like lazy loading and caching to improve performance, and consider using cloud services like Google Cloud Memorystore to optimize your application’s scalability.

Keep in mind that there is no one “right” way to model data in NoSQL. Experiment with different approaches to find the one that works best for your specific use case. ]]>
