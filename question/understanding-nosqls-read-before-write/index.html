Understanding NoSQL’s Read-Before-Write Learning Read-Before-Write in NoSQL Database
NoSQL databases, such as Cassandra, have gained a lot of popularity over the years due to their ability to handle huge amounts of data and concurrency with ease. One of the features that distinguish a NoSQL database from the traditional relational database is “Read-before-write.” In this Q&A Session, we will explore what read-before-write is, how it works, and its impact on Cassandra database performance.

What is Read-Before-Write?

Read-before-write is a feature that promotes checking the existing data before performing an operation in a database. This pattern is prevalent in traditional relational databases such as MySQL, Oracle, or PostgreSQL. In these databases, when updating data, the database engine performs a read operation to check the current state of the data before making updates.

On the other hand, a NoSQL database like Cassandra, encourages performing an update without checking the current state of the data. In other words, Cassandra writes data without any information about the current state of the database. This approach provides faster writes and, therefore, better performance.

How does Read-Before-Write impact Cassandra Performance?

Cassandra is known for its distributed design that offers massive scalability and high-performance reads and writes. By promoting a write-before-read approach, Cassandra can achieve sub-millisecond write latencies, unlike traditional databases that require hundreds of milliseconds for writes.

Adopting a Read-before-write strategy in Cassandra significantly impacts the database performance by introducing an overhead cost of reading data before writing, hence slowing down the write process. The read-before-write operations require more time to execute, thus increasing the overall latency of each operation. This could negatively impact the ability to meet the performance SLAs required to support real-time applications.

Check and Set (CAS) in Cassandra

To address the need to read and query the current state of data before updating it, Cassandra provides a Check and Set (CAS) mechanism that allows detecting concurrent updates to a row before committing the update. The mechanism works by requiring a condition to hold true before applying an update to the database.

The “Check and Set” operation is a two-phase commit mechanism that performs a read operation to check if the condition is met, then performs the write operation if the condition is true. The CAS operation ensures consistency and prevents concurrency issues such as race conditions, deadlocks, and starvation.

The syntax to perform CAS operation in Cassandra is:

UPDATE table_name SET column_name = value WHERE condition IF column_name = value;

The condition that is checked before applying the update is specified at the end of the UPDATE statement. In the above syntax, the column_name must have the expected value before the update is applied. If the value of column_name does not match the expected value, Cassandra will throw an error, and no update will be applied to the database.

Practical Examples of CAS in Cassandra

Consider an example of a table that stores the top scores of a game that has multiple players. Suppose we want to increment the score of a specific player by 10 if the score is currently less than 100. To achieve this, we can use the CAS mechanism:

UPDATE player_scores 
SET score = score + 10 
WHERE player_id = 'ABC' 
IF score < 100;

The operation above checks if the score of the player whose ID is ‘ABC’ is less than 100. If the score is less than 100, then the player’s score is incremented by 10, and the update is applied to the database.

Alternative ways to Read-before-write in Cassandra

While Cassandra discourages reading data before writing and recommends using the CAS mechanism instead, there are situations where read-before-write may be necessary. For instance, when dealing with data that must be unique, checking the data’s presence is a critical requirement.

In this scenario, one recommended solution is to use lightweight transactions (LWT), which is also referred to as a serializable isolation level. LWT is a type of atomic operation that provides unique read-before-write functionality in Cassandra.

The syntax for LWT is similar to the CAS mechanism, but it uses LIGHTWEIGHT_TRANSACTION keyword and is implemented using “IF EXISTS” and “IF NOT EXISTS” clauses, like this:

INSERT INTO player_scores (player_id, score) 
VALUES ('ABC', 100) 
IF NOT EXISTS;

The syntax above inserts a new row into the player_scores table if a row with the specified player_id does not already exist. LWT operations are more expensive as they require additional coordination and processing overhead to ensure consistency.

Recap

Read-before-write is a relational database concept that has a significant impact on performance when adopted in a NoSQL database. While it may be useful in some specific scenarios, Cassandra’s high-performance design philosophy prioritizes write-before-read. The Check and Set mechanism provides an alternative to concurrency control, ensuring strong consistency and preventing race conditions. To achieve better performance in Cassandra, explore other alternatives and implement best practices such as schema design, data modeling, and indexing.
