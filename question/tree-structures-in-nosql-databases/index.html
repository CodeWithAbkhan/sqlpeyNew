Tree Structures in NoSQL Databases How to store tree structures in a NoSQL database?
When developing applications that require storage for tree structures, it’s essential to know how to efficiently store and retrieve data from a database. In this Q&A Session, we’ll explore how to store tree structures in Google App Engine’s BigTable NoSQL database, specifically for a hobby project about collaboratively writing stories.

What’s the requirement for storing tree structures in a database?

Before we start thinking about how to store trees in a database, we need to know the requirements of the project that needs a tree-like structure. In this case, we’re developing an application that allows anyone to write a paragraph, which needs validation from two other people. More, the story should be able to branch at any paragraph, allowing another version of the story to continue in another direction.

For instance, let’s consider the following tree:

    2
   / 
  7   5
 /    
6   11  9
     
      4

In this case, we want to identify the unique storylines in the tree, which are (2, 7, 2), (2, 7, 6, 5), (2, 7, 6, 11), and (2, 5, 9, 4).

What are the common ways to represent trees in a database?

There are four common ways to represent trees in a database:

  • Adjacency list, where each node stores the ID of its parent.
  • Materialized path, where each node stores the path from the root to the node.
  • Nested sets, where each node has ’left’ and ‘right’ IDs, such that all child nodes are contained in that range.
  • Adjacency lists augmented with a root ID.

The choice of the representation depends on the requirements of the project. For our story writing application, we’ll use the materialized path strategy as it’s the default approach used by entity groups in App Engine and it aligns with what we’re trying to achieve.

What is the materialized path strategy?

The materialized path strategy involves creating a string field in each entity that stores the path from the root to the current node. For example, if the root node has id=1, and the current node has id=4, then the path would be “1.4”. If the current node has id=2, the path would be “1.2”.

Using our story example, let’s say we’ve created the following entities:

class Paragraph(ndb.Model):
    # ...
    path = ndb.StringProperty(default="")

p1 = Paragraph(parent=root_key, content="Once upon a time...")
p2 = Paragraph(parent=root_key, content="The end.")
p21 = Paragraph(parent=root_key, content="The great escape.")
p211 = Paragraph(parent=root_key, content="They jumped out of the window.")
p212 = Paragraph(parent=root_key, content="They climbed out of the door.")

Here’s how their paths would be represented:

p1.path == "1"
p2.path == "2"
p21.path == "2.1"
p211.path == "2.1.1"
p212.path == "2.1.2"

As we can see, the path for each paragraph identifies the unique storylines in the tree.

How can we retrieve all the paragraphs in a unique storyline?

Now that we’ve established the materialized path strategy, we can retrieve all the paragraphs in a unique storyline by querying the datastore with the following code:

class Paragraph(ndb.Model):
    # ...
    path = ndb.StringProperty(default="")

def get_storyline(path):
    query = Paragraph.query(Paragraph.path == path)
    paragraphs = query.fetch()
    return paragraphs

To retrieve all the paragraphs that belong to the storyline (2, 7, 2), we could call the following code:

get_storyline("2.7.2")

This will return all the paragraphs that belong to the storyline.

How can we efficiently write data using the materialized path strategy?

When using the materialized path strategy, updates can be costly as it involves updating the path of all child entities. Although, here are a few ways to efficiently write data using this strategy:

  • Batch operations: Batch operations can be utilized to reduce the number of writes to the datastore. In App Engine, the ndb library offers atomi
  • Asynchronous updates: Asynchronous updates can be utilized to remove the bottleneck caused by a large number of writes to the datastore. In App Engine, the ndb library offers async operations.
  • Caching: Caching can be utilized to reduce the number of reads from the datastore. In App Engine, the memcache API offers this feature.

Recap

In recap, we’ve explored how to store tree structures in a database by using the materialized path strategy. We’ve also discussed how to efficiently retrieve data and write data using this strategy. ]]>
