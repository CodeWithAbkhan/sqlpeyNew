NOSQL: Rethinking Document Databases: What Am I Missing? A Deep Dive into Document Databases: Learning the Benefits and Limitations

Introduction

With the rise of NoSql movement, document databases, such as MongoDB and RavenDB, have gained popularity due to their scalability, flexibility, and performance. Yet, implementing document databases can be challenging for those accustomed to relational databases, as it involves a different data structure and data modelling approach. In this Q&A Session, we will explore the benefits and limitations of document databases and address some common misknowings.

Benefits of Document Databases

One of the main benefits of document databases is their scalability. Unlike traditional SQL databases, where scaling can often require complex partitioning and clustering, document databases typically use a distributed architecture, where data is distributed across nodes in a cluster, allowing for easy scaling. Because data is stored in a document-based format, document databases also have the advantage of being schema-less, which means that you can add or remove fields from a document without having to update the entire schema.

Document databases also have a flexible data model, which can be useful when dealing with unstructured, semi-structured or constantly changing data. Since databases like MongoDB use JSON documents, developers can store complex data structures in a single document instead of multiple tables, also allowing for nested structures for more complex data types. This can lead to a more natural data representation, making it easy for developers to work with complex data.

Learning Data Modelling in Document Databases

One common misknowing when working with document databases is how to handle relationships between data. In a relational database, tables can be linked using keys like foreign keys that refer to an ID in another table. In a document database, documents can also have relationships, but unlike relational databases, they’re typically modelled as embedded documents or using references.

For instance, if you have an e-commerce application, you may have products and categories. In a relational database, you might model this with a category table and a product table as well as a foreign key on the product table referencing the related category.

CREATE TABLE categories (
   id SERIAL PRIMARY KEY,
   name TEXT NOT NULL UNIQUE,
   description TEXT
);
 
CREATE TABLE products (
   id SERIAL PRIMARY KEY,
   name TEXT NOT NULL,
   description TEXT,
   category_id INTEGER REFERENCES categories(id),
   price NUMERIC(10, 2),
   image_url TEXT,
   stock INTEGER,
   created_at TIMESTAMP DEFAULT NOW()
);

In a document database, you may have one collection for products and store the category name within the product document either as an embedded subdocument, or a reference depending on the use case assumptions.

{
   "_id": ObjectId("610d598bcf0632c9b1626458"),
   "name": "MacBook Pro 2020",
   "description": "The MacBook Pro is a sleek professional laptop.",
   "category": {
      "_id": ObjectId("610d598bcf0632c9b1626457"),
      "name": "Laptops"
   },
   "price": 1299.99,
   "image_url": "/images/macbook-pro.jpg",
   "stock": 50,
   "created_at": ISODate("2021-08-01T13:00:00Z")
}

Note that by embedding the category document within the product document, we avoid a join operation, giving us better performance at the cost of storing the category data repeatedly. Another benefit of embedding is that it’s easier to visualize the data structure and query the data without needing a join query, which can be beneficial for certain use case patterns.

Limitations of Document Databases

While document databases offer some benefits over relational databases, there are also some limitations to consider. For example, document databases such as MongoDB are less optimal when dealing with transactions, as there are no inherent operations to ensure atomicity, consistency, isolation or durability (ACID). Also, unlike relational databases, queries in document databases can sometimes be more challenging to write because of the nested and sometimes deeply nested documents; a little denormalization solves the problem.

Practical Examples

Let’s consider a practical use case to illustrate how document databases can be used in a real-world scenario. Say we have an app collecting user data, we might define a schema like this:

{
   "_id": ObjectId("610d598bcf0632c9b1626459"),
   "name": "John Doe",
   "email": "johndoe@example.com",
   "password": "dwd989fijd9",
   "last_login": ISODate("2021-08-01T12:00:00Z"),
   "address": {
      "street": "1025 Rua Gabreil McGregor",
      "city": "Lagos",
      "zipcode": "12345",
      "country": "Nigeria"
   },
   "orders": [
      {
         "item": "MacBook Pro 2020",
         "quantity": 1,
         "price": 1299.99
      },
      {
         "item": "Beats Solo Headphones",
         "quantity": 2,
         "price": 179.99
      }
   ]
}

The above schema contains nested documents to represent the user’s address and orders, while also providing easy access to crucial information such as the last login date. With a document structure like this, it’s easy to index, query and update the data, making it a well-suited design for document databases.

Alternative Ways

One alternative data modelling strategy is a hybrid approach, where documents are designed to leverage the strengths of both relational databases and document databases. Instead of starting with a one-size-fits-all approach, hybrid models can be created, which leverages the benefits of both approaches.

Summary

Document databases offer several benefits over traditional SQL databases, including scalability and flexible data models. While working with a document database comes with its own set of challenges, especially when knowing data modelling and relationships between data, they can be well-suited for some use cases and can lead to faster development cycles and better performance. When choosing a database strategy, hybrid data models can be designed utilizing both benefits. ]]>
