NOSQL: Creating a 3-Field Composite Primary Key for Unique Items in DynamoDB
Summary:

The post discusses selecting a good Partition Key (PK) and a Sort Key (SK) for a DynamoDB table that will store invoice line items. The post proposes a different design based on the access patterns required by the application. The two access patterns are getting all invoices for a company and getting a complete invoice for a company. The post reminds us of the characteristics of the Primary Key, Partition Key, and Sort Key, and highlights that the Partition Key is used as input to the hashing function that determines the partition of the items. Lastly, the post recommends using global secondary indexes to optimize the access patterns.

Q&A:

Q: What are the two access patterns required by the application?
A: The two access patterns are getting all invoices for a company and getting a complete invoice for a company.

Q: What is a good Primary Key for the DynamoDB table?
A: A good Primary Key consists of a Partition Key and a Sort Key. The Partition Key should be the CompanyCode, and the Sort Key should be the InvoiceNumber.

Q: What are the characteristics of the Partition Key?
A: The Partition Key is used as input to the hashing function that determines the partition of the items. This means that items with the same Partition Key will be stored in the same partition.

Q: What is the purpose of the Sort Key?
A: The Sort Key allows us to model one-to-many relationships in DynamoDB by ordering the items with the same Partition Key.

Q: What kind of indexes should be used to optimize the access patterns?
A: Global secondary indexes should be used to optimize the access patterns.

Explanation:

The code defines a params object that contains the AttributeDefinitions, KeySchema, GlobalSecondaryIndexes, and ProvisionedThroughput attributes for creating a DynamoDB table that will store invoice line items.

The AttributeDefinitions attribute defines the attributes and their types that will be used as the Primary Key and Secondary Indexes for the table.

The KeySchema attribute defines the Primary Key for the table, which consists of the CompanyCode attribute as the Partition Key and the InvoiceNumber attribute as the Sort Key.

The GlobalSecondaryIndexes attribute defines a global secondary index that will optimize the access pattern of getting all invoices for a company. The index is named InvoiceIndex, and it has the InvoiceNumber attribute as its Partition Key. The Projection attribute specifies that all attributes of the table should be included in the index, and the ProvisionedThroughput attribute specifies the read and write capacity units for the index.

The ProvisionedThroughput attribute specifies the read and write capacity units for the table.

The createTable function is then called with the params object to create the DynamoDB table.

Alternative Ways:

One alternative way to optimize the access pattern of getting all invoices for a company is to use a sparse secondary index. A sparse secondary index is an index that only contains items that have a specific attribute defined. For example, we can create an index with the CompanyCode attribute as its Partition Key and the LineItemId attribute as its Sort Key, and specify a condition expression that checks for the existence of the InvoiceNumber attribute. This will create an index that only contains items that have the InvoiceNumber attribute defined, which will help optimize the access pattern of getting all invoices for a company. Although, this approach requires us to add a condition expression to every query on the index, which may increase the complexity of the application.
