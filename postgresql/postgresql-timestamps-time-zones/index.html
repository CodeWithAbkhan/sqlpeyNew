“PostgreSQL Timestamps: Time Zones Explained”

PostgreSQL offers two distinct timestamp data types: timestamp with time zone (often abbreviated as timestamptz) and timestamp without time zone (abbreviated as timestamp). timestamptz is generally considered the preferred choice for managing date and time information due to its robust time zone handling capabilities.

Internal Storage and Epoch:

Internally, both timestamp types use 8 bytes for storage, representing microseconds from the PostgreSQL epoch, which is January 1, 2000, 00:00:00 UTC. PostgreSQL also natively understands Unix time, which counts seconds from the Unix epoch (January 1, 1970, 00:00:00 UTC). This is utilized in functions like to_timestamp(double precision) and EXTRACT(EPOCH FROM timestamptz).

The source code indicates that timestamps are stored as int64 values with microsecond precision. This precision allows for up to 6 fractional digits for seconds.

/* Julian-date equivalents of Day 0 in Unix and Postgres reckoning */
#define UNIX_EPOCH_JDATE        2440588 /* == date2j(1970, 1, 1) */
#define POSTGRES_EPOCH_JDATE    2451545 /* == date2j(2000, 1, 1) */

timestamp (Without Time Zone):

When you use the timestamp type, PostgreSQL ignores any time zone modifiers provided in input literals. No shifts occur during display. While this might suffice for applications operating within a single time zone, it can lead to misinterpretations if multiple time zones are involved, as the value and its display remain constant regardless of the assumed time zone.

timestamptz (With Time Zone):

The timestamptz type handles time zones more effectively. As stated in the PostgreSQL manual, “For timestamp with time zone, the internally stored value is always in UTC (Universal Coordinated Time…).” The time zone itself is not stored; instead, an input time zone modifier is used to calculate the corresponding UTC timestamp. This UTC value is then stored. When displaying the timestamp, it’s presented according to the current session’s time zone setting. If an input literal lacks an offset, the current session’s time zone is assumed.

This means all calculations are performed using UTC values, ensuring consistency. If your application might involve multiple time zones or if there’s any potential for ambiguity, timestamptz is the recommended choice.

Clients like psql, pgAdmin, or applications using libpq (such as Ruby with the pg gem) will display the offset for the current time zone or a specified time zone. The underlying point in time remains the same, only the display format varies. The manual elaborates: “All timezone-aware dates and times are stored internally in UTC. They are converted to local time in the zone specified by the TimeZone configuration parameter before being displayed to the client.”

Example in psql:

db=# SELECT timestamptz '2012-03-05 20:00+03';
      timestamptz

## Solutions
2012-03-05 18:00:00+01

In this example, the input literal with a +03 offset is converted to the UTC timestamp 2012-03-05 17:00:00. The output is displayed according to the current session’s time zone setting, which in this case is “Vienna/Austria” with a +01 offset during winter. This illustrates that PostgreSQL stores the value consistently (as UTC) and adjusts the display based on the session’s time zone.

Using AT TIME ZONE:

The AT TIME ZONE construct allows you to project timestamp values to a specific time zone. It facilitates conversions between timestamptz and timestamp.

To obtain the UTC timestamp 2012-03-05 17:00:00 as a timestamptz:

SELECT timestamp '2012-03-05 17:00:00' AT TIME ZONE 'UTC';

This is functionally equivalent to:

SELECT timestamptz '2012-03-05 17:00:00 UTC';

To display the same point in time as an EST (Eastern Standard Time) timestamp:

SELECT timestamp '2012-03-05 17:00:00' AT TIME ZONE 'UTC' AT TIME ZONE 'EST';

Here, the first AT TIME ZONE 'UTC' interprets the timestamp value as a UTC timestamp, returning a timestamptz. The second AT TIME ZONE 'EST' converts this timestamptz to a timestamp as it would appear on a clock in the ‘EST’ time zone at that specific moment.

Illustrative Examples:

SELECT ts AT TIME ZONE 'UTC'
FROM  (
   VALUES
      (1, timestamptz '2012-03-05 17:00:00+0')
    , (2, timestamptz '2012-03-05 18:00:00+1')
    , (3, timestamptz '2012-03-05 17:00:00 UTC')
    , (4, timestamp   '2012-03-05 11:00:00' AT TIME ZONE '+6')
    , (5, timestamp   '2012-03-05 17:00:00' AT TIME ZONE 'UTC')
    , (6, timestamp   '2012-03-05 07:00:00' AT TIME ZONE 'US/Hawaii')  -- Aware of DST
    , (7, timestamptz '2012-03-05 07:00:00 US/Hawaii')                  -- Aware of DST
    , (8, timestamp   '2012-03-05 07:00:00' AT TIME ZONE 'HST')        -- Abbreviation, less reliable for DST
    , (9, timestamp   '2012-03-05 18:00:00+1')  -- Potential trap: ignores offset for timestamp input
      ) t(id, ts);

This query returns multiple rows, all representing the UTC timestamp 2012-03-05 17:00:00. Rows 6-8 demonstrate the use of time zone names (US/Hawaii) and abbreviations (HST), highlighting that time zone names are generally preferred as they are aware of Daylight Saving Time (DST) rules and historical shifts, unlike abbreviations which are fixed offsets and might require different ones for summer/standard time. Row 9 serves as a cautionary example where the time zone offset in a timestamp literal is ignored, potentially leading to unexpected results if the session’s time zone differs from what was intended.

Handling User-Specified Time Zones:

  • Storing UTC: If you need to store a time without explicit time zone conversions or storage of the time zone itself, use timestamptz and ensure you enter the time in UTC.

  • Filtering by User’s Local Time: To query records based on a user’s local time, you can leverage now() and specify the time zone:

    -- For absolute global time (UTC)
SELECT * FROM tbl WHERE time_col > (now() AT TIME ZONE 'UTC')::time;

-- For time according to the local clock of the current session
SELECT * FROM tbl WHERE time_col > now()::time;

Rails and Time Zone Handling:

In a Ruby on Rails application, you can set the default time zone and handle user-specific time zones:

# In config/application.rb
config.time_zone = 'UTC'

Then, to display a created_at timestamp in the user’s local time zone:

post.created_at.in_time_zone(current_user.timezone)

Ensure current_user.timezone contains a valid time zone name to avoid ArgumentError: Invalid Timezone.

Alternative Approach in Rails:

An alternative for filtering in Rails is to use the .iso8601 method, which passes the date string directly to PostgreSQL, preventing Rails from automatically converting it to the server’s time zone:

.where("created_at > ?", YOUR_DATE_IN_THE_TIMEZONE.iso8601)

This bypasses Rails’ default time zone conversions, ensuring the date is interpreted as intended.

Angular/TypeScript/Node.js API/PostgreSQL Environment:

For environments involving Angular, TypeScript, Node.js, and PostgreSQL, precise handling of timestamps across the stack is crucial. Using UTC as the base for storage and converting to client-specific time zones for display is a robust strategy. Libraries like moment-timezone or native Intl.DateTimeFormat in JavaScript can assist with client-side time zone conversions.

FAQs on PostgreSQL Timestamps

Q: What is the difference between timestamp and timestamptz in PostgreSQL

ANS: timestamp stores date and time without time zone information, ignoring any input time zone modifiers. timestamptz stores date and time with time zone information, converting input to UTC for internal storage and displaying it according to the session’s time zone. timestamptz is preferred for applications involving multiple time zones.

Q: How does PostgreSQL store timestamps internally

ANS: PostgreSQL stores both timestamp and timestamptz types as 8-byte integer values representing microseconds from the PostgreSQL epoch (2000-01-01 00:00:00 UTC). For timestamptz, this stored value is always in UTC.

Q: How can I convert a timestamp to a specific time zone in PostgreSQL

ANS: You can use the AT TIME ZONE construct. For example, SELECT '2012-03-05 17:00:00'::timestamp AT TIME ZONE 'UTC' AT TIME ZONE 'EST'; converts a timestamp to UTC and then displays it in EST.

Q: When should I use timestamptz versus timestamp

ANS: Use timestamptz whenever your application might involve users or data from different time zones, or when accurate representation of specific moments in time globally is critical. Use timestamp only if you are certain that all operations and users are within a single, fixed time zone and time zone conversions are not required.

Q: How does PostgreSQL handle Daylight Saving Time (DST)

ANS: Time zone names like US/Hawaii in timestamptz are aware of DST rules and historical shifts. Time zone abbreviations like HST are fixed offsets and may not correctly account for DST, making time zone names a more reliable choice for accurate time representation.
