“Fixing Postgres Connection Refused in Dockerized Spring Apps”

When deploying a Spring application alongside a PostgreSQL database using Docker and docker-compose, developers frequently encounter an error indicating the connection to localhost:5432 is refused. This issue arises because each Docker container operates within its own isolated network namespace. Consequently, localhost inside the application container refers to itself, not the host machine or the separate database container.

How does one correctly configure the Spring application’s data source URL to resolve to the PostgreSQL container service name within the docker-compose network?

Primary Solution: Utilizing Service Names for Inter-Container Communication

The most direct approach involves substituting the problematic localhost reference with the service name defined in your docker-compose.yml file. Docker Compose automatically sets up DNS resolution for services within the same network, allowing containers to address each other by their service names.

If your PostgreSQL service is named db in docker-compose.yml, the Java application must point to that service name.

Configuration Adjustment Example

In your Spring configuration file (e.g., application.properties):

Before (Incorrect for Docker networking):

spring.datasource.url=jdbc:postgresql://localhost:5432/sample

After (Corrected using service name ‘db’):

spring.datasource.url=jdbc:postgresql://db:5432/sample

This modification ensures that the Spring application resolves db to the correct internal IP address of the PostgreSQL container.

Leveraging Environment Variables in docker-compose

Another robust method involves using environment variables defined in docker-compose.yml to dynamically override the connection string, keeping sensitive details or environment-specific configurations external to the application code or properties file.

For instance, you can define the database host via an environment variable, which the Spring application reads (often via Spring Boot’s external configuration mechanism).

Consider this setup where the database host environment variable SPRING_DATASOURCE_URL is injected:

docker-compose.yml Snippet:

version: "3.8"
services:
  springapp:
    build: .
    container_name: springapp
    # Overrides the URL defined in application.properties
    environment:
      - SPRING_DATASOURCE_URL=jdbc:postgresql://db:5432/testdb 
    ports:
      - "8080:8080"
    depends_on:
      - db
  db:
    image: postgres:latest
    container_name: db
    environment:
      - POSTGRES_USER=postgres
      - POSTGRES_PASSWORD=postgres
      - POSTGRES_DB=testdb
    volumes:
      - pgdata:/var/lib/postgresql/data
volumes:
  pgdata:

This overrides the local setting, forcing the application to connect to db:5432.

Building Images Directly with docker-compose

If you are currently building your application image manually and then referencing it in docker-compose, you can streamline this process. Instead of using the image: key for your application service, use the build: key pointing to the directory containing your Dockerfile.

Original docker-compose.yml fragment:

web:
  image: myuser/manager:latest

Optimized docker-compose.yml fragment:

web:
  build: . # Instructs docker-compose to build the image from the current directory's Dockerfile

Alternative: Using Dockerfile ENV to Parameterize Connection Host

For maximum flexibility, you can define an environment variable within the Dockerfile itself and use it in the entry point command to construct the JDBC URL dynamically at runtime.

Example Dockerfile:

FROM openjdk:17-jdk-slim
EXPOSE 8080

# Define a default host value, which can be overridden later
ENV DB_HOST_ALIAS=localhost 

ADD target/my-app.jar app.jar
ENTRYPOINT exec java $JAVA_OPTS -jar app.jar --spring.datasource.url=jdbc:postgresql://$DB_HOST_ALIAS:5432/sample

Corresponding docker-compose.yml Override: Here, we override the DB_HOST_ALIAS to point to the PostgreSQL service name:

services:
  springapp:
    build: .
    environment:
      - DB_HOST_ALIAS=db # This replaces 'localhost' defined in the Dockerfile
    # ... other configurations

Example of Complete Configuration Review

A typical setup that avoids the localhost error looks like this, ensuring both services rely on service names:

application.properties (Spring side):

spring.datasource.url=jdbc:postgresql://db:5432/testdb
spring.datasource.driver-class-name=org.postgresql.Driver
spring.datasource.username=postgres
spring.datasource.password=postgres
spring.jpa.properties.hibernate.dialect=org.hibernate.dialect.PostgreSQLDial Dialect
spring.jpa.hibernate.ddl-auto=update

docker-compose.yml:

version: "3.8"
services:
  springapp:
    build: .
    container_name: springapp
    ports:
      - "8000:8080"
    restart: always
    depends_on:
      - db
  db:
    image: postgres:latest
    container_name: db
    environment:
      - POSTGRES_USER=postgres
      - POSTGRES_PASSWORD=postgres
      - POSTGRES_DB=testdb
    ports:
      - "5000:5432" # Exposing 5432 to host for external debugging, optional
    volumes:
      - pgdata:/var/lib/postgresql/data
    restart: always
volumes:
  pgdata:

By using the service name db instead of localhost in the Spring JDBC URL, the connection succeeds across containers. If you are running the database locally outside of Docker, then localhost or the host machine’s IP is correct, but this behavior changes entirely when running both services within the Docker network.

FAQs on Fixing Postgres Connection Refused in Dockerized Spring Apps

Q: Why does localhost fail when connecting Spring to Postgres in Docker

ANS: In a Docker Compose setup, ’localhost’ within the application container refers only to that container itself, not the host machine or other containers like the PostgreSQL service. You must use the name of the database service defined in docker-compose.yml.

Q: What happens if I keep using localhost in my Spring config with docker-compose

ANS: The application attempts to connect to a PostgreSQL instance running on port 5432 inside the application container, which likely doesn’t exist, leading to a connection refused error.

Q: Is changing the URL the only step required for docker-compose

ANS: Usually, yes, if the database container is correctly configured and depends on the application container. Ensuring the application service depends_on the database service helps ensure the database starts first.

Q: How do I connect to a Postgres container running on a different port on my host machine

ANS: The port mapping in docker-compose (e.g., 5000:5432) only affects external access from the host. Inside the network, the application must always use the internal port, 5432, and the service name (e.g., jdbc:postgresql://db:5432/testdb).
