“PostgreSQL Space Optimization: Column Ordering and Alignment Padding”

How can database architects and administrators reduce physical storage consumption in PostgreSQL by strategically ordering columns within a table definition, specifically targeting alignment padding? This optimization technique, sometimes dubbed “Column Tetris,” exploits how PostgreSQL structures data on disk based on type alignment requirements.

The Impact of Alignment Padding

Every data type necessitates specific alignment for efficient memory access. Any space left between columns to satisfy these alignment needs represents wasted physical disk space.

Consider a scenario where smaller types are interspersed with larger ones, leading to substantial padding overhead per row.

Example of Space Waste (Unoptimized Structure):

CREATE TABLE example_waste (
  col_e SMALLINT, -- Requires 6 bytes padding if MAXALIGN is 8
  col_a BIGINT,
  col_f SMALLINT, -- Requires 6 bytes padding if MAXALIGN is 8
  col_b BIGINT,
  col_g SMALLINT, -- Requires 6 bytes padding if MAXALIGN is 8
  col_c BIGINT,
  col_h SMALLINT, -- Requires 6 bytes padding if MAXALIGN is 8
  col_d BIGINT
);

In the structure above, if int2 (2 bytes) is followed by int8 (8 bytes) on a system where alignment dictates 8-byte boundaries, significant padding occurs after each int2. This structure could waste considerable space—potentially 24 bytes per row in this extreme setup.

Alternative Structure for Space Conservation:

The optimized approach groups types by size, typically placing the largest types first to minimize internal gaps.

CREATE TABLE example_savings (
  col_a BIGINT,
  col_b BIGINT,
  col_c BIGINT,
  col_d BIGINT,
  col_e SMALLINT, -- 4 SMALLINTs (8 bytes total) align perfectly with MAXALIGN (8)
  col_f SMALLINT,
  col_g SMALLINT,
  col_h SMALLINT  -- No trailing padding needed if the row size aligns well.
);

By following this principle—ordering 8-byte columns first, then 4-byte, 2-byte, and finally 1-byte columns—storage efficiency increases. Types like BOOLEAN or UUID often require no special alignment padding.

Variable Length Types (varlena) and Alignment

Variable-length types such as TEXT, VARCHAR, and JSONB present a unique situation. Nominally, they require INT alignment (4 bytes on most platforms). However, PostgreSQL may employ a “packed” disk format for smaller instances, overriding standard alignment rules.

When the compressed or packed datum, including a single leading length byte, exceeds 127 bytes, storage reverts to four leading bytes, enforcing strict INT alignment. This mechanism is largely managed by the TOAST system.

While “column tetris” can save a few bytes per row, this practice is generally unnecessary unless dealing with tables containing billions of rows, where the accumulated savings become significant (potentially gigabytes).

Determining Actual Row and Column Size

How can one verify the storage impact of their column layout? PostgreSQL provides diagnostic functions:

  • pg_column_size(value): Reports the space used by a specific value, sometimes showing RAM format size for constants which can differ from on-disk storage for packed/toasted types.
  • The PostgreSQL documentation offers insights into Database Page Layout .

Tuple Overhead: The Constant Cost

Every row (tuple) carries fixed overhead that is not influenced by column ordering:

  1. Item Identifier: 4 bytes per row.

  2. Tuple Header: Typically 23 bytes, plus an optional null bitmap and Object ID field.

  3. Header Padding: Padding between the header and user data must align to MAXALIGN. On 64-bit systems, this is usually 8 bytes. To ascertain the exact MAXALIGN for your server, execute:

    ./pg_controldata /path/to/my/dbcluster

    The user data starts at the t_hoff offset, which must be a multiple of MAXALIGN.

Handling NULLs and Arrays

  • NULL Values: Columns defined as NOT NULL should ideally be placed toward the beginning of the row definition. Columns that frequently contain NULL values should be placed toward the end. While NULL presence is tracked in the null bitmap (minimal cost), positioning columns further back increases the minor cost associated with computing the offset for subsequent columns.
  • Array Types: Using array types (e.g., integer[]) introduces an additional 24 bytes of overhead for the array structure itself, plus space for the elements, often negating any space-saving attempts.

Programmatic Analysis for Optimal Ordering

Instead of manual calculation, system catalogs can reveal the required ordering based on existing table definitions.

Querying Metadata for Recommended Order (By Type Length):

This query retrieves column names, types, alignment, and length metadata for a specified table (my_table), ordering results by type length descending—a heuristic for optimal packing.

SELECT 
    a.attname AS column_name, 
    t.typname AS data_type, 
    t.typalign, 
    t.typlen
FROM 
    pg_class c
JOIN 
    pg_attribute a ON (a.attrelid = c.oid)
JOIN 
    pg_type t ON (t.oid = a.atttypid)
WHERE 
    c.relname = 'my_table'
    AND a.attnum > 0 -- Exclude system columns
ORDER BY 
    t.typlen DESC;

Alternative: Creating a Versatile Metadata View:

A more robust approach involves creating a persistent view to inspect any table’s column properties, including storage type, ordered by length and alignment:

CREATE OR REPLACE VIEW table_packing_analyzer AS
    SELECT 
        n.nspname AS schema_name, 
        c.relname AS table_name,
        a.attname AS column_name, 
        t.typname AS data_type, 
        t.typstorage, 
        t.typalign, 
        t.typlen
    FROM 
        pg_class c
    JOIN 
        pg_namespace n ON (n.oid = c.relnamespace)
    JOIN 
        pg_attribute a ON (a.attrelid = c.oid)
    JOIN 
        pg_type t ON (t.oid = a.atttypid)
    WHERE 
        a.attnum >= 0 -- Include system columns if necessary, change to > 0 for user data only
    ORDER BY 
        n.nspname ASC, 
        c.relname ASC,
        t.typlen DESC, 
        t.typalign DESC, 
        a.attnum ASC;

-- Usage Example:
SELECT * FROM table_packing_analyzer WHERE table_name = 'users_data';

External tools, such as the NikolayS/postgres_dba repository, offer specific scripts (p1 command) designed to analyze and suggest optimal column reordering automatically across an entire database.

FAQs on PostgreSQL Column Alignment Optimization

Q: What is the primary benefit of column ordering in PostgreSQL

ANS: The primary benefit is minimizing wasted space caused by alignment padding that occurs between data types of different sizes within a single row structure.

Q: Does reordering columns affect NULL bitmap storage

ANS: The position of NULL values slightly impacts the cost of calculating offsets for subsequent columns, but NULL values themselves are managed via a specific null bitmap in the header, independent of the column’s position for direct NULL checking.

Q: How do I find the MAXALIGN value for my PostgreSQL instance

ANS: You can determine the MAXALIGN value by executing the ./pg_controldata /path/to/my/dbcluster command within your PostgreSQL binary directory.

Q: Should I use arrays to store homogenous numeric data

ANS: Generally, no. Array types introduce significant fixed overhead (around 24 bytes) plus element storage, usually resulting in less space efficiency than separate columns, even with minor padding issues.
