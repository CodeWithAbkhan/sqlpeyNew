“PostgreSQL Upsert: Efficiently Insert or Update Records”

When managing data in PostgreSQL, you often encounter scenarios where you need to insert a new record if it doesn’t exist, or update it if it already does. This operation, commonly known as “upsert,” can be achieved through various methods, depending on your PostgreSQL version and specific requirements. This post delves into effective strategies for implementing upserts, ensuring data integrity and efficiency.

PostgreSQL 9.5 and Newer: INSERT ... ON CONFLICT

PostgreSQL versions 9.5 and later offer a built-in, highly efficient mechanism for upsert operations: INSERT ... ON CONFLICT. This statement allows you to specify actions to take when a unique constraint violation occurs during an INSERT operation.

Key Features:

  • ON CONFLICT (key) DO UPDATE: Updates existing rows when a conflict is detected on the specified key.
  • ON CONFLICT (key) DO NOTHING: Skips the insert if a conflict is found.
  • Conflict Target: You can specify the conflict target using columns or a constraint name.

Limitations:

  • The columns used for conflict detection must be part of a single unique constraint.
  • For more complex scenarios, such as updating based on multiple conflicting columns or performing conditional merges, the MERGE command is a powerful alternative.

Example: Basic ON CONFLICT Usage

Here’s how you can perform an upsert using ON CONFLICT with different actions:

-- Insert a new record or do nothing if 'id' already exists
INSERT INTO dummy_table(id, name, size)
VALUES (1, 'New Name', 3)
ON CONFLICT DO NOTHING;

-- Insert a new record or update 'name' and 'size' if 'id' already exists
INSERT INTO dummy_table(id, name, size)
VALUES (1, 'Updated Name', 5)
ON CONFLICT(id)
DO UPDATE SET name = EXCLUDED.name, size = EXCLUDED.size;

-- Insert a new record or update 'name' if the constraint 'dummy_pkey' is violated
INSERT INTO dummy_table(id, name, size)
VALUES (1, 'Another Name', 7)
ON CONFLICT ON CONSTRAINT dummy_pkey
DO UPDATE SET name = EXCLUDED.name;

PostgreSQL 15 and Newer: MERGE Command

For more advanced conditional logic and bulk operations, PostgreSQL version 15 introduced the MERGE command, which provides even greater flexibility than ON CONFLICT.

Capabilities:

  • Conditional Logic: Allows WHEN MATCHED and WHEN NOT MATCHED clauses to define actions for existing and new rows.
  • Bulk Operations: Efficiently handles inserting, updating, or deleting rows based on join conditions.

Example: MERGE Statement

The MERGE statement is ideal for synchronizing data from a source table or values to a target table:

MERGE INTO customer_accounts AS ca
USING recent_transactions AS t
ON t.customer_id = ca.customer_id
WHEN MATCHED THEN
  UPDATE SET balance = balance + t.transaction_value
WHEN NOT MATCHED THEN
  INSERT (customer_id, balance)
  VALUES (t.customer_id, t.transaction_value);

PostgreSQL 9.4 and Older: Strategies Without Native Upsert

In versions prior to 9.5, PostgreSQL lacks direct upsert functionality, making it challenging to implement efficiently, especially under concurrent access. The primary approaches involve either handling individual row operations within a retry loop or performing a bulk merge after locking the table.

Strategy 1: Individual Row Retry Loop

This approach is suitable when multiple connections are attempting inserts concurrently. It relies on attempting an INSERT, and if a unique constraint violation occurs, performing an UPDATE. Careful handling of race conditions and potential rollbacks is crucial.

Caveats:

  • Naive implementations can lead to lost updates or incomplete merges.
  • Transactions should be structured to re-check conditions or handle duplicate key errors.
  • This method can be inefficient for large datasets.

Example of a Pitfall (Do Not Use):

-- THIS IS A DEMONSTRATION OF A FLAWED APPROACH. DO NOT REPLICATE.
BEGIN;
UPDATE test_table SET some_data = 'blah' WHERE id = 2;
INSERT INTO test_table (id, some_data)
SELECT 2, 'blah' WHERE NOT EXISTS (SELECT 1 FROM test_table WHERE test_table.id = 2);
COMMIT;

A More Robust (but still potentially inefficient) Transactional Approach:

This uses a DO block with an exception handler for unique_violation.

DO $$
BEGIN
  INSERT INTO test_table(id, some_data) VALUES (2, 'Joe');
EXCEPTION WHEN unique_violation THEN
  UPDATE test_table SET some_data = 'Joe' WHERE id = 2;
END $$;

Important Note: This transactional method is most effective when there are no deletions occurring concurrently and is generally less efficient than newer PostgreSQL features.

Strategy 2: Bulk Upsert with Table Locking

For bulk operations, this method is significantly more efficient. It involves creating a temporary table for new data, locking the target table, and then performing UPDATE and INSERT operations based on the temporary data.

Process:

  1. Create a temporary table: To hold the incoming data.
  2. Load new data: Insert or copy new records into the temporary table.
  3. Lock the target table: Use LOCK TABLE ... IN EXCLUSIVE MODE to prevent concurrent modifications to the target. This allows SELECT but blocks writes.
  4. Update existing records: Execute an UPDATE ... FROM statement using the temporary table.
  5. Insert new records: Perform an INSERT ... SELECT for rows present in the temporary table but not in the target.
  6. Commit: Release the lock and finalize the transaction.

Example:

BEGIN;

CREATE TEMPORARY TABLE new_values (id integer, some_data text);

INSERT INTO new_values (id, some_data) VALUES (2, 'Joe'), (3, 'Alan');

LOCK TABLE test_table IN EXCLUSIVE MODE;

UPDATE test_table
SET some_data = new_values.some_data
FROM new_values
WHERE new_values.id = test_table.id;

INSERT INTO test_table
SELECT new_values.id, new_values.some_data
FROM new_values
LEFT OUTER JOIN test_table ON (test_table.id = new_values.id)
WHERE test_table.id IS NULL;

COMMIT;

Strategy 3: WITH Clause for Conditional Inserts/Updates

This approach uses a Common Table Expression (CTE) to first attempt an update and then conditionally insert if no rows were updated. This can be effective for single inserts on older PostgreSQL versions.

Example (PostgreSQL 9.3):

WITH updated AS (
  UPDATE test_table SET some_data = 'Joe' WHERE id = 2
  RETURNING id
),
inserted AS (
  SELECT '2', 'Joe' WHERE NOT EXISTS (SELECT * FROM updated)
)
INSERT INTO test_table(id, some_data) SELECT * FROM inserted;

SQLAlchemy Integration

For Python developers using SQLAlchemy with PostgreSQL, the library provides convenient methods to leverage ON CONFLICT (for >= 9.5) and manage upserts.

Example using on_conflict_do_update:

from sqlalchemy.dialects.postgresql import insert

# Assuming 'my_table' is a SQLAlchemy mapped class or Table object
# Assuming 'conn' is an active database connection

stmt = insert(my_table).values(
    user_email='test@example.com',
    data='inserted data'
)
stmt = stmt.on_conflict_do_update(
    index_elements=[my_table.c.user_email],
    index_where=my_table.c.user_email.like('%@example.com'),
    set_=dict(data=stmt.excluded.data)
)
conn.execute(stmt)

SQLAlchemy also offers advanced patterns for bulk upserts with error handling and retries, useful for complex applications.

FAQs on PostgreSQL Upsert Strategies

Q: What is the primary benefit of using ON CONFLICT in PostgreSQL 9.5+

ANS: The ON CONFLICT clause provides a native, efficient, and robust way to handle “upsert” operations directly within SQL, simplifying data manipulation and improving performance compared to manual retry loops or table locking methods used in older versions.

Q: When should I consider using the MERGE statement instead of ON CONFLICT

ANS: The MERGE statement is beneficial for more complex conditional logic, such as when you need to perform different actions (INSERT, UPDATE, DELETE) based on whether a row matches a condition, or when synchronizing data between multiple tables with intricate join criteria. It offers greater control than ON CONFLICT for complex data integration tasks.

Q: Are there significant performance differences between ON CONFLICT and MERGE

ANS: Generally, ON CONFLICT is optimized for the specific “insert or update” scenario based on unique constraints. MERGE is more versatile and can handle a broader range of conditional logic, which might introduce a slight overhead for simple upserts but offers superior performance for complex multi-way merges.

Q: What are the main challenges when performing upserts in PostgreSQL versions older than 9.5

ANS: Prior to PostgreSQL 9.5, the absence of native upsert functionality means that implementing this requires workarounds. The main challenges involve managing concurrency to prevent race conditions (where multiple transactions interfere with each other) and ensuring atomicity (that the operation either fully succeeds or fails cleanly), often leading to more complex SQL or application-level logic.

Q: Can I use the individual row retry loop method for all upsert scenarios in older PostgreSQL versions

ANS: While the individual row retry loop can be used, it is generally not recommended for high-concurrency or performance-critical applications due to its inefficiency and the complexity of correctly handling all edge cases like rollbacks and concurrent modifications. Bulk upserts with table locking are often a better alternative for older versions when dealing with larger datasets.

Q: How does the bulk upsert with table locking strategy ensure data integrity

ANS: This strategy ensures data integrity by first loading new data into a temporary table, then acquiring an exclusive lock on the target table. This lock prevents any other write operations while the UPDATE and INSERT statements are executed, guaranteeing that the merge operation is atomic and free from interference from other transactions.
