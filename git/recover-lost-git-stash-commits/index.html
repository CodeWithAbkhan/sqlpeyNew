“Recover Lost Git Stash Commits: Essential Techniques and Commands”

When a Git stash operation goes awry—perhaps through an accidental git stash pop followed by immediate work, or a premature git stash drop—the committed changes can vanish from the standard stash list. Fortunately, these commits often remain in the repository’s object database as “dangling commits.” Recovering them requires digging into Git’s internal plumbing commands. How can you systematically locate and reapply these valuable lost snapshots?

This exploration details several robust techniques, from quick terminal checks to advanced object inspection, to bring back those crucial work-in-progress changes.

Direct Application if the Hash is Known

If you were fortunate enough to catch the output immediately after losing the stash, the commit hash should be visible.

Applying the Commit Directly

Once you possess the specific commit hash ($stash_hash) for the lost stash, you can directly apply its contents:

# Apply the changes from the lost commit hash
git stash apply $stash_hash

Branch Creation for Inspection

For safer manipulation or inspection before merging, create a temporary branch pointing to the lost commit:

# Create a branch named 'recovered' pointing to the lost commit
git branch recovered $stash_hash

After this, you can interact with the changes using standard Git workflow tools before removing the temporary branch.

Locating the Stash Commit Hash

The primary challenge is identifying the correct hash among all dangling commits.

1. Observing Terminal Output Immediately Post-Drop/Pop

If the terminal session where the stash was dropped or popped is still active, the hash is often printed directly.

For git stash pop or git stash drop, observe output similar to this:

$ git stash pop
[...]
Dropped refs/stash@{0} (2ca03e22256be97f9e40f08e6d6773c7d41dbfd1)

The hash (2ca03e22256be97f9e40f08e6d6773c7d41dbfd1) is your target. You can then restore it by creating a branch:

git branch tmp 2cae03e
git stash apply tmp
git stash

2. Using git fsck to Find Dangling Commits

The git fsck (File System Check) command audits the integrity of the object database. We can filter its output to find commits not currently referenced by any branch or tag.

For Linux, Unix, or Git Bash (Windows)

This command extracts all dangling commit hashes:

git fsck --no-reflog | awk '/dangling commit/ {print $NF}'

To view these commits with a detailed history browser, pipe the output to gitk:

gitk --all $( git fsck --no-reflog | awk '/dangling commit/ {print $NF}' )

Alternatively, for a console graph view:

git log --graph --oneline --decorate $( git fsck --no-reflog | awk '/dangling commit/ {print $NF}' )

Stash commits typically have commit messages starting with “WIP on [branch name]: [previous commit message]” if a message was not explicitly supplied during git stash.

For PowerShell (Windows)

The equivalent command structure uses Select-String and ForEach-Object:

git fsck --no-reflog | Select-String 'dangling commit' | ForEach-Object { $_.ToString().Split(" ")[-1] }

And using gitk in PowerShell:

gitk --all $( git fsck --no-reflog | Select-String 'dangling commit' | ForEach-Object { $_.ToString().Split(" ")[-1] } )

3. Filtering Unreachable Commits by Message

If you recall a partial message, filtering unreachable commits can narrow the search significantly. This approach targets commits tagged with the default “WIP” message format:

git fsck --unreachable | grep commit | cut -d" " -f3 | xargs git log --merges --no-walk --grep=WIP

If you named your stash, replace --grep=WIP with a unique part of your custom message (e.g., --grep=MyCustomTitle).

Alternative Recovery Methods

Applying Stash Directly by Hash (Revisited)

Simply use git stash apply followed by the hash you found via git fsck:

$ git stash apply ad38abbf76e26c803b27a6079348192d32f52219

Inspecting Unreachable Objects via Object IDs

This technique lists all objects that are commits and then displays their summaries, allowing visual inspection. This is useful if standard filters fail, though it can be noisy.

for ref in `find .git/objects | sed -e 's#.git/objects/##' | grep / | tr -d /`; do 
  if [ `git cat-file -t $ref` = "commit" ]; then 
    git show --summary $ref; 
  fi; 
done | less

A shorter variation using git fsck --unreachable:

for ref in `git fsck --unreachable | grep commit | cut -d' ' -f3`; do 
  git show --summary $ref; 
done | less

Using git stash save "My Message" instead of the default git stash can make these commits much easier to locate later.

Re-establishing the Stash Reference

If you find the hash ($stash_hash) and wish to restore it to the actual stash list (refs/stash), you can use git update-ref.

# Restore the reference, adding an optional message based on the commit message
git update-ref -m "$(git log -1 --pretty=format:'%s' $stash_hash)" refs/stash $stash_hash

This effectively “re-stashes” the content by updating the reference pointer.

Using git cherry-pick

If you locate the hash, git cherry-pick can apply the changes onto your current branch, using the -m 1 option for merge commits (stashes are merge commits):

git cherry-pick -m 1 $stash_hash_code

If conflicts arise, use git mergetool to resolve them.

Creating a Diff File for Review

If viewing history within Git tools is difficult, you can output all dangling commit diffs to a file for review in an external text editor:

git show $( git fsck --no-reflog | awk '/dangling commit/ {print $3}' ) > ~/stash_recovery.diff

Review ~/stash_recovery.diff to find the commit SHA, then apply it normally.

Using the Reflog (The Simplest Step)

The git reflog command shows operations affecting HEAD, including most recent actions. While it might not always show the stash reference directly after a pop/drop, it provides context for recent activities and is the essential first check before resorting to deep fsck methods.

Platform-Specific Notes

For users on Windows without standard Unix tools like awk or grep, manual piping or utilizing findstr offers avenues:

  1. Run git fsck --unreachable | findstr "commit".
  2. Copy the output hashes.
  3. Create .bat files using start cmd /k git show <hash> to open commit details in separate windows for visual inspection.

If you find a commit hash, restoration is the same: git stash apply <hash>.

Advanced Filtering for Stash Commits

To specifically target commits matching the structure of a default stash (which usually has three parents):

git fsck --no-reflog | \
awk '/dangling commit/ {print $3}' | \
xargs git log --no-walk --format="%H" \
  --grep="WIP on" --min-parents=3 --max-parents=3

This filters dangling commits to only show those that look like merge commits (--min-parents=3) and contain the default stash message pattern.

FAQs on Recover Lost Git Stash Commits

Q: What command shows all lost commits in Git

ANS: The command git fsck --no-reflog followed by filtering for “dangling commit” output will list hashes of all unreferenced objects, including lost stashes.

Q: Can I restore a dropped stash using only the stash ID

ANS: Yes, if you know the commit hash (which is sometimes referred to as the stash ID after it is dropped), you can restore it using git stash apply <commit_hash>.

Q: What tool should I use on Windows if awk is not available

ANS: In PowerShell, you can use Select-String instead of awk. If using Git Bash on Windows, awk is generally available. For the standard CMD prompt, findstr is the equivalent for filtering output.

Q: Is git reflog the best place to look first for a lost stash

ANS: Yes, checking git reflog is the simplest first step, as it tracks recent HEAD movements, which can often point toward the stash operation you just performed.
