“Locating Git Branches Containing a Specific Commit SHA”

A common necessity in Git workflows is determining precisely which branches, both local and remote, possess a specific commit identified by its SHA. Several powerful command-line techniques address this requirement, offering slightly different perspectives on commit inclusion.

Primary Technique: Using git branch --contains

The most direct approach leverages the --contains flag with the git branch command, as documented in the git-branch manual. This command specifically lists branches that include the specified commit. If no commit is provided, it defaults to examining the HEAD reference.

To list local branches that integrate the commit:

git branch --contains <commit_sha>

Including Remote and All References

To expand the search beyond local tracking branches, you incorporate the -a or -r flags:

  1. Remote Tracking Branches Only: To see branches tracked remotely:

    git branch -r --contains <commit_sha>

    Note: This typically shows local branches that have a direct relationship with a remote branch based on the default refspec (e.g., fetch = +refs/heads/*:refs/remotes/origin/*).

  2. All References (Local and Remote): To check every branch reference available to your repository:

    git branch -a --contains <commit_sha>

Handling Custom Refspecs (e.g., Pull Requests)

If the commit resides in a reference namespace not tracked by default, such as a GitHub Pull Request (PR) reference, you must configure and fetch those specific references first.

Suppose you wish to track pull request heads under refs/remotes/origin/pr/*. You must first alter your remote configuration:

# Configure the specific fetch refspec for PR heads
git config --add remote.origin.fetch "+refs/pull/*/head:refs/remotes/origin/pr/*"

# Update remote references based on the new configuration
git fetch

# Now, check all references, including the newly mapped PR refs
git branch -r --contains <commit_sha>

This adjustment is necessary because standard remote tracking (like origin) usually focuses on branch heads (refs/heads/) unless specified otherwise. For context on why this is sometimes needed, review how PRs are often stored outside standard branch tracking on platforms like GitHub .

Examining Command Output

When running the command, you get output showing which branches contain the SHA. For instance, if you look up a recent commit:

# Hypothetical log result for context
commit d590f2ac0635ec0053c4a7377bd929943d475297
Author: Nick Quaranto <nick@example.com>
Date:   Wed Apr 1 20:38:59 2009 -0400

    Green all around, finally.

# Command execution
git branch --contains d590f2
  tests
* master

This output indicates that the commit d590f2... is present in both the tests branch and the currently checked-out master branch.

Alternative: Identifying Cherry-Picked Commits with git cherry

The git branch --contains command is precise; it checks if the exact commit SHA exists in the history of the target branch. If you are interested in finding branches where an equivalent changeset has been applied—perhaps the commit was cherry-picked under a different SHA—git cherry offers a different perspective.

git cherry compares the content differences (the changeset) rather than the commit ID.

For example, if you frequently send patches via email, the upstream repository might incorporate your changes but assign a new SHA upon integrating them. git cherry <upstream_ref> helps reveal which local commits have already been incorporated upstream, even if the SHAs differ. Commits marked with - in the output are generally considered present upstream.

Tracing Merge Origins with Ancestry Path Logging

If the goal is not just containment, but tracing how a commit arrived at HEAD via merges, a combination involving git log with ancestry path filtering proves useful. By examining merge commits between a known older point (<SHA1>) and the current state (HEAD), you can sometimes deduce the source branch from the merge commit message.

git log <SHA1>..HEAD --ancestry-path --merges
