“Advanced Git Debugging: Leveraging Environment Variables for Deep Tracing”

When encountering complex issues during Git operations like git pull or git clone, accessing granular execution details is essential. Git provides a robust set of environment variables to activate various levels of tracing. How can these variables be strategically employed to diagnose network communication, performance bottlenecks, and general command flow?

Enabling General and Network Traces

Git embeds extensive tracing mechanisms. To activate these, specific environment variables control the output destination (stderr or a specified file).

For the most verbose output during a pull operation, you can combine general execution tracing with cURL message logging:

GIT_CURL_VERBOSE=1 GIT_TRACE=1 git pull origin main

Core Git Trace Variables

Several environment variables enable distinct tracing facets within Git:

  • GIT_TRACE: Activates general tracing for built-in Git commands.
  • GIT_TRACE_PACK_ACCESS: Logs information regarding packfile access.
  • GIT_TRACE_PACKET: Provides tracing at the packet level for network interactions.
  • GIT_TRACE_PERFORMANCE: Logs performance metrics, often directed to a specific file.
  • GIT_TRACE_SETUP: Outputs details about repository discovery and environment setup.
  • GIT_MERGE_VERBOSITY: Controls verbosity for recursive merge strategy debugging (values 0 through 5).
  • GIT_CURL_VERBOSE: Logs all messages generated by the underlying cURL library (equivalent to running curl -v).
  • GIT_TRACE_SHALLOW: Aids in debugging fetching or cloning of shallow repositories.

Setting Trace Values: These variables typically accept true, 1, or 2 to write output to standard error (stderr), or an absolute file path (starting with /) to direct the trace output to a file.

Practical Example: Tracing Git Status

To see the trace of a simple git status command, setting GIT_TRACE=1 will show internal execution steps:

$ GIT_TRACE=1 git status
20:11:39.565701 git.c:350               trace: built-in: git 'status'
# ... rest of the status output

Practical Example: Capturing Performance Data

If performance profiling is needed, direct the output to a log file using GIT_TRACE_PERFORMANCE:

$ GIT_TRACE_PERFORMANCE=$PWD/gc_diagnostics.log git gc
Counting objects: 143760, done.
...
$ head gc_diagnostics.log 
20:12:37.214410 trace.c:420             performance: 0.090286000 s: git command: 'git' 'pack-refs' '--all' '--prune'
20:12:37.378101 trace.c:420             performance: 0.156971000 s: git command: 'git' 'reflog' 'expire' '--all'
# ...

SSH Connection Debugging

When connection problems arise over SSH, increasing the verbosity of the SSH client itself is necessary. This can be done by temporarily overriding the GIT_SSH command or using GIT_SSH_COMMAND.

Alternative Solution: Temporarily Injecting SSH Verbosity

For troubleshooting SSH key or credential issues, you can create a wrapper script for SSH:

# Create a temporary wrapper script that calls ssh with max verbosity (-vvv)
echo 'ssh -vvv "$*"' > ssh_debug_wrapper && chmod +x ssh_debug_wrapper

# Execute the Git command using this wrapper
GIT_SSH="$PWD/ssh_debug_wrapper" git pull origin main

# Clean up
rm ssh_debug_wrapper

Debugging Older Git Versions (Pre-1.8)

For very old Git installations where modern environment variables might be ineffective, one could patch the SSH command execution path:

# Create wrapper, set PATH to prioritize it, run command, then clean up
(echo '/usr/bin/ssh -v ${@}' > /tmp/ssh_injector \
 && chmod +x /tmp/ssh_injector \
 && PATH=/tmp:${PATH} GIT_TRACE=1 git clone https://github.com/user/repo.git \
 && rm -f /tmp/ssh_injector) 2>&1 | tee git_clone_log.txt

The Evolution to Trace2 Facility

Git 2.22 introduced the trace2 facility as a modern, structured replacement for older trace methods. Trace2 aims to provide consistent, post-process-friendly diagnostic data.

Trace2 Environment Variables (Introduced in Git 2.22)

Trace2 uses environment variables ending in TRACE2 (after an initial phase using TR2):

  • GIT_TRACE2: Corresponds to the old GIT_TRACE, logging command summary data.
  • GIT_TRACE2_PERF: Replaces GIT_TRACE_PERFORMANCE, extending output with rich timing columns.
  • GIT_TRACE2_EVENT: Writes structured event data, often as JSON records.

These can be set to 1 or an absolute directory path. Setting a directory causes trace files to be written within that location, aiding trace collection across many invocations.

Example using GIT_TRACE2_PERF with Configuration:

Trace2 interacts with configuration settings. For example, setting performance targets globally:

git config --global trace2.perfTarget ~/log.perf
git config --global trace2.normalTarget ~/log.normal
git version

The output in ~/log.perf from a command like git version would look structured:

d0 | main                     | start        |     |  0.001173 |           |            | git version
d0 | main                     | cmd_name     |     |           |           |            | version (version)
d0 | main                     | exit         |     |  0.001227 |           |            | code:0

Advanced Trace2 Features

Subsequent Git releases have enhanced trace2 capabilities:

  1. HTTP Tracing (GIT_TRACE_CURL): Introduced in Git 2.9, this variable provides detailed cURL transport data, overriding GIT_CURL_VERBOSE. Later versions (2.39+) started redacting sensitive headers like Authorization.
  2. Ref Tracing (GIT_TRACE_REFS): For versions supporting it (e.g., Git 2.29+), setting this variable prints operations as they occur within the ref storage backend, useful for debugging ref database inconsistencies.
  3. Environment Logging (trace2_cmd_list_env_vars): Starting in Git 2.27, trace2 can log environment variables alongside configuration parameters, providing a full picture of runtime overrides.
  4. Stopwatch Timers and Counters (Git 2.39): Trace2 gained structured monitoring tools:
    • Timers (timer, th_timer): Measure accumulated time for code spans, useful when regions are impractical.
    • Counters (counter, th_counter): Track global increments (e.g., number of calls to a specific utility function) across threads or the entire process.

Example of Timer Measurement in Trace2:

If you measure an expensive_function called multiple times:

export GIT_TRACE2_PERF=~/perf.log
# ... run test tool that calls expensive_function 3 times
$ cat ~/perf.log | grep timer
d0 | main                     | timer        |     |           |           | test         | name:test1 intervals:3 total:3.001686 min:1.000254 max:1.000929

Other Relevant Commands and Verbosity

  • General Verbosity Flag: For many Git commands, the -v flag increases output detail without setting global environment variables. 
    git clone -v git://server/repo my_local_copy
  • Error Reporting in Traces: Warnings and non-fatal bugs (warning(), bug()) are now traced via trace2 events since Git 2.30 and 2.37, respectively, offering complete insight even when Git does not immediately abort.

FAQs on Advanced Git Debugging Tracing

Q: What is the difference between GIT_CURL_VERBOSE and GIT_TRACE_CURL

ANS: GIT_CURL_VERBOSE logs general cURL messages. GIT_TRACE_CURL (introduced in Git 2.9) provides a more detailed trace dump of all incoming and outgoing data, similar to curl --trace-ascii, and it overrides GIT_CURL_VERBOSE.

Q: How do I direct trace output to a file instead of the terminal

ANS: Set the trace environment variable (like GIT_TRACE=1 or GIT_TRACE2=1) to an absolute file path, e.g., GIT_TRACE=/var/log/git_debug.log git pull.

Q: Which environment variable is best for SSH credential checks

ANS: Use GIT_SSH_COMMAND="ssh -vvv" before your Git command (like clone or pull) to force the underlying SSH client to output detailed diagnostics regarding keys and connection negotiation.

Q: When were environment variables renamed from GIT_TR2 to GIT_TRACE2

ANS: The environment variables were renamed from the abbreviated GIT_TR2* to the clearer GIT_TRACE2* around Git version 2.23 to improve clarity, as ‘TR’ was ambiguous.
