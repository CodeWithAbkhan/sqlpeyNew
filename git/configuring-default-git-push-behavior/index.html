“Configuring Default Git Push Behavior: push.default Strategies”

When executing git push without specifying explicit remote and refspecs, Git relies on the push.default configuration setting to determine which branches to operate on. This setting is critical for workflow safety, especially when dealing with multiple branches. What are the accepted configurations and how can they be applied?

Examining Current push.default Settings

Before making changes, it is useful to inspect the current global or local configuration:

# View the current local configuration for push.default
git config push.default

# View the current global configuration for push.default
git config --global --get push.default

Solution Set 1: Configuring push.default via git config

The behavior can be explicitly set using the git config command.

| Mode | Description | Safety/Use Case | | :

Solutions

| :

push.default
git config push.default
git config push.default current

| :

git config push.default current
git config --global push.default current
git config --global push.default simple

| | nothing | Pushes nothing if no refspec is given. | Highly restrictive, prevents accidental pushes. | | matching | Pushes all branches that share the same name locally and remotely (Default before Git 2.0). | Can be dangerous in shared repositories. | | upstream | Pushes the current branch to its configured upstream branch. | Good for tracking branches. | | current | Pushes the current branch to a remote branch of the exact same name. | Clear, branch-specific push. | | simple | (Default since Git 2.0) Behaves like upstream, but strictly refuses to push if the upstream branch name diverges from the local branch name. | Considered the safest default, ideal for newcomers. |

To enforce a specific behavior globally across all repositories:

# Setting the safest default since Git 2.0
git config --global push.default simple

# Setting to push only the currently checked-out branch to a remote of the same name
git config --global push.default current

For a single repository, omit the --global flag:

git config push.default upstream

Solution Set 2: Pushing the Current Branch Explicitly

If you prefer not to alter the default configuration, you can always specify exactly what to push using the current branch reference:

# Pushes the currently checked-out branch to its remote counterpart on 'origin'
git push origin HEAD

Solution Set 3: Using git push <remote> Behavior

When running git push origin (or any remote name without a refspec), Git pushes changes from all local branches that have a corresponding branch name on the remote named origin.

If you specify a branch:

# Pushes local 'master' branch changes to remote 'master' on 'origin'
git push origin master

# Pushes local 'master' changes to remote 'staging' branch if it exists
git push origin master:staging

Solution Set 4: Custom Shell Functions and Aliases for Convenience

For developers who frequently push only the current branch and wish for a shorter command, shell functions or Git aliases offer robust alternatives.

Bash Alias Example (Getting Current Branch Name)

This method uses shell commands to dynamically capture the current branch name:

# Define function in ~/.bash_profile or similar shell startup file
get_git_branch() {
  echo `git branch 2> /dev/null | sed -e '/^[^*]/d' -e 's/* \(.*\)/\1/'`
}

# Define aliases based on the function
alias gpull='git pull origin `get_git_branch`'
alias gpush='git push origin `get_git_branch`'

Executing gpush will now perform git push origin <current_branch_name>.

Git Alias Example (Using symbolic-ref)

A Git alias can wrap shell execution to push the current branch, optionally setting the upstream tracking link (-u):

# Add this to your .gitconfig file under the [alias] section
pub = "!f() { git push -u ${1:-origin} `git symbolic-ref HEAD`; }; f"

Usage:

  • git pub pushes the current branch to its upstream on origin.
  • git pub staging-server pushes the current branch to its upstream on the remote named staging-server.

Solution Set 5: Automating New Branch Push Setup (Git 2.37+)

For newer Git installations, setting push.autoSetupRemote helps manage behavior when pushing branches that do not yet exist remotely, especially when using push.default set to simple or upstream.

# Enables automatic setup of the upstream remote for new branches on push
git config --global --add --bool push.autoSetupRemote true

Solution Set 6: Advanced Gerrit Integration (Using remote.origin.push)

If your workflow involves systems like Gerrit, you might configure the specific refspec to use when pushing to a remote, overriding broader push.default settings for that remote connection:

# Example script to set push refspec for Gerrit review (assuming remote is 'origin')
#!/bin/bash -eu

CURRENT_BRANCH=$(git branch | grep '^\*' | cut -d" " -f2)
NEW_PUSH_REF="HEAD:refs/for/$CURRENT_BRANCH"

echo "Setting remote.origin.push to $NEW_PUSH_REF"
git config remote.origin.push $NEW_PUSH_REF

This setup forces pushes for the current branch into a review queue (e.g., refs/for/feature-branch).

FAQs on Configuring Default Git Push Behavior

Q: What is the recommended push default setting for new users

ANS: The simple setting is recommended since Git 2.0 as it is the safest, pushing the current branch only to its explicitly tracked upstream branch, refusing pushes if the names mismatch.

Q: How do I check my global push default setting

ANS: You can check the global setting by executing the command: git config --global --get push.default

Q: Does git push origin always push all local branches

ANS: Not necessarily. git push origin pushes local branches to remote branches with matching names on the origin remote, provided push.default is set to matching (older Git versions) or if you don’t specify a refspec and the configuration allows it.
