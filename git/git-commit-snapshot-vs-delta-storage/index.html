“Git Commit: Snapshot vs Delta Storage Mechanics Explained”

When interacting with Git, a core concept frequently arises: Does a Git commit store a full snapshot of the project state, or does it only store the differences (deltas) from the previous state? Exploring the mechanics behind Git’s data representation reveals a nuanced answer involving both high-level conceptual modeling and highly efficient physical storage techniques.

The Conceptual View: Git as a Series of Snapshots

Conceptually, Git operates by viewing your project as a collection of file system snapshots, rather than a sequence of file changes, which is common in many legacy Version Control Systems (VCS) like Subversion.

When you execute git commit, Git captures the complete state of your project’s files (excluding ignored ones) at that exact moment. This saved state is referenced by the commit object.

A key efficiency inherent in this snapshot approach is deduplication:

  1. Identical Content: If multiple files within the repository have exactly the same content, Git stores that content only once, referencing the single stored blob using its unique SHA-1 hash. This applies even if the files reside in different directories or have different names.
  2. Unchanged Files: If a file hasn’t been modified since the previous commit, Git does not duplicate the file’s contents. Instead, the new commit’s structure merely points back to the existing, identical content object already present in the repository.

This structure—where each commit references a map (a “tree”) pointing to content objects (“blobs”)—makes Git resemble a highly optimized, mini file system rather than just a change tracker. This data structure is formally represented as a Directed Acyclic Graph (DAG).

For further reading on this conceptual layer, resources like the Git Reference documentation or the “A Commit in Git: Is it a snapshot/state/image or is it a change/diff/patch/delta? ” from Git Immersion provide valuable background.

The Physical Storage Reality: Efficient Delta Compression

While the conceptual model relies on snapshots, the physical storage layer employs sophisticated techniques, primarily delta compression, to ensure repositories remain small and transfer efficiently.

As noted by contributors, while the snapshot idea is crucial for understanding how Git tracks state, it is not the whole story at the storage level.

How Delta Compression Works in Practice

Git intelligently uses deltas (differences) for storage efficiency, often proving more effective than systems that inherently store only deltas.

  1. Blob Addressing: Every piece of data (a file’s content, a directory structure, or a commit metadata) is stored based on its SHA-1 hash value. This is content addressing.
  2. Packfiles Generation: To maximize space savings, Git periodically consolidates loose objects (commits, trees, blobs) into highly compressed packfiles. This process is typically triggered by commands like git gc.
  3. Smart Delta Selection: Instead of just comparing an object to its immediate predecessor (like some other VCS), Git uses heuristics to find the most similar existing blob in the repository, potentially spanning across older versions or totally different files. It then generates the smallest possible delta between the new object and the best match it finds.
  4. Compression Control: The pack window parameter influences the quality of this delta compression versus the time taken to perform it. While the default offers good results, running git gc --aggressive increases this window (e.g., to 250), dramatically slowing down compression time but yielding superior space savings for historical data.

This means that even though Git logs a full snapshot for every commit, the actual disk space used for older, similar files is minimized by storing them as compact differences relative to other stored content.

Consider an example where two files, src/index.js and .gitignore, are initially empty. Both will result in the same blob hash (e69de...) because their content is identical. However, they require two separate Tree entries (and potentially different Tree objects) to map their distinct paths correctly. If you later modify only .gitignore, a new blob is created for its content, and a new root Tree object is generated to reference the unchanged Blob for src/index.js and the new Blob for .gitignore.
