“Git Merge Strategy: Achieving Equivalent of ‘git merge -s theirs’”

The git merge command offers the -s ours strategy, which stages a merge commit but effectively ignores all changes from the merging branch, preserving only the contents of the branch being merged into (the “ours” side). However, a direct counterpart, git merge -s theirs, which would discard “ours” and only keep content from “theirs,” does not natively exist.

This situation frequently arises when one branch (branchB) is intended to completely overwrite the content of another branch (branchA) during a merge, while still recording a proper merge commit structure with both parent pointers.

How can we reliably implement a merge where the resulting tree reflects only the content of the branch being merged in (theirs), while preserving the merge commit structure?

Alternative Approaches to Select ‘Theirs’ Content During Merge

Several techniques provide functionality similar to what a hypothetical git merge -s theirs would offer.

Solution Set 1: Utilizing -X theirs with Conflict Resolution

The -X <option> (or short form -x <option>) flag configures how the recursive strategy handles merge conflicts. Using -X theirs instructs Git to resolve conflicts by automatically choosing the version from the branch being merged in (branchB).

Key Distinction: This is not truly equivalent to -s theirs because -X theirs still performs a standard recursive merge; it just uses “theirs” as the tie-breaker for conflicts, whereas -s ours (or hypothetical -s theirs) dictates the final content entirely.

If this approach leads to conflicts involving deleted files in branchB, you must explicitly handle those deletions after the initial merge attempt:

# Assuming we are on branchA and merging branchB
git checkout branchA
git merge -X theirs branchB

# If files deleted in branchB cause conflicts, remove them manually:
git rm {DELETED-FILE-NAME-FROM-BRANCHB}

# The merge should now complete or proceed smoothly after manual cleanup.

Solution Set 2: Creating a Merge Commit That Reflects ‘Theirs’ Content (Preserving Parent Order)

This sophisticated workflow uses -s ours to establish the merge structure initially, and then rewinds the tree contents to match branchB, resulting in a merge commit where the content is purely from branchB, but the parent order (branchA as first parent, branchB as second) is maintained.

# 1. Ensure we are on the target branch (branchA)
git checkout branchA

# 2. Create the merge commit structure, discarding 'ours' content temporarily
git merge -s ours branchB    

# 3. Create a temporary reference to the just-created merge commit
git branch branchTEMP         

# 4. Overwrite the working tree and index with branchB's contents
git reset --hard branchB

# 5. Reset the branch pointer (branchA) back to the temporary merge commit, 
#    but keep the current working tree/index state (which is now branchB's content)
git reset --soft branchTEMP

# 6. Amend the merge commit to use the current index content (branchB's files)
git commit --amend

# 7. Clean up the temporary branch
git branch -D branchTEMP

# Verification: Ensure the final merge commit matches branchB exactly
git diff HEAD branchB

Solution Set 3: Recursive Merge with -X theirs (Simplest Conflict Resolution)

This option uses the default recursive strategy but tells it to prefer the incoming branch (branchB) during any conflict resolution.

git checkout branchA
# Implicitly uses -s recursive, applies -X theirs for conflicts
git merge -X theirs branchB

Solution Set 4: Content Replacement via git restore (Post-Merge Amend)

For Git versions 2.23 and newer, this method is quite direct for achieving a merge commit whose final tree matches the second parent (their_branch).

# Start on the branch receiving the merge (our_branch)
git switch our_branch

# Create the merge commit placeholder, discarding 'ours' content initially
git merge -s ours their_branch

# Replace the working tree and index with the exact contents of their_branch
git restore --source=their_branch --worktree --staged :/

# Amend the merge commit to use the content now staged in the index
git commit --amend

Solution Set 5: Using Plumbing Commands for Precise Parentage

If strict control over the parent structure and tree is paramount, low-level commands like git commit-tree can be employed. This method forces the content tree from branchB onto a new merge commit whose parents are the current HEAD (our side) and branchB.

# Ensure clean state first

# 1. Create the merge commit object manually:
#    -p HEAD: Sets the first parent to our current commit
#    -p branchB: Sets the second parent to branchB's tip
#    'branchB^{tree}': Sets the tree content to that of branchB
COMMIT_HASH=$(git commit-tree -m "Take content solely from branchB" -p HEAD -p branchB 'branchB^{tree}')

# 2. Move HEAD to this newly created commit
git reset --hard "$COMMIT_HASH"

Solution Set 6: Manual Conflict Resolution Shortcut

If a standard merge results in conflicts, you can manually select the “theirs” version for every conflicted file:

git merge <branch>

# Resolve all conflicts by selecting the incoming branch's version for every file
git checkout --theirs <file> 
# Repeat for all files, then:
git add .
git commit

Alternatively, for rapid resolution when every file needs “theirs”:

git checkout --theirs .
git add .
git commit

This avoids the need for -s theirs but requires subsequent commit actions.

Solution Set 7: Alias Creation for Convenience

To simplify the complex workflow from Solution Set 2, an alias can be defined in .gitconfig to execute the sequence of merge -s ours, reset --hard, reset --soft, and commit --amend.

Example Alias Definition (in .gitconfig):

[alias]
    mergetheirs = "!git merge -s ours \"$1\" && git branch temp_THEIRS && git reset --hard \"$1\" && git reset --soft temp_THEIRS && git commit --amend && git branch -D temp_THEIRS"

Usage:

git checkout B 
git mergetheirs A # Merges A into B, adopting A's content entirely.

FAQs on Git Merge Strategy Theirs

Q: What is the main difference between git merge -X theirs and git merge -s ours

ANS: -X theirs is a conflict resolution option applied during a recursive merge, meaning it only dictates how conflicts are resolved. -s ours is a distinct strategy that creates a merge commit but intentionally leaves the resulting tree identical to the branch being merged into, effectively ignoring the content of the merging branch.

Q: Can git pull use a strategy option like --strategy=theirs

ANS: Older Git versions might have supported git pull --strategy=theirs remote_branch, but this is deprecated/removed. Modern approaches require git fetch origin followed by git reset --hard origin to achieve a destructive overwrite, which is functionally different from a proper merge.

Q: Does the solution preserve the parent order in the merge commit

ANS: Yes, solutions leveraging an initial git merge -s ours <branchB> followed by content replacement (like Solution Set 2 or 4) specifically maintain the correct parent order where branchA is the first parent and branchB is the second.
