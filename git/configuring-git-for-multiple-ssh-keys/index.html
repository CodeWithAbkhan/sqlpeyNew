“Configuring Git for Multiple SSH Keys: Essential Solutions”

When dealing with multiple remote Git repositories that require distinct SSH identities—for instance, differentiating between personal and work GitHub accounts—standard Git behavior can default to the wrong private key. How can one reliably instruct Git on which SSH key to employ for specific connections, ensuring pushes and pulls utilize the correct credentials? Several robust techniques exist, ranging from fine-grained configuration files to temporary environment variables.

Utilizing the SSH Configuration File (~/.ssh/config)

The most recommended and flexible approach involves configuring host aliases within the SSH configuration file. This method allows SSH (and by extension, Git) to automatically select the appropriate key based on the host alias specified in the remote URL.

Defining Specific Host Aliases

By setting up distinct Host entries, you can map a local alias to a remote server and specify the exact identity file to use.

For a scenario where you need a specific key for a server alias gitserv:

Host gitserv
    Hostname remote.server.com
    IdentityFile ~/.ssh/id_rsa.github
    IdentitiesOnly yes
    AddKeysToAgent yes

When adding or cloning a repository, use the defined alias:

git remote add origin git@gitserv:myrepo.git
# Or clone fresh:
# git clone git@gitserv:myrepo.git

git push -v origin master

Key Directives Explained:

  • IdentitiesOnly yes: Crucial for preventing SSH from unnecessarily trying default identity files (like id_rsa) before attempting the explicitly defined one. This avoids potential authentication delays or unexpected rejections based on wrong key offerings.

  • AddKeysToAgent yes: Allows the key passphrase to be stored temporarily in the ssh-agent, removing the need to re-enter it for subsequent operations.

  • Alternative Configuration for Multiple Keys on the Same Host (e.g., GitHub): If you need different keys for different GitHub users, define multiple hosts pointing to the same github.com, but use different local aliases:

    Host github.com
    Hostname github.com
    IdentityFile ~/.ssh/id_rsa
    User git

Host github-work
    Hostname github.com
    IdentityFile ~/.ssh/id_rsa_work
    User workuser

    To use the work key, change the remote URL accordingly: git clone git@github-work:company/project.git.

Environment Variable Overrides: GIT_SSH_COMMAND

For single commands or temporary sessions, setting the GIT_SSH_COMMAND environment variable offers a direct way to override the default SSH client invocation, specifying the identity file (-i) and necessary options.

Setting the Command Temporarily

This method specifies the exact SSH command arguments for one operation:

GIT_SSH_COMMAND='ssh -i /path/to/your/private/key -o IdentitiesOnly=yes' git clone user@host:repo.git

Platform Specific Notes for GIT_SSH_COMMAND:

  • Windows (CMD): Proper quoting is necessary: set "GIT_SSH_COMMAND=ssh -i private_key_file" (avoiding double quotes around the entire assignment if using set directly).
  • General Shells (Bash/Zsh): You can export it to persist for the current shell session: 
    export GIT_SSH_COMMAND='ssh -i ~/Projects/aws/keys/aws_ubuntu.pem'
git push origin main
    This is particularly useful when connecting to cloud servers via SSH keys (e.g., .pem files from AWS/Azure).

Using core.sshCommand Configuration

Git versions 2.3.0 and later introduce the core.sshCommand configuration option, allowing you to define the SSH command on a per-repository basis, which is saved in .git/config.

Per-Repository Configuration

  1. During Cloning: Use the -c flag to set the configuration for just that single operation: 
    git -c core.sshCommand="ssh -i /path/to/key -o IdentitiesOnly=yes" clone git@host:repo.git
  2. After Cloning (Permanent per Repo): Navigate into the repository and set it permanently in the local .git/config: 
    cd /path/to/my/repo/
git config core.sshCommand 'ssh -i private_key_file -o IdentitiesOnly=yes'
git pull
    This approach ensures that all future operations on that repository use the specified command, overriding environment variables unless GIT_SSH_COMMAND is present.

Leveraging ssh-agent for Key Loading

If your keys are password-protected, loading them into the ssh-agent is essential for non-interactive operations (like scripts or cron jobs).

Loading Keys into the Agent

You can explicitly add keys before running the Git command. The agent will then offer these keys to the SSH process invoked by Git.

# Start the agent if not running (often unnecessary in modern systems)
eval $(ssh-agent -s)

# Add the specific key required
ssh-add /path/to/your/specific/keyfile

# Now run the git command
git clone git@specific-host:user/project.git

Alternative: Agent Integration within a Subshell

You can wrap the key addition and the Git operation into a single command line using ssh-agent to manage the environment variables for that specific execution:

ssh-agent bash -c 'ssh-add /somewhere/yourkey; git clone git@user:user/project.git'

Alternative Approach: SSH Wrapper Script

A more robust, scriptable solution involves creating a wrapper script that sets the GIT_SSH environment variable to point to a shell script that forces the desired key.

Wrapper Script (~/gitwrap.sh):

#!/bin/bash
# Forces SSH to use ~/.ssh/gitkey_rsa for all arguments passed ($@)
ssh -i ~/.ssh/gitkey_rsa "$@"

Usage:

export GIT_SSH=~/gitwrap.sh
git push origin main

This solution forces all Git SSH interactions to use the key specified within the wrapper script until GIT_SSH is unset or redefined.

Per-Repo Configuration Verification

If you suspect the wrong URL or key is being used, check the local repository configuration directly by inspecting the .git/config file:

user@workstation:~/workspace/project-name/.git$ cat config
[core]
    repositoryformatversion = 0
    filemode = true
    bare = false
    logallrefupdates = true
    # Check if sshCommand is defined here
    sshCommand = ssh -i ~/location-of/.ssh/private_key -F /dev/null 
[remote "origin"]
    # Ensure this is the SSH URL, not HTTPS
    url = git@<user-name>/<project-name>.git
    fetch = +refs/heads/*:refs/remotes/origin/*
[branch "master"]
    remote = origin
    merge = refs/heads/master

FAQs on Configuring Git for Multiple SSH Keys

Q: What is the primary reason for using IdentitiesOnly yes in ssh config

ANS: IdentitiesOnly yes explicitly instructs SSH to only use the identity files explicitly mentioned in the configuration block and suppresses the attempt to use other identity files matching default names (like id_rsa), which is critical when managing multiple distinct keys.

Q: Can core sshCommand be set globally

ANS: Yes, you can set core sshCommand globally by adding the –global flag: git config --global core.sshCommand 'ssh -i /path/to/key'. However, using host-specific entries in ~/.ssh/config is generally better for key association per host.

Q: How to use a .pem file with Git on Mac

ANS: On macOS, you can use the GIT_SSH_COMMAND environment variable, passing the .pem file path to the -i flag: export GIT_SSH_COMMAND="ssh -i /Users/user/keypair.pem".

Q: What command confirms the active ssh command used by git

ANS: You can verify configuration using git config --local --get core.sshCommand if configured per-repo, or by running SSH with verbose output: ssh -vT git@hostname.
