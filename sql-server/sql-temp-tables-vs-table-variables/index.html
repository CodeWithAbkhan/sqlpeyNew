“SQL Server Temp Tables (#) vs Table Variables (@): Key Differences and Usage”

When manipulating datasets within stored procedures or batches in SQL Server, developers frequently encounter the choice between using a local temporary table (prefixed with #) or a table variable (prefixed with @). While both mechanisms reside in tempdb for storage, their behavioral differences—particularly concerning transactions, indexing, and the Query Optimizer—dictate which is the superior choice for specific scenarios.

What are the fundamental architectural and functional divergences between local temporary tables (#tmp) and table variables (@tmp) in SQL Server?

Core Behavioral Differences and Trade-offs

The selection between these two structures involves evaluating several critical aspects:

1. Transaction Participation and Rollback

  • Table Variables (@tmp): Do not participate in transactions. Any data inserted into a table variable during a transaction that is subsequently rolled back will remain populated. This isolation can be useful if you need a persistent state midway through a complex rollback scenario.
  • Temporary Tables (#tmp): Act fully within transactions. DML operations performed on them can be rolled back if the enclosing transaction is rolled back.

2. Query Optimization and Statistics

This is perhaps the most significant performance differentiator.

  • Table Variables (@tmp): The Query Optimizer does not create statistics on table variables. Consequently, it defaults to estimating that the variable contains only one row, regardless of the actual data volume. This fixed estimation can lead to severely non-optimal execution plans, especially when processing large datasets.
  • Temporary Tables (#tmp): Are real tables and do generate statistics. This allows the Query Optimizer to build more accurate execution plans based on the actual data distribution and row counts.

3. Indexing Capabilities

The ability to define indexes impacts query performance significantly for larger data volumes.

  • Temporary Tables (#tmp): Support full DDL operations, including the creation of non-unique indexes using CREATE INDEX. If you need efficient access paths across substantial data, temporary tables are advantageous.
  • Table Variables (@tmp): Cannot use CREATE INDEX. Indexing is restricted to what is created implicitly or explicitly via PRIMARY KEY or UNIQUE constraints. For a non-unique index, a common workaround involves creating a composite UNIQUE constraint that includes a unique identity column. (Note: SQL Server 2014 introduced support for non-unique indexes on table variables, but the statistics limitation remains paramount).

4. Scope and Visibility

The lifespan and accessibility vary based on the object type.

  • Table Variables (@tmp): Scope is limited to the batch, stored procedure, or statement block in which they are declared. They are not visible to procedures called by the creating routine or within nested dynamic SQL executed via EXEC or sp_executesql.
  • Temporary Tables (#tmp): Their scope includes code in called procedures and nested dynamic SQL contexts, allowing them to be used across procedure calls within the same session.
  • Global Temporary Tables (##tmp): These are visible to all sessions and users and persist until the last referencing connection closes.

5. Storage Location and Collation

Both store data in tempdb.

  • Collation: Table variables (since SQL Server 2005) inherit the collation from the current database, whereas temporary tables inherit the default collation of tempdb. This difference can cause subtle comparison issues if the database collation differs from tempdb’s collation.

6. Execution Plan Recompilation

  • Table Variables (@tmp): Do not cause stored procedures to recompile when data is inserted or modified, leading to consistent execution plan usage.
  • Temporary Tables (#tmp): Schema modifications (like CREATE INDEX or using SELECT INTO to create structure) on temporary tables can frequently force stored procedures that use them to recompile, impacting performance on subsequent executions.

7. Function Usage

  • Table Variables (@tmp): Can be returned from user-defined functions, which is necessary for functions designed to split strings or encapsulate logic returning a set.
  • Temporary Tables (#tmp): Cannot be used within user-defined functions.

Practical Implementation Examples

Choosing the right structure often involves simple setup differences.

Example 1: Simple Setup

Table Variable Declaration:

DECLARE @SimpleData TABLE (
    RecordID INT PRIMARY KEY,
    Payload VARCHAR(100)
);

INSERT INTO @SimpleData (RecordID, Payload) VALUES (1, 'Initial Test A');

Local Temporary Table Creation (Using SELECT INTO for speed):

If structure definition is unknown or changes often, SELECT INTO is convenient for temp tables:

SELECT 
    E.EmployeeID, 
    D.DeptName, 
    COUNT(E.EmployeeID) AS TotalEmployees
INTO #DepartmentSummary
FROM EmployeeData E
JOIN DepartmentData D ON E.DeptID = D.DeptID
GROUP BY E.EmployeeID, D.DeptName;

-- Can now index this structure if needed
CREATE CLUSTERED INDEX IX_Temp_DeptEmp ON #DepartmentSummary (EmployeeID);

Example 2: Simulation of Logging Differences (Conceptual)

While detailed analysis requires specialized tools like fn_dblog, the concept is that table variables have fewer metadata updates compared to temporary tables, leading to minor transactional log differences, especially around system table updates.

The logging difference is often negligible for basic operations, but the overhead in metadata updates for table variables registering in sys.syssingleobjrefs is an observed artifact when comparing logging records.

When to Favor Which Structure?

A common guideline points toward volume, but the real decision rests on functional requirements:

  1. Use Table Variables (@tmp): For small datasets (often cited as under 1,000 rows) where transaction control/rollback is not needed, or when returning data from a User-Defined Function. Their lack of recompilation is a benefit for simple, repetitive calls.
  2. Use Temporary Tables (#tmp): When dealing with large data volumes, when indexes are required beyond simple constraints, when the data needs to be referenced by nested stored procedures, or when the Query Optimizer needs accurate row counts via statistics.

Alternative: Derived Tables and CTEs

For scenarios where the temporary structure is only needed for a single query execution, consider substituting both temporary objects with Common Table Expressions (CTEs) or derived tables. These structures are processed entirely during the query compilation phase and can sometimes yield faster performance due to optimized execution within a single statement.

-- Using a CTE instead of a persistent structure
WITH AggregatedData AS (
    SELECT 
        DeptName, 
        COUNT(*) AS RowCount
    FROM EmployeeData E
    JOIN DepartmentData D ON E.DeptID = D.DeptID
    GROUP BY DeptName
)
SELECT * 
FROM AggregatedData
WHERE RowCount > 100;

Performance tuning necessitates empirical testing against your specific workload and data profiles. Relying solely on volume guidelines (e.g., “always use @tmp for under 100 rows”) risks future application failures if data growth is not anticipated.
