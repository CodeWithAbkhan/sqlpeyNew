“Fixing Unintended DPI-Awareness Shift in DPI-Unaware Applications”

A peculiar scenario arises when a previously DPI-unaware application, perhaps after minor updates or dependency changes, starts exhibiting DPI-aware behavior, despite having no explicit DPI-related API calls or direct references to WPF assemblies. This shift often occurs because third-party components, now modernized, are DPI-aware by default and implicitly elevate the host application’s awareness level when referenced.

Since the default behavior for older applications (based on the absence of a DPI awareness definition in app.manifest) is DPI-unaware for backward compatibility, restoring this state requires explicit declaration or programmatic intervention.

Solution 1: Explicitly Setting DPI Awareness in the Application Manifest

The primary and recommended approach involves declaring the application’s DPI awareness directly in its manifest file.

For applications targeting older Visual Studio versions, or for clarity, one would reference Hans Passant’s guidance on setting this property. Since Visual Studio 2015 Update 1, this setting is present in app.manifest but commented out. To enforce DPI-Unaware status, you must uncomment and set the <dpiAware> section to false within the <windowsSettings> block.

Observe the structure required in the application manifest (.exe.manifest):

<?xml version="1.0" encoding="utf-8"?>
<assembly manifestVersion="1.0" xmlns="urn:schemas-microsoft-com:asm.v1">
  <assemblyIdentity version="1.0.0.0" name="MyApplication.app"/>

  <!-- ... other sections ... -->
   
  <!-- DPI Awareness Setting -->
  <application xmlns="urn:schemas-microsoft-com:asm.v3">
    <windowsSettings>
      <!-- Setting this to 'false' explicitly enforces DPI-Unaware behavior -->
      <dpiAware xmlns="http://schemas.microsoft.com/SMI/2005/WindowsSettings">false</dpiAware>
    </windowsSettings>
  </application>

  <!-- ... rest of the assembly ... -->
</assembly>

Note for .NET Framework 4.6 Windows Forms Apps: If you opt into DPI awareness (which you are trying to avoid here), you would need to set EnableWindowsFormsHighDpiAutoResizing to true in app.config. For forcing DPI-Unaware, this configuration is usually unnecessary.

For further reading on High DPI development on Windows and setting default DPI awareness per process, consult Microsoft’s documentation on High DPI desktop application development on Windows .

Solution 2: Programmatic Control via Windows API Calls (P/Invoke)

If manifest modification is insufficient, or if you require runtime control over DPI awareness on a per-thread or per-process basis, you can use specific Windows API functions imported via Platform Invoke (P/Invoke).

A. For Windows 7 and Later: SetProcessDPIAware

This function sets the entire process to be DPI-aware, which is the opposite of what is needed, but useful for context. To stay DPI-unaware, you would check if this was called accidentally.

B. For Windows 8.1 and Later: SetProcessDpiAwareness

This API offers finer granularity:

[DllImport("shcore.dll")]
static extern int SetProcessDpiAwareness(ProcessDPIAwareness value);

public enum ProcessDPIAwareness
{
    DPI_Unaware = 0,
    System_DPI_Aware = 1,
    Per_Monitor_DPI_Aware = 2
}

// To enforce DPI Unaware programmatically:
SetProcessDpiAwareness(ProcessDPIAwareness.DPI_Unaware);

C. For Windows 10, Version 1703 and Newer: SetProcessDpiAwarenessContext

This offers the most advanced context control. The relevant context for your goal, especially for GDI content improvement while remaining largely unaware of system scaling, is DPI_AWARENESS_CONTEXT_UNAWARE_GDISCALED. If strict unwareness is required, use Context_Unaware.

Here are the necessary imports and enumeration mappings for modern Windows versions:

// Virtual Enumeration context mapping based on documentation
public enum DpiAwarenessContext
{
    Context_Undefined = 0,
    Context_Unaware = (DPI_AWARENESS_CONTEXT)(-1),
    Context_SystemAware = (DPI_AWARENESS_CONTEXT)(-2),
    Context_PerMonitorAware = (DPI_AWARENESS_CONTEXT)(-3),
    Context_PerMonitorAwareV2 = (DPI_AWARENESS_CONTEXT)(-4),
    Context_UnawareGdiScaled = (DPI_AWARENESS_CONTEXT)(-5)
}

[DllImport("user32.dll", SetLastError = true)]
static extern int SetProcessDpiAwarenessContext(DpiAwarenessContext value);

// Example usage to set the process context to strictly Unaware:
SetProcessDpiAwarenessContext(DpiAwarenessContext.Context_Unaware);

You can also check the existing context using GetWindowDpiAwarenessContext and GetThreadDpiAwarenessContext if you need to debug why the application became aware.

Solution 3: Assembly Attribute Override (Disabling WPF Influence)

If the awareness shift is caused by a third-party component indirectly referencing WPF assemblies (which are DPI-aware by nature), you can explicitly instruct the system to ignore this effect for your assembly by adding an attribute to your project’s AssemblyInfo.cs file:

[assembly: System.Windows.Media.DisableDpiAwareness]

This attribute signals to the runtime that even if dependencies pull in WPF capabilities, your assembly should remain DPI-unaware unless explicitly configured otherwise via the manifest.

This is particularly potent when dealing with managed dependencies that unilaterally change the application’s DPI state.

For more details on the interplay between different DPI awareness levels and contexts, review the MSDN articles on Mixed-Mode DPI Scaling and DPI-aware APIs .

FAQs on Fixing DPI Awareness Shifts

Q: Why does my DPI-Unaware app suddenly become DPI-Aware

ANS: This often happens when a project starts referencing third-party components or dependencies that are DPI-Aware (frequently due to WPF references), causing the application process to inherit DPI awareness unless explicitly prevented.

Q: Is changing the manifest better than using P/Invoke

ANS: Modifying the application manifest (dpiAware=false) is the preferred, declarative method for setting the default process behavior at startup. P/Invoke functions offer more dynamic, runtime control, useful if you need to change context mid-execution or troubleshoot specific threads.

Q: What is the difference between System Aware and Per Monitor Aware

ANS: System DPI Aware means the application renders at a single DPI determined at startup and the OS scales it if the user changes DPI settings. Per Monitor DPI Aware means the application can dynamically react and redraw correctly when the user moves the window between monitors with different scaling factors.
