“Unity: How to Pass Data Between Scenes?”

When developing games in Unity, a common requirement is to transfer data between different scenes. GameObjects and their attached Components are typically destroyed when a new scene loads, necessitating specific strategies to preserve and pass information. This post delves into several proven methods for achieving this, from simple variable persistence to more robust data management techniques.

Solution 1: Leveraging Static Variables

For primitive data types or instances of classes that do not inherit from MonoBehaviour or Object, using the static keyword is a straightforward approach. Static variables belong to the class itself, not to specific instances, and retain their values across scene loads.

When to use:

  • Passing primitive types: int, bool, float, string, double.
  • Passing instances of custom classes that don’t inherit from MonoBehaviour or Object.

Limitations:

  • Cannot directly store references to GameObject, Component, or any type inheriting from Object, as Unity’s garbage collection and scene unloading will still destroy these.

Code Example:

public class SceneDataHandler
{
    // Static variable for an integer value
    public static int playerScore = 0;

    // Static variable for a boolean flag
    public static bool enableSoundEffects = true;

    // Static variable for a float value
    public static float gameTimer = 60.0f;

    // Example of a custom class that can be used with static
    public class CustomDataContainer
    {
        public string message = "Initial Message";
    }
    public static CustomDataContainer sessionData = new CustomDataContainer();
}

Usage in different scripts:

Script A (Setting data):

void Start()
{
    SceneDataHandler.playerScore = 150;
    SceneDataHandler.sessionData.message = "Welcome to Level 2!";
}

Script B (Accessing data in the next scene):

void Start()
{
    Debug.Log($"Player Score: {SceneDataHandler.playerScore}");
    Debug.Log($"Session Message: {SceneDataHandler.sessionData.message}");
}

Note: Attempting to use static with MonoBehaviour scripts or GameObject instances directly will not prevent their destruction upon scene load.

Solution 2: DontDestroyOnLoad

This Unity function is essential when you need to preserve GameObjects, Components, or any Object that would normally be destroyed during scene transitions. By calling DontDestroyOnLoad on a GameObject, you instruct Unity to keep it in memory and active across all subsequent scenes.

When to use:

  • When you need to keep an entire GameObject with its components (including MonoBehaviour scripts) across scenes.
  • To persist game managers, audio systems, or player characters that should not be re-instantiated.

Implementation:

Attach a script to the GameObject you want to persist.

using UnityEngine;

public class PersistentManager : MonoBehaviour
{
    void Awake()
    {
        // Prevent this GameObject from being destroyed when a new scene loads
        DontDestroyOnLoad(this.gameObject);
    }
}

Combining with Static References: You can also combine DontDestroyOnLoad with static references for easier access.

using UnityEngine;

public class GlobalGameManager : MonoBehaviour
{
    // Static reference to the single instance of the manager
    public static GlobalGameManager Instance { get; private set; }

    // Data to persist
    public int levelIndex = 1;
    public string playerName = "Player";

    void Awake()
    {
        // Implement Singleton pattern
        if (Instance == null)
        {
            Instance = this;
            DontDestroyOnLoad(this.gameObject); // Make this GameObject persist
        }
        else
        {
            Destroy(gameObject); // Destroy duplicates
        }
    }
}

Accessing from another script in a different scene:

using UnityEngine;

public class NextSceneController : MonoBehaviour
{
    void Start()
    {
        // Access persistent data
        Debug.Log($"Current Level: {GlobalGameManager.Instance.levelIndex}");
        Debug.Log($"Player Name: {GlobalGameManager.Instance.playerName}");

        // Modify persistent data
        GlobalGameManager.Instance.levelIndex = 2;
    }
}

Solution 3: Local Storage (PlayerPrefs, File I/O)

For data that needs to persist even after the game is closed and reopened (like high scores, settings, or saved game states), local storage mechanisms are necessary.

3a. PlayerPrefs API: Ideal for storing small amounts of simple data, such as player preferences or basic game state.

When to use:

  • Saving user settings (volume, graphics quality).
  • Storing simple game progress (current score, last unlocked level).

Code Example:

using UnityEngine;

public class SaveLoadManager : MonoBehaviour
{
    public int currentScore = 100;
    public string highScoreName = "Guest";

    void OnDisable()
    {
        // Save data when the object is disabled or application quits
        PlayerPrefs.SetInt("SavedScore", currentScore);
        PlayerPrefs.SetString("SavedName", highScoreName);
        PlayerPrefs.Save(); // Explicitly save changes
    }

    void OnEnable()
    {
        // Load data when the object is enabled
        currentScore = PlayerPrefs.GetInt("SavedScore", 0); // Default to 0 if not found
        highScoreName = PlayerPrefs.GetString("SavedName", "Guest"); // Default to "Guest"
    }
}

Important Note: PlayerPrefs data can be easily accessed and modified on a user’s machine. For sensitive data, consider encryption.

3b. Serialization to XML/JSON/Binary: For more complex data structures or larger amounts of information, serializing data into files (XML, JSON, or binary) is more suitable. This allows you to save custom class instances and collections.

When to use:

  • Saving complex game states (inventory, character stats, level progress).
  • When PlayerPrefs becomes unwieldy.

Code Example (using JSON serialization):

First, define your data structure:

using System.Collections.Generic;
using UnityEngine;

[System.Serializable] // Necessary for JSON serialization
public class PlayerSaveData
{
    public int health = 100;
    public float experience = 0f;
    public List<string> inventoryItems = new List<string>();
    public Vector3 playerPosition;
}

Then, create a manager to handle saving and loading:

using UnityEngine;
using System.IO; // Required for file operations

public class FileDataManager : MonoBehaviour
{
    private string saveFileName = "game_save.json";

    public void SaveGame(PlayerSaveData dataToSave)
    {
        string jsonData = JsonUtility.ToJson(dataToSave, true); // 'true' for pretty printing
        string path = Path.Combine(Application.persistentDataPath, saveFileName);
        File.WriteAllText(path, jsonData);
        Debug.Log($"Game saved to: {path}");
    }

    public PlayerSaveData LoadGame()
    {
        string path = Path.Combine(Application.persistentDataPath, saveFileName);
        if (File.Exists(path))
        {
            string jsonData = File.ReadAllText(path);
            PlayerSaveData loadedData = JsonUtility.FromJson<PlayerSaveData>(jsonData);
            Debug.Log($"Game loaded from: {path}");
            return loadedData;
        }
        else
        {
            Debug.LogWarning("Save file not found.");
            return null;
        }
    }
}

Usage:

public class GameSessionManager : MonoBehaviour
{
    public FileDataManager fileManager;
    public PlayerSaveData currentPlayerSave;

    void Start()
    {
        currentPlayerSave = fileManager.LoadGame();
        if (currentPlayerSave == null)
        {
            currentPlayerSave = new PlayerSaveData(); // Create new save data if none exists
        }

        // Example: Update data
        currentPlayerSave.health = 90;
        currentPlayerSave.inventoryItems.Add("Sword");
        currentPlayerSave.playerPosition = new Vector3(10f, 5f, 20f);
    }

    void OnApplicationQuit()
    {
        fileManager.SaveGame(currentPlayerSave);
    }
}

Solution 4: ScriptableObjects

ScriptableObjects act as containers for data that can be created and managed within Unity’s Project Assets. They are not tied to specific GameObjects or scenes, making them excellent for sharing data and references across your project.

When to use:

  • Storing configuration data, game settings, or shared references.
  • Creating data assets that can be easily referenced and modified in the Inspector.
  • Facilitating communication between different parts of your game, including across scenes.

Code Example:

Define your ScriptableObject:

using UnityEngine;
using System.Collections.Generic; // For Dictionary

// Attribute to easily create instances in the Unity editor
[CreateAssetMenu(fileName = "GameSessionData", menuName = "Data/Game Session Data")]
public class GameSessionData : ScriptableObject
{
    public string sessionID = System.Guid.NewGuid().ToString();
    public int currentLevel = 0;
    public float playerHealth = 100f;
    public Dictionary<string, int> itemCounts = new Dictionary<string, int>();
    public Transform playerTransformReference; // Can store scene-specific references

    // Example of custom logic within a ScriptableObject
    public void AddItem(string itemName, int count)
    {
        if (itemCounts.ContainsKey(itemName))
        {
            itemCounts[itemName] += count;
        }
        else
        {
            itemCounts.Add(itemName, count);
        }
    }
}

Creating and Using Instances:

  1. In Unity, right-click in the Project window -> Create -> Data -> Game Session Data. This creates an asset file (e.g., GameSessionData.asset).
  2. Assign this asset to a public field in your MonoBehaviour scripts.

Script to Write Data:

using UnityEngine;
using System.Collections.Generic;

public class DataWriter : MonoBehaviour
{
    // Assign the ScriptableObject asset in the Inspector
    [SerializeField] private GameSessionData sessionData;

    public void UpdateSessionInfo(int level, float health, string item, int count)
    {
        if (sessionData != null)
        {
            sessionData.currentLevel = level;
            sessionData.playerHealth = health;
            sessionData.AddItem(item, count);
            sessionData.playerTransformReference = transform; // Store reference to this GameObject
        }
    }
}

Script to Read Data:

using UnityEngine;

public class DataReader : MonoBehaviour
{
    // Assign the same ScriptableObject asset in the Inspector
    [SerializeField] private GameSessionData sessionData;

    void Start()
    {
        if (sessionData != null)
        {
            Debug.Log($"Session ID: {sessionData.sessionID}");
            Debug.Log($"Current Level: {sessionData.currentLevel}");
            Debug.Log($"Player Health: {sessionData.playerHealth}");
            foreach (var item in sessionData.itemCounts)
            {
                Debug.Log($"Item: {item.Key}, Count: {item.Value}");
            }

            if (sessionData.playerTransformReference != null)
            {
                Debug.Log($"Player transform is referenced from: {sessionData.playerTransformReference.name}");
            }
        }
    }
}

Persistence Note: Changes made to ScriptableObjects in the Unity Editor persist. In a build, they typically persist only for the current session. For long-term persistence, you’d combine them with file I/O (Solution 3b) to load data at the start and save it at the end.

Solution 5: Stateless Scenes Pattern

This advanced pattern involves passing scene parameters and callbacks directly when loading a scene, creating a more functional and testable approach. It minimizes global state by encapsulating scene-specific data and handling outcomes via callbacks.

When to use:

  • For complex scene transitions where specific inputs and outputs need to be managed clearly.
  • When aiming for a cleaner, more modular scene management architecture.

Code Example:

using UnityEngine;
using UnityEngine.SceneManagement;
using System; // For Action

// Class to hold parameters for a scene load
public class SceneLoadParameters
{
    public Action<SceneOutcome> onSceneComplete;
    public string sceneName;
    // Add other input parameters as needed
    public string playerName;
}

// Class to define the outcome of a scene
public class SceneOutcome
{
    public bool success;
    public string resultMessage;
    // Add other output parameters
}

// MonoBehaviour to manage the stateless scene loading
public class StatelessSceneLoader : MonoBehaviour
{
    private static SceneLoadParameters pendingLoadParameters;

    // Method to initiate a scene load with parameters and a callback
    public static void LoadSceneAsync(SceneLoadParameters parameters)
    {
        pendingLoadParameters = parameters;
        SceneManager.LoadScene(parameters.sceneName);
    }

    void Awake()
    {
        if (pendingLoadParameters != null && pendingLoadParameters.sceneName == SceneManager.GetActiveScene().name)
        {
            // Initialize scene with parameters
            // You might find the parameters on a component attached to a persistent GameObject
            // or directly within this loader if it's also persistent.
            Debug.Log($"Scene {pendingLoadParameters.sceneName} loaded with parameters.");
            // Example: find a component to inject parameters into
            var componentToConfigure = FindObjectOfType<SceneSpecificConfig>();
            if (componentToConfigure != null)
            {
                componentToConfigure.Setup(pendingLoadParameters);
            }

            pendingLoadParameters = null; // Clear after use
        }
    }

    // Method to be called by a scene's components to signal completion
    public void NotifySceneComplete(SceneOutcome outcome)
    {
        if (pendingLoadParameters != null && pendingLoadParameters.onSceneComplete != null)
        {
            pendingLoadParameters.onSceneComplete(outcome);
            pendingLoadParameters.onSceneComplete = null; // Prevent multiple calls
        }
    }
}

// Example of a scene-specific component to receive parameters
public class SceneSpecificConfig : MonoBehaviour
{
    private SceneLoadParameters currentParameters;

    public void Setup(SceneLoadParameters parameters)
    {
        currentParameters = parameters;
        // Use parameters.playerName, etc. here
        Debug.Log($"Scene config received player name: {parameters.playerName}");
    }
}

Usage:

// In another script
public class SceneLauncher : MonoBehaviour
{
    public void LoadLevelOne()
    {
        var parameters = new SceneLoadParameters
        {
            sceneName = "LevelOneScene",
            playerName = "Hero",
            onSceneComplete = (outcome) =>
            {
                if (outcome.success)
                {
                    Debug.Log($"Level One completed with message: {outcome.resultMessage}");
                }
                else
                {
                    Debug.LogError("Level One failed.");
                }
            }
        };
        StatelessSceneLoader.LoadSceneAsync(parameters);
    }
}

Solution 6: Singleton Pattern for Game Controllers

Similar to using DontDestroyOnLoad with a static reference, the Singleton pattern provides a globally accessible point for game management and data persistence. A single instance of a controller class is created and maintained throughout the application’s lifecycle.

When to use:

  • For central game managers, audio managers, or input managers that need to be accessible from anywhere.
  • When you need a single instance of a component to manage game-wide data.

Code Example:

using UnityEngine;

public class GameController : MonoBehaviour
{
    // Static property to access the single instance
    public static GameController Instance { get; private set; }

    // Data to persist
    public int currency = 500;
    public float musicVolume = 0.7f;

    void Awake()
    {
        // Ensure only one instance of GameController exists
        if (Instance == null)
        {
            Instance = this;
            DontDestroyOnLoad(gameObject); // Keep this GameObject across scenes
        }
        else
        {
            Destroy(gameObject); // Destroy duplicate instances
        }
    }

    public void AddCurrency(int amount)
    {
        currency += amount;
    }

    public void SetMusicVolume(float volume)
    {
        musicVolume = Mathf.Clamp01(volume); // Ensure volume is between 0 and 1
        // You would typically apply this volume to an AudioSource here
    }
}

Accessing from another script:

using UnityEngine;

public class ShopManager : MonoBehaviour
{
    void PurchaseItem()
    {
        if (GameController.Instance.currency >= 100)
        {
            GameController.Instance.currency -= 100;
            Debug.Log("Item purchased! Remaining currency: " + GameController.Instance.currency);
        }
        else
        {
            Debug.Log("Not enough currency.");
        }
    }
}

Each of these methods offers distinct advantages depending on the type of data you need to pass and its persistence requirements. Choosing the right approach ensures smooth scene transitions and robust data management in your Unity projects.

FAQs on Passing Data Between Unity Scenes

Q: What is the most straightforward way to pass primitive data like integers or strings between scenes

ANS: Using static variables is the most straightforward method for passing primitive data types such as integers, booleans, floats, and strings. These variables retain their values across scene loads without needing special handling, as they are associated with the class itself rather than specific object instances.

Q: When should I use DontDestroyOnLoad

ANS: You should use DontDestroyOnLoad when you need to preserve GameObjects, Components, or any other Unity Objects that would normally be destroyed when a new scene loads. This is crucial for maintaining managers, audio systems, or any persistent elements of your game across different scenes.

Q: How can I save game data that should persist even after closing and reopening the game

ANS: For data that needs to persist beyond a single game session, such as high scores, player progress, or settings, you should use local storage mechanisms like PlayerPrefs for simple data or serialization (JSON, XML, Binary) to files for more complex data structures.

Q: Are ScriptableObjects useful for passing data between scenes

ANS: Yes, ScriptableObjects are excellent for sharing data and references across your project. They act as data containers managed within Unity’s Assets and are not tied to specific scenes or GameObjects, making them ideal for configuration data or shared game state that needs to be accessible from multiple scenes.

Q: What is the Stateless Scenes pattern

ANS: The Stateless Scenes pattern is an advanced approach where scene parameters and callbacks are passed directly during scene loading. This method promotes cleaner, more modular scene management by encapsulating scene-specific data and handling outcomes via callbacks, making the system more testable and organized.

Q: How does the Singleton pattern help with scene data persistence

ANS: The Singleton pattern, when combined with DontDestroyOnLoad, creates a single, globally accessible instance of a manager class (like a GameController). This instance persists across scenes, allowing it to act as a central hub for storing and managing game-wide data that needs to be accessible from any scene.
