“Secure C# Password Hashing: Salts, PBKDF2, and Modern Techniques”

When securing user credentials, simply hashing passwords is no longer sufficient. Proper implementation requires salting—using a unique, random value for each password hash—and employing slow, iterative key derivation functions. What are the accepted and modern approaches in C# for achieving this level of security, especially concerning algorithm choice and comparison safety?

Why Simple Hashing is Insufficient for Passwords

Fast hash algorithms like SHA-256 are designed for data integrity verification, not secret storage. As noted in several expert opinions, they are susceptible to dictionary attacks, even with salts, if the hashing process is too swift.

For password hashing you may want a slow hash algorithm, not a fast one.

The consensus points toward using adaptive key derivation functions such as PBKDF2 , bcrypt, or scrypt.

Solution Set 1: Manual Salting and SHA-256 Implementation

An initial approach involves manually combining the password and a unique salt, then applying a standard hash algorithm like SHA-256.

Concatenating and Hashing Bytes (Initial Method)

This method focuses on correctly combining byte arrays before hashing.

// Initial approach combining byte arrays manually
static byte[] GenerateSaltedHash_V1(byte[] plainText, byte[] salt)
{
  HashAlgorithm algorithm = new SHA256Managed();

  byte[] plainTextWithSaltBytes = 
    new byte[plainText.Length + salt.Length];

  // Copy plain text
  for (int i = 0; i < plainText.Length; i++)
  {
    plainTextWithSaltBytes[i] = plainText[i];
  }
  // Copy salt
  for (int i = 0; i < salt.Length; i++)
  {
    plainTextWithSaltBytes[plainText.Length + i] = salt[i];
  }

  return algorithm.ComputeHash(plainTextWithSaltBytes);            
}

Text can be converted to bytes using Encoding.UTF8.GetBytes(string). If storing the binary hash in a configuration file, use Convert.ToBase64String for serialization and Convert.FromBase64String for deserialization.

Safely Comparing Byte Arrays

Crucially, direct equality checks (==) on byte arrays compare references, not contents. A custom, byte-by-byte comparison is necessary:

public static bool CompareByteArrays_Manual(byte[] array1, byte[] array2)
{
  if (array1.Length != array2.Length)
  {
    return false;
  }

  for (int i = 0; i < array1.Length; i++)
  {
    if (array1[i] != array2[i])
    {
      return false;
    }
  }

  return true;
}

Note on Salts: Salts do not need to be confidential; they should be stored alongside the resulting hash. A new, unique salt must be generated for every password.

Alternative Array Concatenation using LINQ

A cleaner method for combining arrays utilizes LINQ’s Concat:

// Alternative array concatenation using LINQ
public static byte[] Hash_Linq(string value, byte[] salt)
{
    byte[] valueBytes = Encoding.UTF8.GetBytes(value);
    byte[] saltedValue = valueBytes.Concat(salt).ToArray();
    
    // Or using CopyTo:
    // var saltedValue = new byte[valueBytes.Length + salt.Length];
    // valueBytes.CopyTo(saltedValue, 0);
    // salt.CopyTo(saltedValue, valueBytes.Length);

    return new SHA256Managed().ComputeHash(saltedValue);
}

// Password verification using LINQ's SequenceEqual
public bool ConfirmPassword_Linq(string password, byte[] storedHash, byte[] storedSalt)
{
    byte[] passwordHash = Hash_Linq(password, storedSalt);
    // WARNING: SequenceEqual is susceptible to timing attacks (see Solution Set 4)
    return storedHash.SequenceEqual(passwordHash); 
}

Solution Set 2: Adopting PBKDF2 for Slower Hashing

Since fast hashes are discouraged for passwords, the PBKDF2 (Password-Based Key Derivation Function 2) algorithm is often recommended as it is natively available in the framework and can be tuned to be slow.

Implementing PBKDF2 with Metadata (Modern .NET 6+)

The most robust modern approach involves using Rfc2898DeriveBytes.Pbkdf2() (available in .NET 6+ via static method calls) and embedding configuration metadata directly into the output string. This allows for future configuration upgrades (like increasing iteration count) without breaking older hashes.

This solution uses hexadecimal representation via Convert.ToHexString and ensures constant-time comparison using CryptographicOperations.FixedTimeEquals to mitigate timing attacks.

// Requires Microsoft.AspNetCore.Cryptography.KeyDerivation NuGet or relevant framework features
public static class SecretHasher_Modern
{
    private const int _saltSize = 16; // 128 bits
    private const int _keySize = 32; // 256 bits for SHA256 output size
    private const int _iterations = 50000; // Higher iteration count is better
    private static readonly HashAlgorithmName _algorithm = HashAlgorithmName.SHA256;
    private const char segmentDelimiter = ':';

    public static string Hash(string input)
    {
        // 1. Generate cryptographically secure salt and hash using iterative derivation
        byte[] salt = RandomNumberGenerator.GetBytes(_saltSize);
        byte[] hash = Rfc2898DeriveBytes.Pbkdf2(
            input,
            salt,
            _iterations,
            _algorithm,
            _keySize
        );
        
        // 2. Store hash, salt, iterations, and algorithm name together (Metadata format)
        return string.Join(
            segmentDelimiter,
            Convert.ToHexString(hash),
            Convert.ToHexString(salt),
            _iterations,
            _algorithm.Name // Store algorithm name as string
        );
    }

    public static bool Verify(string input, string hashString)
    {
        string[] segments = hashString.Split(segmentDelimiter);
        if (segments.Length != 4) return false;

        try {
            byte[] storedHash = Convert.FromHexString(segments[0]);
            byte[] salt = Convert.FromHexString(segments[1]);
            int iterations = int.Parse(segments[2]);
            HashAlgorithmName algorithm = new HashAlgorithmName(segments[3]);

            // Re-derive the hash using stored parameters
            byte[] inputHash = Rfc2898DeriveBytes.Pbkdf2(
                input,
                salt,
                iterations,
                algorithm,
                storedHash.Length
            );
            
            // 3. Use fixed-time comparison to prevent timing attacks
            return CryptographicOperations.FixedTimeEquals(inputHash, storedHash);
        } catch {
            // Handle parsing or conversion errors gracefully
            return false;
        }
    }
}

PBKDF2 in older .NET Framework Environments

For older environments where Rfc2898DeriveBytes.Pbkdf2() static method is unavailable, you can use the instance constructor. Remember to store the salt separately in this pattern.

private const int SaltSize = 32;
private const int HashSize = 32;
private const int IterationCount = 10000;

public static string GeneratePasswordHash_Legacy(string password, out string salt)
{
    using (Rfc2898DeriveBytes rfc2898DeriveBytes = new Rfc2898DeriveBytes(password, SaltSize))
    {
        rfc2898DeriveBytes.IterationCount = IterationCount;
        byte[] hashData = rfc2898DeriveBytes.GetBytes(HashSize);
        byte[] saltData = rfc2898DeriveBytes.Salt;
        salt = Convert.ToBase64String(saltData); // Salt must be stored!
        return Convert.ToBase64String(hashData);
    }
}

public static bool VerifyPassword_Legacy(string password, string passwordHash, string salt)
{
    using (Rfc2898DeriveBytes rfc2898DeriveBytes = new Rfc2898DeriveBytes(password, SaltSize))
    {
        rfc2898DeriveBytes.IterationCount = IterationCount;
        rfc2898DeriveBytes.Salt = Convert.FromBase64String(salt); // Load stored salt
        byte[] hashData = rfc2898DeriveBytes.GetBytes(HashSize);
        // Comparison is still a vulnerability here if SequenceEqual is used without care.
        return Convert.ToBase64String(hashData) == passwordHash; 
    }
}

Solution Set 3: Utilizing Established Libraries

To avoid reinventing complex cryptographic handling, leverage existing, vetted Microsoft libraries.

Microsoft.AspNet.Identity Crypto Helpers

The System.Web.Helpers.Crypto package (or equivalents in ASP.NET Identity) automates salting and hashing, often using recommended standards internally.

// Using System.Web.Helpers.Crypto (if available)
var hash = Crypto.HashPassword("foo");
var verified = Crypto.VerifyHashedPassword(hash, "foo");

Built-in Password Management (ASP.NET Core)

In modern ASP.NET Core applications, the PasswordHasher<TUser> abstracts away all these details, typically using PBKDF2 with appropriate iteration counts and formats.

// Example usage with ASP.NET Identity PasswordHasher
var ph = new PasswordHasher<ApplicationUser>();
string hashedPassword = ph.HashPassword(user, "testPassword");
var verifyResult = ph.VerifyHashedPassword(user, hashedPassword, "testPassword");
// verifyResult is typically PasswordVerificationResult indicating success

Solution Set 4: Defending Against Timing Attacks

When comparing hashes or derived keys, performance differences based on input similarity can reveal information to an attacker—a timing attack. Standard array comparison methods like SequenceEqual are vulnerable because they stop comparison upon finding the first mismatch.

Implementing Constant-Time Comparison

The correct practice is to ensure the comparison loop runs to completion regardless of where the first difference occurs.

// A timing-safe byte array comparison technique
[MethodImpl(MethodImplOptions.NoOptimization)]
private static bool SlowEquals_ConstantTime(byte[] a, byte[] b)
{
    // XOR lengths first
    uint diff = (uint)a.Length ^ (uint)b.Length;
    
    // Iterate fully, accumulating differences
    for (int i = 0; i < a.Length && i < b.Length; i++)
        diff |= (uint)(a[i] ^ b[i]);
        
    return diff == 0;
}

The modern .NET solution (Solution Set 2) correctly addresses this using CryptographicOperations.FixedTimeEquals, which should be preferred over manual implementations like the one above.

Why Salts Matter: Complexity Multiplication

The purpose of the salt is to ensure that even if two users choose the exact same weak password, their stored hashes are completely different. As one source explains:

If the hackers find a match, bingo! They have your password. To solve this problem, however, we need only salt the hash… In this scenario, not only would a hacker need to guess the password, they’d have to guess the salt as well.

This forces an attacker to run the dictionary attack process for every single user record individually, drastically increasing the computational cost of cracking the database.

FAQs on C Sharp Password Hashing

Q: Should I use SHA256 for password storage in C#

ANS: No, fast hashing algorithms like SHA256 are generally not recommended alone for password storage; use slow key derivation functions like PBKDF2, bcrypt, or scrypt instead, typically by using Rfc2898DeriveBytes or higher-level identity libraries.

Q: What is the primary benefit of using a salt

ANS: A salt ensures that identical passwords result in unique hashes, defeating rainbow table attacks and forcing dictionary attacks to be re-run against every unique salt, multiplying the required computation time for an attacker.

Q: How do I prevent timing attacks when comparing hashes

ANS: Avoid array comparison methods that stop at the first difference, such as naive loops or SequenceEqual. Use constant-time comparison routines like CryptographicOperations.FixedTimeEquals or custom routines designed for this purpose.

Q: What package provides PBKDF2 functionality in modern .NET

ANS: In modern .NET (Core/.NET 5+), PBKDF2 capabilities are often found within the framework primitives accessed via Rfc2898DeriveBytes and related classes, sometimes requiring NuGet packages like Microsoft.AspNetCore.Cryptography.KeyDerivation for older framework compatibility or specific feature sets.
