“ArrayList vs List in C# Performance and Type Safety Differences”

The introduction of Generics in C# significantly altered how collections are managed. When encountering older code or specific API requirements, developers frequently face the decision between using the non-generic System.Collections.ArrayList and the type-safe System.Collections.Generic.List<T>. What are the fundamental technical distinctions that favor one over the other, particularly concerning performance, type integrity, and memory consumption?

Core Differences: Generics, Type Safety, and Casting Overhead

The primary divergence stems from the nature of these classes. List<T> is a generic collection, whereas ArrayList stores references purely as object.

Type Safety and Compile-Time Checks:

List<T> enforces type safety at compile time because you declare the specific type T it will hold. This design prevents runtime casting errors related to mixed types.

In contrast, ArrayList stores everything as object. This allows disparate types to coexist without immediate compiler intervention, leading to potential runtime failures when attempting to use an element as a specific value type (like int).

Consider this example illustrating how ArrayList permits compilation but fails at runtime, while List<T> catches the error immediately:

// Using non-generic ArrayList (Risk of Runtime Error)
System.Collections.ArrayList arrayLegacy = new System.Collections.ArrayList();
arrayLegacy.Add(10);
arrayLegacy.Add("DataPoint"); // Permitted at compile time

int sum = 0;
foreach (int item in arrayLegacy)
{
    // This line throws a runtime error because "DataPoint" cannot be cast to int
    sum += item;
}

// Using generic List<T> (Type Safety Enforced)
List<int> listModern = new List<int>();
listModern.Add(10);
// listModern.Add("DataPoint"); // <-- Compile-time error prevents execution failure
int safeSum = 0;
foreach (int number in listModern)
{
    safeSum += number;
}

The ability of List<T> to prevent runtime casting errors is a substantial advantage for application stability, as detailed in resources like the Microsoft documentation on Generics .

Boxing and Unboxing Penalties:

When value types (like int, struct) are added to the non-generic ArrayList, they must be implicitly converted to object references—a process known as boxing. When retrieved, they must be explicitly converted back, known as unboxing. This constant conversion incurs measurable CPU overhead and increases pressure on the Garbage Collector (GC).

List<T>, when instantiated with a value type (e.g., List<int>), avoids both boxing and unboxing, leading to superior performance, especially during iterative operations or when handling large volumes of value types.

Performance Implications: Benchmarks and GC Activity

The performance impact of boxing/unboxing is not negligible. Benchmarks frequently demonstrate that operations involving value types in an ArrayList can be multiple times slower than the equivalent operation in a List<T>.

Analysis shows that when adding millions of integers:

  • List<int> executes quickly with minimal GC calls.
  • ArrayList executing the same adds can take significantly longer (sometimes 5x to 7x slower), with a massive spike in Garbage Collection cycles due to the creation of numerous boxed objects.

This performance hit is detailed in external analyses examining boxing performance in C# .

Memory Footprint on Different Architectures

Memory usage also differs, especially when targeting 64-bit operating systems. ArrayList, due to its reliance on object pointers even for small value types, exhibits disproportionately higher memory consumption on 64-bit platforms compared to 32-bit systems.

For instance, an ArrayList that occupies 19MB on a 32-bit system might swell to 39MB on a 64-bit system. Conversely, a strongly-typed List<int> of 8MB on 32-bit might only increase slightly to 8.1MB on 64-bit. This memory inefficiency makes List<T> the preferred choice for applications demanding efficient resource utilization.

Thread Synchronization Capabilities

A point where ArrayList retains a specific feature is built-in, albeit inefficient, synchronization:

  1. ArrayList: Possesses the Synchronized() static method and the IsSynchronized property. The Synchronized wrapper locks the entire collection for every add or remove operation. This coarse-grained locking leads to poor scalability under heavy multi-threaded access. It also offers the SyncRoot property for fine-grained locking.

  2. List<T>: Offers no inherent thread-safety mechanisms. Developers must manually implement locking (e.g., using lock(myList) or equivalent) around collection access points to ensure thread safety, which is the recommended approach for modern concurrent programming.

Recommended Usage Scenarios

When to use List<T> (Modern Code):

  • For nearly all new development targeting .NET 2.0 and later.
  • When type safety is paramount to avoid runtime errors.
  • When performance with value types is critical (avoiding boxing).
  • When integrating with features like LINQ (IEnumerable<T>).

When ArrayList might still appear:

  • Interfacing with legacy APIs that mandate its use.
  • When managing truly heterogeneous collections of objects and performance overhead is acceptable (though List<object> is often preferred even here, as per Microsoft recommendations).

Microsoft documentation suggests:

  • For heterogeneous collections: Use List<Object>.
  • For homogeneous collections: Use List<T>.

Alternative Implementation for Thread Safety:

If thread safety is required with List<T>, instead of relying on the inefficient lock-all mechanism of ArrayList.Synchronized(), developers should wrap access using explicit locks:

List<int> threadSafeList = new List<int>();
object listLock = new object();

void AddItem(int value)
{
    lock (listLock)
    {
        threadSafeList.Add(value);
    }
}

FAQs on ArrayList vs ListT Performance Differences

Q: Is ArrayList officially deprecated

ANS: While not strictly marked as obsolete, ArrayList is generally discouraged for new development, favoring the generic List<T> collection due to type safety and performance benefits.

Q: Does List<T> also suffer from performance issues with value types

ANS: No, List<T> is specifically designed to avoid boxing and unboxing when using value types as its generic parameter T, leading to much faster access and iteration than ArrayList.

Q: How does memory use differ between ArrayList and List<T> on 64bit

ANS: ArrayList consumes significantly more memory on 64-bit systems compared to 32-bit systems due to pointer size changes interacting poorly with its object-based storage, whereas List<T> memory usage scales much more predictably.

Q: Can I use ArrayList.Synchronized with List<T>

ANS: No, the ArrayList.Synchronized() method is specific to the ArrayList class. For thread-safe operations on a List<T>, you must implement explicit locking mechanisms around the access points yourself.
