“Custom Authorization in ASP.NET Core: Strategies and Code Examples”

Implementing robust authorization in ASP.NET Core applications ensures that users only access resources and perform actions for which they have explicit permission. While the framework provides built-in authorization mechanisms, there are numerous scenarios where custom authorization logic is necessary. This exploration delves into various strategies and provides practical code examples to help you implement effective custom authorization in your ASP.NET Core projects.

The Evolving Landscape of ASP.NET Core Authorization

ASP.NET Core’s security model has evolved, offering flexible ways to define and enforce authorization. The core concepts revolve around Policies and Requirements, allowing for granular control over access.

Solution 1: Custom IAuthorizationFilter for Claim Requirements

A common need is to directly assert that a user possesses a specific claim type and value. The ASP.NET Core team advocates for a policy-based approach, but for simpler claim assertions, creating a custom attribute implementing IAuthorizationFilter can be more direct.

This solution defines a ClaimRequirementAttribute that uses a TypeFilterAttribute to apply a custom ClaimRequirementFilter. This filter checks for the presence of a specified claim.

// Define a custom attribute for claiming requirements
public class ClaimRequirementAttribute : TypeFilterAttribute
{
    // Constructor takes claim type and value to enforce
    public ClaimRequirementAttribute(string claimType, string claimValue) : base(typeof(ClaimRequirementFilter))
    {
        // Arguments are passed to the filter's constructor
        Arguments = new object[] { new System.Security.Claims.Claim(claimType, claimValue) };
    }
}

// The filter that performs the actual authorization check
public class ClaimRequirementFilter : IAuthorizationFilter
{
    // Store the claim to be checked
    readonly System.Security.Claims.Claim _claim;

    // Inject the required claim
    public ClaimRequirementFilter(System.Security.Claims.Claim claim)
    {
        _claim = claim;
    }

    // This method is called during the authorization phase
    public void OnAuthorization(AuthorizationFilterContext context)
    {
        // Check if the user has the required claim
        var hasClaim = context.HttpContext.User.Claims.Any(c => c.Type == _claim.Type && c.Value == _claim.Value);

        // If the claim is not present, forbid access
        if (!hasClaim)
        {
            context.Result = new ForbidResult();
        }
    }
}

// Example Controller usage
[Route("api/resource")]
public class MyController : Controller
{
    // Apply the custom attribute to protect this action
    [ClaimRequirement(MyClaimTypes.Permission, "CanReadResource")]
    [HttpGet]
    public IActionResult GetResource()
    {
        return Ok("Resource data retrieved successfully.");
    }
}
Solution 2: Implementing AuthorizationHandler for Age Verification

For more complex authorization logic, such as age verification based on a date of birth claim, the recommended approach is to create custom AuthorizationHandler classes. This solution demonstrates how to create an Over18Requirement that checks if a user’s DateOfBirth claim indicates they are 18 or older.

// Define a requirement for age verification
public class Over18Requirement : AuthorizationHandler<Over18Requirement>, IAuthorizationRequirement
{
    // Handle the authorization logic
    public override void Handle(AuthorizationHandlerContext context, Over18Requirement requirement)
    {
        // Check for the DateOfBirth claim
        if (!context.User.HasClaim(c => c.Type == System.Security.Claims.ClaimTypes.DateOfBirth))
        {
            context.Fail(); // Fail if the claim is missing
            return;
        }

        // Retrieve and parse the DateOfBirth claim
        var dobVal = context.User.FindFirst(c => c.Type == System.Security.Claims.ClaimTypes.DateOfBirth).Value;
        var dateOfBirth = Convert.ToDateTime(dobVal);
        int age = DateTime.Today.Year - dateOfBirth.Year;

        // Adjust age if birthday hasn't occurred this year
        if (dateOfBirth > DateTime.Today.AddYears(-age))
        {
            age--;
        }

        // Succeed if the user is 18 or older, otherwise fail
        if (age >= 18)
        {
            context.Succeed(requirement);
        }
        else
        {
            context.Fail();
        }
    }
}

Solution 3: Inheriting AuthorizeAttribute and Implementing IAuthorizationFilter

For ASP.NET Core 2 and later, you can inherit from AuthorizeAttribute and implement IAuthorizationFilter (or IAsyncAuthorizationFilter) to create custom authorization attributes that also benefit from the base AuthorizeAttribute’s functionality. This allows for both attribute-based declaration and filter-based logic.

// Create a custom attribute inheriting from AuthorizeAttribute and IAuthorizationFilter
[AttributeUsage(AttributeTargets.Class | AttributeTargets.Method, AllowMultiple = true, Inherited = true)]
public class CustomAuthorizeAttribute : AuthorizeAttribute, IAuthorizationFilter
{
    private readonly string _someFilterParameter;

    // Constructor to accept custom parameters
    public CustomAuthorizeAttribute(string someFilterParameter)
    {
        _someFilterParameter = someFilterParameter;
    }

    // Implement the authorization logic
    public void OnAuthorization(AuthorizationFilterContext context)
    {
        var user = context.HttpContext.User;

        // If not authenticated, the base AuthorizeAttribute handles redirection
        if (!user.Identity.IsAuthenticated)
        {
            return;
        }

        // Example: Accessing a service for authorization checks
        var someService = context.HttpContext.RequestServices.GetService<ISomeService>();

        var isAuthorized = someService.IsUserAuthorized(user.Identity.Name, _someFilterParameter);
        if (!isAuthorized)
        {
            context.Result = new Microsoft.AspNetCore.Mvc.StatusCodeResult((int)System.Net.HttpStatusCode.Forbidden);
            return;
        }
    }
}

Solution 5: Attribute-Driven Authorization Handlers

This approach involves creating an abstract base handler that processes custom attributes applied to controllers or actions. You then create specific handlers that inherit from this base class to implement your authorization logic.

// Abstract handler to process custom attributes
public abstract class AttributeAuthorizationHandler<TRequirement, TAttribute> : AuthorizationHandler<TRequirement>
    where TRequirement : IAuthorizationRequirement
    where TAttribute : Attribute
{
    protected override Task HandleRequirementAsync(AuthorizationHandlerContext context, TRequirement requirement)
    {
        var attributes = new List<TAttribute>();
        var actionDescriptor = (context.Resource as AuthorizationFilterContext)?.ActionDescriptor as ControllerActionDescriptor;

        if (actionDescriptor != null)
        {
            // Collect attributes from controller and method
            attributes.AddRange(GetAttributes(actionDescriptor.ControllerTypeInfo.UnderlyingSystemType));
            attributes.AddRange(GetAttributes(actionDescriptor.MethodInfo));
        }

        return HandleRequirementAsync(context, requirement, attributes);
    }

    protected abstract Task HandleRequirementAsync(AuthorizationHandlerContext context, TRequirement requirement, IEnumerable<TAttribute> attributes);

    private static IEnumerable<TAttribute> GetAttributes(MemberInfo memberInfo)
    {
        return memberInfo.GetCustomAttributes(typeof(TAttribute), false).Cast<TAttribute>();
    }
}

Solution 8: Authentication Handlers for Custom Schemes

For scenarios involving custom authentication schemes, such as Basic Authentication, you can implement custom AuthenticationHandler classes. These handlers are responsible for validating credentials and creating an authenticated ClaimsPrincipal.

// Registering the custom handler in Startup.cs or Program.cs
// services.AddAuthentication("BasicAuthentication").AddScheme<AuthenticationSchemeOptions, BasicAuthenticationHandler>("BasicAuthentication", null);

public class BasicAuthenticationHandler : AuthenticationHandler<AuthenticationSchemeOptions>
{
    private readonly IUserService _userService; // Your service to authenticate users

    public BasicAuthenticationHandler(
        IOptionsMonitor<AuthenticationSchemeOptions> options,
        ILoggerFactory logger,
        UrlEncoder encoder,
        ISystemClock clock,
        IUserService userService)
        : base(options, logger, encoder, clock)
    {
        _userService = userService;
    }

    protected override async Task<AuthenticateResult> HandleAuthenticateAsync()
    {
        // Check for Authorization header
        if (!Request.Headers.ContainsKey("Authorization"))
            return AuthenticateResult.Fail("Missing Authorization Header");

        User? user = null;
        try
        {
            // Parse and decode credentials
            var authHeader = AuthenticationHeaderValue.Parse(Request.Headers["Authorization"]);
            var credentialBytes = Convert.FromBase64String(authHeader.Parameter);
            var credentials = Encoding.UTF8.GetString(credentialBytes).Split(':', 2);
            var username = credentials[0];
            var password = credentials[1];
            user = await _userService.Authenticate(username, password); // Authenticate against your service
        }
        catch
        {
            return AuthenticateResult.Fail("Invalid Authorization Header");
        }

        if (user == null)
            return AuthenticateResult.Fail("Invalid User-name or Password");

        // Create claims and identity
        var claims = new[] {
            new Claim(ClaimTypes.NameIdentifier, user.Id.ToString()),
            new Claim(ClaimTypes.Name, user.Username),
        };
        var identity = new ClaimsIdentity(claims, Scheme.Name);
        var principal = new ClaimsPrincipal(identity);
        var ticket = new AuthenticationTicket(principal, Scheme.Name);

        return AuthenticateResult.Success(ticket);
    }
}

// Helper to get user ID from claims
public static class ClaimsPrincipalExtensions
{
    public static int? GetUserId(this ClaimsPrincipal principal)
    {
        if (principal.Identity is ClaimsIdentity identity && identity.IsAuthenticated)
        {
            var idClaim = identity.FindFirst(ClaimTypes.NameIdentifier);
            if (idClaim != null && int.TryParse(idClaim.Value, out var userId))
                return userId;
        }
        return null;
    }
}

Solution 13: Transforming Privileges to Claims with IClaimsTransformation

For scenarios where user privileges or roles are stored separately and need to be added as claims upon authentication, IClaimsTransformation is a powerful interface. This allows you to enrich the ClaimsPrincipal dynamically.

// Implement IClaimsTransformation to add claims based on privileges
public class PrivilegeToClaimTransformer : IClaimsTransformation
{
    private readonly IPrivilegeProvider _privilegeProvider; // Service to fetch privileges
    public const string PrivilegeClaimType = "http://example.com/privileges/resolved"; // Marker claim

    public PrivilegeToClaimTransformer(IPrivilegeProvider privilegeProvider)
    {
        _privilegeProvider = privilegeProvider;
    }

    public async Task<ClaimsPrincipal> TransformAsync(ClaimsPrincipal principal)
    {
        if (principal.Identity is ClaimsIdentity identity)
        {
            // Avoid reprocessing if already transformed
            if (identity.HasClaim(PrivilegeClaimType, bool.TrueString))
            {
                return principal;
            }

            // Fetch privileges for the current user
            var userPrivileges = await _privilegeProvider.GetUserPrivileges(identity);
            identity.AddClaim(new Claim(PrivilegeClaimType, bool.TrueString)); // Mark as transformed

            // Add fetched privileges as claims (e.g., roles)
            foreach (var privilege in userPrivileges)
            {
                identity.AddClaim(new Claim(ClaimTypes.Role, privilege));
            }
        }
        return principal;
    }
}

Solution 14: Modernizing AttributeAuthorizationHandler for .NET 5+

With changes in how endpoints and action descriptors are accessed in .NET 5+, the AttributeAuthorizationHandler base class needs slight adjustments to correctly retrieve metadata.

// Updated abstract handler for .NET 5+
public abstract class AttributeAuthorizationHandler<TRequirement, TAttribute> : AuthorizationHandler<TRequirement>
    where TRequirement : IAuthorizationRequirement
    where TAttribute : Attribute
{
    protected override Task HandleRequirementAsync(AuthorizationHandlerContext context, TRequirement requirement)
    {
        var attributes = new List<TAttribute>();

        // Access endpoint metadata to get ControllerActionDescriptor
        if (context.Resource is HttpContext httpContext)
        {
            var endpoint = httpContext.GetEndpoint();
            var actionDescriptor = endpoint?.Metadata.GetMetadata<ControllerActionDescriptor>();

            if (actionDescriptor != null)
            {
                attributes.AddRange(GetAttributes(actionDescriptor.ControllerTypeInfo.UnderlyingSystemType));
                attributes.AddRange(GetAttributes(actionDescriptor.MethodInfo));
            }
        }

        return HandleRequirementAsync(context, requirement, attributes);
    }

    protected abstract Task HandleRequirementAsync(AuthorizationHandlerContext context, TRequirement requirement, IEnumerable<TAttribute> attributes);

    // Helper to get attributes from MemberInfo
    private static IEnumerable<TAttribute> GetAttributes(MemberInfo memberInfo) =>
        memberInfo.GetCustomAttributes(typeof(TAttribute), false).Cast<TAttribute>();
}

// Custom attribute using TypeFilter

{

    {

        public PatientAuthFilter(IAuthService authService, PatientAccessRights[] rights)
        {
            _authService = authService;
            _requiredRights = rights;
        }

        public void OnActionExecuted(ActionExecutedContext context) { }

        public async void OnActionExecuting(ActionExecutingContext context)
        {
            // Assume a single parameter representing patient request details
            var patientRequest = context.ActionArguments.Values.OfType<IPatientRequest>().FirstOrDefault();

            if (patientRequest != null)
            {
                var accessRequest = new PatientAccessRequest
                {
                    Rights = _requiredRights,
                    MemberID = patientRequest.PatientID
                };

                // Call the service to verify access
                var result = await _authService.CheckUserPatientAccess(accessRequest);

                if (result.Status == ReturnType.Failure)
                {
                    // Return Forbidden if access is denied
                    context.Result = new StatusCodeResult((int)System.Net.HttpStatusCode.Forbidden);
                }
            }
            else
            {
                // Handle cases where the expected parameter is missing
                throw new InvalidOperationException("PatientAuthorizeAttribute requires a parameter implementing IPatientRequest.");
            }
        }
    }
}

Solution 17: Abstract Handlers for Reusable Authorization Logic

// Abstract handler for common requirement processing
public abstract class AbstractRequirementHandler<T> : IAuthorizationHandler
    where T : IAuthorizationRequirement
{
    public async Task HandleAsync(AuthorizationHandlerContext context)
    {
        // Process all pending requirements of the specified type
        var pendingRequirements = context.PendingRequirements.OfType<T>().ToList();
        foreach (var requirement in pendingRequirements)
        {
            await HandleRequirementAsync(context, requirement);
        }
    }

}

FAQs on Custom Authorization in ASP.NET Core

Q: What is the primary benefit of using custom authorization attributes in ASP.NET Core

ANS: Custom authorization attributes allow you to encapsulate specific access control logic directly onto your controllers or action methods, making your code cleaner and more declarative regarding security.

Q: How does the policy-based authorization differ from simple claim requirements

ANS: Policy-based authorization is more flexible, allowing you to combine multiple requirements (claims, roles, or custom logic handled by AuthorizationHandler) into a single named policy. Simple claim requirements typically focus on checking for a single claim’s existence.

Q: Can I inject services into custom authorization filters

ANS: Yes, by using TypeFilterAttribute or ServiceFilterAttribute when defining your custom attribute, you can leverage dependency injection to access services within your authorization filter logic.

Q: Is it better to create custom AuthorizeAttribute or implement IAuthorizationFilter directly

ANS: Inheriting from AuthorizeAttribute and implementing IAuthorizationFilter provides the benefits of the base attribute (like handling authentication schemes) while allowing you to add custom logic. Implementing IAuthorizationFilter directly is suitable for simpler scenarios or when you don’t need the base AuthorizeAttribute features.

Q: How do I handle authorization based on dynamic data, like user roles fetched from a database

ANS: This is typically achieved by creating a custom AuthorizationHandler. The handler can inject a service that retrieves the user’s dynamic roles or permissions from a database and then uses this information to call context.Succeed() or context.Fail().

Q: What is the role of IAuthorizationHandler

ANS: IAuthorizationHandler is responsible for evaluating IAuthorizationRequirements. It contains the core logic to determine whether a user meets the criteria defined by a requirement and signals success or failure to the AuthorizationHandlerContext.

Q: Can I create authorization logic that checks multiple conditions

ANS: Absolutely. You can define a single policy that includes multiple requirements, or within a custom AuthorizationHandler, you can implement complex logic that checks various claims, roles, or external data sources.

{
    readonly Claim _claim;

    public ClaimRequirementFilter(Claim claim)
    {
        _claim = claim;
    }

    public void OnAuthorization(AuthorizationFilterContext context)
    {
        var hasClaim = context.HttpContext.User.Claims.Any(c =&gt; c.Type == _claim.Type &amp;&amp; c.Value == _claim.Value);
        if (!hasClaim)
        {

        }
    }
}
