“JSON Deserialization Security Risks with Json.NET TypeNameHandling”

When employing Json.NET in your .NET applications, particularly with TypeNameHandling.All, it’s crucial to address inherent security risks. Without proper safeguards, this feature can inadvertently create avenues for malicious code execution.

How TypeNameHandling.All Can Be Exploited

When TypeNameHandling.All is active and no SerializationBinder is configured, Json.NET attempts to instantiate the exact type specified in the incoming JSON’s metadata. This opens the door for an attacker to supply a serialized representation of a dangerous type present within your application’s code or even the .NET framework itself.

Consider a simple scenario:

public class Vehicle
{
    public string Manufacturer { get; set; }
    public string ModelName { get; set; }
}

A legitimate JSON payload might look like this:

{
   "$type": "Vehicle",
   "Manufacturer": "Toyota",
   "ModelName": "Camry"
}

This payload allows Json.NET to correctly create a Vehicle object and populate its properties.

However, an attacker could craft a payload referencing a class like System.CodeDom.Compiler.TempFileCollection. This class, designed to manage temporary compilation files, has a finalizer that deletes associated files. An attacker could serialize TempFileCollection to point its file collection to critical system files, and upon deserialization, the finalizer could be triggered to delete these files without any direct user interaction.

Here’s a conceptual example of such a malicious payload:

{
   "$type": "System.CodeDom.Compiler.TempFileCollection",
   "BasePath": "%SYSTEMDRIVE",
   "KeepFiles": "False",
   "TempDir": "%SYSTEMROOT%"
}

This hypothetical payload aims to leverage the TempFileCollection’s destructors to delete files based on attacker-controlled paths during the deserialization process.

using System;
using System.Collections;
using System.IO;

[Serializable]
public class TempFileCollection
{
    private Hashtable files;
    public bool KeepFiles { get; set; } // Added for clarity in example
    public string BasePath { get; set; } // Added for clarity in example
    public string TempDir { get; set; } // Added for clarity in example

    ~TempFileCollection()
    {
        if (KeepFiles) { return; }
        // In a real scenario, this would iterate through 'files'
        // For demonstration, we simulate a file deletion attempt
        string potentialFilePath = Path.Combine(BasePath, "malicious_file.txt");
        try
        {
            // This is a simulated deletion for demonstration; actual path would come from 'files'
            if (File.Exists(potentialFilePath))
            {
                File.Delete(potentialFilePath);
                Console.WriteLine($"Attempted to delete: {potentialFilePath}");
            }
        }
        catch (Exception ex)
        {
            Console.WriteLine($"Error deleting file: {ex.Message}");
        }
    }
}

The serialized representation that an attacker might use could look like this:

{
   "$type": "System.CodeDom.Compiler.TempFileCollection",
   "BasePath": "C:\\",
   "KeepFiles": "False",
   "TempDir": "C:\\Windows\\Temp"
}

Additional Attack Vectors

Further research, notably Alvaro Muñoz & Oleksandr Mirosh’s blackhat paper, highlights additional .NET attack gadgets that can be exploited through deserialization:

  • System.Configuration.Install.AssemblyInstaller: This can lead to payload execution upon assembly loading.
  • System.Activities.Presentation.WorkflowDesigner: Allows for static method execution during the parsing of XAML payloads.
  • System.Windows.ResourceDictionary: An attacker can serve a XAML payload from a controlled server, setting the ContentType to application/xaml+xml. The target server might then execute a desired static method during XAML parsing.
  • System.Windows.Data.ObjectDataProvider: Offers several attack vectors, including calling arbitrary methods (even static ones) with controlled parameters, or invoking parametrized constructors of chosen types.
  • System.Windows.Forms.BindingSource: Enables arbitrary getter calls.
  • Microsoft.Exchange.Management.SystemManager.WinForms.ExchangeSettingsProvider: Facilitates jumps from setters to nested BinaryFormatter deserialization, creating further vulnerabilities.

For a more exhaustive list, consult the OWASP Cheat Sheet Series: Deserialization Cheat Sheet. It’s important to note that for an attack to succeed, the gadget type must be assignable to the type expected during deserialization. This is particularly relevant when deserializing to object or dynamic.

Mitigation Strategies

To prevent these vulnerabilities, consider the following:

  1. Avoid TypeNameHandling.All or TypeNameHandling.Objects: If possible, do not use these settings. If you must serialize types, ensure they are strictly controlled.

  2. Implement SerializationBinder: This is the most robust solution. A SerializationBinder allows you to explicitly control which types are allowed during deserialization. You can create a whitelist of approved types.

    public class AllowedTypeBinder : Newtonsoft.Json.Serialization.ISerializationBinder
{
    public void BindToName(Type serializedType, out string assemblyName, out string typeName)
    {
        assemblyName = serializedType.Assembly.FullName;
        typeName = serializedType.FullName;
    }

    public Type BindToType(string assemblyName, string typeName)
    {
        // Define your whitelist of allowed types
        var allowedTypes = new Dictionary<string, Type>
        {
            { "YourNamespace.YourType", typeof(YourNamespace.YourType) },
            { "System.String", typeof(string) },
            { "Vehicle", typeof(Vehicle) } // Example for our Vehicle class
        };

        if (allowedTypes.TryGetValue(typeName, out Type type))
        {
            return type;
        }
        else
        {
            throw new JsonSerializationException($"Type '{typeName}' is not allowed for deserialization.");
        }
    }
}

    Then, when deserializing:

    var settings = new JsonSerializerSettings
{
    TypeNameHandling = TypeNameHandling.All,
    SerializationBinder = new AllowedTypeBinder()
};
var obj = JsonConvert.DeserializeObject<object>(json, settings);

  3. Validate Input: Always sanitize and validate any incoming JSON data before deserialization, especially if TypeNameHandling is enabled.

  4. Limit Permissions: Ensure the application’s execution context has minimal necessary permissions to reduce the impact of a successful exploit.

By understanding these risks and implementing appropriate security measures, you can significantly enhance the safety of your JSON deserialization processes.

FAQs on JSON Deserialization Security

Q: What is the main risk associated with Json.Net's TypeNameHandling All

ANS: The primary risk is deserializing untrusted JSON which can contain malicious types, leading to arbitrary code execution or denial-of-service attacks by exploiting known .NET attack gadgets.

Q: How does a SerializationBinder help prevent these attacks

ANS: A SerializationBinder acts as a gatekeeper, allowing you to define a strict whitelist of permissible types for deserialization. Any type not on this list will be rejected, preventing the instantiation of dangerous classes.

Q: Can System.CodeDom.Compiler.TempFileCollection be used for attacks

ANS: Yes, System.CodeDom.Compiler.TempFileCollection can be exploited. Its finalizer, which deletes temporary files, can be tricked into deleting arbitrary files on the system if the class is serialized with malicious intent.

Q: What are attack gadgets in the context of deserialization

ANS: Attack gadgets are specific classes or methods within the .NET framework or application code that can be leveraged by an attacker during deserialization to achieve malicious outcomes, such as executing arbitrary code.

Q: Should I use TypeNameHandling Objects

ANS: Using TypeNameHandling.Objects carries similar risks to TypeNameHandling.All. It still attempts to deserialize specific types based on metadata, making it vulnerable if not paired with a SerializationBinder or other strong validation measures.
