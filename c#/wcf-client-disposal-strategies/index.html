“Optimal WCF Client Disposal: Strategies to Avoid CommunicationException on Close”

When dealing with Windows Communication Foundation (WCF) clients, correctly managing the object lifecycle, particularly when implementing IDisposable, is crucial. An improper cleanup sequence can frequently lead to a CommunicationException if the underlying channel state is not handled correctly (e.g., trying to Close() an already faulted channel).

What are the expert-recommended patterns and higher-order functions to ensure WCF client channels are safely closed or aborted, thereby preventing runtime exceptions during disposal?

Expert Solutions for Safe WCF Channel Management

Several robust patterns emerge from community experience to wrap WCF interactions, making the client usage clean while guaranteeing proper resource teardown.

Solution 1: Higher-Order Function with Captured Variables (Simple Block Execution)

This approach uses a void-returning wrapper that executes code within a scope, requiring an external variable to capture any return value from the service call.

// Example of a simple execution block
Service<IOrderService>.Use(orderService =>
{
  orderService.PlaceOrder(request);
});

// Handling return values via a captured variable
int newOrderId = 0; // Must be definitely assigned before the scope
Service<IOrderService>.Use(orderService =>
{
    newOrderId = orderService.PlaceOrder(request);
});
Console.WriteLine(newOrderId); // Outputs the updated ID

Solution 2: Overriding Dispose() with State Check

Preferring the simplicity of the using statement, this involves creating a custom class (or overriding the generated client’s Dispose()) that checks the State before attempting to Close(). This guards against calling Close() on a channel already in the Faulted state.

void IDisposable.Dispose()
{
    bool success = false;
    try 
    {
        // Only attempt to close if not already faulted
        if (State != CommunicationState.Faulted) 
        {
            Close();
            success = true;
        }
    } 
    finally 
    {
        // Abort if closing failed (or was skipped due to being faulted)
        if (!success) 
            Abort();
    }
}

Solution 3: Higher-Order Function Returning a Value (TReturn UseService<TChannel, TReturn>)

A more elegant solution involves a generic higher-order function that manages the channel factory, creation, closing, and aborting logic, allowing direct return values from the service operation.

TReturn UseService<TChannel, TReturn>(Func<TChannel, TReturn> code)
{
    var chanFactory = GetCachedFactory<TChannel>();
    TChannel channel = chanFactory.CreateChannel();
    bool error = true;
    try {
        TReturn result = code((TChannel)channel);
        ((IClientChannel)channel).Close();
        error = false;
        return result;
    }
    finally {
        if (error) {
            ((IClientChannel)channel).Abort();
        }
    }
}

// Usage example:
int a = 1;
int b = 2;
int sum = UseService<ICalculator, int>((calc) => calc.Add(a, b));
Console.WriteLine(sum);

This pattern is often preferred for its conciseness and ability to handle returns seamlessly.

Solution 4: Microsoft’s Recommended try-catch-finally Structure

The Microsoft standard relies on explicit exception handling around the call sequence, ensuring Abort() is called within the catch or finally blocks when exceptions occur.

    double result = client.Add(value1, value2);

Solution 6: Extension Method for Safe Disposal (DisposeSafely)

This creates a clean structure resembling the using statement by wrapping the execution inside a Do method that calls a custom extension method DisposeSafely in the finally block.

public static class UsingServiceClient
{
    public static void Do<TClient>(TClient client, Action<TClient> execute)
        where TClient : class, ICommunicationObject
    {
        try
        {
            execute(client);
        }
        finally
        {
            client.DisposeSafely(); // Calls the custom logic
        }
    }

    public static void DisposeSafely(this ICommunicationObject client)
    {
        if (client == null) return;

        bool success = false;
        try
        {
            if (client.State != CommunicationState.Faulted)
            {
                client.Close();
                success = true;
            }
        }
        finally
        {
            if (!success)
            {
                client.Abort();
            }
        }
    }
}

// Usage:
string result = string.Empty;
UsingServiceClient.Do(
    new MyServiceClient(),
    client => result = client.GetServiceResult(parameters));

Solution 8: Wrapper with Built-in Retry Logic

For environments prone to transient network issues, one can embed retry logic within the wrapper itself. This attempts the operation multiple times upon specific transient exceptions before finally failing after the maximum attempts.

This example attempts 5 times with an increasing delay:

public static class Service<T>
{
    // ... factory setup ...
    public static void Use(UseServiceDelegate<T> codeBlock)
    {
        IClientChannel proxy = (IClientChannel)_channelFactory.CreateChannel();
        bool success = false;
        Exception mostRecentEx = null;
        int millsecondsToSleep = 1000;

        for(int i=0; i<5; i++)  // Attempt a maximum of 5 times 
        {
            try
            {
                codeBlock((T)proxy);
                proxy.Close();
                success = true; 
                break;
            }
            // Catch transient exceptions (CTE, ENFE, STBE, TimeoutException, CommunicationException)
            catch (Exception ex) when (ex is ChannelTerminatedException || ex is EndpointNotFoundException || ex is ServerTooBusyException || ex is TimeoutException || ex is CommunicationException)
            {
                mostRecentEx = ex;
                proxy.Abort();
                // Delay (backoff) and retry 
                Thread.Sleep(millsecondsToSleep * (i + 1)); 
            }
            catch(Exception)
            {
                // Rethrow non-transient exceptions immediately
                proxy.Abort();
                throw ;  
            }
        }
        if (success == false && mostRecentEx != null) 
        { 
            proxy.Abort();
            throw new Exception("WCF call failed after 5 retries.", mostRecentEx );
        }
    }
}

Solution 24: Inherited Client with Overridden Dispose

For users of auto-generated clients (ClientBase<T>), inheriting the client and overriding or implementing Dispose provides a clean way to enforce correct channel management without modifying the original proxy code extensively.

public class WcfClient<TService> : ClientBase<TService>, IDisposable
    where TService : class
{
    // ... Constructors ...

    protected virtual void OnDispose()
    {
        bool success = false;
        var channel = base.Channel as IClientChannel;

        if (channel != null)
        {
            try
            {
                if (channel.State != CommunicationState.Faulted)
                {
                    channel.Close();
                    success = true;
                }
            }
            finally
            {
                if (!success)
                {
                    channel.Abort();
                }
            }
        }
    }

    public void Dispose()
    {
        OnDispose();
    }
}
// Usage:
using (WcfClient<IOrderService> orderService = new WcfClient<IOrderService>())
{
    results = orderService.GetProxy().PlaceOrder(input);
}

Alternative: Basic Try-Finally with State Check (Solution 15)

A straightforward implementation focusing only on checking the state before closing or aborting in the finally block is often sufficient if exceptions are not expected to require retry logic.

var client = new ProxyClient();
try
{
    // Perform WCF operations...
    client.SomeOperation();
    client.Close();
}
finally
{
    // Only abort if Close() was not successfully called (i.e., channel is not Closed)
    if(client.State != CommunicationState.Closed)
        client.Abort();
}

FAQs on WCF Client Disposal Strategies

Q: Why does WCF client disposal throw CommunicationException

ANS: This typically happens when the client channel is in a non-clean state, most commonly Faulted, yet the default IDisposable implementation attempts to call Close() instead of Abort(). An explicit check for State != CommunicationState.Faulted before calling Close() resolves this.

Q: Should I always use Close or Abort for IDisposable

ANS: If the operation completed successfully, use Close() for an orderly shutdown. If an exception occurred, or if the state is already Faulted, use Abort() to tear down the connection immediately without waiting for timeouts.

Q: Can I use the 'using' statement easily with ChannelFactory

ANS: Not directly, as the channel returned by CreateChannel() doesn’t implement IDisposable correctly. Solutions like Solution 3, 6, or 14 create wrapper types or higher-order functions that implement correct disposal logic, enabling seamless using statement usage.

Q: What happens if I don't dispose of a WCF client

ANS: If you don’t dispose of it explicitly, network resources held by the channel may eventually be released by the Garbage Collector (GC), but this is unreliable, can lead to resource exhaustion, and might cause the channel to be aborted instead of closed cleanly. Explicit disposal is best practice.
