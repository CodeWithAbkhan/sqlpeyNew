“ASP.NET Core DI: Registering and Resolving Multiple Interface Implementations by Key”

How can one effectively register multiple distinct concrete classes that all implement the same interface within the Microsoft.Extensions.DependencyInjection container, and subsequently resolve a specific implementation at runtime based on an identifying key or name? The default container lacks direct support for named registrations, prompting various creative workarounds.

Below are several established strategies to address this common requirement, ranging from using factory patterns to leveraging newer .NET features.

Workaround 1: Employing a Custom Resolver Delegate (Factory Function)

A straightforward approach involves defining a shared delegate that acts as a factory function. This function accepts a key (like a string) and uses the IServiceProvider to retrieve the correct service instance.

In Startup.cs (or Program.cs for minimal hosting models):

  1. Define the Shared Delegate:

    public delegate IService ServiceResolver(string key);

  2. Register Concrete Services and the Resolver Function: Ensure all implementations (ServiceA, ServiceB, ServiceC) are registered first. Then, register the ServiceResolver using a lambda that contains a switch statement for key mapping.

    services.AddTransient<ServiceA>();
services.AddTransient<ServiceB>();
services.AddTransient<ServiceC>();

services.AddTransient<ServiceResolver>(serviceProvider => key =>
{
    switch (key)
    {
        case "A":
            return serviceProvider.GetService<ServiceA>();
        case "B":
            return serviceProvider.GetService<ServiceB>();
        case "C":
            return serviceProvider.GetService<ServiceC>();
        default:
            throw new KeyNotFoundException($"Service key '{key}' not found.");
    }
});

  3. Usage in a Consumer: Inject the ServiceResolver delegate and invoke it with the required key.

    public class Consumer
{
    private readonly IService _aService;

    public Consumer(ServiceResolver serviceAccessor)
    {
        // Resolve ServiceA using the key "A"
        _aService = serviceAccessor("A");
    }

    public void ExecuteServiceOperation()
    {
        _aService.DoTheThing(); // Assuming IService has DoTheThing()
    }
}

This method keeps the resolution logic centralized but might lead to a large switch statement if many services are involved. For scalability, consider mapping keys to types using a Dictionary<string, Type> instead of a switch.

Workaround 2: Leveraging GetServices and LINQ Filtering

An alternative is to register all implementations of the base interface (IService) and retrieve them as an IEnumerable<IService>. Selection is then performed client-side using LINQ based on type, or potentially a property if the interface defines one (e.g., a Name property).

Registration:

services.AddSingleton<IService, ServiceA>();
services.AddSingleton<IService, ServiceB>();
services.AddSingleton<IService, ServiceC>();

Resolution (Example using Type comparison):

var services = serviceProvider.GetServices<IService>();
// Retrieve ServiceB explicitly
var serviceB = services.First(o => o.GetType() == typeof(ServiceB));

Note: This approach can sometimes be viewed as leaning towards the Service Locator pattern, as the client code handles the selection logic rather than the container itself.

Workaround 3: Interface Inheritance Hierarchy (Type-Safe Naming)

Instead of using strings or external keys, you can enforce named resolution through strong typing by creating specific interfaces that inherit from the base interface.

  1. Define Specific Interfaces:

    public interface IService { }
public interface IServiceA : IService { }
public interface IServiceB : IService { }
public interface IServiceC : IService { }

  2. Implement and Register Specific Interfaces:

    public class ServiceA : IServiceA { }
public class ServiceB : IServiceB { }

// Registration using the derived interfaces
container.Register<IServiceA, ServiceA>();
container.Register<IServiceB, ServiceB>();

  3. Usage: Consumers explicitly request the interface variant they need, ensuring compile-time safety.

    public class Consumer
{
    public Consumer(IServiceA serviceAInstance, IServiceB serviceBInstance)
    {
        // ... use serviceAInstance and serviceBInstance
    }
}

This is highly type-safe but requires creating new interfaces for every distinct implementation variant.

Workaround 4: Injecting IEnumerable<T> for All Implementations

Similar to Workaround 2, but explicitly injecting the collection into the consumer and performing filtering. This is often used when you need all services that implement an interface, or when you apply filtering logic in a dedicated factory class wrapping the collection.

Registration: Register all implementations against the base interface (IService):

// Example using reflection to dynamically register all types implementing IService
Assembly.GetEntryAssembly().GetTypesAssignableFrom<IService>().ForEach((t) =>
{
    services.AddScoped(typeof(IService), t);
});

Usage:

public class MyController
{
    private readonly IEnumerable<IService> _services;
    
    public MyController(IEnumerable<IService> services)
    {
        _services = services;
    }
    
    public void LocateAndUseSpecificService()
    {
        // Assuming IService has a Name property for identification
        var specificService = _services.FirstOrDefault(s => s.Name == "TargetName");
        specificService?.PerformAction();
    }
}

Workaround 5: Using Generic Type Parameters for Distinction

If the different implementations serve distinct purposes that can be categorized by a type, you can use generics. Each service registers against IService<T> where T differentiates it.

Registration:

// Registering ServiceA specifically for the 'CustomerSavedConsumer' context
services.AddTransient<IService<CustomerSavedConsumer>, ServiceA>();
services.AddTransient<IService<ManagerSavedConsumer>, ServiceB>();

Usage: The consumer injects the specific generic type needed.

public class MyController
{
    // Direct, compile-time safe injection of the needed variant
    private readonly IService<CustomerSavedConsumer> _customerService;

    public MyController(IService<CustomerSavedConsumer> customerService)
    {
        _customerService = customerService;
    }
}

This method is very clean and provides compile-time safety, provided your scenario naturally fits a generic categorization.

Workaround 6: Keyed Dependency Injection (Modern .NET 8+)

For applications running on .NET 8 or later, the framework introduced native support for Keyed DI Services, which directly solves this problem without custom factories or complex workarounds.

Registration (in Program.cs):

builder.Services.AddKeyedSingleton<IMemoryCache, BigCache>("big_cache_key");
builder.Services.AddKeyedSingleton<IMemoryCache, SmallCache>("small_cache_key");

Usage: Use the [FromKeyedServices] attribute on constructor parameters to specify which keyed service to inject.

class CacheConsumer([FromKeyedServices("big_cache_key")] IMemoryCache cache)
{
    public object GetData() => cache.Get("data");
}

If the IKeyedServiceProvider is needed for runtime resolution, it can also be injected. This is the recommended approach for modern applications.

Workaround 7: Utilizing a Dictionary Mapping

Registering an entire Dictionary<string, TService> containing all instances is another pattern. The dictionary itself is registered as a singleton, and consumers resolve the dictionary to look up instances by key.

Registration: Manually instantiate and register the dictionary.

var dbConnections = new Dictionary<string, IConnectionFactory>(StringComparer.OrdinalIgnoreCase)
{
    { "ReadDB", new ConnectionFactory("connectionString1") },
    { "LogDB", new ConnectionFactory("connectionString5") }
};
services.AddSingleton(dbConnections);

Resolution: Consumers either inject the dictionary directly or use a factory function that abstracts the dictionary lookup:

// Direct Dictionary resolution
var logDb = serviceProvider.GetRequiredService<Dictionary<string, IConnectionFactory>>()["LogDB"];

This method is fast (hash map lookup) but requires exposing the dictionary type or abstracting it slightly more complexly than a simple Func.

Workaround 8: Switching to an External IoC Container (e.g., StructureMap)

If the built-in container’s limitations are too restrictive, you can replace it entirely (or augment it) with a third-party IoC container like StructureMap, which natively supports named registrations.

This involves swapping services.BuildServiceProvider() with the external container’s setup and configuration, and ensuring the ASP.NET Core pipeline uses the container’s resulting IServiceProvider.

StructureMap Registration Example Snippet:

container.Configure(config =>
{
    config.For<IPet>().Use<Cat>().Named("A");
    config.For<IPet>().Use<Dog>().Named("B");
    config.Populate(services); // Integrate with existing services
});
return container.GetInstance<IServiceProvider>();

This grants access to richer features like named resolution directly within the container’s API.

Workaround 9: Custom Factory Pattern with Extension Methods

This involves creating a dedicated, fluent factory builder structure. This approach registers services dynamically based on key/type mappings provided through fluent extension methods, often resulting in lazy instantiation of the correct service. This avoids the anti-pattern of putting resolution logic inside the service itself.

Workaround 10: Visitor/Engine Pattern for Decision Making

Instead of having consumers select services via a key, introduce a decision engine (e.g., IServiceDecisionEngine<TContext>). This engine encapsulates the business logic required to determine which specific implementation (ServiceA or ServiceB) is required based on context data, and only injects the necessary concrete services into the engine itself.

FAQs on Registering and Resolving Multiple Interface Implementations by Key

Q: Is using Func<string, IService> considered the Service Locator anti-pattern

ANS: Yes, relying heavily on a factory function that requires looking up services by a key often shares characteristics with the Service Locator pattern, which is generally discouraged because it hides dependencies at compile time. However, in the context of required named resolution absent native support, it is a pragmatic workaround.

Q: Can I use the implementation's ToString() method for identification

ANS: Yes, one proposed solution suggests registering services and then using IServiceProvider.GetServices<T>() followed by filtering the resulting collection using the object’s ToString() result as the identifier key. This requires modifying the implementation to override ToString().

Q: What is the best approach if I am using .NET 8 or newer

ANS: The best and officially supported method for keyed resolution is using Keyed DI services via AddKeyedSingleton, AddKeyedScoped, AddKeyedTransient, and injecting via the [FromKeyedServices] attribute.

Q: Does using IEnumerable<IService> violate DI principles

ANS: Injecting IEnumerable<T> to receive all registered implementations is a supported pattern by Microsoft. The potential design issue arises if the consuming class then uses complex logic (like type checking) to select one instance, which deviates from the Single Responsibility Principle.
