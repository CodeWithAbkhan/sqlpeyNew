“SQL Server: Efficiently Pass Arrays to Stored Procedures”

When working with SQL Server, a common challenge arises in how to effectively pass collections or arrays of data to stored procedures. This is crucial for operations like bulk inserts, updates, or filtering based on a list of identifiers. Fortunately, SQL Server offers several robust mechanisms to handle this scenario, each with its own advantages depending on your specific needs and the SQL Server version you are utilizing.

Let’s delve into the various approaches, from older, simpler methods to more modern, performant techniques.

Solution 1: Leveraging STRING_SPLIT and OPENJSON (SQL Server 2016+)

For SQL Server 2016 and later, the introduction of STRING_SPLIT and OPENJSON provides streamlined ways to handle delimited strings and JSON arrays.

Using STRING_SPLIT

This function allows you to break a delimited string into rows.

Stored Procedure Example:

CREATE PROCEDURE dbo.ProcessEmployeeListString
  @EmployeeIDs varchar(max)
AS
BEGIN
  SET NOCOUNT ON;

  SELECT EmployeeId = value
  FROM STRING_SPLIT(@EmployeeIDs, ',');
END
GO

-- Execution:
EXEC dbo.ProcessEmployeeListString @EmployeeIDs = '101,102,103';
Using OPENJSON

This function parses JSON text and returns objects and properties from the JSON input as rows and columns.

Stored Procedure Example:

CREATE PROCEDURE dbo.ProcessEmployeeListJson
  @EmployeeIDsJson varchar(max)
AS
BEGIN
  SET NOCOUNT ON;

  SELECT EmployeeId = value
  FROM OPENJSON(@EmployeeIDsJson);
END
GO

-- Execution:
EXEC dbo.ProcessEmployeeListJson @EmployeeIDsJson = '[101, 102, 103]';

Solution 2: Table-Valued Parameters (TVPs) (SQL Server 2008+)

Table-Valued Parameters are user-defined table types that you can use to pass multiple rows of data into a stored procedure or function. This is generally considered a highly efficient and maintainable approach.

1. Create a User-Defined Table Type:

CREATE TYPE dbo.EmployeeIDList AS TABLE
(
  EmployeeId INT PRIMARY KEY -- Consider adding a primary key for performance
);
GO

2. Create the Stored Procedure:

CREATE PROCEDURE dbo.ProcessEmployeeListTVP
  @EmployeeIDs dbo.EmployeeIDList READONLY
AS
BEGIN
  SET NOCOUNT ON;

  SELECT EmployeeId
  FROM @EmployeeIDs;
END
GO

3. C# Code Example to Populate and Pass TVP:

// Assume 'connection' is an open SqlConnection
int[] employeeIdsArray = { 101, 102, 103 }; // Your array of IDs

DataTable tvpDataTable = new DataTable();
tvpDataTable.Columns.Add(new DataColumn("EmployeeId", typeof(int)));

foreach (var id in employeeIdsArray)
{
    tvpDataTable.Rows.Add(id);
}

using (var connection = new System.Data.SqlClient.SqlConnection("YourConnectionString"))
{
    connection.Open();
    SqlCommand cmd = new SqlCommand("dbo.ProcessEmployeeListTVP", connection);
    cmd.CommandType = CommandType.StoredProcedure;

    SqlParameter tvpParameter = cmd.Parameters.AddWithValue("@EmployeeIDs", tvpDataTable);
    tvpParameter.SqlDbType = SqlDbType.Structured;
    tvpParameter.TypeName = "dbo.EmployeeIDList"; // Must match the created TYPE name

    cmd.ExecuteNonQuery();
}

Solution 3: XML Parameters (SQL Server 2005+)

Passing data as XML is a versatile method that has been available since SQL Server 2005.

Stored Procedure Example:

CREATE PROCEDURE dbo.ProcessEmployeeListXml
    @EmployeeIdsXml XML
AS
BEGIN
    DECLARE @EmployeeList TABLE (EmployeeId BIGINT);

    INSERT INTO @EmployeeList (EmployeeId)
    SELECT EmployeeNode.value('.', 'BIGINT')
    FROM @EmployeeIdsXml.nodes('/ArrayOfIds/Id') AS XmlData(EmployeeNode);

    SELECT EmployeeId FROM @EmployeeList;
END
GO

-- XML Schema Collection for data integrity (Optional but Recommended)
IF NOT EXISTS (SELECT * FROM sys.xml_schema_collections WHERE name = 'xsdArrayOfBigInt')
BEGIN
    CREATE XML SCHEMA COLLECTION [dbo].[xsdArrayOfBigInt]
    AS N'<xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
        <xs:element name="ArrayOfIds">
            <xs:complexType>
                <xs:sequence>
                    <xs:element maxOccurs="unbounded" name="Id" type="xs:unsignedLong" />
                </xs:sequence>
            </xs:complexType>
        </xs:element>
    </xs:schema>';
END
GO

-- Execution with XML:
EXEC dbo.ProcessEmployeeListXml @EmployeeIdsXml = '<ArrayOfIds><Id>101</Id><Id>102</Id><Id>103</Id></ArrayOfIds>';

Solution 4: String Concatenation with Pattern Matching (All SQL Server Versions)

A simpler, though potentially less performant for large datasets, method is to pass a delimited string and use LIKE for pattern matching. This is best when the list is relatively small.

Stored Procedure Example:

CREATE PROCEDURE dbo.ProcessEmployeeListLike
  @EmployeeIdListWithDelimiters VARCHAR(MAX) -- e.g., ';101;102;103;'
AS
BEGIN
  SET NOCOUNT ON;

  SELECT EmployeeId
  FROM EmployeesTable -- Replace with your actual employee table
  WHERE @EmployeeIdListWithDelimiters LIKE '%;' + CAST(EmployeeId AS VARCHAR(20)) + ';%';
END
GO

-- Execution:
EXEC dbo.ProcessEmployeeListLike @EmployeeIdListWithDelimiters = ';101;102;103;';

Solution 5: User-Defined Functions for String Splitting (SQL Server 2005+)

Before STRING_SPLIT was available, creating a custom function to split strings was a common practice.

Custom Split Function:

CREATE FUNCTION dbo.SplitStringToInts
(
   @InputList      VARCHAR(MAX),
   @Delimiter VARCHAR(255) = ',' -- Default delimiter is comma
)
RETURNS TABLE
AS
  RETURN (
      SELECT Item = CONVERT(INT, Item)
      FROM
      (
          SELECT Item = x.i.value('(./text())[1]', 'VARCHAR(MAX)')
          FROM
          (
              SELECT [XMLData] = CONVERT(XML, '<i>' + REPLACE(@InputList, @Delimiter, '</i><i>') + '</i>').query('.')
          ) AS a
          CROSS APPLY [XMLData].nodes('i') AS x(i)
      ) AS y
      WHERE Item IS NOT NULL
  );
GO

Stored Procedure Using the Function:

CREATE PROCEDURE dbo.ProcessEmployeeListCustomSplit
  @EmployeeIdList VARCHAR(MAX)
AS
BEGIN
  SET NOCOUNT ON;

  SELECT EmployeeId = Item
  FROM dbo.SplitStringToInts(@EmployeeIdList, ',');
END
GO

-- Execution:
EXEC dbo.ProcessEmployeeListCustomSplit @EmployeeIdList = '101,102,103';

Performance and Maintainability Considerations

  • Table-Valued Parameters (TVPs): Generally offer the best combination of performance and maintainability, especially for larger datasets. They provide strong typing and efficient data streaming to the stored procedure without requiring in-memory duplication for large collections. This contrasts with DataTable methods which can duplicate data.
  • STRING_SPLIT and OPENJSON: Excellent choices for SQL Server 2016+ due to their built-in nature and efficiency. STRING_SPLIT is straightforward for delimited strings, while OPENJSON is ideal for JSON arrays.
  • XML Parameters: A solid option for older versions or when dealing with more complex hierarchical data. However, they can introduce overhead due to XML parsing and can be less performant than TVPs for simple lists.
  • String Concatenation with LIKE: Suitable for very small lists where performance is not a critical concern. It’s simple to implement but can become a bottleneck with larger datasets.
  • Custom Split Functions: A good fallback for pre-SQL Server 2016 environments when STRING_SPLIT is unavailable, especially when you need granular control over the splitting logic. However, these can be slower than built-in functions.

When choosing a method, consider the size of your data, the SQL Server version you are running, and the importance of code maintainability.

FAQs on SQL Server Pass Arrays

Q: What is the best way to pass an array to a SQL Server stored procedure

ANS: The most recommended and efficient method for modern SQL Server versions (2008+) is using Table-Valued Parameters (TVPs). For SQL Server 2016 and newer, STRING_SPLIT and OPENJSON are also excellent, performant choices for specific data formats.

Q: Can I use a simple string to pass multiple values to a stored procedure

ANS: Yes, you can pass a delimited string (e.g., ‘1,2,3’) and use functions like STRING_SPLIT (SQL Server 2016+) or custom split functions to parse it within the stored procedure. Older versions might rely on LIKE clauses or XML.

Q: Is passing data via XML efficient in SQL Server

ANS: XML can be efficient, especially for older SQL Server versions, but it generally incurs more overhead than Table-Valued Parameters due to XML parsing. For simple lists, TVPs or STRING_SPLIT/OPENJSON are usually preferred for performance.

Q: What are Table-Valued Parameters (TVPs) in SQL Server

ANS: TVPs are user-defined table types that allow you to pass multiple rows of data into a stored procedure or function as a single parameter, offering strong typing and efficient processing.

Q: Which SQL Server version supports STRING_SPLIT

ANS: The STRING_SPLIT function was introduced in SQL Server 2016.
