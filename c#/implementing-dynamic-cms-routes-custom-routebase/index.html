“Implementing Dynamic CMS Routes in ASP.NET MVC with Custom RouteBase”

How does one achieve flexible, content-managed system (CMS)-style routing—where URLs map directly to database content identifiers—within the traditional ASP.NET MVC routing pipeline? The accepted method involves creating a specialized route handler by deriving from RouteBase.

This approach requires implementing two critical overrides: GetRouteData to process incoming HTTP requests into recognizable route values, and GetVirtualPath to construct URLs from route values (reverse routing).

Defining the Page Data Structure

First, we establish a structure to hold the essential information for each dynamic page, typically fetched from a data source like a database.

public class PageInfo
{
    // Note: VirtualPath must exclude any leading slash for correct comparison.
    // Example: "events/conventions/mycon"
    public string VirtualPath { get; set; }
    public Guid Id { get; set; }
}

Developing the Custom Route Handler: CustomPageRoute

The core logic resides in the custom route class, inheriting from RouteBase. This class manages the bidirectional translation between URL paths and internal route data structures.

1. Handling Incoming Requests: GetRouteData

This method is invoked when the framework attempts to resolve an incoming URL path.

  • It retrieves the raw path from httpContext.Request.Path and removes the leading slash.
  • It then consults a list of available pages (ideally cached) to find a match based on the cleaned path.
  • If a PageInfo object matches the path, a new RouteData object is constructed, pointing to a specific Controller and Action, and injecting the page’s unique identifier (Id) as a route value. Query string parameters can optionally be merged here.
public override RouteData GetRouteData(HttpContextBase httpContext)
{
    RouteData result = null;

    // Remove leading slash from the request path
    var path = httpContext.Request.Path.Substring(1);

    // Attempt to find the page matching the URI path
    var page = GetPageList(httpContext)
        .FirstOrDefault(x => x.VirtualPath.Equals(path, StringComparison.OrdinalIgnoreCase));

    if (page != null)
    {
        result = new RouteData(this, new MvcRouteHandler());

        // Integrate query strings if present
        AddQueryStringParametersToRouteData(result, httpContext);

        // Map the request to a known controller and action
        result.Values["controller"] = "CustomPage";
        result.Values["action"] = "Details";

        // Store the database primary key as a route value
        result.Values["id"] = page.Id;
    }

    // Crucial: Return null if no match is found, allowing subsequent routes to process the request.
    return result;
}

2. Generating URLs: GetVirtualPath

This method reverses the process, taking route values (like controller, action, and ID) and generating a corresponding URL string.

  • It attempts to locate the corresponding PageInfo record using the provided id, controller, and action values.
  • If a match is successful, it returns a VirtualPathData object containing the actual VirtualPath string.
public override VirtualPathData GetVirtualPath(RequestContext requestContext, RouteValueDictionary values)
{
    VirtualPathData result = null;
    PageInfo page = null;

    var pages = GetPageList(requestContext.HttpContext);

    if (TryFindMatch(pages, values, out page))
    {
        if (!string.IsNullOrEmpty(page.VirtualPath))
        {
            result = new VirtualPathData(this, page.VirtualPath);
        }
    }

    // Crucial: Always return null if the values do not resolve back to a known path.
    return result;
}

Helper Method: Matching Logic (TryFindMatch)

The inverse logic resides here, ensuring that generating a path from an Id leads to the correct VirtualPath.

private bool TryFindMatch(IEnumerable<PageInfo> pages, RouteValueDictionary values, out PageInfo page)
{
    page = null;
    Guid id = Guid.Empty;

    // Validate and parse the ID from route values
    if (!Guid.TryParse(Convert.ToString(values["id"]), out id))
    {
        return false;
    }

    var controller = Convert.ToString(values["controller"]);
    var action = Convert.ToString(values["action"]);

    // Verify that the route values align with expected parameters
    if (action == "Details" && controller == "CustomPage")
    {
        page = pages.Where(x => x.Id.Equals(id)).FirstOrDefault();
        return page != null;
    }
    return false;
}

Registering the Custom Route

The custom route must be added to the routing table, typically within the Application_Start method of Global.asax. It is critical to place this custom route before the generic Default route, as routing pipelines process entries sequentially.

// In RouteConfig.cs or Global.asax.cs
public static void RegisterRoutes(RouteCollection routes)
{
    // Standard route exclusion for ASP.NET resources
    routes.IgnoreRoute("{resource}.axd/{*pathInfo}");

    // Optimize lookup speed by enforcing lowercase URLs (requires matching logic adjustment if needed)
    routes.LowercaseUrls = true;

    // Register the dynamic CMS route first
    routes.Add(
        name: "CustomPageRoute", 
        item: new CustomPageRoute());

    // The standard default route catches everything else
    routes.MapRoute(
        name: "Default",
        url: "{controller}/{action}/{id}",
        defaults: new { controller = "Home", action = "Index", id = UrlParameter.Optional }
    );
}

The Corresponding Controller Action

A controller, in this case, CustomPageController, must exist to handle the requests routed by our custom handler. The action method signature must match the parameters defined in GetRouteData (specifically, accepting the Guid id).

public class CustomPageController : Controller
{
    public ActionResult Details(Guid id)
    {

Alternative Scenario: Using Attribute Routing (Modern Approach)

For applications using ASP.NET Core or newer versions of ASP.NET MVC with attribute routing enabled, a less intrusive method avoids overriding RouteBase. You could define routes directly on the controller methods using attributes, but this often requires dynamic route registration techniques if the paths are entirely content-driven and not known at compile time. However, for classic ASP.NET MVC (pre-Core), subclassing RouteBase remains the canonical way to implement fully dynamic, database-driven URL resolution.

FAQs on Implementing Dynamic CMS Routes Custom RouteBase

Q: What is the main purpose of overriding GetRouteData in a custom route

ANS: The main purpose is to inspect the incoming HTTP path, match it against stored content identifiers (like paths or slugs), and populate the RouteData object with necessary values (controller, action, and primary key) so the MVC pipeline can select the correct endpoint.

Q: Why must GetRouteData return null if no match is found

ANS: Returning null signals the ASP.NET routing engine that this specific route handler could not process the request, allowing the framework to proceed to the next registered route in the pipeline, such as the default route.

Q: What is the significance of LowercaseUrls being set to true

ANS: Setting routes.LowercaseUrls = true generally improves performance slightly because string comparisons are faster when case sensitivity is guaranteed. If enabled, the matching logic in GetRouteData should use case-insensitive comparison or ensure all stored paths are lowercase.

Q: How is reverse routing handled for this custom route

ANS: Reverse routing, or URL generation, is handled by overriding GetVirtualPath. This method takes route values (like the content ID) and looks up the corresponding VirtualPath string from the cached content list.
