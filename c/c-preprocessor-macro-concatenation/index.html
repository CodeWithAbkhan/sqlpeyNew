“C Preprocessor Macro Concatenation: Strategies & Pitfalls Explained”

The C preprocessor offers powerful mechanisms for code generation and manipulation through macros. A common advanced technique involves concatenating tokens to form new identifiers. This often requires a nuanced approach to ensure correct behavior across different C standards and preprocessor implementations.

Standard C Preprocessor (using ##)

The ## operator, introduced in C99, provides a direct and reliable method for token pasting. It allows two adjacent tokens to be merged into a single new token.

Consider a scenario where you need to construct a function name dynamically based on a macro definition.

Example 1: Dynamic Function Naming with ##
// xx.c
#define CURRENT_VERSION 3
#define PASTER(prefix, suffix) prefix ## _ ## suffix
#define FUNCTION_NAME(base_name) PASTER(base_name, CURRENT_VERSION)

extern void FUNCTION_NAME(process_data)(char *input_buffer);

// To see the preprocessed output:
// $ gcc -E xx.c

When preprocessed with gcc -E xx.c, the output demonstrates the concatenation:

// Preprocessed Output:
# 1 "xx.c"
# 1 "&lt;built-in&gt;"
# 1 "&lt;command-line&gt;"
# 1 "xx.c"





extern void process_data_3(char *input_buffer);

The ## operator facilitates this by pasting process_data with _ and then _ with 3 to form process_data_3.

The Role of Two Levels of Indirection

You might wonder why a two-level indirection pattern is often employed. This technique is crucial for correctly expanding macro arguments before they are subject to concatenation.

Let’s analyze the standard’s behavior regarding macro replacement:

  • Argument Substitution: When a macro is invoked, its arguments are first identified. Any macros within these arguments are expanded. Crucially, before substitution, the entire argument is processed as if it were part of the preprocessing file, meaning all internal macros are expanded.
  • The ## Operator: When ## appears between a parameter and another token, or between two parameters, it concatenates them. The standard dictates that this operation occurs after argument substitution and full macro expansion of the arguments themselves.

In FUNCTION_NAME(process_data), the argument process_data is first fully expanded. Then, PASTER(process_data, CURRENT_VERSION) is evaluated. CURRENT_VERSION expands to 3. Finally, process_data ## _ ## 3 performs the concatenation to produce process_data_3.

Consider a simpler case without the extra indirection:

#define VARIABLE 3
#define NAME(fun) fun ## _ ## VARIABLE
NAME(mine)

Preprocessing this yields mine_VARIABLE. The VARIABLE macro was not expanded within the NAME macro’s replacement list before being pasted.

Alternative for Dynamic Naming (Two-Level Indirection)

A common pattern for ensuring argument expansion before pasting involves an extra layer of indirection:

#define VARIABLE 3
#define NAME2(func, suffix) func ## _ ## suffix
#define NAME1(func, suffix) NAME2(func, suffix)
#define NAME(func) NAME1(func, VARIABLE)

int NAME(my_custom_function)(int value);

This structure ensures that VARIABLE is expanded in NAME1 before being passed to NAME2 for concatenation. While the precise mechanics can seem arcane, this two-step process guarantees that arguments are fully resolved before the ## operator performs its action.

Traditional C Preprocessor (Pre-C99)

Before the ## operator, achieving token concatenation was more challenging and often less reliable, relying on preprocessor-specific behaviors.

Example 2: Token Pasting without ## (using comments)

One method involved using comments (/**/) to separate tokens, preventing the preprocessor from seeing them as a single token that needed space separation.

// x-paste.c
#define DATA_VERSION 3
#define PASTE_TOKENS(a, b) a/**/b
#define CONCAT_VERSIONS(base, version) PASTE_TOKENS(PASTE_TOKENS(base, _), version)
#define CONSTRUCTED_NAME(base) CONCAT_VERSIONS(base, DATA_VERSION)

extern void CONSTRUCTED_NAME(event_handler)(const char *message);

// To see the preprocessed output with GCC:
// $ gcc -E x-paste.c

With GCC 6.3.0, this might produce:

// GCC Preprocessed Output:
# 1 "x-paste.c"
# 1 "&lt;built-in&gt;"
# 1 "&lt;command-line&gt;"
# 1 "x-paste.c"





extern void event_handler_3(const char *message);

However, this approach could be brittle. Different preprocessors might handle comments in comments differently. For instance, the Clang preprocessor might introduce unwanted spaces:

// Clang Preprocessed Output (potential issue):
# 1 "x-paste.c"
# 1 "&lt;built-in&gt;" 1
# 1 "&lt;built-in&gt;" 3
# 329 "&lt;built-in&gt;" 3
# 1 "&lt;command line&gt;" 1
# 1 "&lt;built-in&gt;" 2
# 1 "x-paste.c" 2





extern void event_handler _ 3(const char *message);

These spaces render the identifier syntactically invalid. The C99 standard’s ## operator largely resolved these cross-preprocessor compatibility issues.

Attempting to directly paste with comments inside the separator could also fail:

#define VARIABLE 3
#define PASTER(x,y) x/**/_/**/y // <-- Problematic comment placement
#define EVALUATOR(x,y) PASTER(x,y)
#define NAME(fun) EVALUATOR(fun,VARIABLE)

extern void NAME(mine)(char *x);

Preprocessing this with GCC might result in mine_VARIABLE instead of the intended mine_3, as the VARIABLE macro was not expanded before concatenation.

Understanding Macro Expansion and Indirection

The behavior of macros, especially with concatenation, is governed by specific rules regarding when macro arguments are expanded.

  1. Prescan: Macro arguments are evaluated. If an argument is not part of a concatenation (##) or stringification (#) within the macro definition, it is fully expanded before being substituted.
  2. Substitution: The macro body is replaced with its expanded content, including the expanded arguments.
  3. Rescan: After substitution, the preprocessor rescans the result for further macro expansions.
Step-by-Step Example: No Indirection
#define PASTE_NO_INDIR(x, y) x ## y
PASTE_NO_INDIR(pref_, FOO) // Assume FOO is not defined or is some identifier
  • Prescan: FOO is not part of stringification/concatenation within PASTE_NO_INDIR itself. So, it might be treated literally if not defined. If FOO were a macro, it would expand here.
  • Substitution: pref_FOO is formed.
  • Rescan: pref_FOO is not a macro.

If FOO was bar: #define FOO bar PASTE_NO_INDIR(pref_, FOO) results in pref_bar.

Step-by-Step Example: With Indirection
#define PASTE_WITH_INDIR_2(x, y) x ## y
#define PASTE_WITH_INDIR_1(x, y) PASTE_WITH_INDIR_2(x, y)
#define MACRO_VALUE FOO // Assume FOO is not defined or is some identifier

PASTE_WITH_INDIR_1(pref_, MACRO_VALUE)
  • Prescan (Outer PASTE_WITH_INDIR_1): The argument MACRO_VALUE is not directly part of ## in PASTE_WITH_INDIR_1’s definition. Therefore, it gets fully expanded. MACRO_VALUE expands to FOO. The call effectively becomes PASTE_WITH_INDIR_2(pref_, FOO).
  • Substitution (Inner PASTE_WITH_INDIR_2): Now, pref_ is pasted with FOO.
  • Rescan: pref_FOO is not a macro.

If FOO was bar: #define FOO bar PASTE_WITH_INDIR_1(pref_, MACRO_VALUE) results in pref_bar.

This two-level indirection ensures that the value of MACRO_VALUE (which could itself be another macro) is used in the final concatenation, rather than the macro name itself.

Preventing Infinite Expansions

The preprocessor’s design also prevents infinite loops during expansion. For instance:

#define ADD_ONE(num) (num + 1)
ADD_ONE(ADD_ONE(5))

When the outer ADD_ONE is called, its argument ADD_ONE(5) is not part of a ## or # operation within ADD_ONE’s definition. Thus, ADD_ONE(5) is fully expanded first to (5 + 1). The outer macro then becomes ( (5 + 1) + 1 ), avoiding an infinite recursive expansion.

FAQs on C Preprocessor Macro Concatenation

Q: What is the primary purpose of the ## preprocessor operator

ANS: The ## operator, also known as token pasting, is used to concatenate two preprocessor tokens to form a single new token. This is useful for creating dynamic identifiers like function names or variable names based on macro definitions.

Q: Why is double indirection sometimes necessary for macro concatenation

ANS: Double indirection is often required to ensure that macro arguments are fully expanded before they are subjected to the ## token pasting operator. This guarantees that the intended values or identifiers are concatenated, rather than the macro names themselves.

Q: How did token pasting work before the ## operator was standardized

ANS: Before the ## operator, developers relied on techniques like using comments (/**/) between tokens to prevent the preprocessor from merging them prematurely. This method was less reliable and subject to variations in preprocessor implementations, often leading to portability issues.

Q: Can the ## operator be used with stringification

ANS: No, the ## operator is for concatenating tokens into identifiers, while the # operator is for stringifying a single token into a string literal. They serve different purposes in macro manipulation.

Q: What happens if a macro argument contains another macro when using ##

ANS: If a macro argument contains another macro and it is subject to concatenation via ##, the inner macro will typically be expanded first due to the standard’s argument prescan rules, provided the argument is not directly part of a ## operation in the outer macro’s definition. Double indirection helps ensure this expansion.
