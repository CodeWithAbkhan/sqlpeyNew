“Diving Deep into ARM Register Roles: FP, LR, SP, and PC”

How do the Application Binary Interface (ABI) standards, specifically APCS versus the newer AAPCS (post-GCC 5.0+), dictate the usage of the Frame Pointer ($\text{FP}$) register in ARM architecture, particularly concerning stack tracing and unwinding?

The requirement for the Frame Pointer ($\text{FP}$) depends on the specific ABI standard in place. In the older APCS standard, $\text{FP}$ was mandated. However, under the modern AAPCS (as used by GCC 5.0 and later), utilizing $\text{FP}$ is optional. Even when not strictly required by the AAPCS, the compiler can still employ it. When $\text{FP}$ is used, debug information annotates the stack and frame pointer usage, aiding stack tracing and code unwinding. It is worth noting that if a function is compiled as static, the compiler has greater latitude and might not strictly adhere to any published convention.

What differentiates the general-purpose ARM registers from the specialized registers like $\text{LR}$ (Link Register, $\text{R14}$) and $\text{PC}$ (Program Counter, $\text{R15}$)?

Virtually all ARM registers are designated as general purpose, except for $\text{LR}$ ($\text{R14}$) and $\text{PC}$ ($\text{R15}$), which have roles deeply embedded in the instruction set architecture. You are correct in observing that $\text{LR}$ typically holds the return address (what might be point $\text{A}$ in a typical diagram before a call). The $\text{PC}$ and $\text{LR}$ are intrinsically linked: $\text{PC}$ indicates “where you are” executing presently, while $\text{LR}$ holds “where you were” meant to return to. These two registers define the control flow aspect of a function call.

Explain the functional relationship between the Stack Pointer ($\text{SP}$, $\text{R13}$) and the Frame Pointer ($\text{FP}$, $\text{R11}$), and how the $\text{FP}$ creates a window into the stack frame.

The $\text{SP}$ ($\text{R13}$) indicates the current location of the top of the stack, which holds temporary data or local variables for the current function (e.g., locals within $\text{foo()}$ or $\text{bar()}$). The $\text{FP}$ ($\text{R11}$) serves as a fixed reference point for accessing data associated with the current function’s stack frame—it acts as a “picture window” onto the stack. The ABI defines the specific layout of this frame. Typically, upon entry, the caller’s $\text{LR}$ and the previous $\text{FP}$ value are saved within this frame. This structure forms a linked list of stack frames. By tracing back through the stored previous $\text{FP}$ values, one can unwind the call stack until reaching the initial frame, often terminated by a $\text{NULL}$ $\text{FP}$. In essence, $\text{SP}$ shows where the stack is currently growing, much like $\text{PC}$ shows current execution, whereas $\text{FP}$ shows where the stack was relative to the previous frame’s structure, analogous to $\text{LR}$. Each saved $\text{LR}$ is stored relative to its corresponding $\text{FP}$.

If $\text{A}$ points to the $\text{FP}$ and $\text{LR}$ of the caller, and $\text{B}$ points to the active $\text{PC}$ and $\text{SP}$ of the current function, how does the compiler set up the frame upon entry to a new function?

$\text{B}$ generally represents the dynamic, active state ($\text{PC}$ and $\text{SP}$) of the current execution context. $\text{A}$ represents the saved state ($\text{FP}$ and $\text{LR}$) of the function that initiated the call. If a function proceeds to call another subroutine, the compiler prepares $\text{B}$ by establishing a new frame, saving the necessary context ($\text{A}$’s values) relative to the new frame structure.

Can you illustrate the typical ARM assembler sequence for a function prologue (setup) and epilogue (return), noting the impact of optimization techniques like leaf optimization?

The assembler sequence demonstrates the mechanics. Note that compiler optimization heavily influences the output; for instance, if a function does not invoke other functions (a leaf function), the compiler might skip frame setup entirely, performing only a tail call optimization if possible.

; Function foo() entry - Prologue Setup
mov     ip, sp                 ; Preserve current SP into IP (R12)
stmdb   sp!, {fp, ip, lr, pc}  ; Save FP, IP (old SP), LR, and PC onto the stack (lowering SP)
sub     fp, ip, #4             ; Set the new frame pointer relative to the saved state. (Assuming 32-bit registers)
    ...
; Function call to subroutine 'baz'
bl      baz                    ; Branch and Link to baz
    ...
; Function foo() exit - Epilogue Return
ldm     sp, {fp, sp, lr}       ; Restore FP, SP, and LR from the stack (raising SP)
    ...
bx      lr                     ; Return to address stored in LR

In the example above, if $\text{baz}$ is not called, the compiler might apply leaf optimization, resulting in a much simpler entry, perhaps only requiring the $\text{bx lr}$ instruction if no local variables require stack space beyond what registers provide. This variability explains discrepancies seen in web examples.

What are the core register relationships to remember regarding function machinery?

  1. Code Registers: $\text{PC}$ and $\text{LR}$ are linked. One tracks “Where execution is now” ($\text{PC}$), the other tracks “Where execution was supposed to go back to” ($\text{LR}$).
  2. Data Registers: $\text{SP}$ and $\text{FP}$ are linked. One tracks “Where current local data resides” ($\text{SP}$), the other tracks “Where the reference point for the previous frame’s local data was” ($\text{FP}$).

These pairs collaborate with parameter passing mechanisms to form the core function call mechanism. These concepts are generally applicable across CPU architectures and compiled languages, though specific register assignments vary. Proper articulation of the function prologue and epilogue demonstrates the mechanics of stack operations, including how a stack overflow event might occur on an ARM platform.
