“Solved How to Master C++ Expression Evaluation Order and Avoid Undefined Behavior”

Method 1: Navigating C++98 and C++03 Sequence Points

For C++ versions predating C++11, the concept of “sequence points” is central to how expression evaluation is ordered. While C++11 and later versions introduced “sequenced before,” “unsequenced,” and “indeterminately sequenced” relations, the fundamental aim remains similar: to define precise moments when all prior computational effects are finalized.

What Exactly are Sequence Points?

The C++ Standard defines a sequence point as a specific point in time during program execution where all side effects of prior evaluations are guaranteed to be complete, and no side effects of subsequent evaluations have yet commenced. Think of it as a synchronization point for expression evaluation.

Exploring Side Effects

What do we mean by “side effects”? An expression’s evaluation typically produces a value. If, in addition to yielding a value, this evaluation alters the state of the program’s execution environment, it’s considered to have a side effect.

Consider this illustration:

int current_val = next_val++; // Where 'next_val' is an integer.

Here, beyond the assignment operation, the ++ operator modifies the value of next_val. This modification is a side effect.

A helpful alternative definition by comp.lang.c author Steve Summit describes a sequence point as “a point in time at which the dust has settled and all side effects which have been seen so far are guaranteed to be complete.”

Common Sequence Points in C++98/03

The C++ Standard specifies several common sequence points:

  • At the end of a full expression’s evaluation (§1.9/16). A “full-expression” is an expression that isn’t a subexpression of another. Example: 
    int data_point = 15; // Semicolon acts as a sequence boundary here.
  • During the evaluation of certain expressions, after the first operand’s evaluation (§1.9/18). This applies to built-in logical AND (&&), logical OR (||), conditional (? :), and comma (,) operators.
    • operand_a && operand_b
    • operand_a || operand_b
    • condition ? expr_true : expr_false
    • expr_left , expr_right (for the comma operator, not a function argument separator like func(val1, val2++))
  • At a function call, after the evaluation of all function arguments but before execution of any expressions within the function body (§1.9/17). This applies whether the function is inline or not.

Defining Undefined Behavior (UB)

The C++ Standard, in Section §1.3.12, defines Undefined Behavior as:

“behavior, such as might arise upon use of an erroneous program construct or erroneous data, for which this International Standard imposes no requirements.”

This implies that if your program triggers UB, the compiler is free to do anything. It might crash, produce incorrect results, or even appear to work correctly on one system but fail on another.

The Connection Between Undefined Behavior and Sequence Points

Crucially, the order of evaluation for operands of individual operators and subexpressions, along with the order in which side effects occur, is typically unspecified.

For example:

int first_val = 7, second_val = 8;

int combined_sum = first_val++ + second_val++; // Order of 'first_val++' and 'second_val++' evaluation is indeterminate.

The Standard in §5/4 states a critical rule:

“Between the previous and next sequence point a scalar object shall have its stored value modified at most once by the evaluation of an expression.”

Informally, this means a variable cannot be modified more than once between any two sequence points. The terminating semicolon of an expression statement usually marks the next sequence point.

Violating this rule leads to Undefined Behavior. Consider these examples of UB:

index_counter++ * ++index_counter; // Undefined Behavior: 'index_counter' modified multiple times between sequence points.
my_int = ++my_int; // Undefined Behavior: Variable 'my_int' is modified and accessed in an unsequenced manner.
++some_var = 5; // Undefined Behavior: Attempting to assign to the result of a pre-increment.
val_k = ++val_k + 1; // Undefined Behavior: 'val_k' is modified and its previous value is used for computation unsequenced.
++++++counter_val; // Undefined Behavior: Multiple increments on 'counter_val' without sequencing.

result_var = (result_var, ++result_var, ++result_var); // Undefined Behavior: 'result_var' modified multiple times within the expression due to comma operator semantics.

However, some seemingly complex expressions are well-defined if they respect sequencing rules:

final_value = (final_value, ++final_value, 9) + 1; // Well-defined behavior: Comma operator ensures sequencing.
variable_x = (++variable_x, variable_x++, variable_x); // Well-defined behavior: Each sub-expression is sequenced.
int current_j = current_i;
current_j = (++current_i, current_i++, current_j * current_i); // Well-defined: Sequencing ensures predictable outcome.

Another vital rule: “Furthermore, the prior value shall be accessed only to determine the value to be stored.” This means if an object is written to within a full expression, all accesses to it within that same expression must be directly involved in calculating the value to be written.

Illustrations of this rule leading to UB:

std::printf("Values: %d %d", loop_idx, ++loop_idx); // Undefined Behavior: 'loop_idx' modified and accessed without proper sequencing.
data_arr[arr_idx] = arr_idx++; // Undefined Behavior: Array index 'arr_idx' is modified and used for array access in an unsequenced way.
int sum_calc = item_val + item_val++; // Undefined Behavior: 'item_val' modified and accessed within the same unsequenced expression.

Method 2: Embracing C++11’s Sequenced Before Relations

C++11 significantly revised the terminology around expression evaluation, moving away from “sequence points” to a more granular model based on “sequenced before” relationships.

The Shift to ‘Sequenced Before’

In C++11, sequence points are indeed replaced by the concepts of “sequenced before” and “sequenced after” relationships (along with “unsequenced” and “indeterminately sequenced” categories).

Deconstructing ‘Sequenced Before’

“Sequenced Before” (§1.9/13) defines an asymmetric and transitive relationship between evaluations executed by a single thread, establishing a strict partial order.

Formally, if evaluation A is sequenced before evaluation B, then A’s execution must precede B’s execution. If neither A is sequenced before B nor B is sequenced before A, then A and B are “unsequenced” (their execution can overlap). “Indeterminately sequenced” evaluations cannot overlap, but their execution order is unspecified.

The Term ‘Evaluation’ in C++11

In C++11, the “evaluation” of an expression or sub-expression broadly includes:

  • Value computations: Determining an object’s identity (for glvalue) or fetching a previously assigned value (for prvalue).
  • Initiation of side effects.

Crucially, (§1.9/14) states: “Every value computation and side effect associated with a full-expression is sequenced before every value computation and side effect associated with the next full-expression to be evaluated.”

A simple illustration:

int some_value;
some_value = 10;
++some_value;

The value computation and side effect related to ++some_value are sequenced after the value computation and side effect of some_value = 10.

Undefined Behavior and Sequencing in C++11

Most importantly, (§1.9/15) dictates:

“Except where noted, evaluations of operands of individual operators and of subexpressions of individual expressions are unsequenced.”

For instance, consider:

int main()
{
     int original_number = 25;
     original_number = (original_number << 2) + (original_number >> 2);
}

The evaluation of operands for the + operator (i.e., (original_number << 2) and (original_number >> 2)) are unsequenced relative to each other. Similarly for the << and >> operators’ operands.

Further, (§1.9/15) clarifies: “The value computations of the operands of an operator are sequenced before the value computation of the result of the operator.” This means, for x + y, the values of x and y are computed before the result of their addition.

The core rule for Undefined Behavior in C++11 regarding sequencing is:

“If a side effect on a scalar object is unsequenced relative to either (a) another side effect on the same scalar object or (b) a value computation using the value of the same scalar object, the behavior is undefined.”

Here are C++11 examples that trigger UB:

int counter_start = 7, values_array[12] = { };
void custom_func(int, int);

my_integer = my_integer++ * ++my_integer; // Undefined Behavior
calc_var = ++calc_var + calc_var++; // Undefined Behavior
data_val = ++data_val + ++data_val; // Undefined Behavior
element_idx = arr_data[element_idx++]; // Undefined Behavior
test_function(arg_val = -1, arg_val = -1); // Undefined Behavior

Some cases that remain well-defined in C++11:

array_element = data_collection[++array_element]; // Well-defined Behavior
outcome_value = ++outcome_value + 1; // Well-defined Behavior
++++++integer_var; // Well-defined Behavior

Method 3: C++17’s Refinements for Expression Evaluation

C++17 (N4659) introduced proposals to refine expression evaluation order, aiming for stricter and more intuitive behavior in certain idiomatic C++ constructs.

One notable change involves assignment and compound assignment operators. The standard now clarifies:

“In all cases, the assignment is sequenced after the value computation of the right and left operands, and before the value computation of the assignment expression. The right operand is sequenced before the left operand.”

This, combined with the clarification that “An expression X is said to be sequenced before an expression Y if every value computation and every side effect associated with the expression X is sequenced before every value computation and every side effect associated with the expression Y,” makes several previously undefined behaviors now valid.

An example that becomes well-defined in C++17:

target_array[++target_idx] = target_idx; // Well-defined in C++17

However, some similar cases still result in undefined behavior. Compare these:

  • Pre-C++17 (e.g., N4140): 
    counter = counter++ + 1; // Behavior is undefined in older C++ standards.
  • C++17 (N4659): 
    current_val_c17 = current_val_c17++ + 1; // C++17: 'current_val_c17' is incremented.
new_total = new_total++ + new_total; // C++17: Still undefined behavior.

While C++17 offers more predictable behavior in certain scenarios, it’s still prudent to avoid overly complex expressions that rely on these subtle sequencing rules.

Method 4: C99 Perspective on Evaluation Order

It’s helpful to recognize that similar principles apply in the C language. C99 (ISO/IEC 9899:TC3) specifies rules regarding evaluation order that share common ground with C++.

  • “[…]the order of evaluation of subexpressions and the order in which side effects take place are both unspecified.” (Section 6.5 pp 67)
  • “The order of evaluation of the operands is unspecified. If an attempt is made to modify the result of an assignment operator or to access it after the next sequence point, the behavior is undefined.” (Section 6.5.16 pp 91)

This highlights that the core challenges of unspecified evaluation order and side effects are not unique to C++, stemming from a common linguistic heritage.

Method 5: Impact on Concurrency and Compiler Optimizations

The evolution from “sequence points” to “sequenced before” relationships is not merely a cosmetic change; it reflects deeper implications, particularly concerning concurrency and compiler optimizations.

  • Concurrency: The modern “unsequenced” and “indeterminately sequenced” categories explicitly permit concurrent evaluation. For a function call like call_utility(param_a, param_b);, in older standards, param_a would be evaluated then param_b, or vice-versa, in a strictly serial fashion. C++11 and later allow for instructions from param_a and param_b to be interleaved or even evaluated on different CPU cores if resources permit, which is crucial for modern multi-threaded environments.
  • Compiler Optimizations: The C++ Standard’s rules regarding sequence points and sequencing are crafted to empower optimizing compilers. They allow compilers to reorder actions in ways that do not cross defined sequencing boundaries. By classifying behavior as Undefined Behavior when such reordering could be observably detected by the program, the standard gives compilers tremendous freedom. This design choice prioritizes performance by allowing aggressive optimizations, even if it places a burden on developers to ensure their code avoids UB. For example, in some languages, caching values or performing redundant computations might be allowed without memory barriers, but in C++, directly observing such effects by unsequenced access to modified data typically results in Undefined Behavior.

FAQs on Solved How to Master C++ Expression Evaluation Order and Avoid Undefined Behavior

Q: What are sequence points in C++

ANS: In older C++ standards (C++98 and C++03), sequence points are specific points in program execution where all side effects of previous evaluations are complete, and no side effects of subsequent evaluations have begun. They act as synchronization points.

Q: How do side effects relate to sequence points

ANS: A side effect is a change to the program’s state during expression evaluation (like modifying a variable). Sequence points ensure that all side effects from prior expressions are visible and complete before proceeding to subsequent operations.

Q: What is undefined behavior in C++

ANS: Undefined Behavior or UB is a situation where the C++ standard imposes no requirements on a program’s actions. This can result from erroneous code constructs, such as modifying the same scalar object multiple times between sequence points, and can lead to unpredictable outcomes like crashes or incorrect results.

Q: How does C++11 handle expression sequencing

ANS: C++11 replaced the concept of sequence points with “sequenced before” and “sequenced after” relationships. This model defines a strict partial order for evaluations. If operations are not explicitly sequenced, they are considered “unsequenced” or “indeterminately sequenced,” allowing for more optimization and potential concurrency.

Q: What does sequenced before mean

ANS: “Sequenced before” is an asymmetric and transitive relation between two evaluations (A and B). If A is sequenced before B, it means A’s execution must complete before B’s execution begins. If neither is sequenced before the other, they are unsequenced.

Q: Did C++17 change evaluation rules

ANS: Yes, C++17 introduced refinements to expression evaluation order, particularly for assignment and compound assignment operators. These changes make certain expressions that were previously undefined behavior now well-defined, such as a[++i] = i;.

Q: Can concurrent evaluation occur without strict ordering

ANS: Yes, with the “unsequenced” and “indeterminately sequenced” concepts introduced in C++11, the standard explicitly allows for operations that are not sequenced relative to each other to be executed concurrently, or have their instructions interleaved, which is beneficial for modern multi-core processors.
