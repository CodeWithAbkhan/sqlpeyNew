Distinguishing char* and char[] Behavior in C

Although both types can hold strings and decay into pointers when passed to functions, their underlying type definitions and memory allocation strategies differ significantly.

The Role of Array Decay

When an array name, such as char s[10], is used in most expression contexts, it undergoes array-to-pointer decay. This means the array name implicitly converts into a pointer to its first element (&s[0]).

If a function is declared to accept a char* argument, passing an array automatically triggers this decay, making the types appear interchangeable to the function signature:

void printStringPointer(char* str) {
    // Function expects a pointer
    printf("Pointer received.\n");
}

int main() {
    char dataArray[10] = "Visible";
    
    // Implicit decay: dataArray converts to &dataArray[0]
    printStringPointer(dataArray); 
    
    // Explicitly passing the address of the first element (same result)
    printStringPointer(&dataArray[0]); 
    
    return 0;
}

Size Measurement Differences

The sizeof operator reveals a core distinction:

  • sizeof(char*) yields the size of the pointer variable itself (typically 4 bytes on x86 or 8 bytes on x86-64 systems).
  • sizeof(char[]) yields the total size allocated in memory for the array, including the null terminator \0.

Consider this demonstration of size and length:

#include <stdio.h>
#include <string.h>

int main() {
    char *ptrStr = "DynamicData"; // Pointer initialized to a string literal
    char arrStr[] = "DynamicData"; // Array allocated on the stack

    // Size of the pointer variable (address)
    printf("Size of char* (ptrStr): %zu bytes\n", sizeof(ptrStr)); 
    
    // Size of the allocated array (characters + null terminator)
    printf("Size of char[] (arrStr): %zu bytes\n", sizeof(arrStr)); 

    // strlen ignores size and counts characters until '\0'
    printf("Length of ptrStr: %zu\n", strlen(ptrStr)); 
    printf("Length of arrStr: %zu\n", strlen(arrStr)); 
    
    return 0;
}

String Literal Initialization and Mutability

A critical difference arises when initializing with string literals (text enclosed in double quotes, like "hello"):

  1. char q[] = "text";: Memory for the array, including the null terminator, is allocated (usually on the stack if local, or in the .data section if global/static). This memory is writable, and its contents can be altered. This is equivalent to char q[] = {'t', 'e', 'x', 't', '\0'};.

  2. char *p = "text";: The pointer p is allocated memory (usually on the stack), but it is initialized to point to an unnamed, static array of characters created from the string literal. This string literal is often placed in the read-only data segment (.rodata). Attempting to modify the contents pointed to by p results in Undefined Behavior (UB), often causing a segmentation fault.

For example, modifying an array is safe, while modifying the memory pointed to by a pointer initialized via a string literal is dangerous:

// Example illustrating writability difference
char array_safe[] = "modify me";
char *ptr_unsafe = "read only me";

// Safe modification (writes to stack-allocated memory)
array_safe[0] = 'X'; 

// Unsafe modification (attempts to write to read-only .rodata segment)
// *ptr_unsafe = 'Y'; // <-- Results in UB/Crash

This read-only nature of string literals is commonly seen when using functions like mkstemp, where using an array prevents modification errors:

// APUE style example of safe vs. unsafe template usage
char good_template[] = "/tmp/tempXXXXXX"; /* SAFE: Memory allocated on stack and modifiable */
char *bad_template = "/tmp/tempXXXXXX";   /* UNSAFE: Points to read-only data; modifying it crashes */

If you examine the object file output (e.g., using objdump), static arrays initialized from literals typically reside in the writable .data section, whereas pointers initialized from literals point into the typically read-only .rodata section.

Alternative Viewpoints and Semantics

While arrays decay to pointers when passed to functions, certain operations remain fundamentally different:

  • Pointer Reassignment: A char* variable can be reassigned to point to a different memory location: p = new_address;.
  • Array Reassignment: A declared char[] variable cannot be reassigned to point elsewhere; its identity is fixed to its initial allocated block of memory. Operations like p++; are valid for pointers but generally illegal or meaningless for the array variable itself (though p+2 calculates an address relative to the array’s start).

In contexts requiring explicit ROM maps or constant data tables across compilation units, using extern const unsigned char arr[] is preferred, as it signals constant, initialized data, which the compiler might place in specific read-only segments, accessible via extern const unsigned char* arr; or extern const unsigned char arr[]; in other units.

FAQs on char* vs char[]

Q: What happens when I pass a char array to a function expecting char*

ANS: The array name decays, meaning the address of its first element is passed as a char*. The function treats it as a pointer.

Q: Why does changing char* initialized with a string literal cause a crash

ANS: String literals are often stored in read-only memory segments (.rodata), and attempting to write to this memory results in undefined behavior, usually a segmentation fault.

Q: Is char p[6] = 'hello' the same as char p[] = 'hello'

ANS: No. char p[6] = "hello" explicitly allocates 6 bytes. char p[] = "hello" uses “magic” initialization, allocating exactly enough space for the characters plus the mandatory null terminator, which would be 6 bytes in this case. If the initialization string were longer than the declared size, the extra characters are ignored, and the array might be undersized if the null terminator cannot fit (e.g., char p[5] = "hello").

Q: Can I use p++ on a char array variable p

ANS: No. p++ is invalid for a declared array variable (char p[]) because arrays are fixed memory blocks. It is valid for a pointer variable (char *p).
