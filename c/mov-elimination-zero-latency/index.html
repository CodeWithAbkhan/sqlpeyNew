“MOV Elimination: Does it Really Have Zero Latency on Modern CPUs?”

Does the MOV instruction truly offer zero latency on modern CPUs, or is it a nuanced behavior influenced by microarchitecture and specific instruction patterns? This exploration delves into the mechanics and observed performance impacts of MOV elimination, supported by practical assembly examples and benchmarking.

The core concept of MOV elimination, often referred to as register renaming for MOV, allows certain copy operations to bypass actual execution units. Instead, the operation is handled during the instruction issue or rename stage. This effectively removes the latency and execution port usage associated with a typical instruction.

CPUs Supporting MOV Elimination:

The CPUs that benefit from MOV elimination include:

  • AMD Bulldozer family: Primarily for XMM vector registers.
  • AMD Zen family: For both integer and XMM vector registers. Zen 2 and later also support YMM registers. (Refer to Agner Fog’s microarchitecture guides for detailed explanations on YMM register halves across different Zen generations).
  • Intel Ivy Bridge and later: For integer and most vector registers (excluding MMX).
  • Intel Goldmont and later (low-power CPUs): Supports XMM and integer registers. This includes Alder Lake E-cores for integer/XMM, but not YMM.
  • Exceptions: Notably, Intel Ice Lake and Tiger Lake are affected by a microcode update that disabled register renaming for general-purpose integer registers as a workaround for an erratum. However, XMM/YMM/ZMM renaming remains functional. Rocket Lake and Alder Lake P-cores are not similarly affected.

You can often observe the effects of zero-latency MOV instructions by checking uops.info results for mov r32, r32, which will show latency=0 on CPUs where elimination occurs. Conversely, latency=1 is typically shown for CPUs like Ice Lake and Tiger Lake, indicating their performance after microcode updates.

Performance Implications in Loops

The throughput of simple loops can be sensitive to instruction scheduling and dependency chains, even with MOV elimination.

Consider a loop structure:

loop:
    ; ... instructions ...
    inc eax          ; Example instruction 1
    add ebx, eax     ; Example instruction 2
    loop loop        ; Macro-fused into one uop on Intel

Even if MOV instructions are eliminated, they still need to be tracked by the out-of-order execution engine. While they might not consume an execution unit, they consume issue bandwidth and occupy entries in the reorder buffer (ROB).

Front-end vs. Back-end Bottlenecks:

Intel CPUs since Core 2 generally have an issue width of 4 micro-operations (uops) per clock. A loop with a MOV that is fully eliminated might still be bottlenecked by:

  • Front-end Throughput: The maximum number of uops the CPU can decode and issue per clock (typically 4).
  • Taken Branch Throughput: The ability to execute conditional branches that are predicted as taken (usually 1 per clock).
  • Dependency Chains: The inherent latency of instructions that depend on the results of previous instructions within the loop. For example, an ADD depending on an INC from the prior iteration.
  • Port Contention: On Haswell, for instance, there are four ALU ports (0, 1, 5, 6). While INC and ADD can use any of these, the loop’s structure and dependencies can still lead to stalls.

In a loop like the example above, where INC and ADD are dependent on previous iterations, out-of-order execution can’t perfectly parallelize them within a single clock cycle. If an INC stalls the dependency chain, the subsequent ADD will also be delayed. Furthermore, taken branches might be restricted to specific ports (e.g., port 6), and if other instructions occupy that port, throughput can decrease.

The addition of a MOV instruction, even if eliminated, can impact the front-end’s ability to issue uops ahead of the back-end. While only 3 out of 4 uops in a typical loop might require an execution unit, the MOV still consumes issue bandwidth and can affect how the front-end fills the out-of-order execution scheduler.

The Loop Buffer (LSD):

Modern CPUs often employ a Loop Stream Detector (LSD) or similar buffer. For small, tight loops, this buffer can cache a sequence of instructions, allowing them to be issued repeatedly with minimal front-end overhead. This contributes to a more consistent issue rate, often around 4 uops per clock if available. However, even with the LSD, suboptimal scheduling can introduce performance penalties if dependency chains are not managed efficiently.

A Practical Demonstration: MOV Elimination in Action

Let’s examine a common assembly benchmark to illustrate MOV elimination. The following code attempts to measure the performance of a loop involving MOV and LEA instructions.

_start:
    mov     ecx, 2000000000 ; Initialize loop counter (approx. 1 billion iterations)
align 16  ; Alignment for potential uop-cache benefits, though not critical for LSD loops.
.loop:
    mov eax, ecx       ; Instruction 1: Copy value from ECX to EAX
    lea ecx, [rax-1]   ; Instruction 2: Calculate ECX = EAX - 1 (effectively ECX--)

    dec ecx            ; Instruction 3: Decrement ECX
    jnz .loop          ; Instruction 4: Jump if ECX is not zero

.end:
    xor edi, edi       ; Standard exit sequence
    mov eax, 231       ; __NR_exit_group syscall number
    syscall            ; Exit the program

Compiling and Benchmarking:

Using yasm and ld to assemble and link, followed by perf to gather performance counters:

yasm -felf64 -Worphan-labels -gdwarf2 mov-elimination.asm && \
ld -o mov-elimination mov-elimination.o && \
objdump -Mintel -drwC mov-elimination && \
taskset -c 1 ocperf.py stat -etask-clock,context-switches,page-faults,cycles,instructions,branches,uops_issued.any,uops_executed.thread -r2 ./mov-elimination

Observed Results (on a Haswell/Skylake equivalent):

  • With MOV eax, ecx and LEA ecx, [rax-1]: The loop typically completes around 2 billion cycles for 1 billion iterations, indicating roughly 2 cycles per iteration. This performance suggests MOV elimination is active, as a non-eliminated MOV would likely add a cycle, pushing the iteration time to 3 cycles. The uops_issued.any count usually reflects the total number of uops generated, while uops_executed.thread indicates those that actually used an execution unit. When MOV is eliminated, these counts diverge.

  • With MOV ecx, ecx (self-copy): CPUs often cannot eliminate MOV instructions where the source and destination registers are the same. This modification typically results in approximately 3 billion cycles for 1 billion iterations, showing a clear increase in latency due to the non-eliminated MOV impacting the dependency chain. Here, uops_issued.any and uops_executed.thread counts tend to be very close.

  • Without the MOV instruction: Removing the MOV altogether results in a loop with only LEA, DEC, and JNZ. Performance returns to around 2 billion cycles for 1 billion iterations, reinforcing the idea that the MOV itself, when eliminated, doesn’t add latency.

Insights from Performance Counters:

  • cycles:u: Total CPU cycles spent in user space.
  • instructions:u: Total instructions executed.
  • branches:u: Total branch instructions.
  • uops_issued.any: Total micro-operations issued by the front-end.
  • uops_executed.thread: Total micro-operations executed by the back-end.

When MOV elimination occurs, uops_issued.any is higher than uops_executed.thread because the eliminated MOVs are issued but not executed.

MOV Elimination and Dependencies

The effectiveness of MOV elimination can be influenced by how quickly the result of an eliminated MOV is overwritten or used. Intel’s optimization manuals suggest that reordering instructions to use the result of a zero-latency MOV quickly can improve its efficiency, particularly for MOVZX.

Consider this scenario:

__loop1:
    add edx, 1
    add edx, 1
    add ecx, 1
    jnc __loop1

__loop2:
    mov eax, edx       ; Mov 1
    add eax, 1         ; Add 1 to EAX
    mov edx, eax       ; Mov 2: Update EDX with the result
    add edx, 1         ; Add 1 to EDX
    add ecx, 1         ; Increment ECX
    jnc __loop2

On CPUs with MOV elimination (like Haswell), both __loop1 and __loop2 might complete in approximately 2 cycles per iteration. This is because the MOV instructions in __loop2 are likely eliminated, preventing them from extending the dependency chain beyond what’s inherent in the ADD operations. Without elimination, __loop2 would be expected to take around 4 cycles per iteration.

Limitations and Nuances

  • MOV same, same: As demonstrated, MOV instructions copying a register to itself (mov ecx, ecx) are generally not eliminated.
  • Vector MOV: While vector register copies (movaps xmm0, xmm1) are often eliminated on supporting CPUs, specific operations like PXOR xmm0, xmm0 still require an execution unit.
  • Register Overwriting: The exact behavior and efficiency of MOV elimination can be influenced by the processor’s internal tracking mechanisms, potentially involving limited-size tables for reference counts.
  • Microcode Updates: Errata in CPUs can lead to specific MOV operations being excluded from elimination via microcode patches.
  • Hyper-Threading: On some Intel processors, performance counters like uops_executed.thread might not be available when Hyper-Threading is enabled, potentially requiring the use of uops_executed.core instead.

The behavior observed across different CPU generations highlights the evolving nature of microarchitectural optimizations. While MOV elimination offers performance benefits by reducing latency and execution port pressure, its impact is always viewed within the context of the entire instruction pipeline and the specific workloads being executed.

FAQs on MOV Elimination

Q: What is MOV elimination

ANS: MOV elimination is a CPU optimization where a MOV instruction, particularly register-to-register copies, bypasses the execution units. It’s handled during the instruction issue or rename stage, effectively having zero latency and not consuming execution ports.

Q: Which CPUs support MOV elimination

ANS: AMD Bulldozer and Zen families (for vector registers), and Intel Ivy Bridge and later (for integer and most vector registers) generally support MOV elimination. Low-power Intel CPUs like Goldmont and Alder Lake E-cores also benefit. However, some Intel CPUs like Ice Lake and Tiger Lake have limitations due to microcode updates affecting integer registers.

Q: Can MOV same,same be eliminated

ANS: No, MOV instructions that copy a register to itself (e.g., mov ecx, ecx) are typically not subject to elimination because the source and destination are identical.

Q: Does MOV elimination affect loop performance

ANS: Yes, MOV elimination can significantly improve loop performance by reducing instruction latency. However, loops can still be bottlenecked by other factors like dependency chains, front-end issue width, or taken branch throughput.

Q: How can I check if MOV elimination is working

ANS: You can observe the difference in performance counter metrics like uops_issued.any versus uops_executed.thread. When MOV is eliminated, uops_issued.any will be higher as these instructions are issued but not executed. Benchmarking loops with and without the MOV instruction, or using MOV same,same versus MOV reg1, reg2, can also reveal its presence.
