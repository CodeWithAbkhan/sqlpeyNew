“Kernel Module File I/O: VFS vs. Direct Syscalls in Linux”

When developing modules for the Linux kernel, interacting with the filesystem requires careful attention to API stability and security contexts. Direct invocation of system call handlers is generally discouraged. What is the recommended, “deeper” approach for performing file Input/Output (I/O) operations within a kernel module, and what specific functions facilitate this?

The preferred methodology involves interfacing directly with the Virtual File System (VFS) layer functions, bypassing the user-space system call entry points whenever possible. This ensures the operations execute within the kernel’s context securely.

Implementing File Operations via VFS Functions (Pre-Kernel 4.14 Style)

For achieving file access similar to user-space open, read, write, and close, specific VFS helper routines exist. These often require manipulating the memory segment descriptor using get_fs() and set_fs() when dealing with paths or data buffers that might originate from or target user space, although for pure kernel access, the setup is slightly different.

Essential headers for this level of access include:

#include <linux/fs.h>
#include <asm/segment.h>
#include <asm/uaccess.h>
#include <linux/buffer_head.h>

Kernel File Opening Analogue (file_open)

To obtain a struct file * pointer analogous to the open(2) system call:

struct file *safe_kernel_file_open(const char *path, int flags, int rights) 
{
    struct file *filp = NULL;
    mm_segment_t oldfs;
    int err = 0;

    // Switch context to kernel data space for path processing
    oldfs = get_fs();
    set_fs(get_ds());
    
    filp = filp_open(path, flags, rights);
    
    // Restore original segment context
    set_fs(oldfs);
    
    if (IS_ERR(filp)) {
        err = PTR_ERR(filp);
        printk(KERN_ERR "File open failed with error: %d\n", err);
        return NULL;
    }
    return filp;
}

Kernel File Closing Analogue (file_close)

Releasing the file structure reference:

void safe_kernel_file_close(struct file *file) 
{
    if (file) {
        filp_close(file, NULL);
    }
}

Reading Data from a File (file_read)

Performing a read operation at a specified offset, again requiring context switching if paths or buffers are involved:

int kernel_pread_vfs(struct file *file, unsigned long long offset, unsigned char *data, unsigned int size) 
{
    mm_segment_t oldfs;
    int ret;

    oldfs = get_fs();
    set_fs(get_ds());

    // vfs_read uses the provided offset pointer
    ret = vfs_read(file, data, size, &offset);

    set_fs(oldfs);
    return ret;
}

Writing Data to a File (file_write)

Executing a write operation, similar in structure to reading:

int kernel_pwrite_vfs(struct file *file, unsigned long long offset, unsigned char *data, unsigned int size) 
{
    mm_segment_t oldfs;
    int ret;

    oldfs = get_fs();
    set_fs(get_ds());

    // vfs_write uses the provided offset pointer
    ret = vfs_write(file, data, size, &offset);

    set_fs(oldfs);
    return ret;
}

Synchronizing File Changes (file_sync)

Ensuring data is flushed to persistent storage:

int kernel_file_sync(struct file *file) 
{
    if (file) {
        // Use vfs_fsync for kernel synchronization calls
        vfs_fsync(file, 0);
    }
    return 0;
}

Note: Earlier versions sometimes suggested file_fsync, which is deprecated or removed in favor of the vfs_fsync pattern.

Evolving Kernel Interfaces (Linux Kernel 4.14+)

With the release of kernel version 4.14 and later, the VFS interface evolved to provide cleaner, safer kernel-space entry points that do not necessitate the manual setting and restoring of the memory segment descriptor (set_fs/get_fs) when dealing with kernel memory buffers.

The functions vfs_read and vfs_write are no longer exported for module use. Instead, specific kernel-only routines are provided:

  • Reading: ssize_t kernel_read(struct file *file, void *buf, size_t count, loff_t *pos);
  • Writing: ssize_t kernel_write(struct file *file, const void *buf, size_t count, loff_t *pos);

Crucially, because these functions are designed exclusively for kernel operations, filp_open can now be used directly without the segment context dance, as it is assumed the path string itself resides in kernel memory space.

Example using Modern Kernel APIs (Conceptual)

If you are targeting modern kernels (4.14+), the implementation simplifies significantly:

// Assume file structure obtained via filp_open (now safer for kernel paths)
struct file *kfile = filp_open("/path/to/kernel/data", O_RDWR, 0); 

if (!IS_ERR(kfile)) {
    char kernel_buffer[256];
    loff_t position = 0;
    ssize_t bytes_read;

    // Use kernel_read, buf is kernel pointer, pos is kernel pointer
    bytes_read = kernel_read(kfile, kernel_buffer, sizeof(kernel_buffer) - 1, &position);

    if (bytes_read > 0) {
        kernel_buffer[bytes_read] = '\0';
        printk(KERN_INFO "Read successful: %zd bytes\n", bytes_read);
    }

    filp_close(kfile, NULL);
}

This transition reflects the kernel’s ongoing effort to restrict unsafe access patterns and enforce proper context separation between user and kernel modes during file system interaction.

FAQs on Kernel Module File Interaction

Q: Why should kernel modules avoid direct system call handlers for file I O

ANS: Direct system call handling often bypasses necessary security checks and context validation that the VFS layer enforces, potentially leading to instability or security vulnerabilities if user space memory pointers are mishandled within the kernel context.

Q: What is the purpose of get_fs and set_fs

ANS: These functions manage the memory segment selector (mm_segment_t), which dictates whether memory access operations (like reading or writing data buffers) should target the user address space or the kernel address space.

Q: Are vfs_read and vfs_write available in all kernel versions for modules

ANS: No, after Linux kernel version 4.14, vfs_read and vfs_write are typically not exported for direct use in modules; developers should use kernel_read and kernel_write instead for kernel-space specific I/O.
