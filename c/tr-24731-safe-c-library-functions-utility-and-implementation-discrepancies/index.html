“TR 24731 Safe C Library Functions: Utility and Implementation Discrepancies”

The Technical Report (TR) 24731 introduces specifications for “safer” functions intended to mitigate common buffer overflow and error-handling vulnerabilities in C programming. However, developer adoption and perception vary widely, largely influenced by existing library support, perceived necessity, and critical differences between proposed standards and actual implementations, notably by Microsoft.

How do experienced developers view the utility of the TR 24731 bounds-checking interfaces (Part 1) and the dynamic allocation functions (Part 2)?

Developer Sentiment on TR 24731-1 (Bounds-Checking Interfaces)

A significant portion of the community expresses strong reservations about the efficacy and necessity of the TR 24731-1 functions.

Criticism Regarding Design Philosophy

Several experts view these functions as addressing symptoms rather than root causes in software design. They argue that adopting these interfaces can foster a false sense of security, potentially discouraging the rigorous application of existing, time-tested secure coding practices.

Ulrich Drepper, lead maintainer for glibc, famously criticized the proposal, stating:

The proposed safe(r) ISO C library fails to address to issue completely. … Proposing to make the life of a programmer even harder is not going to help. But this is exactly what is proposed. … They all require more work to be done or are just plain silly.

Furthermore, the review provided by the Austin Group (responsible for POSIX maintenance) detailed numerous issues with the proposed functions, leading some developers to avoid any implementation that supports or plans to support them. The perceived lack of widespread community traction, outside of the standards committee heavily influenced by entities like Microsoft, suggests limited future standardization success.

Compiler Support and Platform Specificity

Support for these functions appears predominantly tied to specific vendor toolchains:

  • Visual Studio: MSVC (e.g., Visual Studio 2008 onwards) often provides implementations and issues warnings encouraging their use.
  • glibc: This core library explicitly stated it would not support the proposed functions, avoiding the issue entirely for Linux environments relying on it.

Developers often find themselves forced to integrate platform-specific boilerplate code (#define __STDC_WANT_LIB_EXT1__ 1 and similar directives) simply to compile cleanly on Windows, undermining the goal of cross-platform consistency.

Value Assessment of Specific Functions

When forced to engage with these functions, developers highlight varying levels of utility:

  • Valuable: The removal of the dangerous %n format specifier from the printf_s() family is appreciated.
  • Low Value/Disappointing: Functions like tmpfile_s() and tmpnam_s() are criticized for not achieving true security improvements, falling short of robust alternatives like mkstemp() which simultaneously create and open the temporary file, avoiding Time-of-Check to Time-of-Use (TOCTOU) vulnerabilities. strerrorlen_s() is also noted as providing marginal benefit.

Implementation Divergence: Microsoft vs. ISO Standard

A critical factor inhibiting cross-platform utility is the inconsistency between Microsoft’s early implementations and the formal Annex K specification in C11. This divergence renders the functions effectively unusable for code intended to be portable across Windows and other systems without conditional compilation.

Example: vsnprintf_s() Interface Discrepancy

The ISO C11 standard (Annex K) defines vsnprintf_s with two primary buffer/size parameters:

// ISO/IEC 9899:2011 Annex K Interface
int vsnprintf_s(char * restrict s, rsize_t n,
                const char * restrict format, va_list arg);

However, older Microsoft documentation specified a three-parameter version:

// Microsoft MSDN Interface (Pre-UCRT changes)
int vsnprintf_s(
   char *buffer,
   size_t sizeOfBuffer,
   size_t count, // Maximum characters to write, or _TRUNCATE
   const char *format,
   va_list argptr 
);

The difference in argument count means direct substitution is impossible. Similar incompatibilities are noted in functions like scanf_s() (where buffer size parameter type differs) and localtime_s().

Example: strtok_s() Mismatch

The signature mismatch extends to string manipulation functions:

  • Microsoft Variant: char *strtok_s(char *strToken, const char *strDelimit, char **context); (3 arguments)
  • Annex K Variant: char *strtok_s(char * restrict s1, rsize_t * restrict s1max, const char * restrict s2, char ** restrict ptr); (4 arguments)

This disparity effectively eliminates the primary benefit of using the TR functions for writing code portable across Windows and POSIX-compliant systems.

TR 24731-2 (Dynamic Allocation Functions) Reception

The second part of the TR, focusing on dynamic memory allocation and string formatting, receives a warmer reception from those who have used similar features in other environments.

Developers strongly advocate for standardization of functionality similar to asprintf() and vasprintf() (prevalent in glibc). These functions provide a safe, flexible means to format text into a newly allocated string without manual size calculation.

Similarly, memory stream I/O functions, specifically open_memstream(), are praised. Like asprintf(), these allocate the necessary buffer and provide a FILE* interface, simplifying printing operations whether targeting a physical file or an in-memory buffer.

Alternative Approaches and Proposed Improvements

Rather than strictly adhering to TR 24731-1, some developers have created their own platform-independent safety layers, addressing the most frequently misused functions across Linux, Windows, and embedded systems.

A proposed improvement to the general string handling philosophy suggests modifying standard C functions like strcpy() and strcat() to return a pointer to the null terminator of the newly written string, rather than the start of the destination buffer. This idiom change would facilitate efficient string concatenation without recalculating string lengths repeatedly, while maintaining null-termination guarantees.

For functions like file opening, many argue that standard functions like fopen() followed by a mandatory return value check are sufficient, rendering functions like fopen_s() redundant unless specific, nuanced error reporting is critical.

Furthermore, BSD-derived functions like strlcpy() and strlcat(), though widely preferred by many C programmers for their simple and effective bounds handling, have been consistently rejected by both Microsoft and glibc proponents for proprietary reasons.

Status of Standardization

  • C11: Incorporates TR 24731-1 functions as an optional Annex K feature. It excludes the useful TR 24731-2 dynamic allocation functions.
  • C18: Maintained the status quo regarding Annex K.
  • Future Proposals: There have been serious proposals (e.g., N1967) to completely remove Annex K from subsequent C standards due to its flawed implementation experience and lack of traction.

FAQs on TR 24731 Safe C Library Functions

Q: What is the primary criticism against TR 24731-1 functions

ANS: The primary criticism is that they mask underlying software design flaws rather than fixing them, potentially creating a false sense of security and hindering the promotion of proven secure coding habits.

Q: Which TR 24731 functions are favored by developers in Part 2

ANS: Developers strongly favor standardization of asprintf()/vasprintf() functionality for safe dynamic string allocation and memory stream functions like open_memstream().

Q: Does the C11 standard include all TR 24731 functions

ANS: No C11 includes TR 24731-1 functions optionally in Annex K but omits the dynamic allocation functions specified in TR 24731-2.

Q: Why are Microsoft implementations of TR functions problematic

ANS: Microsoft’s early implementations, and sometimes even current ones, have function signatures and parameter types that differ from the formal ISO Annex K specification, breaking cross-platform code compatibility.
