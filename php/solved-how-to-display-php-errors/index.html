“Solved How to Display PHP Errors”

This comprehensive guide explores various effective strategies to reveal those hidden PHP errors, from server-wide configurations to in-script overrides and advanced debugging tools.

Method 1: Configuring PHP Directives (php.ini, .htaccess, or in-script)

The core of PHP error reporting lies within two crucial directives: error_reporting and display_errors.

Option A: Modifying php.ini (Recommended for Development Environments)

This is the most robust way to enable error display, as it affects how PHP compiles and runs all your scripts. Syntax errors, which prevent your script from even executing, will only be caught if these settings are enabled in your loaded php.ini.

Steps to Modify php.ini:

  1. Locate your php.ini file: Create a new PHP file (e.g., info.php) with the following content: 
    <?php
phpinfo();
?>
    Browse to this file in your web browser. Look for “Loaded Configuration File” and “Additional .ini files parsed” at the top of the output. These paths will guide you to the active php.ini file.
  2. Edit the php.ini file: Find and set the following directives: 
    ; Enable displaying errors directly in the browser output
display_errors = On

; Report all PHP errors, warnings, and notices
error_reporting = E_ALL
    For PHP versions 5.2.4 or newer, display_errors can also be set to "stderr" to direct errors to the standard error output stream, which is useful in certain server setups. 
    display_errors = "stderr"
    For the most comprehensive error reporting that covers all possible error types across PHP versions, error_reporting can also be set to -1: 
    ; Report all possible PHP errors
error_reporting = -1
  3. Restart your web server: After saving changes to php.ini, you must restart your web server (e.g., Apache, Nginx) or PHP-FPM for the changes to take effect.

Option B: Using In-Script ini_set() and error_reporting()

For specific scripts or when you don’t have access to php.ini (common in shared hosting environments), you can override the default PHP settings at runtime. Place these lines at the very beginning of your PHP script to ensure they take effect before most of your code executes.

<?php
// Enable displaying all errors directly to the browser
ini_set('display_errors', '1'); // Can also use 'On'

// Configure PHP to report all types of errors
error_reporting(E_ALL);

// Optionally, enable display of startup errors
ini_set('display_startup_errors', 1);

// You can also fine-tune error reporting, e.g., to exclude notices
// error_reporting(E_ALL & ~E_NOTICE);

// Your application's PHP code follows here
// ...
?>

Important Consideration: These in-script directives will not catch syntax errors (parse errors) that occur before these lines are processed, as the script literally fails to compile at that point. For such critical errors, the php.ini or web server log approach is necessary.

Option C: Modifying .htaccess File (Apache Web Server)

For Apache web servers, you can place directives in an .htaccess file within your project’s root directory. This provides a way to control PHP settings for specific directories without modifying the main php.ini. However, this method is less commonly supported on modern, well-managed servers due to performance overhead and security implications.

Create or edit your .htaccess file:

# Enable PHP error display for this directory
php_flag  display_errors        on

# Set PHP error reporting level to all errors (-1 is equivalent to E_ALL)
php_value error_reporting       -1

Remember that .htaccess changes might require Apache’s AllowOverride All directive to be set for the directory.

Method 2: Inspecting Error Logs

Regardless of whether errors are displayed on screen, PHP usually logs them to a file. Checking these logs is vital, especially for errors that prevent your script from fully executing (like syntax errors) or for production environments where display_errors should be Off.

Option A: PHP Error Log

By default, PHP can log errors to a file. Ensure log_errors is set to On in your php.ini:

log_errors = On
error_log = /path/to/your/php_error_log.txt ; Specify a path for the log file

The php_error_log.txt (or whatever you name it) will contain detailed error messages, including timestamps and file/line numbers.

Option B: Web Server Error Logs (Apache, Nginx)

Your web server (Apache, Nginx, IIS) also maintains its own error logs. Syntax errors and other issues preventing PHP from even starting up are often recorded here.

  • Apache: Look for error.log typically in /var/log/apache2/ on Linux, or logs/ within your Apache installation directory on Windows. You can tail the log file in real-time on Linux: 
    sudo tail -f /var/log/apache2/error.log
    This command displays the last few lines of the log and continues to show new lines as they are added, offering immediate feedback during debugging. You might also want to check the last 50 errors: 
    sudo tail -50f /var/log/apache2/error.log
  • Nginx: Error logs are usually found in /var/log/nginx/error.log.
  • IIS: Errors can be found in the event viewer or specific IIS logs.

Method 3: Utilizing Debugging Tools and IDEs

For more sophisticated debugging, dedicated tools and integrated development environments (IDEs) offer enhanced capabilities beyond simple error display.

Option A: Xdebug

Xdebug is a powerful PHP extension that provides a wealth of debugging features, including stack traces, function call logging, code coverage analysis, and remote debugging with IDEs like VS Code, PhpStorm, or Sublime Text. It makes error reports much more informative and allows you to step through your code line by line.

Option B: IDEs with Built-in Debuggers

Modern IDEs for PHP development often come with integrated debuggers or support Xdebug setup:

  • PhpStorm: Renowned for its robust PHP support and excellent Xdebug integration.
  • Visual Studio Code (VS Code): With the PHP Debug extension, VS Code offers powerful debugging capabilities.
  • PhpEd: Provides a debugger very similar to Xdebug, integrating directly into the editor for a unified debugging experience.

These tools allow you to set breakpoints, inspect variables, and follow the execution flow, providing a much deeper insight into your code’s behavior and the origin of errors.

Option C: Nette Tracy

For better visualization of errors and exceptions in PHP, consider using a library like Nette Tracy . It provides a beautiful and highly functional error page with stack traces, request data, and much more, making it easier to diagnose issues.

Method 4: Implementing Custom Error and Shutdown Handlers

For ultimate control over how errors are processed and displayed, you can register your own custom error and shutdown functions. This allows you to log errors to custom locations, format them, or send notifications.

Custom Error Handler Example:

This code defines a function ErrorHandler that takes error details and formats them before printing.

<?php

// Enable displaying errors, but control HTML output
ini_set('display_errors', 'On');
ini_set('html_errors', 0); // No HTML tags in error messages

// Report all errors
error_reporting(-1);

/**
 * Custom function to handle PHP errors.
 *
 * @param int    $type    The error type.
 * @param string $message The error message.
 * @param string $file    The file where the error occurred.
 * @param int    $line    The line number where the error occurred.
 * @return bool True if the error was handled, false otherwise.
 */
function CustomPhpErrorHandler($type, $message, $file, $line)
{
    $_KNOWN_ERRORS = [
        0x0001 => 'E_ERROR',
        0x0002 => 'E_WARNING',
        0x0004 => 'E_PARSE',
        0x0008 => 'E_NOTICE',
        0x0010 => 'E_CORE_ERROR',
        0x0020 => 'E_CORE_WARNING',
        0x0040 => 'E_COMPILE_ERROR',
        0x0080 => 'E_COMPILE_WARNING',
        0x0100 => 'E_USER_ERROR',
        0x0200 => 'E_USER_WARNING',
        0x0400 => 'E_USER_NOTICE',
        0x0800 => 'E_STRICT',
        0x1000 => 'E_RECOVERABLE_ERROR',
        0x2000 => 'E_DEPRECATED',
        0x4000 => 'E_USER_DEPRECATED'
    ];

    $error_name = array_search($type, array_flip($_KNOWN_ERRORS));
    if (!$error_name) {
        $error_name = 'E_UNKNOWN';
    }

    // Output the formatted error message
    error_log(sprintf("%s Error in file '%s' at line %d: %s\n", $error_name, basename($file), $line, $message));
    return true; // Indicate that the error was handled
}

// Set our custom error handler
$previous_error_handler = set_error_handler("CustomPhpErrorHandler");

// Example of code that might trigger an error
// trigger_error("This is a custom error message.", E_USER_WARNING);

// Other PHP code would go here
// ...
?>

Shutdown Handler Example:

A shutdown function is registered to execute when the script finishes or unexpectedly terminates. This is particularly useful for catching fatal errors that cannot be handled by a regular error handler.

<?php

// Enable error reporting
error_reporting(E_ALL);
ini_set('display_errors', 'On');

/**
 * Handles fatal errors or last occurring error during script shutdown.
 */
function ScriptShutdownHandler()
{
    // Retrieve information about the last error that occurred
    $last_error = error_get_last();

    // Check if a fatal error or other type of error occurred
    if ($last_error && is_array($last_error)) {
        // You can log this error, display it, or trigger a custom error handler
        // For demonstration, let's dump it. In production, you'd log it.
        echo "<pre>Fatal Error or Script Termination Issue:\n";
        var_dump($last_error);
        echo "</pre>";
        // Optionally, call a custom error handler for the last error
        // return call_user_func_array('CustomErrorHandlerFunction', $last_error);
    }
    return true; // Indicate normal shutdown or handled error
}

// Register the shutdown function
register_shutdown_function('ScriptShutdownHandler');

Method 5: Environment-Specific Error Display

For projects with development and production environments, it’s best practice to conditionally enable error display based on the environment.

<?php
// Determine if the current environment is local or development
$is_dev_environment = (
    $_SERVER['SERVER_NAME'] === "127.0.0.1" ||
    $_SERVER['SERVER_NAME'] === "localhost" ||
    substr($_SERVER['SERVER_NAME'], 0, 3) === "192" || // Common for local IPs
    strpos($_SERVER['SERVER_NAME'], '.dev') !== false // Custom local domains
);

if ($is_dev_environment) {
    // Enable full error display and reporting for development
    ini_set('display_errors', 'On');
    ini_set('display_startup_errors', 'On'); // Display errors that occur during PHP's startup sequence
    error_reporting(E_ALL | E_STRICT); // Report all errors including strict standards
    ini_set('html_errors', '1'); // Display errors as HTML

    // Customize error output for better readability in browser
    ini_set('error_prepend_string', "<div style='color:red; font-family:monospace; border:1px solid red; padding:8px; margin:10px 0;'>");
    ini_set('error_append_string', "</div>");
} else {
    // In production, disable display errors but ensure logging
    ini_set('display_errors', 'Off');
    ini_set('display_startup_errors', 'Off');
    error_reporting(E_ALL & ~E_NOTICE & ~E_DEPRECATED & ~E_STRICT); // Log all but notices/deprecated/strict
    ini_set('log_errors', 'On');
    ini_set('error_log', '/path/to/your/production_error_log.txt'); // Specific log file for production
}

// Example usage of a custom APPLICATION_LIVE constant
if (preg_match("%^(www.)?yourlivedomain.com$%", $_SERVER["HTTP_HOST"])) {
    define('APPLICATION_LIVE', true);
} elseif (preg_match("%^(www.)?yourdevdomain.net$%", $_SERVER["HTTP_HOST"])) {
    define('APPLICATION_LIVE', false);
} else {
    die("INVALID HOST REQUEST (" . $_SERVER["HTTP_HOST"] . ")");
    // You'd log this or take other appropriate action.
}

if (!APPLICATION_LIVE) {
    // Development-specific error settings using APPLICATION_LIVE
    ini_set("display_errors", "1");
    ini_set("display_startup_errors", "1");
    ini_set("html_errors", "1");
    ini_set("docref_root", "http://www.php.net/");
    ini_set("error_prepend_string", "<div style='color:red; font-family:verdana; border:1px solid red; padding:5px;'>");
    ini_set("error_append_string", "</div>");
}
// Further PHP code
// ...
?>

Method 6: Database Error Reporting

When working with databases, it’s essential to configure your database libraries to throw exceptions for errors instead of returning false or silent failures. This makes database-related issues immediately apparent. Learn more about databases like MySQL or Oracle , and general SQL concepts.

MySQLi Exceptions:

Add this near the top of your script, before creating a new mysqli instance:

<?php
// Enable MySQLi to throw exceptions on errors or strict warnings
mysqli_report(MYSQLI_REPORT_ERROR | MYSQLI_REPORT_STRICT);

// Example MySQLi connection (will now throw exception on failure)
// $db_connection = new mysqli("localhost", "user", "wrong_pass", "db_name");
?>

PDO Exceptions:

Set the PDO::ATTR_ERRMODE attribute to PDO::ERRMODE_EXCEPTION when creating your PDO instance or afterwards.

<?php
try {
    // Create a PDO connection and set error mode in constructor
    $pdo_instance = new PDO('mysql:host=localhost;dbname=testdb', 'db_user', 'db_pass', [
        PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION
    ]);

    // Or set it after creating the instance
    // $pdo_instance->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);

    // Example: This will now throw a PDOException on error
    // $pdo_instance->query("SELECT * FROM non_existent_table");

} catch (PDOException $e) {
    // Catch and display the PDO exception
    echo "Database Error: " . $e->getMessage();
}
?>

Method 7: Debugging Specific PHP Features

Some PHP functions or libraries have their own error reporting mechanisms that require specific activation.

JSON Parsing Errors:

After using json_decode() or json_encode(), use json_last_error() and json_last_error_msg() to get details about any parsing issues. For more details on JSON errors, see methods to fix JSONDecodeError for other languages too.

<?php
$malformed_json_data = '{ "name": "Test", "age": 30, }'; // Trailing comma makes it invalid JSON

$decoded_data = json_decode($malformed_json_data);

if (json_last_error() !== JSON_ERROR_NONE) {
    echo "JSON Error encountered: " . json_last_error_msg();
    // Common JSON errors can also be seen in Python: https://sqlpey.com/python/top-10-methods-to-fix-jsondecodeerror-expecting-value/
}
?>

Regular Expression Errors:

Use preg_last_error() after any preg_ function call to identify regex-related problems.

<?php
$pattern_with_error = '/abc['; // Unclosed character class

preg_match($pattern_with_error, 'test string');

if (preg_last_error() !== PREG_NO_ERROR) {
    echo "Regex Error: " . preg_last_error();
}
?>

cURL Request Debugging:

When making HTTP requests using cURL, enabling CURLOPT_VERBOSE provides detailed output about the request and response.

<?php
$curl_session = curl_init();
curl_setopt($curl_session, CURLOPT_URL, "http://example.com");
curl_setopt($curl_session, CURLOPT_RETURNTRANSFER, true);
curl_setopt($curl_session, CURLOPT_VERBOSE, true); // Enable verbose output for debugging

$curl_response = curl_exec($curl_session);

if (curl_errno($curl_session)) {
    echo 'Curl error: ' . curl_error($curl_session);
}

curl_close($curl_session);
?>

Shell Command Execution:

When executing shell commands via exec(), shell_exec(), etc., redirecting standard error (2>&1) and checking the return status is essential.

<?php
$command_output = '';
$return_status = -1;

// Example: Try to list a non-existent directory and capture all output
exec('ls -l /nonexistent_dir 2>&1', $command_output, $return_status);

if ($return_status !== 0) {
    echo "Command failed with status: " . $return_status . "\n";
    echo "Output: \n" . implode("\n", $command_output);
}
?>

Method 8: Other Useful Tips

  • error_reporting(~0): This bitwise NOT operator for 0 ~0 effectively turns on all error bits, ensuring all possible errors are reported regardless of PHP version changes to the E_ALL constant. 
    <?php
error_reporting(~0); // Report every single error, warning, notice, etc.
ini_set('display_errors', 1); // Ensure they are displayed
?>
  • error_get_last(): This function can retrieve information about the last error that occurred. It’s especially handy in shutdown functions or when error display is off and you need to get the last known issue. 
    <?php
// Simulate an error
$undefined_variable = $non_existent_var;

// Retrieve the last error details
$last_error_info = error_get_last();

if ($last_error_info) {
    echo "<pre>Last Error Detected:\n";
    var_dump($last_error_info);
    echo "</pre>";
}
?>
  • Avoid @ operator during development: The @ (error suppression) operator should generally be avoided during development as it hides errors, making debugging difficult. Use it sparingly and only when you explicitly expect and handle potential errors.
  • Strict Typing (declare(strict_types=1)): While not directly an error display mechanism, using strict types in PHP 7+ can help catch type-related errors earlier, leading to more predictable code. 
    <?php
declare(strict_types=1);

function sumNumbers(int $a, int $b): int {
    return $a + $b;
}

// This would now cause a TypeError
// sumNumbers(5, '10');
?>

FAQs on Solved How to Display PHP Errors

Q: Why are my PHP errors not showing

ANS: PHP errors might not be showing due to default server configurations that disable display_errors in php.ini or .htaccess for security reasons, especially in production environments. Syntax errors can also prevent ini_set from taking effect.

Q: How to enable display errors in phpini

ANS: To enable display errors in php.ini, locate your php.ini file (using phpinfo()), then find the display_errors directive and set it to On. Remember to restart your web server afterward for the changes to apply.

Q: What is error_reporting E ALL

ANS: error_reporting(E_ALL) is a PHP function that sets the error reporting level to display all possible PHP errors, warnings, and notices. It helps developers see even minor issues in their code during development. Using -1 is also an equivalent for E_ALL.

Q: Can I use htaccess for PHP error settings

ANS: Yes, you can use an .htaccess file to override PHP error settings like display_errors and error_reporting if your web server configuration (Apache) allows it. However, this method is often discouraged for performance and security reasons compared to php.ini or in-script ini_set.

Q: What is Xdebug used for

ANS: Xdebug is a powerful PHP extension primarily used for debugging. It provides advanced features such as step debugging (executing code line by line), stack traces, code coverage analysis, and profiling, significantly aiding in identifying and resolving complex issues in PHP applications.
