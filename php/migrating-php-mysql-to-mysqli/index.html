“Migrating PHP mysql_* to mysqli_* : Best Practices & Code Examples”

When working with PHP and databases, transitioning from the older mysql_* functions to the more robust mysqli_* extension is a critical step for security, performance, and compatibility with modern PHP versions. This post delves into various approaches and provides practical code examples to facilitate this migration.

Why Migrate from mysql_* to mysqli_*?

The mysql_* extension has been deprecated since PHP 5.5 and removed in PHP 7.0. Its use is strongly discouraged due to security vulnerabilities and lack of support for newer MySQL features. The mysqli_* (MySQL Improved) extension offers significant advantages, including:

  • Object-Oriented Interface: A cleaner, more readable, and less error-prone way to interact with the database.
  • Prepared Statements: Essential for preventing SQL injection attacks, a common security flaw.
  • Enhanced Debugging: Better error reporting mechanisms.
  • Support for Newer MySQL Features: Access to advanced functionalities available in recent MySQL versions.

Solution Approaches for Migration

Several strategies can be employed to transition your codebase from mysql_* to mysqli_*.

Solution 1: Direct Function Replacement (Procedural Style)

The most straightforward approach involves systematically replacing mysql_* function calls with their mysqli_* equivalents. The mysqli extension provides a procedural API that closely mirrors the old mysql_* functions, making the transition smoother for those familiar with the older style.

Key Replacements:

  • mysql_connect() becomes mysqli_connect()
  • mysql_error() becomes mysqli_connect_error() or mysqli_error($link)
  • mysql_query() becomes mysqli_query($link, $query)
  • mysql_select_db() can be integrated into mysqli_connect() as a fourth parameter or used as mysqli_select_db($link, $dbName)

Example:

Consider this old mysql_* code:

<?php
// Old mysql_* connection
$link = mysql_connect("localhost", "user", "password");
mysql_select_db("mydatabase", $link);
$result = mysql_query("SELECT * FROM users", $link);
// ... process $result
mysql_close($link);
?>

Here’s how you would rewrite it using the procedural mysqli_* API:

<?php
// New mysqli_* connection (procedural)
$link = mysqli_connect("localhost", "user", "password", "mydatabase");

if (mysqli_connect_errno()) {
    die("Connect failed: " . mysqli_connect_error());
}

$result = mysqli_query($link, "SELECT * FROM users");

if (!$result) {
    die('Invalid query: ' . mysqli_error($link));
}

// ... process $result
mysqli_close($link);
?>

Important Note: Many mysqli_* functions require the database connection link as the first argument, unlike their mysql_* predecessors. For instance, mysql_query($query) becomes mysqli_query($link, $query).

Solution 2: Object-Oriented Approach with mysqli

The mysqli extension also offers a powerful object-oriented interface, which is generally recommended for new development and for refactoring existing code to improve clarity and maintainability.

Example Connection:

<?php
// New mysqli_* connection (Object-Oriented)
$mysqli = new mysqli("localhost", "user", "password", "mydatabase");

if ($mysqli->connect_errno) {
    die("Connect failed: (" . $mysqli->connect_errno . ") " . $mysqli->connect_error);
}

// Set character set for better compatibility
if (!$mysqli->set_charset("utf8mb4")) {
    printf("Error loading character set utf8mb4: %s\n", $mysqli->error);
    exit();
}

$result = $mysqli->query("SELECT * FROM users");

if (!$result) {
    die('Invalid query: (' . $mysqli->errno . ') ' . $mysqli->error);
}

// ... process $result
$mysqli->close();
?>
Solution 3: Leveraging Prepared Statements for Security

Prepared statements are crucial for preventing SQL injection. The mysqli extension supports them natively.

Example:

<?php
$mysqli = new mysqli("localhost", "user", "password", "mydatabase");

if ($mysqli->connect_errno) {
    die("Connect failed: " . $mysqli->connect_error);
}

// Get user input
$user_input = $_POST['username'];

// Prepare the statement
$stmt = $mysqli->prepare("SELECT * FROM users WHERE username = ?");

// Bind parameters (s = string, i = integer, d = double, b = blob)
$stmt->bind_param('s', $user_input);

// Execute the statement
$stmt->execute();

// Get the result
$result = $stmt->get_result();

// Fetch data
while ($row = $result->fetch_assoc()) {
    print_r($row);
}

$stmt->close();
$mysqli->close();
?>

Comparison to mysql_real_escape_string:

While mysql_real_escape_string was used in the old mysql_* extension for escaping strings, it was not a foolproof solution against SQL injection. Prepared statements are the recommended and secure method.

Solution 4: Automated Migration with Tools

For large projects with numerous files, manual replacement can be time-consuming. Tools like Rector can automate the migration process.

Using Rector:

  1. Install Rector:

    composer require rector/rector --dev

  2. Create rector.php in your project root:

    <?php

use Rector\Set\ValueObject\SetList;
use Rector\Config\RectorConfig;

return static function (RectorConfig $rectorConfig): void {
    $rectorConfig->sets([
        SetList::MYSQL_TO_MYSQLI,
    ]);
};

  3. Run Rector:

    • To see the proposed changes: 
      vendor/bin/rector process src --dry-run
    • To apply the changes: 
      vendor/bin/rector process src

    Replace src with the directory containing your PHP files.

Solution 6: Considering PDO

For a more abstract and database-agnostic approach, consider using PHP Data Objects (PDO). PDO provides a consistent interface across different database systems, making it easier to switch databases in the future.

Example PDO Connection:

<?php
$host = 'localhost';
$db   = 'mydatabase';
$user = 'user';
$pass = 'password';
$charset = 'utf8mb4';

$dsn = "mysql:host=$host;dbname=$db;charset=$charset";
$options = [
    PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
    PDO::ATTR_EMULATE_PREPARES   => false,
];

try {
    $pdo = new PDO($dsn, $user, $pass, $options);
} catch (\PDOException $e) {
    throw new \PDOException($e->getMessage(), (int)$e->getCode());
}

// Using prepared statements with PDO
$stmt = $pdo->prepare("SELECT * FROM users WHERE username = ?");
$stmt->execute([$_POST['username']]);
$user = $stmt->fetch();

print_r($user);
?>

Key Considerations During Migration

  • Connection Parameters: Ensure all connection parameters are correctly passed. With mysqli, the database name can be passed as the fourth argument to mysqli_connect().
  • Error Handling: Implement robust error handling. mysqli supports exceptions, which can simplify error management. Enable reporting with mysqli_report(MYSQLI_REPORT_ERROR | MYSQLI_REPORT_STRICT);.
  • Function Signatures: Pay close attention to the arguments required by mysqli_* functions, especially the connection link identifier.
  • Character Sets: Explicitly set the character set (e.g., utf8mb4) using mysqli_set_charset() for proper handling of diverse character data.
  • Deprecations: Be aware that some older mysql_* functions have no direct mysqli counterpart (e.g., mysql_create_db). You may need to use mysqli_query() with SQL statements like CREATE DATABASE or rely on prepared statements for database manipulation.
  • Legacy Code Management: For extensive legacy codebases, consider a phased migration or the use of shim functions as a temporary bridge. However, a complete rewrite using modern practices like prepared statements and object-oriented mysqli or PDO is the ideal long-term solution.

Conclusion on Migration

Migrating from the deprecated mysql_* extension to mysqli_* is essential for maintaining secure, efficient, and modern PHP applications. While manual replacement is feasible for smaller projects, tools like Rector can significantly accelerate the process for larger codebases. Always prioritize security by adopting prepared statements. For long-term flexibility, consider PDO.

FAQs on Migrating PHP mysql_* to mysqli_*

Q: What is the main reason to move from mysql to mysqli in PHP

ANS: The primary reasons are security, performance, and compatibility. The mysql_* extension is deprecated and removed in recent PHP versions, lacks support for modern MySQL features, and is more vulnerable to security threats like SQL injection compared to mysqli’s prepared statements and improved error handling.

Q: Can I still use the procedural style with mysqli

ANS: Yes, the mysqli extension offers both an object-oriented and a procedural API. The procedural API closely mirrors the old mysql_* functions, making it a familiar transition for developers.

Q: Is it mandatory to switch to mysqli or PDO

ANS: If you are using PHP 7 or later, it is mandatory to switch, as the mysql_* extension has been removed. For older PHP versions, it is strongly recommended for security and to leverage newer database features.

Q: How do prepared statements improve security

ANS: Prepared statements separate the SQL command from the data. The database server compiles the command first, and then the data is sent separately, ensuring that any special characters in the data are treated as literal values rather than executable SQL code, thus preventing SQL injection.

Q: What is the difference between mysqli_connect_error and mysqli_error

ANS: mysqli_connect_error() is used to retrieve the error message from the last connection attempt. mysqli_error($link) (or $mysqli->error in OO style) is used to retrieve the error message from the last query execution on a specific connection ($link or $mysqli).

Q: How can I handle character encoding issues during migration

ANS: After establishing a connection using mysqli, it is crucial to set the character set using $mysqli->set_charset("utf8mb4"); or mysqli_set_charset($link, "utf8mb4"); to ensure consistent data handling.
