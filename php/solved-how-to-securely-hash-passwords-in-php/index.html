Q: What are the fundamental 'Don'ts' when handling passwords in PHP?

ANS: Absolutely avoid limiting password characters or length. Never strip or escape special characters. Critically, never store passwords in plain text, email them insecurely, or log them. Refrain from using weak hashing algorithms like SHA1, MD5, or even SHA256, as modern cracking methods can easily defeat them. Also, ensure you don’t mix bcrypt with the raw output of hash() to prevent security weaknesses.

Q: What are the recommended 'Dos' for secure password handling in PHP?

ANS: Prioritize using scrypt when possible, and bcrypt if scrypt isn’t an option. For situations where neither is available, PBKDF2 with SHA2 hashes is a viable alternative. Always reset all user passwords if the database is compromised. For enhanced security, enforce a minimum password length (e.g., 8-10 characters) and require a mix of uppercase letters, lowercase letters, numbers, and symbols to increase password entropy.

Q: Why is password hashing so crucial?

ANS: Password hashing is essential for protecting user accounts from malicious access when a database is compromised. The primary goal is to deter attackers by making it computationally expensive (in terms of time and money) to decipher plain-text passwords. Robust hashing also provides a critical window to change all passwords in a system if a breach occurs.

Q: What contributes to a strong password?

ANS: A strong password relies on entropy, which is the measure of variation within the password. Passwords using a broad range of characters (uppercase, lowercase, numbers, symbols) have higher entropy than those limited to just letters. Longer passwords and those incorporating Unicode characters can significantly increase entropy, making them harder to crack. While complexity requirements can help, overly predictable patterns can sometimes reduce entropy.

Q: What are the current best practices for password hashing in PHP?

ANS: The current best practices strongly recommend bcrypt and scrypt. While scrypt is considered more future-proof, bcrypt is widely adopted and has seen extensive review. PBKDF2 with SHA2 hashes serves as a solid fallback. For PHP versions 5.5 and later, the built-in password_hash() and password_verify() functions abstract much of the complexity and are highly recommended.

Solved: How to Securely Hash Passwords in PHP

Ensuring the security of user passwords is a fundamental aspect of web development. Storing passwords insecurely can lead to severe breaches, compromising user accounts and sensitive data. This guide delves into the critical do’s and don’ts, the rationale behind robust hashing, and practical implementation strategies using PHP.

The Pillars of Secure Password Handling: Do’s and Don’ts

Before diving into specific algorithms, understanding the core principles of secure password management is paramount.

What NOT to Do:

  • Don’t Restrict Characters or Length: Allow users to create complex passwords using a wide range of characters and lengths. Imposing arbitrary limits can paradoxically weaken security by forcing users into predictable patterns.
  • Don’t Strip or Escape: Never manipulate or escape characters in a password before hashing. This can alter the intended password and lead to usability issues.
  • Never Store Plain-Text Passwords: This is the most critical security sin. If your database is compromised, all passwords will be immediately exposed.
  • Avoid Emailing Passwords: Sending passwords via email, especially in plain text, is highly insecure. If a user loses their password, issue a temporary one or provide a secure reset mechanism.
  • Never Log Passwords: Passwords should never be written to log files, even for debugging purposes.
  • Steer Clear of Weak Hashing Algorithms: MD5, SHA1, and SHA256 are easily crackable with modern hardware. Advanced brute-force attacks can defeat these algorithms rapidly.
  • Don’t Mix Hashing Outputs: If using algorithms like bcrypt, ensure consistent output formatting (e.g., hex or base64) and avoid mixing them with the raw output of other hashing functions.

What TO Do:

  • Embrace Modern Hashing Algorithms: Utilize scrypt for its resistance to specialized hardware attacks. If scrypt is unavailable, bcrypt is the next best choice. PBKDF2 with SHA2 hashes is a suitable alternative when the former are not an option.
  • Implement Password Salting: Always salt passwords. A salt is a unique, random string added to a password before hashing. This ensures that even identical passwords have different hash outputs, preventing attackers from using pre-computed rainbow tables for cracking.
  • Reset Passwords Post-Compromise: If your database is breached, the most secure course of action is to reset all user passwords immediately.
  • Enforce Strong Password Policies: Encourage users to create strong passwords by implementing policies that require a minimum length (e.g., 8-10 characters) and a mix of character types (uppercase, lowercase, numbers, symbols). This increases password entropy.

Why Hash Passwords? The Defense Against Breaches

The fundamental reason for hashing passwords is to create a one-way transformation that is computationally expensive to reverse. When a user registers, their password is not stored directly but as a hash. When they log in, the entered password is hashed using the same method and salt, and this new hash is compared to the stored hash.

This process serves several critical functions:

  1. Deters Attackers: By making password retrieval difficult and time-consuming, hashing discourages attackers. Even if an attacker gains access to the database, they cannot easily obtain the plain-text passwords.
  2. Mitigates Data Exposure: In the event of a data breach, the exposure of hashed passwords is far less damaging than the exposure of plain-text credentials.
  3. Provides Time for Response: A robust hashing algorithm gives administrators sufficient time to detect a breach, secure the system, and notify users, potentially before significant damage is done.

As Jeremiah Grossman, CTO of Whitehat Security, noted, “password storage is ever so much more important than password complexity.” If passwords are not stored securely, complexity alone offers little protection.

What Constitutes a “Good” Password? The Role of Entropy

Entropy, in the context of passwords, refers to the randomness and unpredictability of a password. Higher entropy means a password is harder to guess or crack.

  • Character Set: Using a wider range of characters (alphanumeric, symbols, and potentially Unicode) increases entropy. A password composed solely of lowercase letters has much lower entropy than one including uppercase letters, numbers, and symbols.
  • Length: Longer passwords inherently have more possible combinations, thus higher entropy.
  • Randomness vs. Patterns: While patterns make passwords memorable, they reduce entropy. Truly random passwords are the most secure but often the least memorable. Striking a balance, perhaps through passphrases or password managers, is key.

It’s a delicate balance; overly strict policies on character types or patterns can sometimes reduce entropy by making passwords predictable. The goal is to make them as random and unpredictable as possible while remaining usable.

Best Practices: bcrypt and scrypt

bcrypt: This algorithm is built on the Blowfish cipher and includes a “cost” factor, which dictates how computationally intensive the hashing process is. By increasing the cost, you make brute-force attacks significantly harder, though it also increases server load. bcrypt is widely supported and considered a strong standard.

scrypt: Designed to be even more resistant to specialized hardware attacks (like those using GPUs or ASICs) than bcrypt, scrypt uses more memory-intensive computations. While gaining traction, its adoption might not be as widespread as bcrypt yet.

PHP’s Built-in Solution: password_hash() and password_verify()

Since PHP 5.5, the language provides a robust, built-in API for password handling: password_hash() and password_verify(). This is the highly recommended approach for modern PHP applications.

  • password_hash($password, PASSWORD_DEFAULT, ['cost' => 12]);

    This function takes the plain-text password, a hashing algorithm constant ( PASSWORD_DEFAULT is recommended as it points to the strongest algorithm supported by the PHP version), and an optional array of options, including the cost factor. It automatically generates a secure, random salt and includes it within the resulting hash string.

  • password_verify($password, $hash);

    This function compares a plain-text password against a stored hash. It extracts the salt and algorithm used from the hash itself, ensuring correct verification even if the underlying default algorithm changes in future PHP versions.

<?php
// Example of using password_hash() and password_verify()

$userPassword = 'P@sswOrd123!';

// Hash the password with a cost factor of 12
// PASSWORD_DEFAULT will use the strongest algorithm available in your PHP version
$hashedPassword = password_hash($userPassword, PASSWORD_DEFAULT, ['cost' => 12]);

echo "Hashed Password: " . $hashedPassword . "\n";

// To verify a login attempt:
$loginAttemptPassword = 'P@sswOrd123!';
if (password_verify($loginAttemptPassword, $hashedPassword)) {
    echo "Password verification successful!\n";
} else {
    echo "Password verification failed.\n";
}

$wrongPassword = 'wrongPassword!';
if (password_verify($wrongPassword, $hashedPassword)) {
    echo "Password verification successful!\n"; // This will not be printed
} else {
    echo "Password verification failed.\n";
}
?>

This approach is superior because it handles salt generation, algorithm selection, and re-hashing logic automatically, making it difficult for developers to make critical security mistakes.

Alternative Hashing: PBKDF2

When bcrypt or scrypt are not options, PBKDF2 (Password-Based Key Derivation Function 2) is a strong alternative. It involves repeatedly applying a pseudorandom function (like SHA256) to the password along with a salt. The number of iterations (a “cost” factor) determines its resistance to brute-force attacks.

A common implementation pattern for PBKDF2 involves storing the algorithm, iterations, salt, and the final hash in a delimited string.

<?php
/*
 * Password hashing with PBKDF2.
 * Author: havoc AT defuse.ca
 * www: https://defuse.ca/php-pbkdf2.htm
 */

// These constants may be changed without breaking existing hashes.
define("PBKDF2_HASH_ALGORITHM", "sha256");
define("PBKDF2_ITERATIONS", 1000); // Recommended minimum is 1000, but higher is better
define("PBKDF2_SALT_BYTES", 24);
define("PBKDF2_HASH_BYTES", 24);

define("HASH_SECTIONS", 4);
define("HASH_ALGORITHM_INDEX", 0);
define("HASH_ITERATION_INDEX", 1);
define("HASH_SALT_INDEX", 2);
define("HASH_PBKDF2_INDEX", 3);

function create_hash($password)
{
    // Generate a random salt
    $salt = base64_encode(mcrypt_create_iv(PBKDF2_SALT_BYTES, MCRYPT_DEV_URANDOM));
    
    // Format: algorithm:iterations:salt:hash
    return PBKDF2_HASH_ALGORITHM . ":" . PBKDF2_ITERATIONS . ":" .  $salt . ":" . 
        base64_encode(pbkdf2(
            PBKDF2_HASH_ALGORITHM,
            $password,
            $salt,
            PBKDF2_ITERATIONS,
            PBKDF2_HASH_BYTES,
            true // Raw output
        ));
}

function validate_password($password, $good_hash)
{
    $params = explode(":", $good_hash);
    if(count($params) < HASH_SECTIONS)
       return false; // Invalid hash format
       
    $pbkdf2 = base64_decode($params[HASH_PBKDF2_INDEX]);
    
    // Compare hashes in constant time to prevent timing attacks
    return slow_equals(
        $pbkdf2,
        pbkdf2(
            $params[HASH_ALGORITHM_INDEX],
            $password,
            $params[HASH_SALT_INDEX],
            (int)$params[HASH_ITERATION_INDEX],
            strlen($pbkdf2), // Match key length to the stored hash length
            true // Raw output
        )
    );
}

// Compares two strings $a and $b in length-constant time.
function slow_equals($a, $b)
{
    $diff = strlen($a) ^ strlen($b);
    for($i = 0; $i < strlen($a) && $i < strlen($b); $i++)
    {
        $diff |= ord($a[$i]) ^ ord($b[$i]);
    }
    return $diff === 0; 
}

/*
 * PBKDF2 key derivation function as defined by RFC 2898.
 * $algorithm - The hash algorithm to use. Recommended: SHA256
 * $password - The password.
 * $salt - A salt that is unique to the password.
 * $count - Iteration count. Higher is better, but slower. Recommended: At least 1000.
 * $key_length - The length of the derived key in bytes.
 * $raw_output - If true, the key is returned in raw binary format. Hex encoded otherwise.
 * Returns: A $key_length-byte key derived from the password and salt.
 */
function pbkdf2($algorithm, $password, $salt, $count, $key_length, $raw_output = false)
{
    $algorithm = strtolower($algorithm);
    if(!in_array($algorithm, hash_algos(), true))
        die('PBKDF2 ERROR: Invalid hash algorithm.');
    if($count <= 0 || $key_length <= 0)
        die('PBKDF2 ERROR: Invalid parameters.');

    $hash_length = strlen(hash($algorithm, "", true));
    $block_count = ceil($key_length / $hash_length);

    $output = "";
    for($i = 1; $i <= $block_count; $i++) {
        // $i encoded as 4 bytes, big endian.
        $last = $salt . pack("N", $i);
        // First iteration
        $last = $xorsum = hash_hmac($algorithm, $last, $password, true);
        // Perform the other $count - 1 iterations
        for ($j = 1; $j < $count; $j++) {
            $xorsum ^= ($last = hash_hmac($algorithm, $last, $password, true));
        }
        $output .= $xorsum;
    }

    if($raw_output)
        return substr($output, 0, $key_length);
    else
        return bin2hex(substr($output, 0, $key_length));
}

//

## Solutions
Usage Example

$myPassword = "SuperSecretPassword123!";
$generatedHash = create_hash($myPassword);

echo "PBKDF2 Generated Hash: " . $generatedHash . "\n";

// Verify a login attempt
$loginPassword = "SuperSecretPassword123!";
if (validate_password($loginPassword, $generatedHash)) {
    echo "PBKDF2 Password verification successful!\n";
} else {
    echo "PBKDF2 Password verification failed.\n";
}

    echo "PBKDF2 Password verification successful!\n"; // This will not be printed
} else {
    echo "PBKDF2 Password verification failed.\n";
}

?>

When using PBKDF2, it’s crucial to select a high iteration count (e.g., 1000 or more, depending on performance needs) and a strong hashing algorithm like SHA256.

The Importance of Random Salts

Salting is fundamental. A salt ensures that even if two users have the same password, their stored hashes will differ. This is vital for thwarting rainbow table attacks, where pre-computed hashes for common passwords are used to quickly crack stored hashes.

Using unique, randomly generated salts for each password is the most effective approach. Storing the salt alongside the hash in the database is necessary for verification. While using user-specific information like a User ID as a salt can be better than no salt, a truly random salt provides the strongest defense against pre-computation and makes it significantly harder for attackers to create targeted cracking tables.

Legacy Practices and Considerations

In older PHP versions (pre-5.5), or for compatibility with legacy systems, libraries like Phpass were popular. Phpass is a simple, one-file PHP class that implements various hashing methods, falling back to older algorithms like MD5 if necessary, but prioritizing stronger ones like bcrypt when available.

<?php
// Example using the Phpass library (if you need to support very old PHP or systems)
// You would typically include the PasswordHash.php file.

// Assuming PasswordHash class is available
require_once 'PasswordHash.php'; 

$passwordToHash = 'MyOldPassword';
$hasher = new PasswordHash(8, false); // Cost factor 8, portable false

$hashed = $hasher->HashPassword($passwordToHash);
echo "Phpass Hashed: " . $hashed . "\n";

// Verifying
$loginPassword = 'MyOldPassword';
if ($hasher->CheckPassword($loginPassword, $hashed)) {
    echo "Phpass Password verification successful!\n";
} else {
    echo "Phpass Password verification failed.\n";
}
?>

However, for any new development or where possible, migrating to PHP’s native password_hash() is strongly advised.

Server and Database Security: The Foundation

No matter how strong your password hashing is, it’s only one layer of security. The underlying server and database configurations must also be secure:

  • Server Ports: Change default ports for remote access (SSH, FTP) to deter automated scans.
  • Usernames: Avoid default or easily guessable administrative usernames like “admin” or “root.” Use sudo for elevated privileges on Unix-based systems.
  • Database Security:
    • Isolate your database server from your application server if feasible.
    • Grant your application’s database user only the necessary privileges.
    • Use a strong, unique password for the database user, separate from any server credentials.
  • Secure Transmission: Always use SSL/TLS to encrypt data transmitted between the client browser and the server, especially during login and registration.

Final Thoughts on Security

Password security is an ongoing effort. While algorithms like bcrypt and scrypt offer robust protection, always stay informed about emerging threats and best practices. Regular security audits and testing of your application’s defenses are crucial. Remember, even the strongest security measures are only as good as their implementation and the security of the systems they protect.
