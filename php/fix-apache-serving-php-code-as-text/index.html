“Fix Apache Serving PHP Code as Text Instead of Executing It”

Encountering a situation where your web browser renders raw PHP script content instead of the processed output is a common frustration when configuring Apache web servers. This indicates that the PHP interpreter module is either not loaded, not properly configured to handle .php files, or is being overridden by another setting.

This detailed breakdown gathers various solutions that users have successfully employed across different Linux distributions and Apache versions to ensure PHP scripts execute server-side.

Core Configuration Adjustments for PHP Execution

The fundamental problem often lies in instructing Apache how to treat files ending with the .php extension. Several configuration directives address this mapping.

Method 1: Enabling PHP Module via a2enmod (Debian/Ubuntu Specific)

On systems using the Apache utilities like a2enmod (e.g., Debian/Ubuntu), ensure the necessary PHP module is both installed and enabled.

For environments using PHP 7.0 or similar versions:

# Install PHP and the Apache module package
sudo apt-get install php libapache2-mod-php

# Enable the required MPM and PHP modules
sudo a2enmod mpm_prefork && sudo a2enmod php7.0

# Apply changes
sudo service apache2 restart

If you are on a system where PHP versions conflict (e.g., seeing multiple versions listed via yum list installed | grep 'php' on CentOS), removing the conflicting version and restarting Apache may be necessary, as suggested in one scenario.

Method 2: Explicitly Setting the Handler in Configuration Files

If module enabling doesn’t suffice, you might need to manually tell Apache which handler to use for PHP files, often by editing apache2.conf or httpd.conf.

A common fix involves adding a <FilesMatch> block to define the PHP handler:

<FilesMatch "\.php$">
    SetHandler application/x-httpd-php
</FilesMatch>

This can be placed at the bottom of /etc/apache2/apache2.conf or /etc/httpd/conf/httpd.conf. Remember to restart the service afterward: sudo service apache2 restart or sudo service httpd restart.

Alternative for PHP 5/older setups (Uncommenting the LoadModule):

If the module is installed but commented out in your configuration (e.g., /etc/apache2/httpd.conf):

#LoadModule php5_module libexec/apache2/libphp5.so  <-- Original commented line
LoadModule php5_module libexec/apache2/libphp5.so   <-- Ensure this is active

Method 3: Utilizing AddType within <IfModule mime_module>

For Apache 2.4 and newer installations, adding the necessary AddType directive within the mime_module block ensures proper content type declaration for .php files.

Locate the configuration block (often in httpd.conf or a dedicated mime configuration file) and insert:

<IfModule mime_module>
    # ... existing directives ...
    AddType application/x-httpd-php .php
    AddHandler application/x-httpd-php .php
    # ... other directives ...
</IfModule>

Method 4: Addressing Module Version Conflicts (e.g., PHP 7 vs. PHP 8 on CentOS)

When upgrading PHP versions (e.g., to PHP 8 on CentOS 7 with Apache 2), configuration files might still reference the old module name (e.g., mod_php7.c).

You must search through configuration directories like /etc/httpd/conf.d/ for references to older modules and update them to the generic or new version:

Change this:

<IfModule mod_php7.c>
    # ... settings ...
</IfModule>

To this:

<IfModule mod_php.c>
    # ... settings ...
</IfModule>

Restarting Apache applies these registry updates.

Method 5: Disabling Conflicting Modules (e.g., suphp or Event MPM)

If you are using a specific module handler like suphp, it might actively suppress PHP execution handled by the standard mod_php. Deactivating the conflicting module can solve the issue.

For example, disabling suphp:

sudo a2dismod suphp
sudo service apache2 restart

In some cases, the multi-processing module (MPM) needs to be set to prefork for PHP modules to load correctly, especially with older PHP versions or specific configurations:

sudo a2dismod mpm_event && sudo a2enmod mpm_prefork && sudo service apache2 restart

Environmental and Access Issues

Sometimes the server configuration is correct, but how you are accessing the file or what environment you are running in causes the display issue.

Method 6: Correct URL Access Protocol

If you are testing locally, ensure you are accessing files via http://localhost/... and not directly via the file system protocol file:///.... Browsers restrict direct file access, and running PHP scripts requires the web server to process them.

Incorrect Access Example: file:///Applications/MAMP/htdocs/form/form.html

Correct Access Example: http://localhost:8080/form/form.html (If your MAMP/XAMPP runs on port 8080)

If using XAMPP, always run the control panel as an administrator to avoid permission issues that might prevent Apache from binding correctly.

Method 7: Checking File Syntax and Access Location

If only a single PHP file exhibits this behavior, the issue might be minimal:

  1. Missing Opening Tag: Ensure the file starts with <?php. If it starts with just ?php (missing <), Apache treats the content as plain text. 
    <?php
phpinfo();
?>
  2. Misplaced .htaccess Directives: A misconfigured .htaccess file, particularly those controlling URL rewriting (RewriteCond/RewriteRule), can inadvertently block PHP execution handlers. Try temporarily removing or renaming .htaccess to isolate this cause.
  3. User Directory Configuration: If using user home directories (like ~/public_html), check the configuration file for mod_userdir (e.g., /etc/apache2/mods-enabled/php5.conf). It might contain directives explicitly disabling PHP execution in user directories, which need commenting out.

Method 8: Utilizing PHP-FPM (For Newer Setups or Specific Distributions)

On modern systems (like CentOS 8+) or when using newer PHP versions (like PHP 7.2+), the setup often relies on PHP-FPM managed by Apache via FastCGI.

If standard module loading fails, installing and enabling the FPM service resolves the issue:

# For CentOS/RHEL systems
sudo yum module install php:7.2 
# Enable and start FPM service
systemctl enable --now php-fpm

# Enable necessary Apache modules for proxying FPM requests
sudo a2enmod actions fastcgi alias proxy_fcgi 
sudo service httpd restart

FAQs on Fix Apache Serving PHP Code as Text Instead of Executing It

Q: How do I check if the PHP module is loaded in Apache

ANS: On Debian/Ubuntu systems, use apache2ctl -M | grep php. On CentOS/RHEL, check loaded modules with httpd -M | grep php. Look for entries like php7_module or similar indicators.

Q: Should I use AddHandler or AddType for PHP files

ANS: Both directives are often used together or interchangeably depending on the Apache version and configuration style. AddType sets the MIME type, while SetHandler (often within <FilesMatch>) explicitly forces Apache to use a specific handler like application/x-httpd-php.

Q: I am getting an error about libphp.so missing in Termux

ANS: If using Termux on Android, this usually means the shared object file path is incorrect in httpd.conf. You may need to locate the correct path for libphp.so using tools like apt-file search and then create a symbolic link (ln -s) to where Apache expects the module.

Q: What is the role of MPM in PHP execution

ANS: The Multi-Processing Module (MPM) dictates how Apache handles connections. The mpm_prefork module is generally required for older PHP versions or configurations that use threaded modules, as it runs each process separately, whereas mpm_event is more modern but sometimes conflicts if not properly configured with PHP-FPM.
